---
title: Enterprise encrypted backup and recovery
description: Configure commercial PostgreSQL backups, authenticate recovery artifacts, and rehearse an isolated restore with retained keys.
---

The commercial `backups` module provides `mercato-backup`, a standalone PostgreSQL recovery command that works without application bootstrap. `mercato backups` is the application convenience wrapper; use the standalone command for JSON output or recovery when the original application is unavailable.

## Provision the operator environment

Use the commercially licensed Enterprise package, Node 24 or later, and matching PostgreSQL 16, 17 or 18 client/server majors. Enable `OM_ENABLE_ENTERPRISE_MODULES` and `OM_ENABLE_ENTERPRISE_MODULES_BACKUPS`. An operator with the required commercial rights must also set `OM_ENTERPRISE_COMMERCIAL_RIGHTS_ATTESTED=true`; these settings are capability/rights attestations, not a license purchase or a runtime license-key validator.

Set `OM_BACKUP_BINARIES_DIR` to an operator-controlled directory containing `pg_dump`, `pg_restore` and `psql`. Configure named libpq services in a private `PGSERVICEFILE` and credentials in a private `PGPASSFILE` (both owner-only, mode 0600). There is no `DATABASE_URL` fallback and passwords never belong in command arguments. Remote connections require verified TLS; plaintext connections are limited to loopback or local sockets.

Provision private output/workspace directories with mode 0700. The workspace stores sensitive run identities and temporary recovery files. Keep it on an appropriately sized protected volume. Stop application replicas, workers, schedulers, integrations and other writers before a protected rotation/recovery drill. A quiesced backup conservatively examines the whole cluster transaction horizon: unrelated writers can cause refusal.

For an application wrapper, enable the module before running the normal generation/build workflow. `mercato backups labels --output /srv/recovery/private/labels.json` exports metadata labels without opening a database. The standalone create command accepts that file through `--labels-file` and otherwise uses table names.

## Configure without exposing secrets

Inject credentials through the deployment secret manager. These examples configure paths and capability flags only; do not paste passwords, archive identities or application keys into shell history:

```sh
export OM_ENABLE_ENTERPRISE_MODULES=true
export OM_ENABLE_ENTERPRISE_MODULES_BACKUPS=true
export OM_ENTERPRISE_COMMERCIAL_RIGHTS_ATTESTED=true
export OM_BACKUP_BINARIES_DIR=/usr/lib/postgresql/16/bin
export PGSERVICEFILE=/srv/recovery/private/pg_service.conf
export PGPASSFILE=/srv/recovery/private/pgpass
export OM_BACKUP_REQUIRE_ENCRYPTION=true
```

Set the rights attestation only for a version you are licensed to use. Provision service entries `source` and `scratch` with distinct database identities; `scratch` must never point at the source. Restrict custody files to their owner and keep application-key escrow separate from the encrypted archive. The examples below use placeholder identifiers/digests/challenges returned by earlier commands; replace them with independently checked values.

## Create and verify

Put one to ten age X25519 public recipients in a recipients file. Include an independently controlled offline escrow recipient. Private identities and application DEKs belong in separate custody domains; an archive identity cannot decrypt tenant field ciphertext.

```sh
mercato-backup preflight --source-service source
mercato-backup create --source-service source --output /srv/recovery/output --workspace /srv/recovery/private --recipients-file /srv/recovery/private/recipients --quiesced --json
```

Retain the returned `backupId`, artifact path and `manifestSha256` through an independent trusted channel. A readable file or a successful decrypt does not authenticate the artifact's producer; age recipients are public. Verification requires the independently trusted manifest digest:

```sh
mercato-backup verify --artifact /srv/recovery/output/BACKUP_ID --trusted-manifest-sha256 TRUSTED_DIGEST --identity-file /srv/recovery/private/escrow.identity --json
```

Backup chunks, schema and index are encrypted independently of application field-encryption maps. The database values are copied as stored ciphertext, so historic application keys must remain retrievable. File names do not include entity names. Whole-database coverage does not include attachments/object-store files, Vault state, Redis, WAL or cluster-global roles. Unsupported external/foreign relation kinds refuse rather than imply complete coverage.

`--no-encryption` deliberately removes archive confidentiality. It requires typed `UNENCRYPTED` confirmation on an interactive terminal or `--confirm-unencrypted` for unattended use and displays an explicit warning. Set `OM_BACKUP_REQUIRE_ENCRYPTION=true` to forbid that option; invalid policy values fail closed.

## Resume safely

Interrupted commands report a non-zero status, the durable run identifier and a resume command. Reuse the same source, private workspace, output, recipients and chunk settings. A resume against another database/cluster refuses. Interrupted entities are restarted within the retained snapshot when possible or in a new epoch after process loss; completed entities are reused. DDL changes restart the affected artifact plan. Consistency labels never upgrade after a multi-snapshot boundary.

```sh
mercato-backup status /srv/recovery/output/.BACKUP_ID.partial --workspace /srv/recovery/private --json
```

The original protected workspace identity is sufficient for same-host resume. Before moving partial state to a new host, obtain `partialStateSha256` from status while the original trusted workspace identity is available and transport it independently. Artifact-only cross-host resume additionally requires `--trusted-partial-sha256` plus an escrow identity. This binds the run-key envelope, preparation and encrypted checkpoint bytes; public-recipient encryption alone does not authenticate a checkpoint. Preserve newly recovered workspace identities privately for later retries. If the original trusted identity and an independent partial-state digest are both lost, start a fresh backup.

Do not bypass live locks. Explicit `--take-over-lock RUN_ID` is an operator decision that can disrupt a live run. Automatic takeover is limited to stale local locks whose process is no longer alive.

## Isolated recovery

Provision an empty target from `template0`, with the matching PostgreSQL major, encoding/collation and required extensions. Keep it isolated from production queues, object stores, SMTP, callbacks and workers at the network/credential layer. No automatic promotion or production overwrite is provided.

```sh
mercato-backup preflight --target-service scratch --artifact /srv/recovery/output/BACKUP_ID --trusted-manifest-sha256 TRUSTED_DIGEST --identity-file /srv/recovery/private/escrow.identity --workspace /srv/recovery/private --json
mercato-backup restore --target-service scratch --confirm-target FRESH_CHALLENGE --artifact /srv/recovery/output/BACKUP_ID --trusted-manifest-sha256 TRUSTED_DIGEST --identity-file /srv/recovery/private/escrow.identity --workspace /srv/recovery/private --max-staging-bytes 1073741824 --json
```

The challenge binds the target and artifact and expires; obtain a fresh challenge on resume. Default `full` verification authenticates every artifact chunk before any target write; data is authenticated and hashed again while each load transaction runs. `--verify-mode streaming` saves the initial full pass but may discover a damaged later chunk after earlier chunks are loaded; the target stays quarantined. Chunk data and its journal marker commit together, so retry does not double-apply committed chunks. Reports are durable before journal cleanup, and a bound terminal receipt makes cleanup retryable.

An `exercise` adds declarative checks from an owner-only JSON checks file: `artifact-integrity`, `row-count`, `migration-fingerprint` and `encrypted-canary`. Checks are bounded, not SQL/shell execution. Encrypted-canary checks name an entity key, a whitelisted field, exact primary-key values, a custody handle and the expected SHA-256 of a synthetic canary. Supply the historic test DEKs through a separate owner-only `--canary-keys-file` mapping custody handles to base64 keys; do not put key bytes in arguments, artifacts or reports. The implementation uses the platform's authenticated decryption helper. Never substitute synthetic test custody for a deployment's real escrow acceptance.

## Rotation and retirement

Protected Enterprise rotation requires both a verified quiesced recovery artifact and the separate full data-correctness verifier. Core rotation remains available only through its explicit per-invocation unprotected-risk acknowledgment when Enterprise protection is unavailable. A failed protected operation never silently downgrades.

Retain old keys, backup recipients and pre-rotation artifacts until every consumer and historical recovery requirement has been independently inventoried and tested. Successful backup creation, restore, or scoped verification does not authorize deleting keys. Investigate failed or incomplete runs with writers stopped; perform any recovery cutover as a separate operator decision.

Native COPY transport receives one PostgreSQL protocol frame per row. The one-MiB stream buffer bounds queued frames, but does not split a single giant field. The measured memory envelope covers the documented synthetic fixtures and jobs settings; it does not certify arbitrary PostgreSQL one-GiB fields or eight simultaneous giant rows. Size rows and concurrency for the available memory, and run an isolated rehearsal on representative data before deployment.

Offline verification checks both custom-archive schema TOCs using the matching `pg_restore` binary without opening a database connection. Configure the private native-tool directory through `OM_BACKUP_BINARIES_DIR`. A bound restore resume authenticates the target journal and verifies only unfinished artifact chunks; completed COPY chunks stay bound to the trusted manifest in the same transaction as their data. Obtain a fresh challenge after each interrupted attempt. Success reports include consistency, per-entity expected/loaded rows, resume count, attempt phase timings, FK and recovery-check results; `promotionReady` remains false. Failed validations produce a separate durable quarantine report and retain the restore journal for repair/retry.

Quiesced keyset resume reuses a committed prefix only after authenticating every retained ciphertext file and re-proving the exact source database, catalog and continuous PostgreSQL postmaster lifetime. It starts after the encrypted last key, keeps contiguous chunk sequences and independently checks retained rows plus the remaining snapshot count. Restarting/replacing PostgreSQL invalidates that lifetime proof and refuses partial-backup reuse; start a fresh backup. Restore source-collision checks compare the stable physical origin and database OID, so a server restart cannot make an old archive safe to restore into its source database.

Sequence recovery compares the captured counter state with the integer values actually restored, using MAX for ascending and MIN for descending allocation while preserving non-unit increments and bigint precision. Empty sequences keep their original is_called state. All plans are validated before nontransactional setval calls; an interrupted apply can be replayed. Owned cyclic sequences and ownership of non-integer/domain columns are refused before export instead of applying lexical or ambiguous counter ordering.

Status exposes an owner-private, unencrypted aggregate checkpoint without entity names. These display counts are advisory and never authorize resume. Providing a recovery identity or the original workspace enables decrypted per-entity status. Status and checkpoint export do not repair/truncate a torn journal; repair belongs to an explicitly resumed writer. Preflight accepts --operation create, restore or exercise; its database/baseline checks are read-only. Generic command reports use exclusive private paths. Resume derives its original encryption/recipient/chunk settings from authenticated preparation unless an explicit compatible option is provided.


## Rehearse recovery before relying on it

Use a disposable, network-isolated environment and representative synthetic records, including encrypted scalar fields, custom documents and sequences. Do not run a rehearsal against a production target.

1. Create and verify an encrypted artifact as above, retaining its trusted digest independently. Confirm command exit status and the returned consistency label; an interrupted or multi-snapshot run is not a quiesced recovery point.
2. Provision a fresh empty scratch target and obtain its fresh challenge through `preflight --operation exercise`. Prepare an owner-only checks file. A minimal integrity/migration example is:

   ```json
   [{ "type": "artifact-integrity" }, { "type": "migration-fingerprint" }]
   ```

3. Run the restore exercise, using that fresh challenge and a new private report path:

   ```sh
   mercato-backup preflight --operation exercise --target-service scratch --artifact /srv/recovery/output/BACKUP_ID --trusted-manifest-sha256 TRUSTED_DIGEST --identity-file /srv/recovery/private/escrow.identity --workspace /srv/recovery/private --json
   mercato-backup exercise --target-service scratch --confirm-target FRESH_CHALLENGE --artifact /srv/recovery/output/BACKUP_ID --trusted-manifest-sha256 TRUSTED_DIGEST --identity-file /srv/recovery/private/escrow.identity --workspace /srv/recovery/private --checks-file /srv/recovery/private/checks.json --report /srv/recovery/private/exercise-report.json --json
   ```

4. Inspect the durable report, loaded counts, sequence allocation and application-level behavior against retained key custody. The minimal checks above do not exercise application-key recovery: add encrypted-canary checks and their separate `--canary-keys-file` to establish that part of the drill. `keyRecovery: not-tested` is not a passing key-recovery rehearsal. `promotionReady` remains false even after successful checks.
5. In a separate disposable drill, interrupt a run and use its explicit resume command and fresh target challenge; check that committed chunks are not duplicated. Test a deliberately damaged copy of an artifact and confirm verification refuses. Preserve the original artifact and trusted digest unchanged.
6. Record the tested application version, PostgreSQL versions, consistency, elapsed time and outcomes in a small sanitized operator report. Keep backup files, dumps, database volumes, private workspaces, raw logs and keys out of GitHub issues, PR comments and attachments. Share only redacted aggregate reports and output screenshots. Delete disposable targets and test custody only after the rehearsal is reviewed; production retention remains a separate policy decision.

No published throughput or memory guarantee applies to arbitrary deployments. Rehearse with your actual row sizes, extensions, concurrency and available disk; successful archive verification alone does not prove an application can recover.
