The deals workspace delivers kanban-style pipeline management alongside structured deal records. Grant `customers.deals.view` for read access and `customers.deals.manage` to let operators create, update, and move opportunities between stages.

![Deals list view](/screenshots/open-mercato-deals-listing.png)

## Track pipeline performance

- **List view** under **Customers → Deals** offers a sortable table with stage, probability, expected close, linked people and companies, and last update. Filters help sales leaders zero in on specific segments or owners.
- **Export** triggers a CSV of the current slice so pipeline reviews can happen offline. Every column maps to the deal entity exposed by `/api/customers/deals`.
- **Inline actions** open the deal, duplicate it, or jump straight to activity logging.

![Sales pipeline board](/screenshots/open-mercato-sales-pipeline.png)

## Kanban pipeline board

- **Sales pipeline** presents stages as draggable columns. Drag deals between stages to update status instantly; undo prompts appear after each change to make corrections painless.
- **Stage configuration** pulls from the dictionary under **Customers → Configuration → Deal stages**. Each stage can expose colour coding to match the board headers and provide visual cues.
- **Lane metrics** show deal counts per stage, helping teams spot bottlenecks without leaving the board.

## Create and edit deals

![Create deal form](/screenshots/open-mercato-create-deal.png)

- **Deal form** captures title, status, pipeline stage, value, currency, probability, and expected close date. Dictionaries power dropdowns, and custom fields appear in the panel on the right.
- **Associations** allow linking people and companies while creating or editing a deal. Search surfaces lifecycle badges so sellers can validate the right contact in seconds.
- **Undo support** keeps edits safe—each save operation includes an undo toast with `Undo` action.

![Deal summary view](/screenshots/open-mercato-log-deal-activity.png)

## Configure terminal deal statuses

Open **Settings → Customers → Deal settings** (`/backend/config/customers/deals`) to configure which status values mean won, lost, or closed without an outcome. Reading the vocabulary requires `customers.deals.view`; saving or resetting it requires `customers.deals.manage`. The vocabulary applies to the whole tenant, including its organizations. Saving or resetting requires an unrestricted tenant-wide `customers.deals.manage` grant. Managers whose grant covers only selected organizations receive HTTP 403 before any tenant-wide impact count is calculated.

Enter comma-separated aliases in each group. Empty entries and trailing commas are ignored. Enclose aliases containing commas in double quotes (for example, `"signed, approved"`). The first value is the preferred spelling for new writes; the remaining values recognize alternative spellings. For example:

```json
{
  "won": ["signed", "win", "won"],
  "lost": ["declined", "lost", "loose"],
  "closed": ["archived", "closed"]
}
```

Each group accepts 1–20 distinct values, each 1–50 characters after trimming. Groups cannot overlap, and `open` and `in_progress` remain active statuses. Built-in aliases retain their meaning: `win`/`won` always mean won, `lost`/`loose` always mean lost, and `closed` remains terminal, even when omitted from a custom group. Dictionary labels remain independently localizable; changing a label does not change its outcome.

The list, Kanban, map, aggregates, closure controls, and AI deal updates use the same vocabulary. Selecting a won or lost alias matches every alias of that outcome. Selecting a closed alias matches all terminal outcomes. Unknown values remain active. Existing deals are not rewritten when settings change. If removing, reassigning or adding aliases changes the classification of persisted deals, the editor shows the number affected and requires confirmation. Reset uses the same confirmation flow. Cancel leaves the setting untouched. If the candidate, version or affected population changes before confirmation, the server requires a fresh confirmation. Stored statuses and explicit closure outcomes remain unchanged. Closing by a won/lost status also records the closure outcome and selects a matching terminal pipeline stage when available; reopening clears closure details.

**Save** creates a tenant override. **Reset** removes the override and uses the environment default, or the built-in vocabulary when no valid environment default exists. Settings changes support undo. A conflict message means someone saved a newer version; reload before saving again.

Operators can set a server-side default for tenants without an override:

```dotenv
OM_CUSTOMERS_DEAL_STATUS_VOCABULARY='{"won":["signed","win","won"],"lost":["declined","lost","loose"],"closed":["archived","closed"]}'
```

Resolution order is the tenant's `customers/dealStatusVocabulary` module configuration, then `OM_CUSTOMERS_DEAL_STATUS_VOCABULARY`, then the built-in groups `win`/`won`, `lost`/`loose`, and `closed`. Instance module-configuration rows are ignored. Invalid tenant configuration falls back to the environment; invalid environment JSON or values fall back to built-ins. Database failures surface as errors. Restart the server after changing its environment.

API clients can read or update `/api/customers/settings/deal-status-vocabulary`. GET returns `{ vocabulary, source, updatedAt }`, where `source` is `tenant`, `env`, or `default`. PUT accepts `{ "vocabulary": { ... }, "reclassificationConfirmation": { "fingerprint": "..." } }`, with confirmation optional for changes that affect no existing deal classification. `{ "vocabulary": null }` resets the tenant override. Send the latest `updatedAt` in `x-om-ext-optimistic-lock-expected-updated-at` when updating. A stale version returns the existing optimistic-lock HTTP 409 before impact calculation; reset preserves a record version for subsequent updates.

When persisted deal classifications would change, save/reset returns HTTP 409 with `code: "deal_status_reclassification_confirmation_required"` and `impact: { affectedDeals, fingerprint }`, without changing the setting or exposing deal IDs/titles. After showing the count and obtaining explicit confirmation, retry the same candidate with `reclassificationConfirmation: { fingerprint }` and the same current version header. A stale fingerprint returns refreshed impact. A fingerprint is a freshness token; permissions are checked on every attempt.

Undo runs the same authorization, version and impact checks against current persisted deals, including deals created after the original save. If undo returns the confirmation response, API clients can explicitly confirm and retry the existing audit undo request with the returned fingerprint in `x-om-customers-deal-status-reclassification-confirmation`. The undo request body remains unchanged. A normal editor reset can also reverse an override through the shared confirmation dialog. Scope comes from the authenticated tenant.

## Collaborate on deal timelines

- **Highlights** display the key metrics at the top of the deal page: stage, probability, value, and expected close. Use the inline `Edit deal details` action to tweak them.
- **Notes** let teams leave free-form updates. Keyboard shortcuts (`Cmd/Ctrl + Enter` to submit, `Escape` to close) mirror the rest of the app.

![Add note dialog on deal](/screenshots/open-mercato-add-deal-comment.png)

- **Activities** track structured interactions tied to the deal. Logging a call or meeting automatically links the selected people and company, reinforcing a full-funnel timeline across entities.
- **Log activity** dialog honours dictionary-driven activity types and custom fields, ensuring consistent reporting downstream.

## Related permissions

- **Deals**: `customers.deals.view` (read) and `customers.deals.manage` (create/update).
- **Activities**: `customers.activities.view` for the timeline plus `customers.activities.manage` to log or edit entries.
- **Widgets**: customer dashboards expose the `Sales pipeline` widget to anyone with `customers.widgets.new-customers` or custom dashboard privileges.
