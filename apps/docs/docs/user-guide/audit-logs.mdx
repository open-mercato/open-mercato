The **Security → Audit Logs** page surfaces every command executed through the new undo-aware pipeline.

- **Action Log** lists create, update, and delete events with the actor, scoped tenant/organization, and when the change happened. If the last action is undoable the banner exposes an **Undo last action** button that replays the command’s `undo` handler.
- **Access Log** records read events (for example when a user opens a detail view) so administrators can inspect who looked at sensitive resources.
- Use the toggle to filter for undoable entries and the refresh button to pull the latest records without leaving the page.
- The Access Log is paginated (50 records per page by default) so you can page through longer histories without exporting data.

![Audit log timeline showing undoable entries](/screenshots/open-mercato-action-logs.png)

Undo support is currently available for directory tenants/organizations, auth users/roles, and example todos. Additional modules can opt-in by implementing command handlers with `undo` snapshots.

## Undo and Diffs

- Clicking **Undo last action** triggers the command bus with the stored `undoToken`. The UI only enables this button for the most recent, undoable entry to guarantee replay order.
- After a successful undo the entry is marked as **undone** and its token is cleared, preventing accidental double-undos. To "redo" the operation, simply run the original action again (for example, resubmit the edit form); it will generate a fresh command entry with a new undo token.
- Selecting any row opens the operation drawer, which renders before/after snapshots and a diff of the changed fields. These values come from the command’s `snapshotBefore`, `snapshotAfter`, and `changes` metadata.

![Operation drawer highlighting changed fields and snapshots](/screenshots/open-mercato-operation-details.png)

### Banner auto-dismiss timeout

The Undo banner auto-dismisses **10 seconds** after the action is recorded. The timer pauses while an undo request is in flight so a slow API does not collapse the banner mid-click. Override the default by setting `NEXT_PUBLIC_OM_UNDO_BANNER_TIMEOUT_MS` (in milliseconds) at build time:

```env
# .env (or .env.local)
NEXT_PUBLIC_OM_UNDO_BANNER_TIMEOUT_MS=15000
```

Non-numeric, zero, or negative values fall back to the 10s default. The variable is read at build time because it is a `NEXT_PUBLIC_*` env, so you must rebuild the app after changing it.

## Retention

Access logs are retained for **90 days** by default. You may increase this period with `AUDIT_LOGS_RETENTION_DAYS`; values below 90 days are raised to the minimum. `AUDIT_LOGS_RETENTION_BATCH_SIZE` controls how many rows one worker job deletes and defaults to 1000.

Cleanup runs outside the request path through the queue worker registered by the module. If the scheduler module is not enabled, logging continues and an operator can run cleanup manually:

```bash
yarn mercato audit_logs access-retention:prune --dry-run --tenant <uuid> --org <uuid>
yarn mercato audit_logs access-retention:prune --tenant <uuid> --org <uuid>
```

Use `--class core` or `--class non_core` for class-specific runs, `--retention-days` to increase the period, and `--batch` to adjust the bounded batch size. A global run requires the explicit `--all-scopes` flag.

CRUD access-log writes are blocking by default: a successful response is not returned until the log insert succeeds. `OM_CRUD_ACCESS_LOG_MODE=async` is available for low-assurance deployments that explicitly accept possible log loss on process failure.

The Access Log page shows the normalized request context, including method, path, request and session identifiers, result, user agent, and source IP when trusted proxy depth is configured. The source IP uses the same `RATE_LIMIT_TRUST_PROXY_DEPTH` safety rule as rate limiting; forwarded headers are ignored by default.

Access records can be downloaded from `GET /api/audit_logs/audit-logs/access/export`. The CSV export applies the same tenant, organization and actor scope as the Access Log list.

## Signed evidence bundles

For an offline evidence package, use the scoped JSON export:

```bash
export OM_AUDIT_EVIDENCE_HMAC_KEY="<secret-from-your-secret-manager>"
yarn mercato audit_logs evidence:export --tenant <uuid> --org <uuid> --out ./evidence/audit.json
yarn mercato audit_logs evidence:verify --file ./evidence/audit.json
```

The file combines action and access records, gives each record a correlation ID, and protects their content and order with an HMAC-SHA256 chain and bundle signature. If Agent Orchestrator is enabled, its runs, proposals, spans, tool calls and guardrail results are added automatically.

The JSON can contain sensitive data. It is written with owner-only permissions but is not encrypted by the export command. Store it in an encrypted, access-controlled location. The signature detects changes made after export; it does not prove that source database rows were unchanged before the export was created.

## Removing credentials from older action logs

New action logs filter passwords, tokens, API keys, private keys, recovery codes and similar credential fields before they reach the database. The database migration removes these values from plaintext historical JSON fields.

If tenant data encryption has been used, run the application-level cleanup after deploying the migration. It decrypts each affected field with the configured KMS or Vault key, replaces credentials with `[REDACTED]`, and encrypts the sanitized value again:

```bash
yarn mercato audit_logs sensitive-data:redact --dry-run --batch 250
yarn mercato audit_logs sensitive-data:redact --batch 250
```

Use `--tenant <uuid>` and `--org <uuid>` to limit the scan. The command uses bounded, keyset-ordered batches and can be repeated safely. It prints row identifiers and counts only, never stored payloads. If an encrypted row cannot be decrypted or encrypted again, that row is left unchanged and the command exits with an error. Restore access to the configured KMS or Vault keys before retrying.
