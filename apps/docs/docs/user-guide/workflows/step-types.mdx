# Step Types

Steps are the building blocks of workflows. Each step type serves a specific purpose in orchestrating your business process. This guide explains when and how to use each type.

## Step Types Overview

| Step Type | Purpose | Execution | When to Use |
|-----------|---------|-----------|-------------|
| **START** | Entry point | Auto-advances immediately | Beginning of every workflow |
| **END** | Exit point | Completes the workflow | End of every workflow path |
| **USER_TASK** | Human decision/input | Waits for user action | Approvals, reviews, manual data entry |
| **AUTOMATED** | Automated processing | Executes activities, then advances | API calls, calculations, data updates |
| **WAIT_FOR_SIGNAL** | External trigger | Waits for signal from outside | Payment confirmations, webhook callbacks |
| **WAIT_FOR_CONDITION** | Wait on the run's own data | Waits until a condition over the context holds | "Wait until the grid approval lands", "wait until the balance is paid" |
| **IF_ELSE** | Two-way decision | Advances immediately, routes on conditions | Yes/no gates: qualified, approved, in budget |
| **SWITCH** | Multi-way decision | Advances immediately, routes on one field's value | Routing on a status, a plan tier, a financing choice |
| **SUB_WORKFLOW** | Call another workflow | Executes child workflow | Reusable processes, modular workflows |

:::tip Changing your mind
A step's type is not permanent. The step inspector's **Change type…** control converts a step in place, keeping its id, name, position and wiring; configuration the new type cannot execute is parked in a visible *Unmapped configuration* drawer rather than deleted, so converting back restores it. START and END are the exceptions — they define the shape of the workflow and cannot be converted.
:::

## START

The START step is the entry point for every workflow. When you start a workflow instance, execution begins here.

**Characteristics:**
- Every workflow must have exactly one START step
- Automatically advances to the next step (no waiting)
- Cannot have incoming transitions (it's the beginning)
- Must have at least one outgoing transition

**Use Cases:**
- Initialize workflow context with input data
- Mark the beginning of the process
- Route to the first real step

**Example:**
```json
{
  "stepId": "start",
  "stepName": "Start",
  "stepType": "START"
}
```

## END

The END step marks completion of the workflow. When execution reaches an END step, the workflow instance is marked as COMPLETED.

**Characteristics:**
- Workflows must have at least one END step
- Can have multiple END steps for different outcomes (approved, rejected, cancelled)
- Cannot have outgoing transitions (it's the end)
- Automatically sets workflow status to COMPLETED

**Use Cases:**
- Mark successful completion
- Mark failure or cancellation
- Differentiate between multiple outcomes

**Example:**
```json
{
  "stepId": "end-approved",
  "stepName": "Request Approved",
  "stepType": "END"
}
```

## USER_TASK

USER_TASK steps require human intervention—someone needs to review data, make a decision, or provide input.

**Characteristics:**
- Creates a task that appears in the [Work Inbox](./user-tasks#the-work-inbox)
- Workflow pauses at this step until the task is completed
- Can be assigned to a user, a role queue, a context value, or a business rule
- Supports custom forms for data collection, and decision buttons bound to outgoing routes
- Tracks a deadline, reminders before it, and what happens when it passes

**Configuration:**

### Assignment

Assign tasks to specific users or roles:

- **Assigned to User**: Direct assignment to a single user by user ID
- **Assigned to Roles**: Any user with the specified role(s) can claim and complete the task
- **Assignment Rules**: Dynamic assignment based on workflow context (e.g., assign to the requester's manager)

### Form Schema

Define fields users must fill when completing the task:

```json
{
  "userTaskConfig": {
    "formSchema": [
      {
        "fieldName": "decision",
        "fieldType": "select",
        "label": "Decision",
        "required": true,
        "options": ["approve", "reject"]
      },
      {
        "fieldName": "comments",
        "fieldType": "textarea",
        "label": "Comments",
        "required": false
      }
    ]
  }
}
```

### Deadline, reminders and breach

- **Deadline**: an ISO 8601 duration from task creation (`P2D`, `PT30M`) that becomes the task's due date
- **Reminders**: offsets before the deadline, each firing a notification to whoever the task is offered to
- **When the deadline passes**: notify, reassign to a user or role, or follow a route out of the step

The older `escalationRules` field is still accepted for existing definitions but nothing executes it — see [Deadlines, reminders and breach](./user-tasks#when).

### Decisions

Bind a button to each outgoing route so the assignee's choice is what routes the run, instead of a free-text field the next step has to interpret. See [Decisions](./user-tasks#decisions).

**Use Cases:**
- Approval workflows (purchase orders, expense reports)
- Review processes (content review, code review)
- Data entry (capturing information not available in the system)
- Decision points (route based on human judgment)

[**Learn more about user tasks →**](./user-tasks)

## AUTOMATED

AUTOMATED steps perform automatic processing without human intervention. They execute activities (like calling APIs or sending emails) and automatically advance when complete.

**Characteristics:**
- Executes immediately when reached
- Can run activities during the step or on outgoing transitions
- Automatically advances after activities complete
- Supports async execution for long-running activities

**Configuration:**

Activities can be configured either on the step itself or on outgoing transitions:

```json
{
  "stepId": "process-payment",
  "stepName": "Process Payment",
  "stepType": "AUTOMATED",
  "activities": [
    {
      "activityId": "call-payment-gateway",
      "activityName": "Call Payment Gateway",
      "activityType": "CALL_API",
      "config": {
        "url": "https://payment-gateway.example.com/charge",
        "method": "POST",
        "body": {
          "amount": "{{context.amount}}",
          "currency": "USD"
        }
      }
    }
  ]
}
```

**Use Cases:**
- Call external APIs (payment processing, inventory checks)
- Send notifications (email, SMS)
- Update database records
- Perform calculations or transformations
- Emit domain events

[**Learn more about activities →**](./activities)

## WAIT_FOR_SIGNAL

WAIT_FOR_SIGNAL steps pause workflow execution until an external system sends a specific signal. This is useful for long-running processes that depend on events outside the workflow.

**Characteristics:**
- Workflow pauses at this step
- Waits for a signal with a matching name
- Merges signal payload into workflow context
- Automatically advances when signal is received
- Supports timeouts to avoid waiting indefinitely

**Configuration:**

```json
{
  "stepId": "wait-payment",
  "stepName": "Wait for Payment Confirmation",
  "stepType": "WAIT_FOR_SIGNAL",
  "signalConfig": {
    "signalName": "payment-confirmed",
    "timeout": "7 days"
  }
}
```

**Sending Signals:**

External systems send signals via API:

```typescript
POST /api/workflows/instances/{instanceId}/signal
{
  "signalName": "payment-confirmed",
  "payload": {
    "transactionId": "txn_123",
    "paidAmount": 150.00
  }
}
```

The signal payload is merged into the workflow context, making it available to subsequent steps.

**Use Cases:**
- Wait for payment confirmation from payment gateway
- Wait for external approval from third-party system
- Wait for webhook callbacks (shipping updates, API responses)
- Coordinate with other workflows or systems

[**Learn more about signals →**](./signals)

## SUB_WORKFLOW

SUB_WORKFLOW steps call another workflow as a child process. This enables workflow reuse and modular design.

**Characteristics:**
- Starts a new workflow instance (child)
- Parent workflow waits for child to complete
- Can pass input context to child workflow
- Receives output context from child when it completes
- Supports timeouts to prevent indefinite waiting

**Configuration:**

```json
{
  "stepId": "sub-validate-customer",
  "stepName": "Validate Customer",
  "stepType": "SUB_WORKFLOW",
  "config": {
    "workflowId": "customer-validation-v1",
    "inputMapping": {
      "customerId": "{{context.customerId}}",
      "orderAmount": "{{context.totalAmount}}"
    },
    "timeout": "1 hour"
  }
}
```

**Output Handling:**

When the child workflow completes, its final context is merged into the parent workflow's context under a namespaced key.

**Use Cases:**
- Reusable validation processes
- Modular approval chains
- Multi-tenant processes (each tenant has their own workflow definition)
- Complex processes that benefit from decomposition

## WAIT_FOR_CONDITION

Pause the workflow until something becomes true about the run's own data — no external signal needed. Use it when the thing you are waiting for arrives as a context update rather than as a named event.

```json
{
  "stepId": "await_grid_approval",
  "stepName": "Await grid approval",
  "stepType": "WAIT_FOR_CONDITION",
  "config": {
    "condition": {
      "operator": "AND",
      "rules": [
        { "field": "gridApproval.status", "operator": "==", "value": "APPROVED" }
      ]
    },
    "timeout": "P30D",
    "onTimeout": "FAIL",
    "pollIntervalMs": 3600000
  }
}
```

**Parameters:**
- `condition` (**required**): the predicate over the run context, built with the same condition editor as transition conditions
- `timeout` (**required**): an ISO-8601 duration after which the wait gives up. It is mandatory on purpose — a condition that never becomes true must not be able to hang a run forever
- `onTimeout` (**required**): `FAIL` to fail the step when the deadline passes, or `CONTINUE` to carry on anyway
- `pollIntervalMs` (optional): how often to re-check as a backstop, between 5 seconds and 1 hour

The condition is re-checked whenever the instance's context is written, so in practice the workflow wakes as soon as the data lands; the poll is only a safety net for updates that arrive some other way.

## IF_ELSE and SWITCH

These two are **decision steps**. They do no work of their own — they advance immediately, and the decision is made by their outgoing routes, evaluated in priority order. That means everything you already know about [transitions](./transitions) applies: each route carries a condition, the routes are ordered, and the last one should be an unconditioned *otherwise* route.

- **IF_ELSE** is the two-way gate: one conditioned route plus an otherwise route.
- **SWITCH** routes on a single field, one route per value, plus an otherwise route.

```json
{
  "steps": [
    { "stepId": "qualify_gate", "stepName": "Qualified?", "stepType": "IF_ELSE" }
  ],
  "transitions": [
    {
      "transitionId": "qualified",
      "fromStepId": "qualify_gate",
      "toStepId": "contact_attempted",
      "trigger": "auto",
      "priority": 100,
      "transitionName": "Qualified",
      "condition": { "operator": "AND", "rules": [{ "field": "leadScore", "operator": ">", "value": 60 }] }
    },
    {
      "transitionId": "not_qualified",
      "fromStepId": "qualify_gate",
      "toStepId": "nurture_lead",
      "trigger": "auto",
      "priority": 0,
      "transitionName": "Otherwise"
    }
  ]
}
```

In the Studio these steps get a dedicated inspector: you edit the branches as a list of cases with their conditions, drag them to change which is tried first, and the editor warns you when a decision step has **no otherwise route** — that is the shape that silently stalls a run when nothing matches.

:::note Older engines refuse these definitions
`IF_ELSE`, `SWITCH` and `WAIT_FOR_CONDITION` were added after the first release. A definition that uses them is stamped with the engine version it needs, and an older engine refuses to start it rather than mis-executing a step type it does not understand.
:::

## Choosing the Right Step Type

```mermaid
graph TD
    A[Need a workflow step?] --> B{Human involved?}
    B -->|Yes| C[USER_TASK]
    B -->|No| D{Waiting for external event?}
    D -->|Yes| E[WAIT_FOR_SIGNAL]
    D -->|No| F{Calling another workflow?}
    F -->|Yes| G[SUB_WORKFLOW]
    F -->|No| H{Automated action?}
    H -->|Yes| I[AUTOMATED]
    H -->|No| J{Start or end?}
    J -->|Start| K[START]
    J -->|End| L[END]
```

**Quick Decision Guide:**

1. **Starting a workflow?** → Use START
2. **Ending a workflow?** → Use END
3. **Need human input or decision?** → Use USER_TASK
4. **Waiting for external system?** → Use WAIT_FOR_SIGNAL
5. **Calling another workflow?** → Use SUB_WORKFLOW
6. **Automated processing?** → Use AUTOMATED
