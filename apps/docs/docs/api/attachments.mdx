All examples assume the environment variables defined in [REST API Overview](./overview):

```bash
export BASE_URL="http://localhost:3000/api"
export API_KEY="<paste your API key secret here>"
export ORG_ID="<organization uuid in scope>"
export TENANT_ID="<tenant uuid in scope>"
export RECORD_ID="<entity record id you want to attach files to>"
```

- Pass `X-Api-Key: $API_KEY` on every request. API-key calls must always include `organizationId` and `tenantId` in payloads.
- Required features: `attachments.view` for read-only endpoints, `attachments.manage` for uploads, updates, transfers, partitions, and deletes.
- Custom fields can be written with either `cf_<slug>` keys or a `customFields` object. Multipart uploads accept a JSON string for `customFields`.

## OCR / text extraction

Open Mercato supports two text-extraction methods for attachments:

1. **LLM-based OCR** (recommended) – uses OpenAI's GPT-4o vision capabilities for images and PDFs
2. **Pure-JS extraction** – in-process fallback for plain text, PDFs, and DOCX files when LLM OCR is unavailable

### LLM-based OCR (images and PDFs)

**Environment Variables**

Configure LLM-based OCR with the following variables in your `.env`:

```bash
# Required for LLM-based OCR
OPENAI_API_KEY=your_openai_api_key_here

# Optional: OCR model selection (default: gpt-4o)
# Supported models: gpt-4o, gpt-4o-mini
OCR_MODEL=gpt-4o

# Optional: Custom prompt for text extraction
# OCR_DEFAULT_PROMPT="Extract all text content from this image..."

# Optional attachment defaults and limits
# OM_DEFAULT_ATTACHMENT_OCR_ENABLED=true
# OM_ATTACHMENT_MAX_UPLOAD_MB=25
# OM_ATTACHMENT_TENANT_QUOTA_MB=512
```

Attachment env naming follows the standard `OM_*` prefix. Legacy `OPENMERCATO_*` aliases are still read for backward compatibility, but new deployments should use the `OM_*` names.

**How it works**

- **Images** (PNG, JPG, GIF, BMP, WebP, TIFF): Sent directly to GPT-4o for text extraction
- **PDFs**: Parsed with `pdfjs-dist`; text-layer content is used directly when available, and scanned/image-only pages are rendered through the Node canvas backend before OCR
- **Processing**: Asynchronous – uploads return immediately, content is populated in the background
- **Model selection**: Per-partition model override available in partition settings UI
- **Extracted text**: Stored in `Attachment.content` field and shown in the metadata dialog
- **Security**: No `pdf2pic`, GraphicsMagick, Ghostscript, or external binaries are used in any extraction path
- **Fallback**: when LLM OCR is unavailable, plain text files are read directly, PDFs are parsed with `pdfjs-dist`, and DOCX files are parsed with `mammoth`

### Pure-JS extraction (plain text, PDF, DOCX)

No additional setup required — extraction runs in-process with no external binaries.

Supported formats and their extractors:

| Format | Extractor |
|--------|-----------|
| Plain text (`text/*`, `.txt`, `.md`, `.csv`, `.log`) | Direct UTF-8 read |
| PDF (`.pdf`) | `pdfjs-dist` — text layer content |
| Word document (`.docx`) | `mammoth` |

Formats **not** extracted (returned as no content): `.doc` (legacy binary Word), `.xlsx`, `.xls`, `.pptx`, `.ppt`, `.msg`, and other Office/Outlook formats. LLM-based OCR remains available for these files where the partition is configured with an OCR model.

### Configuration

- `OM_DEFAULT_ATTACHMENT_OCR_ENABLED=true|false` controls whether new partitions opt into OCR by default.
- `OM_ATTACHMENT_MAX_UPLOAD_MB=<number>` sets the global upload cap per file before field-specific limits are applied. Default: `25`.
- `OM_ATTACHMENT_TENANT_QUOTA_MB=<number>` sets the tenant-wide stored attachment quota. Default: `512`.
- Each partition has a `requiresOcr` flag; disable it to skip extraction for that partition.
- Partition-specific model selection is available in the partition settings UI for image/PDF OCR.

## Attachments per record

### List attachments — `GET /attachments?entityId=<id>&recordId=<id>`

**Feature:** `attachments.view`

Returns files assigned to a specific entity record, ordered newest first.

```bash
curl -X GET "$BASE_URL/attachments?entityId=catalog:catalog_product&recordId=$RECORD_ID" \
  -H "X-Api-Key: $API_KEY" \
  -H "Accept: application/json"
```

The payload includes `id`, `fileName`, `fileSize`, `createdAt`, `partitionCode`, `url`, `thumbnailUrl`, `tags`, and `assignments`.

Pagination is optional and opt-in: pass **both** `page` (minimum `1`) and `pageSize` (minimum `1`, maximum `100`) to page the result. When you do, the response adds `total`, `page`, `pageSize`, and `totalPages` alongside `items`; when you omit either one, every attachment for the record is returned without those fields. Paging is unclamped, exactly like the other list endpoints — a page past the end returns an empty `items` array and echoes back the page you asked for, so a loop that keeps requesting the next page while the current one is full terminates on its own. Use `totalPages` if you need to know where the list ends before you get there.

### Upload attachment — `POST /attachments` (multipart)

**Feature:** `attachments.manage`

Fields:

- `entityId` and `recordId` — required.
- `file` — required binary part.
- Optional: `fieldKey` (validates max size/extension + partition overrides from custom-field definitions), `partitionCode` override, `tags` (JSON string array), `assignments` (JSON string array of `{ type, id, href?, label? }`), `customFields` JSON map.

```bash
curl -X POST "$BASE_URL/attachments" \
  -H "X-Api-Key: $API_KEY" \
  -F "entityId=catalog:catalog_product" \
  -F "recordId=$RECORD_ID" \
  -F "file=@./hero.jpg" \
  -F "tags=[\"hero\",\"web\"]"
```

Response contains the stored item plus a prebuilt `thumbnailUrl` (`/api/attachments/image/{id}`).

Executable file types (`.exe`, `.js`, `.sh`, …) and active content — HTML, XHTML, XML and **SVG** — are rejected with `400`, whatever MIME type the client declares. SVG is not accepted on this route; see [Vector images from module code](#vector-images-from-module-code).

### Delete attachment — `DELETE /attachments?id=<uuid>`

**Feature:** `attachments.manage`

```bash
curl -X DELETE "$BASE_URL/attachments?id=$ATTACHMENT_ID" \
  -H "X-Api-Key: $API_KEY"
```

Deletes the record, purges cached thumbnails, and removes the stored asset.

## Attachment library

Use the library endpoints to browse or edit attachments across entities.

### Search library — `GET /attachments/library`

**Feature:** `attachments.view`

Query parameters: `page` (default `1`), `pageSize` (max `100`), `search` (file name substring), `partition`, `tags` (comma separated), `sortField` (`fileName`, `fileSize`, `createdAt`), `sortDir`.

```bash
curl -X GET "$BASE_URL/attachments/library?page=1&pageSize=20&tags=hero" \
  -H "X-Api-Key: $API_KEY"
```

Response includes paginated items, available partitions, and discovered tag list.

### Retrieve attachment — `GET /attachments/library/{id}`

**Feature:** `attachments.view`

Returns metadata for a single attachment: base fields, tags, assignments (enriched with labels/links when possible), partition label, and any custom field values.

### Update metadata — `PATCH /attachments/library/{id}`

**Feature:** `attachments.manage`

Body accepts `tags` (array), `assignments` (array of `{ type, id, href?, label? }`), plus optional custom-field keys (`cf_<slug>` or `customFields`). Returns the updated tags/assignments/custom fields.

### Delete attachment — `DELETE /attachments/library/{id}`

**Feature:** `attachments.manage`

Removes the attachment and its stored file.

## Transfer attachments between records

**Endpoint:** `POST /attachments/transfer`  
**Feature:** `attachments.manage`

Move multiple attachments within the same entity to a new record id.

```bash
curl -X POST "$BASE_URL/attachments/transfer" \
  -H "X-Api-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "entityId": "catalog:catalog_product",
    "attachmentIds": ["'$ATTACHMENT_ID'"],
    "fromRecordId": "old-record-id",
    "toRecordId": "new-record-id"
  }'
```

Assignments pointing at `fromRecordId` are rewritten to `toRecordId`.

## Storage partitions

Partition endpoints let you route uploads to different buckets or visibility tiers.

- List partitions — `GET /attachments/partitions` (`attachments.manage`)  
  Ensures default partitions exist and returns `code`, `title`, `description`, `isPublic`, `requiresOcr`, `envKey`.
- Create partition — `POST /attachments/partitions` (`attachments.manage`)  
  Body: `code`, `title`, optional `description`, `isPublic`, `requiresOcr`. Fails when the environment locks partition management (demo/onboarding).
- Update partition — `PUT /attachments/partitions` (`attachments.manage`)  
  Body: `id`, `code` (immutable), `title`, optional `description`, `isPublic`, `requiresOcr`.
- Delete partition — `DELETE /attachments/partitions?id=<uuid>` (`attachments.manage`)  
  Default partitions cannot be removed; partitions in use return `409`.

## Vector images from module code

Modules that need to store a vector image — a company logo, a brand mark — upload through the `attachmentService` DI contract rather than this REST API, and opt in per call:

```ts
const attachmentService = container.resolve('attachmentService') as AttachmentService
await attachmentService.createScoped({
  tenantId, organizationId, entityId, recordId, partitionCode,
  fileName: 'logo.svg',
  declaredMimeType: 'image/svg+xml',
  buffer,
  allowVectorImage: true,
})
```

With `allowVectorImage: true`, an `.svg` file (or an extension-less file declared or sniffed as `image/svg+xml`) is sanitised on the server with DOMPurify's SVG profile and only the sanitised document is stored. What a logo needs survives: `<style>` blocks (including the CDATA-wrapped ones design tools export), gradients, clip paths, masks, filters, `<use>` pointing at `#id` in the same document, `viewBox`/`preserveAspectRatio`, and embedded PNG/JPEG/GIF/WebP as base64 `data:` URIs on `<image>` or `<feImage>`. Comments, editor metadata and a plain DOCTYPE are dropped. Anything that would change what the file does or how it renders is **rejected rather than stripped** — the first such finding stops the check — with a machine-readable `code` in the error body:

| `code` | Status | Cause |
| --- | --- | --- |
| `vector_image_too_large` | 413 | over 1 MiB, before or after sanitising |
| `vector_image_malformed` | 400 | not UTF-8, not well-formed XML, or the root is not `<svg>` |
| `vector_image_entity_declaration` | 400 | a DTD declaration (`<!ENTITY>`, `<!ATTLIST>`, `<!ELEMENT>`, `<!NOTATION>`) or a DOCTYPE internal subset |
| `vector_image_too_complex` | 400 | over 4,000 markup tags or nodes, 2,000 elements, nesting deeper than 64, 64 attributes on one element or 6,000 in total, or over 10,000 units of render work (path, points and text length and filter primitives, weighted as measured in Chrome) once in-document references are expanded, more than 32 filter primitives, an `feMorphology` radius over 4 or an `feConvolveMatrix` — `<use>`, `href`s, and `url(#…)` paint, clip paths, masks, filters and markers, nested or inherited — or a reference cycle; or a stylesheet over 2,000 rules, 32 selectors or 16 references in one rule, or 20,000 selector × reference pairs |
| `vector_image_unsafe_content` | 400 | scripts, event handlers, `foreignObject`, embedded documents, XHTML elements, `javascript:`/non-raster `data:` URLs, `<set>`/`<animate>`, a `<style>` containing anything but text, `href` and `xlink:href` that disagree, an `id` or `class` that trimming would change, a fragment that is not a plain ASCII id (a letter, digit or `_`, then letters, digits, `_`, `-`, `.`), an `xml:id`, a fragment `href` on `<image>`, SMIL animation, an embedded raster over 4,096 px a side, `url()` outside `fill`, `stroke`, `clip-path`, `mask`, `filter` and the `marker` properties, the CSS `d` property, `if()`, CSS with escapes, expressions, custom properties, `var()`, or unterminated strings, comments or `url(`, or a stylesheet outside the exporter subset (at-rules, combinators, pseudo-classes, attribute selectors, nesting; selectors may be a type, `*`, `.class` or `#id`) |
| `vector_image_external_reference` | 400 | links, `url()`, `@import` or stylesheets pointing outside the document |
| `vector_image_sanitizer_unavailable` | 500 | the sanitiser could not be loaded |

Show a stored SVG with `<img src="/api/attachments/file/{id}">` (or its `thumbnailUrl`); never insert its markup into a page. `attachmentService.readScoped()` returns it as an `application/octet-stream` download, because a module route cannot keep a sandboxing CSP of its own over the app-wide one. A sanitised document that is still larger than the call's upload limit is rejected with the usual `413` upload-size error. Without the flag, `createScoped` rejects SVG exactly like the REST route. List endpoints return the file URL as a stored vector image's `thumbnailUrl`, because the image route below only resizes raster formats.

## File delivery and imaging

These routes stream files and thumbnails. Access depends on partition visibility:

- Public partitions: no token required unless `requireAuthForPublic` is enabled server-side.
- Private partitions: require auth; scope must match attachment `organizationId`/`tenantId` or be a superadmin.

- Download original file — `GET /attachments/file/{id}`  
  Add `?download=1` to force a download response. Respects partition cache headers. Raster images render inline; an SVG renders inline as `image/svg+xml` only when it was stored through the sanitised vector path and its bytes still match the recorded digest, under `Content-Security-Policy: default-src 'none'; img-src data:; style-src 'unsafe-inline'; sandbox`. Every other file is served as `application/octet-stream` with `attachment` disposition and every response carries `X-Content-Type-Options: nosniff`. An SVG renders inline only when requested at the canonical `/api/attachments/file/{id}`; a percent-encoded spelling of the path gets a download. In the Next.js app every response whose raw path starts with `/api/attachments/file/` — including the API dispatcher's own errors — carries `Content-Security-Policy: default-src 'none'; img-src data:; style-src 'unsafe-inline'; sandbox` from `next.config.ts`, which Next.js keeps over the route's own header; the route itself sets `default-src 'none'; sandbox` on its non-SVG responses for other hosts.
- Serve/rescale image — `GET /attachments/image/{id}/{slug?}?width=<n>&height=<n>&cropType=cover|contain`  
  Returns a resized image (Sharp) and caches thumbnails per size. Omit `width`/`height` to stream the original image type while keeping access controls in place. Raster formats only — SVG returns `400`; use the file route for vector images.
