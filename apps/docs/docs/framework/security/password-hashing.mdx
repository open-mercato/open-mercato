# Password Hashing

Staff (`auth`) and customer-portal (`customer_accounts`) passwords are hashed through one service, `passwordHasher`. By default it uses **bcrypt with cost 10**, exactly as earlier versions did. You can opt into **Argon2id**, the algorithm the [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) recommends, without forcing anyone to reset a password.

## Configuration

| Variable | Default | Meaning |
|---|---|---|
| `OM_PASSWORD_HASH` | `bcrypt` | `bcrypt` or `argon2id`. Any other value logs a warning and falls back to `bcrypt`. |
| `OM_PASSWORD_ARGON2_MEMORY_KIB` | `19456` | Argon2id memory cost in KiB (19 MiB). |
| `OM_PASSWORD_ARGON2_TIME_COST` | `2` | Argon2id iterations. |
| `OM_PASSWORD_ARGON2_PARALLELISM` | `1` | Argon2id lanes. |

The values are read once per process; restart the app and workers after changing them. The Argon2id defaults are the OWASP minimum. Raise memory or iterations if your servers can afford a slower login.

## How migration works

- Every stored hash says which algorithm made it (`$2a$`, `$2b$`, `$2y$` for bcrypt, `$argon2id$` for Argon2id). Verification picks the algorithm from the hash, so **both kinds keep working whichever algorithm is configured**.
- `OM_PASSWORD_HASH` decides how **new** passwords are hashed: sign-up, invitations, user creation, password change and reset, `mercato auth add-user` and `mercato auth set-password`.
- After a **successful** staff or portal login, a hash made with another algorithm, or with other Argon2id parameters, is replaced with a fresh one. The update only applies when the stored hash has not changed in the meantime, so a concurrent password change always wins. If the update fails, the error is logged and reported and the login still succeeds.
- With the default `bcrypt`, bcrypt hashes are never rewritten, so the database is not touched on login.

Switching back from `argon2id` to `bcrypt` works the same way in reverse: Argon2id passwords keep verifying and are re-hashed to bcrypt on the next login.

## Before you switch

- **Downgrades.** Open Mercato versions released before this service can only verify bcrypt. If you need to roll back to such a version, first set `OM_PASSWORD_HASH=bcrypt` and let users log in, or plan to reset the passwords of users who were migrated.
- **Enterprise security module.** Its change-password and sudo re-authentication still verify passwords with bcrypt only, so do not enable `argon2id` together with `OM_ENABLE_ENTERPRISE_MODULES` until that module supports it.
- **Timing during migration.** Login always spends one password verification, also for unknown accounts, so response time does not reveal whether an account exists. While users are being migrated, accounts that still have a bcrypt hash verify at bcrypt cost and the rest at Argon2id cost. The difference disappears as users log in.
- **Platform.** Argon2id uses the [`@node-rs/argon2`](https://github.com/napi-rs/node-rs/tree/main/packages/argon2) package, with prebuilt binaries for Linux (glibc and musl, x64 and arm64), macOS and Windows. It is loaded only when a process hashes or verifies an Argon2id password; bcrypt-only installs never load it.

## Scope

Only user and customer-portal passwords use this service. API keys, MFA one-time and recovery codes, SCIM tokens, checkout link passwords and agent client secrets are random secrets, not user-chosen passwords, and keep their own bcrypt hashing.

## Custom hasher

The hasher implements `hash(password)`, `verify(password, storedHash)`, `needsRehash(storedHash)` and `equalizeTiming(password)`. To plug in your own, call `setPasswordHasher()` from `@open-mercato/shared/lib/auth/passwordHasher` during app bootstrap (for example in your app's `di.ts`). The `passwordHasher` DI registration always resolves the active instance.
