# Reference Example Module

`example` is the platform's canonical reference module. It is real, compiling code — not prose, not a tutorial — that demonstrates one working way to use nearly every extension point this framework exposes: CRUD, custom fields, encryption, events, UMES, AI tools, notifications, search, integrations, and more. This page is a capability-by-capability index into it: look up what you want to build, follow the exact source link, and read only that file.

## What this module is — and is not

- **It is the canonical app-local teaching module.** One minimal, real declaration per mechanism, kept in sync as the framework evolves.
- **Its source ships everywhere.** The same tree exists in the monorepo (`apps/mercato/src/modules/example/`), in the `create-mercato-app` template, and in every built-in standalone preset (`classic`, `empty`, `crm`).
- **It is source-present but runtime-disabled by default — in every layout, including this monorepo.** No route, page, migration, seed, ACL grant, event, widget, worker, or navigation entry loads until you explicitly enable it. To run it locally for inspection:

  ```ts
  // src/modules.ts
  export default [
    { id: 'example', from: '@app' },
  ]
  ```

  Then regenerate the runtime registries and apply its committed migrations before starting the app:

  ```bash
  yarn generate
  yarn db:migrate
  ```

  `yarn generate` never applies migrations on its own — skipping `yarn db:migrate` after enabling `example` on an already-initialized app leaves its routes active without their tables.

- **It is a reference for one compiling way to do something — not the production authority for everything.** For provider internals (payment gateways, shipping carriers, webhook adapters), it demonstrates the integration seam only; the normative guide is `om-integration-builder`. For workflow orchestration beyond a minimal trigger, see the `workflows` framework guide. For mutation-capable AI (tools that write, not just read), see `om-create-ai-agent`. For portal/customer authentication, see the `customer_accounts` module guide.
- **Do not copy the whole tree.** `example` is deliberately broad — it doubles as the platform's own QA surface, and it contains demo pages, probe routes, and mock adapters that must never appear in a product module. Copy **one** capability at a time, from the exact file this page names, and rename every `example`-scoped identifier (module id, entity id, table names, route paths, command/event ids, widget/ACL/i18n ids) before the code is yours — the module's own [copy/adapt checklist](https://github.com/open-mercato/open-mercato/blob/develop/apps/mercato/src/modules/example/README.md#copy--adapt-checklist) has the exact 10-step list.

## How to read this page

Every row below carries:

- **Capability** — the stable `capabilityId` from the module's machine-readable inventory (`references/surface-inventory.json`), so a row here and a row in that file are always the same thing.
- **Demonstrates** — what the linked file actually proves, in one sentence to one short paragraph.
- **Source** — the exact file(s) to open, linked at the `develop` branch. Read only these — not the surrounding directory.

Sections are grouped by what you're trying to build, not by where the files happen to live. A `readable` row (everything below except the final section) passed the module's own reference-quality gate and is safe to read and adapt. The final **Testing Evidence** section is different: it is `qa-only` — present because the module doubles as QA surface, working, but never a pattern to copy. See the [module's README](https://github.com/open-mercato/open-mercato/blob/develop/apps/mercato/src/modules/example/README.md) for the full reference-quality gate and the read-status legend.
