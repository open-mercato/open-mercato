# Module overrides

Use `entry.overrides` in `apps/<app>/src/modules.ts` when an app needs to replace or disable a contract shipped by an upstream module. The override is static app configuration: it applies during bootstrap before the affected registries are stored.

```ts
import type { ModuleEntry } from './modules'

export const enabledModules: ModuleEntry[] = [
  {
    id: 'example',
    from: '@app',
    overrides: {
      routes: {
        api: {
          'GET /api/example/override-probe': {
            handler: async () => Response.json({ ok: true, source: 'override' }),
            metadata: { requireAuth: false },
          },
        },
        pages: {
          '/backend/example': null,
          '/frontend/store': { metadata: { title: 'Storefront' } },
        },
      },
    },
  },
]
```

Resolution order is:

1. Programmatic `apply*Overrides(...)`.
2. `modules.ts` inline `entry.overrides`.
3. File-based overrides where a domain supports them.
4. The module's own registrations.

`null` disables the contract. A definition replaces it. Programmatic overrides can restore a contract disabled by `modules.ts` by mapping the same id back to a definition.

The default app and `create-mercato-app` template also export a non-applied `moduleOverrideExamples` object from `src/modules.ts`. It is a copyable catalog for all wired domains; it does not change runtime behavior unless you assign one of those shapes to a module entry's `overrides` field.

## Domains

| Domain | Key | Stable id |
|---|---|---|
| AI | `ai.agents`, `ai.tools` | agent id / tool name |
| API routes | `routes.api` | `'METHOD /api/path'` |
| Page routes | `routes.pages` | `'/backend/path'` or `'/frontend/path'` |
| Event subscribers | `events.subscribers` | subscriber id |
| Workers | `workers` | worker id |
| Widget injection | `widgets.injection` | injection widget id — either the registry `key` (`module:widget:file`) or the widget's own `widgetId` (`module.injection.widget`) |
| Component overrides | `widgets.components` | component handle |
| Dashboard widgets | `widgets.dashboard` | widget id |
| Notification types and handlers | `notifications.types`, `notifications.handlers` | type id / handler id |
| API interceptors | `interceptors` | interceptor id |
| Command interceptors | `commandInterceptors` | interceptor id |
| Response enrichers | `enrichers` | enricher id |
| Page guards | `guards` | middleware id |
| CLI commands | `cli` | command string |
| Setup hooks | `setup` | module id |
| ACL features | `acl.features` | feature id |
| DI bindings | `di` | container key |
| Encryption maps | `encryption.maps` | entity id |
| Sidebar nav ordering | `nav.groupOrder` | nav group id |

## Examples

### Full `modules.ts` Catalog

Use this shape when you need to find the correct key for a domain quickly. Keep only the domains you actually intend to override.

```ts
import type { ModuleOverrides } from '@open-mercato/shared/modules/overrides'

export const moduleOverrideExamples: ModuleOverrides = {
  ai: {
    agents: { 'catalog.catalog_assistant': null },
    tools: { inbox_ops_accept_action: null },
  },
  routes: {
    api: { 'DELETE /api/example/items': null },
    pages: { '/backend/example/reports': null },
  },
  events: {
    subscribers: { 'example.todo.audit': null },
  },
  workers: { 'example:sync': null },
  widgets: {
    injection: { 'example.sidebar': null },
    components: { 'page:/backend/example': null },
    dashboard: { 'example.kpi': null },
  },
  notifications: {
    types: { 'example.notice': null },
    handlers: { 'example.notice.toast': null },
  },
  interceptors: { 'example.items.interceptor': null },
  commandInterceptors: { 'example.command.interceptor': null },
  enrichers: { 'example.items.enricher': null },
  guards: { 'example.backend.guard': null },
  cli: { 'example seed': null },
  setup: { seedExamples: false },
  acl: {
    features: { 'example.manage': null },
  },
  di: { exampleService: null },
  encryption: {
    maps: { 'example:item': null },
  },
}
```

Setting an ACL feature to `null` is an exact runtime denial, not only a catalog change. The denial wins over a stale explicit database grant, `module.*`, `*`, staff super-admin, and portal-admin status. Open Mercato intentionally does not migrate or delete stored grants: they remain inert while the null override exists and become effective again if a higher-precedence definition restores the feature or the null override is removed.

Browser capability fields contain the concrete effective feature IDs after ACL and module overrides are applied. They do not contain wildcard strings or a separate deny-list.

`setup` overrides apply to the module entry that carries them. For example, `setup: { seedExamples: false }` on `{ id: 'catalog', ... }` skips catalog's `seedExamples` hook; it does not address setup hooks by a separate map key.

### Routes

```ts
overrides: {
  routes: {
    api: {
      'DELETE /api/catalog/products/[id]': null,
      'POST /api/catalog/products': {
        handler: async (req) => Response.json({ ok: true }),
        metadata: { requireAuth: true, requireFeatures: ['catalog.manage'] },
      },
    },
    pages: {
      '/backend/catalog/products': null,
      '/frontend/products': { metadata: { navHidden: true } },
    },
  },
}
```

### Events, Workers, CLI

```ts
overrides: {
  events: {

    },
  },
  workers: {
    'catalog:reindex': {
      id: 'catalog:reindex',
      queue: 'catalog-reindex-fast',
      concurrency: 4,
      handler: async (job, ctx) => {},
    },
  },
  cli: {
    'catalog reindex': null,
  },
}
```

### Widgets

```ts
overrides: {
  widgets: {
    injection: {
      'catalog.product.toolbar': null,
    },
    components: {
      'page:/backend/catalog/products': {
        target: { componentId: 'page:/backend/catalog/products' },
        priority: 10,
        propsTransform: (props) => props,
      },
    },
    dashboard: {
      'catalog.low_stock': null,
    },
  },
}
```

An injection widget is addressable by two ids: the generated registry `key`
(`catalog:product-seo:widget`) and the widget module's own `widgetId`
(`catalog.injection.product-seo`). Either spelling disables or replaces the widget
in both the entries registry and every injection table that places it, so you never
need to list both — and neither is reported as a stale override.

The dispatcher must also run in the browser. `ClientBootstrap` re-registers the
injection, dashboard and notification registries after hydration, so an app that
forks it MUST call `applyModuleOverridesFromEnabledModules(enabledModules, { domains: ['widgets', 'notifications'] })`
before those registrations — otherwise the raw generated registries overwrite the
filtered ones and a disabled widget reappears once hydration finishes.

:::warning Keep client-side overrides off server-only env gates

Because the browser re-evaluates `src/modules.ts`, an `enabledModules` entry gated on
a server-only environment variable **MUST NOT** carry `widgets` or `notifications`
overrides. Next.js inlines only `NEXT_PUBLIC_*` values into the client bundle, so a
gate such as `parseBooleanWithDefault(process.env.OM_ENABLE_ENTERPRISE_MODULES, false)`
is always `false` in the browser: the entry is absent there, the server dispatches its
overrides and the client does not, and the widget the server correctly hid reappears
the moment hydration finishes.

```ts
// ✗ the override is server-only — it never reaches the browser
if (parseBooleanWithDefault(process.env.OM_ENABLE_ENTERPRISE_MODULES, false)) {
  enabledModules.push({
    id: 'record_locks',
    from: '@open-mercato/enterprise',
    overrides: { widgets: { injection: { 'catalog.injection.product-seo': null } } },
  })
}

// ✓ gate the module on the server variable, declare the override on an ungated entry
//   (or gate it on a NEXT_PUBLIC_ variable, which is inlined into both bundles)
```

Outside production `ClientBootstrap` compares the browser's `enabledModules` against
the build-time `enabled-module-ids.generated` list and warns for every module the
browser cannot see, so the mismatch shows up in the console instead of silently.

:::

### Sidebar Nav Ordering

Core ranks a built-in list of sidebar nav groups ahead of everything else, so an app's own group would
otherwise sit below the shipped ones no matter what `priority` or `order` its pages declare.
`nav.groupOrder` lets the app decide:

```ts
overrides: {
  nav: {
    groupOrder: ['my_app.nav.group'],
  },
}
```

- **Prepends, does not replace.** The ids listed rank first, in the order given. Any group not named
  keeps the ordering it has today — so listing just your own group is enough, and you cannot
  accidentally demote a shipped group by forgetting it.
- **It is a default.** Role and per-user sidebar preferences still apply on top, so an operator's own
  arrangement wins over this.
- **Declare it once.** Ordering is a single app-wide decision; if two module entries declare it, the
  later one in load order wins and a warning names both.
- Unknown group ids are ignored.

Per-role ordering is a different mechanism: seed `SidebarPreferencesSettings.groupOrder` on a
`RoleSidebarPreference` row (see the sidebar customization page, which writes exactly those rows).
Use `nav.groupOrder` for an app-wide default and role preferences when different roles need different
orders.

## Programmatic Overrides

Use programmatic helpers for env-driven boot decisions and tests:

```ts
import {
  applyApiRouteOverrides,
  applyPageRouteOverrides,
  applyWorkerOverrides,
} from '@open-mercato/shared/modules/overrides'

applyApiRouteOverrides({ 'GET /api/example/override-probe': null })
applyPageRouteOverrides({ '/backend/example': null })
applyWorkerOverrides({ 'example:sync': null })
```

Sidebar nav ordering has the same tier, and it takes precedence over the `modules.ts` declaration:

```ts
import { applyNavGroupOrderOverrides } from '@open-mercato/shared/modules/overrides'

applyNavGroupOrderOverrides(['my_app.nav.group'])
applyNavGroupOrderOverrides(null) // clear, falling back to modules.ts
```

Programmatic calls must happen before the affected registry registers its base entries. The standard app bootstrap already calls `applyModuleOverridesFromEnabledModules(enabledModules)` for inline `modules.ts` overrides.

## Notes

- Override your own app module by editing the module directly; use `entry.overrides` for cross-module app policy.
- API route keys normalize method case and trailing slashes.
- Page route keys normalize `/frontend/foo` to frontend route `/foo`; `/backend/foo` stays backend.
- Stale keys log a warning so operators can find renamed or removed upstream contracts.
