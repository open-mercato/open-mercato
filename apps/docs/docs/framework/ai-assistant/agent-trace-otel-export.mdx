# Exporting agent traces to OpenTelemetry

Agent Orchestrator can send persisted runs to any backend that accepts OTLP over HTTP with JSON or protobuf (Jaeger, Grafana Tempo, a vendor collector). Spans use the OpenTelemetry GenAI semantic conventions (`gen_ai.*`, version 1.43) plus `om.*` attributes for platform concepts. Export is opt-in, fail-open and never affects a run.

## Enabling export

Export happens only when all of these hold:

1. **Deployment switch**: `OM_AGENT_OTEL_EXPORT=on`, with a usable http(s) endpoint and a supported protocol (`http/json` or `http/protobuf`). Alternatively, tenants can send to their own endpoint, see [Tenant destinations](#tenant-destinations); that path needs the switch on and `OM_AGENT_OTEL_EXPORT_TENANT_ENDPOINTS=allow`, but no deployment endpoint.
2. **Tenant opt-in**: the tenant enables export on `/backend/settings/otel-export`.
3. **Allowlist**: if the tenant set an agent allowlist, the run's agent is on it. No allowlist exports every agent.
4. **Source**: the run's source is listed in `OM_AGENT_OTEL_EXPORT_SOURCES` (default `runtime,eval`).

Tenant settings are stored in module config `agent_orchestrator/otel_export`: `enabled`, `content` (`none` or `full`), `exportUserIds` and `agentAllowlist` and `destination` (`deployment` or `integration`). A malformed or unreadable record disables export for the tenant. Saving needs `agent_orchestrator.agents.manage`. Saving `content = full` additionally needs `agent_orchestrator.trace.view_content` and a deployment that allows content (`OM_AGENT_OTEL_EXPORT_CONTENT=allow`); otherwise it is refused with `422`: `content_export_not_allowed`.

## Environment variables

| Variable | Default | Purpose |
| --- | --- | --- |
| `OM_AGENT_OTEL_EXPORT` | off | Deployment master switch. |
| `OM_AGENT_OTEL_EXPORT_ENDPOINT` | none | OTLP traces URL. Falls back to `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`, then `OTEL_EXPORTER_OTLP_ENDPOINT` plus `/v1/traces`. |
| `OM_AGENT_OTEL_EXPORT_HEADERS` | none | Request headers as `key=value` pairs (URL-encoded values). Falls back to `OTEL_EXPORTER_OTLP_HEADERS`. |
| `OM_AGENT_OTEL_EXPORT_PROTOCOL` | `http/json` | `http/json` or `http/protobuf`; anything else disables deployment-endpoint export. |
| `OM_AGENT_OTEL_EXPORT_CONTENT` | `deny` | `allow` lets tenants opt into prompt and response content export. |
| `OM_AGENT_OTEL_EXPORT_TENANT_ENDPOINTS` | `deny` | `allow` lets organizations export to their own endpoint through the `agent_orchestrator_otel_export` integration. |
| `OM_AGENT_OTEL_EXPORT_PRIVATE_HOSTS` | none | Comma-separated hosts (exact or dot-boundary suffix) that tenant endpoints may resolve to private addresses, for example an in-cluster collector. Empty denies every private address. |
| `OM_AGENT_OTEL_EXPORT_DELAY_MS` | `30000` | Delay between run completion and export, so late spans are included. Maximum 24 hours. |
| `OM_AGENT_OTEL_SERVICE_NAME` | `open-mercato-agents` | `service.name` resource attribute. |
| `OM_AGENT_OTEL_EXPORT_SOURCES` | `runtime,eval` | Run sources that may be exported. |
| `OM_AGENT_OTEL_TRACE_URL_TEMPLATE` | none | Link template for the run page. Must contain the token `{traceId}`. |
| `RATE_LIMIT_AGENT_ORCH_OTEL_EXPORT_TEST_POINTS` | `1` | Test-span requests allowed per window, per tenant. |
| `RATE_LIMIT_AGENT_ORCH_OTEL_EXPORT_TEST_DURATION` | `10` | Window in seconds. |
| `RATE_LIMIT_AGENT_ORCH_OTEL_EXPORT_TEST_BLOCK_DURATION` | none | Optional block time in seconds after the limit is hit. |

The endpoint and headers stay server-side. They are never logged, returned by the API or shown in the UI, and the HTTP client does not follow redirects, so credentials never leave the configured host.

## What is exported

Per run: the run span, its LLM, tool and agent spans with the attributes from [Trace capture policy and step metadata](./agent-trace-capture), proposal dispositions, guardrail checks as span events, evaluation results, and the workflow span for runs that belong to a workflow. Resource attributes carry the service name, version, deployment environment, tenant and organization ids and the GenAI semconv version.

## What is never exported

- Run input and output, proposal payloads, tool-call summaries, evaluation evidence, and process input, failure reasons or subject titles. These are encrypted or free text.
- Prompt and response content, unless all three content locks are open (see [Content export](#content-export)). By default only hashes, sizes and counts leave the system.
- User ids, unless the tenant turns on `exportUserIds`.

String attributes pass through a redaction step that masks email addresses, authorization schemes and secret-looking keys before they are sent.

## Content export

Prompt and response content is exported only when all three locks are open:

1. **Deployment**: `OM_AGENT_OTEL_EXPORT_CONTENT=allow`.
2. **Tenant**: the tenant setting `content = full`. Only users with `agent_orchestrator.trace.view_content` can opt in (the settings API, the command and its undo all check it).
3. **Run**: the run was captured with `om.capture = full` (see [Trace capture policy](./agent-trace-capture)). Runs captured at a lower level export no content.

With the locks open, the worker reads the stored request and response artifacts of each LLM span and adds one `gen_ai.client.inference.operation.details` event to the span with these attributes: `gen_ai.system_instructions`, `gen_ai.input.messages`, `gen_ai.output.messages` and `gen_ai.tool.definitions`. Messages follow the GenAI message schema (text, reasoning, tool call and tool call response parts); binary parts become file metadata (modality, MIME type, size, sha256) and never carry bytes or file names. Every string passes a second redaction pass (emails and secret-looking values) on top of the one applied at capture time.

Limits: each content attribute is capped at 64 KiB and marked `om.truncated` when cut; a run reads at most 4 MiB of stored content; export requests are split so no body exceeds 4 MiB (a single oversized span is sent alone).

Each LLM span carries `om.content.export_status`:

| Value | Meaning |
| --- | --- |
| `exported` | All content keys of the span loaded. |
| `unavailable` | Storage failed or the content could not be read. |
| `expired` | Retention removed the content. |
| `over_budget` | The 4 MiB run budget was exhausted. |
| `not_captured` | The span has no stored content. |

Every artifact read for export is recorded in the content access log, like a manual read through the run page, including reads dropped for budget. Tool call arguments and results are exported only for tool spans that carry a `gen_ai.tool.call.id` matching the LLM content; native and OpenCode runs do not record that id yet, so tool spans currently export no content. The `otel:export --dry-run` backfill maps runs without content and never prints it.

## Protobuf

Set `OM_AGENT_OTEL_EXPORT_PROTOCOL=http/protobuf` to send `application/x-protobuf` bodies. The encoder is hand-written, with no OpenTelemetry SDK dependency, and normalizes ids, timestamps and value types exactly like the JSON encoder. Integers beyond signed 64-bit are sent as decimal strings. Tenant destinations choose their own protocol.

## Tenant destinations

An organization can send its runs to its own OTLP endpoint instead of the deployment endpoint:

1. The deployment sets `OM_AGENT_OTEL_EXPORT=on` and `OM_AGENT_OTEL_EXPORT_TENANT_ENDPOINTS=allow`.
2. An administrator configures the `agent_orchestrator_otel_export` integration for the organization (credentials: `endpoint`, optional `headers` as URL-encoded `key=value` pairs, `protocol`) and enables it. Credentials are stored per organization, encrypted, and never returned by the API or shown again.
3. The tenant sets `destination = integration` on `/backend/settings/otel-export`.

Endpoints are vetted before every export and by the integration health check: http(s) only, no credentials in the URL, and every DNS answer must be a public address (loopback, link-local and metadata, private, CGNAT, multicast and mapped or transition addresses are refused) unless the host is listed in `OM_AGENT_OTEL_EXPORT_PRIVATE_HOSTS`. The connection is pinned to the vetted addresses so a DNS change cannot redirect it, the hostname is kept for Host, SNI and certificate checks, and redirects are not followed. The endpoint, headers and the block reason are never logged or returned.

The destination fails closed: when it cannot be resolved, nothing is sent and the deployment endpoint is never used as a fallback. Failures are reported with these codes in export health, test span responses and backfill skips:

| Code | Cause |
| --- | --- |
| `deployment_unconfigured` | Destination is `deployment` but the switch is off or the endpoint is missing or unusable. |
| `integration_unconfigured` | No valid credentials for the organization. |
| `integration_disabled` | Credentials exist but the integration is not enabled. |
| `tenant_endpoints_denied` | The deployment does not allow tenant endpoints. |
| `endpoint_blocked` | The endpoint failed the SSRF checks. |

## Deterministic ids

Trace, run, span, workflow and disposition ids are derived by hashing stable identifiers, not generated randomly. The trace id is anchored on the workflow instance when there is one, otherwise on the root run, so every run of a workflow lands in one trace. Re-exporting a run produces the same ids, which lets a backend merge repeated exports of the same spans, and the run page can show the trace id and a deep link without extra storage.

## Delivery guarantees

Delivery is **at-least-once**. The queue has no job-id deduplication, so a retry after an ambiguous failure, or a manual backfill, can deliver a run twice. Because ids are deterministic, backends that deduplicate on span id collapse the copies; others may show duplicates.

A persistent subscriber on `agent_orchestrator.run.completed` and `agent_orchestrator.run.ingested` enqueues a job on the `agent-orchestrator-otel-export` queue, delayed by `OM_AGENT_OTEL_EXPORT_DELAY_MS`. The worker re-checks the gate, builds the payload and sends it:

- `2xx`: success.
- `429`, `502`, `503`, `504`, timeouts and network errors: retried with exponential backoff (5 s, 10 s, 20 s, up to 5 minutes), honoring `Retry-After` up to one hour, for at most 5 attempts.
- Unexpected failures inside the worker (loading the run, reading settings, the database or the queue): retried with the same backoff and attempt limit.
- Any other status: dropped and reported as an error.

Failures are reported through the error reporter and recorded as export health; they never fail the run. Enqueueing is best-effort: if a subscriber cannot enqueue the job, it reports the error and carries on without failing the event, so other subscribers of the same event are not re-run. A queue outage at that moment can therefore drop an export; backfill the window with `otel:export`.

The `invoke_workflow` root span is built only from the process instance, so every run of the execution exports the same span. It is included only once the process reaches a terminal status; runs exported earlier already point to its span id. Because a process can finish after its last run was exported (a user task, an approval or a non-agent step at the end), the subscribers that mark a workflow instance completed, failed or cancelled also enqueue a re-export of the latest exportable top-level run of that execution, scoped to its tenant and organization. Ids are deterministic, so the repeated run spans merge and the export now carries the root. A process without agent runs exports nothing.

## Health and test span

The settings page shows the last success and last error code for the tenant, and the system health panel has an OTel export line (down when the deployment is off, unknown before the first attempt, degraded after an error, ok otherwise).

Use **Send test span** (`POST /api/agent_orchestrator/otel-export/test`) to send one synthetic `om.export.test` span. A backend rejection returns `ok: false` with a normal response; a disabled deployment returns `409`, and exceeding the rate limit returns `429`.

## Trace link

Set `OM_AGENT_OTEL_TRACE_URL_TEMPLATE` to your backend's trace URL with the `{traceId}` token, for example `http://127.0.0.1:16686/trace/{traceId}`. When the run passes the same gate as the exporter (deployment switch, tenant opt-in, agent allowlist and run source), the run page shows the trace id and an Open in tracing backend link. Templates that do not resolve to an http(s) URL are ignored.

## Backfill CLI

Replay persisted runs, for example after enabling export or after an outage:

```bash
# Inspect the OTLP payload of one run, no network and no queue (NDJSON on stdout)
yarn mercato agent_orchestrator otel:export --run RUN_ID --dry-run

# Enqueue every run in a window for one tenant
yarn mercato agent_orchestrator otel:export --since 2026-10-01T00:00:00Z --until 2026-10-08T00:00:00Z --tenant TENANT_ID --limit 500
```

Options: `--run`, or `--since` with optional `--until`; `--tenant`; `--limit` (1 to 1000); `--dry-run`. Without `--dry-run` the deployment switch must be on, and each run still has to pass the tenant gate. The command prints how many runs were enqueued and why others were skipped.

## Local collector and Jaeger

A compose profile starts an OTLP collector that forwards to Jaeger:

```bash
docker compose --project-directory . -f starters/docker/compose.agent-otel.yml --profile agent-otel up
```

Then set:

```bash
OM_AGENT_OTEL_EXPORT=on
OM_AGENT_OTEL_EXPORT_ENDPOINT=http://127.0.0.1:4318/v1/traces
OM_AGENT_OTEL_TRACE_URL_TEMPLATE=http://127.0.0.1:16686/trace/{traceId}
```

Open the Jaeger UI at `http://127.0.0.1:16686`.

## Integration tests

`TC-AGENT-OTEL-001` and `TC-AGENT-OTEL-002` contain delivery cases that need a fake OTLP receiver on port 4319. They run only when the app under test is started with export on and pointed at that port, and skip with a reason otherwise. CI does not set these variables, so the delivery cases run locally:

```bash
OM_AGENT_OTEL_EXPORT=on \
OM_AGENT_OTEL_EXPORT_ENDPOINT=http://127.0.0.1:4319/v1/traces \
OM_AGENT_OTEL_EXPORT_DELAY_MS=0 \
OM_AGENT_OTEL_TRACE_URL_TEMPLATE='http://127.0.0.1:16686/trace/{traceId}' \
yarn test:integration:ephemeral:start
```
