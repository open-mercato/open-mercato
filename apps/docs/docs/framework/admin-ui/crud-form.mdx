# CrudForm

A lightweight, extensible form component for admin CRUD pages. It supports validation via Zod, mobile-first fullscreen UX, inline help, a header with back navigation, and richer editors like tags, rich text, and relations. You can also embed fully custom React components per field.

## Basic usage

```tsx
import { CrudForm, type CrudField } from '@open-mercato/ui/backend/CrudForm'
import { z } from 'zod'

const schema = z.object({
  title: z.string().min(1, 'Title is required'),
  is_done: z.boolean().optional(),
})

const fields: CrudField[] = [
  { id: 'title', label: 'Title', type: 'text', required: true, description: 'A clear summary of the task' },
  { id: 'is_done', label: 'Done', type: 'checkbox' },
]

<CrudForm
  title="Create Todo"
  backHref="/backend/todos"
  schema={schema}
  fields={fields}
  submitLabel="Create"
  cancelHref="/backend/todos"
  successRedirect="/backend/todos"
  onSubmit={async (values) => { /* ... */ }}
/>
```

## Props
- `schema`: Zod schema for validation.
- `fields`: Array of field descriptors (see below).
- `initialValues`: Initial values map.
- `submitLabel`: Submit button label.
- `cancelHref`: Optional cancel link.
- `successRedirect`: Navigate on success.
- `onSubmit(values)`: Submit handler (sync or async).
- `entityId`: When set, CrudForm fetches module custom field definitions for this entity and auto-appends fields marked `formEditable`. This keeps forms in sync with dynamic custom fields without hardcoding them.
- `onDelete()`: Optional delete handler; when provided, a Delete button appears at the top and bottom of the form.
- `twoColumn`: When `true`, uses a two-column grid on desktop. Prefer `groups` for richer two-column layouts.
- `groups`: Optional grouped layout rendered as two responsive columns (1 on mobile). Each group can target column 1 or 2, have a title, own field list, and embed a custom component. A special `kind: 'customFields'` group renders module-defined custom fields for the `entityId`.
- `hiddenGroupIds`: Optional list of `CrudFormGroup.id` values to omit, so a host can drop built-in cards without rebuilding `groups`. Presentation-only — see [Hiding groups by id](#hiding-groups-by-id).
- `title`: Header title (shown on all breakpoints).
- `backHref`: Back link URL in the header.

## Field types
Built-in `type` values:
- `text`, `number`, `date`, `textarea`, `checkbox`
- `select` (with `options` or async `loadOptions`)
- `tags` (simple tags input; press Enter or comma to add)
- `richtext` (basic contenteditable runtime with HTML value)
- `relation` (searchable list; client-side filter)
- `custom` (render custom React component)

Common field properties:
- `id`: Field key in values map.
- `label`: Human-readable label.
- `required`: When `true`, renders an asterisk and validate via `schema`.
- `placeholder`: Optional placeholder.
- `description`: Inline field help below the input.

Select/relation properties:
- `options: { value: string; label: string }[]`
- `loadOptions?: (query?: string) => Promise<{ value: string; label: string }[]>` (merged with `options` when loaded)

## Custom field renderer
Use `type: 'custom'` to embed your own React component:

```tsx
const fields: CrudField[] = [
  {
    id: 'assignee',
    label: 'Assignee',
    type: 'custom',
    component: ({ value, setValue, error, autoFocus }) => (
      <MyUserPicker value={value} onChange={setValue} autoFocus={autoFocus} error={error} />
    ),
  },
]
```

The component receives `{ id, value, setValue, error, autoFocus }`.

## Grouped layout (two columns)

```tsx
import type { CrudFormGroup } from '@open-mercato/ui/backend/CrudForm'

const groups: CrudFormGroup[] = [
  { id: 'details', title: 'Details', column: 1, fields: ['title'] },
  { id: 'status', title: 'Status', column: 2, fields: ['is_done'] },
  { id: 'attributes', title: 'Attributes', column: 2, kind: 'customFields' },
  {
    id: 'info',
    title: 'Info',
    column: 2,
    component: ({ values }) => <pre className="text-xs">{JSON.stringify(values, null, 2)}</pre>,
  },
]

<CrudForm
  entityId="example:todo"
  fields={[ /* base fields */ ]}
  groups={groups}
  onDelete={async () => {
    // await DELETE; then redirect with flash message
    router.push('/backend/todos?flash=' + encodeURIComponent('Record has been removed') + '&type=success')
  }}
/>
```

Behavior:
- Renders two columns on large screens, and one stacked column on mobile.
- A group may contain `fields` as ids referencing the `fields` prop, inline field configs, or a mix.
- `kind: 'customFields'` includes the module-defined custom fields and respects an optional group `title`.
- `component` lets you inject custom React content into the group (e.g., action buttons, previews).

## Hiding groups by id

To render a built-in form without some of its cards, pass `hiddenGroupIds` instead of copying the page or rebuilding the `groups` array:

```tsx
<CrudForm
  fields={createCompanyFormFields(t)}
  groups={createCompanyFormGroups(t)}
  hiddenGroupIds={['profile', 'customFields']}
  onSubmit={handleSubmit}
/>
```

Behavior:
- Groups are matched on their stable `CrudFormGroup.id`. Injected widget cards use the id `widget:<widgetId>`.
- Hidden groups reserve no column space and contribute no header, sortable entry, collapsible state, or validation focus target. Hiding the only column-2 group collapses the layout to a single column.
- Ids that match no declared group are ignored (with a development-mode warning), so a stale id after a rename never breaks the page.
- A user's saved group order survives hiding: a hidden group keeps its stored position and returns to it once the group is shown again.
- Omitting the prop — or passing an empty array — preserves existing rendering and submission behavior exactly.

:::caution Hiding is presentation-only
Fields that live only in a hidden group **keep their values and are still submitted unchanged**, so hiding a group can never clear the underlying columns. A `required` field that lives only in a hidden group is skipped by the built-in required check (the same way `visibleWhen` works), but a host-supplied Zod `schema` is **not** bypassed — do not hide a group whose fields the schema requires unless defaults supply them.
:::

:::caution Hiding a widget card does not disable the widget
An injected widget's handlers belong to the injection spot, not to its card. Hiding a `widget:<widgetId>` group therefore removes the card while `onBeforeSave` and `transformFormData` keep running, and the widget's fields stay required — so a validation failure can block save with nothing on screen to fix. Do not hide a widget group that gates saving; disable the widget instead.
:::

Because hosts address groups by id, a built-in group's `id` is a contract surface: see [`BACKWARD_COMPATIBILITY.md`](https://github.com/open-mercato/open-mercato/blob/main/BACKWARD_COMPATIBILITY.md) before renaming one, and pin a builder's ids with a guard test.

## Server-verified section policies

Use [section overrides](../modules/overrides.mdx#crudform-sections) when adding, hiding, or replacing a group changes what the form can write. A host registers the exact compositions it supports. Each alternative identifies the ordered groups, contribution IDs, callers, payload and custom-field ownership, dependencies, and guarded mutation surfaces for one `(hostId, formVariant, formOperation)` tuple.

### Extend a published host

Use `defineCrudFormExtension` to change sections of a host that already publishes a section policy. In the contributing module's `form-sections.ts`, export `crudFormExtensions` with one declaration per host. This example assumes the host publishes the `details` and `notes` groups, lists `title` as a field of `details`, and provides a custom-field definition set.

```ts
import { add, defineCrudFormExtension, field, hide, modify } from '@open-mercato/ui/backend/crud-form-extensions'

export const crudFormExtensions = [defineCrudFormExtension({
  id: 'my_app.product_form',
  host: 'crud-form:inventory.product',
  targets: [{ formVariant: 'edit', formOperation: 'update' }],
  sections: {
    notes: hide(),
    details: modify({ fields: {
      title: field.patch({ labelKey: 'my_app.fields.product_name' }),
    } }),
    'supplier-info': add({
      after: 'details',
      titleKey: 'my_app.sections.supplier',
      fields: {
        supplier_ref: field.add({ type: 'text', labelKey: 'my_app.fields.supplier_ref' }),
      },
    }),
  },
})]
```

- Use `modify` on a base that publishes `fields`, `fieldSchemas`, `fieldPayloadPaths`, `projectField`, and `refinements` through `defineCrudFormFieldGranularSection` from `@open-mercato/ui/backend/crud-form-field-granular`. Unchanged fields retain their validators and projectors. `field.remove()` drops dependent optional refinements; a dependent mandatory refinement blocks generation.
- For a component-only group use `hide()` or `replace(() => import('./details.client'))`. A replacement exports `crudFormSectionRuntime` and preserves the published payload ownership. Omitted required leaves need approved preservation on update or a `defaults` provider on the declaration.
- Use i18n keys for labels and validation messages. Define browser choices as literal `{ value, labelKey }` entries or a literal `import()` loader. Use `validate.client` for a literal loader and `validate.server` for a server callback. Declarative rules with `enforce: 'client-and-server'` run in both places. The façade checks server rules against the admitted field again before the transactional write.

An explicit field store takes precedence over the section's store. With neither declared, the field uses `store.customField()`.

| Store | Host or module requirements |
| --- | --- |
| `store.customField(key?)` | Use a `snake_case` key. The host maps the definition-set ID to its entity through `customFieldSeedEntities` and supplies the matching form scope. The seed pipeline installs the definition and the host persists the value. |
| `store.table(entityId)` | Export a contributing-module ORM entity with scalar `tenantId`, `organizationId`, and `hostId` in a unique tuple, plus `id`, `updatedAt`, and columns for the owned fields. Ship its migration. |
| `store.sink(config)` | Supply the persistence, load, and lifecycle callbacks appropriate to the declared transaction, locking, and undo contract. |
| `store.external(config)` | Export an owned mirror entity with the same scoped tuple, `updatedAt`, the shared `outboxColumns` mixin, and nullable JSON `values`. Ship its migration and implement the versioned delivery callback. Share the mirror's delivery `contractId` across create and update, and advance it when remote behavior changes. |

Run `yarn generate`, review the extension summary, and commit `form-sections.revisions.json`. The generator assigns `<extension>.<section>` for one target and `<extension>.<variant>.<operation>.<section>` for multiple targets. The round-trip ID appends `@v<n>` to the contribution ID. For a conflict, use the exact contribution ID in [`overrides.forms.sections`](../modules/overrides.mdx#crudform-sections) or set that address to `null` to mask it.

### Advanced host declarations and hand-written contributions

Use the primitives to publish new host facts, supply a custom adapter, or bind an independent mutation surface. The wrapper compiles contributions into these same policy contracts.

- In module-root `form-sections.ts`, export `crudFormSections` with `defineCrudFormSections` from `@open-mercato/shared/modules/form-sections`. Add the baseline and supported alternatives and associate server capabilities with the exact host and surfaces. A required leaf that a section omits needs explicit coverage, such as preservation from the locked record on update or a registered `server-default` provider.
- Pair each fact with `lazyCrudFormSectionRuntime(() => import('./section.client'))`. The client module exports `crudFormSectionRuntime` with the fact's `id` and `roundTripId`. A host runtime contains `sectionDescriptors`. Use `defineCrudFormSectionRuntime` from `@open-mercato/ui/backend/injection/crud-form-section-runtime` to pair each section's group, owned fields, validator, and payload projector. Revisions have the form `<descriptor-id>@v<n>`.
- Pass the existing grouped form props and an explicit `formVariant` and `formOperation`. Use `injectionSpotId="crud-form:my_app.record"` for host `my_app.record`. Pass `resourceId` for an update and omit it for a create. Policy identity is independent of `initialValues.id`. Supply `sectionCustomFieldDefinitionSets` when sections own custom fields. Each key names an exact set of entity IDs that the runtime and server facts agree on.
- Use `compositionValidator` for invariants across active sections. The form projects and validates owned values, then merges each section's payload by leaf. Report client errors against visible, owned fields. The server validates invariants that depend on hidden or preserved values.
- Run `yarn generate` and commit the module-root `form-sections.runtime-revisions.json` ledger. Increase the revision in both declarations when a fact or runtime changes semantically. The paired registries use the same enabled-module graph. The browser registry loads client code through literal imports and the server facts registry holds the server callbacks.

Configured groups can use `ComponentReplacementHandles.section(crudFormSectionScope({ hostId, formVariant, formOperation }), sectionId)`. Import both helpers from `@open-mercato/shared/modules/widgets/component-registry`.

### Bind mutations to the façade

Use the accepted mutation surface's API path. For a conventional single-resource `makeCrudRoute`, declare `derivedHosts` with `defineCrudRouteSectionHost` from `@open-mercato/shared/lib/crud/form-sections/derived-route-host`. The generator registers a sibling `<route>/section-policy` endpoint with the declared methods. The original route keeps its URL and callers. Use `runCrudFormSectionMutation` from `@open-mercato/shared/lib/crud/form-sections/mutation-facade` to implement a hand-written adapter for custom routes or independent child actions.

`onSubmit` receives `CrudFormSubmitContext<TSectionPayload>` from `@open-mercato/ui/backend/CrudForm`. The example assumes an update whose derived façade accepts the projected payload and an `id`.

```tsx
<CrudForm
  fields={fields}
  groups={groups}
  initialValues={record}
  injectionSpotId="crud-form:my_app.record"
  formVariant="edit"
  formOperation="update"
  resourceId={record.id}
  onSubmit={async (values, context) => {
    if (context?.mutation && context.sectionPayload) {
      await context.mutation.write(endpoint, { ...context.sectionPayload, id: record.id })
      return
    }
    await saveLegacy(values)
  }}
/>
```

`mutation.write(endpoint, body)` serializes JSON. `mutation.request(endpoint, init)` accepts request options. Both bind the HTTP method, protected policy headers, and expected version from the accepted surface. In `onDelete`, use `context.mutation` when the configured parent-delete surface is present. For an accepted child action use the group or widget context's `runSectionMutation`, supplying the declared mutation surface, request operation, target resource kind and ID, and the child's own `expectedUpdatedAt` for edits or deletes. The façade checks the authenticated scope, host, target, and final mutation input again on each request.

### Roll out and recover

Keep the legacy submit path for forms outside the configured-host ledger. Enable an alternative after its runtime, server capabilities, and guarded route are available together. A configured form waits for matching browser registrations and the authorized resolve response from `POST /api/extensions/crud-form-sections/resolve` before mounting editable controls. A rejected or stale policy blocks those controls and writes for that form.

Reload the form for the current scope after an organization change or a `409 extension_policy_mismatch` response. If the form still fails, check that the enabled modules and the generated server and browser registries match and that the provider can authorize the record. To roll back activation, use the matching `null` masks or disable the contributing module and regenerate both registries. Once the last effective override for a tuple is removed, that tuple uses its existing form and route behavior.

## Mobile UX
- On small screens the form is fullscreen with a sticky header that shows the `title` and a `backHref` link.
- On desktop it renders as a standard card with border and padding.
- Focus is not auto-forced; the browser manages focus normally.

## Validation
Provide a Zod schema via `schema`. Field-level errors are displayed under each field; a general form error (from `onSubmit`) shows above actions.

Custom fields rules:
- Field definitions can include rule-based validation (required, integer/float, lt/lte/gt/gte, eq/ne, regex) with custom messages.
- When `entityId` is provided, CrudForm fetches definitions, marks fields with a `required` rule, and validates values client-side before submit.
- The API also validates the same rules server-side to keep forms and custom user entities consistent.

Rules live in the field definition JSON under `validation`:
```
validation: [
  { rule: 'required', message: 'Required' },
  { rule: 'integer', message: 'Must be integer' },
  { rule: 'gte', param: 1, message: '>= 1' },
  { rule: 'lte', param: 5, message: '<= 5' },
]
```

## Notes
- Keep field validation in Zod; mark `required: true` for labels only (the schema drives actual validation).
- Prefer simple value shapes for portability (e.g., tags as `string[]`, relations as a single foreign key `string`).

## Custom field text

Stored custom-field labels, descriptions, fieldset labels, and group text render literally by default. A form can opt into translation with `resolveCustomFieldText?: (text: string, context: { entityId: string; path: string }) => string`. The callback changes display text only; definition keys and submitted values stay unchanged.

The context identifies the owning entity and metadata location:

| Metadata | Path |
| --- | --- |
| Field label or description | `fields.<fieldKey>.label` / `fields.<fieldKey>.description` |
| Field group title or hint | `fields.<fieldKey>.group.title` / `fields.<fieldKey>.group.hint` |
| Fieldset label or description | `fieldsets.<fieldsetCode>.label` / `fieldsets.<fieldsetCode>.description` |
| Fieldset group title or hint | `fieldsets.<fieldsetCode>.groups.<groupCode>.title` / `fieldsets.<fieldsetCode>.groups.<groupCode>.hint` |

Keep module-specific defaults and namespaced translation keys in the owning module. Translate only recognized metadata whose stored text still matches its seeded default, return customized or unknown text unchanged, and pass the stored text as the translator fallback. Memoize the resolver with the current translator as a dependency so locale changes update the same mounted form.

## Custom Fields → Editors and Inputs
When `entityId` is provided, custom fields are fetched from `/api/entities/definitions` and rendered automatically:

- `kind: 'boolean'` → checkbox
- `kind: 'integer'|'float'` → number input
- `kind: 'select'` → select; `multi: true` renders multi-select checkboxes
- `kind: 'text'` + `multi: true` → tags input (free-form tagging)
- `kind: 'multiline'` → rich text area; you can choose the editor via definition `configJson.editor`:
  - `markdown` → UIW Markdown editor
  - `simpleMarkdown` → Simple toolbar markdown textarea
  - `htmlRichText` → ContentEditable rich text (HTML value)

Declare these hints via the DSL in your module:

```ts
defineFields(E.example.todo, [
  cf.text('labels', { label: 'Labels', multi: true, input: 'tags' }),
  cf.multiline('description', { label: 'Description', editor: 'markdown' }),
])

## Custom Fields → Visibility
Custom field visibility is controlled per field via `custom_field_defs.config_json` and affects forms, filters, and list pages:

- `formEditable` (default true): include the field in CrudForm when `entityId` is provided.
- `filterable` (default false): include the field in DataTable filter overlays.
- `listVisible` (default true): show the field as a column in generic records lists.

You can edit these flags in the admin under Backend → Custom Fields → Definitions. For programmatic control, set them in your DSL or seeding CLI.

To apply list visibility to a table, fetch definitions and filter columns via helper:

```ts
import { fetchCustomFieldDefs } from '@open-mercato/ui/backend/utils/customFieldDefs'
import { applyCustomFieldVisibility } from '@open-mercato/ui/backend/utils/customFieldColumns'

const defs = await fetchCustomFieldDefs('example:todo')
const visibleColumns = applyCustomFieldVisibility(columns, defs)
```
