# Scheduler CLI Commands

The scheduler module provides CLI commands for managing scheduled jobs from the command line.

## Available Commands

### scheduler list

List all scheduled jobs with optional filtering.

```bash
yarn mercato scheduler list [options]
```

**Options:**

| Option | Description | Example |
|--------|-------------|---------|
| `--tenant <id>` | Filter by tenant ID | `--tenant tenant-123` |
| `--scope <type>` | Filter by scope type | `--scope system` |
| `--enabled <bool>` | Filter by enabled status | `--enabled true` |
| `--module <id>` | Filter by source module | `--module currencies` |

**Examples:**

```bash
# List all schedules
yarn mercato scheduler list

# List only system-scoped schedules
yarn mercato scheduler list --scope system

# List enabled schedules for a tenant
yarn mercato scheduler list --tenant tenant-123 --enabled true

# List schedules created by a module
yarn mercato scheduler list --module currencies
```

**Output:**

### scheduler run

Manually execute a scheduled job immediately.

```bash
yarn mercato scheduler run <schedule-id>
```

:::note
Like `POST /api/scheduler/trigger`, this command requires `QUEUE_STRATEGY=async`: it enqueues the run on the `scheduler-execution` queue for a worker to execute. With the local strategy it exits with an error, because the local scheduler runs due schedules by polling and never consumes that queue.
:::

**Arguments:**

| Argument | Description | Required |
|----------|-------------|----------|
| `schedule-id` | The UUID of the schedule to run | Yes |

**Example:**

```bash
yarn mercato scheduler run 123e4567-e89b-12d3-a456-426614174000
```

The command only enqueues the run; a `scheduler-execution` worker executes it later. It does not wait for the result. A disabled schedule is still enqueued (and the command still reports success), but the worker skips it and emits `scheduler.job.skipped`.

The sample shows the lines `scheduler run` prints. The `mercato` CLI wrapper logs additional lines around them.

**Output (Success):**

```
🚀 Manually triggering schedule: Fetch Currency Rates

  ID: 123e4567-e89b-12d3-a456-426614174000
  Type: cron
  Schedule: 0 */6 * * *
  Target: currency-rates

✓ Job successfully triggered via scheduler-execution queue (job 42)
  The worker will pick it up and enqueue to: currency-rates
✓ Manual trigger completed
```

While the run is waiting or running, and if it fails, it appears in the schedule's execution history at [`GET /api/scheduler/jobs/{id}/executions`](../api/scheduler.mdx). Completed jobs are removed from the queue, so a successful run does not stay in that history.

**Exit Codes:**

- `0` - Run enqueued
- `1` - Failed: missing or invalid `schedule-id`, schedule not found, `QUEUE_STRATEGY` is not `async`, the database/app container could not be initialized, or the job could not be enqueued

### scheduler start

Start the scheduler engine.

:::tip
Behavior differs based on `QUEUE_STRATEGY`:
- **Local:** Starts polling engine (keeps running)
- **Async:** One-time sync with BullMQ (exits after sync)
:::

```bash
yarn mercato scheduler start
```

The samples below show the lines the `scheduler start` command prints. The `mercato` CLI wrapper and the scheduler services can log additional lines around them.

**Local Strategy Output:**

```
🚀 Starting scheduler (strategy: local)...

✓ Local scheduler started (polling every 30 seconds)
Press Ctrl+C to stop.

💡 Tip: For production, use QUEUE_STRATEGY=async with Redis.
```

On Ctrl+C (or `SIGTERM`) the local scheduler stops and prints:

```
📛 Shutting down...
✓ Stopped
```

**Async Strategy Output:**

```
🚀 Starting scheduler (strategy: async)...

✓ Scheduler sync completed

BullMQ is managing all schedules.
Start workers to process jobs:
  yarn mercato queue worker --all
```

**Options:**

`scheduler start` takes no command-line options. Set the local poll interval with the `SCHEDULER_POLL_INTERVAL_MS` environment variable (default `30000`):

```bash
# Start with default settings
yarn mercato scheduler start

# Start with a custom poll interval (local mode)
SCHEDULER_POLL_INTERVAL_MS=60000 yarn mercato scheduler start
```

**Exit Codes:**

- `0` - Success (async: sync complete, local: clean shutdown on Ctrl+C or `SIGTERM`)
- `1` - Startup failed (the database/app container could not be initialized, the scheduler service is unavailable, the local polling engine failed to start, or the BullMQ sync failed)

## Common Workflows

### Development Setup

```bash
# 1. Check scheduler status
yarn mercato scheduler status

# 2. List existing schedules
yarn mercato scheduler list

# 3. Start scheduler (keeps running, runs due schedules by polling)
yarn mercato scheduler start
```

`scheduler run` needs `QUEUE_STRATEGY=async`, so it is not available with the local strategy used here.

### Production Setup

```bash
# 1. Ensure environment is configured
export QUEUE_STRATEGY=async
export REDIS_URL=redis://localhost:6379

# 2. Check status
yarn mercato scheduler status

# 3. Sync schedules (one-time)
yarn mercato scheduler start

# 4. Start workers (separate process)
yarn mercato queue worker --all

# 5. Monitor execution
yarn mercato queue status scheduler-execution
```

### Debugging Failed Schedules

```bash
# 1. List all schedules
yarn mercato scheduler list

# 2. Check status
yarn mercato scheduler status

# 3. Trigger the schedule manually (async mode), then check its executions
yarn mercato scheduler run <schedule-id>

# 4. Check logs
tail -f logs/scheduler.log

# 5. Check queue job counts, including failed jobs (async mode)
yarn mercato queue status scheduler-execution
```

To see why a specific schedule failed, read its execution history with [`GET /api/scheduler/jobs/{id}/executions`](../api/scheduler.mdx) (async mode).

### Monitoring Production

```bash
# Check scheduler health
yarn mercato scheduler status

# View active schedules
yarn mercato scheduler list --enabled true

# Check waiting, active, completed and failed job counts (async mode)
yarn mercato queue status scheduler-execution
```

Per-schedule execution history is available through [`GET /api/scheduler/jobs/{id}/executions`](../api/scheduler.mdx) (async mode).

## Environment Variables

The scheduler CLI respects these environment variables:

| Variable | Description | Default |
|----------|-------------|---------|
| `QUEUE_STRATEGY` | Execution strategy: `local` or `async` | `local` |
| `REDIS_URL` | Redis connection URL (async mode) | `redis://localhost:6379` |
| `SCHEDULER_POLL_INTERVAL_MS` | Poll interval in milliseconds (local mode) | `30000` |
| `DATABASE_URL` | PostgreSQL connection URL | Required |
| `LOG_LEVEL` | Logging level: `debug`, `info`, `warn`, `error` | `info` |

## Exit Codes Reference

| Code | Meaning | Context |
|------|---------|---------|
| `0` | Success | All commands |
| `1` | Any failure (missing or unknown arguments, not found, database/startup or enqueue failure) | All commands |

## Integration with Other CLI Tools

### Worker Management

```bash
# Start all workers (includes scheduler execution worker)
yarn mercato queue worker --all

# Start only scheduler worker
yarn mercato queue worker scheduler-execution

# Check scheduler queue status
yarn mercato queue status scheduler-execution
```

### Queue Management

The `queue` CLI provides `worker`, `status` and `clear`:

```bash
# Show waiting, active, completed and failed job counts
yarn mercato queue status scheduler-execution

# Remove all jobs from the scheduler execution queue
yarn mercato queue clear scheduler-execution
```

There is no CLI command to list or retry individual jobs. Inspect a single job with [`GET /api/scheduler/queue-jobs/{jobId}?queue=scheduler-execution`](../api/scheduler.mdx) (async mode); take `jobId` from the `queueJobId` field of the executions endpoint, or from the `(job …)` id that `scheduler run` prints.

### Database Management

```bash
# View scheduler tables
yarn mercato db:schema --table scheduled_jobs

# Run migrations
yarn mercato db:migrate

# Generate new migration (after entity changes)
yarn mercato db:generate
```

## Troubleshooting

### "Schedule not found"

```bash
# List all schedules to verify ID
yarn mercato scheduler list

# Check if schedule was soft-deleted
yarn mercato db:query "SELECT * FROM scheduled_jobs WHERE id = '<id>'"
```

### "Lock acquisition failed"

```bash
# Check if another scheduler instance is running
ps aux | grep "scheduler start"

# Release stuck lock (PostgreSQL)
yarn mercato db:query "SELECT pg_advisory_unlock_all()"
```

### "Redis connection failed"

```bash
# Check Redis status
redis-cli ping

# Verify REDIS_URL
echo $REDIS_URL

# Test connection
redis-cli -u $REDIS_URL ping
```

### "No workers running"

```bash
# Check scheduler queue status
yarn mercato queue status scheduler-execution

# Start workers
yarn mercato queue worker --all

# Check worker logs
tail -f logs/worker.log
```

## Best Practices

1. **Use scripts for automation** - Add scheduler commands to package.json scripts
2. **Monitor in production** - Set up cron jobs to check scheduler status
3. **Log everything** - Use `--verbose` flag when debugging
4. **Test manually first** - Enable the schedule, then trigger it once with `scheduler run` (async mode); runs of disabled schedules are skipped by the worker
5. **Graceful shutdowns** - Always use Ctrl+C instead of kill -9
6. **Check status regularly** - Run `scheduler status` to catch issues early
7. **Filter list output** - Use filters to reduce noise in large deployments
8. **Sync after changes** - Re-run `scheduler start` after modifying schedules (async mode)
