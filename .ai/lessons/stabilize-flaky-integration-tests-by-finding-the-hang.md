# Stabilize flaky integration tests by finding the hang, not by raising the timeout

**Context**: `TC-CUR-004` ("Set Base Currency from UI") failed ~1/60 in the `ephemeral-integration` CI shards with `Test timeout of 30000ms exceeded` plus a secondary `apiRequestContext.fetch: Target page, context or browser has been closed` reported from the `finally` teardown.

`TC-WC-023` failed after successfully receiving and quarantining a claim line because it required the emitted event to remain in the local queue file. The ephemeral harness runs queue workers concurrently, and the local strategy removes completed jobs, so queue residency was a race rather than durable evidence of emission. The stable assertion accepts either a still-queued job or the command's durable `line_received` quarantine timeline record.

`TC-SX-009` intermittently created duplicate people or addresses because its polling helper manually drained `data-sync-import` while the ephemeral app also ran its background worker. The local queue supports concurrent producers but explicitly does not lease jobs between concurrent consumers. A focused reproduction delivered one queued job twice through two consumer instances. Keep the uniqueness assertions and call `drainIntegrationQueue` unconditionally for both import and event queues. The shared helper observes managed workers without starting another consumer, drains explicitly when workers are disabled, and uses the app process when `OM_TEST_APP_ROOT` is set. A caller-side worker flag reads the Playwright environment rather than the app's environment and can leave a standalone app with no consumer.

`TC-CRM-065` selected ten unfiltered people although its scenario created three fixtures. The matching search response arrived after deletion because rerenders restarted the debounce, and the blocked fixture was already visible in the initial list. An exact response/fixture-row guard prevented that mutation, but a cold local attempt still timed out with an empty search field; the passing retry's trace showed typing overlapping the initial client fetch. Wait for a row populated by the client effect before typing, then verify the filtered response IDs, rendered rows, selected count, and confirmation count before any bulk mutation. Fixture visibility alone does not prove the filter has finished. Evidence: CI run `40225746832`, its retry trace, and `customers/__integration__/TC-CRM-065.spec.ts`. Select exact fixture rows, retain the dependency-toast assertion, and verify post-mutation state by fixture IDs.

`TC-PHONE-HUB-006` correctly observed a cache miss after command-side invalidation but intermittently received an empty list because its `q` filter depended on asynchronously populated full-text tokens. The cache behavior was synchronous; record discoverability was not. A run-unique exact `providerKey` filter keeps the three cache reads identical while removing the unrelated search-index readiness race.

`TC-SALES-ADDR-CONTACT-002` waited for Generate to be enabled before clicking Define new address. Generate is already enabled in server markup because `DocumentNumberField` starts with `loading=false`; the guard can pass before React attaches the switch handler. Artifact `12787797409` from run `40616644170` shows the failed attempt's switch still unchecked at timeout; only the passing retry has a trace, so the original click timing remains inferred. A controlled browser fixture using the actual number field and switch reproduces the lost click before hydration. Arm the automatic document-number POST response wait before navigation, require success, and verify its number has reached the form input before the single switch click. Assert the switch becomes checked, then retain the existing quote creation and both address-snapshot assertions. This establishes client readiness without repeated toggles or larger timeouts.

`TC-WF-011` timed out waiting for Customize while the failed screenshot and error context showed the Triggers dialog covering the editor (issue #7563, CI run `38944964985`, shard 14). The preceding whole-node click also addressed the START node's nested trigger cap, whose handler opens Triggers and stops propagation. Checking only the step inspector missed that separate modal. Click the existing `WORKFLOW_NODE_TITLE_SELECTOR` within the node and assert both the inspector's absence and the Triggers dialog's hidden state before Customize. Only the passing retry has a trace, so the failed click coordinates and network activity remain unobserved; do not describe this as a slow Customize endpoint or increase its response timeout.

**Problem**: The secondary "context closed" error is a symptom of the test-level timeout tearing the worker down mid-request — it is not the cause. Two real causes hid behind it: (1) the row-actions dropdown is opened with `actionsButton.press('Enter')` and then the menu item is clicked directly; if the Radix trigger swallows the keypress before hydration, the menu never opens and `.click()` auto-waits on a never-mounting element until the whole test times out; (2) login + navigation + three sequential ≤10s waits + fixture setup/teardown genuinely does not fit a 30s budget under 15-shard parallel load — every other login+nav spec already uses 60–120s, and this one was the lone 30s outlier.

**Rule**: When an integration test "times out," read the trace to find which await actually blocked before reaching for a bigger number. Make UI interactions deterministic: after a keyboard-driven menu open, assert the target item is visible with a *bounded* budget and fall back to a pointer click, so a missed keypress fails fast instead of hanging until the suite timeout. A click on server-rendered markup can also land before React hydration; poll the first observable state transition and retry only while the component is still idle. For unit tests of intervals, retries, leases, or heartbeats, do not assert after a short wall-clock sleep: wait until the operation has reached the state that installs the timer, then advance fake timers by the exact interval. After enqueueing work, assert a durable outcome or an allowed state transition instead of requiring a transient `pending` snapshot that a faster worker may already have advanced. When a test targets synchronous cache invalidation, use a synchronous exact filter for record visibility; do not make the assertion depend on an eventually consistent search projection unless indexing behavior is itself under test. Overrides that wrap an interactive login surface must be registered before that surface hydrates; activating the wrapper later remounts uncontrolled inputs and can erase credentials typed by autofill or a fast user. When the scenario targets a specific lifecycle hook, use a least-privilege fixture so a higher-priority optional widget cannot correctly intercept the mutation first and mask the hook under test. Parallelize independent fixture requests and teardowns while retaining dependency ordering instead of spending the test budget on serial setup. Make `finally` teardown best-effort (`.catch(() => {})`) so it cannot mask the real failure with a "context closed" error. Only after removing the hang should you align the per-test budget with the established login+nav convention. Prefer fixing the interaction over inflating the clock.

**Applies to**: every Playwright spec under `**/__integration__/*.spec.ts` that drives `RowActions`/dropdown menus or client-hydrated controls, cache tests whose list filters can route through asynchronous search/query-index projections, login surfaces extended through component overrides, every lifecycle test where optional injection widgets share the same host, any spec whose `finally` block issues API calls after the body may have failed, and unit tests that prove queue lease renewal or other timer-driven concurrency behavior.
