# Background work, part 8 — operator surface for leased jobs

**Date**: 2026-08-21
**Status**: Draft v1.3 — implementation spec split out of part 4 v3 (Phase 3). Awaiting review. Depends on part 6 (DTO fields incl. `redrivable`, `stuck`, `mirrorAttempts`, `leaseOwner`, `leaseEpoch`, `nextRunAt`, the re-drive route with its three 409 refusal codes and its in-handler kind-feature 403, `progress.job.redriven`, `mirror_stuck`); nothing depends on it.
**Series**: [part 1](./2026-08-21-background-work-01-data-sync-problems.md) — `data_sync` problems (D-n) · [part 2](./2026-08-21-background-work-02-sibling-modules-problems.md) — sibling modules (Q/P/W/S/… ids) · [part 3](./2026-08-21-background-work-03-common-problems-and-requirements.md) — classes C-1…C-14, requirements R-A…R-M, open decisions Δ-1…Δ-11 · [part 4](./2026-08-21-background-work-04-solution.md) — options, decision, shared invariants · [part 5](./2026-08-21-background-work-05-queue-transport-contract.md) — queue transport contract · [part 6](./2026-08-21-background-work-06-leased-jobs-in-progress.md) — leased tier in `progress` · [part 7](./2026-08-21-background-work-07-data-sync-adoption.md) — `data_sync` adoption · [part 8](./2026-08-21-background-work-08-operator-surface.md) — operator surface.
**Scope of this spec**: the operator surface that makes the leased tier operable — **two new backend pages for the `progress` module** (a jobs list and a job detail; the module has no `backend/` directory today, only the list/detail/cancel API routes and the top bar), filters for stuck/parked/unmirrored rows, bulk re-drive and cancel, the `data_sync` dashboard's live refresh, and Retry/Cancel affordances on runs. No schema, no service change, no new API route beyond what part 6 ships; two new page URLs (category 7, additive) and one sidebar entry.

## 📝 TLDR

Part 6 gives operators the facts (`parkedAt`, `errorCode`, `cancelRequestedAt`, `mirrorAttempts`, `leaseOwner`, `leaseEpoch`, `nextRunAt`, the server-derived `redrivable` and `stuck`, `mirror_stuck`, a re-drive route with three 409 refusal codes plus a 403 for the kind's own feature, and a `progress.job.redriven` event); this spec puts them where operators look — which first means giving operators a place to look: `packages/core/src/modules/progress/` has **no backend pages** (`api/`, `data/`, `lib/`, `i18n/`, `migrations/`, tests only; the only progress UI is `packages/ui/src/backend/progress/ProgressTopBar.tsx`), so part 4's R-K score ("list/detail/cancel exist") is true of the API routes, not of pages. This spec adds the list page and the detail page, then a "stuck" filter, a "parked" badge and a Re-drive action on them and as a bulk action, a `data_sync.run.*` client broadcast so the dashboard refreshes without a manual reload, and Retry/Cancel on a run row (D-26, R-K2/K3). **Re-drive is offered exactly where part 6 admits it**: every affordance below is enabled from the DTO's `redrivable` flag, which the server derives from the same predicate as the `redrive` statement, so the UI never offers a button the route will refuse with `not_redrivable`.

## 📝 Design

| Surface | Change | Backed by |
|---|---|---|
| `GET /api/progress/jobs` list (existing) | filter `state` ∈ {stuck, parked, cancelling, unmirrored} derived server-side: **parked** = `parked_at is not null`; **cancelling** = `cancel_requested_at` set and non-terminal; **unmirrored** = terminal ∧ `subject_type` set ∧ `domain_mirrored_at is null` (deferred kinds awaiting Q5, **including rows whose mirror the reconciler has given up on** at `maxMirrorAttempts` (`mirror_stuck`) — part 6 §7 step 5 stops re-selecting those, so this filter and the `stuck` derivation are the only places they surface, until the kind's retention collects them); **stuck** = part 6's server-derived `stuck` — leased ∧ (`running` ∧ `lease_expires_at < now() − grace` ∧ (`next_run_at is null` ∨ `next_run_at < now() − pendingTtl`) ∨ `mirror_attempts >= maxMirrorAttempts`); the `next_run_at` clause — with Q1's `pendingTtl` backlog tolerance for a scheduled delivery, the bare lease grace when `next_run_at` is null (part 6 §3) — is what keeps a slice awaiting its transport retry (`failSlice` released the lease, `next_run_at` set) *or whose available retry is still queued behind other runs* out of the list, exactly as Q1 ignores it; a driver that died *after* claiming such a delivery is the null case (part 6's claim consumes the delivery, `next_run_at = null`), so it appears stuck — and re-drivable — as soon as the lease grace passes, never after `pendingTtl`. The same pass derives each row's `redrivable` from part 6 §3's predicate (leased ∧ kind registered in this process ∧ (`failed` ∨ `running` ∧ expired lease beyond grace ∧ `next_run_at` null or `pendingTtl` past)). Both derivations are the server's because the client sees neither the kind's `maxMirrorAttempts` nor the reconciler grace/`pendingTtl` | part 6 DTO fields; no new column |
| **Progress list page — new** (`packages/core/src/modules/progress/backend/progress/page.tsx` → `/backend/progress`) | `page.meta.ts` `{ requireAuth: true, requireFeatures: ['progress.view'], pageTitle, breadcrumb }`; sidebar entry under Settings → System ("Background jobs", `progress.view`); `DataTable` over `GET /api/progress/jobs` with the existing list params (`status`, `jobType`, `includeCompleted`, `page`, `pageSize ≤ 100`) plus the new `state`; columns name · kind (`jobType`) · status badge · progress · lease owner/epoch · updated; filter chips for the four states; `StatusBadge` tokens `status-warning` (cancelling, stuck) / `status-danger` (parked, unmirrored); `RowActions` ids `view`, `redrive`, `cancel` — **Re-drive** rendered only when `redrivable` (route ACL `progress.update` + kind features), **Cancel** (`progress.cancel`, no kind feature) | new page over the existing list route; `DataTable` + `RowActions` |
| **Progress detail page — new** `backend/progress/[id]/page.tsx` → `/backend/progress/[id]`, same metadata; reads `GET /api/progress/jobs/[id]`; detail sections (`.ai/ui-backend-components.md`) for identity, lease, counters, subject link (`subject_type = 'data_sync.run'` → the run page) | "parked — `errorCode`" alert (and "stuck — mirror failed `mirrorAttempts` times" when `stuck` is set and `mirrorAttempts > 0`; "stuck — lease expired" when `stuck` is set and it is not); Re-drive button when `redrivable`, Cancel when non-terminal; `leaseOwner`, `leaseEpoch` and `nextRunAt` ("retrying at …" while a transport backoff is pending) for support; a failed Re-drive is shown by its outcome — three 409 codes plus the **403** part 6 §4 declares (the kind's `requiredFeatures` are checked in the handler, after the row is loaded, because the kind is a column value and cannot sit in the route's static `requireFeatures` literal): `lock_key_held` names the live operation (link), `domain_refused` explains that the domain record is gone, `not_redrivable` that the row changed under the operator (the list refetches), and **403** that the operator may view progress jobs but not re-drive *this kind* ("re-driving a `data_sync` job needs `data_sync.run`") — a message the row action cannot pre-empt, since `redrivable` is about the row, not about the caller's features | existing detail sections |
| Bulk actions | Re-drive selected / Cancel selected via the existing bulk-operation pattern (`core:progress` + DataTable bulk guide): **one request per row, per-row outcomes, never all-or-nothing** — rows answering 409 are reported with their refusal code (`lock_key_held` / `not_redrivable` / `domain_refused`) and rows answering **403** (the kind's `requiredFeatures`, checked in-handler — part 6 §4) with the same message the detail page uses, in the operation's result list; the other rows proceed; selection of non-`redrivable` rows is allowed but those rows are skipped client-side and counted as "skipped" rather than sent | part 6 route |
| `data_sync` dashboard | `data_sync.run.*` events (incl. the new `data_sync.run.redriven`) gain `clientBroadcast: true`; the dashboard subscribes with `useAppEvent` and refetches on change — today it never auto-refreshes (`backend/data-sync/page.tsx` has no interval; part 1 D-26), so an operator who re-drives a run sees it move within one event instead of after a manual reload | `events` DOM Event Bridge |
| `data_sync` run row | **Retry is two-tiered, both existing semantics kept.** (1) job `redrivable` → **"Retry" = re-drive the run's job** (`POST /api/progress/jobs/[id]/redrive`: same run id, same `lock_key`, cursor and counters preserved, audit via `progress.job.redriven.by`). (2) job not `redrivable` and run `failed \| cancelled` → **"Retry as new run"** = the existing `POST /api/data_sync/runs/[id]/retry` (part 7: unchanged — admits cancelled runs, supports `fromBeginning`, starts from the previous cursor), which is what the dashboard and the run page call today (`page.tsx:357`, `runs/[id]/page.tsx:295`); the dialog keeps its "from the beginning" checkbox. A cancelled-by-mistake run therefore never loses its Retry. (3) neither → no Retry; "Run" starts a fresh run. A 409 from (1) (`domain_refused`, `lock_key_held`) is shown by its code and offers (2) or "Run". Cancel = `POST …/runs/[id]/cancel` (part 7: request only; the row renders "cancelling" from the response/`cancelRequestedAt` until the event arrives) | part 6 + part 7 `onRedrive`, retry route, cancel route |

Every dialog: `Cmd/Ctrl+Enter` submit, `Escape` cancel. All strings via locale files. No hardcoded status colours — `{property}-status-{status}-{role}` tokens only.

## 📝 Risks & Impact Review

| Risk | Sev | Mitigation | Residual |
|---|---|---|---|
| **Bulk Re-drive over a large selection** fans out one request per row, each of which is a `redrive` transaction (part 6 §3: CAS + `onRedrive` + enqueue) — a 100-row page re-driven at once is 100 short write transactions and 100 enqueues | Med | the list's `pageSize` is capped at 100 (the platform rule), so a single bulk action is bounded by the page; the requests run through the existing bulk-operation pattern with its progress reporting, not in one unbounded burst; non-`redrivable` rows are skipped client-side and never sent; every row is its own transaction, so a slow or refused row never holds a lock across the others | an operator can still start 100 domain operations with two clicks — deliberate (that is the point of the action) and audited: each one emits `progress.job.redriven` with `by` |
| **The row the operator clicked changed under them** — re-driven by someone else, claimed by the reconciler, or its domain row moved between list render and click | Low | already handled by the server, and the UI is built on that: `redrivable` comes from the same predicate as the `redrive` statement, and the three 409 codes plus the 403 each render a distinct message; `not_redrivable` refetches the list | a stale page shows a Re-drive button for a row the route will refuse — one refused request, no state change |
| **403 on Re-drive is not predictable from the row** — `redrivable` describes the row, the kind's `requiredFeatures` describe the caller | Low | the 403 has its own message on the detail page and in the bulk result list (part 6 §4); the sidebar entry and both pages are gated on `progress.view`, so the surface is visible to exactly the operators expected to use it | an operator with `progress.view` + `progress.update` but no kind feature sees Re-drive and is refused on click; hiding it would need per-kind feature data on every row |
| **The `progress` module gains its first `backend/` directory** — two new page URLs, a sidebar entry, i18n namespace | Low | additive (category 7): no existing route, page or component changes; the pages are ordinary `DataTable`/detail-section pages built from `.ai/ui-backend-components.md` families; guarded by the existing `progress.view` | — |
| **`clientBroadcast: true` on `data_sync.run.*`** puts run events on the SSE bridge for every connected backend session | Low | payloads unchanged and already tenant/organization-scoped by the bridge; the dashboard subscribes and refetches rather than rendering event payloads; the event volume is one per run transition, not per batch | a busy tenant's dashboards refetch on each run transition — bounded by the transition rate, and strictly less traffic than the polling this replaces (there is none today: D-26) |
| **Live refresh masks a stale dashboard** if the bridge is down | Low | the refetch is triggered by events but the page still loads its data on mount and on manual reload, exactly as today | an operator on a dead SSE connection is back to today's behaviour (manual reload) with no error shown |
| Compat surfaces touched | — | 5 events (`clientBroadcast` added, payloads unchanged); 7 two new page URLs + one list filter param; 10 ACL none new | — |
| Rollback | — | UI-only: revert the package; the list filter param is ignored by the previous server; the page URLs disappear with the files | no data to migrate back |

## 📋 Integration coverage (`.ai/qa/tests/`)

0. Progress pages exist and are guarded: `/backend/progress` renders the list for a user with `progress.view` and is refused without it; the sidebar entry appears; a row links to `/backend/progress/[id]`, which renders the detail sections and the subject link for a `data_sync` job; `pageSize` capped at 100.
1. Progress list: a parked job appears under the "parked" filter, shows the badge, and Re-drive moves it to pending (assert via the API); a terminal failed (non-parked) job also shows Re-drive; a `completed` and a `cancelled` job do not (`redrivable: false`). A user holding `progress.view` + `progress.update` but **not** the kind's `requiredFeatures` (`data_sync.run`) sees the Re-drive action on a `redrivable` row, gets **403** on click and the "needs `data_sync.run`" message, and the row is unchanged (part 6 §4).
2. Bulk Re-drive on two parked jobs; bulk Cancel on two running jobs → both "cancelling".
2b. **Bulk Re-drive with a partial failure**: select one parked job, one parked job whose lock key is held by a live operation, and one completed job → the result lists one re-driven, one `lock_key_held` naming the live job, one skipped; the re-driven row is `pending`, the others unchanged.
3. `data_sync` dashboard updates within one event of a run transition without a page reload — including after a Retry (`data_sync.run.redriven`).
4. Run row Retry/Cancel: Retry on a parked run re-drives the *same* run (run id unchanged, `sync_runs.status` back to `running`); on a **cancelled** run the row shows "Retry as new run", which calls the existing retry route and creates a new run from the cancelled run's cursor (and from null with "from the beginning"); the cancelling state renders from the cancel route's `cancelling` response and resolves on `data_sync.run.cancelled`; Retry on a run whose `sync_runs` row was deleted shows the `domain_refused` message and offers "Retry as new run"/"Run" instead.
5. Screenshots attached for QA (`needs-qa`): list with filters, detail with parked alert, dashboard live update.
