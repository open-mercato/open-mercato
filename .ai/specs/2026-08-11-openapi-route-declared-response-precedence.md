# OpenAPI Route-Declared Response Precedence

- **Status:** Implemented (pending review)
- **Date:** 2026-08-11
- **Type:** OSS shared library bug fix
- **Package:** `@open-mercato/shared` (`src/lib/openapi/generator.ts`)

## TLDR

A response a route declares for a status code must win over the response the generator infers from route metadata. Previously the metadata-inferred `401`/`403` overwrote the route's own declaration, so hand-written authorization responses were replaced by generic text and — because inferred entries are marked `x-autoGenerated` and both docs renderers skip those — disappeared from the rendered documentation.

## Overview

`buildResponses()` assembles the OpenAPI `responses` object for one operation from three sources:

1. `openApi.responses` — success and other statuses the route declares.
2. `openApi.errors` — error statuses the route declares.
3. Entries inferred from route metadata: `401` when `requireAuth` is set, `403` when `requireFeatures` is non-empty. These carry `xAutoGenerated: true`.

Sources 1 and 2 are explicit author intent. Source 3 is a fallback for routes that did not document their authorization failures. The generator had no rule expressing that ordering.

## Problem Statement

The inferred entries were appended to the same array as the route's declared errors and the whole array was walked with an unconditional assignment:

```typescript
const errorList = [...(errors ?? [])]
if (metadata?.requireAuth) errorList.push({ status: 401, /* ... */ xAutoGenerated: true })
if (metadata?.requireFeatures?.length) errorList.push({ status: 403, /* ... */ xAutoGenerated: true })
// ...
for (const res of [...list, ...errorList]) {
  entries[String(res.status || 200)] = { /* ... */ }
}
```

Because the inferred entries were appended last and each iteration assigned `entries[status]` unconditionally, they overwrote any route declaration for the same status — whether that declaration came from `responses` or from `errors`.

Two consequences, neither of which produced a warning at generation time:

- **Description and schema loss.** A route documenting `403 – "outside the active scope"` with a typed error body published the generic `"Forbidden – missing required features"` with a bare `{ error: string }` body instead.
- **Silent removal from rendered docs.** The overwriting entry carries `x-autoGenerated: true`, and both the markdown emitter (`generateMarkdownFromOpenApi`) and the API Explorer skip responses carrying that marker. A response the author deliberately documented was therefore dropped from the docs entirely, and a hand-written response was mislabelled as generated.

Every route combining `requireAuth`/`requireFeatures` metadata with its own `401`/`403` documentation was affected.

## Proposed Solution

Make precedence explicit rather than positional:

- Collect metadata-inferred entries in their own list instead of appending them to the route's declared errors.
- Emit every explicitly declared entry (`responses` then `errors`) first.
- Emit each inferred entry only when its status key is not already present.

An explicit declaration through **either** `responses` or `errors` therefore always wins, and inferred entries remain a fallback for undocumented statuses while keeping their `x-autoGenerated` marker.

### Why reordering the single loop is not sufficient

Swapping the iteration to `[...errorList, ...list]` fixes only declarations made through `responses`. A status declared through `errors` sits inside the same array *before* the inferred entry, so the inferred entry still overwrites it. Correctness here cannot come from array order; it has to come from an explicit "do not overwrite an existing key" rule applied to the inferred entries alone.

## Architecture

```text
responses[]  ─┐
              ├─> emit unconditionally (declared wins, last declared wins on collision)
errors[]     ─┘
                     │
metadata     ────────┴─> emit only when the status key is still absent
(401/403)                (keeps x-autoGenerated: true)
```

## Scope

- Document generation only. Runtime authorization is enforced by the API dispatcher and is untouched; `buildResponses` has no runtime role.
- No change to `OpenApiResponseDoc`, `OpenApiMethodDoc`, or any other exported type.
- Collisions **between two explicit sources** (the same status in both `responses` and `errors`) retain the existing last-wins behavior. Redefining that is an unrelated behavior change and is deliberately out of scope.

## Migration & Backward Compatibility

No contract surface changes: no type, signature, import path, route, DB, DI key, ACL feature, or generated-file format is modified. `x-autoGenerated` retains its meaning — it now marks only genuinely generated entries.

The generated OpenAPI document does change for affected operations, which is the point of the fix. For any route that declared its own `401`/`403` alongside `requireAuth`/`requireFeatures` metadata, the published response now carries the route's description and schema, no longer carries `x-autoGenerated`, and consequently becomes visible in the markdown docs and the API Explorer where it was previously suppressed. Consumers that relied on those responses being absent or generically worded will see the corrected content.

## Testing

`packages/shared/src/lib/openapi/__tests__/response-precedence.test.ts` exercises the public `buildOpenApiDocument` against a route whose metadata sets both `requireAuth` and `requireFeatures`:

- `403` declared through `responses` keeps its description, schema, and absence of `x-autoGenerated`.
- `403` declared through `errors` keeps the same.
- `401` declared through `errors` keeps its description.
- `401` declared through `responses` keeps its description.
- A route declaring neither still receives both inferred entries, each marked `x-autoGenerated: true`, while an unrelated declared `404` is left alone.
- A declared `403` coexists with the inferred `401` on the same operation.
- The synthesised success response still appears when the route declares only errors.
- A route with no `requireAuth`/`requireFeatures` metadata receives no inferred entries at all, and a route requiring auth without features receives only the `401`.
- The explicit-vs-explicit collision documented above as out of scope is pinned: a status declared in both `responses` and `errors` resolves to the `errors` entry.

The suite was verified to be non-vacuous by temporarily restoring the single unconditional loop (6 of 13 assertions fail) and by temporarily applying the naive `[...errorList, ...inferredList, ...list]` reorder (4 of 10 failed against the suite as it stood then — every `errors`-declared case).

| Risk | Severity | Affected area | Mitigation | Residual risk |

| Published docs change for every route that declared its own `401`/`403` — those responses become visible where the `x-autoGenerated` filter previously hid them | Low | Generated OpenAPI document, markdown docs, API Explorer | This is the intended correction; the new content is the route's own authored documentation | Consumers diffing the generated document will see additions and reworded entries on affected operations |

## Final Compliance Report

- No `packages/enterprise/` file touched.
- No contract surface modified (types, signatures, import paths, event IDs, widget spot IDs, API routes, DB schema, DI keys, ACL features, notification IDs, CLI commands, generated-file formats all unchanged).
- No database migration, no API surface change, no UI-rendering file changed.
- No new dependency, no `any` introduced, no user-facing string added.
- Behavior change is confined to the generated OpenAPI document and is covered by unit tests shipped in the same change.

## Success Metrics

An operation's published `responses` entry for a status the route documents is byte-identical to that documentation, and `x-autoGenerated` appears only on entries the generator synthesised.
