# An AST-Capable `GeneratorPlugin` Output Contract

> One of three specs split out of issue [#1637](https://github.com/open-mercato/open-mercato/issues/1637).
> Siblings: [`2026-07-30-ast-first-package-build-scripts.md`](2026-07-30-ast-first-package-build-scripts.md) (package build scripts),
> [`2026-07-30-ast-first-module-registry-emitters.md`](2026-07-30-ast-first-module-registry-emitters.md) (CLI-internal emitters).
> This is the only one of the three that changes a public contract, and the only one with **no OSS consumer today** — read § Decisions for the maintainer before scheduling it.

## TLDR

**Key Points:**
- `GeneratorPlugin.buildOutput` forces every plugin author to return a generated file as a `string`. This spec adds a structural, AST-backed alternative and deprecates the string hook.
- The new shape is a **union of two interfaces**, not an optional field bolted onto the old one. A genuinely AST-only plugin — no string emitter at all — type-checks. The published `GeneratorPlugin` keeps its exact resolved shape.
- The builder handed to the AST hook has **no free-form statement or import method**. Raw TypeScript enters only through explicitly named `{ kind: 'raw' }` expression and type nodes, each parsed and rejected at generation time if it is not a single valid expression/type. Every built file is checked for syntactic diagnostics before it is written.
- `packages/enterprise` holds the repository's only `GeneratorPlugin` implementation and is commercially licensed, so it is out of scope. The AST path is exercised end-to-end by fixture plugins in the CLI test suite instead.

**Scope:**
- `packages/shared/src/modules/generators/types.ts` — the union, the expression vocabulary, the builder interface
- `packages/shared/src/modules/generators/index.ts` — new exports
- `packages/cli` — the builder implementation on the existing AST helpers, plus host resolution and the diagnostics gate
- Compile-time contract tests, runtime resolution tests, fixture AST plugins
- `UPGRADE_NOTES.md`, `BACKWARD_COMPATIBILITY.md` § 2, `packages/cli/AGENTS.md`, `apps/docs/docs/architecture/generators.mdx`

**Out of scope:**
- `packages/enterprise/src/modules/security/generators.ts` — commercially licensed; external contributions are not accepted. Its migration belongs to its owner and is exactly what the additive design enables.
- `bootstrapRegistration.registrationImports` / `buildCall` — a separate string surface on the same interface; see § Non-Goals.
- The CLI's own emitters — see the sibling spec.

## Overview

Modules declare extra generated output files by exporting `generatorPlugins: GeneratorPlugin[]` from a module-root `generators.ts`. The CLI discovers them by dynamic import at generation time, collects per-module import statements and entry expressions, and asks each plugin to render its file:

```ts
// packages/cli/src/lib/generators/module-registry.ts:3389-3397
for (const [pluginId, plugin] of pluginRegistry) {
  const state = pluginState.get(pluginId)!
  const importSection = state.imports.join('\n')
  const entriesLiteral = state.configs.join(',\n  ')
  const content = plugin.buildOutput({ importSection, entriesLiteral })
  writeGeneratedFile({ outFile, checksumFile, content, structureChecksum, result, quiet })
}
```

`importSection` and `entriesLiteral` are pre-joined text. The plugin's only job is to wrap them in more text. Every existing implementation therefore looks like this (`packages/enterprise/src/modules/security/generators.ts:3-10`):

```ts
return `// AUTO-GENERATED by mercato generate registry
${importSection ? `${importSection}\n` : ''}type SecurityMfaProviderEntry = { moduleId: string; providers: unknown[] }

export const securityMfaProviderEntries: SecurityMfaProviderEntry[] = [
${entriesLiteral ? `  ${entriesLiteral}\n` : ''}]
`
```

Verified against `develop@ecc10b3db`.

> **Market Reference**: Angular's `@schematics/angular` and Nx both kept a string/text hook alive for years after introducing typed tree APIs, and both learned the same lesson this spec encodes: an *optional* new hook alongside a *required* old one is not an adoption path, because a new author must still satisfy the old one. Angular's `Rule` union and Nx's `Generator`/`Executor` overloads both ended up expressed as unions where each variant is complete on its own. Adopted: union-of-complete-variants plus a dated deprecation window. Rejected: exposing the underlying compiler AST type in the public contract (Angular exposes `ts.SourceFile` in some schematic helpers and is stuck supporting a TypeScript major range because of it).

## Problem Statement

**1. The type signature steers authors to string concatenation.** `buildOutput: (params: { importSection: string; entriesLiteral: string }) => string`. Nothing else is on offer. A plugin cannot express "an exported const of this type initialised to this array" — only "here is some text".

**2. String assembly moves the failure to the consumer.** A missing comma or newline produces a generated `.ts` file that is written successfully, checksummed, and then fails at the compile step of whatever imports it. The AST path in the CLI cannot emit an unparseable file; plugin output can, and does not even get a syntax check today.

**3. An optional hook next to a required legacy hook is not an adoption path.** This was the substantive finding against the first draft of this design (PR [#4636](https://github.com/open-mercato/open-mercato/pull/4636) review, High-2): if `buildOutput` stays required while `buildAstOutput` is optional, a new plugin author must still write the deprecated string emitter, and the "AST hook only" test case cannot be written without defeating the type system. Keeping the legacy field required is not free — it is precisely what blocks adoption of the new path.

**4. A builder that accepts arbitrary statement and import strings does not solve the problem it claims to.** This was the second finding (Medium-1): `addStatement(statement: string)` and `addImportStatement(statement: string)` let a plugin assemble unchecked TypeScript through a different door, so the guarantee "the AST path cannot emit an invalid file" would be false.

**5. `packages/shared` must not gain a `ts-morph` dependency in its public types.** Every package and every third-party module imports `@open-mercato/shared`. Exposing `ts-morph`'s `SourceFile` in the hook signature would put a codegen-only dependency, pinned to a specific `ts-morph` major, into everyone's type graph.

## Proposed Solution

### The union

The published `GeneratorPlugin` is refactored into a base interface plus a legacy extension. Splitting an interface into `Base` + `extends Base` preserves the **resolved member set**, so structural readers and `import type { GeneratorPlugin }` consumers see no change. Two optional members are added to it, which § 2 of `BACKWARD_COMPATIBILITY.md` permits freely.

```ts
// packages/shared/src/modules/generators/types.ts

/** Fields every generator plugin provides regardless of how it emits output. */
export interface GeneratorPluginBase {
  /** Unique ID, e.g. 'security.mfa-providers' */
  id: string
  /** Convention file path relative to module root, e.g. 'security.mfa-providers.ts' */
  conventionFile: string
  /** Import variable prefix used in generated code, e.g. 'SECURITY_MFA_PROVIDERS' */
  importPrefix: string
  /** Output filename relative to the generated output directory */
  outputFileName: string
  /** Structural entry producer. Preferred over `configExpr` when present. */
  configEntry?: (params: { importName: string; moduleId: string }) => GeneratedExpression
  /** Contributes a registration call to `bootstrap-registrations.generated.ts`. */
  bootstrapRegistration?: GeneratorPluginBootstrapRegistration
}

/**
 * String-emitting plugin. Resolved shape is unchanged from the pre-2026-07-30
 * `GeneratorPlugin`; `configEntry` and `buildAstOutput` are additive optionals.
 */
export interface GeneratorPlugin extends GeneratorPluginBase {
  configExpr: (importName: string, moduleId: string) => string
  /**
   * @deprecated Use `buildAstOutput` (see `AstGeneratorPlugin`). Still honoured when
   * `buildAstOutput` is absent. Scheduled for removal no earlier than the second minor
   * release after `buildAstOutput` ships; see UPGRADE_NOTES.md.
   */
  buildOutput: (params: { importSection: string; entriesLiteral: string }) => string
  buildAstOutput?: (context: GeneratorPluginAstContext) => void
}

/** AST-emitting plugin. Requires no string emitter. */
export interface AstGeneratorPlugin extends GeneratorPluginBase {
  buildAstOutput: (context: GeneratorPluginAstContext) => void
  /** Optional legacy entry producer; wrapped as a validated raw expression when used. */
  configExpr?: (importName: string, moduleId: string) => string
  /** @deprecated Ignored when `buildAstOutput` is present. */
  buildOutput?: (params: { importSection: string; entriesLiteral: string }) => string
}

/** What the CLI host accepts. */
export type AnyGeneratorPlugin = GeneratorPlugin | AstGeneratorPlugin

export interface GeneratorPluginAstContext {
  builder: GeneratedFileBuilder
  imports: readonly GeneratedImportDeclaration[]
  entries: readonly GeneratedExpression[]
}
```

**Why the union works and how the host narrows it.** Both constituents declare `configExpr`, `buildOutput` and `buildAstOutput` — required in one, optional in the other — so property access on `AnyGeneratorPlugin` resolves without a discriminant, yielding `Fn | undefined` for each. The host narrows with a plain `typeof plugin.buildAstOutput === 'function'` check; no type predicate, no cast, no discriminant field. `GeneratorPlugin[]` remains assignable to `AnyGeneratorPlugin[]`, so an existing `generatorPlugins: GeneratorPlugin[]` export keeps compiling untouched. An object with neither output hook satisfies neither constituent and is a **compile error**.

### The expression vocabulary

Declared in `packages/shared` without importing `ts-morph`. The CLI maps each node onto the existing writers in `packages/cli/src/lib/generators/ast/writers.ts` — this is a serialisable mirror of the vocabulary that is already there (`GeneratedValue`, `GeneratedObjectEntry`, `objectLiteral`, `arrayLiteral`, `callExpression`, `asExpression`, `nullishCoalesce`, `propertyAccess`), not a second vocabulary.

```ts
export type GeneratedExpression =
  | { kind: 'literal'; value: string | number | boolean | null }
  | { kind: 'reference'; name: string }
  | { kind: 'array'; items: readonly GeneratedExpression[] }
  | { kind: 'object'; properties: readonly GeneratedObjectProperty[] }
  | { kind: 'propertyAccess'; expression: GeneratedExpression; name: string }
  | { kind: 'call'; callee: GeneratedExpression; args: readonly GeneratedExpression[] }
  | { kind: 'as'; expression: GeneratedExpression; type: GeneratedTypeReference }
  | { kind: 'nullishCoalesce'; operands: readonly GeneratedExpression[] }
  /** Escape hatch. Parsed at generation time; rejected unless it is exactly one expression. */
  | { kind: 'raw'; source: string }

export type GeneratedObjectProperty =
  | { kind: 'property'; name: string; value: GeneratedExpression }
  | { kind: 'spread'; value: GeneratedExpression }

export type GeneratedTypeReference =
  | { kind: 'name'; name: string; typeArguments?: readonly GeneratedTypeReference[] }
  | { kind: 'array'; element: GeneratedTypeReference }
  /** Escape hatch. Parsed at generation time; rejected unless it is exactly one type node. */
  | { kind: 'raw'; source: string }

export interface GeneratedImportDeclaration {
  moduleSpecifier: string
  defaultImport?: string
  namespaceImport?: string
  namedImports?: readonly { name: string; alias?: string; isTypeOnly?: boolean }[]
  isTypeOnly?: boolean
}
```

Every node carries a required `kind` discriminant, including `GeneratedObjectProperty.kind: 'property'`, so the CLI's mapper can `switch (node.kind)` exhaustively and a new kind added later is a compile error at the mapper rather than a silent fall-through.

**What the type vocabulary does not cover.** `GeneratedTypeReference` models named references (with type arguments) and arrays, and nothing else — no object type literal, no union, no function type. That is a deliberate floor, not an oversight, but it means the first realistic adopter reaches for the escape hatch immediately: the only known implementation declares `type SecurityMfaProviderEntry = { moduleId: string; providers: unknown[] }`, which is expressible only as `{ kind: 'raw', source: '{ moduleId: string; providers: unknown[] }' }`. That raw type node is parsed and rejected unless it is exactly one type node, so the guarantee holds — but the structural coverage of *type* positions is materially thinner than of *expression* positions, and a reader should not infer otherwise. If a real consumer turns out to declare object type aliases routinely, the additive fix is one more kind (`{ kind: 'members'; members: readonly { name: string; type: GeneratedTypeReference; isOptional?: boolean }[] }`), which can ship on its own timeline without touching the plugin interface.

### The builder

```ts
export interface GeneratedFileBuilder {
  addImport(declaration: GeneratedImportDeclaration): void
  addTypeAlias(options: { name: string; type: GeneratedTypeReference; isExported?: boolean }): void
  addConst(options: {
    name: string
    type?: GeneratedTypeReference
    initializer: GeneratedExpression
    isExported?: boolean
  }): void
  /** Emits `export default <name>` for an identifier declared earlier in the file. */
  addDefaultExport(name: string): void
}
```

There is deliberately **no** `addStatement(string)` and **no** `addImportStatement(string)`. Imports are structural, so an import cannot be malformed. Declarations are structural, so the file's statement list is entirely AST-managed. The only raw source a plugin can contribute is a single expression or a single type node, through a node kind whose name says so.

**What the honest guarantee is.** The AST path guarantees that *file structure* — imports, declarations, exports, ordering, formatting — is AST-managed and that no contributed fragment reaches the output unparsed. It does not claim every leaf expression is structurally typed: `{ kind: 'raw' }` exists, is named, and is validated. Validation has three parts:

1. **Fragment validation.** Each `{ kind: 'raw' }` expression is parsed as an expression and each raw type as a type node. Anything that is not exactly one node — extra statements, trailing tokens, a bare `;` — is a generation-time error naming the plugin id, the node path and the offending source. This is the same technique `ast/imports.ts:11` already uses for import statements, where `toImportSpec` throws on anything it cannot parse.
2. **Whole-file validation.** After the hook returns, the built source file is checked for **syntactic** diagnostics before `writeGeneratedFile` is called; any diagnostic aborts generation, naming the plugin and the position. Semantic diagnostics are deliberately not checked: generated files import modules that only resolve inside the consumer's project, so semantic checking would be noise. `structural-contracts.test.ts` already applies exactly this syntax-only standard to every CLI-generated file.
3. **Emptiness check.** A plugin whose file ends up with no declarations is a generation-time error naming the plugin id, rather than a silently empty artifact.

### Resolution rules in the host

| Situation | Behavior |
|---|---|
| `buildAstOutput` present | It is used. `buildOutput`, if also present, is not called; a one-line warning names the plugin id so the author knows the string emitter is dead code. |
| Only `buildOutput` present | It is used, unchanged, byte for byte as today. No syntax gate is applied to its output (see Edge Cases). |
| Neither present | Generation fails with an error naming the plugin id and both hook names. Today the same situation is a bare `TypeError: plugin.buildOutput is not a function`. |
| `configEntry` present | Used to build each entry as a `GeneratedExpression`. |
| Only `configExpr` present, AST hook in use | Each returned string is wrapped as `{ kind: 'raw', source }` and therefore parse-validated — strictly better than today's blind interpolation. |
| Neither entry producer present | Generation fails with an error naming the plugin id. This is the one invariant the type system cannot express in this design (see Residual gaps). |

### Design Decisions

| Decision | Rationale |
|----------|-----------|
| Union of two complete interfaces, not one interface with two optional hooks | The optional-hook shape does not permit an AST-only plugin, which was the whole point (review finding High-2). |
| `GeneratorPlugin` refactored into `GeneratorPluginBase` + `extends`, resolved shape preserved | Structurally identical member set, so no consumer observes it. Asserted by a compile-time test against a frozen inline copy of the pre-change shape. |
| `buildOutput` stays **required on `GeneratorPlugin`** and becomes optional only on the new `AstGeneratorPlugin` | Making it optional on the published interface is an observable narrowing for structural readers; introducing the AST variant costs nothing and achieves the same adoption path. |
| Structural vocabulary declared in `shared`, implemented in `cli`, no `ts-morph` import | `shared` is imported by every package and every third-party module; a codegen-only dependency must not enter its public type graph, and the contract must not be coupled to a `ts-morph` major. |
| Vocabulary mirrors `ast/writers.ts` rather than inventing kinds | The CLI already has these builders. The mirror is a serialisation of them, so there is one vocabulary with two representations, not two vocabularies. |
| No free-form statement/import strings on the builder | Otherwise the "cannot emit an invalid file" guarantee is false (review finding Medium-1). |
| Raw fragments allowed but named and parse-validated | The alternative — a complete expression grammar in a public type — is a large surface for a contract with zero consumers today. Naming and validating the escape is the honest middle. |
| Syntax gate applies to AST-hook output only, not to legacy `buildOutput` output | Applying it to the legacy path would turn an existing silent breakage into a hard generation failure for an unchanged plugin — a behavior change smuggled into an additive release. Offered as a follow-up, opt-in. |
| Ship it last of the three specs | It is the only public-contract change, and the two migrations should have exercised the AST helpers first. |
| `packages/enterprise` untouched; AST path validated by fixture plugins | Commercial licence, no external contributions. `module-subset.test.ts:124-165` already builds an inline CommonJS `generators.ts` fixture mirroring the enterprise plugins; the AST variant is added beside it. |

### Alternatives Considered

| Alternative | Why Rejected |
|-------------|-------------|
| Optional `buildAstOutput`, `buildOutput` left required (the first draft) | An AST-only plugin cannot be written; the planned "AST hook only" test cannot type-check. Rejected in review. |
| Replace `buildOutput` outright | Breaks every third-party plugin in one release; forbidden by `BACKWARD_COMPATIBILITY.md`. |
| Make `buildOutput` optional on `GeneratorPlugin` itself | Observable narrowing for structural readers, and unnecessary once the union exists. |
| Expose `ts-morph`'s `SourceFile` in the hook | Puts a build-time dependency in `shared`'s public types for every consumer and pins the contract to a `ts-morph` major. |
| A complete expression/statement grammar in `shared` (no raw escape at all) | Large public surface for a contract with no consumer yet, and still incomplete — arrow bodies, generics and JSX would all need modelling. `{ kind: 'raw' }` plus validation gets the guarantee that matters at a fraction of the surface. |
| Keep `addStatement(string)` for convenience | Reintroduces the unchecked path this spec exists to close. |
| Migrate `packages/enterprise` in the same change | Not legally available to external contributors. |
| Fold this into the CLI-emitter spec | Different blast radius, different review requirements (`BACKWARD_COMPATIBILITY.md`, `UPGRADE_NOTES.md`, deprecation window), and neither needs the other. Splitting was the review's primary finding. |

### Non-Goals

`GeneratorPluginBootstrapRegistration.registrationImports: string[]` and `buildCall: (name) => string` are a second string surface on the same interface. They are left alone here: `registrationImports` entries are already parse-validated the moment the host hands them to `addImportStatements`, and `buildCall` produces a call expression inside a function body that the sibling CLI spec keeps as a string on purpose. Typing them is a natural follow-up once this contract has a real consumer — designing it now would freeze a second speculative shape.

## Architecture

```
packages/shared/src/modules/generators/types.ts        [contract: union + vocabulary + builder interface]
        │ declared, zero dependencies
        ▼
packages/cli/src/lib/generators/plugin-file-builder.ts [NEW: implements GeneratedFileBuilder]
        │ maps GeneratedExpression ──► ast/writers.ts   (objectLiteral, arrayLiteral, callExpression,
        │ maps GeneratedImportDeclaration ──► ast/imports.ts        asExpression, nullishCoalesce, …)
        │ validates { kind: 'raw' } via the TS parser  (same technique as ast/imports.ts toImportSpec)
        ▼
packages/cli/src/lib/generators/module-registry.ts     [host: resolution + syntax gate + writeGeneratedFile]
        ▲
packages/enterprise/.../security/generators.ts         [only real consumer — NOT TOUCHED, keeps using buildOutput]
packages/cli/.../__tests__/  fixture plugins           [AST-path coverage in OSS]
```

No new AST helper primitive is required; if a mapping proves one missing it is added to `writers.ts` beside the existing ~45 writers.

### Data Models

None. No entity, table, migration or persisted field is introduced or changed.

## API Contracts

No HTTP endpoint or CLI command changes. The contract surface is `BACKWARD_COMPATIBILITY.md` **§ 2 (Type Definitions & Interfaces, STABLE)**.

Note that `GeneratorPlugin` is **not currently enumerated** in § 2's immutable-required-fields list, even though it is a documented plugin contract (`packages/cli/AGENTS.md` § Generator Plugins, `apps/docs/docs/architecture/generators.mdx`). Adding it is part of this spec's deliverable:

```
- `GeneratorPlugin`: `id`, `conventionFile`, `importPrefix`, `configExpr`, `outputFileName`,
  `buildOutput` — MUST NOT remove before the removal release announced in UPGRADE_NOTES.md;
  `configEntry`, `buildAstOutput`, `bootstrapRegistration` remain optional.
  `AstGeneratorPlugin`: `id`, `conventionFile`, `importPrefix`, `outputFileName`,
  `buildAstOutput` — MUST NOT remove.
```

| Change | Classification |
|---|---|
| `GeneratorPlugin` split into `GeneratorPluginBase` + `extends` | ✓ Not a change — identical resolved member set (asserted by compile-time test) |
| `configEntry?`, `buildAstOutput?` added to `GeneratorPlugin` | ✓ ADDITIVE (optional fields) |
| `GeneratorPluginBase`, `AstGeneratorPlugin`, `AnyGeneratorPlugin`, `GeneratorPluginAstContext`, `GeneratedFileBuilder`, `GeneratedExpression`, `GeneratedObjectProperty`, `GeneratedTypeReference`, `GeneratedImportDeclaration` exported | ✓ ADDITIVE (new types, no rename) |
| `buildOutput` marked `@deprecated`, still honoured | ✓ ADDITIVE — deprecation protocol: `@deprecated` JSDoc, bridge kept ≥ 1 minor, `UPGRADE_NOTES.md` entry, this spec as the referenced document |
| Host accepts `AnyGeneratorPlugin` instead of `GeneratorPlugin` | ✓ Widening — `GeneratorPlugin[]` stays assignable |
| Error instead of `TypeError` when no hook is present | ✓ Improvement to an already-failing path |

**Deprecation timeline.** `buildOutput` is removed no earlier than the second minor release after `buildAstOutput` ships, and only once `packages/enterprise` has migrated. `configExpr` becomes optional on `GeneratorPlugin` in the same removal release, not before.

## Edge Cases & Failure Scenarios

| Scenario | Behavior | Test |
|---|---|---|
| Plugin defines both hooks | `buildAstOutput` wins; a warning names the plugin id | runtime resolution test |
| Plugin defines only `buildOutput` | Unchanged behavior, byte-identical output | runtime resolution test; the enterprise plugin is the live case |
| Plugin defines neither | Generation fails naming the plugin id and both hooks; also a compile error under `AnyGeneratorPlugin` | runtime test + `@ts-expect-error` compile-time test |
| Plugin defines `buildAstOutput` but no entry producer | Generation fails naming the plugin id. Not expressible as a compile error in this design — see Residual gaps | runtime resolution test |
| `{ kind: 'raw', source: "1 as any; sideEffect()" }` | Rejected: parses to more than one expression. Error names plugin id, node path, source | fragment-validation test |
| `{ kind: 'raw', source: "" }` or whitespace | Rejected as not an expression | fragment-validation test |
| `{ kind: 'raw' }` type node that is not a type (`"return 1"`) | Rejected as not a type node | fragment-validation test |
| Deeply nested object/array with a raw leaf | Validated at every raw leaf; the error path identifies the leaf (`entries[2].properties.targets`) | fragment-validation test |
| Hook adds nothing to the builder | Generation fails: empty generated file, plugin id named | resolution test |
| Hook throws | Generation fails with the plugin id prefixed onto the original error, not an anonymous stack | resolution test |
| Two plugins share an `id` | Unchanged: first registration wins (`module-registry.ts:2867`) | existing behavior |
| Two plugins target the same `outputFileName` | Unchanged and still unguarded — the second write clobbers the first. Out of scope; noted as a follow-up | — |
| Legacy `buildOutput` returns invalid TypeScript | Unchanged: written as-is, fails at the consumer's compile step. Deliberate — see Design Decisions | — |
| Plugin file is a CommonJS `generators.ts` (as the test fixtures are) | Unchanged: the host dynamic-imports it and reads `generatorPlugins ?? default` | fixture tests |

### Residual gaps

- **No entry producer.** An `AstGeneratorPlugin` with neither `configEntry` nor `configExpr` type-checks but fails at generation time with a named error. Closing this at the type level would require a second union axis (four constituents) whose error messages are materially worse than the runtime error. Deliberate.
- **Legacy output is not syntax-checked.** By design, to avoid turning an existing silent breakage into a hard failure in an additive release. Follow-up: an opt-in `OM_GENERATE_STRICT_PLUGIN_SYNTAX` gate.
- **Type positions are thinner than expression positions.** `GeneratedTypeReference` models only named references and arrays, so an object type alias — what the only known implementation declares — goes through the validated `{ kind: 'raw' }` type node. The syntax guarantee is unaffected; the *structural* guarantee is weaker for types than for expressions, and a `{ kind: 'members' }` kind is the additive fix if a real consumer needs it.
- **Zero OSS consumers.** The AST path is covered by fixture plugins, not by production code. See below.

## Risks & Impact Review

| Risk | Severity | Affected area | Mitigation | Residual |
|---|---|---|---|---|
| The contract is designed with no real consumer and turns out wrong | **High** | a public, `BACKWARD_COMPATIBILITY.md`-governed surface that then cannot be changed freely | Ship this spec **last** of the three, so the two migrations have exercised the same helpers first; keep the vocabulary minimal (nine expression kinds, three type kinds) so extension stays additive; validate against the only known implementation by rebuilding the enterprise plugins' output shape as read-only test fixtures without touching that package | Real. This is the maintainer decision in D1 below — the cheapest mitigation available is not to ship it yet |
| `GeneratorPlugin` refactor is not actually shape-preserving | Medium | every third-party plugin | Compile-time test asserting mutual assignability with a frozen inline copy of the pre-change shape, in both directions | None once the test exists |
| A plugin adopts `buildAstOutput`, then `ts-morph` changes behavior under it | Low | plugin authors | The contract exposes no `ts-morph` type; the builder is the seam, so a `ts-morph` major is a CLI-internal upgrade | None |
| Raw-fragment validation is bypassable | Low | the syntax guarantee | Two layers: per-fragment parse plus whole-file syntactic diagnostics before write | A raw fragment that is syntactically valid but semantically wrong still reaches the file — same as today, and out of reach of a syntax gate |
| New public surface (nine exported types) that later needs pruning | Medium | `shared`'s public API | All new; nothing is removed. If a kind proves useless it can be deprecated on its own timeline without touching the plugin interface | Some surface will probably go unused |
| Warning noise for a plugin defining both hooks | Low | generate output | One line per plugin per run | None |
| Enterprise plugin breaks despite being untouched | Low | commercial edition | It satisfies `GeneratorPlugin`, which is assignable to `AnyGeneratorPlugin`; the resolution rule calls `buildOutput` exactly as today; a fixture mirroring it is asserted byte-identical before and after | None |

**Blast radius.** One public interface in `packages/shared`, one host loop in `packages/cli`, plus new types. No runtime, tenant, data, UI, or HTTP surface. The output of every existing plugin is byte-identical.

**Compatibility.** § 2 (Type Definitions & Interfaces, STABLE) — additive only, with the full deprecation protocol applied to `buildOutput`: `@deprecated` JSDoc, bridge retained for ≥ 1 minor, `UPGRADE_NOTES.md` entry, this spec as the referenced document, and `GeneratorPlugin` added to § 2's enumeration so the next change to it is governed.

**Rollback.** A single revert. The hook is opt-in and, with `packages/enterprise` out of scope, has no adopter to strand.

**What this does not change.** `writeGeneratedFile`, the structure-checksum mechanism, plugin discovery, the `id` de-duplication rule, the set of generated files and their paths, and `bootstrapRegistration` handling.

## Phasing

One phase — the contract, its implementation, its tests, and its documentation must land together or the contract is undocumented and unproven. It is sequenced **after** both sibling specs.

## Implementation Plan

1. **Compile-time contract tests first.** Add `packages/shared/src/modules/generators/__tests__/plugin-contract.types.test.ts` (type-level only, no runtime assertions) covering: (a) a frozen inline copy of the pre-change `GeneratorPlugin` shape is mutually assignable with the new `GeneratorPlugin`; (b) legacy-only plugin satisfies `GeneratorPlugin` and `AnyGeneratorPlugin`; (c) AST-only plugin (no `buildOutput`, no `configExpr`) satisfies `AstGeneratorPlugin` and `AnyGeneratorPlugin`; (d) both-hooks plugin satisfies `AnyGeneratorPlugin`; (e) neither-hook object is rejected — `@ts-expect-error`; (f) `GeneratorPlugin[]` is assignable to `AnyGeneratorPlugin[]`. Written against the *current* types, (c)–(e) initially failing, so the type work is driven by them.

## Decisions for the maintainer

| # | Question | Default in this spec |
|---|---|---|
| D1 | Should this ship at all before an OSS consumer exists? The only implementation of `GeneratorPlugin` is in `packages/enterprise`, which is out of scope for external contributors — so this freezes a public, BC-governed shape with zero production consumers and only fixture coverage. | **Ship it last, after both sibling specs.** The issue asks for it and the additive design is what lets the enterprise owner migrate on their own schedule. If you would rather wait for a consumer, this spec can be parked without affecting the other two — they have no dependency on it. |
| D2 | Union of two interfaces (`GeneratorPlugin \| AstGeneratorPlugin`), or a single interface with both hooks optional? | **Union.** Both-optional cannot reject a plugin with no hook at all, and it makes `buildOutput` optional on the published interface — an observable narrowing. |
| D3 | Nine expression kinds plus a validated `{ kind: 'raw' }`, or narrow to structure-only and accept raw for every leaf? | **Nine kinds plus validated raw.** The nine kinds cover every *expression* the only known implementation emits. Raw remains for arrow bodies, generics, and — the case that shows up first in practice — the object type literal in a `type … = { … }` alias, which the three type kinds deliberately do not model (see § The expression vocabulary). |
| D4 | Should the syntax gate also apply to legacy `buildOutput` output? | **No, not in this change** — it would turn an existing silent breakage into a hard generation failure for an unchanged plugin. Offered as an opt-in follow-up. |
| D5 | Type `bootstrapRegistration.registrationImports` / `buildCall` in the same change? | **No** — see Non-Goals. A second speculative shape frozen at the same time doubles the D1 risk. |
