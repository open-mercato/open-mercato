# Catalog Bulk-Create (Products & Categories)

## 📝 TLDR

Catalog has a bulk-delete endpoint but no bulk-create — importing N products or categories today costs N HTTP requests, each paying the full fixed per-request overhead (auth, ACL, container build) plus the row's own insert work and its per-record side effects. This spec adds `POST /api/catalog/products/bulk-create` and `POST /api/catalog/categories/bulk-create`, modeled on the existing `bulk-delete` route's `ProgressJob` + `@open-mercato/queue` scaffolding.

Both endpoints still call the existing `catalog.products.create` / `catalog.categories.create` commands **once per row**, on that row's own `EntityManager`, so every interceptor, guard, validator, event, and audit snapshot behaves exactly as it does on the single-row path. The throughput work happens entirely **around** the command, through three levers the repository already ships or already establishes as a pattern:

1. **`ctx.bulkImport.skipReindex`** (already implemented, `packages/shared/src/lib/commands/types.ts:21-28,44`) defers the inline `query_index` / `search_tokens` reindex, with one batched rebuild at end-of-run. The spec that introduced that flag measured this as ~65% of per-record write cost — it is the single largest lever available and the previous draft of this spec did not use it.
2. **A job-scoped reference-data memo cache** for the lookups that repeat across rows (tax rate, option-schema template, unit-of-measure, parent category), passed to the commands as plain resolved values — *not* via MikroORM's identity map, which provably cannot serve these lookups (see Verified Against The Codebase, finding V1).
3. **End-of-batch deferral of the category hierarchy rebuild**, which today runs once per created category and rewrites every category in the organization — an O(N²) side effect that made the previous draft's 10,000-row category cap unshippable.

## 📝 Overview

The deliverable is two additive `202 Accepted` routes, two queue workers, two lib entry points, one additive `CommandRuntimeContext` field, one additive `BulkImportSuppression` flag, and two i18n job labels. No new entities, no migrations, no new event IDs, no changed API contract on any existing route.

This document is a **revision** of the design reviewed on PR #5609. The reviewed draft's central mechanism — sharing one `EntityManager` across a batch so its identity map would serve repeated reference-data lookups — was verified against the installed MikroORM and **does not work**; that mechanism, the `ctx.transactionalEm` change it required, the 100-row fork boundary, and Resolved Assumption #10 are all removed. The route/queue/`ProgressJob` scaffolding and the "unchanged command per row" stance survive unchanged, because both were verified sound.

## 📝 Problem Statement

`packages/core/src/modules/catalog/api/` has a `bulk-delete` route but no bulk-create for products or categories. Each `POST /api/catalog/products` call pays the full fixed per-request overhead — auth, ACL, request container construction — plus, inside the command, a set of scoped reference-data lookups (tax rate V3, option-schema template V4, unit-of-measure V5) that are identical for every row sharing a value, plus the row's own insert and dependent-collection work, plus per-record side effects (inline `query_index`/`search_tokens` reindex, event emission, cache invalidation). At the throughput the issue measures, a catalog on the order of tens of thousands of SKUs (typical B2B/wholesale) takes hours to import.

The issue reports ~44 queries per call. This spec does not attempt to reconcile that figure against a hand-counted per-row breakdown: the reviewed draft asserted "roughly 9-10 explicit DB round-trips… consistent with ~44 once each helper's internal statements are counted individually", which invites the reader to accept a 4x gap on trust. The honest statement is that the exact query count is not the design input; the *shape* is. What this endpoint can remove is (a) N-1 request-overhead instances, (b) the repeated resolution of reference data shared across rows, (c) N-1 inline reindex passes, and (d) for categories, N-1 whole-organization hierarchy rebuilds. What it cannot remove is work proportional to each row's own content (offers/categories/tags sync, custom-field writes) — see Risks.

The closest existing precedent — `bulk-delete` — solves only (a): its worker loops `commandBus.execute('catalog.products.delete', ...)` once per ID, so every row still pays its own command-internal work. The same is true of `customers/lib/bulkDeals.ts`. Going beyond (a) is what distinguishes this spec, and the levers for doing so are the ones enumerated in Resolved Assumptions #12-#14 — all of which are existing repository primitives or additive extensions of one.

Two other in-flight issues (#5605, #2967) target parts of the same per-request overhead (an unscoped `custom_field_defs` scan, schema-cache scoping); they help every row including this endpoint's, without removing the shapes above. PR #4718 ("high-performance streaming data importers and exporters") explored batch-import for `customers` and was closed without merging; it is not being resurrected, and file/streaming import stays out of scope (Resolved Assumption #7).

## 📝 Proposed Solution

Add one bulk-create route per entity, each accepting a JSON array of the same per-row shape the single-row create endpoint validates. The route does the cheap, synchronous work only — auth, ACL, request-shape and size validation, `ProgressJob` creation — then enqueues one `@open-mercato/queue` job carrying the whole batch and returns `202` immediately with the `progressJobId`, exactly like `bulk-delete`.

The worker's row loop:

1. **One synthetic command context for the job**, built the way `bulk-delete`'s worker already builds one, with `bulkImport: { skipReindex: true, skipDerivedRebuild: <true for categories> }` set on it (Resolved Assumptions #12, #13).
2. **Batch pre-resolution, once.** Before the loop, scan every structurally-valid row for the distinct reference-data keys it needs and resolve each **once**, into the memo cache described in step 3: for products the distinct tax-rate IDs, option-schema IDs and UOM values; for categories the distinct parent-category IDs plus a single batched fetch of existing slugs in scope. This is one query per key type, not per row. It is an optimization, never a correctness gate — a key the scan misses simply resolves on first use (step 3).
3. **A job-scoped reference-data memo cache**, threaded to the command through a new optional `CommandRuntimeContext` field, `referenceData?: ReferenceDataCache`. The cache is a plain `Map` behind a `get(key, load)` interface; the catalog helpers (`resolveScopedTaxRate`, `requireOptionSchemaTemplate`, `resolveCanonicalUnitCode`, `assertParentScope`) consult it before querying and populate it on a miss, so the command path is unchanged when the field is absent.

   **Two rules make this safe, and both are non-negotiable:**

   - **Cache resolved values, never managed entities.** A MikroORM entity instance belongs to the `EntityManager` that loaded it, and each row runs on its own. `resolveScopedTaxRate` and `resolveCanonicalUnitCode` already return plain values (V3, V5), so they memoize directly. `requireOptionSchemaTemplate` returns an entity that is assigned as a relation — `record.optionSchemaTemplate = optionSchemaTemplate` (V4) — so what is memoized is the **validated id plus its scope-check result**, and the relation is set on the row's own `EntityManager` via `em.getReference(CatalogOptionSchemaTemplate, id)`, which needs no query. The same applies to `assertParentScope`, which memoizes a validated-parent-id set (V7). Handing a cached entity instance across rows would attach one `EntityManager`'s object to another's unit of work and is forbidden.
   - **Key every entry on the full scope.** Cache keys are `(entityKind, identifier, organizationId, tenantId)`. These lookups run through `findOneWithDecryption`, so a cached value can hold decrypted field data; a key missing the scope would be a cross-tenant leak. The cache lives for one job and one scope and is discarded with it.

4. **Per-row command execution, unchanged.** For each row, `commandBus.execute('catalog.products.create' | 'catalog.categories.create', { input, ctx, skipCacheInvalidation: true })`. The command forks its own `EntityManager` exactly as it does today, so each row keeps its own transaction, its own event emission, and its own audit-snapshot capture — and a row whose flush throws leaves no residue for the next row, because its `EntityManager` is discarded with it (Resolved Assumption #10).
5. **Per-row failures are caught, not fatal.** A row that fails validation, references something that does not resolve, or violates a DB constraint is caught, pushed into `failedItems` with its index and reason, and the loop continues (Resolved Assumption #5), matching the `customers/lib/bulkDeals.ts` precedent.
6. **Checkpoint before each attempt.** Before row `i`, the worker writes `{ processedCount: i, meta: { lastAttemptedRowIndex: i } }` through the single `progressService.updateProgress` call it makes for that row anyway (V12 — `meta` merges, so the job's creation metadata is preserved). Resume semantics are Resolved Assumption #11's: continue at `lastAttemptedRowIndex + 1`, and treat the one indeterminate row by natural-key pre-check where a key exists, else record it as `indeterminate`.
7. **End-of-run restoration, in a `finally`.** Whatever the terminal status — `completed`, `cancelled`, or `failed` — the worker runs, in order: the batched `query_index` rebuild for the affected entity type (owed for `skipReindex`, V9); for categories, `rebuildCategoryHierarchyForOrganization` once (owed for `skipDerivedRebuild`, Resolved Assumption #12); and the end-of-run `invalidateCrudCache` sweep under `runWithCacheTenant` (Resolved Assumption #14, mirroring V10). Each of these is the caller's contractual debt for a suppression it opted into, so none of them may be skipped on the cancellation or failure path — a cancelled import still created rows.
8. **Completion.** `ProgressJob.resultSummary = { createdCount, failedCount, createdIds, failedItems }`; status `completed` (even with partial per-row failures), `failed` (whole-batch/infra failure), or `cancelled`.

**Alternatives considered:**

- *Share one `EntityManager` across the batch so its identity map serves reference-data lookups (the reviewed draft's mechanism)* — **rejected on evidence**: V1 shows the identity map is never consulted for a scoped compound `where`, and V2 shows `fork()` does not share it anyway. It would have shipped the `bulk-delete` pattern under a more complicated description of itself.
- *Reuse `bulk-delete`'s exact per-row pattern with no further levers* — rejected (Resolved Assumption #2): removes HTTP overhead only, leaving the reindex, the reference-data repetition, and the category hierarchy rebuild untouched.
- *New bulk-only helper functions duplicating the command's per-row logic* — rejected (Resolved Assumption #3): bypasses interceptors registered on the create commands, violating AGENTS.md's "never bypass command side effects", and creates a second drifting copy of intricate per-row logic.
- *Pass the batch `EntityManager` through `ctx.transactionalEm`* — rejected (Resolved Assumption #3): that field means "run inside my transaction instead of opening your own"; reusing it for a plain non-transactional EM widens its contract silently and would let a faithful future implementation delete per-row atomicity with no test failing.
- *One big chunked SQL transaction per 500 rows with deferred side effects* — rejected in an earlier review round: introduces a non-atomic commit → index → event → checkpoint sequence whose crash windows duplicate or drop side effects without an outbox design.
- *A new `catalog.product.bulk_created` event* — rejected (Resolved Assumption #8).
- *Suppressing per-row events via `skipEvents`* — rejected (Resolved Assumption #8): the SSE/`pg_notify` saving does not justify making bulk-created rows invisible to webhooks, integrations, and notification handlers.
- *CSV/file-based streaming import* — rejected (Resolved Assumption #7), out of scope per the issue.

Both entities share the route/queue/progress scaffolding as a common pattern; each gets its own validators, pre-resolution queries, and worker. There is no shared generic "bulk mutate any entity" abstraction in the codebase today, and inventing one is out of scope.

**Mutation guard: exempt, deliberately.** Bulk create is **not** wrapped in `validateCrudMutationGuard` / `runCrudMutationGuardAfterSuccess`, and neither is `bulk-delete` (V10) — the reviewed draft's claim that it was is corrected here. The exemption reasoning in `lib/bulkDelete.ts:85-90` applies with more force to create than to delete: the guard exists to catch a collaborative field edit racing another editor by comparing an expected `updated_at`, and a queued create job has no prior version to compare against because the record does not exist yet. Single-record create on the detail screen keeps riding the CRUD mutation-guard decorator with the version header, unchanged.

**Contract-surface changes, in full.** Two additive fields and one additive command behavior:

- `CommandRuntimeContext.referenceData?: ReferenceDataCache` — new optional field (`packages/shared/src/lib/commands/types.ts`). Absent for every existing caller; commands that do not read it are unaffected. Additive per `BACKWARD_COMPATIBILITY.md` §2/§3.
- `BulkImportSuppression.skipDerivedRebuild?: boolean` — new optional flag on an existing optional type, in the same advisory idiom as `skipNotifications` (V9). Unset for every existing caller.
- `createCategoryCommand` honors `skipDerivedRebuild` by omitting the hierarchy rebuild from its atomic flush. The command ID, validator, interceptor pipeline, event emission, and audit-snapshot capture are untouched, and with the flag unset — every caller today — the behavior is byte-for-byte what it is now.

`createProductCommand` needs **no** change at all beyond the optional memo consultation inside the three shared helpers it already calls; the helpers gain an optional parameter with today's behavior as the default.

## 📝 Data Model

No new entities, tables, or migrations. Reuses:

- `ProgressJob` (`packages/core/src/modules/progress/data/entities.ts`) — new `jobType` values `catalog.products.bulk_create` / `catalog.categories.bulk_create`; `meta: { lastAttemptedRowIndex, totalItems }`; `resultSummary: { createdCount, failedCount, createdIds: string[], failedItems: Array<{ index: number, sku?: string, slug?: string, reason: 'validation' | 'conflict' | 'reference' | 'indeterminate', message: string }> }`. `meta` writes merge rather than replace (V12), so the job's creation metadata survives every checkpoint.
- Existing `CatalogProduct` / `CatalogProductCategory` and their dependent tables (offers, category assignments, tags) — no schema change; rows are inserted through the same commands the single-row path uses.
- Existing `catalog.product.created` / `catalog.category.created` events (`packages/core/src/modules/catalog/events.ts`) — no new event IDs, no change to when or how they fire (Resolved Assumption #8).

**Explicitly not added:** provenance columns tying a created row to its originating `progressJobId`. They would make resume exactly-once rather than at-most-once, but they are a migration on two hot tables, and Resolved Assumption #11's design reduces the ambiguity to a single row that is reported rather than silently duplicated. Recorded as a possible future hardening.

## 📝 API Contracts

### `POST /api/catalog/products/bulk-create`

Request:
```ts
{
  items: Array<ProductCreateRow>  // same per-row shape as productCreateSchema, 1..2000 items
}
```
`ProductCreateRow` omits `organizationId`/`tenantId` (taken from the authenticated scope, once, for the whole batch — not per row).

Response `202`:
```ts
{ ok: true, progressJobId: string, message: string }
```
- `400` — standard validation error (empty array, more than 2,000 items, a structurally invalid row). No `ProgressJob` is created.
- `413` — request body exceeds the 8 MiB cap (Resolved Assumption #9), checked before parsing, following the convention in `.ai/specs/2026-08-01-payment-gateway-webhook-body-limits.md`. Item count alone is a poor proxy for size: a product row carries nested option schemas, offers, tags, and custom fields, so 2,000 rows can differ by orders of magnitude in bytes.
- `401`/`403` — standard auth/ACL error (`requireAuth: true, requireFeatures: ['catalog.products.manage']`).

### `POST /api/catalog/categories/bulk-create`

Same shape, `items: Array<CategoryCreateRow>` (1..2000), same 8 MiB cap, `requireFeatures: ['catalog.categories.manage']`.

### Progress / result retrieval

No new read endpoint — the existing progress-module job-detail path (already consumed by `ProgressTopBar`, SSE with poll fallback) is reused unchanged; `resultSummary` surfaces `createdCount`/`failedCount`/`createdIds`/`failedItems` once the job reaches a terminal status.

## 📝 UI/UX

No new backend page. `ProgressTopBar` already renders any `ProgressJob` by `jobType`; this spec adds two `jobType` i18n labels ("Bulk product import", "Bulk category import") and surfaces `resultSummary.failedItems` through the standard `ProgressJob` completion-with-failures presentation, reused as-is.

The labels ship in **Phase 1**, not a later polish phase: AGENTS.md's "never hard-code user-facing strings" rule makes them part of the cost of shipping the job type at all, they are two locale entries, and deferring them means Phase 1 ships a job that renders with a raw `jobType` fallback for no saving.

## 📝 Edge Cases & Failure Scenarios

- **Whole-request validation failure** (malformed JSON, empty/oversized `items` array): `400` before any `ProgressJob` is created — nothing to clean up.
- **Request body over the byte cap**: `413` before parsing, before any job is created.
- **Individual row invalid** (schema violation, or a reference that resolves to nothing even after a DB lookup): caught by the command's own validation, pushed to `failedItems` with `reason: 'validation'` or `'reference'`, loop continues, job still completes.
- **Genuine duplicate within the batch** (two rows carrying the same SKU/slug): the second row's command call fails against the first (already committed); caught, pushed to `failedItems` with `reason: 'conflict'`. This is a real, reportable input-data problem.
- **A row's flush fails**: the row's own `EntityManager` is discarded with the row (Resolved Assumption #10). No pending insert survives into the next row, so a failure at row 7 of a batch cannot produce spurious `failedItems` for rows 8+ or a phantom write on a later retry.
- **Worker crash / queue redelivery mid-batch**: the worker re-reads the job, **re-checks `isCancellationRequested` before doing anything** (V13 — `CANCEL_FROM_STATUSES` and `START_FROM_STATUSES` both include `failed`, so a cancelled job that the queue redelivers can otherwise be restarted), then resumes at `meta.lastAttemptedRowIndex + 1`. Row `lastAttemptedRowIndex` itself is the one row whose outcome is unknown: if its natural key is present, a pre-check for an existing row in scope decides whether it was created (skip) or not (attempt); if the row has no natural key — a SKU-less product or a name-only category, which V8 shows the constraints cannot catch — it is **not** re-attempted and is recorded in `failedItems` with `reason: 'indeterminate'` and a message naming the row index, so the operator verifies exactly one row instead of hunting for silent duplicates across a window. **Documented limitation:** the natural-key pre-check cannot distinguish "created by this job's prior attempt" from "created concurrently by an unrelated actor between the crash and the resume"; the rare latter case is skipped, which is the same trade-off `bulk-delete`-class jobs already make and is acceptable because such a collision is a data-integrity concern independent of this endpoint.
- **Whole-batch/infra failure** (a pre-resolution query throws, DB connectivity lost before any row starts): `ProgressService.failJob(...)`; the queue's own retry policy (`attempts: 3`, exponential backoff) applies per the standard worker contract. The end-of-run restoration in Proposed Solution step 7 still runs, because rows may already have been created.
- **User cancels mid-flight**: cooperative `progressService.isCancellationRequested` check between rows; the worker stops before the next row, marks the job `cancelled`, reports `resultSummary` for completed rows, and **still runs the full end-of-run restoration** — a cancelled category import that created 300 rows owes those rows their hierarchy rebuild, their index entries, and a cache invalidation exactly as a completed one does. Already-created rows remain (creation is non-destructive, Resolved Assumption #6); no batch-level undo is introduced.
- **Reference-data memo miss** (a value the pre-resolution scan did not capture): the helper's normal DB query runs as it always has and populates the memo — the cache is an optimization layered on the existing lookup, never a replacement for it, so a miss costs one query and nothing else. Miss rates are logged via the structured logger (`createLogger`) so the batch's real hit rate is observable in production.
- **Two concurrent bulk-create jobs in the same organization** (categories): both defer the hierarchy rebuild and both run it at end-of-batch. The rebuild is idempotent — it recomputes the whole tree from current rows (V6) — so the later of the two produces the correct final state regardless of interleaving. A reader of `treePath`/`depth` between the first row's commit and the rebuild sees stale derived fields on the new rows; this is a real, documented consequence of the deferral, bounded by the job's duration, and is why the rebuild runs in a `finally` rather than only on the success path.

## 📝 Risks & Impact Review

| Risk | Severity | Affected area | Mitigation | Residual |
|------|----------|---------------|------------|----------|
| Deferred category hierarchy rebuild leaves derived fields (`treePath`, `depth`, `ancestorIds`) stale for the duration of a job | Medium | Category tree readers during an import | Rebuild runs once in a `finally` covering completed/cancelled/failed; the rebuild is idempotent and recomputes from current rows | Stale derived fields for the job's duration; acceptable for an explicitly asynchronous import, and strictly better than the O(N²) alternative (V6) |
| `skipReindex` leaves `query_index`/`search_tokens` stale until the batched rebuild | Medium | Search and list projections during an import | The flag's own contract requires the end-of-run rebuild; it runs in the same `finally` as the hierarchy rebuild, before terminal status is reported | Search results omit in-flight rows until the job ends; identical to the trade-off `.ai/specs/2026-07-08-bulk-import-side-effect-suppression.md` already accepted |
| Memo cache holds decrypted reference-data values | High if mishandled | Tenant isolation | Keys carry `(entityKind, identifier, organizationId, tenantId)`; the cache is created per job, for one scope, and discarded with it; values are plain resolved data, never entities | None if the keying rule holds — enforced by the cross-scope unit test in Phase 1 step 1 |
| At-most-once resume can leave one row uncreated | Low | Import completeness | The indeterminate row is reported in `failedItems` with its index and a distinct `reason` | Operator re-submits one row; strictly preferable to the reviewed draft's silent duplication of up to 19 (V8) |
| 2,000 `clientBroadcast` events per product batch | Low | SSE fan-out / `pg_notify` | Accepted with its number (Resolved Assumption #8); bounded by the item cap and spread over a background job's runtime; categories unaffected (V11) | Follow-up filed for per-emit broadcast throttling |
| Content-proportional work is not reduced | Low | Expectations | Stated explicitly rather than implied | Offers/categories/tags sync and custom-field writes stay O(row); this endpoint's win is the fixed and shared-per-batch costs only |

- **Blast radius**: two additive API routes, two queue workers, two lib files, two optional context fields, one command behavior behind an unset-by-default flag, two i18n labels. No existing route, schema, event ID, or DI key changes.
- **Backward compatibility**: additive only per `BACKWARD_COMPATIBILITY.md` §2 (types — optional fields), §3 (signatures — optional parameters), §5 (event IDs — none added), §7 (API routes — new routes), §8 (DB schema — unchanged), §10 (ACL features — reused). No deprecation protocol is triggered.
- **Rollback**: no migrations, no schema change — rollback is reverting the PR. Existing single-row create/delete behavior is unaffected either way, because every new field is optional and unset on the existing paths.
- **Interaction with #5605/#2967**: this endpoint's custom-field write path still goes through the same custom-field-defs resolution those issues target; if they land first, this endpoint benefits automatically. This spec does not duplicate that fix.
- **Queue/worker connection budget**: one job holds one `EntityManager` at a time (the command's own per-row fork) plus the memo cache, which stores plain values and is bounded by the batch's distinct reference-data cardinality. Combined with the existing worker-concurrency cap, this stays within the documented `DB_POOL_MAX` invariant the same way `bulk-delete`'s worker does.

## 📋 Phasing

- **Phase 1 — Products bulk-create.** Route, queue, `ProgressJob`, the reference-data memo cache, `ctx.bulkImport.skipReindex` + batched rebuild, end-of-run cache invalidation, checkpoint/resume, and the two i18n labels. Products first because `createProductCommand` needs no behavioral change (Resolved Assumption #9) and because products is where the memo cache has shared reference data to work on.
- **Phase 2 — Categories bulk-create.** Reuses Phase 1's scaffolding; adds the `skipDerivedRebuild` flag, the command's honoring of it, and the end-of-batch hierarchy rebuild (Resolved Assumption #12), plus the parent-id memo and batched slug pre-fetch.
- **Phase 3 — Docs.** API reference for both endpoints under `apps/docs`, cross-linking this spec and the compatibility stance. (The i18n labels moved into Phase 1; what remains here is documentation only.)

Each phase ships a working, independently useful capability.
