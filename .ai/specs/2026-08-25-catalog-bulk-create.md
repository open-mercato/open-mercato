# Catalog Bulk-Create (Products & Categories)

## 📝 TLDR

Catalog has a bulk-delete endpoint but no bulk-create — importing N products or categories today costs N HTTP requests, each paying the full fixed per-request overhead (auth, ACL, container build) plus the row's own insert work and its per-record side effects. This spec adds `POST /api/catalog/products/bulk-create` and `POST /api/catalog/categories/bulk-create`, modeled on the existing `bulk-delete` route's `ProgressJob` + `@open-mercato/queue` scaffolding.

Both endpoints still call the existing `catalog.products.create` / `catalog.categories.create` commands **once per row**, on that row's own `EntityManager`, so every interceptor, guard, validator, event, audit snapshot **and inline `query_index` reindex** behaves exactly as it does on the single-row path. The throughput work happens entirely **around** the command, through two levers plus the request-overhead saving:

1. **N-1 fixed per-request overheads removed** — one auth/ACL/container build for the whole batch instead of one per row. This is the saving the originating issue actually measures, and it needs no new primitive.
2. **A job-scoped reference-data memo cache** for the lookups that repeat across rows (tax rate, option-schema template, unit-of-measure, parent category), passed to the commands as plain resolved values — *not* via MikroORM's identity map, which provably cannot serve these lookups (see Verified Against The Codebase, V1).
3. **End-of-batch deferral of the category hierarchy rebuild**, which today runs once per created category and rewrites every category in the organization — an O(N²) side effect that made an earlier draft's 10,000-row category cap unshippable.

**`ctx.bulkImport.skipReindex` is deliberately *not* used** (Resolved Assumption #13). Earlier drafts of this spec called it "the single largest lever available"; V9/V15 show that is false at the scale this endpoint targets — the flag's mandatory restoration is a *whole-entity-type* rebuild with no id list and no staleness filter, so importing 2,000 rows into a 40,000-SKU catalog would repay 2,000 targeted per-record upserts with a 40,000-row walk. The lever is net-negative for an incremental import and is dropped rather than repaid.

## 📝 Overview

The deliverable is two additive `202 Accepted` routes, two queue workers, two lib entry points, one additive `CommandRuntimeContext` field, one additive `BulkImportSuppression` flag, one additive optional argument on `ProgressService.updateProgress`, and one bulk-only per-row field (`parentRef`) on the category row shape. No new entities, no migrations, no new event IDs, no changed API contract on any existing route.

This document is the third revision of the design first reviewed on PR #5609. Round 1 removed the shared-`EntityManager` / identity-map mechanism (disproved in V1/V2). Round 2's review found that two of the primitives the redesign leaned on do something *adjacent to* what the design needed — the per-row checkpoint is not durably written per row (V12), and `skipReindex`'s restoration is a whole-entity-type rebuild (V15) — and that a category tree cannot be created in a single batch at all under the current row shape (V17). All three are resolved here, at the mechanism level. The route/queue/`ProgressJob` scaffolding, the "unchanged command per row" stance, and the memo-cache design survive unchanged; the review recorded all three as settled.

**Relationship to PR #5610 — these two must reconcile before either merges.** PR #5610 implements this spec and **edits this same file**, so the two branches will conflict on merge. Its implementation predates this revision and differs on four points, each of which is a decision this document now owns: it uses a 20-row `checkpointInterval` with `meta.lastCompletedRowIndex` where this revision uses a durably-written per-row `lastAttemptedRowIndex` (Resolved Assumption #11 — #5610's own plan notes the throttle problem and works around it with a boundary search rather than fixing the write); it has no `parentRef`, so it cannot create a category tree in one batch (Resolved Assumption #15); it does not use `skipReindex`, which matches this revision (Resolved Assumption #13); and it added the batch-envelope mutation-guard registry call, which this revision adopts (Architecture). The `priorNaturalKeys` resume classification and the `failedItems[].code` / `message` split both come **from** #5610 and are adopted here. The recommended order is to land this spec first, then update #5610 to match on the checkpoint and `parentRef` — but whichever order is chosen, the reconciliation is deliberate, not a merge-conflict resolution to be improvised.

| 11 | Checkpoint strategy and resume semantics | **Durably-written per-row checkpoint, at-most-once semantics, plus a prior-key snapshot.** Before attempting row `i`, the worker writes `meta.lastAttemptedRowIndex = i` through `progressService.updateProgress(..., { forcePersist: true })` — a new option (Phase 1 step 2) that bypasses the *persist* throttle while leaving the *broadcast* throttle intact. The remaining design keeps every projection consistent by construction. A future whole-catalog *initial* load — where batch size approaches entity-type size — is the workload where `skipReindex` + one full `reindexEntity` does pay; that is recorded as a possible future opt-in request flag, gated on a measurement, and an operator can already run the reindex CLI manually for that case. |
| 14 | Cache invalidation | Mirror `bulk-delete` exactly: every row runs with `skipCacheInvalidation: true`, and the worker invalidates once at end-of-run under `runWithCacheTenant` (V10). | Without it a completed import reports `createdCount: 2000` while the catalog list endpoint keeps serving a cached page with none of the new rows until its TTL expires, and the user concludes the import silently failed. |
| 15 | Can a batch create a category *tree*, given that a row cannot reference a parent created in the same batch (V17)? | **Yes, via a bulk-only `parentRef?: number`** on `CategoryCreateRow`: the zero-based index of an **earlier** row in the same `items` array whose created id becomes this row's `parentId`. Mutually exclusive with `parentId`; a self-reference, a forward reference, or an out-of-range index is a structural request error (`400`), detectable without touching the database. If the referenced row failed to be created, the referring row fails with `code: 'parent_ref_failed'`. | Importing a taxonomy is the central use case for category bulk-create, and without this it takes one request per tree level — a constraint nowhere stated in the earlier drafts and one that made Phase 2's own acceptance test unimplementable as written. `parentRef` is resolved **entirely in the worker**, which substitutes the created id into `parentId` before calling the command, so `categoryCreateSchema`, `assertParentScope` and the command are untouched and every parent is still validated exactly as today. The alternative — letting the client supply a per-row `id` — was rejected: it means accepting client-assigned primary keys on a hot table, which is a larger contract change with its own collision and authorization questions, and it would have to be honored by `createCategoryCommand` itself. |
| 16 | Unknown keys in a bulk row: strip silently (today's behavior) or reject? | **Reject with `400`.** The bulk row validators split custom fields with the same `splitCustomFieldPayload` the commands use, then strict-parse the remainder against the create schema's known keys plus the bulk-only `parentRef`. | V17 shows a plain zod object silently strips unknown keys, so a client that sends `id` (the natural thing to try when building a tree) gets server-generated ids and no error. Silent stripping is a poor contract for an import API where the client cannot inspect each row afterwards; failing the request tells them immediately. This is bulk-only — the single-row create routes keep today's lenient behavior, so nothing existing changes. |

## 📝 Problem Statement

`packages/core/src/modules/catalog/api/` has a `bulk-delete` route but no bulk-create for products or categories. Each `POST /api/catalog/products` call pays the full fixed per-request overhead — auth, ACL, request container construction — plus, inside the command, a set of scoped reference-data lookups (tax rate V3, option-schema template V4, unit-of-measure V5) that are identical for every row sharing a value, plus the row's own insert and dependent-collection work, plus per-record side effects. At the throughput the issue measures, a catalog on the order of tens of thousands of SKUs (typical B2B/wholesale) takes hours to import.

The issue reports ~44 queries per call. This spec does not attempt to reconcile that figure against a hand-counted per-row breakdown: an earlier draft asserted "roughly 9-10 explicit DB round-trips… consistent with ~44 once each helper's internal statements are counted individually", which invites the reader to accept a 4x gap on trust. The honest statement is that the exact query count is not the design input; the *shape* is. What this endpoint can remove is (a) N-1 request-overhead instances, (b) the repeated resolution of reference data shared across rows, and (c) for categories, N-1 whole-organization hierarchy rebuilds. What it explicitly **cannot** remove is work proportional to each row's own content (offers/categories/tags sync, custom-field writes) **or the per-record `query_index` upsert**, which stays inline for the reasons in Resolved Assumption #13 — see Risks.

The closest existing precedent — `bulk-delete` — solves only (a): its worker loops `commandBus.execute('catalog.products.delete', ...)` once per ID, so every row still pays its own command-internal work. The same is true of `customers/lib/bulkDeals.ts`. Going beyond (a) is what distinguishes this spec, through (b) and (c).

Two other in-flight issues (#5605, #2967) target parts of the same per-request overhead (an unscoped `custom_field_defs` scan, schema-cache scoping); they help every row including this endpoint's, without removing the shapes above. PR #4718 ("high-performance streaming data importers and exporters") explored batch-import for `customers` and was closed without merging; it is not being resurrected, and file/streaming import stays out of scope (Resolved Assumption #7).

## 📝 Proposed Solution

Add one bulk-create route per entity, each accepting a JSON array of the same per-row shape the single-row create endpoint validates (strict-parsed, plus `parentRef` for categories). The route does the cheap, synchronous work only — auth, ACL, request-shape and size validation, `ProgressJob` creation with server-resolved translated `name`/`description` — then enqueues one `@open-mercato/queue` job carrying the whole batch and returns `202` immediately with the `progressJobId`, exactly like `bulk-delete`.

The worker's row loop:

1. **One synthetic command context for the job**, built the way `bulk-delete`'s worker already builds one. It carries `bulkImport: { skipDerivedRebuild: true }` for categories and **no `bulkImport` at all** for products (Resolved Assumption #13): products need no suppression, so the product path sets no flag and incurs no restoration debt.
2. **Batch pre-resolution, once.** Before the loop, scan every structurally-valid row for the distinct reference-data keys it needs and resolve each **once**, into the memo cache described in step 3: for products the distinct tax-rate IDs, option-schema IDs and UOM values; for categories the distinct **pre-existing** parent-category IDs (rows using `parentRef` name a row of this batch and are resolved during the loop instead, Resolved Assumption #15) plus a single batched fetch of existing slugs in scope. This is one query per key type, not per row. It is an optimization, never a correctness gate — a key the scan misses simply resolves on first use (step 3).
3. **A job-scoped reference-data memo cache**, threaded to the command through a new optional `CommandRuntimeContext` field, `referenceData?: ReferenceDataCache`. The cache is a plain `Map` behind a `get(key, load)` interface; the catalog helpers (`resolveScopedTaxRate`, `requireOptionSchemaTemplate`, `resolveCanonicalUnitCode`, `assertParentScope`) consult it before querying and populate it on a miss, so the command path is unchanged when the field is absent.

   **Two rules make this safe, and both are non-negotiable:**

   - **Cache resolved values, never managed entities.** A MikroORM entity instance belongs to the `EntityManager` that loaded it, and each row runs on its own. `resolveScopedTaxRate` and `resolveCanonicalUnitCode` already return plain values (V3, V5), so they memoize directly. `requireOptionSchemaTemplate` returns an entity that is assigned as a relation — `record.optionSchemaTemplate = optionSchemaTemplate` (V4) — so what is memoized is the **validated id plus its scope-check result**, and the relation is set on the row's own `EntityManager` via `em.getReference(CatalogOptionSchemaTemplate, id)`, which needs no query. The same applies to `assertParentScope`, which memoizes a validated-parent-id set (V7). Handing a cached entity instance across rows would attach one `EntityManager`'s object to another's unit of work and is forbidden.
   - **Key every entry on the full scope.** Cache keys are `(entityKind, identifier, organizationId, tenantId)`. These lookups run through `findOneWithDecryption`, so a cached value can hold decrypted field data; a key missing the scope would be a cross-tenant leak. The cache lives for one job and one scope and is discarded with it.

4. **Per-row command execution, unchanged.** For each row, `commandBus.execute('catalog.products.create' | 'catalog.categories.create', { input, ctx, skipCacheInvalidation: true })`. The command forks its own `EntityManager` exactly as it does today, so each row keeps its own transaction, its own event emission, its own audit-snapshot capture, and — for products — its own inline `query_index.upsert_one` (V15, Resolved Assumption #13). A row whose flush throws leaves no residue for the next row, because its `EntityManager` is discarded with it (Resolved Assumption #10). For a category row carrying `parentRef`, the worker substitutes the referenced row's created id into `parentId` before this call, so the command validates the parent through the ordinary `assertParentScope` path.
5. **Per-row failures are caught, not fatal.** A row that fails validation, references something that does not resolve (including a `parentRef` whose target row failed), or violates a DB constraint is caught, pushed into `failedItems` with its index and reason, and the loop continues (Resolved Assumption #5), matching the `customers/lib/bulkDeals.ts` precedent.
6. **Durable checkpoint before each attempt.** Before row `i`, the worker writes `{ processedCount: i, meta: { lastAttemptedRowIndex: i } }` through `progressService.updateProgress(jobId, input, ctx, { forcePersist: true })`. The `forcePersist` option is new (Phase 1 step 2) and exists because the ordinary call is **not** a durable write: V12 shows it merges `meta` in memory and persists only on a 250 ms / 1 % / 5 s throttle held in-process. The option bypasses the persist throttle and leaves the broadcast throttle untouched, so the checkpoint costs one `UPDATE` and **no** extra `pg_notify`/SSE fan-out. The write must go through the service rather than a direct `nativeUpdate`, because the throttle entry caches the `ProgressJob` instance for the process's lifetime (`progressServiceImpl.ts:95-109`) and a later throttled persist would write its cached `meta` straight back over an out-of-band update. Resume semantics are Resolved Assumption #11's: continue at `lastAttemptedRowIndex + 1`, and treat the one indeterminate row by natural-key pre-check where a key exists, else record it as `indeterminate`.
7. **End-of-run restoration, in a `finally`.** Whatever the terminal status — `completed`, `cancelled`, or `failed` — the worker runs: for categories, `rebuildCategoryHierarchyForOrganization` once (owed for `skipDerivedRebuild`, Resolved Assumption #12); then the end-of-run `invalidateCrudCache` sweep under `runWithCacheTenant` (Resolved Assumption #14, mirroring V10). There is **no** `query_index` rebuild to run, because nothing suppressed the index (Resolved Assumption #13) — which also removes the ordering hazard that a category reindex would have had to run *after* the hierarchy rebuild to avoid capturing stale derived fields. Each remaining item is the caller's contractual debt for a suppression it opted into, so neither may be skipped on the cancellation or failure path — a cancelled import still created rows.
8. **Completion.** `ProgressJob.resultSummary = { createdCount, failedCount, createdIds, failedItems }`; status `completed` (even with partial per-row failures), `failed` (whole-batch/infra failure), or `cancelled`.

**Alternatives considered:**

- *Share one `EntityManager` across the batch so its identity map serves reference-data lookups* — **rejected on evidence**: V1 shows the identity map is never consulted for a scoped compound `where`, and V2 shows `fork()` does not share it anyway.
- *Use `ctx.bulkImport.skipReindex` and repay it with one `reindexEntity` run at end-of-batch* — **rejected on arithmetic** (V15, Resolved Assumption #13): the restoration has no id list, so it walks the whole entity type; at this endpoint's target scale that costs about 20× what the suppression saved, and for categories it would index an entity type nothing else indexes (V16).
- *Use `skipReindex` and repay it targeted, by re-emitting `query_index.upsert_one` per `createdId` at end-of-run* — rejected as complexity without a saving: it is roughly the same total work as letting the inline upsert run, and it adds a window in which a dead worker leaves the index stale with nobody owning the repair. If a batched by-id rebuild is ever wanted as a reusable primitive, adding a `recordIds` option to `ReindexJobOptions` is a real, additive piece of work that deserves its own spec and its own tests.
- *Reuse `bulk-delete`'s exact per-row pattern with no further levers* — rejected (Resolved Assumption #2): removes HTTP overhead only, leaving the reference-data repetition and the category hierarchy rebuild untouched.
- *New bulk-only helper functions duplicating the command's per-row logic* — rejected (Resolved Assumption #3): bypasses interceptors registered on the create commands, violating AGENTS.md's "never bypass command side effects", and creates a second drifting copy of intricate per-row logic.
- *Pass the batch `EntityManager` through `ctx.transactionalEm`* — rejected (Resolved Assumption #3): that field means "run inside my transaction instead of opening your own"; reusing it for a plain non-transactional EM widens its contract silently and would let a faithful future implementation delete per-row atomicity with no test failing.
- *Let the client supply a per-row `id` so a batch can build a tree* — rejected (Resolved Assumption #15) in favour of the worker-resolved `parentRef`: client-assigned primary keys on a hot table are a much larger contract change, and `parentRef` needs no change to the command or its validator at all.
- *Write the checkpoint with a direct `nativeUpdate` instead of a new service option* — rejected (Proposed Solution step 6): the progress service caches the `ProgressJob` instance behind its throttle, so an out-of-band write is clobbered by the next throttled persist.
- *One big chunked SQL transaction per 500 rows with deferred side effects* — rejected in an earlier review round: introduces a non-atomic commit → index → event → checkpoint sequence whose crash windows duplicate or drop side effects without an outbox design.
- *A new `catalog.product.bulk_created` event* / *suppressing per-row events via `skipEvents`* — both rejected (Resolved Assumption #8).
- *CSV/file-based streaming import* — rejected (Resolved Assumption #7), out of scope per the issue.

Both entities share the route/queue/progress scaffolding as a common pattern; each gets its own validators, pre-resolution queries, and worker. There is no shared generic "bulk mutate any entity" abstraction in the codebase today, and inventing one is out of scope.

**Mutation guards: the optimistic-lock check is exempt, the guard registry is not.** These are two different mechanisms and the distinction matters:

- **Optimistic-lock guard — exempt, deliberately.** Bulk create is **not** wrapped in `validateCrudMutationGuard` / `runCrudMutationGuardAfterSuccess`, and neither is `bulk-delete` (V10). The exemption reasoning in `lib/bulkDelete.ts:85-90` applies with more force to create than to delete: that guard exists to catch a collaborative field edit racing another editor by comparing an expected `updated_at`, and a queued create job has no prior version to compare against because the record does not exist yet. Single-record create on the detail screen keeps riding the CRUD mutation-guard decorator with the version header, unchanged.
- **Mutation-guard registry — runs, at the batch envelope, before enqueue.** AGENTS.md's "never bypass mutation guards" rule is about the registered policy guards (`getAllMutationGuardInstances` + `runMutationGuards`, plus the bridged legacy guard), which is a separate concern from version checking: a guard that would block a single `create` MUST block the bulk version of the same write, or the endpoint becomes a hole around every policy the registry enforces. Each route therefore runs the registry once for the request, with `operation: 'create'`, `resourceId: null`, and a `mutationPayload` naming the batch (`{ bulk: true, itemCount }`), and returns the guard's own status/body when it denies. `afterSuccess` callbacks are **not** invoked: the rows are created later by a queue worker, from a context with no request headers and no record to report, so a guard needing per-record post-processing subscribes to `catalog.product.created` / `catalog.category.created` instead.

**Contract-surface changes, in full.** Three additive fields/arguments and one additive command behavior:

- `CommandRuntimeContext.referenceData?: ReferenceDataCache` — new optional field (`packages/shared/src/lib/commands/types.ts`). Absent for every existing caller; commands that do not read it are unaffected. Additive per `BACKWARD_COMPATIBILITY.md` §2/§3.
- `BulkImportSuppression.skipDerivedRebuild?: boolean` — new optional flag on an existing optional type, in the same advisory idiom as `skipNotifications` (V9). Unset for every existing caller.
- `ProgressService.updateProgress(jobId, input, ctx, options?: { forcePersist?: boolean })` — new **optional fourth argument** on an existing interface method (`progress/lib/progressService.ts:13`). Additive per `BACKWARD_COMPATIBILITY.md` §3: every existing call site compiles and behaves identically, and a third-party `ProgressService` implementation with a three-parameter `updateProgress` still satisfies the interface (TypeScript accepts fewer parameters). The in-repo implementation MUST persist before resolving when the option is set; the doc comment states that obligation, and the residual risk of an implementation that ignores it is recorded in Risks.
- `createCategoryCommand` honors `skipDerivedRebuild` by omitting the hierarchy rebuild from its atomic flush. The command ID, validator, interceptor pipeline, event emission, and audit-snapshot capture are untouched, and with the flag unset — every caller today — the behavior is byte-for-byte what it is now.

`createProductCommand` has **no behavioral change**: the three shared helpers it calls gain an optional cache parameter that defaults to today's behavior, and the command's call sites pass that optional cache through — a signature-level edit with no change to what the command does.

## 📝 Data Model

No new entities, tables, or migrations. Reuses:

- `ProgressJob` (`packages/core/src/modules/progress/data/entities.ts`) — new `jobType` values `catalog.products.bulk_create` / `catalog.categories.bulk_create`; `meta: { lastAttemptedRowIndex, priorNaturalKeys, totalItems }`; `resultSummary: { createdCount, failedCount, createdIds: string[], failedItems: Array<{ index: number, title?: string, name?: string, code: FailureCode, message: string }> }`, where each entity carries its own display field for readability (`title` for products, `name` for categories). **`code` is the stable identifier callers branch on; `message` is human-readable prose and may change** — `'validation' | 'sku_taken' | 'handle_taken' | 'slug_taken' | 'parent_not_found' | 'parent_ref_failed' | 'command_failed' | 'indeterminate'`. Splitting the two is what lets follow-up #5736 turn `message` into a translation key without breaking any consumer. `meta` writes merge rather than replace (V12), so the job's creation metadata survives every checkpoint; the checkpoint write is durable per row only because it passes `forcePersist` (Resolved Assumption #11).
- Existing `CatalogProduct` / `CatalogProductCategory` and their dependent tables (offers, category assignments, tags) — no schema change; rows are inserted through the same commands the single-row path uses.
- Existing `catalog.product.created` / `catalog.category.created` events (`packages/core/src/modules/catalog/events.ts`) — no new event IDs, no change to when or how they fire (Resolved Assumption #8).
- Existing `query_index` projection — written inline per created product exactly as on the single-row path (Resolved Assumption #13); categories are not inline-indexed today and this endpoint does not change that (V16).

**Explicitly not added:** provenance columns tying a created row to its originating `progressJobId`. They would make resume exactly-once rather than at-most-once, but they are a migration on two hot tables, and Resolved Assumption #11's design reduces the ambiguity to a single row that is reported rather than silently duplicated. Recorded as a possible future hardening.

## 📝 API Contracts

### `POST /api/catalog/products/bulk-create`

Request:
```ts
{
  items: Array<ProductCreateRow>  // same per-row shape as productCreateSchema, 1..2000 items
}
```
`ProductCreateRow` omits `organizationId`/`tenantId` (taken from the authenticated scope, once, for the whole batch — not per row). Rows are strict-parsed after the standard custom-field split, so `cf_*` keys are accepted and any other unknown key is a `400` (Resolved Assumption #16).

Response `202`:
```ts
{ ok: true, progressJobId: string, message: string }
```
- `400` — standard validation error (empty array, more than 2,000 items, a structurally invalid row, an unknown key on a row). No `ProgressJob` is created.
- `413` — request body exceeds the 8 MiB cap (Resolved Assumption #9), checked before parsing, following the convention in `.ai/specs/2026-08-01-payment-gateway-webhook-body-limits.md`. Item count alone is a poor proxy for size: a product row carries nested option schemas, offers, tags, and custom fields, so 2,000 rows can differ by orders of magnitude in bytes.
- `401`/`403` — standard auth/ACL error (`requireAuth: true, requireFeatures: ['catalog.products.manage']`).

### `POST /api/catalog/categories/bulk-create`

Same shape, `items: Array<CategoryCreateRow>` (1..2000), same 8 MiB cap, `requireFeatures: ['catalog.categories.manage']`.

`CategoryCreateRow` is `categoryCreateSchema`'s per-row shape (minus the scope fields) plus one bulk-only field:

```ts
parentRef?: number  // zero-based index of an EARLIER row in this same items array
```

- `parentRef` and `parentId` are mutually exclusive; supplying both is a `400`.
- `parentRef` must be `>= 0` and `<` the row's own index. A self-reference, a forward reference, or an out-of-range index is a `400` — the whole reference graph is checked at the route, before any job is created, because it needs no database access.
- At run time the worker substitutes the referenced row's created id into `parentId`; the command then validates it through the ordinary `assertParentScope` path (V7, V17). If the referenced row was not created (it failed, or the job resumed past it as `indeterminate`), the referring row is recorded in `failedItems` with `code: 'parent_ref_failed'`, and so is anything that transitively referenced it.

### Progress / result retrieval

No new read endpoint — the existing progress-module job-detail path (already consumed by `ProgressTopBar`, SSE with poll fallback) is reused unchanged; `resultSummary` surfaces `createdCount`/`failedCount`/`createdIds`/`failedItems` once the job reaches a terminal status.

## 📝 UI/UX

No new backend page and **no `ProgressTopBar` change**. V18 corrects an assumption an earlier draft of this spec made: `ProgressTopBar` does not render by `jobType` at all — it renders the job's persisted `name` and `description`, written once at job creation, and there is no jobType→label lookup to add an entry to.

So the two routes resolve their strings **server-side** with `resolveTranslations()` and persist the already-translated `name` and `description` on the `ProgressJob` (`catalog.progress.bulk_create_products.name` and `.description`, and the category equivalents, in the catalog locale files). This satisfies AGENTS.md's "never hard-code user-facing strings" rule with no UI change and no fallback design for pre-existing jobs.

The trade-off is stated rather than hidden: a persisted translated label is frozen in the locale of the user who started the import, so a colleague viewing the same job in another locale sees the starting user's language. Translating at render instead would need a persisted key plus a `ProgressTopBar` change plus a fallback for every job row already in the database — a broader change that would also fix `bulk-delete`, which hardcodes both strings in English today (V18). That broader fix is worth doing and is filed as a follow-up rather than absorbed into this spec's scope.

`resultSummary.failedItems` surfaces through the standard `ProgressJob` completion-with-failures presentation, reused as-is.

## 📝 Edge Cases & Failure Scenarios

- **Whole-request validation failure** (malformed JSON, empty/oversized `items` array, unknown key on a row, an invalid `parentRef` graph): `400` before any `ProgressJob` is created — nothing to clean up.
- **Request body over the byte cap**: `413` before parsing, before any job is created.
- **Individual row invalid** (schema violation, or a reference that resolves to nothing even after a DB lookup): caught by the command's own validation, pushed to `failedItems` with `code: 'validation'` or `'parent_not_found'`, loop continues, job still completes.
- **A `parentRef` chain broken by an earlier failure**: the referring row and everything transitively below it are recorded with `code: 'parent_ref_failed'` naming the index that failed, so the operator can see the whole affected subtree rather than one confusing row.
- **Genuine duplicate within the batch** (two rows carrying the same SKU/slug): the second row's command call fails against the first (already committed); caught, pushed to `failedItems` with the entity's own conflict code (`sku_taken` / `handle_taken` / `slug_taken`). This is a real, reportable input-data problem.
- **A row's flush fails**: the row's own `EntityManager` is discarded with the row (Resolved Assumption #10). No pending insert survives into the next row, so a failure at row 7 of a batch cannot produce spurious `failedItems` for rows 8+ or a phantom write on a later retry.
- **Worker crash / queue redelivery mid-batch**: the worker re-reads the job, **re-checks `isCancellationRequested` before doing anything** (V13 — `CANCEL_FROM_STATUSES` and `START_FROM_STATUSES` both include `failed`, so a cancelled job that the queue redelivers can otherwise be restarted), then resumes at `meta.lastAttemptedRowIndex + 1`. Because the checkpoint is written with `forcePersist` (Resolved Assumption #11), the persisted index is the row actually attempted and not a throttled approximation of it (V12). Row `lastAttemptedRowIndex` itself is the one row whose outcome is unknown, and `meta.priorNaturalKeys` decides it (Resolved Assumption #11): a key that exists now but was **not** in the pre-attempt snapshot was written by this job, so the row is reclaimed rather than re-created or reported as a conflict against itself, and its real id enters `createdIds`; a key that **was** in the snapshot belongs to somebody else, so the row is reported as the genuine conflict it is and that foreign id never enters `createdIds`. Only if the row has no natural key at all — a SKU-less product or a name-only category, which V8 shows the constraints cannot catch — is it **not** re-attempted and instead recorded in `failedItems` with `code: 'indeterminate'` and a message naming the row index, so the operator verifies exactly one row instead of hunting for silent duplicates across a window. The snapshot is what removes the previous revision's documented limitation here: a key-based pre-check on its own could not tell "created by this job's prior attempt" from "created concurrently by an unrelated actor", and would silently skip the second case.
- **Whole-batch/infra failure** (a pre-resolution query throws, DB connectivity lost before any row starts): `ProgressService.failJob(...)`; the queue's own retry policy (`attempts: 3`, exponential backoff) applies per the standard worker contract. The end-of-run restoration in Proposed Solution step 7 still runs, because rows may already have been created.
- **User cancels mid-flight**: cooperative `progressService.isCancellationRequested` check between rows; the worker stops before the next row, marks the job `cancelled`, reports `resultSummary` for completed rows, and **still runs the full end-of-run restoration** — a cancelled category import that created 300 rows owes those rows their hierarchy rebuild and a cache invalidation exactly as a completed one does. Already-created rows remain (creation is non-destructive, Resolved Assumption #6); no batch-level undo is introduced.
- **Reference-data memo miss** (a value the pre-resolution scan did not capture): the helper's normal DB query runs as it always has and populates the memo — the cache is an optimization layered on the existing lookup, never a replacement for it, so a miss costs one query and nothing else. Miss rates are logged via the structured logger (`createLogger`) so the batch's real hit rate is observable in production.
- **Reference data changed mid-job**: the memo has **no TTL and no invalidation** — it is keyed on `(entityKind, identifier, organizationId, tenantId)` and lives for the whole job. A tax rate, option-schema template or unit dictionary entry that is edited or soft-deleted while a 2,000-row job is running keeps resolving to its pre-job value for the rest of the batch. This is a deliberate consistency trade, and the right one for an explicitly asynchronous import: a batch that resolved the same input two different ways depending on when a row happened to run would be far harder for an operator to reason about than one that is internally consistent as of its start.
- **Two concurrent bulk-create jobs in the same organization** (categories): both defer the hierarchy rebuild and both run it at end-of-batch. The rebuild is idempotent — it recomputes the whole tree from current rows (V6) — so the later of the two produces the correct final state regardless of interleaving. A reader of `treePath`/`depth` between the first row's commit and the rebuild sees stale derived fields on the new rows; this is a real, documented consequence of the deferral, bounded by the job's duration, and is why the rebuild runs in a `finally` rather than only on the success path.

## 📝 Risks & Impact Review

| Risk | Severity | Affected area | Mitigation | Residual |
|------|----------|---------------|------------|----------|
| Deferred category hierarchy rebuild leaves derived fields (`treePath`, `depth`, `ancestorIds`) stale for the duration of a job | Medium | Category tree readers during an import | Rebuild runs once in a `finally` covering completed/cancelled/failed; the rebuild is idempotent and recomputes from current rows | Stale derived fields for the job's duration; acceptable for an explicitly asynchronous import, and strictly better than the O(N²) alternative (V6) |
| Memo cache holds decrypted reference-data values | High if mishandled | Tenant isolation | Keys carry `(entityKind, identifier, organizationId, tenantId)`; the cache is created per job, for one scope, and discarded with it; values are plain resolved data, never entities | None if the keying rule holds — enforced by the cross-scope unit test in Phase 1 step 1 |
| Memo cache serves pre-job values after reference data changes mid-job | Low | Import consistency | Documented as a deliberate consistency trade (Edge Cases); the cache is discarded with the job | A long job can create rows against a tax rate that was edited while it ran; internally consistent as of job start |
| A third-party `ProgressService` implementation ignores `forcePersist` | Medium | Resume correctness on non-default implementations | The interface doc comment states the obligation; the in-repo implementation honors it and is covered by a unit test asserting a database write per call | On such an implementation the resume window degrades to the throttled window V12 describes (up to 1 % of the batch) rather than one row. Detectable, documented, and no worse than the behavior before this spec |
| One extra `UPDATE` on `progress_jobs` per row for the durable checkpoint | Low | Import throughput | Accepted openly rather than claimed away (Resolved Assumption #11); the write is a single-row PK update, small beside the row's own inserts, and it does **not** add a broadcast because `forcePersist` leaves the broadcast throttle intact | ~1 extra small UPDATE per created row; measured by the Phase 1 step 8 near-cap test |
| Per-record `query_index` upsert is not batched away | Low | Expectations | Stated explicitly rather than implied: `skipReindex` was evaluated and rejected on arithmetic (V15, Resolved Assumption #13) | Indexing cost per row is identical to the single-row path; the endpoint's index-related win is zero, by design and by measurement |
| 2,000 `clientBroadcast` events per product batch | Low | SSE fan-out / `pg_notify` | Accepted with its number (Resolved Assumption #8); bounded by the item cap and spread over a background job's runtime; categories unaffected (V11) | Follow-up #5733 filed for per-emit broadcast throttling |
| At-most-once resume can leave one row uncreated | Low | Import completeness | The indeterminate row is reported in `failedItems` with its index and a distinct `code`; the checkpoint is durable per row (Resolved Assumption #11) so the window is one row, not a throttled batch of them | Operator re-submits one row |
| Content-proportional work is not reduced | Low | Expectations | Stated explicitly rather than implied | Offers/categories/tags sync and custom-field writes stay O(row); this endpoint's win is the fixed and shared-per-batch costs only |

- **Blast radius**: two additive API routes (each running the existing mutation-guard registry at the batch envelope), two queue workers, two lib files, two optional context fields, one optional service argument, one command behavior behind an unset-by-default flag, four locale entries. No existing route, schema, event ID, or DI key changes.
- **Backward compatibility**: additive only per `BACKWARD_COMPATIBILITY.md` §2 (types — optional fields), §3 (signatures — optional parameters, including `updateProgress`'s fourth argument), §5 (event IDs — none added), §7 (API routes — new routes), §8 (DB schema — unchanged), §10 (ACL features — reused). No deprecation protocol is triggered.
- **Rollback**: no migrations, no schema change — rollback is reverting the PR. Existing single-row create/delete behavior is unaffected either way, because every new field and argument is optional and unset on the existing paths.
- **Interaction with #5605/#2967**: this endpoint's custom-field write path still goes through the same custom-field-defs resolution those issues target; if they land first, this endpoint benefits automatically. This spec does not duplicate that fix.
- **Queue/worker connection budget**: one job holds one `EntityManager` at a time (the command's own per-row fork) plus the memo cache, which stores plain values and is bounded by the batch's distinct reference-data cardinality. Combined with the existing worker-concurrency cap, this stays within the documented `DB_POOL_MAX` invariant the same way `bulk-delete`'s worker does.

## 📋 Phasing

- **Phase 1 — Products bulk-create.** Route, queue, `ProgressJob`, the `forcePersist` progress option, the reference-data memo cache, end-of-run cache invalidation, checkpoint/resume, and the job labels. Products first because `createProductCommand` needs no behavioral change (Resolved Assumption #9) and because products is where the memo cache has shared reference data to work on.
- **Phase 2 — Categories bulk-create.** Reuses Phase 1's scaffolding; adds the `skipDerivedRebuild` flag, the command's honoring of it, the end-of-batch hierarchy rebuild (Resolved Assumption #12), the `parentRef` resolution (Resolved Assumption #15), and the parent-id memo plus batched slug pre-fetch.
- **Phase 3 — Docs.** API reference for both endpoints under `apps/docs`, cross-linking this spec and the compatibility stance.

Each phase ships a working, independently useful capability.

**Sequencing note on the memo cache.** The memo cache is the one part of Phase 1 whose value is not yet measured — it is bounded by how much reference data a real batch actually shares, and Phase 1 step 4's numeric criterion is the honest measure of it. Splitting it out (ship the route, queue, checkpoint and cache invalidation first; add the memo once that measurement exists on real batches) is a reasonable alternative sequencing and would let the `CommandRuntimeContext.referenceData` contract surface be justified by data rather than by argument. It is kept in Phase 1 here because the three helper signatures and the route land in the same files either way, and splitting would mean touching them twice; an implementer who finds Phase 1 too large should split at this seam first.
