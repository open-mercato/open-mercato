# eComm Release 4 (Write Side) — Consolidated Decisions

> **Release scope**: Cart Phases 1–3 · Promotions (SPEC-055) Phases 1–3 · Buyer-Scoped Catalog Visibility Phase 3.
> **Verified against**: `develop` @ `28ca93ed97` (2026-10-14).
> **Source analyses**: `ANALYSIS-2026-10-14-cart-module-release-4.md` (C, F, W ids) · `ANALYSIS-2026-10-14-spec-055-promotions-release-4.md` (P ids) · `ANALYSIS-2026-10-14-buyer-scoped-catalog-visibility-phase-3.md` (V ids) · scope and status: `ANALYSIS-2026-10-14-ecommerce-release-4-scope.md`.
> **Decided by the owner on 2026-10-14.** Every decision below follows the analysis recommendation; "Walked through" means it was put to the owner one at a time with a worked scenario, "Adopted as a batch" means the owner accepted the recommendation list in one answer.
> **Authority**: where a spec text and this record disagree, this record wins until the spec revision (PLAN.md Phase 0) lands. After that, the revised specs are authoritative and this record is the audit trail.

## Decisions

| Id (analysis ids) | Decision | How decided |
|---|---|---|
| D-R4-1 (C1, V1, F1) | **Scope is server-derived.** Public cart routes resolve the buyer through `storeContextService` (soft DI at the route edge), verify `cart.store_id === ctx.store.id`, and pass the `assortmentScope` to the commands as an internal, branded input. Request schemas are `.strict()` and contain no scope, channel, store or actor field. No `storeContextService` means no storefront carts. | Walked through |
| D-R4-2 (C2, V2, F2) | **Public routes always create a `storefront` cart** bound to the store resolved from the host. Other channels (`api`, `agent`, `pos`, `pay_link`) are created only by a command from an authenticated principal holding an explicit feature. `channel` is immutable. Enforcement key (cart C2): enforce the assortment check iff the cart is `storefront` **or** a scope is supplied. | Walked through (key adopted as a consequence) |
| D-R4-3 (C12, F8, V7) | **Extract shared seams and repoint ecommerce.** New additive services: `catalogBuyerPricingService.resolveLinePrice(...)` and `catalogScopedProductService.loadScopedProducts(ids, scope)` in `catalog` (ancestor-expanded categories, batch, tenant/org scoped, `isActive`), and the quantity-rule derivation in `availability`. ecommerce is refactored onto them with no behaviour change (`TC-ECOM-*` are the safety net). This records the owner approval for the multi-module change. | Walked through |
| D-R4-4 (C6, V3, F7) | **Lock surface in Release 4.** `cartService.lock/unlock/markConverted` (DI) and commands `cart.lock/unlock/markConverted`, no public route, in Cart Phase 3. `lock` runs the trigger-5 re-price and the §6a.2 visibility pass first and refuses with `409 cart_has_unavailable_lines` while a line is flagged. Columns: `locked_at`, `lock_expires_at`, `checkout_session_id`. | Walked through |
| D-R4-5 (V4, W2) | **A flagged ("no longer available") line is excluded from totals and from promotion evaluation**, shown separately with a warning. One nullable state column on `CartLine`, in the Phase 1 migration. Removing it never changes the price. | Walked through |
| D-R4-6 (C7, Q5, W2) | **Token transport:** header `X-Cart-Token` on header-bound routes `/api/cart/current/*`; never in a path or query string. The storefront app owns the httpOnly cookie. Admin `/carts` and `/carts/[id]` stay free for Phase 4. Add a test that no route accepts a token in the path or query. | Walked through |
| D-R4-7 (C3, P4, P5, F4, V1/C4c) | **Gift (`ADD_FREE_ITEM`) lines** are real `CartLine`s with `promotion_id` + `origin: 'promotion'` (in the unique key, so they never merge into a paid line), actor `system`, buyer-immutable (`409 promotion_line_immutable`), excluded from eligibility but included in totals, flagged in `CartContext.items[]`. A gift that fails the buyer's assortment is not inserted and yields a `product_unavailable` warning. `product-page`, `dynamic-labels` and `free-products` respect the buyer's scope or require authenticated server callers. | Walked through |
| D-R4-8 (C4, P6, F5, X3) | **Code reservations hold capacity**, per cart: `cart_id` on `CodeReservation`, unique `(code_id, cart_id)`, idempotent `reserveCode`, `extendReservation`, release by `cartId`, a promotions-side sweeper. The per-customer limit counts `CodeUsage` plus other carts' active reservations. A guest cannot hold a code that has a per-customer limit. The cart extends on activity and emits `cart.promotion.no_longer_valid` plus a warning when a reservation lapses. | Walked through |
| D-R4-9 (P1, C10, F3) | **Line discounts reach `sales` as a line total:** `discountAmountBasis: 'line'`, `discountAmount = \|net line discount\|`, `discountPercent = null`; `CartLine.discount_total_net` is persisted. SPEC-055 §B.6 rule 1 / A-R6 / `TC-PROM-060` and cart §3.2/§14 are rewritten, and the claim in the 2.1.1 changelog that the identifiers "occur nowhere" is corrected. The release invariant is defined as: the same `SalesLineSnapshot[]` + adjustments give equal `SalesDocumentAmounts` for `quote` and `order`, compared as 4-dp numerics per key; the gate builds an order through the existing `sales` command from the cart's lines. | Walked through |
| D-R4-10 (P2, C5) | **Money in `ResolvedEffect` carries both sides:** every amount-carrying effect has `amountNet` and `amountGross` (+ `basis` for audit), rounded once, half-up, at the currency's fraction digits in integer minor units, passed through verbatim by the cart. | Walked through |
| D-R4-11 (P3, C3/A1/A2) | **Promotions HTTP API ships** (`evaluate`, `product-page`, `dynamic-labels`, `free-products`, `codes/*`, `usage/*`), authenticated with the standard API key (`x-api-key`), new features `promotions.evaluate`, `promotions.codes.redeem`, `promotions.usage.manage` (admin only in `defaultRoleFeatures`). `X-Module-Key` is dropped. Tenant and organization come from auth, never from the body; every referenced `promotionId`/`codeId` is ownership-checked; a cross-tenant test per route. | Walked through |
| D-R4-12 (P7, C6) | **Budget cap:** lock the promotion row (`SELECT … FOR UPDATE`) inside the transaction, re-read the sum, then write the usage. No serializable isolation, no retry helper. Test: N concurrent registrations inside one ambient transaction never exceed the budget. | Walked through |
| D-R4-13 (P8, R-H3) | **Time and cache:** the cache holds every `active = true` promotion; callers pass `evaluatedAt` in the context and date windows are filtered at evaluation. `totalDiscountGranted` lives in a separate small counters key, read only for budget-capped promotions. The main cache is invalidated only by promotion mutations. | Walked through |
| D-R4-14 (P10) | **Rule set in the Release 4 UI:** only rules with a data source: `order_value`, `order_date`, `product_count`, `cart_weight`, `row_total`, `product`, `category`, `product_attribute`, `customer_group` (replaces `user_group`), `code`, `customer_order_history`. Hidden until a source exists: `producer`, `exclude_pharmaceutical`, `consent_flag`, `delivery_method`, `payment_method`, `shipping_address`, and `delivery_discount` / `DELIVERY_DISCOUNT` (this also settles cart C5: delivery effects are not part of the cart-stage totals). Models and validators may stay. | Walked through |
| D-R4-15 (P10 sub-question) | **The `category` rule includes descendants** (ancestor match, the same logic as `scope_keys` in visibility); the UI echo line lists what is covered. | Walked through |
| D-R4-16 (P9, W8) | **Promotion × promotional price kind:** the cart promotion applies by default; each item in the context carries `priceIsPromotional`; a promotion can set `exclude_flags: exclude_promotional_prices`. The unbacked "promotional-price-visibility toggle" is removed from the form spec. | Walked through |
| D-R4-17 (C9) | Module id stays `cart` (singular) — a recorded exception to the plural rule, like `ecommerce` and `checkout`. | Adopted as a batch |
| D-R4-18 (C13, W4) | Only `token_hash` is stored for the cart token; the plaintext token is shown once at creation. | Adopted as a batch |
| D-R4-19 (C14, W14) | Phase 4 seam columns go into the Phase 1 migration: `Cart.kind` (default `basket`) + `proposed_to_cart_id` + check constraint, `CartLine.added_by_actor_type/id`, `CartMergeLog.merged_by_actor_type/id` + `proposal_cart_id`, `Cart.resolved_at`. Every basket query filters `kind = 'basket'`; non-basket carts are refused with `409 proposal_cart_immutable`; `strategy: 'manual'` returns `501 not_supported`. Availability fields are **not persisted** on `CartLine` (computed per response); GET writes only when a trigger fires. | Adopted as a batch |
| D-R4-20 (Q6, C8) | Q6: adopt the stated default (proposal carts follow the 90-day purge counted from `resolved_at`); the only Release 4 obligation is the `resolved_at` column. | Adopted as a batch |
| D-R4-21 (C11, X2, W17) | The promotion context is enriched on the promotions side, in batch, from `productId`/`variantId`; the cart sends ids, prices and quantities. Fields the cart stage cannot know are `null`. Promotions that newly appear at checkout are disclosed through `priceChanges`. | Adopted as a batch |
| D-R4-22 (V5, W4) | Lock and merge routes resolve the buyer context fresh (`storeContextService.resolve(request, { fresh: true })`, additive option) instead of the 60 s cached one. An expiry sweeper for `customer_groups.membership.expired` is a follow-up. | Adopted as a batch |
| D-R4-23 (V8) | `cart.line.visibility_rejected` is emitted once per request with a rejected count, and carries tenant and organization; never one per line, not `clientBroadcast`. | Adopted as a batch |
| D-R4-24 (V10, F3) | Recorded as an obligation on checkout (spec 7): call the same `evaluateCartVisibility` at submit, re-evaluate delivery effects, disclose newly appearing promotions, and refuse a channel/store mismatch. | Adopted as a batch |

| D-R4-27 (P13) | Benefits with `fixed` amounts or tiers, and `order_value` / `row_total` thresholds, require a single `eligible_currency` (write-path validation). | Adopted as a batch |

## Implementation order (from the cart analysis §11, confirmed)

1. Spec revisions (Phase 0).
2. Promotions Phases 1 → 2 (no cart dependency).
3. Shared seams (D-R4-3) and the ecommerce refactor.
4. Cart Phase 1, with the visibility check built into the first line command, plus the R1 suite.
5. Cart Phase 2.
6. Promotions Phase 3.
7. Cart Phase 3 plus the visibility gate (R1/R7/R13), totals equivalence with promotions, and the P95 benchmark.

No storefront add-to-cart path ships before step 4 completes.

## Non-goals of this release

Cart Phase 4 (B2B approvals, bulk lines, admin list, proposal seam §7a), SPEC-055 Phases 4–5 (search, notifications, injection slots, POS subscription, extension infrastructure), visibility Phase 4 (per-customer overrides), checkout, delivery/payment/address/consent-based promotion rules.
