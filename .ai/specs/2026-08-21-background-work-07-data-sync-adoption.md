**Scope of this spec**: `data_sync` as the first leased kind — `startDataSyncRun` atomicity, the engine as a bounded slice, the ownership fence extended with the lease epoch, rethrown errors, fenced cancel (incl. the existing cancel route), the scheduled trigger and out-of-tree in-process drivers through the lease, the run-status mirror and its re-open on operator re-drive, the existing retry route kept as "new run", and the soak that proves it. Plus **step 0**, the mechanism-independent hardening that only needs part 5 (`queueJobId`, `sync_runs.job_id`, the stall default) and can ship first. Closes fsh#101.

## 📝 TLDR

A run stops being one multi-day queue job and becomes a chain of ≤ 5-minute slices under a `progress_jobs` lease: created atomically with its `sync_runs` row, single-runner by a partial unique index instead of a racy SELECT, heartbeated through both `next()` and the handler phase, yielding on budget and SIGTERM, rethrowing transient errors so the transport retries the slice, refusing stale deliveries by identity, cancelled cooperatively through the lease's own channel, repaired by the reconciler under `orphanPolicy: 'redrive'` (the adapter contract is idempotent by construction), and **mirrored onto `sync_runs.status` in the same transaction as every terminal transition** so the dashboard can never show a run as `running` after its job has ended.

## 📝 Design — today vs the leased tier

| Today | With the leased tier |
|---|---|
| `startDataSyncRun`: `createJob` → `createRun` → `queue.add` (D-13) | `em.begin()`: `createLeasedJob({ kind, lockKey, subject }, scope, em)` + `createRun` → commit → `emitCreated()` → `enqueueLeasedJob`; enqueue failure → reconciler pending predicate. **Where the EM comes from** (the exported function takes `{ syncRunService, progressService, scope, input }` only, `start-run.ts:30-35`, and neither service exposes one): the params object gains `em?: EntityManager` and this spec updates every in-repo call site to pass the container's request-scoped EM — `sync_excel`'s import route, `sync-akeneo`'s `first-import.ts`, the retry route (`api/runs/[id]/retry.ts:132`) and `workers/sync-scheduled.ts:111` (plan step 1). There is **no ambient fallback**: nothing in this repo ever *enters* MikroORM's `RequestContext` (the DI container only reads it, `packages/shared/src/lib/di/container.ts:207` — `RequestContext.getEntityManager() ?? orm.em`, and the `?? orm.em` branch is the live one), so an ALS lookup would always return undefined. When `em` is absent, `startDataSyncRun` throws a descriptive error naming the migration ("pass the request-scoped EM from your container"). Declared as a category-2/3 signature addition in the compat table; "out-of-tree" field deployments must pass `em` on upgrade, covered by UPGRADE_NOTES. **`job_type` is the kind**: `data_sync.import` / `data_sync.export` (today `start-run.ts:42` writes `data_sync:<direction>`); a caller-supplied `input.progressJob.jobType` (`start-run.ts:21-22`) is **ignored** for leased runs — an unregistered `job_type` would be parked `no_handler` on its first tick — and logged once as deprecated |
| `findRunningOverlap` plain SELECT (D-11) | kept for the 409 message only; the **partial unique index** on `lock_key = data_sync:<integrationId>:<entityType>:<direction>` — exactly the three columns `findRunningOverlap` keys on (`sync-run-service.ts:437-453`), no other component — is the guarantee; the unique violation maps to the same 409 |
| one BullMQ job = whole run (D-1) | `step()` drives `forEachBatch` until `sliceBudgetMs` (5 min) elapses — the sole slice bound; no batch-count cap — returns `budget`; the engine stops *after* a yield, never mid-`next()`; the adapter is closed (`iterator.return()`), the next slice reopens from `run.cursor` — the replay clause already required of every adapter |
| heartbeat only around `next()` (D-6) | `heartbeat()` called around `next()` **and** the handler phase; `committed: true` after `commitBatchProgress` |
| ownership fence `status='running' ∧ batches_completed=N` | fence adds `EXISTS (select 1 from progress_jobs p where p.id = run.progress_job_id and p.lease_owner = $owner and p.lease_epoch = $epoch)` — a cross-module SQL reference, read-only, no ORM relation; no lease column on `sync_runs` |
| engine swallows errors (D-17, D-16) | engine **rethrows**; `QueueUnrecoverableError` for the fatal allowlist (from fsh#101, fail-fast only) — parked with `error_code = 'unrecoverable'` preserved even when the mirror cannot commit (part 6 §5 step 4, §6 Q1 row 2); transport retries the slice under the kind's `retry` (`attempts 5`, exponential 5 s, max 5 min — part 5's `maxDelay` mapping); `consecutive_failures` resets on commit; at `maxConsecutiveFailures` the slice fails terminally with the verdict `error_code = 'retry_exhausted'` (part 6 §5 step 4) |
| post-commit bookkeeping unguarded (D-18) | wrapped: log/progress write failures are logged, never fatal |
| `data_sync.run.started` emitted on every delivery with a `resumed` flag (`sync-engine.ts:558-565`) | emitted **once per run**, on the slice that moves the run `pending → running` (`resumed: false`); later slices emit nothing — liveness is the lease, not an event stream; the `resumed: true` variant is retired for leased runs (declared in the compat table). The `pending → running` transition is the **engine's alone**: `onRedrive` never performs it (a still-`pending` run stays `pending` through a re-drive — contracts), so a run whose job is re-driven before its first slice ran still emits its one `started`; the single stated exception is the never-started park carve-out (contracts) |
| cancel advisory, `markCancelled` immediately (D-21, D-22) | `signal` from the heartbeat response; engine checks `signal.aborted` at the batch boundary and passes `signal` to the adapter (#5403); `cancelled` written by the slice in the terminal transaction that also mirrors the run |
| `POST /api/data_sync/runs/[id]/cancel`: `markCancelled` on the job, then `sync_runs.status = 'cancelled'` + integration state + log, all immediately (`api/runs/[id]/cancel.ts:81-110`) | the route **requests** cancel only: `progressService.cancelJob(run.progressJobId)` (part 6 §8 — a `pending` job is cancelled at once with the mirror; a `running` one gets `cancel_requested_at`), **no direct `sync_runs` write**; the integration-state `degraded` upsert and the "Sync run cancelled" log move to the kind's after-commit hook for `cancelled`, so they run exactly when the run is cancelled. Response `{ ok: true, status: run.status }` — `cancelling` (job `running`) or `cancelled` (job was `pending`); the 409 for non-`pending`/`running` runs is unchanged |
| `POST /api/data_sync/runs/[id]/retry`: a **new** run from `previous.cursor` (or `fromBeginning`), admitted for `failed` **or `cancelled`** runs (`retry.ts:63-64, 132`) | **kept, unchanged**: it is the only way to resume a *cancelled* run (part 6's `redrive` refuses `cancelled`) and the only "from the beginning" path; it goes through `startDataSyncRun`, so the new run is a leased job under the same `lock_key`, which the index refuses while the old job is live. Part 8 wires Retry to the re-drive when the run's job is `redrivable` and to this route otherwise |
| `onJobAbandoned` + 5-min sweep (D-9) | retired for data_sync queues (kept in `packages/queue` for others); reconciler + `orphanPolicy: 'redrive'` (the adapter contract is idempotent by construction); poison after 3 orphan re-drives without a committed batch (`poisonRedrivesWithoutCommit`, Q1), `never_started` after 10 lost hand-backs without a commit (`maxRedrives`, Q2) — both on `redrives_since_commit` |
| out-of-tree in-process drivers (D-10, S9): `startDataSyncRun({ createProgressJob: false })` then `engine.runImport` in-process, no lease — there is **no** in-tree `data_sync` CLI (`packages/core/src/modules/data_sync/` has no `cli.ts`; the only sync CLI is `sync_akeneo`'s `configure-from-env`) | `createProgressJob` is **ignored** (kept on the type, logged once as deprecated — the lease is mandatory): `startDataSyncRun` always creates the leased job on the caller's EM transaction and enqueues it; a driver that must run in-process binds `runSlice` for the kind's queue in its own process (the worker factory part 6 ships) and lets the transport deliver to it, so its slice runs under the same lease and a killed process is an orphan the reconciler sees. **`engine.runImport`/`runExport` refuse at entry when called without a lease on a leased run** (the run's job carries `lock_key` and the caller passed no lease context ⇒ throw a descriptive error naming the migration — "bind `runSlice`", this row) instead of letting the first `commitBatchProgress` fail its epoch `EXISTS` fence with `SyncRunOwnershipConflictError` after a page of work. This is a behaviour break for the unmodified S9 pattern (`createProgressJob: false` + in-process `runImport`), declared as such in the compat table — not additive. No new command is added by this spec |
| `sync-scheduled`: `lastRunAt` flushed before anything durable (S-14) | start the run first (one transaction), then `lastRunAt`; a second firing hits the unique index → 409 → skipped (Fivetran semantics) |
| stale sweep from the browser (D-5) | reconciler; the tracked-tier sweep carries `lock_key is null` (part 6 §6 Q4) so it never touches a run's leased job; `sync_runs.status` and `last_error` mirrored by `onTransition` **inside the terminal transaction** (part 6 §7, `mirror: 'atomic'`) on every terminal/park/cancel transition (D-28) — a run can no longer stay `running` while its job is terminal. `sync_runs` has no finished timestamp and gains none: the run's end time is its job's `progress_jobs.finished_at` (via `progress_job_id`), and `sync_runs.updated_at` moves with the mirror |
| `retryRun` / operator retry: a new run from the old cursor (D-26) | **re-drive of the same run**: part 6's `redrive` re-opens `sync_runs` through `onRedrive` in the same transaction (`failed → 'running'`, a still-`pending` run stays `pending`, `last_error = null` — contracts), so the next slice's fenced commit lands and the run keeps its id, cursor, counters and history; a fresh run is still what "Run" does |
| `paused` declared, never written (D-26) | unchanged here; becomes `waiting` in the Q6 follow-up |

## 📝 Contracts

- `LeasedJobKind` registrations in `packages/core/src/modules/data_sync/job-kinds.ts` (part 6 §4's auto-discovered convention file, loaded by every process — web, worker, out-of-tree drivers — because the re-drive route and `startDataSyncRun` need the kind, not only the worker): `data_sync.import` and `data_sync.export`, `queue` = the existing per-direction queues, `requiredFeatures: ['data_sync.run']` (gates re-drive only; cancel stays `progress.cancel`), `lease: { ttlMs: 60_000, sliceBudgetMs: 300_000, pendingTtlMs: 900_000 }`, `budget: { maxRedrives: 10, maxConsecutiveFailures: 5, poisonRedrivesWithoutCommit: 3 }`, `retry: { attempts: 5, backoff: { type: 'exponential', delay: 5_000, maxDelay: 300_000 } }`, `orphanPolicy: 'redrive'`, `mirror: 'atomic'`. The kind id is also the row's `job_type` (rename from `data_sync:<direction>`; caller overrides ignored — design table).
- `lock_key = data_sync:<integrationId>:<entityType>:<direction>` — the same triple `findRunningOverlap` keys on and nothing more, so the index and the SELECT answer the same question; `subject = { type: 'data_sync.run', id: run.id }`.
- `StartDataSyncRunInput.createProgressJob` (`start-run.ts:20`, exported; its only reader is `start-run.ts:37` itself — the in-repo callers `sync-akeneo` and `sync_excel` call `startDataSyncRun` without the field and are covered by this spec's own implementation): **kept** on the type for unknown out-of-tree users, marked `@deprecated`, ignored with a one-time deprecation log — the same treatment as `progressJob.jobType` **and `progressJob.cancellable`**: part 6's `createLeasedJob` accepts neither and forces `cancellable: true` (a leased run must be stoppable through `cancelJob`, the only cancel entry point — today's route ignores the flag via `markCancelled`, so a caller that passed `cancellable: false` loses nothing it actually had). Removing the field would be a category-2 break.
- **Batch size**: the leased delivery payload is fixed at `{ jobId, seq, redrives, scope }` (part 4 §5.1), so `batchSize` stops travelling in the queue payload (today its only home — `start-run.ts:79-80`, `sync-import.ts:16-17`). `startDataSyncRun` persists it at start into `sync_runs.parameters.batchSize` (the existing json column, `entities.ts:56-57`; merged over `input.parameters`, default 100 as today); `step()` reads it from the run row it loads anyway and passes it to the engine — the engine's slice loop takes it from the run, not from an argument. Constant for the life of the run, surviving yields, retries and re-drives.
- Cancel route `POST /api/data_sync/runs/[id]/cancel`: loads the run, keeps its 404/409/mutation-guard checks, then calls `progressService.cancelJob(run.progressJobId, ctx)` and returns `{ ok: true, status }` where `status` is re-read from the run (`cancelled` if the job was `pending` and the terminal transaction just mirrored it; `cancelling` otherwise — a run status the API *reports* from `cancel_requested_at`, not a `sync_runs.status` value). It no longer calls `markCancelled` (which returns a leased row unchanged, part 6 §3), `syncRunService.markStatus(run.id, 'cancelled')`, `integrationStateService.upsert` or `integrationLogService.write`; the last two run from the kind's after-commit hook for the `cancelled` transition (below). A run whose job is tracked-tier (created before this spec shipped) keeps today's path behind `if (!job.lockKey)` for one minor release.
- After-commit hooks — the kind's `onAfterTransition(job, scope, container)` and `onAfterRedrive(job, scope, container)` (the declared `LeasedJobKind` members, part 6 §4; run at-most-once by whichever process committed the transition: a worker slice, the **reconciler worker** for Q1/Q2 parks and Q3 cancels — so reconciler-driven transitions run these hooks too, in that worker's container — or the web process for a pending-path cancel). `onAfterTransition`, switching on the job's terminal status, carries **all** the operational telemetry the engine's finalize writes today (`sync-engine.ts:424-470`, `updateOperationalState`/`writeOperationalLog` — it would otherwise be silently dropped for leased runs): on `completed` → emit `data_sync.run.completed`, `integrationStateService.upsert(… 'healthy')`, "Sync run completed" log; on `failed` (incl. parks) → emit `data_sync.run.failed`, upsert `'unhealthy'`, log; on `cancelled` → emit `data_sync.run.cancelled`, upsert `'degraded'`, the "Sync run cancelled" log the route wrote today. `onAfterRedrive` emits `data_sync.run.redriven`. All best-effort and at-most-once (a throw is logged, never retried — part 6 §7 step 4).
- Retry route `POST /api/data_sync/runs/[id]/retry`: unchanged (status gate `failed | cancelled`, `fromBeginning`, `startDataSyncRun` → a new leased run). It is the "resume a cancelled run" and "restart from the beginning" path; the re-drive is the "continue this run" path.
- `onTransition(job, scope, em)`: one fenced UPDATE against the columns `sync_runs` actually has (`entities.ts:4-72`: `status`, `last_error`, `updated_at`; there is **no** `finished_at`/`error_message`) — `update sync_runs set status = $mapped, last_error = $msg, updated_at = now() where id = $runId and progress_job_id = $jobId and deleted_at is null and status in ('pending','running')` — idempotent, no events, returns `{ matched }` (part 6 §7: `matched = 0` is a failed mirror, counted in `mirror_attempts`, never recorded as mirrored); `data_sync.run.completed|failed|cancelled` are emitted from the after-commit hook.
- `onRedrive(job, scope, em)`: the re-open, one fenced UPDATE inside part 6's `redrive` transaction — `update sync_runs set status = case when status = 'failed' then 'running' else status end, last_error = null, updated_at = now() where id = $runId and progress_job_id = $jobId and deleted_at is null and status in ('pending','running','failed')` — idempotent, no events. **It never performs `pending → running`** (part 6 §4's re-open rule): a `running` run (the expired-lease case) matches and stays `running`; a `pending` run — the expired-lease case where the slice died before the engine's first `markStatus(run.id, 'running')`, `sync-engine.ts:558` — matches and **stays `pending`**, so the re-driven slice itself moves it `pending → running` (`markStatus('running')` accepts the transition, `sync-run-service.ts:206`) and emits the run's single `data_sync.run.started` — the cadence row survives a re-drive; only `failed` is mapped back to `'running'`. **The one stated carve-out**: a run whose job was parked while the run had never left `pending` (`never_started`, or any park/verdict landing before the first `markStatus('running')`) was mirrored `failed` *from* `pending`, and nothing on `sync_runs` records that `started` never fired — its re-drive re-opens it as `running` and that run emits no `data_sync.run.started`; `data_sync.run.redriven` (emitted for every committed re-drive) and the terminal event are its lifecycle signals. `matched = 0` (run soft-deleted, or `cancelled`/`completed`) rolls the re-drive back and the route answers 409 `domain_refused`. This is what lets the re-driven slice pass the ownership fence below: without it `claimRunOwnership` (`sync-run-service.ts:322-336`, `status: 'running'`) would match zero rows on a run the park had mirrored to `failed`, throw `SyncRunOwnershipConflictError` on every slice and burn the retry budget. `batches_completed` and `cursor` are untouched — the re-driven run resumes where it stopped. The after-commit hook emits `data_sync.run.redriven` (additive id, `clientBroadcast` — part 8's dashboard refresh).
- Ownership fence in `commitBatchProgress`: existing `status='running' ∧ batches_completed=N` **and** `exists (select 1 from progress_jobs p where p.id = sync_runs.progress_job_id and p.lease_owner = $owner and p.lease_epoch = $epoch)` — a read-only cross-module SQL reference, no ORM relation, no lease column on `sync_runs`.
- Adapter contract: **signature unchanged**; the replay clause (reopen from `run.cursor`) is now exercised on every yield.
- `sync_runs.job_id` (text, exists, never written): carries the latest `queue_job_id` from step 0 on.

## 📝 Edge Cases & Failure Scenarios (the part 1 scenarios under this design; mechanism-level cases are in part 6)

| Scenario | Behaviour under this design |
|---|---|
| S1 deploy, two replicas, mid-batch | SIGTERM → runner aborts `signal` → engine finishes the current batch → `yieldSlice({interrupted:true})` → `ctx.yield({data})` → `close()` returns; the new pod claims the rewritten delivery at once. No stall, no attempt, no budget. Grace shorter than a page (Railway default 0 s): SIGKILL → lease expires ≤ 60 s → reconciler takes and re-drives within one tick with `redrives+1`, reset by the next committed batch. |
| S2 transient error mid-batch | `failSlice` + rethrow → transport retries the same delivery after 5 s/10 s/…; the retry claims (lease released, same `seq, redrives` — `claim` reads no `next_run_at`, so a retry the broker delivers a little early is accepted) and resumes from `run.cursor`. Same end state whether the outage lasted 1 s or 5 min (R-F4). After 5 consecutive failures with no commit → terminal `failed` with `error_code = 'retry_exhausted'`, `sync_runs.status = 'failed'` in the same commit, no further transport attempt (part 6 §5 step 4); re-drivable by an operator. |
| S5 double start | second `createLeasedJob` violates the partial unique index inside the transaction → both rows roll back → 409. No window. |
| S6 enqueue fails after the row exists | row `pending` with `pending_since`, no lease; reconciler Q2 re-drives it after `pendingTtl` (15 min) with a new delivery id. |
| S7 stale sweep false positive | leased rows are not subject to the heartbeat-based sweep — by the `lock_key is null` clause on both of its predicates and the revive path (part 6 §6 Q4, invariant 10), not by convention; a run yielding between slices (`pending`, old `created_at`) or waiting out a transport backoff (`running`, no heartbeat) is judged by its lease only. The lease is heartbeated through the handler phase. |
| S8 abandoned while alive | no stall budget consumed by deploys; a poison page parks after 3 redrives without a commit (`error_code='poison'`) with operator re-drive. |
| **Operator re-drives a parked or failed run** | part 6 `redrive` + `onRedrive` in one transaction: `progress_jobs` → `pending` (both budgets reset) and `sync_runs` re-opened with `last_error = null` (`failed → 'running'`; a still-`pending` run stays `pending` and emits its single `data_sync.run.started` on the re-driven slice — contracts); the new delivery claims, the engine reopens the adapter from `run.cursor`, and the first `commitBatchProgress` passes the fence (`status = 'running'`, `batches_completed = N`, lease `EXISTS`). A run that had exhausted the transport's retry budget (S2) is re-drivable the same way. If the run was soft-deleted meanwhile → 409 `domain_refused`, nothing changes. |
| S9 in-process out-of-tree driver killed | it ran `runSlice` under the lease (design table) → orphan → reconciler. |
| **Operator cancels a running leased run through `POST …/runs/[id]/cancel`** | the route calls `cancelJob` only: `cancel_requested_at` set, response `cancelling`; the slice's next heartbeat (≤ 20 s) aborts `signal`, the engine stops at the batch boundary, the §7 cancel transaction writes `progress_jobs.cancelled` **and** `sync_runs.status = 'cancelled'` together; then the after-commit hook emits `data_sync.run.cancelled`, marks the integration `degraded` and writes the log. If the slice is dead, Q3 does the same after the lease expires. With the route as it stood (`markStatus('cancelled')` first) the slice's next `claimRunOwnership` (`status: 'running'`, `sync-run-service.ts:322-336`) would match zero rows and burn the retry budget, and the later mirror (`status in ('pending','running')`) would match zero rows forever — `mirror_stuck` on a run the dashboard already showed as cancelled. |
| **Operator cancelled by mistake** | `redrive` refuses `cancelled` (part 6 §3); the existing retry route starts a new run from the cancelled run's cursor (the old job is terminal, so the `lock_key` is free); part 8 offers exactly that. |
| S10 abandon report lost | not needed: the reconciler reads Postgres. |
| S11 Akeneo reconciliation after last yield | unchanged here; the `finalizeRun` adapter hook is a data_sync follow-up. |
| Heartbeat inside the slice's domain transaction | impossible by construction: `heartbeatLease` runs on a forked EM (invariant 1); the engine's `withAtomicFlush` transaction never contains a lease statement. |
| Rolling deploy with mixed versions | new columns nullable/defaulted; old workers ignore them; old `startDataSyncRun` still works (tracked tier) until the data_sync worker is updated — this spec ships worker and route together. **Deliveries already queued at cutover** carry the previous release's `{ runId, batchSize, scope }` payload on the *same* queue names (`sync-import.ts:16-23`, `queue-policy.ts:6-7`) and their runs are tracked-tier jobs no reconciler repairs; handed to `runSlice` they would be refused (`claim(undefined, …)` → null → `delivery_refused`) and the transport job completed — one D-5 `running`-forever zombie per in-flight run. The new worker therefore binds `runSlice` **behind a one-minor-release payload shim**: a delivery whose payload has no `jobId` runs the old handler body (`engine.runImport(runId, batchSize, scope)` and its catch block), with `onJobAbandoned` kept and guarded to exactly those `runId`-shaped deliveries, so in-flight runs drain under the old semantics; the shim is removed together with the cancel route's tracked-tier fallback after one minor release (compat table). |
| `sync_runs` row deleted while the job is live | the terminal mirror matches zero rows → `DomainMirrorMismatchError` → the job row stays non-terminal, `mirror_attempts` grows, `mirror_stuck` surfaces it under part 8's "stuck" filter; the resolution is to **restore the `sync_runs` row** — the next mirror attempt then matches and the job ends normally, from the slice's transport retry or the next reconciler tick. Cancel is not a way out (`onTransition` mismatches on the cancel transaction too) and neither is re-drive (`onRedrive` answers `domain_refused`), and part 8 ships no job-row delete, so a run row that is *permanently* gone is an operator database action and the generic "delete a stuck job row" affordance is a Q6 follow-up. What the design guarantees here is the negative: never a silently `completed` job beside a missing run. |
| Run completes, then the process dies before `sync_runs` is updated | impossible under part 6 §7: the run's `status` is written by `onTransition` in the same transaction as the job's terminal CAS; a crash before commit leaves both `running`, the lease expires, the reconciler re-drives, `step()` finds the cursor at the end and returns `drained`, and the terminal transaction is retried. |

| Rollback | — | redeploy the previous `data_sync` worker and route; leased rows in flight are parked by the reconciler (`no_handler`, `domain_mirrored_at` stamped in the park CAS, collected by retention) — **their `sync_runs` rows are not touched** (no hook exists to mirror them) and stay `running` until the kind registers again and an operator re-drives (`onRedrive` admits `running`) or cancels them, or until they are fixed by hand; the previous worker's `abandoned-run.ts` does not see them (it keys on queue abandonment). **The queues must also be drained of `pj-*` deliveries before the previous worker re-binds** (`data-sync-import`/`data-sync-export` are the same queue names, `queue-policy.ts:6-7`): the old handler reads `job.payload.runId` (`sync-import.ts:42`) — `undefined` on a `{ jobId, seq, redrives, scope }` payload — so each leftover delivery throws through its `DATA_SYNC_QUEUE_ATTEMPTS` (3) attempts, spams the logs and is retained as a failed job holding its id; remove them via `removeJob` on every `sync_runs.job_id`/`queue_job_id` or flush the two queues. A leased run whose cancel was requested before the rollback is cancelled by Q3's unregistered-kind branch instead of parked (part 6 §6) — its `sync_runs` row is equally untouched. Rolling **forward** needs no drain: the payload shim in the rolling-deploy row runs leftover `{ runId }` deliveries through the old handler for one minor release. Stated as the honest cost of rolling back with runs in flight. Step 0 is independently revertible | operators must drain or re-drive in-flight runs — and clear `pj-*` deliveries — around a rollback |
