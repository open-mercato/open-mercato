# MCP HTTP tool calls require a per-user session token, no fallback

## TLDR
Close #5173 for good: `mcp:serve-http` (the chat-facing MCP transport) now has exactly one unauthenticated outcome — `UNAUTHORIZED`. The default-off `allowApiKeyFallback` opt-in that PR #9314 initially shipped is removed rather than kept, because retaining the vulnerable branch behind a flag does not satisfy the Emergency Security Exception.

## Problem statement
`createMcpServerForRequest` (`packages/ai-assistant/src/modules/ai_assistant/lib/http-server.ts`) builds one MCP server per HTTP request from a base `toolContext` scoped to the transport-level `x-api-key` — which is provisioned from the superadmin account by `mcp-ensure-api-key.ts`. The original code authorized any tool call that omitted the per-user `_sessionToken` argument using that transport key's ACL. Because session tokens are minted only on a brand-new chat session and a minting failure "continues without a session key," a model omission, a prompt injection, or a turn on an existing session could run a tool call with superadmin authority — a classic confused-deputy bypass.

PR #9314's first pass made the fallback opt-in via `McpServerConfig.allowApiKeyFallback` / `mcp:serve-http --allow-api-key-fallback`, default off. Formal review (2026-11-14) rejected this: the repository's [Emergency Security Exception](../../BACKWARD_COMPATIBILITY.md#emergency-security-exception) requires that "no partial bridge retains the vulnerable branch behind a flag, a config toggle, or an opt-in." An opt-in is exactly that — any deployment that turns it on reopens the same bypass for every call through that transport, including one reached from a chat turn, because the HTTP transport has no way to distinguish an "operator" caller from a "chat" caller at the request level.

## Proposed solution
Delete the opt-in entirely instead of gating it. `mcp:serve-http` keeps exactly the branch structure it already had for the two authenticated cases (session token present → `resolveSessionContext`; none of the above → `UNAUTHORIZED`) and loses the third (`allowApiKeyFallback` → `resolveApiKeyContext`). `McpServerConfig` no longer declares the field; `cli.ts` no longer parses or wires the flag.

Operators who need genuine header-only / unattended access do not need a new mechanism: the stdio transport (`mcp:serve`) already supports it through `--allow-unauthenticated-superadmin` (shipped 2026-06-11, #2673), and that transport is a distinct CLI process that OpenCode's chat-facing Docker container never starts and a chat turn can never select. This is the "explicit operator mode... that cannot be selected by a user conversation" the original issue's own implementation guidance asked for — it already existed, so the fix is to point operators at it rather than build a second one next to the chat transport.

## Architecture
No new surface. `createMcpServerForRequest` drops its now-unused third parameter (`apiKeyRecord: ApiKey`) along with the deleted branch and the `resolveApiKeyContext` helper it alone called; `runMcpHttpServer`'s call site is updated to match. The server-level `x-api-key` check in `runMcpHttpServer` is unchanged — it still gates connecting to the HTTP endpoint at all — only the per-tool-call fallback it used to feed is removed. Stdio `mcp:serve` / dev-only `mcp:dev` are untouched.

## Migration & Backward Compatibility
`McpServerConfig.allowApiKeyFallback` and `mcp:serve-http --allow-api-key-fallback` are removed. Neither shipped in a released version — both were introduced and removed again inside PR #9314 before merge — so this is not a break of a previously shipped contract, but it is still a deliberate, disclosed behavior change from `main`'s pre-#5173 behavior: a deployment that calls `mcp:serve-http` with only an `x-api-key` header and no `_sessionToken` now always gets `UNAUTHORIZED`, with no opt-in to restore the old header-only authorization.

- **Client migration (chat-facing callers):** none required. The web chat and Code Mode flows already mint and pass a per-user `_sessionToken` on every tool call.
- **Operator migration (header-only / automation callers):** switch to `mercato ai_assistant mcp:serve --allow-unauthenticated-superadmin --tenant <id>` (or `--user <id>` for a scoped-ACL identity) instead of `mcp:serve-http`.
- No database, event-id, route, ACL-feature, or widget-spot change. No stored credential or data becomes unusable.
- This ships under the [Emergency Security Exception](../../BACKWARD_COMPATIBILITY.md#emergency-security-exception): the removed branch is itself the vulnerability, so no bridge release is offered. See the dated [`BACKWARD_COMPATIBILITY.md`](../../BACKWARD_COMPATIBILITY.md#mcp-http-session-token-no-fallback-2026-11-14-5173) entry and [`UPGRADE_NOTES.md`](../../UPGRADE_NOTES.md#mcp-http-tool-calls-require-a-per-user-session-token-no-fallback-5173) for the full migration text, and requirement 5 (named maintainer sign-off) for the open approval this PR still needs before merge.

## Validation plan
- Unit (`lib/__tests__/http-server-session-fallback.test.ts`): missing token → `UNAUTHORIZED`, `loadAcl` never called; empty-string token treated as missing; a config object carrying a stray `allowApiKeyFallback: true` (defensive — the type no longer declares the field) still fails closed; a valid session token resolves per-user identity normally.
- Boundary (`lib/__tests__/http-server-auth-boundary.test.ts`): exercises the real `node:http` server started by `runMcpHttpServer` end-to-end over the real MCP wire protocol (`@modelcontextprotocol/sdk`'s client `Client` + `StreamableHTTPClientTransport`), with the real tool registry, `executeTool`, and `hasRequiredFeatures` — only the DB-backed lookups (`findApiKeyBySecret`, `findSessionApiKeyWithSecret`) and `rbacService.loadAcl` are stubbed, since this package has no live-Postgres Jest lane. Proves a missing x-api-key is rejected before any tool runs; the superadmin-owned transport key alone (no `_sessionToken`) is rejected with no fallback; an invalid/expired `_sessionToken` never executes a tool; a restricted session is denied a tool outside its granted feature and never executes it; and a same-scope call succeeds under the session identity, with `loadAcl` asserted to never be called for the transport key's identity in any denial case.

## Risks and architecture
Blast radius is confined to the single auth branch inside `createMcpServerForRequest`; no other module, route, or transport is touched. The residual risk is operational: a deployment that was relying on the brief window where `allowApiKeyFallback` existed (PR #9314, unreleased) must switch to `mcp:serve --allow-unauthenticated-superadmin` before upgrading, or header-only automation stops working. No in-repo caller depends on the removed field, so no further code migration is needed.

## Final compliance review
Tenant/organization scoping, RBAC enforcement per tool call, and the two-tier auth model (transport key + session token) are unchanged except for the removal of the fallback. No module-boundary or ORM changes. No `any` introduced. `BACKWARD_COMPATIBILITY.md` carries the dated Emergency Security Exception entry; `UPGRADE_NOTES.md` carries client and operator migration text. Maintainer sign-off (exception requirement 5) is still outstanding — the PR carries the `security` label and calls out the waiver for a human maintainer's explicit approval, which a same-account automated review cannot supply.
