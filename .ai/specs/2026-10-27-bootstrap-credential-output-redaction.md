# Bootstrap credential output redaction

## TLDR

Issue #7822: remove bootstrap passwords from initialization output and redact secret-bearing module CLI options before logging. Keep account identifiers, command execution arguments, exit status and first-run container behavior.

## Overview & Problem Statement

Operators initializing an app can expose live administrator credentials to terminal capture, CI and container logs. The CLI success banner retains passwords solely to display them, the generic module dispatcher echoes unredacted options, and exception messages can repeat inputs. Both first-run container scripts forward success and failure output. This is distinct from predictable bootstrap defaults (#7809).

## Proposed Solution

Remove password-only presentation state from the initialization banner. Sanitize module argument logs and initialization/module exception messages using an internal CLI output helper. Verify successful and failed initialization output through both first-run script copies.

## Architecture

`packages/cli/src/lib/cli-output.ts` owns output-only sanitization. Credential suffixes are matched case-insensitively after normalizing hyphens/underscores, including versioned secrets; both `--option value` and `--option=value` are masked. Passwords, tokens, credentials, authorization/bearer values, common secret keys and database/Redis connection strings are covered. Token counts, token-cache durations and raw-token storage booleans are configuration values, not credential suffixes. Actual short, numeric or boolean credentials remain redacted. Known secret CLI/environment values and URI passwords are masked in dispatcher failure diagnostics. The banner uses already-sanitized arguments plus URI-password masking, without globally replacing environment values. The original argument array goes unchanged to command handlers.

The exported `redactRailwayCliArgs` helper remains intentionally available with its existing behavior for downstream import compatibility. The framework dispatcher now uses the generic helper, while the Railway helper and its regression test preserve the older provider-specific import surface.

Initialization lists the same deduplicated account identifiers and completion banner without collecting presentation passwords. Production derived passwords remain generated by the existing mechanism, and its environment overrides remain available to redact failures. The two shell scripts remain byte-identical and continue forwarding CLI output and preserving marker/exit behavior. No global console interception or provider-specific configuration is introduced.

## Data Models & API Contracts

No entity, schema, tenancy, authorization, encryption map, HTTP API, event, DI key or generated registry changes. No API/UI integration paths are affected. Account creation, password hashing, demo defaults and reset behavior remain owned by existing auth code. Third-party commands remain responsible for their own output; this change protects CLI-owned banners and failure diagnostics.

## Implementation & Validation

One phase, one confidentiality invariant: framework-owned initialization and dispatcher logs must not reveal credential inputs.

1. Remove initialization password presentation and sanitize dispatcher arguments/errors.
2. Cover supplied/generated passwords, success/failure, split/equals/repeated options, unchanged execution inputs and URI credentials. Run captured real initialization output through both starter and generated-app first-run scripts, asserting exit status and marker state.
3. Document migration and run targeted CLI tests, boot-script tests and focused TypeScript checks. The full configured build/generate/i18n/typecheck/test/app-build gate remains required in CI when unavailable locally.

## Risks & Impact Review

| Scenario | Severity / area | Mitigation | Residual risk |
|---|---|---|---|
| Automation expects a stdout password | Medium / operators | Supply credentials through existing overrides or use password reset; disclose removal below | Existing log-scraping scripts must change |
| A module throws an error containing its secret input | High / CLI | Mask known CLI/environment credentials and URI passwords | Arbitrary third-party console output and transformed/encoded secret fragments remain the module's responsibility |
| A benign flag contains a sensitive name | Low / diagnostics | Redaction only changes logs; original execution args stay intact | Some non-secret diagnostic values can be masked |
| First-run success/failure changes marker state or exit code | Medium / deployment | Replay actual CLI output through both shell-script copies and retain existing recovery tests | Live Railway/production deployment is not exercised |

## Migration & Backward Compatibility

Consumers that scrape passwords from stdout must supply credentials through the existing environment variables or use the existing password-reset flow. No CLI command or flag is removed. The final spec records the security-output exception, operator migration and validation evidence.

The removed surface is plaintext credential output: retaining it behind a bridge or toggle would keep the disclosure reachable. This is the narrow security exception to the deprecation protocol; no insecure output opt-in is retained. The dated `BACKWARD_COMPATIBILITY.md` entry and `UPGRADE_NOTES.md` carry client and operator migration. A named human maintainer must acknowledge the waiver before merge; automated review cannot supply that sign-off.

Operators should supply the existing `OM_INIT_SUPERADMIN_PASSWORD`, `OM_INIT_ADMIN_PASSWORD` and `OM_INIT_EMPLOYEE_PASSWORD` overrides from their secret manager when they need known initial credentials. If production derived passwords were generated without overrides, use the configured password-reset flow; no replacement secret file is created. Rotate bootstrap credentials that may already appear in retained logs and restrict/purge those logs according to retention policy. This patch cannot remove previously copied credentials.
