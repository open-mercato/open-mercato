# Issue 9142: constrain user-task completion context writes

Status: implemented on the fix branch; human compatibility approval pending.

## Problem and scope

Staff and portal task completion share `taskHandler.completeUserTask`. The handler checks required-field presence but accepts unrelated keys and engine state, then persists the completed task and merges its payload into workflow or branch context. A task assignee can redirect later privileged workflow activities.

Keep the existing handler, routes, DI registration, tenant/organization and ownership checks, forms, decision routing, and context merge architecture. No schema migration, startup/configuration changes, or dependencies.

## Implementation

Before mutating any entity, normalize the task's schema with `normalizeTaskFormSchema`, accepting both JSON Schema `properties` and Studio `fields`. Reject any submitted top-level key absent from its own declared properties. Missing/empty schemas authorize no form keys; empty submissions remain supported. Reject all `__`-prefixed keys and `findReservedContextKeys` results even when declared. Required-field validation retains its existing behavior.

The legitimate `__decision` value is generated by `withRecordedDecision` only after validating the authored `decisionId`; callers cannot inject the engine's decision field through `formData`. Preserve optional fields, false/zero/empty-string values, and authored nested values without adding type validation or changing nesting.

Map `FORM_VALIDATION_FAILED` explicitly to HTTP 400 on staff completion, matching portal completion. Invalid submissions must leave task, context, events, and branch continuation untouched.

## Regression coverage

- Both schema shapes: allow declared fields; reject undeclared context keys.
- Missing/empty schemas: allow `{}`; reject nonempty payloads.
- Reserved fields, including declared ones, cannot write internal workflow state.
- Empty, falsy, and nested authored values retain existing behavior.
- Staff and portal routes return 400 with no mutation, and valid submissions still complete.
- Valid decision buttons still select and record the authored decision; forged `__decision` fails.
- Main and parallel branch paths share pre-mutation validation.

## Migration & Backward Compatibility

This intentionally stops accepting arbitrary completion payload keys on `POST /api/workflows/tasks/[id]/complete`, `POST /api/workflows/portal/tasks/[id]/complete`, and the `taskHandler` DI completion behavior. Client request/response envelope shapes, URLs, permissions, events and database schema remain unchanged, but payloads previously used as arbitrary context patches now fail with 400.

Clients must send only authored form fields and use `decisionId` for a decision. Operators must inventory custom task widgets/integrations and pending tasks, declare intended editable context keys in the task form schema, and remove engine-reserved field names. No migration or retrospective context repair is performed; audit suspicious existing runs separately.

Retaining permissive completion behind a compatibility bridge would retain the exploit. Client/operator instructions ship in `UPGRADE_NOTES.md` and a dated entry ships in `BACKWARD_COMPATIBILITY.md`. The repository's emergency security exception still requires a named maintainer's human waiver approval before merge; automated review cannot waive it. The draft PR records this gate.
