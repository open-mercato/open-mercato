# CRM Calendar — public meeting booking page per user

## 📝 TLDR
**Key points:**
- A public, no-login page at **`/calendar/{orgSlug}/{userSlug}/meetings`** where an external person picks a free slot in a CRM user's calendar, enters e-mail, first name and last name, and books a meeting.
- A confirmed booking creates a scheduled `CustomerInteraction` (a meeting) owned by that user. It appears in the CRM Calendar (`/backend/calendar`, spec `2026-06-11-crm-calendar.md`). The booker receives an e-mail with an `.ics` attachment and a private manage link for cancelling or rescheduling.
- Each user opts in and configures their own booking profile with five essentials: the on/off switch with the link, a page title, the meeting length, weekly hours (one range per day) and whether each booking needs their approval (requests not answered within 24 hours expire). A collapsed **Advanced** section holds description, location, minimum notice, horizon, a buffer after meetings, a daily cap and booker self-service, all with defaults, so turning the page on is enough to share the link.
- The visitor can add an optional note about what the meeting is about; the owner sees it in the request row. Accepting a request is one click.
- The feature lives in the **`customers`** module. It adds two entities plus an idempotency-key table. It also makes these additive changes to existing code: the conflicts route is refactored onto a shared busy-time helper (same contract, including its e-mail visibility filter); the directory module's organization lookup is refactored onto an exported `resolveOrganizationBySlug` helper that booking reuses (same behaviour); `people.create` and `interactions.cancel` gain the same `transactionalEm` support as `interactions.create`/`update`; the customers module's direct emit helpers defer to commit when a command runs inside a caller's transaction (booking nests the CRM commands through the command bus's existing ambient execution, which needs no change); and a `customers` upgrade action registers the maintenance schedule. No existing entity or route contract changes, and no existing command gains a new failure mode.

**Scope:** booking profile settings (a backend profile page), public booking page, slot engine, booking requests with an approval and expiry lifecycle, manual matching of the booker to a CRM person, `.ics` e-mails, one reminder e-mail to the booker, and booker self-service cancel and reschedule.

**Out of scope:** multiple meeting types per user, team or round-robin pages, payments, custom booking questions (beyond the one optional free-text note), video-conference link generation, integration with external calendar providers (Google, Microsoft; see below), bulk accept/decline, date overrides and multiple time ranges per day, CAPTCHA (an extension point only), and guarantees about e-mail delivery (the platform's existing event and e-mail delivery is used as a black box; Proposed Solution → E-mail delivery).
- **Intended users (this phase) and external calendars:** this phase is for users who manage their calendar wholly in Open Mercato, or who block their Google or Microsoft calendar time for meeting requests by hand (by adding those meetings as CRM events, or by keeping their working hours to times they are free). Availability only knows what is in the Open Mercato calendar, and the settings page says so plainly. Integration with external calendar providers is out of scope: it can only be built once calendar connectors exist in the codebase, and none do today. When a connector later syncs external events into CRM interactions, they block times with no change to this feature. Accepting this limit for this phase is the product owner's call: confirmation is requested from the product owner (pkarw) on PR #8214, and this sentence will then name who accepted it and when. The UX review asked for that decision; it did not make it.
- **The bookings module:** the bookings module spec (`2026-08-10-bookings-module.md`, §19 `/book/{slug}`) remains the home for service and resource bookings with pricing (a car, a room, a paid service). This feature is a personal "book a meeting with me" link, like Calendly, for sales and customer calls over CRM interactions. When a CRM user asks for "a booking link", they get this page. This spec neither depends on the bookings module nor blocks it; shared UI components (the month picker, the slot list) may be reused at code level.

## 📝 Overview
CRM users schedule meetings with prospects and customers by trading e-mails about availability. The CRM Calendar already shows every scheduled interaction, but external people cannot see when a user is free or book time with them. This spec adds a personal booking link, similar to Calendly or cal.com, that treats the user's CRM calendar as busy time, so bookings do not collide with the user's CRM schedule.

> **Market reference:** **cal.com** (open-source leader) and **Calendly** (commercial canon), plus **Odoo Appointments** and **HubSpot Meetings** (CRM-native).
> **Adopted:** the "first available day" landing, a month picker with day dots plus a vertical slot list, minimum notice, horizon, a buffer after meetings, a daily cap, a "requires confirmation" mode with a request lifecycle, an optional "what is this about" note, one reminder e-mail, a booker manage link (cancel/reschedule), `.ics` with a stable UID and SEQUENCE, and display in the visitor's timezone with a 12/24-hour switch.
> **Rejected for v1:** multiple event types per user (one booking profile per user keeps settings and URL simple; additive later), routing forms, payments, and custom questions (cal.com/Calendly carry heavy builder UIs for these). Also cut to keep the settings small (UX review, 17 Nov 2026): date overrides (a day off is blocked with a CRM event), multiple ranges per day, a start-time interval separate from the meeting length, a buffer before meetings, a configurable response deadline and change cutoff, a per-user cap on new requests (a system setting instead) and bulk accept/decline. Busy time from external calendars belongs to a future integrations provider.

## 📝 Problem Statement
- External parties cannot book time with a CRM user without back-and-forth e-mail.
- Meetings agreed by e-mail are entered by hand and often miss the CRM link to a person, so CRM activity history is incomplete.
- Any booking tool outside the CRM does not see CRM-scheduled interactions, so it double-books.

## 📝 User Stories (story map)

### Epic A — Set up my booking page (CRM user)
- **US-A1** As a CRM user, I want to turn on a public booking page and share its link, so that external people can book me.
  - AC: off by default, with every other value defaulted, so turning it on and saving is enough. The link name defaults to my e-mail's local part (normalised, with a numeric suffix on a collision) and can be changed from the link's menu with live validation (format, taken). The full URL `/calendar/{orgSlug}/{slug}/meetings?id={publicId}` is shown with **Copy** and **Open** (the `id` binds the link to this profile). Enabling without an org slug shows a blocking inline error, and a link whose org slug belongs to another organization is shown as unavailable. Save uses optimistic locking; a conflict shows the conflict bar.
- **US-A2** As a CRM user, I want to set my page title, meeting length and working hours, so that only times I actually work are offered.
  - AC: defaults are "Meet with {first name}", 30 min and Mon–Fri 09:00–17:00 in my browser's timezone. Working hours show as a one-line summary ("Mon to Thu, 09:00 to 17:00") with **Edit**, which opens a dialog with one on/off switch and one range per weekday; an end before the start is rejected inline. The preview card shows the next 5 slots, with an empty state when nothing is bookable; while the page is off it says to turn the page on and save to see the preview.
- **US-A3** As a CRM user, I want sensible limits I rarely have to touch, so that bookings don't overwhelm me.
  - AC: a collapsed **Advanced** section whose closed state summarises the current values. Inside: description, location, the booking window as a sentence with in-place values ("People can book up to [60] days ahead, with at least [2] hours notice"), the buffer after meetings and the daily cap as a sentence ("Keep [10] minutes free after each meeting, and take at most [any] bookings a day"), and, from Phase 3, the booker self-service switch. The bracketed values are examples; the defaults are 60 days, 2 hours, no buffer and no daily limit. An empty daily cap means unlimited.
- **US-A4** As a CRM user, I want to require approval, so that I can vet requests before they reach my calendar.
  - AC: a switch (default on). Requests not answered within 24 hours, or by the meeting start if earlier, expire automatically; the deadline is fixed, not configurable.
- **US-A5** As a CRM user, I want to allow bookers to cancel or reschedule online.
  - AC: a switch in Advanced (default on). Changes close 1 hour before the meeting; the cutoff is fixed. While the switch is off, bookers cannot cancel or reschedule online: the manage page shows the booking read-only and says to reply to the invite e-mail.

### Epic B — Book a meeting (external visitor, not logged in)
- **US-B1** As a visitor, I want to land on the first day with free times, so that I don't have to hunt.
  - AC: that day is preselected, days without slots are disabled, month navigation is limited to the horizon, and the slot length is visible. Available days carry a dot as well as a tint (not colour alone), and today has an outline ring. Times are in my timezone, with a switcher, and in my locale's 12- or 24-hour format, with a 12h / 24h switch next to the timezone. The page renders in my browser language when the app has it, otherwise in the default locale, with a language switch in the footer. With no availability, the empty state reads "No times available in the next N days". An unknown or disabled page shows "This booking page isn't available".
- **US-B2** As a visitor, I want to pick a time from a vertical list, enter e-mail, first name and last name, and say what the meeting is about, so that I can book quickly.
  - AC: the selected slot shows a summary (date, start and end, timezone, and the location only when the owner entered one). E-mail, first name and last name are required, the e-mail format is validated; "What would you like to talk about?" is optional (up to 500 characters). The consent checkbox is **unticked by default** and required. Errors show under each field after submit, the first invalid field gets focus, and a summary is announced through `aria-live`. The keyboard works end to end. Back returns to the slots with the selected day kept.
- **US-B3** As a visitor, I want a clear result.
  - AC: instant booking reads "You're booked" plus "invite on its way to {email}", and, when the meeting is more than 24 hours away, "We'll e-mail you a reminder 24 hours before the meeting". Approval mode reads "Request sent", with the confirm-by time. "Just taken" returns me to the refreshed slots with a banner and keeps what I typed. A rate limit or a network error keeps me on the form with a retry message.
- **US-B4** As a booker, I want to cancel or reschedule from the e-mail link.
  - AC: the page shows the meeting summary with Cancel (confirmation dialog: "Keep meeting" / "Cancel meeting") and Reschedule (the same picker). After the cutoff both are disabled with an explanation. A pending request can be cancelled from the same link. Once a request is cancelled, declined or expired, or its meeting is over, the link shows only "This link has expired".
- **US-B5** As a booker, I want a reminder before the meeting, so that I don't forget it.
  - AC: one e-mail 24 hours before the start, with the meeting summary and (from Phase 3) the manage link. None when the meeting was confirmed less than 24 hours before its start, or was cancelled; a moved meeting gets its reminder for the new time, unless it is moved to less than 24 hours ahead.

### Epic C — Handle requests (CRM user)
- **US-C1** As a CRM user, I want to see pending requests and accept or decline them before they expire.
  - AC: three tabs (Pending, Upcoming, History) and a "Respond by" column. Each pending row shows the visitor's note, so I can decide without opening anything. **Accept is one click**: it creates a new person for a new booker (or keeps the existing person for a reschedule) and sends the invite; only when the slot now overlaps something does a small dialog ask me to confirm, showing the request and what it overlaps. Linking to an existing person is a separate action afterwards (US-C2). Decline takes an optional message to the booker. A request that has already expired shows "This request expired at {time}" and greys out. The empty state for each tab says why it is empty, and a user with no enabled page and no requests sees a "Set up booking page" call to action. On a phone the list becomes cards with full-width Accept and Decline. Users without `customers.booking.manage_own` get no access.
- **US-C2** As a CRM user, I want to link a confirmed booking's auto-created person to an existing CRM person.
  - AC: a picker. On success, the toast confirms the link and offers **Open {auto-created person}**, so the leftover record is one click away; it stays in the CRM, where the owner can delete it like any person.
- **US-C3** As a CRM user, I want pending requests visible in my CRM Calendar.
  - AC: a hatched "Pending: {booker name}" block; clicking it runs the same one-click Accept (with the overlap dialog when needed) or Decline.

### Cross-cutting rules
- All times are stored in UTC, the public page shows times in the visitor's timezone, and the backend shows them in the viewer's browser timezone, as the CRM Calendar does (users have no stored timezone); the settings page's working hours and preview use the profile timezone.
- Dialogs: `Cmd/Ctrl+Enter` submits, `Escape` cancels. Dialog footers carry no keyboard hint text, and pages and cards carry no description line under their titles.
- Values are never joined with a dash or a middot; they go in separate elements or lines.
- One primary action per view.
- No busy details are ever shown publicly, only free starts.

## 📝 Proposed Solution
1. **Booking profile** (`CustomerBookingProfile`): one per user per organization, edited on a new backend profile page **My meeting booking**. It is opt-in and off by default.
2. **Public page:** a chrome-less frontend page in `customers/frontend/calendar/[orgSlug]/[userSlug]/meetings/`. It loads the first day with free slots, a month calendar widget marking days with availability, the slot length, and the vertical list of start times. Picking a slot opens a form (e-mail, first name, last name, and an optional note about the meeting). Submitting goes through the public request route.
3. **Slot engine** (`customers/lib/booking/slots.ts`): a pure function. Inputs are the profile, busy intervals and a date range; the output is the free starts. Busy intervals come from a shared server helper extracted from the existing conflicts route, so both are built on one query helper; the booking mode adds participants, recurring series and all-day items (see Architecture → Busy time).
4. **Booking request** (`CustomerBookingRequest`): holds the booker's details and the lifecycle `pending → confirmed | declined | expired | cancelled`. Every state change runs as a conditional update (`… WHERE id = ? AND status = 'pending' AND expires_at > now()` for accept/decline, and the matching guard for expire and cancel), so exactly one transition wins (see Architecture → State transitions).
   - Without approval, a request is created already `confirmed`.
   - With approval, it is `pending` with `expiresAt = min(createdAt + 24 h, startsAt)` (for a reschedule successor also capped at the original meeting's `starts_at` minus the 60-minute change cutoff, and recomputed whenever the original moves, so a reschedule can never be accepted inside the cutoff or after the original has started, and an unanswered one expires early enough to tell the booker in time that the reschedule did not go through) (the fixed `BOOKING_APPROVAL_DEADLINE_HOURS = 24` in `lib/booking/constants.ts`; not configurable per profile). A pending request blocks its slot. The owner gets a notification and accepts or declines from a backend list. A scheduler job expires overdue requests.
5. **Person linking (no automatic matching):** on confirmation the system always creates a **new** CRM person (`source = 'public_booking'`) from the typed details and attaches the interaction to it. It never matches by e-mail, because a typed e-mail is a claim, not an identity. In the backend, the user can **Link to existing person**: this moves the interaction to the chosen person. The auto-created person is **kept** (Architecture → Link to existing person); the owner can delete it from the CRM like any other person. Accepting a request offers no person choice: it is one click, and linking is always the separate action afterwards. A **reschedule** keeps the booking's existing person and never creates a second one.
6. **E-mails:** each booking event causes a fixed e-mail, sent through the platform's existing delivery (E-mail delivery, below); calendar e-mails carry an `EmailAttachment` holding `text/calendar` content built by a small RFC 5545 builder (`customers/lib/booking/ics.ts`):

   | Booking event (after commit) | Recipient | E-mail | `.ics` |
   |---|---|---|---|
   | `created` with status `pending` (approval on; not for a reschedule successor, whose booker sees "Reschedule requested" on the manage page) | booker | "request received" (manage link from Phase 3) | none |
   | `confirmed` | booker | confirmation + manage link | `METHOD:REQUEST` |
   | `declined` | booker | "declined", with the owner's optional reason; for a reschedule successor, the "reschedule not confirmed" notice | none |
   | `expired` | booker | "expired"; for a reschedule successor, the "reschedule not confirmed" notice | none |
   | `cancelled` of a booking the booker was invited to (by the booker, the owner, a CRM cancel, delete or unscheduling, the person-delete cascade, or undo of accept) | booker | cancellation | `METHOD:CANCEL` |
   | `cancelled` by the booker or by the person-delete cascade | owner | the `customers.booking_request.cancelled` notification (in-app, and e-mail when the owner's preferences allow) | none |
   | `updated` (owner move or retitle) and `rescheduled` (instant reschedule, accepted reschedule) | booker | update | `METHOD:REQUEST`, same `UID`, `SEQUENCE + 1` |
   | none: the maintenance job enqueues it 24 hours before the start (Reminder, below) | booker | reminder (meeting summary; manage link from Phase 3) | none |

   **Manage tokens (Phase 3):** the manage token is **derived and verified, never stored**. The link carries `{manage_chain_id}.{mac}`, where `manage_chain_id` is the id of the first request in the booking's reschedule chain (a successor copies its predecessor's value) and `mac = base64url-without-padding(HMAC-SHA256(CUSTOMERS_BOOKING_TOKEN_SECRET, "customers.booking.manage.v1" ‖ 0x00 ‖ tenant_id ‖ 0x00 ‖ manage_chain_id))` (`lib/booking/tokens.ts`; the version label separates this use of the secret from any other). **Verification:** the route parses the chain id, loads the one request of that chain with `manage_link_holder = true` (unique per chain), re-derives the mac with that row's `tenant_id`, and compares with `crypto.timingSafeEqual` on equal-length buffers; the mac is verified **before** anything is decrypted or returned. An unparsable token, no holder row, or a mismatch all return the same `404` with the code `booking_link_invalid`, which the page renders as one card, "This link isn't valid. Reply to the invite e-mail to change your meeting." (no existence leak). Only the mac is secret: the chain id also appears in the `.ics` UID, and knowing it does not help to forge the mac. The manage `GET` and writes have their own rate-limit buckets, separate from the booking form's: per client IP for every request, and **per chain id only after the mac verifies**, so requests with forged macs can never fill the booker's bucket and lock them out of cancelling; a separate per-chain bucket counts only **failed** verifications and, when full, refuses further failed attempts for that chain without ever refusing a valid mac. Manage-link **cancel** is the one exception to the booking wrapper's fail-closed rule: without a registered or healthy rate limiter it still runs, because the mac is the credential and a missing limiter must never stop a booker from cancelling; manage-link **reschedule** stays fail-closed (`503 booking_unavailable` without a limiter), so a forwarded link cannot be used for unlimited reschedules. The token path segment is redacted from logs. So no token or token hash is stored (a database leak yields no working links), every e-mail rebuilds the same link (no rotation: retried sends and quick successive e-mails never change a link, and an open manage page keeps working), and **rotating `CUSTOMERS_BOOKING_TOKEN_SECRET` revokes every link** while new e-mails get links that work with the new secret. `manage_link_holder` is set when a request is created, pending or confirmed, in every phase (a reschedule successor starts without it and takes it only when accepted), so a booker manages a request with the same link before and after the owner confirms it, and bookings made before Phase 3, or while the secret was unset, get working links as soon as both exist; it moves to an accepted reschedule successor (Architecture → Reschedule) and is cleared on anonymisation. Without the secret, e-mails carry no link and keep Phase 1's "reply to change" copy. The same applies while the profile's self-service switch is off (`allow_booker_cancel = false`): new e-mails carry no link, and links already sent open the manage page read-only. **The secret:** checked with the platform's existing secret policy in `packages/shared/src/lib/auth/jwt.ts` (`isUnsafeJwtSecret`: at least 32 characters, not one of its `PLACEHOLDER_SECRETS`); the trimmed value is the HMAC key; generate it with `openssl rand -base64 32`; it is used for nothing else (never `AUTH_SECRET`, `JWT_SECRET` or a pepper) and is blank in `.env.example`. Modules have no start hook, and app code under `apps/mercato/src/` is off limits, so the check runs in `lib/booking/tokens.ts` the first time a link is built or verified in a process: an **unset** secret means links off (`isUnsafeJwtSecret` treats unset as unsafe, so the code checks for unset first); a secret that is **set but unsafe** also means links off, plus one `reportError` per process (code `customers.booking_token_secret_unsafe`), so an operator sees it without a broken deployment. E-mails then carry the "reply to change" copy and verification returns `booking_link_invalid`. The HMAC key is the configured value with surrounding whitespace trimmed (the policy check sees the same trimmed value). **Once the booking is final** (cancelled, declined, expired) **or its meeting has ended, the link has expired**: the manage `GET` returns `410 booking_link_expired` and the page shows one card with no booking details, so a forwarded or old link exposes nothing. The state is read when the link is opened, so nothing has to clear it, and only a link whose mac verifies gets this answer.

   **E-mail delivery (a black box):** the booking module decides *which* e-mail a committed change causes and *what* it says; delivering it is the platform's job.
   - **Mechanism:** every booking change commits first and then emits its typed booking event (`customers.booking_request.*`, API Contracts → Events) with `persistent: true`, through the same after-commit side-effect path every command uses. The e-mails in the table above are sent through a booking-owned queue, like checkout's e-mail queue but always enqueued, on every queue strategy: one **persistent** subscriber on the booking events (`subscribers/booking-mail.ts`) only enqueues a `customers-booking-mail` job, `{ tenantId, organizationId, requestId, event, icsSequence?, startsAt? }` (`icsSequence` for update e-mails, `startsAt` for reminders), and never throws (an enqueue failure is reported with `reportError` and that e-mail is lost, a delivery failure and out of scope), so it never makes the events worker re-run the event's other subscribers (owner notifications, webhooks, workflow triggers), which run in the same queue job. The mail worker (`workers/booking-mail.ts`) reads the request, runs the content check below, renders the e-mail and hands it to the shared `sendEmail` (`@open-mercato/shared/lib/email/send`); a failure (including a deployment with no outbound e-mail provider) uses the queue's standard retries, and the queue itself reports a job that exhausts them (`queue.job_exhausted`). Owner-facing messages are typed notifications created through the notifications module, whose existing e-mail strategy and per-user channel preferences decide whether they also arrive as e-mail.
   - **Out of scope:** every guarantee about e-mail delivery: whether, when, how many times and in which order an e-mail arrives. Event persistence, queueing, retries, dead-lettering, the mail transport (including its timeouts) and delivery reporting belong to the events, queue, notifications and e-mail packages, and the booking module uses them as they are. It adds no outbox, delivery lease, retry state, delivery record, mail cap or failure notification. A lost, late, duplicated (a retried mail job, or a re-run of the booking event after another subscriber failed, can send again, as any platform e-mail can) or reordered e-mail never changes a booking: the request row is the source of truth, and the manage page and the backend always show it. Calendar clients resolve reordered invitations by the `.ics` `SEQUENCE` (Architecture → Sequence allocation).
   - **Content check at send time (best effort):** the mail job reads the request through the decryption helpers (tenant- and organization-scoped) and sends nothing when the request is anonymised or the e-mail no longer describes the booking:

     | E-mail | Sent only when |
     |---|---|
     | request received | the request is `pending`, has no `previous_request_id`, and `expires_at` is in the future |
     | confirmation | the request is `confirmed` and its meeting has not started |
     | update | the request is `confirmed`, its meeting has not started, and its `ics_sequence` equals the event's `icsSequence` (an older update is dropped once a newer one exists) |
     | cancellation | the request is `cancelled`, it has an `interaction_id` (the booker was invited; `superseded` and `original_cancelled` rows never hold one), and its meeting has not ended |
     | decline, expiry | the request has that status and no `previous_request_id` |
     | reschedule not confirmed | the request is a declined or expired reschedule successor, and its predecessor is still `confirmed` with `starts_at` in the future |
     | reminder | the request is `confirmed`, its meeting has not started, its `starts_at` equals the job's `startsAt`, and it is still eligible for the current move: `reminder_triggered_at` is set and `starts_at_changed_at <= starts_at − 24 h` |

     Every e-mail that describes a confirmed meeting (confirmation, update, reminder, and the original meeting in the "reschedule not confirmed" notice) also requires the **live interaction to agree**: read by the request's (for the "reschedule not confirmed" notice, the predecessor's) `interaction_id` without the `deleted_at IS NULL` filter, it exists, is not deleted or `canceled`, and agrees with that request's snapshot on every field the e-mail shows: the start (`scheduled_at` = `starts_at`), the end (`scheduled_at` + duration = `ends_at`, where a missing `duration_minutes` counts as 30 minutes, as in busy time), and the decrypted title and location (= `title_snapshot`, `location_snapshot`). So no e-mail describes a meeting the owner has just cancelled, deleted, unscheduled, moved or edited (for example a new room or duration with the same start) in the CRM before the sync job caught up; the sync job's own update follows with the new values and a higher `SEQUENCE`. A confirmation skipped this way is normally replaced by that update, which carries the same `METHOD:REQUEST` `.ics` and, from Phase 3, the manage link. If the owner undoes the change before the sync job runs, there is nothing to sync and the booker gets no confirmation e-mail; this is accepted as best effort, as for the reminder (the booking is confirmed, and the success page already offered the `.ics`).

     The e-mail is rendered from the request's current values (time, title, location, `ics_sequence`; the predecessor's current time for the "reschedule not confirmed" notice), never from the event payload. The "reschedule not confirmed" notice reads "Your reschedule request did not go through. Your meeting is on {the meeting's current time}." It never says that the original time stays, because the owner may have moved the meeting after the request was made. One rule covers every case, including a refused accept after a CRM move to another future time: when the mail job runs, the notice is sent with the meeting's current time if the original is upcoming and agrees with the CRM; otherwise it is skipped, and the sync job's own update or cancellation e-mail tells the booker the meeting's state. A change that commits between this read and the send can still produce an outdated e-mail; that is accepted, and the change's own e-mail follows. When decryption leaves a field the e-mail uses still encrypted (the key service is unavailable: the field is in `getEncryptedFieldNames(…, { ignoreRuntimeHealth: true })` and still has the `isEncryptedPayloadShape` form), the mail job throws, so the queue's retries cover a short outage (a few seconds); a longer one loses the e-mail, a delivery failure and out of scope; no ciphertext is ever e-mailed.
   - **Recipients:** booker e-mails go to the request's decrypted `email`, in the booker's locale, with `replyTo` set to the owner's address (read by `owner_user_id` with the customers module's existing `findInteractionUserInScope`; omitted when the owner was deleted or has no address). When the booker cancels, the owner gets the `customers.booking_request.cancelled` notification (API Contracts → Notifications), never an e-mail to the booker's address.

   **Reminder:** one e-mail to the booker 24 hours before the start. The maintenance job triggers it, and it is delivered like every other booking e-mail:
   - **Trigger:** each tick (every 5 minutes) marks due bookings with one conditional statement in its own short transaction, `UPDATE customer_booking_requests SET reminder_triggered_at = now() WHERE status = 'confirmed' AND anonymised_at IS NULL AND reminder_triggered_at IS NULL AND starts_at > now() AND starts_at <= now() + interval '24 hours' AND starts_at_changed_at <= starts_at - interval '24 hours' RETURNING id, tenant_id, organization_id, starts_at`, and after commit enqueues a `customers-booking-mail` job (`event: 'reminder'`, with `startsAt`) for each returned row (one statement over all tenants; each returned row carries its own tenant and organization; an enqueue failure loses that reminder, a delivery failure and out of scope). Overlapping ticks mark a row once. The statement does not set `updated_at`, so it never makes an owner or booker holding the page get a false `409`.
   - A meeting that has already started is never marked (a tick after an outage sends nothing for past meetings), and neither is a booking confirmed or moved less than 24 hours before its start, because the booker was just told the time (`starts_at_changed_at` is set on confirmation and on every move).
   - Every statement that changes `starts_at` (an owner move through the sync job, an instant reschedule) also sets `starts_at_changed_at = now()` and `reminder_triggered_at = NULL`, so a moved meeting is reminded for its new time, unless the move lands less than 24 hours before it; a reminder job for the old time is dropped by the content check. The mark is set before the content check runs, so a reminder dropped for a passing disagreement (for example a CRM cancel undone before the sync job ran) is not sent later; this is accepted as best effort. An accepted reschedule successor is a new row with no mark. A cancelled meeting is no longer `confirmed`, so it is never marked and an earlier event for it sends nothing. The owner gets no reminder from this feature (the CRM calendar already handles that).

   **E-mail safety** (there is no e-mail confirmation step, by decision):
   - booker e-mails and the `.ics` contain **no** booker-supplied text at all: no names or note in the greeting, subject, body, `ATTENDEE CN` or description (the attendee is the e-mail address only). So the form cannot inject content into a mail sent to an arbitrary address. The visitor's note is shown only inside the backend, to the owner;
   - every `.ics` (`REQUEST` and `CANCEL`) carries the `ORGANIZER` that RFC 5546 requires: the owner's e-mail address with the owner's display name as `CN`, or, when the owner was deleted or has no address, the instance sender (`resolveDefaultEmailFromAddress()`) with the profile title as `CN`;
   - owner-facing notifications never store or e-mail the booker's name (API Contracts → Notifications); where the app shows it, it is escaped plain text truncated to 100 characters;
   - `replyTo` is the owner's e-mail, so "reply to change" reaches the owner;
   - **no separate outbound mail cap:** every e-mail to an address the booking page has not mailed before is caused by a new request, which the per-profile creation cap bounds (`CUSTOMERS_BOOKING_MAX_NEW_REQUESTS_PER_DAY`, API Contracts → Abuse controls); every later e-mail goes to the same booker and is caused by an owner action, the maintenance job or the booker's own manage-link action.
   - **Default locale** (used wherever this spec says "default locale"): the platform `defaultLocale` from `@open-mercato/shared/lib/i18n/config`. Users have no stored language, and the tenant's `translations.supported_locales` setting is an unordered list with no default, so the booking module reads neither.
   - booker e-mails use the booker's `locale`: the language the public page was shown in at submit (see UI/UX → Public page → Language), sent in the request body and validated against the app's enabled locales, falling back to `Accept-Language` and then the default locale.

7. **Manage link:** `{chainId}.{mac}`, an HMAC of a server secret and the booking, verified by re-deriving it and never stored (E-mails → Manage tokens). It opens `/calendar/{orgSlug}/{userSlug}/meetings/manage/{token}` with **Cancel** and **Reschedule** (the same slot picker, at `…/manage/{token}/reschedule`). The pages send `Referrer-Policy: no-referrer`, and the token path segment is redacted in request logs. A reschedule under approval mode creates a new `pending` request for the new time, while the old meeting stays confirmed until the decision (see Architecture → Reschedule).

### Alternatives considered
| Alternative | Why rejected |
|---|---|
| Fold into the bookings module §19 | That design is per service and per resource, with pricing and staff pools. This feature is per CRM user over CRM interactions. Coupling them would block a small feature on a large, unimplemented module. |
| New interaction status `pending` instead of a request entity | Changes a contract surface (`interactionStatusValues`, calendar rendering, every filter on status) and still needs somewhere to keep booker PII and expiry. A dedicated request entity is additive. |
| Create the person at request time | Spam requests would litter CRM with persons. Pending requests hold the details on the request row. The person is created only on confirmation. |
| Match the person by e-mail automatically | Lets anyone attach a meeting to a real customer by typing their address (impersonation). This was rejected explicitly in the Q&A. |
| Reuse `planner` availability (weekly/RRULE rules, date-specific rules, timezones) | Planner subjects are staff members and resources, not auth users, so a CRM user without a staff record would have no availability; `planner` is also an optional module, while booking lives in the always-present `customers` module. Booking needs only one weekly-hours list per profile (at most one range per day), kept in one `weekly_hours` jsonb column; there are no date overrides, and days off or breaks are CRM events that block time through busy time. If a later version wants staff-backed availability, an adapter can read planner rules into the same slot engine input. |
| A booking-owned mail outbox with delivery leases, retries, a send ceiling and a daily mail cap | Rejected on 22 Nov 2026: it made the booking module re-implement reliable e-mail delivery, which the platform's persistent events, queue and e-mail transport already own. Booking e-mails use that delivery as a black box, and delivery guarantees are out of scope. |
| User slug unique installation-wide (no org segment) | Answered: add the org slug. A per-organization user slug lets two organizations both have `/…/anna/meetings`. |

### Busy time ("everything that blocks the backend calendar")
Today, `GET /api/customers/interactions/conflicts` defines a blocked interval for a user as follows:
- an interaction with `author_user_id` or `owner_user_id` equal to the user,
- `status` not terminal (`TERMINAL_INTERACTION_STATUS_LIST`),
- `scheduled_at` set and `deleted_at` null,
- covering `[scheduled_at, scheduled_at + coalesce(duration_minutes, 30))`.

- visible to the **caller**: the route applies `applyEmailVisibilityFilter` (the viewer's own id, conversation grants from `listGrantsForViewer` and shared channels from `listSharedChannelIds`) before selecting conflicts. `userId` may name someone other than the caller, so this filter is an access boundary: without it a viewer could probe another user's private scheduled e-mails and read their titles through the route's title lookup.

This spec **extracts** the interval query (the `WHERE` and overlap part only) into `lib/booking/busy.ts` as `findBusyIntervals(em, options)`, where `options` is a discriminated union:

```ts
type FindBusyIntervalsOptions =
  | { mode: 'legacy'; tenantId: string; userId: string | null; from: Date; to: Date;
      organizationIds?: string[]; excludeId?: string; viewer: BusyViewer; limit?: number }
  | { mode: 'calendar'; tenantId: string; userId: string; from: Date; to: Date;
      organizationIds?: string[]; excludeInteractionIds?: string[]; timezone: string }
```

The helper reads **interactions only**, returning `{ id, startsAt, endsAt, interactionType }[]` ordered by `scheduled_at` ascending (`interactionType` feeds the route's `type` field). In `legacy` mode it takes an optional `limit`, which the conflicts route passes as 10 so its SQL stays `ORDER BY scheduled_at LIMIT 10` exactly as today; the route keeps its title lookup and response shape.
- **`mode: 'legacy'`:** exactly today's predicate (author **or** owner, `organizationIds` and `excludeId` honoured) **including the e-mail visibility filter**. `viewer` is **required** in this mode (enforced by the type: `{ mode: 'legacy', viewer: { userId: string | null, sharedConversations, sharedChannelIds } }`), and the helper applies `applyEmailVisibilityFilter` with it **before** the user predicate, the ordering and the limit, exactly where the route applies it today. The route keeps resolving the viewer (`null` for API-key callers) and the grants as it does now and passes them in. The conflicts route switches to it as a pure refactor, so its behavior and access boundary do not change. Parity tests are pinned against the existing conflicts fixtures and add the access cases: another user's private scheduled e-mail is **not** returned (and its title is not leaked), a conversation share and a shared channel make it visible, and an API-key caller (`viewer.userId = null`) sees exactly what it sees today. Two more route behaviors are preserved: with `userId: null` (an API key without a bound user and no `userId` query) the author/owner predicate is **not** applied, exactly like the route's `if (checkUserId)`; and the route keeps its early `{ hasConflicts: false }` return for an empty `organizationIds` list before calling the helper. Both have parity cases. This refactor ships as its own PR (Step 2) before any booking behaviour (Step 1 only adds tables).
- **`mode: 'calendar'`:** used by booking only, server-side. It takes no `viewer`, because it reads the **owner's own** schedule to compute free time, and its result never leaves the booking code as ids or titles: the public API only returns free starts. So the owner's private scheduled e-mails do block availability, which is the intended meaning of "busy". It follows the CRM Calendar's own conflict rule (`lib/calendar/conflicts.ts`: **owner or participant**). It does **not** use `author_user_id`, so meetings an assistant creates for someone else do not consume the assistant's availability. On top of that:
  - **participants:** interactions whose `participants` jsonb contains `{ "userId": <user> }`;
  - **recurring series:** masters selected like the `recurrenceMasters=true` mode (start ≤ `to`, no end before `from`), expanded server-side with the shared `expandOccurrencesWithLimit` (`@open-mercato/core/helpers/calendar/recurrence`), which is generic over its items and expands each in its `raw.timezone`; busy time passes `master.timezone ?? profile.timezone`, so a master without a timezone expands in the profile timezone, and no calendar code changes;
  - **all-day items:** they block the whole day in the profile timezone (`lib/calendar/timezone.ts`, `date-fns-tz`; no new dependency). This is how an owner takes a day off or a lunch break, since profiles have no date overrides and one range per day.
- **Scope:** busy time covers **all organizations of the user within the tenant**, not just the profile's organization. A user with booking pages in two organizations, or with CRM meetings in another one, cannot be double-booked. This is a read of the owner's own records and leaks nothing across tenants.

The booking layer, `lib/booking/availability.ts` (`loadBusyTime(em, profile, range, { excludeInteractionIds?, excludeRequestIds? })`), then builds busy time as the union of:
- the user's `calendar`-mode intervals,
- `CustomerBookingRequest` rows for **any profile of the same user** that are `pending` with `expiresAt > now`, or `confirmed` whose padded end (`ends_at` plus its own profile's `bufferAfter`) is after now (each with its own profile's `padAfter`, below), so the buffer still holds after the meeting itself has ended. Confirmed rows block whatever the state of their interaction, so a meeting marked `done` early (calendar-mode busy skips terminal interactions) or one whose interaction is gone while the sync job has not caught up keeps its slot; a confirmed row and its live interaction cover the same time and count once.

**Buffer:** a profile has one buffer, after meetings (`bufferAfter`). A slot `[s, e)` on a profile is free only when both hold:
- its padded range `[s, e + bufferAfter)` overlaps no busy interval (CRM meetings are not padded);
- the slot itself overlaps no **booking** of the same owner padded with the `bufferAfter` of the profile it was booked on (confirmed requests and pending requests with `expiresAt > now`; `loadBusyTime` returns these intervals with their own `padAfter`, which `computeFreeSlots` applies).

So after every booking there is at least the `bufferAfter` of the profile it was booked on, and before a new booking there is at least the new profile's `bufferAfter` ahead of the next busy item, whatever order they were booked in (the cal.com model, where existing bookings carry their event type's buffer). The slot list and the write gate use this one definition (`lib/booking/slots.ts`), so they cannot disagree.

### Keeping the booking in sync with the interaction
The owner can edit, reschedule, cancel or delete the created interaction from the CRM Calendar like any other. A subscriber on the interaction's existing CRUD/lifecycle events keeps the linked request (looked up via `interaction_id`) in sync:

| Owner action on the interaction | Request becomes | E-mail to booker |
|---|---|---|
| Cancelled (status `canceled`) or deleted | upcoming meetings: `cancelled`, `cancelled_by = owner`; a past meeting is left as it is (it happened) | cancellation, `METHOD:CANCEL` (upcoming only) |
| Unscheduled (the CRM update clears the time: `scheduledAt: null`, or `date: null`, which the existing update contract maps to the same state) | an upcoming booking (its last invited `ends_at` > now): `cancelled`, `cancelled_by = owner`, with the CANCEL built from the request's last invited `starts_at`/`ends_at` and `ics_sequence + 1`; a meeting that has ended is left as it is. The CRM update contract is unchanged | cancellation, `METHOD:CANCEL` (upcoming only) |
| Time or duration changed to a new, non-null time | `confirmed` (a pending reschedule successor's `expires_at` is recomputed from the new start, Architecture → Reschedule), with `starts_at`/`ends_at` updated, `ics_sequence + 1`, and, when `starts_at` moved, `starts_at_changed_at = now()` and `reminder_triggered_at = NULL` in the same statement (Proposed Solution → Reminder) | update, `METHOD:REQUEST`; none when the meeting had already ended before the edit and still has |
| Title or location changed | unchanged except the snapshots | update, `METHOD:REQUEST`, `SEQUENCE + 1`; none for a meeting that has ended |
| The person is deleted (cascade) | upcoming meetings only: `cancelled`, `cancelled_by = person_deleted`; past meetings are left as they are (they happened, and the 90-day anonymisation covers them) | cancellation, `METHOD:CANCEL` |
| Moved to another person | unchanged; `customer_entity_id` follows the interaction | none |
| Completed (status `done`, `customers.interaction.completed`) | unchanged (stays `confirmed`); `done` is the owner's record that the meeting happened | none |
| An interaction edit is undone (undo emits the CRUD `updated` event) | handled by the same snapshot diff as any edit | update if the booker-visible fields changed |

**Only confirmed bookings are synced:** the job ignores requests that are not `confirmed` (cancelled, declined, expired, pending), so it never changes the `ics_sequence` of a cancelled booking. **Ended and anonymised bookings:** the sync job skips **anonymised** rows entirely (`anonymised_at IS NOT NULL`: no snapshot write, no sequence, no e-mail), so the clean-up is never undone. For a meeting that has ended (`ends_at <= now()`, and the new time also in the past) it may update the snapshots but sends nothing and allocates no sequence.

A cancelled request is never re-opened, even if the interaction is later restored through undo. The restored interaction stays a normal CRM meeting; the owner can re-invite the booker manually. This matches the rule that ended requests are final (the slot may already be re-booked).

**Cancelling joins the booking transaction.** `interactions.cancel` currently forks its own EntityManager (`commands/interactions.ts`), unlike `interactions.create`/`update`, so it cannot be atomic with the request update. Step 13 makes it honour `ctx.transactionalEm` and `ctx.transactionLifetime` the same way in `prepare`, `execute` and `captureAfter` (`ctx.transactionalEm ?? fork()`, its effects through the deferral in Architecture → Public request write). Every booking path that cancels a meeting (owner cancel, booker cancel, undo of confirm) cancels the interaction, the request and any pending successor in one transaction.

**Pending reschedule cascade:** whenever a confirmed request is cancelled (by the booker, by the owner, by interaction cancel or delete, or by the person-delete cascade), its pending reschedule successor, if any, is set to `cancelled` (`cancelled_by = 'original_cancelled'`) **in the same transaction**, and no separate e-mail is sent for it. Such a row stays **visible** in the Meeting requests list with the badge "Cancelled: original cancelled".

**Sequence allocation:** a booking's `SEQUENCE` belongs to its `ics_uid` and is allocated, never copied. Every path that causes a `METHOD:REQUEST` or `METHOD:CANCEL` for a UID (the owner-sync job, booker reschedule, accept of a reschedule, every cancel) allocates the number in a transaction holding the same per-owner lock as public writes (`pg_advisory_xact_lock(hash(tenantId, userId))`) and allocates the number there with `UPDATE … SET ics_sequence = ics_sequence + 1 WHERE id = :liveRequestId RETURNING ics_sequence` on the request that currently holds the UID's interaction. The returned value is carried by the path's booking event as `icsSequence`, and the e-mail is rendered with the request's current value (Proposed Solution → E-mail delivery). So owner edits and booking actions on one UID are serialised, each one sends a strictly higher number, and no path sends a value computed earlier (RFC 5546 §2.1.4: a higher SEQUENCE supersedes a lower one).

**Detecting changes:** interaction events carry ids and status only, so the request keeps snapshot columns (`starts_at`, `ends_at`, `title_snapshot`, `location_snapshot`). On each `customers.interaction.updated` (and the other lifecycle events in the table), the subscriber only enqueues a booking-owned job, `customers-booking-interaction-sync`, with `interaction_id` in its payload (the queue does not deduplicate; the job is idempotent because it diffs against the snapshots), and never throws for control flow; an enqueue failure is rethrown, so the events worker re-runs the event (with its other subscribers, accepted for this rare case) rather than losing a state change. The job does the work under the per-owner lock and uses the standard queue retries (so a lock timeout is retried); the queue reports a job that exhausts them. The job loads the interaction and the request through the decryption helpers (tenant and organization scope) and diffs the decrypted values against the snapshots (an interaction with no `duration_minutes` counts as 30 minutes, as in busy time), writing new snapshots back through the encryption service; it emits `customers.booking_request.updated` (which causes the update e-mail) only when something the booker sees has changed.

**Person-delete cascade:** the person-delete command removes interactions with `nativeDelete` and emits no interaction events, so a booking-owned path cancels the bookings instead. It is deliberately simple and never reads audit-log states:
- **Subscriber:** a persistent subscriber on `customers.person.deleted` only enqueues a booking-owned job, `customers-booking-person-delete-cascade`, with `{ tenantId, organizationId, entityId }` (the event's `entityId`; its `id` is the person *profile* id, `commands/people.ts`) and `delayMs` of 2 minutes, roughly the undo-toast window. It never throws for control flow. Only an enqueue failure (rare) is rethrown: the events worker then re-runs the event, including the other `customers.person.deleted` subscribers (`sales`, `customer_accounts`, webhooks, workflow triggers) that share its queue job, which is accepted because a lost job would leave the bookings out of sync.
- **Job:** in one transaction it takes the per-owner lock (`pg_advisory_xact_lock`) of **every** owner with a confirmed request for that person, in ascending lock-key order (no deadlock between two cascades), then re-checks that the person is still deleted (no live `customer_entities` row for `entityId`). If the person exists again (the delete was undone, which is the common case for an undo within the delay), it does nothing. Otherwise it cancels each **upcoming** confirmed request with that `customer_entity_id` (`ends_at > now()`, `anonymised_at IS NULL`, and its interaction no longer exists, so a meeting already moved to another person is never cancelled; past and anonymised rows are never touched or e-mailed, so a GDPR erasure months later sends nothing), with `cancelled_by = 'person_deleted'` and `cancelled_at = now()`, cascades to pending successors (`original_cancelled`), and commits, then emits `customers.booking_request.cancelled` per request, which sends each booker's CANCEL. It uses the queue's standard retries (3 attempts, exponential backoff); the queue reports a job that exhausts them.
- **No backstop:** the subscriber and the job run on the platform's persistent events and queue, whose durability and retries are used as they are. When a job exhausts its retries (the queue reports it), its bookings stay `confirmed` with a dangling `interaction_id`: their e-mails are skipped (the live interaction is gone), their rows still hold the slot and count toward the caps, and the manage page shows the "being updated" state with no actions. From Phase 2 the owner sees such a booking with a "Needs attention" badge in the Upcoming tab (rows carry `syncPending`, read for the page in one batched query of its interactions) and resolves it by cancelling it there, which works when the interaction is already gone (API Contracts → owner cancel); Phase 1 has no Meeting requests page and so no owner remedy, and the booking stays until its meeting ends. The same applies when an interaction-sync job exhausts its retries (Risks).
- **Accepted risk:** an undo that commits while the job's transaction is open (after its re-check) is not blocked; the bookers then have a CANCEL for meetings that were restored. The window is the duration of one short transaction, two minutes after the delete; the cancellations stay final, consistent with "cancelled is final", and the restored meetings stay normal CRM meetings the owner can re-send.
Undoing a person delete restores the interactions silently (no interaction events). The booking requests stay `cancelled` and the bookers have their CANCEL; this is consistent with "cancelled is final". The Meeting requests list shows them as "Cancelled: person deleted", and the owner can book a new meeting manually; undo itself is never blocked.

**No loops:** booking commands run with `ctx.syncOrigin = 'customers.booking'`, which the interaction commands already copy into their event payloads (`commands/interactions.ts`). The subscriber ignores events with that origin. The interaction's `source` column is **not** used as a marker, because it persists and would hide later owner edits.

### Command context for public writes
Public writes follow the checkout public submit route (`checkout/api/pay/[slug]/submit/route.ts`), with one difference:
- `commandBus.execute` gets `auth: null` and `selectedOrganizationId = profile.organizationId`;
- `organizationScope: null`, exactly like checkout. Strict scope mode already accepts `null` together with `selectedOrganizationId` (`shared/lib/commands/scope.ts`);
- `syncOrigin = 'customers.booking'`.

With no auth, `normalizeAuthorUserId` leaves `author_user_id` null; `owner_user_id = profile.userId` is passed as normal input. No new actor fields are introduced: the action log shows the command with no user, and the request row records `source = 'public'`. Backend writes (accept, decline, link, cancel) run as the signed-in user, as usual.

**Undo:**
- **confirm:** undoing it cancels the interaction and sets the request to `cancelled` (`cancelled_by = 'owner'`); its `cancelled` event sends the booker's CANCEL. The undo handler runs with the command bus's `atomicReplay: true`; its `stabilizeReplay` sets `lock_timeout` and takes the per-owner advisory lock (the CANCEL's `SEQUENCE` allocation needs it) before the bus claims the token, so the undo-token claim and the cancellation commit in one transaction (`bindReplayTransactionContext` gives the handler `transactionalEm` and `transactionLifetime`; the `cancelled` event is emitted only when the lifetime completes `committed`, through `onTransactionLifetimeComplete`), and a crash cannot consume the token without cancelling. The bus rejects a second undo of the same token. Undo is refused with `409 meeting_ended` once the meeting has ended, like owner cancel, and with `409 request_state_changed` unless the request is still `confirmed` and still holds the `interaction_id` the accept created (an accepted reschedule has moved it to a successor, or the booking was cancelled). The booker was told about the meeting, so they must be told it is gone;
- **accepting a reschedule:** not undoable (the meeting moved and the booker was e-mailed the new time). The owner can move it back from the calendar, and the sync sends an update;
- **link-person:** undoing it moves the interaction and the reschedule chain's `customer_entity_id` back;
- **decline and cancel:** not undoable, because the booker's state would flip back without a matching e-mail. The owner can still book a new meeting manually.

**Action-log PII:** the command bus stores each command's full input as `commandPayload`, and `people.create` stores a `snapshotAfter` with names. So:
- the booker's e-mail and names are passed through the request row, never through a booking command's input, and every booking command's `captureBefore`/`captureAfter` snapshot is **ids and status only** (request id, status, `interaction_id`, `customer_entity_id`, `starts_at`, `ics_sequence`), so neither the command payload nor the snapshots carry PII;
- **undoable** booking commands (`confirm`, i.e. accept, and `link-person`) keep replay **enabled**: they supply an ids-only `redoInput` (`{ requestId, expectedUpdatedAt }`) and leave `replayable` unset, so the bus still issues an undo token (`CommandLogMetadata.redoInput`; `replayable: false` would clear it);
- **non-undoable** booking commands (public `create` with its inline confirm, which runs with no user to undo it, `decline`, `cancel`, and `reschedule` including accepting a reschedule) use `replayable: false`, which is the intended effect: an audit entry without an undo token or payload;
- the auto-created person's own `people.create` log entry **does** keep the name and e-mail. That is standard CRM behavior for any person record, covered by the CRM's GDPR tooling and not by this feature's anonymisation (see Data Model → Retention).

### State transitions
All transitions live in `lib/booking/transitions.ts` and run as one conditional `UPDATE … SET status = :to, updated_at = now() WHERE id = :id AND status = :from [AND expires_at > now()] RETURNING *` inside the command's transaction:

| Transition | Guard |
|---|---|
| accept, decline | `status = 'pending' AND expires_at > now()`; the API's `expectedUpdatedAt` is checked as well |
| expire | `status = 'pending' AND expires_at <= now()` |
| expire on refused accept (reschedule successor whose original starts within 60 minutes) | `status = 'pending'`; also sets `expires_at = least(expires_at, now())`, with the same fields, event and e-mail as expire |
| cancel by the booker | `status IN ('pending','confirmed')` plus the caller's `expectedUpdatedAt`, and the profile's `allow_booker_cancel`; also cancels a pending successor in the same transaction; a pending request gets no CANCEL e-mail (it was never invited) |
| cancel by the owner | `status = 'confirmed'` and `ends_at > now()`, plus `expectedUpdatedAt`; a pending request is declined instead, so the owner never sends a CANCEL for an invitation that was never sent |
| reschedule (booker) | `status = 'confirmed'` plus the caller's `expectedUpdatedAt`, and the profile's `allow_booker_cancel` |
| accept of a reschedule successor | the above, **plus** the predecessor still `confirmed` (checked under the owner lock) **and** its live interaction still current (Architecture → Reschedule → live-predecessor check); otherwise `409 original_booking_gone` and the successor is cancelled with `cancelled_by = 'original_cancelled'` |

Zero rows updated means the action lost the race: the API returns `409 request_state_changed`, and only the winner's e-mail is sent. For accept and decline, an expired request (status `expired`, or still `pending` with `expires_at <= now()`) returns `409 request_expired` instead: the command checks this on the row it reads under the per-owner lock, **before** the version check below (the expiry job's own update changes `updated_at`, so the version check would otherwise answer with the generic conflict), and again when the conditional update matches no row, so the Meeting requests page can say "This request expired at {time}" rather than show the generic conflict bar. This replaces read-then-compare locking for these rows, so accept and expiry can no longer both commit.

**Optimistic locking on every edit or delete.** The status guard alone would accept a stale `confirmed` row after the owner moved the meeting or changed the person, so every write on a request also carries the version the user viewed:
- every read that feeds an action returns the request's `updatedAt`: the backend list and the public manage `GET`;
- every action sends it back as `expectedUpdatedAt`: accept, decline, link-person, owner cancel, and the public cancel and reschedule;
- the command checks it with `enforceCommandOptimisticLockWithGuards` (`resourceKind: 'customers.booking_request'`) on the request row, read under the per-owner lock, after the expiry check for accept and decline (above) and before the conditional transition;
- **the linked interaction is part of the version.** An ordinary CRM edit (`customers.interactions.update` from the calendar) commits the interaction first; the request row only catches up when the sync job runs, which can be delayed. The request version alone would therefore still look current. So for a confirmed request:
  - reads that feed an action also return `interactionUpdatedAt` (the linked interaction's `updatedAt`), and the manage page shows the time, title and location **from the live interaction** (decrypted), not from the snapshots, so the booker sees an owner's move as soon as it commits. When the live interaction is unscheduled (`scheduled_at IS NULL`), `canceled` or deleted but the sync job has not yet updated the request, the manage page shows the request's snapshot time with "This meeting is being updated by the organiser. Reload later, or reply to the invite e-mail." and offers no actions (`canCancel` and `canReschedule` false), and the Meeting requests list marks the row "Needs attention";
  - actions on a confirmed request (owner cancel, link-person, public cancel and reschedule) send it back as `expectedInteractionUpdatedAt`. Accepting a pending reschedule successor has no interaction of its own to send a version for; it locks and checks the **predecessor's** live interaction instead (Architecture → Reschedule → live-predecessor check);
  - the booking command reads the interaction with `SELECT … FOR UPDATE` in its transaction and requires `updatedAt = expectedInteractionUpdatedAt`, `scheduled_at IS NOT NULL`, `status <> 'canceled'` and `deleted_at IS NULL`; otherwise it returns `409` and changes nothing (owner cancel is the one exception, API Contracts → owner cancel), so a booker can never re-schedule or re-cancel a meeting the owner has just unscheduled, cancelled or deleted in the CRM. The row lock waits for an in-flight CRM write to commit, so the check sees its result. Ordinary interaction commands are unchanged: the interaction row they already update is the shared version boundary, and no extra lock is needed on their side;
  - nested interaction writes then run with `request: null`, so they do not pick up the HTTP request's version header; the check above already pinned the version the user viewed;
- a stale write returns the unified `409` conflict contract. The backend shows the standard conflict bar; the public manage page shows "This booking was changed. Reload to see the latest details" with a **Reload** button.

### Reschedule
- **Busy time for a reschedule excludes the booking being moved:** `findBusyIntervals` in `calendar` mode takes `excludeInteractionIds`; the booking layer (`lib/booking/availability.ts`, which unions the helper's intervals with the request rows) takes `excludeRequestIds`, and the daily cap ignores the request being moved. So the booker's own meeting does not block overlapping new times or use up the cap. The reschedule picker reads its free times from the manage link's own slots route (API Contracts → Public), which applies the same exclusions; the slug-based public slots route cannot, because it does not know which booking is being moved.
- **Instant mode:** under the owner lock, the new `startsAt` is validated as an offered slot (with the exclusions above). The same request row is updated (`starts_at`, `ends_at`, snapshots, `starts_at_changed_at = now()` and `reminder_triggered_at = NULL` in the same statement, and `ics_sequence` allocated as in Architecture → Sequence allocation), the **same interaction** is moved through the interaction update command (with the booking `syncOrigin`), which writes its start and its `duration_minutes` together: the new time is an offered slot, so it has the profile's current meeting length, and `ends_at` is the new start plus that length; when that interaction is `done` (the owner completed it early), the same update also sets `status = 'planned'`, so the rescheduled meeting is open again rather than a completed meeting at a future time; and its `rescheduled` event sends the update `METHOD:REQUEST` with the same UID. The manage token stays the same.
- **Approval mode:** a new `pending` request is created, with `previous_request_id` pointing at the confirmed one, `source = 'reschedule'`, the same `ics_uid` and `customer_entity_id`, `ics_sequence` left at 0 (a placeholder; no number is reserved while pending), and `interaction_id` **null** until accept (so the sync lookup by `interaction_id` always finds exactly one row, the confirmed one). It holds the new slot and the old meeting stays confirmed. The old manage token **remains valid** and its page shows "Reschedule requested for {new time}, waiting for confirmation".
  - **Live-predecessor check (on accept):** the predecessor request's `status` lags an ordinary CRM cancel or delete of its interaction until the queued sync job runs, and the CRM commands do not take the per-owner lock. So, under the per-owner lock and **before** anything else in the acceptance transaction (before either request's status or `interaction_id` changes, the token moves or a sequence is allocated), the command reads the predecessor's interaction by `predecessor.interaction_id` with `SELECT … FOR UPDATE`, **without** the `deleted_at IS NULL` filter. The row lock waits for an in-flight CRM cancel or delete to commit, so the check sees its result. The original counts as **gone** when the predecessor is not `confirmed`, its `interaction_id` is null, the interaction row is missing (person-delete `nativeDelete`), `deleted_at` is set (`customers.interactions.delete`), `status = 'canceled'` (`customers.interactions.cancel`), or `scheduled_at IS NULL` (an ordinary CRM update unscheduled it, even while the sync job is still queued); `done` is not gone (see the sync table); accepting reopens it (see **On accept** below). When the original is gone, the command commits only the successor's cancellation (`cancelled_by = 'original_cancelled'`, `cancelled_at = now()`, no e-mail of its own) and returns `409 original_booking_gone`; it does **not** move, update or revive the interaction, change the predecessor, move the token or send anything. The predecessor is left to the queued sync job (or the person-delete cascade), which cancels it and sends the booker's single CANCEL when it runs; its successor cascade then finds the successor already cancelled and does nothing. This does not depend on the queue having run.
  - **Original within the change cutoff:** the successor's deadline is `min(created_at + 24 h, successor starts_at, original starts_at − 60 min)`. Whenever the sync job moves the original (or an instant change moves it), it recomputes, in the same locked transaction, the pending successor's `expires_at = least(created_at + 24 h, starts_at, <new original starts_at> − 60 min)` with `WHERE status = 'pending' AND expires_at > now()`, so the deadline follows the original in both directions but a successor whose deadline has already passed (expired on read, its slot already released) is never revived. The acceptance also reads the locked live original's `scheduled_at` and, when it is not more than 60 minutes in the future, refuses with `409 request_expired` and expires the successor in its own transaction through the **expire-on-refused-accept** transition (`lib/booking/transitions.ts`: `status = 'pending'` → `expired` with `expires_at = least(expires_at, now())`, setting `decided_at` and `outcome_at` and emitting the `expired` event exactly as the expiry job does; it does not depend on the sync job having recomputed `expires_at` yet), so the slot is released and the alert's "the time was released" is true. The `expired` event causes the "reschedule not confirmed" notice, which gives the meeting's current time and is sent only while the original is still upcoming and its live interaction agrees with the predecessor (Proposed Solution → E-mail delivery → content check); otherwise it is not sent, and the sync job's CANCEL or update tells the booker what changed. An original that was completed early (`done`) but still lies more than 60 minutes in the future is accepted and reopened as before.
  - **On accept** (guarded: the predecessor is still `confirmed` and passes the live-predecessor check above): under the per-owner lock, the sequence is allocated **at acceptance** from the live predecessor (Architecture → Sequence allocation): `predecessor.ics_sequence + 1`, read and incremented in the same locked transaction, then written to the successor, together with `starts_at_changed_at = now()` (a new row with no reminder mark; the predecessor is no longer `confirmed`, so no reminder is sent for it). Owner edits made while the request was pending have already raised the predecessor's number, so the accept e-mail always supersedes them. The existing interaction is moved to the new time, with its start and `duration_minutes` taken from the successor's slot (same UID, the newly allocated SEQUENCE, update e-mail; a `done` interaction is reset to `planned` in the same update, as in instant mode), in the same locked transaction the predecessor's `interaction_id` is **first** set to null and **then** the successor takes it, as two explicit statements (`nativeUpdate` on the predecessor, then on the successor), never a single unit-of-work flush, whose statement order the ORM does not guarantee (the unique partial index on `interaction_id` is checked per statement, so assigning first would fail), so exactly one row ever holds an interaction; the predecessor becomes `cancelled` (`cancelled_by = 'superseded'`, no CANCEL e-mail), and the token is re-pointed: the accept takes its locks in a fixed order, the per-owner advisory lock, then the predecessor's **request** row (`SELECT … FOR UPDATE`), then the predecessor's interaction row (the live-predecessor check), and then moves the link in two explicit statements, first `manage_link_holder = false` on the predecessor and then `true` on the successor (the unique partial index on `(manage_chain_id) where manage_link_holder` is checked per statement, like `interaction_id`). The successor already carries the predecessor's `manage_chain_id`, so the link the booker holds keeps working and now manages the new time. Only one reschedule can be pending per booking (`409 reschedule_pending`).
  - **On decline or expiry:** the new request ends, the booker is e-mailed the "reschedule not confirmed" notice with the meeting's current time, and the old token keeps managing the original meeting.

### Link to existing person
The link command moves the interaction (`entity`) and the reschedule chain's `customer_entity_id` to the chosen person, and **keeps the auto-created person**. Deleting it automatically would have to be guarded against ordinary CRM writes that add dependents (an interaction, comment, deal link and so on) to that person, and those writes do not take the booking's per-owner lock, so a "no dependents, delete it" decision could race a dependent being created and leave a dependent on a soft-deleted person. Keeping it is the simple, safe choice: the auto-created person is a normal CRM record (with `source = 'public_booking'`), and the owner can delete it from the CRM like any person (through the existing person-delete command, which already handles its dependents). The link never calls the person-delete command and never soft-deletes anything. So that the leftover record is not forgotten, the success toast links to the auto-created person; deleting it there goes through the normal person delete and its dependency checks.
- Undo restores the person **this** link displaced: the chain's `customer_entity_id` before the link, captured in the command's ids-only `captureBefore` (the auto-created person for a first link, the previously linked person after a relink). It requires the chain's current `customer_entity_id` to still be the person this link set (otherwise, after a later link or a CRM move of the meeting to another person, undo returns `409 request_state_changed` and changes nothing), then locks the displaced person's row and checks it still exists and is not deleted; when it was deleted meanwhile, undo returns `409 person_gone` ("The previous person was deleted, so this link can't be undone.") and changes nothing.

### Slot computation
For each local day `d` in the range (profile timezone):
1. Take the day's single window from `weeklyHours[weekday(d)]` (none means the day is off; a one-off day off is a CRM event, which blocks through busy time).
2. Walk the window from its start in steps of `slotDurationMinutes` (start times follow the meeting length; there is no separate interval); a slot is the range `[t, t + slotDurationMinutes)`.
3. Drop a slot that falls before `now + minNoticeMinutes`, after `today + horizonDays`, or whose padded range (slot plus the buffer after) overlaps busy time, or that overlaps an owner booking padded with its own profile's buffer (see Busy time).
4. When `maxBookingsPerDay` is reached (confirmed plus pending), drop the whole day.

The first-available scan goes forward in 31-day chunks up to the horizon and returns the **first free instant** (`firstAvailableAt`). The client converts it to the visitor's local date, so the preselected day is right in every timezone. The function is pure and unit-tested with fixed `now`. Timezone math uses `date-fns-tz` and `lib/calendar/timezone.ts`, which are already dependencies.

The same rules are the **write-side gate**, split in two so the API can tell the errors apart: `isOnGrid(profile, startsAt, now)` (working hours, the slot grid, notice and horizon: never offered → `422`) and `isFree(profile, busy, startsAt, { dayCount, excludeRequestIds? })` (busy time with buffers and the `maxBookingsPerDay` daily limit: offered but taken → `409`). `isOfferedSlot` is their conjunction, so `startsAt` is accepted only when it is exactly one of the computed starts.

### Public request write (race safety)
`POST …/requests`. Steps 1–2 run **before** the transaction, so a slow verification hook (for example an external CAPTCHA check) never holds a database connection. The transaction starts at step 3, and its first statement is `SET LOCAL lock_timeout` (`CUSTOMERS_BOOKING_LOCK_TIMEOUT_MS`, default 5 s; a booking-only setting, separate from the pool-wide opt-in `DB_LOCK_TIMEOUT_MS`), so every lock wait inside it is bounded. **Any** lock timeout inside a booking write (SQLSTATE 55P03; the existing `isTransientLockDbError` also matches other transient lock and connection errors, which are mapped the same way; the key row, the owner lock, the interaction `SELECT … FOR UPDATE`, or a row lock in a nested command) returns `503 booking_busy` with `Retry-After` on public routes and `409 request_state_changed` on backend routes:
1. Resolve the profile (it must be active) and require `publicId` to match its `public_id` (otherwise `404`; nothing is recorded). Apply the origin check, the fail-closed rate limiter (`503` without a limiter, `429` over a limit), `runMutationGuards` and the `customers.public-booking.verify-submission` hook.
2. Validate the payload with zod (`400`/`422` on invalid input).
3. **Idempotency:** insert a placeholder key row (`customer_booking_idempotency_keys`, `fingerprint`, `response = null`) with `ON CONFLICT (tenant_id, scope, key) DO NOTHING`. If the row already existed, a request with the same key is either finished or still in flight: the insert waits on the other transaction's row lock until it commits (bounded by the lock timeout; a timeout returns `503 booking_busy` with `Retry-After`), then this request reads the stored row and returns its stored response (same payload) or `422` (different payload); if the other request rolled back, the row is gone and this request proceeds as new. This runs before any availability check, so a retry never sees its own booking as busy.
4. Take `pg_advisory_xact_lock(hash(tenantId, userId))` to serialise writes per **owner**, so two profiles of the same user cannot race. Then re-read the profile by its id inside the transaction: it must still be active with the same `public_id` (otherwise `404`, nothing recorded), and its current settings (approval, meeting length, hours, notice, horizon, buffer, daily limit) are the ones every later step uses, not those read in step 1. The profile `PUT` takes the same per-owner lock before it writes, so a settings change and a booking never interleave. The transaction's `lock_timeout` applies, so a burst against one owner cannot hold pooled connections indefinitely: on timeout the public routes return `503 booking_busy` (retryable, `Retry-After`) and backend routes return `409 request_state_changed`. The shared `withAdvisoryXactLock` helper is **not** used: it runs its body in its own forked transaction and forbids further forks, while the booking write must run inside the `withAtomicFlush` transaction whose lifetime the nested commands join. Every other use of the per-owner lock in this spec (sync job, reschedule, accept) uses the same timeout.
5. **Offered:** `isOnGrid(profile, startsAt, now)` checks working hours, the slot grid, notice and horizon. Off-grid → `422 slot_not_offered`.
6. **Caps:** the daily creation cap (`CUSTOMERS_BOOKING_MAX_NEW_REQUESTS_PER_DAY`), the per-e-mail and per-IP open-request caps, and the owner-wide pending cap. Over any → `429` (`too_many_requests_today` or `too_many_open_requests`).
7. **Free:** load busy time with an overlap query over `[startsAt − 240 min, endsAt + bufferAfter + 240 min]` (240 minutes is the largest allowed buffer, so a padded booking from another profile is seen; the slots read widens its range edges the same way), and the count of bookings on the slot's profile-local day; `isFree(profile, busy, startsAt, { dayCount, excludeRequestIds? })` checks the padded slot against busy intervals and the `maxBookingsPerDay` daily limit, excluding a moved request. Busy or day full → `409 slot_taken`.
8. Insert the request.
9. If approval is off, confirm inline: create the person and the interaction through the existing commands, with `ownerUserId = profile.userId` and the outer `ctx.transactionalEm`. The support must cover **every** phase the command has that reads or writes (`execute` and `captureAfter` for `people.create`, which has no `prepare`): each uses `ctx.transactionalEm ?? fork()`. A fork inside the uncommitted outer transaction cannot see the new rows, so `people.create`'s `captureAfter` (which forks today) would return an empty snapshot; `interactions.create` already does this in `captureAfter`. (`interactions.cancel` is covered under Architecture → Keeping the booking in sync.) `interactions.create` already honours it. `people.create` does **not** today (it forks its own EntityManager), so Step 8 adds `transactionalEm` support to `people.create` as an additive change (the same pattern as `interactions.create`). Without that change there is no single transaction, and a rollback would leave an orphan person.
10. Write the response into the idempotency row without the `ics` (`{ requestId, status, startsAt, endsAt, expiresAt?, selfService }`; a replay of a confirmed booking rebuilds the `ics` from the decrypted request row, so the table holds no PII), in the same transaction, so the key and the booking commit or roll back together.
11. Commit.

**A rejected request leaves no key behind.** Every refusal after step 3 (`409`, `422`, `429`, `503`) rolls the whole transaction back, which also removes the placeholder key row. A retry with the same key is therefore evaluated again from scratch, and only a successful response is ever replayed.

The response precedence is therefore: rate limit and origin, validation, idempotent replay, `422 slot_not_offered`, `429` caps, `409 slot_taken`. Other public writes use the same building blocks:
- **manage-link writes** (`cancel`, `reschedule`) resolve the request by verifying the token and loading the chain's `manage_link_holder` row (Proposed Solution → Manage tokens), not by slug, and run the rate limiter, origin check and `runMutationGuards`, but **not** the `verify-submission` hook (holding the token is the credential; the bot check guards creation). Cancel works whether or not the profile is active and regardless of every cap. The one setting that turns it off is the owner's self-service switch: with `allow_booker_cancel = false`, cancel and reschedule both return `409 self_service_disabled` and the manage `GET` returns `canCancel: false` and `canReschedule: false`. Reschedule needs an active profile: otherwise it returns `409 profile_inactive`, the manage `GET` returns `canReschedule: false`, and the page offers Cancel only; without a registered or healthy rate limiter, `cancel` still runs (the mac is the credential) and `reschedule` returns `503 booking_unavailable`.
- **approval-mode reschedule:** steps 1–4 (with the manage-link exceptions above), then the `cutoff_passed`, `reschedule_pending` and `expectedUpdatedAt`/`expectedInteractionUpdatedAt` checks (`409`), then steps 5–7 with the own-booking exclusions (a reschedule chain counts as **one** open booking: the moved request, and any pending successor whose predecessor is still confirmed, are left out of the per-e-mail and per-IP open-request counts, so a booker at the per-e-mail cap can reschedule each of their bookings), then insert the successor and write the idempotency response;
- **instant reschedule:** steps 1–4 (with the manage-link exceptions), the same `409` checks, steps 5 and 7 with the exclusions (no cap check, no new row), then move the request and the interaction and write the idempotency response;
- **cancel:** steps 1–4 (with the manage-link exceptions), the expired-link check (`410 booking_link_expired`; it runs after the idempotent replay of step 3, so a retried cancel still gets its stored response), the `cutoff_passed` and version checks, then the cancel transition (no slot or cap checks) and the idempotency response.

**Side effects run after commit.** `ctx.bulkImport` is **not** enough here: the bus only passes those flags to its queued CRUD flush (`dataEngine.flushOrmEntityChanges`), while the nested commands also emit directly. `people.create` calls `emitQueryIndexUpsertEvents` (`commands/shared.ts`, which emits `query_index.upsert_one` straight to the event bus), and `interactions.create` emits the parent `customers:customer_entity` index upsert and the `customers.next_interaction.updated` lifecycle event (`emitNextInteractionUpdatedEvent`). Each nested `execute` also flushes the CRUD queue as soon as it returns. All of that would escape before the outer transaction commits.

The framework already owns this boundary: `withAtomicFlush` begins a **transaction lifetime** (`shared/lib/commands/transaction-lifetime.ts`) and completes it with `committed` or `rolled_back` only after the real commit or rollback, and `onTransactionLifetimeComplete(em, cb)` registers work against it. The command bus already runs a nested command inside a caller-owned transaction when the caller passes `transactionalEm` together with the `transactionLifetime` that owns it (**ambient execution**, `packages/shared/src/lib/commands/command-bus.ts`): it gives the command a scoped container whose `em` is the transaction's and whose `dataEngine` is an isolated command-transaction scope, runs the command's whole `runPostCommit()` (after-interceptors, cache invalidation, the CRUD flush) only when the lifetime completes `committed`, and discards its CRUD effects on `rolled_back`. Booking uses this as it is; the bus is not changed (Step 8):
- **Direct emitters:** the nested commands also emit outside `runPostCommit()`: `emitQueryIndexEvents` (upsert and delete paths, `customers/commands/shared.ts`) and `emitLifecycleEvent` (`customers/commands/interactions.ts`, which carries `customers.next_interaction.updated` and the interaction lifecycle events). These two customers helpers register their emit with the existing `onTransactionLifetimeComplete` for `committed` when the command runs on an owned lifetime, and emit immediately otherwise, as today.
- **Commands that fork:** `people.create` and `interactions.cancel` resolve and fork their own EntityManager today, so they still gain `ctx.transactionalEm ?? fork()` in every phase that reads or writes (Steps 8 and 13); ambient execution supplies the transaction's `em` and lifetime in their context.

The booking command opens its transaction with `withAtomicFlush(em, …, { transaction: true })`, reads the token with `getTransactionLifetime(em)`, and passes `transactionalEm`, `transactionLifetime` and the booking `syncOrigin` to the nested `people.create`, `interactions.create`, `interactions.update` and `interactions.cancel`. Then:
- **on commit:** each nested command's complete tail runs exactly once: after-interceptors, cache invalidation, the CRUD flush (person and interaction `created` events and index entries), the person `customers:customer_entity` index upsert, the parent projection upsert, and `customers.next_interaction.updated`;
- **on rollback:** none of it runs, and the container is discarded.

A failing completion callback is already reported through `reportError` by `completeTransactionLifetime` (`shared.transaction_completion_callback_failed`); indexing itself belongs to the platform's indexer.

Booking events are emitted after commit, and e-mails and notifications are sent by their subscribers (Proposed Solution → E-mail delivery), so a mail failure never rolls back a booking. The `Idempotency-Key` header is required on every public write (`requests`, `cancel`, `reschedule`). Keys are stored **only** in `customer_booking_idempotency_keys` (`tenant_id`, `organization_id`, `scope`, `key`, `fingerprint`, `response`, `created_at`; unique `(tenant_id, scope, key)`, where `scope` names the write and its target (`request:{profileId}`, `cancel:{manageChainId}` or `reschedule:{manageChainId}`); purged after 24 h by the maintenance job); the request row carries no idempotency columns. Stored responses hold ids, status and times only (a replay of a confirmed booking rebuilds its `ics` from the request row), so the table holds no PII and needs no encryption entry, even when the purge does not run. The same key and payload returns the stored response; the same key with a different payload returns `422`.

### Public profile resolution and the org slug
`organizations.slug` is unique per `(tenant_id, slug)`, not globally. The booking page resolves the organization **exactly as the customer portal does**, through a shared `resolveOrganizationBySlug(container, { slug, host })` helper that Step 2 extracts from `directory/api/get/organizations/lookup.ts` (which then calls it, with unchanged behaviour): a custom-domain host mapped through the optional `domainMappingService` (resolved from the container the helper receives) fixes the tenant for API calls; booking pages themselves are served on the platform host only, because the app proxy rewrites every page on a mapped custom host to the portal (`apps/mercato/src/proxy.ts`), so `publicUrl` and `linkAvailable` are computed for the platform host; otherwise the lookup is unscoped (the portal's existing, deliberate cross-tenant read), and when several tenants have an organization with that slug, the oldest one (`created_at` ascending) wins. The resolver then finds the active profile with that user slug inside that one organization (link names are unique per organization).

**Stable link identity.** Each profile has a `public_id`: 12 random base62 characters, generated when the profile is first saved, globally unique and never changed. It is not a secret; it only binds a link to one profile. The published link is `/calendar/{orgSlug}/{userSlug}/meetings?id={public_id}` (the settings page's preview, **Copy** and **Open**, `publicUrl`, and `bookingPageUrl` on the manage pages). When the public profile or slots read carries `id`, the profile resolved from the slugs must have that `public_id`; otherwise the answer is the unavailable `404`, so a shared link never opens another profile's page, whatever happens to the slugs. The profile read returns `publicId`, and the booking form always sends it (body `publicId`, required): the write resolves the profile from the slugs and requires the same `public_id` before any input is validated or recorded, otherwise `404` and nothing is written. So a form that was opened before an organization rename or takeover can never deliver the visitor's name, e-mail or note to another profile, organization or tenant. A URL typed without `id` still resolves by the slugs alone, and the page then names the organization before any details are entered.

 So the booking page uses the same rule as the directory lookup route that the portal client calls. A newer organization renamed into an existing slug never takes over an older tenant's booking page. An older organization renamed into a newer one's slug wins the slug, exactly as it would the portal lookup, but published links and open forms carry the profile's `public_id` (below), so only a URL typed without it can reach the older organization's page (Risks).

Enabling a profile is refused with `org_slug_missing` when its organization has no slug. `GET /api/customers/booking-profile` returns `linkAvailable: false` when the organization has no slug or its slug resolves to another organization, and the settings page then shows the "organization link unavailable" error.

**Org slug changes:** the booking link always starts with the organization's slug, which belongs to the directory module; the user slug is the only part the owner configures. When an administrator changes the organization's slug, every booking link of that organization changes with it: old links return 404, manage links keep working because they resolve by token only (UI/UX → Manage page), and the settings page shows the new link. The booking module never intercepts, refuses or watches organization updates, and a redirect from old slugs is out of scope.

### Cross-module boundaries
- Owner identity: `userId` is an FK id to `auth` users, with no ORM relation. The auth `User` has no avatar, active flag or timezone. The public page shows the display name (falling back to the e-mail's local part) and **initials** in the avatar. An owner counts as "active" when the user has `deleted_at IS NULL` and still has access to the profile's organization; otherwise the page returns 404.
- Organization slug: read through `directory` as the portal does.
- E-mail: `@open-mercato/shared/lib/email/send`. Notifications go through the `notifications` module's typed notifications (`customers/notifications.ts`).
- Scheduler: soft-optional, **registered in Phase 1** as one **system-scoped** schedule whose id is `stableScheduleUuid('customers:booking-maintenance')` (that key only seeds the uuid; the schedule's target queue is `customers-booking-maintenance`, because BullMQ rejects `:` in a queue name) (the scheduler's primary key is a uuid; `stableScheduleUuid` is a private helper copied per module, so the customers module copies the one in `cart/lib/scheduling.ts` rather than importing it); the worker iterates over tenants itself. Registration happens in **two** places, because `seedDefaults` runs only when a tenant is created: `setup.ts` `seedDefaults` covers new installs, and a `customers.register-booking-maintenance-schedule` upgrade action (`configs/lib/upgrade-actions.ts`, the same pattern as `cart.register-sweeper-schedules` and `promotions.register-code-reservation-sweep-schedule`) covers existing installs that upgrade into the feature. Upgrade actions run only when an admin triggers them (`POST /api/configs/upgrade-actions`, `configs.manage`, per tenant and organization), so until then the schedule can be missing: the booking settings page and the Meeting requests page show a warning while it is missing.

The pages cannot read the scheduler themselves (employees have no scheduler access), so the server computes `maintenanceSchedule: 'registered' | 'missing' | null` and returns it from `GET /api/customers/booking-profile` and `GET /api/customers/booking-requests/counts`:
- `missing`: no schedule row. Warning: "Booking maintenance is not scheduled: reminders, expiry e-mails and the 90-day data clean-up will not run. Ask an administrator to run the pending upgrade action.";
- `registered`: no warning (the schedule row exists, whatever its state);
- `null`: the scheduler module is absent. Warning: "The scheduler module is not installed: reminders, expiry e-mails and the 90-day data clean-up run only when an administrator runs `mercato customers booking-maintenance`." (expiry itself is still derived on read).

The state comes from the scheduler service's existing `exists(id)`; the scheduler needs no change. A schedule that an administrator disabled or soft-deleted in Scheduler still exists, so it shows no warning: the scheduler owns its schedules' state. Registration omits `isEnabled` and does not clear `deletedAt`, so re-running the upgrade action never overrides an administrator's choice.

The upgrade action declares `requiredModules: ['scheduler']`, so it is hidden on installs without the scheduler. Like the cart and promotions actions, it declares its `version` and the i18n `messageKey`/`ctaKey`/`successKey`/`loadingKey`. Both are idempotent on the stable id. The upgrade action is listed in UPGRADE_NOTES. When `schedulerService` is not registered, expiry still works at read time (pending blocks only while `expiresAt > now`, and lists show `expired` from the derived state); the job only makes the status change and the "expired" e-mail happen. Anonymisation then needs the CLI to be run by hand.

Indexes:
- `(profile_id, status, starts_at)`: busy lookup and daily cap.
- `(organization_id, owner_user_id, status, created_at)`: backend list.
- `(status, expires_at) where status = 'pending'`: expiry job.
- **unique** `(interaction_id) where interaction_id is not null`: enforces that one request holds an interaction, and serves the sync job's lookup on every `customers.interaction.updated`.
- `(tenant_id, owner_user_id, status, starts_at)`: per-owner busy time and caps across all profiles and organizations.
- `(owner_user_id, email_hash) where email_hash is not null`: the per-e-mail cap.
- `(organization_id, email_hash) where email_hash is not null`: org-wide exact e-mail search for `customers.booking.manage` holders.
- `(customer_entity_id)`: the cascade job's lookup.
- `(profile_id, created_at)`: the daily creation cap (`CUSTOMERS_BOOKING_MAX_NEW_REQUESTS_PER_DAY`), counted under the per-owner lock on each write that inserts a request row.
- `(owner_user_id, client_ip_hash) where client_ip_hash is not null`: the per-IP open-request cap.
- **unique** `(manage_chain_id) where manage_link_holder`: one link holder per chain, and the manage-link lookup; global, not tenant-prefixed, because the token carries only the chain id (the tenant comes from the row and is bound by the mac).
- `(starts_at) where status = 'confirmed' and anonymised_at is null and reminder_triggered_at is null`: the reminder trigger's scan of confirmed meetings starting in the next 24 hours.

**Encryption map** (`customers/encryption.ts`, added to `defaultEncryptionMaps`):

```ts
{
  entityId: 'customers:customer_booking_request',
  fields: [
    { field: 'email', hashField: 'email_hash' },
    { field: 'first_name' },
    { field: 'last_name' },
    { field: 'decline_reason' },
    { field: 'booker_message' },
    { field: 'title_snapshot' },
    { field: 'location_snapshot' },
  ],
},
```

**Provisioning:** tenant encryption maps are seeded only at tenant creation, so a new map entry never reaches existing tenants by itself, and without a persisted rule `encryptEntityPayload` would write the first booking in plaintext with `email_hash` empty. So:
- **new tenants and organizations** get the entry through the existing seeding at tenant creation;
- **existing tenants** get it from a forward-only, idempotent customers migration that runs `buildEncryptionMapBackfillSql(bookingRequestEncryptionMap)` (`shared/lib/encryption/migration-backfill.ts`), with an empty `down()` as the helper requires. It inserts the entry for every (tenant, organization) scope with active maps that lacks it, and appends missing field rules to existing rows. Scopes with encryption disabled are skipped. The migration ships in Step 1, the same release as the tables, so the map is in place before public writes exist (Step 8);
- **operator recovery only:** `yarn mercato entities seed-encryption --tenant <uuid> [--org <uuid>]` re-seeds one scope. It is not part of the upgrade path.

**Foreign keys:** only `profile_id` is a real database FK. `interaction_id`, `customer_entity_id` and `previous_request_id` are plain uuid columns, the FK-id-plus-snapshot pattern used for cross-aggregate links. The existing person-delete command hard-deletes the person and its interactions with `nativeDelete`, and every FK option would break something: `NO ACTION` makes person delete fail (a behavior change on an existing command), `SET NULL` erases the `customer_entity_id` the `customers.person.deleted` subscriber matches on (bookers never get their CANCEL), and `CASCADE` deletes the requests before the subscriber runs. Readers treat a dangling id as "gone".

Plus a small table, `customer_booking_idempotency_keys`, for public-write idempotency (see Architecture → Public request write).

**Retention and PII placement:** booker PII is kept out of every place the module does not control:
- **titles:** created interactions are titled with the profile title ("Meet with Anna"), never the booker's name; the booker is visible through the linked person;
- **events and notifications:** event payloads carry ids, `status`, `icsSequence` and `cancelledBy` only; notification texts say "New meeting request for {date time}" and resolve the name only when rendered for an authorised viewer;
- **audit log:** the platform action log stores command payloads and snapshots. Booking commands therefore use ids-only inputs (a redacted `redoInput` where undo is kept, `replayable: false` where it is not) and ids-only snapshots (Architecture → Command context), so their log entries never hold the e-mail or names. The auto-created person's own creation entry does hold them (standard CRM behavior).

Declined, expired and cancelled requests, and confirmed requests whose meeting ended, are anonymised 90 days later by the maintenance job (Phase 1):
- e-mail and names are replaced with a fixed marker (written through the encryption service like any other value), and `booker_message`, `decline_reason`, `title_snapshot` and `location_snapshot` are cleared;
- `email_hash` and `client_ip_hash` are cleared, `manage_link_holder` is set to false (so every link to the booking stops working), and `anonymised_at` is set.

**Not covered:** the person auto-created on confirmation is a normal CRM record and follows the CRM's retention and GDPR tooling, not this job.

Without the scheduler, the job can be run by hand with the CLI command `mercato customers booking-maintenance`. Confirmed requests whose meeting ended more than 90 days ago are anonymised the same way, because the person record holds the CRM copy. Interactions and persons follow the CRM's normal retention.

## 📝 API Contracts
Every handler exports `openApi`. Public routes declare `requireAuth: false`; all public writes go through commands.

### Public (no auth)
**Abuse controls** on the write routes (`requests`, `cancel`, `reschedule`):
- **Client IP:** resolved with the platform's `getClientIp`, which needs `RATE_LIMIT_TRUST_PROXY_DEPTH` set to the number of proxies in front of the app (it defaults to 0). Booking setup documents that this is **required** behind a proxy or load balancer. When the IP cannot be resolved, every **per-IP** limit below is **skipped**, never applied to a shared bucket, so visitors are never pooled into one lockout. The per-profile and per-e-mail limits still apply.
- **Rate limit** per resolved IP and per profile for the booking form and slot reads, through a module-local wrapper over the platform rate limiter; manage-link reads and writes use their own buckets (per IP, and per chain id after the mac verifies; Proposed Solution → Manage tokens), so booking-form spam on a profile never blocks a booker's cancel. Unlike checkout's wrapper, which lets requests through when the limiter is not registered, the booking wrapper is **fail-closed on writes**: with no rate limiter registered, public `POST`s return `503 booking_unavailable`, except the manage-link `cancel`, which still runs; reads stay available.
- **IP-independent creation cap:** checked **only** on writes that insert a request row: `POST …/requests` and an approval-mode reschedule (which creates a successor). Cancel and instant reschedule are never refused by it, so a booker can always cancel even when an attacker has exhausted the owner's quota. At most `CUSTOMERS_BOOKING_MAX_NEW_REQUESTS_PER_DAY` new requests per profile in any rolling 24 h (default 20, allowed 1–200; a system setting, not a per-user one, so abuse protection is an operator decision), counted on `created_at` under the per-owner lock, over every row created in the window whatever its status, so a book-then-cancel loop through the manage link cannot get around it. This is the bound that holds in the **default deployment**: `RATE_LIMIT_TRUST_PROXY_DEPTH` defaults to 0, so `getClientIp` returns `null` and every per-IP control below is skipped. Without it, a script rotating e-mail addresses could fill the whole horizon in instant mode, where nothing is pending. Over the cap: `429 too_many_requests_today`, and the owner is notified once per day (`customers.booking_request.cap_reached` with `cap: 'creation'`). The trade-off is that an attacker can exhaust one owner's daily quota, but cannot fill the calendar or create unbounded persons and e-mails. Per-IP protection being off (no trusted proxy depth configured) is an operator concern: the deployment documentation states it, and the booking module logs one `warn` per process the first time it handles a public write without it (modules have no start hook); the user's settings page does not show it.
- **Outstanding-request caps:**
  - at most 2 open (pending or future confirmed) requests per `email_hash` per owner; a reschedule chain (a confirmed request and its pending successor) counts once;
  - at most 3 open requests per `client_ip_hash` per owner (skipped when the IP is unknown);
  - the owner-wide pending cap `maxBookingsPerDay == null ? 10 : max(10, 2 × maxBookingsPerDay)` (10 when meetings per day are unlimited) counts at most 3 requests per `client_ip_hash`, and requests with an unknown IP count individually. So one resolved source cannot fill it, and unresolved traffic is still bounded by the cap itself.

  Over a cap, the route returns `429 too_many_open_requests`. The owner is notified when the owner-wide cap is hit (`cap_reached` with `cap: 'pending'`), so they can review the pending list.

  A `429` rolls back the booking transaction, so the route creates `cap_reached` (creation and pending) **after the rollback**, outside that transaction; its `groupKey` with `skipExistingGroup` keeps it to one per cap per day.
- **Bot check:** a server-side verification hook, `customers.public-booking.verify-submission` (DI-overridable, default no-op), plus the client form extension point `customers.public-booking.form`, where the matching CAPTCHA widget renders. A CAPTCHA provider plugs into both in v1 without code changes here.
- **Origin check** against `CUSTOMERS_BOOKING_ALLOWED_ORIGINS`, falling back to `APP_URL`/`NEXT_PUBLIC_APP_URL`. This is CSRF hygiene only, not abuse protection, and is applied on POST only.

### ACL (`acl.ts`, additive)
- `customers.booking.manage_own`: **no** dependency on `customers.interactions.manage`. It authorises only the caller's own booking profile and the requests and meetings that profile created. It is added to `defaultRoleFeatures` for `admin` (already covered by `customers.*`) and `employee`. The `employee` role does **not** gain `customers.interactions.manage`, so the existing grant boundary is unchanged.
- **Owner scope is enforced in the booking commands**, not by the feature alone: every backend booking command loads the request under the per-owner lock and requires `request.owner_user_id = auth.sub`, unless the caller has `customers.booking.manage` (then organization scope applies). Otherwise it returns 404, the same as an unknown id. The nested interaction commands are invoked only on the request's own `interaction_id`, so a booking action can never reach another interaction.
- **Effect for owners without `interactions.manage`:** they handle booking meetings through the booking actions (accept, decline, link person, cancel, from the Meeting requests page or a pending block in the calendar). Editing a booking meeting directly in the CRM Calendar still needs `customers.interactions.manage`, exactly as for any other interaction; when an owner who has it edits the meeting there, the sync job informs the booker.
- `customers.booking.manage`: `admin` only (via `customers.*`).

Existing tenants pick these up with `yarn mercato auth sync-role-acls`, which is noted in UPGRADE_NOTES.

### Events (`events.ts`, additive)
Booking lifecycle events are emitted after commit with `persistent: true`. Their payloads carry ids plus `status`, `icsSequence` and `cancelledBy` (null unless cancelled) (no PII); they drive the booking e-mails (Proposed Solution → E-mail delivery) and serve notification, webhook and workflow consumers. `events.ts` declares a `payloadSchema` for them, as the existing customers events do (for example `dealClosurePayloadSchema`); that schema is descriptive metadata (workflow editor, events API), so each step that emits a booking event asserts the **emitted** payload in its tests: Step 8 (`created`, `confirmed`), Step 11 (`updated`, and `cancelled` from the sync job and the person-delete cascade), Step 13 (`confirmed`, `declined`, `cancelled`), Step 14 (`expired`), Step 16 (`person_linked`), Step 18 (`cancelled` by the booker) and Step 19 (`rescheduled`, `cancelled` with `superseded`).
`customers.booking_request.created`, `.confirmed`, `.declined`, `.expired`, `.cancelled`, `.rescheduled`, `.updated` (an owner change of the time, duration, title or location applied by the sync job), `.person_linked`. Accepting a reschedule successor emits only `rescheduled` for the successor and `cancelled` (`cancelledBy = 'superseded'`) for the predecessor, never `confirmed`; an instant reschedule emits only `rescheduled`. A successor cancelled together with its original emits its own `cancelled` with `cancelledBy = 'original_cancelled'`, and no e-mail follows it (Proposed Solution → E-mail delivery). Payload: ids plus `status`, `icsSequence` and `cancelledBy` (no PII).

### Notifications (additive)
To the owner:
- `customers.booking_request.pending`, with an **Open request** `href` action to the Meeting requests page, which opens the Pending tab with the row highlighted (`?tab=pending&highlight={requestId}`; Step 13 ships the notification as text only, and Step 15 adds the action when that page exists). It has no inline Accept/Decline: notification `commandId` actions send only `{ id, …payload }` and cannot carry `expectedUpdatedAt`, and an accept may need the overlap dialog,
- `customers.booking_request.confirmed` (instant booking only; the subscriber skips it when `decided_by_user_id` is set, because the owner accepted it),
- `customers.booking_request.cancelled` (when the booker cancels, or the person-delete cascade cancels the booking, with a text per `cancelledBy`), with an **Open request** `href` action to the Meeting requests page, which opens the History tab with the row highlighted (`?tab=history&highlight={requestId}`; the action is added in Step 15, when that page exists, and in Phase 1 the notification is text only),
- `customers.booking_request.cap_reached`, with a `cap` field (`creation` | `pending`) and one text per value: the daily creation cap was hit, or the owner-wide pending cap was hit; at most one per cap per day (below).

Every owner notification is created with `notificationService.createBatch(…, { skipExistingGroup: true })` and a `groupKey`: `{requestId}` for `pending`, `confirmed` and `cancelled`, and `{profileId}:{cap}:{local date in the profile timezone}` for `cap_reached`. That option skips the notification when one with the same type and key already exists in any status, including a dismissed one, so a retried subscriber or a repeated refusal never notifies twice. The notifications subscriber skips an owner who was deleted or is no longer in the organization's scope (checked before `createBatch`, which would otherwise throw) and never throws for that case, so a missing owner never makes the events worker re-run the event. The booking notification types declare no `channels` restriction and are not `nonOptOut`, so the owner's preferences decide in-app and e-mail delivery (both default on; e-mail also needs the deployment's notification e-mail delivery, `NOTIFICATIONS_EMAIL_ENABLED`, on by default); the e-mail links to the notification in the panel, and the `href` action is the in-app click target.

Notification texts carry the date and time only; they never store or e-mail the booker's name, which is resolved only when an authorised viewer opens them in the app.

## 📝 UI/UX

### Public page `/calendar/{orgSlug}/{userSlug}/meetings`
Chrome-less: no backend menus, headers or portal nav. It uses the same `@open-mercato/ui` primitives and DS tokens as backend pages (Card, Button, Input, Calendar/day-picker, Badge, Spinner).
- **Header card:** owner initials avatar, owner name and organization name on two separate lines, title, description, a clock icon with "{n} min", the location **only when the owner entered one** (no video link is promised or generated), and the confirmation mode ("Instant confirmation", or, when approval is on, "{first name} confirms within 24 hours").
- **Layout:** three columns: header card, then the month calendar, then the slot list.
- **Calendar and slots:** in the month calendar, available days carry a tint **and a dot** (availability never depends on colour alone), unavailable days are disabled, and today has an outline ring with `aria-current="date"`; days of the adjacent months fill the first and last rows. A legend under the grid explains the dot and the ring. Prev/next month is limited to the horizon. The slot column shows the selected day's heading, then the slots stacked vertically as full-width buttons. Below the `lg` breakpoint (1024px) the columns stack (mobile-first).
- **Timezone and time format:** under the calendar, a timezone switcher (default: the browser timezone) and a **12h / 24h** segmented switch. The format defaults to the visitor's locale (`Intl.DateTimeFormat(locale, { hour: 'numeric' }).resolvedOptions().hourCycle`: 24-hour for `en-GB`, `pl`, `de`; 12-hour for `en-US`) and the choice is remembered in the browser. It applies to the slot list, the summaries and the result card.
- **Language:** the page renders in the visitor's browser language (`Accept-Language`, matched against the app's enabled locales) and otherwise in the default locale (Proposed Solution → E-mail safety). The footer, next to "Powered by Open Mercato", has a language select; changing it re-renders the page and sets a locale cookie. The language in use at submit is sent as `locale` and becomes the booker's e-mail language.
- **Initial state:** the day selected is the visitor-local date of `firstAvailableAt`. With no availability at all, the slot column shows an empty state, "No times available in the next {horizon} days" with "{first name}'s calendar is full. Check back later." underneath, and every day is disabled (navigation still works).
- **Unavailable page:** an unknown slug, a disabled profile, an inactive owner and a link whose org slug resolves to another organization all render the same 404 card, "This booking page isn't available. The link may be mistyped, or the page was turned off. Ask the person who sent it for a new link.", with no owner details.
- **Slot picked:** the card switches to a details step. The left column keeps the header with the chosen date, start and end time, timezone and location (when set), plus a **Back** button. The right column holds the form: e-mail, first name, last name, an optional "What would you like to talk about?" textarea (≤ 500 characters; from Phase 2, when the owner can read it), the consent checkbox (**unticked by default**; privacy text from `content`), and **Book meeting** (or **Request meeting** when approval is on). Back returns to the slots with the selected day kept.
- **Result:** a centred card showing one of two outcomes:
  - **confirmed:** "You're booked", the invite e-mail address, a meeting summary, an **Add to calendar (.ics)** download built from the `ics` field of the response, the reminder line "We'll e-mail you a reminder 24 hours before the meeting" (only when the meeting is more than 24 hours away), and the change hint: "To change it, use the link in your e-mail" when the response's `selfService` is true, otherwise "Need to change it? Reply to the invite e-mail" (the reply goes to the owner);
  - **pending:** "Request sent", "{name} will confirm by {expiresAt}. We'll e-mail {email} either way.", an "Awaiting confirmation" badge, a note that the time is held until then and released if not confirmed, and, when the response's `selfService` is true, "You can cancel the request with the link in your e-mail".
- **Errors:**
  - **validation:** after the first submit, each invalid field shows its error underneath ("Enter a full e-mail address, like name@example.com", "Enter your last name", "Tick the box to send your request"), the first invalid field gets focus, and a summary is announced through `aria-live`; errors clear as fields are fixed;
  - **`409 slot_taken` and `422 slot_not_offered`:** back to the slot list with a warning banner, "That time was just taken. Pick another time. Your details are kept.", and refreshed slots;
  - **`429`:** an error alert above the submit button, "Too many requests right now. Try again in a few minutes.";
  - **`404`** (the page was turned off, or its link changed, while the form was open): the unavailable card;
  - **network or `5xx`:** "Your request wasn't sent. Check your connection and try again."
- **Accessibility:** the calendar has full keyboard navigation (arrow keys and Enter), each slot list is a `role="listbox"` per day, labels are tied to inputs, invalid fields carry `aria-invalid` and `aria-describedby`, and form errors are announced through `aria-live`.

- **Narrow screens:** below the `sm` breakpoint (640px) the `DataTable` renders a card list. Each card shows the meeting date and time, the Respond by badge, the booker's name and e-mail and the note (the line is left out when there is none), with full-width **Decline** and **Accept** buttons; sorting moves into a single control above the list, and dialogs become bottom sheets. Dialogs: `Cmd/Ctrl+Enter` submits, `Escape` cancels; footers carry no keyboard hint text. The CRM Calendar shows pending requests for the current user as hatched "Pending: {booker name}" blocks. An enricher cannot add rows, so none is used. Pending blocks show only the signed-in user's own requests, also for holders of `customers.booking.manage`, who handle colleagues' requests on the Meeting requests page. ## 📝 Edge Cases & Failure Scenarios
| Scenario | Behavior |
|---|---|
| Two visitors submit the same slot at the same time | The per-owner advisory lock plus the offered-slot recheck: the first gets 201, the second gets 409 `slot_taken` and the UI refreshes slots |
| The owner adds a CRM meeting over a pending request's time | Allowed (the backend calendar shows the conflict badge). Accepting later asks for confirmation ("Overlaps {title}, {time}") and may proceed |
| The approval deadline passes | Read paths treat the request as expired immediately. The job sets `expired` within one 5-minute tick, and its event causes the expiry e-mail; without the scheduler, status is derived on read |
| The deadline is after the slot start | `expiresAt` is capped at `startsAt` |
| The profile is disabled or the slug changed while a booking flow is open | Submit returns 404 and the page shows the unavailable card (UI/UX → Public page). Existing bookings and manage links keep working (keyed by token, not slug); on a disabled profile the manage page offers Cancel only |
| The owner is deleted or loses access to the organization | Profile resolution requires `deleted_at IS NULL` and organization access; the public page returns 404. Pending requests expire normally |
| A crafted request for a time that was never offered (03:17, a weekend, inside notice, past the horizon, off-grid) | `422 slot_not_offered`; nothing is written |
| Accept and expiry (or two accepts) at the same moment | The conditional update lets exactly one win; the loser gets `409 request_state_changed`, and only the winner's event (and so its e-mail) is emitted |
| The person is deleted while bookings point at it | The `customers.person.deleted` subscriber enqueues the delayed cascade job, which cancels the upcoming confirmed requests and then emits the cancellations that send the bookers' CANCEL e-mails, unless the delete was undone first |
| E-mail send fails | The booking stays committed. Delivery, retries and failure reporting belong to the platform and are out of scope (Proposed Solution → E-mail delivery); the manage page and the backend always show the booking's real state |
| A DST transition on a slot day | Slots are generated in the profile timezone over wall-clock windows; a non-existent local time is skipped and an ambiguous one takes the first occurrence. Unit-tested for Europe/Warsaw and America/New_York |
| Visitor and profile timezones differ by a date line | The calendar widget marks days by the **visitor's** local date of each slot. The slots API returns instants, and the client groups them |
| The booker cancels after the cutoff | 409 `cutoff_passed`; the page says "reply to the invite e-mail" (the reply goes to the owner) |
| A manage token after a reschedule | Instant mode: the same token. Approval mode: the old token stays valid while the new request is pending, moves to the new request on accept, and keeps managing the original meeting on decline or expiry |
| A reschedule under approval | See Architecture → Reschedule: the existing interaction is moved on accept (same UID, higher SEQUENCE, no CANCEL), and the original stays on decline or expiry |
| A second reschedule while one is pending | `409 reschedule_pending` |
| The owner needs a day off or a lunch break | No date overrides or second ranges: the owner adds a CRM event (all-day for a day off), which blocks those times through busy time |
| The owner keeps meetings in Google or Outlook | Not checked (no external calendar sync); the settings page says so. Bookings can collide with those meetings unless the owner mirrors them as CRM events or narrows working hours |
| The visitor's note contains markup, links or a very long text | Stored as plain text (≤ 500 characters, trimmed), rendered escaped and clamped to two lines in the list; never sent in any e-mail, notification or `.ics` |
| A meeting is moved after its reminder was triggered | The move sets `starts_at_changed_at` and clears `reminder_triggered_at`, and a pending reminder job for the old time is dropped by the content check, so the booker gets a reminder for the new time (none if the move lands less than 24 hours before the new start) |
| The owner clicks Accept on a request that expired a minute ago | `409 request_expired`; the page explains that the request expired and the time was released, and the row greys out |
| The owner cancels or deletes the original meeting in the CRM Calendar, then accepts its pending reschedule before the sync job has run | The acceptance locks and reads the live predecessor interaction, sees it `canceled` or deleted, cancels the successor (`original_cancelled`) and returns `409 original_booking_gone`; nothing is moved or sent. The sync job later cancels the original, and the booker gets one CANCEL. |
| Link to a person that belongs to another organization | 404 (scoped lookup) |
| An abusive volume of requests | The IP-independent daily creation cap (`CUSTOMERS_BOOKING_MAX_NEW_REQUESTS_PER_DAY`, holds in every deployment), the fail-closed write rate limiter, and idempotency; per-IP limits apply only when a trusted proxy depth is set. Pending requests also count toward `maxBookingsPerDay`. A CAPTCHA plugs in through the form extension point `customers.public-booking.form` plus the `customers.public-booking.verify-submission` hook |
| Organization slug collision across tenants | Resolved as the customer portal resolves it: a custom domain fixes the tenant, otherwise the oldest organization with the slug wins. The other organization's published links carry its profile's `public_id`, so they return 404 instead of opening the winning organization's page, and a form already open on its page is refused with 404 before anything is recorded; only a URL typed without `id` can open the winning organization's page, which names that organization. The other organization's settings page shows "organization link unavailable" until its slug changes |
| Mass bookings with rotating e-mails from one source | First the per-profile daily creation cap (`CUSTOMERS_BOOKING_MAX_NEW_REQUESTS_PER_DAY`; every created row counts, so book-and-cancel loops are bounded too, and so are e-mails to new addresses); the owner is notified at the cap. The per-IP open-request cap, per-IP rate limit and IP weighting of the owner-wide cap add to this only when `RATE_LIMIT_TRUST_PROXY_DEPTH` is set |

## 📝 Risks & Impact Review
| Risk | Severity | Area | Mitigation | Residual |
|---|---|---|---|---|
| A public endpoint leaks a user's schedule | Medium | privacy | Slots expose only free starts, never busy titles or reasons; opt-in; 404s are uniform | Free/busy shape is inferable by design (same as Calendly) |
| Spam bookings fill a user's calendar | Medium | abuse | Rate limits, approval mode, daily cap, manage-token cancel, decline from the list | No CAPTCHA in v1 |
| A person record created from an e-mail address that is not the booker's | Medium | data quality, privacy | No e-mail confirmation and no CAPTCHA, by **conscious product decision** (acknowledged in the UX review of 17 Nov 2026): approval mode (on by default) creates the person only when the owner accepts; instant mode is bounded by the creation and open-request caps; the person is marked `source = 'public_booking'` and shown as "New from booking" so the owner can check or link it | Someone can still put another person's address into an owner's CRM; the CAPTCHA extension point and an e-mail confirmation step remain possible later |
| Double bookings with meetings kept outside the CRM | Medium | product | The settings page states that only the Open Mercato calendar blocks times; the owner can mirror outside meetings as CRM events or narrow working hours; approval mode lets the owner catch a clash before accepting | Until a calendar integration syncs external events into the CRM |
| Extracting the busy predicate changes conflict-route behavior or its access boundary | Medium | customers API, privacy | Pure refactor; `legacy` mode requires the viewer and applies the e-mail visibility filter before selection; existing conflicts tests stay green; parity tests including private e-mail, conversation share, shared channel and API-key caller | Low |
| PII in booking requests | Medium | GDPR | Encrypted columns, `findWithDecryption`, 90-day anonymisation; no PII in events, notifications, interaction titles or action-log payloads | The auto-created person follows CRM retention, not this job |
| The public form used as a mail relay | Medium | abuse | No booker free text in mails (the visitor's note never leaves the backend); no booker names in any e-mail; the creation cap bounds e-mails to new addresses; per-IP and per-e-mail caps | No e-mail confirmation by product decision |
| A booking action reaching interactions it does not own | Medium | RBAC | `manage_own` has no `interactions.manage` dependency; commands require `owner_user_id = auth.sub` (or `booking.manage`) and touch only the request's own `interaction_id`; a regression test (Step 13) | — |
| Scheduler not installed | Low | expiry, reminders, retention | Derived-on-read expiry; a warning on the settings and requests pages; CLI for manual runs | Without the scheduler, expiry e-mails, reminders and anonymisation need the CLI; a schedule an administrator disabled or soft-deleted in Scheduler shows no booking warning (the scheduler owns that state), so they stop until it is re-enabled |
| Org slug not globally unique: an older organization renamed into a newer tenant's slug wins that slug (as it does the portal lookup) | Low | routing, privacy | Published links and the booking form carry the profile's `public_id`, and the profile read, the slots read and the booking write reject any other profile with 404 before anything is recorded, so shared links and open forms never reach another tenant; the newer tenant's settings page shows `linkAvailable: false` | A visitor who types the URL without its `id` sees the winning organization's page, which names that organization before any details are entered. The platform fix is globally unique organization slugs in `directory`, a follow-up outside this spec |
| An organization slug change breaks booking links already shared in e-mails or signatures | Low | routing | The settings page always shows the current link; manage links keep working (token only); documented in UPGRADE_NOTES for organization renames | Old links return 404 until the owner shares the new one; no redirect and no notification |
| A booking e-mail is lost, late, duplicated, reordered or outdated | Low | booker e-mail | Delivery belongs to the platform's events, queue and e-mail transport and is out of scope; each e-mail is rendered from the current request and skipped when it no longer describes the booking; the `.ics` `SEQUENCE` lets calendar clients keep the newest invitation; the manage page and the backend always show the real state | An outdated e-mail when a change commits during a send; a lost e-mail when the process stops between a commit and its event emit, or when the platform's delivery drops it |
| A sync or person-delete cascade job exhausts its retries (the queue's standard 3 attempts span only seconds, so a database outage of about 20 seconds is enough) | Low | booking state | Queue retries; the queue reports the exhausted job (`queue.job_exhausted`); e-mails about the booking are skipped because the live interaction disagrees; the owner can cancel the booking from the Meeting requests page even though its interaction is gone | The booking stays `confirmed`, holding its slot, and its booker gets no CANCEL until the owner cancels it (from Phase 2, through the "Needs attention" badge) or the meeting ends; Phase 1 has no owner remedy |
| A manage link leaks (forwarded e-mail) | Low | booker self-service | The token is an HMAC of a server secret, unguessable; manage writes still need `expectedUpdatedAt`, and reschedule is fail-closed on the rate limiter (only cancel runs without one) and mutation guards; a link expires once its booking is final or over, and stops verifying on anonymisation; rotating `CUSTOMERS_BOOKING_TOKEN_SECRET` revokes all links | A forwarded link lets its holder cancel or reschedule that one booking until it is cancelled or its meeting is over |

### Migration & Backward Compatibility
Additive. The implementation adds a dated `BACKWARD_COMPATIBILITY.md` section, "CRM Calendar Public Booking" (created by Step 2, extended by each later step that changes a contract), covering: the optional `transactionalEm` support in `people.create` and `interactions.cancel`; the customers emit helpers (`emitQueryIndexUpsertEvents`, `emitQueryIndexDeleteEvents`, the interactions lifecycle emits), which defer to commit **only** when the command runs on an owned transaction lifetime and are otherwise unchanged; and the directory module's new `resolveOrganizationBySlug` export (the portal lookup rule, used by `organizations/lookup` and by booking). The command bus is not changed: booking uses its existing ambient execution.
- **Additive:** new tables, routes, ACL features, events, notifications and a frontend route. The conflicts route keeps its contract. `people.create` and `interactions.cancel` gain optional `transactionalEm` support, used through the command bus's existing ambient execution; existing callers pass no transaction and are unaffected. No `DataEngine` interface change. No change to `CustomerInteraction`'s columns, statuses or indexes.
- **RBAC:** the default `employee` role gains only the new `customers.booking.manage_own`; no existing grant changes.
- **Environment variables (additive, all optional, recorded as ADDITIVE rows in the dated `BACKWARD_COMPATIBILITY.md` section and added blank or with their defaults to `apps/mercato/.env.example` and the create-app template in the step that introduces them):** `CUSTOMERS_BOOKING_TOKEN_SECRET` (Step 18; manage links are off without it), `CUSTOMERS_BOOKING_LOCK_TIMEOUT_MS` (Step 8), `CUSTOMERS_BOOKING_ALLOWED_ORIGINS` (Step 8), `CUSTOMERS_BOOKING_MAX_NEW_REQUESTS_PER_DAY` (Step 8).

**Rollback:** the preferred rollback is to disable profiles. Data stays, public pages return 404, and the CRM interactions already created remain normal meetings. Reverting the code is possible as well. The migration `down` drops the three booking tables (profiles, requests, idempotency keys) and **loses all booking history**, including the link from interactions back to their requests, so it is a last resort only. The encryption-map backfill migration is forward-only (empty `down()`), so the booking-request map rows stay in `encryption_maps`; they are inert without the table.

## 📋 Phasing
- **Phase 1: Instant booking (MVP).** Profile settings page (in Phase 1 the Approval row is hidden and profiles are saved with `requires_approval = false`; Phase 2 shows it, defaulting new profiles to on; the public form's note field also arrives in Phase 2, when the owner can read the note), the reminder e-mail (triggered by the maintenance job), public page, slot engine with the write-side offered-slot gate, busy-time extraction, confirmed bookings with an auto-created person (in one real transaction), `.ics` confirmation e-mail, interaction→request sync (owner changes inform the booker, plus the person-delete cascade), abuse controls shipped **together with** the public write (Step 8), the idempotency table, and the maintenance job **with its system-scoped schedule and CLI**. Ships on its own: no manage links are sent (`manage_link_holder` is already set when a request is created, so these bookings get working links once Phase 3 and the secret are in place), and e-mails say "reply to this e-mail to change the meeting" (`replyTo` = owner).
- **Phase 2: Approval and matching.** `requiresApproval` (the Approval row on the settings page, and the public page's approval states and note field), the pending lifecycle with conditional transitions, expiry added to the existing maintenance job, the `pending` owner notification, the Meeting requests list (tab counts), one-click accept and decline, owner cancel, Link to existing person (the auto-created person is kept), pending blocks in the CRM Calendar.
- **Phase 3: Booker self-service.** Manage tokens and the manage page, booker cancel, and reschedule (instant and approval semantics, token re-pointing).

## 📋 Final Compliance Report
- Tenant and organization scoping on every query, with four documented exceptions: the maintenance job's statements run over all tenants and scope each row they return; busy time covers all of the owner's organizations within the tenant; the organization lookup by slug is the portal's unscoped read; and the manage link is looked up by chain id, with the tenant bound by the mac. The public resolver derives the organization from the slug pair, never from the request body.
- No cross-module ORM relations (`userId` and the org are FK ids only).
- Booker e-mail and names, the visitor's note (`booker_message`), the decline reason and the title and location snapshots are declared in `customers/encryption.ts` (`email` → `email_hash`), provisioned for existing tenants by a backfill migration, and read only through the decryption helpers.
- All writes go through commands; backend forms use `CrudForm` or `useGuardedMutation`.
- Optimistic locking on the profile (`CrudForm`), plus conditional state transitions with `expectedUpdatedAt` on every request write (accept, decline, link-person, owner cancel, public cancel and reschedule), enforced with `enforceCommandOptimisticLockWithGuards`.
- No PII in events, notifications, interaction titles or action-log payloads.
- No hard-coded strings; DS tokens only.
- Every custom write route runs `runMutationGuards`.
- Contract changes: additive. Each step that changes a contract adds its own part of the dated `BACKWARD_COMPATIBILITY.md` section in the same PR: Step 2 (the additive `resolveOrganizationBySlug` export in directory), Step 8 (`people.create` support, emit-helper timing), Step 13 (`interactions.cancel` support). Each step that introduces an environment variable adds its ADDITIVE row as well: Step 8 (lock timeout, allowed origins, daily creation cap) and Step 18 (token secret).
