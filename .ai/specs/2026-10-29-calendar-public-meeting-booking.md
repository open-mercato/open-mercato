# CRM Calendar — public meeting booking page per user

## 📝 TLDR
**Key points:**
- A public, no-login page at **`/calendar/{orgSlug}/{userSlug}/meetings`** where an external person picks a free slot in a CRM user's calendar, enters e-mail, first name and last name, and books a meeting.
- A confirmed booking creates a scheduled `CustomerInteraction` (a meeting) owned by that user. It appears in the CRM Calendar (`/backend/calendar`, spec `2026-06-11-crm-calendar.md`). The booker receives an e-mail with an `.ics` attachment and a private manage link for cancelling or rescheduling.
- Each user opts in and configures their own booking profile with five essentials: the on/off switch with the link, a page title, the meeting length, weekly hours (one range per day) and whether each booking needs their approval (requests not answered within 24 hours expire). A collapsed **Advanced** section holds description, location, minimum notice, horizon, a buffer after meetings, a daily cap and booker self-service, all with defaults, so turning the page on is enough to share the link.
- The visitor can add an optional note about what the meeting is about; the owner sees it in the request row. Accepting a request is one click.
- The feature lives in the **`customers`** module. It adds two entities plus an idempotency-key table. It also makes these additive changes to existing code: the conflicts route is refactored onto a shared busy-time helper (same contract, including its e-mail visibility filter); the CRM Calendar types move from `components/calendar/types` to `lib/calendar/types.ts` (a `@deprecated` re-export stays) and the recurrence expander gains an optional fallback-timezone parameter; the scheduler module's service gains an additive `isActive(id)` method (a second package, `packages/scheduler`); `people.create` and `interactions.cancel` gain the same `transactionalEm` support as `interactions.create`/`update`; the command bus lets a nested command join a caller-owned transaction lifetime (the existing `transactionLifetime` mechanism, generalised from atomic replay); and a `customers` upgrade action registers the maintenance schedule. One change is a **behavior change** rather than additive: the directory module's organization update gets a command interceptor that can refuse a slug change (see Risks → Migration & Backward Compatibility). No existing entity or route contract changes.

**Scope:** booking profile settings (a backend profile page), public booking page, slot engine, booking requests with an approval and expiry lifecycle, manual matching of the booker to a CRM person, `.ics` e-mails, one reminder e-mail to the booker, and booker self-service cancel and reschedule.

**Out of scope:** multiple meeting types per user, team or round-robin pages, payments, custom booking questions (beyond the one optional free-text note), video-conference link generation, integration with external calendar providers (Google, Microsoft; see below), bulk accept/decline, date overrides and multiple time ranges per day, and CAPTCHA (an extension point only).
- **Intended users (this phase) and external calendars:** this phase is for users who manage their calendar wholly in Open Mercato, or who block their Google or Microsoft calendar time for meeting requests by hand (by adding those meetings as CRM events, or by keeping their working hours to times they are free). Availability only knows what is in the Open Mercato calendar, and the settings page says so plainly. Integration with external calendar providers is out of scope: it can only be built once calendar connectors exist in the codebase, and none do today. When a connector later syncs external events into CRM interactions, they block times with no change to this feature. Accepting this limit for this phase is the product owner's call: confirmation is requested from the product owner (pkarw) on PR #8214, and this sentence will then name who accepted it and when. The UX review asked for that decision; it did not make it.
- **The bookings module:** the bookings module spec (`2026-08-10-bookings-module.md`, §19 `/book/{slug}`) remains the home for service and resource bookings with pricing (a car, a room, a paid service). This feature is a personal "book a meeting with me" link, like Calendly, for sales and customer calls over CRM interactions. When a CRM user asks for "a booking link", they get this page. This spec neither depends on the bookings module nor blocks it; shared UI components (the month picker, the slot list) may be reused at code level.

## 📝 Overview
CRM users schedule meetings with prospects and customers by trading e-mails about availability. The CRM Calendar already shows every scheduled interaction, but external people cannot see when a user is free or book time with them. This spec adds a personal booking link, similar to Calendly or cal.com, that reads the same busy data the backend calendar uses, so bookings never collide with the user's CRM schedule.

> **Market reference:** **cal.com** (open-source leader) and **Calendly** (commercial canon), plus **Odoo Appointments** and **HubSpot Meetings** (CRM-native).
> **Adopted:** the "first available day" landing, a month picker with day dots plus a vertical slot list, minimum notice, horizon, a buffer after meetings, a daily cap, a "requires confirmation" mode with a request lifecycle, an optional "what is this about" note, one reminder e-mail, a booker manage link (cancel/reschedule), `.ics` with a stable UID and SEQUENCE, and display in the visitor's timezone with a 12/24-hour switch.
> **Rejected for v1:** multiple event types per user (one booking profile per user keeps settings and URL simple; additive later), routing forms, payments, and custom questions (cal.com/Calendly carry heavy builder UIs for these). Also cut to keep the settings small (UX review, 17 Nov 2026): date overrides (a day off is blocked with a CRM event), multiple ranges per day, a start-time interval separate from the meeting length, a buffer before meetings, a configurable response deadline and change cutoff, a per-user cap on new requests (a system setting instead) and bulk accept/decline. Busy time from external calendars belongs to a future integrations provider.

## 📝 Problem Statement
- External parties cannot book time with a CRM user without back-and-forth e-mail.
- Meetings agreed by e-mail are entered by hand and often miss the CRM link to a person, so CRM activity history is incomplete.
- Any booking tool outside the CRM does not see CRM-scheduled interactions, so it double-books.

## 📝 User Stories (story map)

### Epic A — Set up my booking page (CRM user)
- **US-A1** As a CRM user, I want to turn on a public booking page and share its link, so that external people can book me.
  - AC: off by default, with every other value defaulted, so turning it on and saving is enough. The link name defaults to my e-mail's local part (normalised, with a numeric suffix on a collision) and can be changed from the link's menu with live validation (format, taken). The full URL `/calendar/{orgSlug}/{slug}/meetings` is shown with **Copy** and **Open**. Enabling without an org slug, or with an ambiguous one, shows a blocking inline error. Save uses optimistic locking; a conflict shows the conflict bar.
- **US-A2** As a CRM user, I want to set my page title, meeting length and working hours, so that only times I actually work are offered.
  - AC: defaults are "Meet with {first name}", 30 min and Mon–Fri 09:00–17:00 in my browser's timezone. Working hours show as a one-line summary ("Mon to Thu, 09:00 to 17:00") with **Edit**, which opens a dialog with one on/off switch and one range per weekday; an end before the start is rejected inline. The preview card shows the next 5 slots, with an empty state when nothing is bookable.
- **US-A3** As a CRM user, I want sensible limits I rarely have to touch, so that bookings don't overwhelm me.
  - AC: a collapsed **Advanced** section whose closed state summarises the current values. Inside: description, location, the booking window as a sentence with in-place values ("People can book up to [60] days ahead, with at least [2] hours notice"), the buffer after meetings and the daily cap as a sentence ("Keep [10] minutes free after each meeting, and take at most [any] bookings a day"), and the booker self-service switch. An empty daily cap means unlimited.
- **US-A4** As a CRM user, I want to require approval, so that I can vet requests before they reach my calendar.
  - AC: a switch (default on). Requests not answered within 24 hours, or by the meeting start if earlier, expire automatically; the deadline is fixed, not configurable.
- **US-A5** As a CRM user, I want to allow bookers to cancel or reschedule online.
  - AC: a switch in Advanced (default on). Changes close 1 hour before the meeting; the cutoff is fixed.

### Epic B — Book a meeting (external visitor, not logged in)
- **US-B1** As a visitor, I want to land on the first day with free times, so that I don't have to hunt.
  - AC: that day is preselected, days without slots are disabled, month navigation is limited to the horizon, and the slot length is visible. Available days carry a dot as well as a tint (not colour alone), and today has an outline ring. Times are in my timezone, with a switcher, and in my locale's 12- or 24-hour format, with a 12h / 24h switch next to the timezone. The page renders in my browser language when the app has it, otherwise in the default locale, with a language switch in the footer. With no availability, the empty state reads "No times available in the next N days". An unknown or disabled page shows "This booking page isn't available".
- **US-B2** As a visitor, I want to pick a time from a vertical list, enter e-mail, first name and last name, and say what the meeting is about, so that I can book quickly.
  - AC: the selected slot shows a summary (date, start and end, timezone, and the location only when the owner entered one). E-mail, first name and last name are required, the e-mail format is validated; "What would you like to talk about?" is optional (up to 500 characters). The consent checkbox is **unticked by default** and required. Errors show under each field after submit, the first invalid field gets focus, and a summary is announced through `aria-live`. The keyboard works end to end. Back returns to the slots with the selection kept.
- **US-B3** As a visitor, I want a clear result.
  - AC: instant booking reads "You're booked" plus "invite sent to {email}", and, when the meeting is more than 24 hours away, "We'll e-mail you a reminder 24 hours before the meeting". Approval mode reads "Request sent", with the confirm-by time. "Just taken" returns me to the refreshed slots with a banner and keeps what I typed. A rate limit or a network error keeps me on the form with a retry message.
- **US-B4** As a booker, I want to cancel or reschedule from the e-mail link.
  - AC: the page shows the meeting summary with Cancel (confirmation dialog: "Keep meeting" / "Cancel meeting") and Reschedule (the same picker). After the cutoff both are disabled with an explanation. Cancelled and expired states are shown read-only.
- **US-B5** As a booker, I want a reminder before the meeting, so that I don't forget it.
  - AC: one e-mail 24 hours before the start, with the meeting summary and (from Phase 3) the manage link. None when the meeting was confirmed less than 24 hours before its start, or was cancelled; a moved meeting gets its reminder for the new time.

### Epic C — Handle requests (CRM user)
- **US-C1** As a CRM user, I want to see pending requests and accept or decline them before they expire.
  - AC: three tabs (Pending, Upcoming, History) and a "Respond by" column. Each pending row shows the visitor's note, so I can decide without opening anything. **Accept is one click**: it creates a new person for a new booker (or keeps the existing person for a reschedule) and sends the invite; only when the slot now overlaps something does a small dialog ask me to confirm, showing just the overlap. Linking to an existing person is a separate action afterwards (US-C2). Decline takes an optional message to the booker. A request that has already expired shows "This request expired at {time}" and greys out. The empty state for each tab says why it is empty, and a user without an enabled page sees a "Set up booking page" call to action. On a phone the list becomes cards with full-width Accept and Decline. Users without `customers.booking.manage_own` get no access.
- **US-C2** As a CRM user, I want to link a confirmed booking's auto-created person to an existing CRM person.
  - AC: a picker. On success, the toast says whether the auto-created person was removed or kept (because it holds other data).
- **US-C3** As a CRM user, I want pending requests visible in my CRM Calendar.
  - AC: a hatched "Pending: {booker name}" block; clicking it runs the same one-click Accept (with the overlap dialog when needed) or Decline.

### Cross-cutting rules
- All times are stored in UTC, the public page shows times in the visitor's timezone, and the backend shows them in the user's timezone.
- Dialogs: `Cmd/Ctrl+Enter` submits, `Escape` cancels. Dialog footers carry no keyboard hint text, and pages and cards carry no description line under their titles.
- Values are never joined with a dash or a middot; they go in separate elements or lines.
- One primary action per view.
- No busy details are ever shown publicly, only free starts.

## 📝 Proposed Solution
1. **Booking profile** (`CustomerBookingProfile`): one per user per organization, edited on a new backend profile page **My meeting booking**. It is opt-in and off by default.
2. **Public page:** a chrome-less frontend page in `customers/frontend/calendar/[orgSlug]/[userSlug]/meetings/`. It loads the first day with free slots, a month calendar widget marking days with availability, the slot length, and the vertical list of start times. Picking a slot opens a form (e-mail, first name, last name, and an optional note about the meeting). Submitting goes through the public request route.
3. **Slot engine** (`customers/lib/booking/slots.ts`): a pure function. Inputs are the profile, busy intervals and a date range; the output is the free starts. Busy intervals come from a shared server helper extracted from the existing conflicts route, so the calendar's notion of "blocked" and the booking page's notion of "busy" stay identical (see Architecture → Busy time).
4. **Booking request** (`CustomerBookingRequest`): holds the booker's details and the lifecycle `pending → confirmed | declined | expired | cancelled`. Every state change runs as a conditional update (`… WHERE id = ? AND status = 'pending' AND expires_at > now()` for accept/decline, and the matching guard for expire and cancel), so exactly one transition wins (see Architecture → State transitions).
   - Without approval, a request is created already `confirmed`.
   - With approval, it is `pending` with `expiresAt = min(createdAt + 24 h, startsAt)` (the fixed `BOOKING_APPROVAL_DEADLINE_HOURS = 24` in `lib/booking/constants.ts`; not configurable per profile). A pending request blocks its slot. The owner gets a notification and accepts or declines from a backend list. A scheduler job expires overdue requests.
5. **Person linking (no automatic matching):** on confirmation the system always creates a **new** CRM person (`source = 'public_booking'`) from the typed details and attaches the interaction to it. It never matches by e-mail, because a typed e-mail is a claim, not an identity. In the backend, the user can **Link to existing person**: this moves the interaction to the chosen person. The auto-created person is then **soft-deleted** (`deleted_at` set, **never** through the existing person-delete command, which hard-deletes and cascades) only when the new `countPersonDependents` helper finds nothing else attached to it (Architecture → Link to existing person). Accepting a request offers no person choice: it is one click, and linking is always the separate action afterwards. A **reschedule** keeps the booking's existing person and never creates a second one.
6. **E-mails:** shared `sendEmail` with an `EmailAttachment` holding `text/calendar` content built by a small RFC 5545 builder (`customers/lib/booking/ics.ts`). Each lifecycle step sends a fixed e-mail:

   | Event | Recipient | E-mail | `.ics` |
   |---|---|---|---|
   | Request received (approval on) — `request_received` | booker | "request received" | none |
   | Confirmed — `confirmation` | booker | confirmation + manage link | `METHOD:REQUEST` |
   | Declined — `decline` | booker | "declined", with the owner's optional reason | none |
   | Expired — `expiry` | booker | "expired" | none |
   | Cancelled (by the booker, the owner, a CRM cancel or delete, the person-delete cascade, or undo of accept) — `cancellation` | booker | cancellation | `METHOD:CANCEL` |
   | Cancelled by the booker — `owner_cancellation_notice` | owner | notification e-mail | none |
   | Moved or retitled (owner move, instant reschedule, accepted reschedule) — `update` | booker | update | `METHOD:REQUEST`, same `UID`, `SEQUENCE + 1` |
   | Reschedule declined or expired — `reschedule_declined`, `reschedule_expired` | booker | "your original time stays" | none |
   | 24 hours before the start | booker | reminder (meeting summary; manage link from Phase 3) | none |

   **Manage tokens (Phase 3):** the manage token is **derived and verified, never stored**. The link carries `{manage_chain_id}.{mac}`, where `manage_chain_id` is the id of the first request in the booking's reschedule chain (a successor copies its predecessor's value) and `mac = base64url-without-padding(HMAC-SHA256(CUSTOMERS_BOOKING_TOKEN_SECRET, "customers.booking.manage.v1" ‖ 0x00 ‖ tenant_id ‖ 0x00 ‖ manage_chain_id))` (`lib/booking/tokens.ts`; the version label separates this use of the secret from any other). **Verification:** the route parses the chain id, loads the one request of that chain with `manage_link_holder = true` (unique per chain), re-derives the mac with that row's `tenant_id`, and compares with `crypto.timingSafeEqual` on equal-length buffers; the mac is verified **before** anything is decrypted or returned. An unparsable token, no holder row, or a mismatch all return the same `404` with the code `booking_link_invalid`, which the page renders as one card, "This link isn't valid. Reply to the invite e-mail to change your meeting." (no existence leak). Only the mac is secret: the chain id also appears in the `.ics` UID, and knowing it does not help to forge the mac. The manage `GET` and writes have their own rate-limit buckets, separate from the booking form's: per client IP for every request, and **per chain id only after the mac verifies**, so requests with forged macs can never fill the booker's bucket and lock them out of cancelling; a separate per-chain bucket counts only **failed** verifications and, when full, refuses further failed attempts for that chain without ever refusing a valid mac. Manage-link **cancel** is the one exception to the booking wrapper's fail-closed rule: without a registered or healthy rate limiter it still runs, because the mac is the credential and a booker must always be able to cancel; manage-link **reschedule** stays fail-closed (`503 booking_unavailable` without a limiter), so a forwarded link cannot be used for unlimited reschedules. The token path segment is redacted from logs. So no token or token hash is stored (a database leak yields no working links), every e-mail rebuilds the same link (no rotation: failed or retried sends, cap deferrals and quick successive e-mails never change a link, and an open manage page keeps working), and **rotating `CUSTOMERS_BOOKING_TOKEN_SECRET` revokes every link** while new e-mails get links that work with the new secret. `manage_link_holder` is set on confirmation in every phase, so bookings confirmed before Phase 3, or while the secret was unset, get working links as soon as both exist; it moves to an accepted reschedule successor (Architecture → Reschedule) and is cleared on anonymisation. Without the secret, e-mails carry no link and keep Phase 1's "reply to change" copy. **The secret:** checked with the platform's existing secret policy in `packages/shared/src/lib/auth/jwt.ts` (`isUnsafeJwtSecret`: at least 32 characters, not one of its `PLACEHOLDER_SECRETS`); the trimmed value is the HMAC key; generate it with `openssl rand -base64 32`; it is used for nothing else (never `AUTH_SECRET`, `JWT_SECRET` or a pepper) and is blank in `.env.example`. Modules have no start hook, and app code under `apps/mercato/src/` is off limits, so the check runs in `lib/booking/tokens.ts` the first time a link is built or verified in a process: an **unset** secret means links off (`isUnsafeJwtSecret` treats unset as unsafe, so the code checks for unset first); a secret that is **set but unsafe** also means links off, plus one `reportError` per process (code `customers.booking_token_secret_unsafe`), so an operator sees it without a broken deployment. E-mails then carry the "reply to change" copy and verification returns `booking_link_invalid`. The HMAC key is the configured value with surrounding whitespace trimmed (the policy check sees the same trimmed value). **Once the booking is final** (cancelled, declined, expired) **or its meeting has ended**, the manage page shows only the status, time and owner, never the booker's name or e-mail, so a forwarded or old link exposes no booker details.

   **Reminder:** one e-mail to the booker 24 hours before the start. The job queue (Redis or file) cannot join a database transaction, so the request row is the reminder's outbox, like the durable bulk operation in the reference example module.
   - **Start version:** every request has `starts_at_version` (integer), set to 1 on confirmation and incremented on every change of `starts_at` (owner move through the sync job, instant reschedule, and an accepted reschedule successor at acceptance). It is the reminder's version key: an integer compares exactly in SQL and in a job payload, which a `timestamptz` would not (Postgres keeps microseconds, a JS `Date` milliseconds). `starts_at_changed_at` is written at the same moments (on confirmation, and to `now()` on every move) and is used only for the 24-hour rule below; `decided_at` and `created_at` are not used, because a move changes neither.
   - **No version bump from reminder bookkeeping:** every reminder statement in this section (claim, lease, attempt count, defer, close, delivery record, sweep, abandonment) is a raw conditional SQL `UPDATE` that never sets `updated_at`, so reminder bookkeeping never makes the request's optimistic-lock version change; an owner or booker holding the page around `starts_at − 24 h` gets no false `409`. The same applies to the mail-cap reservation on the profile row. Each of these statements also **runs on its own, in its own short transaction (autocommit)**, never inside a longer transaction, and every time comparison in them uses `statement_timestamp()`; where this section writes `now()`, read `statement_timestamp()`. So a lease or due-time check always uses the moment the statement runs.
   - **Queue contract:** the queue is only a wake-up signal. `Queue.enqueue` assigns its own job ids and its coalescing is best effort on both strategies (Redis can add a follow-up for an active job, and the local strategy retries a failed job up to its own attempt limit), so duplicate jobs for one reminder are expected. Exclusivity, versioning, backoff and retries live on the request row: the reminder worker never relies on job ids, coalescing or queue retries, and needs no queue change.
   - **Claim** (the maintenance job, every 5 minutes): one conditional statement selects and claims in one step, `UPDATE … SET reminder_start_version = starts_at_version, reminder_attempts = 0, reminder_next_attempt_at = now(), reminder_sent_at = NULL, reminder_lease_owner = NULL, reminder_lease_expires_at = NULL WHERE status = 'confirmed' AND anonymised_at IS NULL AND (reminder_start_version IS NULL OR reminder_start_version <> starts_at_version) AND starts_at > now() AND starts_at <= now() + 24 h AND starts_at_changed_at <= starts_at − 24 h RETURNING id, reminder_start_version`. So a meeting that has already started is never claimed (a tick after an outage sends nothing for past meetings); a booking confirmed or moved less than 24 hours before its start is never claimed, because the booker was just told the time; and a move that commits concurrently either lands before the statement (and is evaluated) or bumps the version after it. **A claim is valid only for the current version:** a row whose `reminder_start_version` differs from `starts_at_version` counts as unclaimed, whatever its other reminder columns say, and the next claim re-initialises all of them. So a move never has to clear reminder columns, and a move that read the row before a claim and saved after it cannot strand the claim. Overlapping ticks claim a row once. **After commit** the job enqueues a plain `customers:booking-reminder` job `{ tenantId, organizationId, requestId, startVersion }` per returned row (no coalescing key, no delay), so the worker never needs an unscoped read to find the request's scope. A claim that rolls back enqueues nothing.
   - **Re-enqueue:** each tick also enqueues the same payload for open claims that are due and unleased: `status = 'confirmed'`, `anonymised_at IS NULL`, `reminder_start_version = starts_at_version`, `reminder_sent_at IS NULL`, `reminder_attempts < 3`, `reminder_next_attempt_at <= now()`, `starts_at > now()` and `reminder_lease_expires_at IS NULL OR reminder_lease_expires_at <= now()` (a partial index on `reminder_next_attempt_at` where `reminder_sent_at IS NULL AND reminder_next_attempt_at IS NOT NULL` serves this scan). This covers a crash between commit and enqueue, a lost job, a crashed worker, a failed send and the end of a deferral. It does not change the row; the backoff is enforced by the lease.
   - **Delivery lease** (`workers/booking-reminder.ts`): each job run generates a random lease token and takes the claim with **one** conditional statement: `UPDATE … SET reminder_lease_owner = :token, reminder_lease_expires_at = now() + 2 min, reminder_next_attempt_at = now() + 10 min WHERE id = :requestId AND tenant_id = :tenantId AND organization_id = :organizationId AND reminder_start_version = :startVersion AND starts_at_version = :startVersion AND reminder_sent_at IS NULL AND reminder_attempts < 3 AND reminder_next_attempt_at <= now() AND (reminder_lease_expires_at IS NULL OR reminder_lease_expires_at <= now()) RETURNING …`. The job's own `startVersion` is compared with **both** the claim and the current start, so a job for an older start (queued, or retried by the queue, after a move and a new claim) matches no row and exits without changing anything. Zero rows also covers a reminder that is sent, closed, not yet due (backoff or deferral), or leased by a simultaneous job; that job exits too. So of two simultaneous jobs exactly one proceeds, and several queued jobs for one claim cannot spend its attempts back to back: each send is at least 10 minutes after the previous one. Every later write by the worker is guarded by `reminder_lease_owner = :token AND reminder_start_version = :startVersion AND starts_at_version = :startVersion`, so a worker that lost its lease, or whose meeting moved meanwhile, changes nothing; after a move the next tick claims the new version.
   - **Key outage:** in the send step, **after** the attempt update and the owner lookup and **before** the cap reservation (so it gives back only an attempt it counted, checks the owner's fields once they are loaded, and spends no cap slot, except when the key becomes unavailable between this check and the final snapshot's decryption, below), the reminder applies the mail outbox's key-outage check (E-mail safety → Delivery) to the request's encrypted fields it uses (`email`, `title_snapshot`, `location_snapshot`; booker e-mails carry no booker names) and to the owner's `email`/`name` used for `replyTo`; when a value is still encrypted, it sends nothing, **gives the attempt back**, releases the lease and moves `reminder_next_attempt_at` 10 minutes ahead, so an outage delays the reminder but never uses up its attempts. **Checks under the lease:** the worker reads the request and the **live** interaction (by `interaction_id`, through the decryption helpers, tenant and organization scoped, without the `deleted_at IS NULL` filter). It **closes** the claim (`reminder_next_attempt_at = NULL`, lease cleared, nothing sent, nothing reported) only for request-level terminal states: the request is not `confirmed`, is anonymised, or `starts_at <= now()`. When the interaction disagrees with the request (it is missing, deleted or `canceled`, or its `scheduled_at` differs from the request's `starts_at`), the request may simply be waiting for the sync job, and a CRM cancel or delete can still be undone, so the worker **defers**: it releases the lease and keeps `reminder_next_attempt_at = now() + 10 min`, with no attempt counted. Request-level terminal states take precedence over these deferrals. If the sync job then cancels or moves the request, the closing sweep or the version change ends the claim; if the change is undone or the meeting is moved back before the sync runs, the next attempt finds them in agreement and sends.
   - **Mail cap:** the reminder reserves its slot in the profile's daily counter (E-mail safety → mail cap) **after** the send step's attempt update below has re-checked the request and renewed the lease, so a slot is never spent on a reminder that the re-check stops. The reservation is kept if the send then fails, so the cap bounds send attempts. A reminder does not use the mail outbox. When the reservation is refused, the worker keeps the claim and, in one statement guarded by its lease token, gives the attempt back (`reminder_attempts = reminder_attempts − 1`), sets `reminder_next_attempt_at` to the next local midnight of the profile, computed in that same statement from the database clock (`(((statement_timestamp() AT TIME ZONE p.timezone)::date + 1)::timestamp AT TIME ZONE p.timezone)`, joining the request to its profile on `p.id = r.profile_id AND p.tenant_id = r.tenant_id AND p.organization_id = r.organization_id`), and releases the lease; nothing is sent. It does not read `mail_cap_day`, which another reservation may have moved meanwhile. If the stored day is ahead of that midnight, the next attempt is simply refused and deferred again, so nothing is lost; no attempt is counted for a deferral, and the owner gets the usual once-a-day `cap_reached` notification with `cap: 'mail'`. Because the lease requires `reminder_next_attempt_at <= now()`, no job sends it earlier; the first tick after that time re-enqueues it and the checks run again, and a deferral that lasts past the meeting's start is closed by the closing sweep without a mail.
   - **Send:** after the checks, and before the cap reservation above, the worker counts the attempt and renews its lease in one statement, `UPDATE … SET reminder_attempts = reminder_attempts + 1, reminder_lease_expires_at = now() + 2 min WHERE <guards above> AND reminder_lease_expires_at > now() AND status = 'confirmed' AND anonymised_at IS NULL AND starts_at > now() RETURNING …`. The request-level checks are repeated here, in the statement that commits to sending, because a booker or owner cancel, an accepted reschedule (which marks this row `superseded`) or an anonymisation does not change `starts_at_version` and can commit after the read-only checks; under READ COMMITTED the conditional update re-evaluates them against the committed row. Zero rows means the lease was lost, the meeting moved, or the request was cancelled, superseded or anonymised during the checks: the worker sends nothing and exits. Otherwise the order is: the owner lookup for `replyTo`, the key-outage check (above; it covers the request's and the owner's fields), the cap reservation, the final lease renewal with its snapshot, rendering within the preparation deadline, the pre-send claim, the send. So it reserves the cap slot (above) and, when that succeeds, renews its lease once more with a guarded statement (`reminder_lease_expires_at = statement_timestamp() + 2 min WHERE <token and version guards> AND reminder_lease_expires_at > statement_timestamp() AND status = 'confirmed' AND anonymised_at IS NULL AND starts_at > statement_timestamp()`), and only when that returns a row, with the request's current `starts_at`, `ends_at`, `ics_sequence`, `title_snapshot`, `location_snapshot` and `email` in its `RETURNING` (the `ics_sequence` returned here is the `:snapshotIcsSequence` the pre-send claim checks) (decrypted again, with the same key-outage check: a value still encrypted at this point sends nothing and runs the same give-back as the first check, giving the attempt back, releasing the lease and moving `reminder_next_attempt_at` 10 minutes ahead; the cap slot already reserved is not returned), builds the reminder from that final snapshot (the request row's values win; the live interaction is used only to decide whether to defer, see Checks under the lease) within a **30-second preparation deadline** (a `Promise.race` against a 30-second timer started when the final renewal returns, covering decryption and rendering only; missing it takes the failed-send path: nothing is sent, `reminder_attempts` stays counted, the lease is released and `reminder_next_attempt_at` keeps the lease's `+ 10 minutes`; after the third attempt the tick's abandonment statement closes and reports it), and then, **immediately before calling the mail transport**, runs the **pre-send claim**: `UPDATE customer_booking_requests SET reminder_lease_expires_at = statement_timestamp() + interval '2 minutes' WHERE id = :requestId AND reminder_lease_owner = :token AND reminder_lease_expires_at > statement_timestamp() AND reminder_start_version = :startVersion AND starts_at_version = :startVersion AND reminder_sent_at IS NULL AND status = 'confirmed' AND anonymised_at IS NULL AND starts_at > statement_timestamp() AND ics_sequence = :snapshotIcsSequence RETURNING id`. Only when it returns a row does the worker send through the booking mail path, under the mail outbox's **transport settlement rules** (E-mail safety → Delivery) applied to `reminder_lease_*`: it waits for the transport to settle with no caller-side timer, renews its lease every 30 seconds while the send is in flight, stops renewing at the 10-minute send ceiling (outcome unknown, reported once), and records a success whenever it arrives. So the transport call starts inside a freshly renewed lease the worker owns, and neither the abandonment statement nor another job can take the claim while a send is in flight. **When the claim returns no row, the transport is never called**: the worker runs the reminder give-back guarded by its token and an unexpired lease (`reminder_attempts − 1`, `reminder_next_attempt_at = statement_timestamp()`, lease released), so the next attempt rebuilds from a fresh snapshot; when that also returns no row the lease was lost and the worker exits without changes. The cap slot already reserved is not returned. After the mail server accepts the message, `UPDATE … SET reminder_sent_at = now(), reminder_lease_owner = NULL, reminder_lease_expires_at = NULL WHERE id = :requestId AND reminder_start_version = :startVersion AND reminder_sent_at IS NULL` records delivery, deliberately not guarded by the lease token, so a success that arrives after the ceiling or after another job took the claim is still recorded and stops further sends. A failed send (the transport rejects) is **caught, not rethrown**: the worker, if it still holds its lease, releases it and leaves `reminder_next_attempt_at = now() + 10 min` from the lease, so the queue sees a completed job on both strategies and never retries it; the outbox owns the retry. An unexpected error outside the send (for example the database being unavailable) may still be retried by the queue; that retry is just another job for the same claim and goes through the same lease and backoff.
   - **Closing sweep and abandonment:** each tick runs two conditional statements over unsent, unleased open claims (`reminder_sent_at IS NULL AND reminder_next_attempt_at IS NOT NULL AND (reminder_lease_expires_at IS NULL OR reminder_lease_expires_at <= now())`), so no claim waits forever and none needs a job to end it:
     - `UPDATE … SET reminder_next_attempt_at = NULL WHERE <open, unleased> AND (status <> 'confirmed' OR anonymised_at IS NOT NULL OR starts_at <= now())` closes claims whose request was cancelled, anonymised or started meanwhile (for example during a backoff, a time-mismatch deferral or a cap deferral past the start), and stale claims whose version no longer matches (`OR reminder_start_version <> starts_at_version`, for a meeting moved to inside 24 hours that will not be claimed again), without a report;
     - `UPDATE … SET reminder_next_attempt_at = NULL WHERE <open, unleased> AND status = 'confirmed' AND anonymised_at IS NULL AND reminder_start_version = starts_at_version AND reminder_attempts >= 3 RETURNING id` closes abandoned claims, including one whose worker crashed after its third increment but before sending; after commit the tick reports each returned row once with `reportError`. Being one statement with the version check, it never reports a claim made stale by a move (the sweep above closes those silently), and two overlapping ticks cannot both return the same row. The report is at most once: a crash after the commit and before `reportError` loses it.

     So every claim ends either sent (`reminder_sent_at`) or closed (`reminder_next_attempt_at IS NULL`), and only abandoned claims are reported.
   - **Delivery is at least once.** A second identical reminder can reach the booker in two rare cases: the process stops after the mail server accepted the reminder but before `reminder_sent_at` is written, or a send outlives the 10-minute ceiling and is delivered after a later attempt has already sent. In both, a later attempt sends again (at most 3 sends per claim); a late success is still recorded, so it stops any attempt that has not yet passed its pre-send claim. This is chosen over at most once, because a lost reminder is worse than a duplicate with identical content. A run that loses its lease before its pre-send claim never sends; while a send is in flight the heartbeat keeps the lease. A move committed while a reminder send is in flight produces its update e-mail through the mail outbox, and the two are **not ordered**: the booker can receive the update and then a reminder showing the old time. The update carries the higher `SEQUENCE`, so a calendar client keeps the new time; the reminder is plain text with no `.ics`. This is accepted (Risks) rather than holding the per-owner lock across a mail-server call.
   - Any change of `starts_at` increments `starts_at_version` and sets `starts_at_changed_at` **in the same statement that writes `starts_at`** (a SQL increment, `starts_at_version = starts_at_version + 1`, never a value computed in memory); the reminder columns are left as they are, because the claim treats a version mismatch as unclaimed (an accepted reschedule successor is a new row with `starts_at_version = 1` and no claim). So a moved meeting is reminded for its new time, unless the move lands less than 24 hours before the new start. A cancelled meeting is no longer `confirmed`: it is not claimed, and an open claim is closed by the next tick's closing sweep. The owner gets no reminder from this feature (the CRM calendar already handles that).

   **E-mail safety** (there is no e-mail confirmation step, by decision):
   - booker e-mails and the `.ics` contain **no** booker-supplied text at all: no names or note in the greeting, subject, body, `ATTENDEE CN` or description (the attendee is the e-mail address only). So the form cannot inject content into a mail sent to an arbitrary address. The visitor's note is shown only inside the backend, to the owner;
   - owner-facing e-mails and notifications may show the booker's name, as escaped plain text truncated to 100 characters;
   - `replyTo` is the owner's e-mail, so "reply to change" reaches the owner;
   - a per-profile cap of 50 outbound booking e-mails per day applies (configurable through `CUSTOMERS_BOOKING_DAILY_MAIL_CAP`). The **cap day** is the calendar date in the profile timezone, and the counter lives on the profile row (`mail_cap_day`, `mail_cap_count`). Every booking e-mail reserves one slot with one atomic statement before it is handed to the mail transport, and the **database computes the day inside that statement**; no caller passes a day, so a worker that stalls across midnight cannot carry an old date into the reservation:
     `UPDATE customer_booking_profiles SET mail_cap_count = CASE WHEN mail_cap_day IS NULL OR (statement_timestamp() AT TIME ZONE timezone)::date > mail_cap_day THEN 1 ELSE mail_cap_count + 1 END, mail_cap_day = GREATEST(mail_cap_day, (statement_timestamp() AT TIME ZONE timezone)::date) WHERE id = :profileId AND (mail_cap_day IS NULL OR (statement_timestamp() AT TIME ZONE timezone)::date > mail_cap_day OR mail_cap_count < :cap) RETURNING mail_cap_day, mail_cap_count`.
     The stored day **never moves backwards**: a later day resets the count to 1, the same day adds one, and an earlier computed day (the profile's `timezone` was changed to a zone that is behind, or a statement with an earlier timestamp commits after a later one) counts against the stored day instead of resetting it. `statement_timestamp()` is used rather than `now()`, so a reservation inside a long transaction still uses the time it runs. The statement does not touch `updated_at`, so it never conflicts with the settings form's optimistic lock. Zero rows means the cap is reached; concurrent senders cannot both pass it. A reserved slot is not returned when the send fails.
     **Mail outbox: every booking e-mail except the reminder is written by the transaction that causes it.** Creating a pending request (`request_received`), confirming a booking (instant or accept), declining, expiring, cancelling (booker or owner cancel, the sync job after a CRM cancel or delete, the person-delete cascade and its backstop, undo of accept), the sync job's owner-move and title updates, an instant reschedule, and accepting, declining or expiring a reschedule each insert their e-mails, **in the same transaction**, as rows of the mail outbox `customer_booking_mail_outbox` (Data Model) with `INSERT … ON CONFLICT (request_id, kind, request_status, ics_sequence) DO NOTHING`, `send_after = statement_timestamp()`, and the state the e-mail describes stamped from the transaction's own `RETURNING status, ics_sequence`. No booking e-mail is sent by an event subscriber or by the causing code after commit, so a crash after commit cannot lose an e-mail: the rows commit with the change, and the outbox worker is the **only** sender. The reminder alone keeps its own claim on the request row (Reminder). After commit the causing code enqueues a best-effort wake-up job `{ tenantId, organizationId, outboxId, sendVersion }`. **Every statement that pushes `send_after` forward** (the lease itself, a failed send, a released lease, a cap deferral, the key-outage give-back) also enqueues a wake-up with `delayMs` equal to the new delay, computed by the database in the same statement (`RETURNING send_version, ceil(greatest(0, extract(epoch from send_after - statement_timestamp()) * 1000))`), not the app server's clock; so a worker killed mid-send is retried after its 10-minute backoff. Each row has an integer `send_version`, incremented by **every** statement that writes `send_after` (an integer compares exactly in SQL and in a job payload, which a `timestamptz` would not: Postgres keeps microseconds, a JS `Date` milliseconds). Each wake-up job carries the version it was enqueued for (`{ tenantId, organizationId, outboxId, sendVersion }`), taken from that statement's `RETURNING send_version`. The worker's lease statement includes `AND send_version = :sendVersion`, so a job whose `sendVersion` differs from the row's current `send_version` takes no lease and exits (it reads the row only to choose between re-queueing a not-yet-due current job and exiting), because the statement that changed it enqueued its own job; duplicate jobs for the current version (the tick's re-enqueue, a crash and retry) are harmless, because the lease lets only one proceed. A job that matches but finds the row not yet due, **or due but still leased by another worker** (a send in flight keeps its lease through the heartbeat), re-queues itself once for the remaining time (until `send_after`, or until `lease_expires_at` for a leased row); the chain of such re-queues is bounded because the heartbeat stops at the send ceiling, and only while the row is open (`sent_at IS NULL AND closed_at IS NULL`) and `attempts < 3`, with the delay computed by the same expression; otherwise it exits, so retries and deferrals do not depend on the maintenance schedule. The maintenance tick additionally enqueues one for every due, unleased, open row, with the row's current `send_version` in the payload (selected in the same scan), which only matters when a wake-up job itself was lost; without the scheduler such a row waits for the manual CLI run (Risks). Booking events (`customers.booking_request.*`) remain for in-app notifications, webhooks and workflows only; no e-mail depends on them, and no mail code subscribes to them.
     **Kinds and the state each one requires at send time** (`lib/booking/mailState.ts` supplies this per-kind SQL condition in two forms built from one definition: with parameters, for the worker's locking statements on one row, and **row-based**, reading its inputs from the outbox row being scanned (`d.kind`, `d.request_status`, `d.ics_sequence`) and from the joined request and predecessor, for the tick's close; it is the only copy): `request_received` → `pending` with `expires_at > statement_timestamp()` (expiry is derived on read when the scheduler is missing); `confirmation` → `confirmed` with `starts_at > statement_timestamp()`, **without** a sequence match, with its meeting fields (`ics_uid`, `ics_sequence`, `starts_at`, `ends_at`, `title_snapshot`, `location_snapshot`) taken only from the snapshot returned by the **final** send guard (Delivery), so a confirmation is always sent even when the owner edited the meeting before it went out (an `update` row for that edit may follow; the booker's calendar keeps the higher `SEQUENCE`); `update` (owner move or title change, instant reschedule, accepted reschedule) → `confirmed`, `starts_at > statement_timestamp()` and the stamped `ics_sequence`, so an older update is closed once a newer one exists; `cancellation` (the booker's CANCEL) and `owner_cancellation_notice` (the owner's e-mail when the booker cancels; a separate kind, so it never collides with the CANCEL on the unique key) → `cancelled` with `ends_at > statement_timestamp()` and **no** sequence match (a cancelled request's sequence never changes, because the sync job never touches requests that are not `confirmed`); `decline` → `declined`; `expiry` → `expired`; `reschedule_declined`, `reschedule_expired` ("your original time stays") → the successor's `declined`/`expired` **and** the predecessor still `confirmed` with its meeting in the future (joined through `previous_request_id`). A cancelling transaction writes the booker's `cancellation` only for a request that was `confirmed` (the booker already holds its `.ics`, from the confirmation e-mail or the success page's download), never for `superseded` or `original_cancelled` rows, and writes the `owner_cancellation_notice` only for a booker cancel. So a newer update supersedes an older one, and a cancellation closes a not-yet-sent confirmation (the status moved on) while the CANCEL itself is sent.
     **Over the cap:** the worker's cap reservation is refused, so the row is deferred to the profile's next local midnight (below) and the owner gets the once-a-day `cap_reached` notification with `cap: 'mail'`; the e-mail is sent then, with a fresh cap slot and the same state check.
     **Delivery** (`workers/booking-mail-outbox.ts`) follows the reminder's outbox rules. Due rows are open rows with `send_after <= statement_timestamp()`, `sent_at IS NULL`, `closed_at IS NULL` and `attempts < 3`. The worker takes a 2-minute lease with one conditional update that also moves `send_after` 10 minutes ahead. It then runs **one guarded statement** that locks and re-checks the request, as the reminder's send step does: a CTE that locks the request row, and for reschedule-outcome kinds the predecessor too, so Postgres waits for in-flight writes to them and re-evaluates the conditions against the committed rows under READ COMMITTED: `WITH req AS (SELECT r.id, r.ics_uid, r.manage_chain_id, r.profile_id, r.owner_user_id, r.ics_sequence, r.starts_at, r.ends_at, r.title_snapshot, r.location_snapshot, r.decline_reason, r.email, r.first_name, r.last_name, r.booker_locale, r.booker_timezone [, p.starts_at AS original_starts_at, p.ends_at AS original_ends_at, for reschedule-outcome kinds] FROM customer_booking_requests r [JOIN customer_booking_requests p ON p.id = r.previous_request_id, for reschedule-outcome kinds only] WHERE r.id = :requestId AND r.tenant_id = :tenantId AND r.organization_id = :organizationId AND r.anonymised_at IS NULL AND <the kind's state condition above> FOR SHARE OF r [, p]) UPDATE customer_booking_mail_outbox d SET attempts = d.attempts + 1, lease_expires_at = statement_timestamp() + interval '2 minutes' FROM req WHERE d.id = :id AND d.lease_owner = :token AND d.lease_expires_at > statement_timestamp() RETURNING d.id AS outbox_id, req.*`. Every e-mail uses the request's `ics_uid` (shared by the whole reschedule chain, so an accepted reschedule updates the same calendar entry, never a new one), `manage_chain_id` for the manage link (Manage tokens), and `profile_id` for the profile's title and timezone. **Recipients:** booker kinds go to the decrypted `email`, in the booker's locale; `owner_cancellation_notice` goes to the owner, in the **default locale** (defined below), whose address and display name the worker reads by `owner_user_id` with the customers module's existing `findInteractionUserInScope` (filtered by tenant, decrypted with the request's organization), and who is also the `replyTo` of booker e-mails; the owner's notice never goes to the booker's address. When the owner was deleted or has no address, the owner's notice is closed unsent and booker e-mails go out without `replyTo`. The owner's `email` and `name` are encrypted fields of `auth:user`, and `findOneWithDecryption` leaves them encrypted during a key-service outage, so the key-outage check below also covers them (`getEncryptedFieldNames('auth:user', tenantId, organizationId, { ignoreRuntimeHealth: true })`): the owner's notice, and any booker e-mail that needs the owner as `replyTo`, gives its attempt back instead of being sent to a ciphertext address. The decline e-mail includes the decrypted `decline_reason`; "your original time stays" shows `original_starts_at`/`original_ends_at`. The returned `title_snapshot`, `location_snapshot`, `decline_reason`, `email`, `first_name` and `last_name` are ciphertext in an encryption-enabled tenant, so the worker decrypts them with the tenant encryption service's `decryptEntityPayload` (entity `customers:customer_booking_request`, tenant and organization scoped, as `findWithDecryption` does) before building the e-mail. That method returns a value unchanged when its key is unavailable, so after decryption the worker treats a field as **not decrypted** only when the field is mapped for encryption for that tenant, read with `getEncryptedFieldNames(entityId, tenantId, organizationId, { ignoreRuntimeHealth: true })` (not `isEnabled()`, which also reports the key service's health and is therefore false during exactly the outage this check is for), the field is one the e-mail uses, its raw value has the platform's encrypted-value shape (`isEncryptedPayloadShape`, `packages/shared/src/lib/encryption/aes.ts`: `iv:ct:tag:v1` with exact IV and tag lengths), and decryption returned it unchanged; then the key is unavailable, so the worker sends nothing, **gives the attempt back** (as for a cap deferral), releases the lease and sets `send_after = statement_timestamp() + 10 min` (a write of `send_after`, so it bumps `send_version` and enqueues a delayed wake-up, as every such statement does), so a key-service outage delays e-mails but never uses up their attempts (the 72-hour close still bounds them). With encryption off for the tenant the check is skipped. During a key-service outage values may be stored as plain text, so a typed value that happens to have the encrypted-value shape could be mistaken for a missing key; that is rare, and it only delays the e-mail until the 72-hour close. The kind, stamped status and sequence are parameters taken from the lease statement's `RETURNING`. The statement autocommits, so its locks end with it and do not cover the send; a change that commits while the send is in flight is the remaining case (Risks). Zero rows means the e-mail no longer describes the booking, or the lease was lost; the worker cannot tell which, so it sends nothing and closes the row with `UPDATE … SET closed_at = statement_timestamp() WHERE id = :id AND lease_owner = :token AND lease_expires_at > statement_timestamp()`, which does nothing when the lease was lost (the job holding it decides). Otherwise, after the owner lookup (for `replyTo` and the owner's notice) and then the key-outage check above (on the request's and the owner's fields), it reserves a cap slot; a refused reservation moves `send_after` to the next local midnight, gives the attempt back and releases the lease. After a successful reservation it renews its lease in one more guarded statement of the same shape as the state check: `WITH req AS (SELECT r.id, r.ics_uid, r.manage_chain_id, r.profile_id, r.owner_user_id, r.ics_sequence, r.starts_at, r.ends_at, r.title_snapshot, r.location_snapshot, r.decline_reason, r.email, r.first_name, r.last_name, r.booker_locale, r.booker_timezone [, p.starts_at AS original_starts_at, p.ends_at AS original_ends_at, p.ics_sequence AS original_ics_sequence, for reschedule-outcome kinds] FROM customer_booking_requests r [JOIN customer_booking_requests p ON p.id = r.previous_request_id, for reschedule-outcome kinds] WHERE r.id = :requestId AND r.tenant_id = :tenantId AND r.organization_id = :organizationId AND r.anonymised_at IS NULL AND <the kind's mailState condition> FOR SHARE OF r [, p]) UPDATE customer_booking_mail_outbox d SET lease_expires_at = statement_timestamp() + interval '2 minutes' FROM req WHERE d.id = :id AND d.lease_owner = :token AND d.lease_expires_at > statement_timestamp() AND d.closed_at IS NULL RETURNING d.id AS outbox_id, req.*`. The outbox row's id is returned as `outbox_id`, because `req.*` also has an `id` (the request's) that would otherwise overwrite it in the returned row; every later statement binds its `:id` to `outbox_id` (the same value as the job payload's `outboxId`). **The e-mail is built from this final snapshot**, not from the first statement's values (only `owner_user_id`, `profile_id` and `manage_chain_id`, which never change, may come from the first; the booker's `first_name`/`last_name` are used only in the `owner_cancellation_notice`, escaped and truncated to 100 characters): the worker decrypts it again (with the same key-outage check; a value still encrypted at this point sends nothing and runs the same give-back statement as the first check, which gives the attempt back, writes `send_after`, bumps `send_version` and enqueues a delayed wake-up; the cap slot already reserved is not returned, which can only happen if the key becomes unavailable between the two decryptions) and renders the e-mail from it, so a move, title change or sequence change committed during the owner lookup or the cap reservation is always reflected, which matters for a `confirmation` because it is sent without a sequence match. When it returns no row, the worker sends nothing and runs the same lease-guarded close as the state check's zero-row path, so a cancel or other state change committed during a slow cap reservation closes the row instead of leaving it open (and a third attempt is never reported as a failure). When it returns a row, the worker decrypts and renders the e-mail from it within a **30-second preparation deadline** (decryption and rendering raced with `Promise.race` against a 30-second timer started when the final send guard returns; the deadline does not cover the pre-send claim or the send). Missing the deadline takes the **failed-send path**: nothing is sent, the attempt stays counted, and on the third attempt the worker closes the row, reports it and notifies the owner exactly as for a third failed send (No row waits forever); otherwise it releases its lease and `send_after` keeps the lease's `+ 10 minutes` with its delayed wake-up, so a slow key service or renderer is retried with the normal backoff and reaches the third-failure close, instead of retrying at once and spending a cap slot each time. Then, **immediately before calling the mail transport**, it runs the **pre-send claim**: `WITH req AS (SELECT r.id FROM customer_booking_requests r [JOIN customer_booking_requests p ON p.id = r.previous_request_id, for reschedule-outcome kinds] WHERE r.id = :requestId AND r.tenant_id = :tenantId AND r.organization_id = :organizationId AND r.anonymised_at IS NULL AND <the kind's mailState condition> AND r.ics_sequence = :snapshotIcsSequence [AND p.ics_sequence = :snapshotOriginalIcsSequence, for reschedule-outcome kinds] FOR SHARE OF r [, p]) UPDATE customer_booking_mail_outbox d SET lease_expires_at = statement_timestamp() + interval '2 minutes', unknown_pending = d.unknown_pending + 1 FROM req WHERE d.id = :id AND d.lease_owner = :token AND d.lease_expires_at > statement_timestamp() AND d.closed_at IS NULL AND d.sent_at IS NULL RETURNING d.id AS outbox_id`. It succeeds only while the worker still owns an unexpired lease, the request still satisfies the kind's condition (which pins its status to the stamped `request_status`), and the request (and, for reschedule outcomes, the original request whose time the e-mail shows) still has the `ics_sequence` of the rendered snapshot (a move or title change bumps `ics_sequence`), and it renews the lease to a full 2 minutes, so the transport call always starts inside a lease the worker owns, however long preparation or a process pause before the claim took. **When it returns no row, the worker never calls the transport.** The snapshot changed (or the lease was lost), so it runs the give-back guarded by its token and an unexpired lease (`attempts = attempts − 1`, `send_after = statement_timestamp()`, `send_version + 1`, lease released, an immediate wake-up enqueued), so the next attempt rebuilds the e-mail from a fresh snapshot; when that also returns no row, the lease was lost (another job or the tick took over) and the worker exits without changes. The cap slot already reserved is not returned. After a successful claim the worker calls the transport and **waits for it to settle**. No caller-side timer ends a send early: the platform `EmailTransport.send` (`packages/shared/src/lib/email/transport.ts`) has no cancellation contract, so a send cannot be stopped once started, and a timer that released the lease would only let a retry start while delivery may still be in progress. **Transport settlement rules** (both workers; the reminder applies them to its `reminder_*` columns with three differences: it keeps no `unknown_pending`/`notify_on_settle`, because it never sends `mail_failed`; it has no `send_version` and enqueues no wake-ups of its own, because the maintenance tick re-enqueues its due claims; and a late rejection after its third-attempt ceiling close is reported with `reportError` only, as its abandonment is, with no `mail_failed`):
     - **Lease heartbeat:** while the send is in flight, the worker renews its lease every 30 seconds (`UPDATE … SET lease_expires_at = statement_timestamp() + interval '2 minutes' WHERE id = :id AND lease_owner = :token AND closed_at IS NULL AND sent_at IS NULL`), so neither the tick nor another job can take the row while delivery may still be in progress. The heartbeat catches its own errors (a database error is reported with `reportError` and the next tick of the heartbeat tries again), treats a renewal that updates no row as "keep waiting for the send, stop renewing" (the row was sent by a late success elsewhere or closed), and its timer is always cleared when the send settles or the ceiling is reached, so a heartbeat can never surface as an unhandled rejection or outlive the send.
     - **Send ceiling:** 10 minutes after the **pre-send claim**, when the transport call starts (not the reminder's tick claim, which can be hours older after a deferral; a constant in `lib/booking/constants.ts`, overridable in tests) the heartbeat stops. The shared transport contract carries no timeout or cancellation, so the ceiling is the only bound the booking module sets. If the send is still pending, the outcome is **unknown**. The worker **ends its queue job** (so a hung send never holds the local strategy's single worker or an async concurrency slot beyond the ceiling) and leaves a detached handler on the transport promise that applies the success rule below if the send ever resolves, applies the settlement rules below (which decrement `unknown_pending`); on a **rejection** (late or not; the in-flight failure path runs the same check right after its decrement) it then runs `UPDATE … SET notify_on_settle = false WHERE id = :id AND notify_on_settle AND unknown_pending = 0 AND sent_at IS NULL AND closed_at IS NOT NULL RETURNING id` and, only when that returns the row, reports the failure once and notifies the owner (`customers.booking_request.mail_failed`), because a failure-type close happened and every send for that row is now known not to have delivered; a rejection while the row is open, or on a row closed as obsolete or ended, is otherwise ignored, and only one settlement can clear the flag, and catches its own database errors with `reportError`, so a late settlement can never surface as an unhandled rejection. It reports the unknown outcome once with `reportError` (code `customers.booking_mail_outcome_unknown`). The unresolved send is already recorded on the outbox row: the pre-send claim incremented `unknown_pending` in the same statement that started the send, and only its settlement decrements it, so the counter is right even if the process dies mid-send. On an attempt before the third it lets its lease expire and enqueues a wake-up for the row's current `send_version`, delayed until the lease's expiry (computed by the database), so a later attempt retries without depending on the maintenance tick; that is the at-least-once duplicate window. On the **third** attempt it closes the row itself (`UPDATE … SET closed_at = statement_timestamp(), notify_on_settle = (unknown_pending > 0) WHERE id = :id AND lease_owner = :token AND closed_at IS NULL AND sent_at IS NULL RETURNING id, unknown_pending`, and, like the third-failure close, it decides from that `RETURNING`: if the send already settled as a rejection before the close (so `unknown_pending = 0`), it reports the failure and notifies the owner once, because every send is known not to have delivered; the reminder sets `reminder_next_attempt_at = NULL` under its token and version guards) **without** `mail_failed`, because the e-mail may have been delivered. A closed row is never reported again by the tick or the reminder's abandonment statement. **Unresolved sends block failure notices:** a **failure-type close** (the worker's third-failure close, after its own send's settlement has decremented the counter; the tick's 72-hour or 3-attempt close; this ceiling close) of an outbox row whose `unknown_pending` is above zero reports the outcome as unknown with `reportError`, **never** sends `mail_failed`, and sets `notify_on_settle = true` in the same statement, because an earlier send may still be delivered. Closes that are not failures (an obsolete row, an ended meeting, a state check that no longer holds) never set it. The failure notice, if any, comes from the settlement that resolves the last unresolved send (below).
     - **Success**, whenever it arrives (even after the ceiling or after another job took the row): `UPDATE … SET sent_at = COALESCE(sent_at, statement_timestamp()), unknown_pending = greatest(unknown_pending - 1, 0), notify_on_settle = false, lease_owner = CASE WHEN lease_owner = :token THEN NULL ELSE lease_owner END, lease_expires_at = CASE WHEN lease_owner = :token THEN NULL ELSE lease_expires_at END WHERE id = :id`, deliberately **not** guarded by the lease (one statement: it records the delivery and settles the counter), because the mail was delivered whoever holds the row now. Every pre-send claim requires `sent_at IS NULL`, so once a late success is recorded no further send starts; a row the tick had meanwhile closed after its ceiling also gets its `sent_at`. If the worker process dies before a pending send settles, its detached handler is lost and `unknown_pending` stays above zero, so the row is closed as unknown and never notified as failed.
     - **Failure** (the transport rejects): first `UPDATE … SET unknown_pending = greatest(unknown_pending - 1, 0) WHERE id = :id` (not lease-guarded, so the counter settles whoever holds the row), then the failed-send path, guarded by the lease token; because a long send may have outlived the lease's own wake-up, the release also enqueues a wake-up for the current `send_version` delayed until `greatest(send_after, statement_timestamp())` (zero when `send_after` has passed) (with a lost lease nothing changes; the current holder decides). A rejection is caught, not rethrown, so neither queue strategy retries the job; the outbox owns the retry.

     Delivery is at least once.
     **No row waits forever:** when a send fails on its **third** attempt, the worker itself (after its own send's settlement has decremented `unknown_pending`) closes the row with `UPDATE … SET closed_at = statement_timestamp(), notify_on_settle = (unknown_pending > 0) WHERE id = :id AND lease_owner = :token AND closed_at IS NULL AND sent_at IS NULL RETURNING id, unknown_pending`, and only when a row comes back, after that commits: with `unknown_pending = 0` it reports once with `reportError` and notifies the owner (`customers.booking_request.mail_failed`; skipped, with the report kept, when the owner no longer exists); with `unknown_pending > 0` it reports the outcome as unknown and sends no notification (the settle handler notifies later if every unresolved send rejects), so a permanently failing e-mail is surfaced even without the scheduler. Each tick additionally runs `UPDATE … SET closed_at = statement_timestamp(), notify_on_settle = (unknown_pending > 0 AND NOT <ended> AND NOT <obsolete>) WHERE closed_at IS NULL AND sent_at IS NULL AND (lease_expires_at IS NULL OR lease_expires_at <= statement_timestamp()) AND (NOT EXISTS (SELECT 1 FROM customer_booking_requests r LEFT JOIN customer_booking_requests p ON p.id = r.previous_request_id WHERE r.id = request_id AND (CASE WHEN kind IN ('reschedule_declined','reschedule_expired') THEN p.ends_at ELSE r.ends_at END) > statement_timestamp()) OR created_at < statement_timestamp() − interval '72 hours' OR attempts >= 3) RETURNING id, unknown_pending, <which condition matched>` and decides what to report from that `RETURNING` only (never from an earlier read): rows whose meeting has ended (for `reschedule_declined`/`reschedule_expired` the **original** meeting, which is the one the e-mail is about; for the other kinds the request's own meeting or requested slot), or whose request no longer exists, close without a report, and the other rows (older than 72 hours, or left at 3 attempts by a worker that died before closing) are reported and notified once, except a row with `unknown_pending > 0` (returned by the same statement), which is reported as an unknown outcome without `mail_failed` (Transport settlement rules), and a row for which the tick's statement returns `obsolete = true`, computed as `NOT (<row-based mailState condition>)` over a `LEFT JOIN` of the request and its predecessor, i.e. a row whose request no longer satisfies its kind's condition (for example cancelled during a third attempt whose lease expired), which closes without a report because the e-mail is obsolete, not failed. The lease guard means the tick never closes a row whose send is in flight, and the `closed_at IS NULL` guards mean a row is closed, reported and notified at most once (`created_at < statement_timestamp() − 72 h`), so a cap that is exceeded day after day cannot build an unbounded backlog of late declines and cancellations (Risks). The maintenance job deletes sent and closed rows after 7 days.
   - **Default locale** (used wherever this spec says "default locale"): the platform `defaultLocale` from `@open-mercato/shared/lib/i18n/config`. Users have no stored language, and the tenant's `translations.supported_locales` setting is an unordered list with no default, so the booking module reads neither.
   - booker e-mails use the booker's `locale` (the owner's notice uses the default locale): the language the public page was shown in at submit (see UI/UX → Public page → Language), sent in the request body and validated against the app's enabled locales, falling back to `Accept-Language` and then the default locale.

7. **Manage link:** `{chainId}.{mac}`, an HMAC of a server secret and the booking, verified by re-deriving it and never stored (E-mails → Manage tokens). It opens `/calendar/{orgSlug}/{userSlug}/meetings/manage/{token}` with **Cancel** and **Reschedule** (the same slot picker, at `…/manage/{token}/reschedule`). The pages send `Referrer-Policy: no-referrer`, and the token path segment is redacted in request logs. A reschedule under approval mode creates a new `pending` request for the new time, while the old meeting stays confirmed until the decision (see Architecture → Reschedule).

### Alternatives considered
| Alternative | Why rejected |
|---|---|
| Fold into the bookings module §19 | That design is per service and per resource, with pricing and staff pools. This feature is per CRM user over CRM interactions. Coupling them would block a small feature on a large, unimplemented module. |
| New interaction status `pending` instead of a request entity | Changes a contract surface (`interactionStatusValues`, calendar rendering, every filter on status) and still needs somewhere to keep booker PII, tokens and expiry. A dedicated request entity is additive. |
| Create the person at request time | Spam requests would litter CRM with persons. Pending requests hold the details on the request row. The person is created only on confirmation. |
| Match the person by e-mail automatically | Lets anyone attach a meeting to a real customer by typing their address (impersonation). This was rejected explicitly in the Q&A. |
| Reuse `planner` availability (weekly/RRULE rules, date-specific rules, timezones) | Planner subjects are staff members and resources, not auth users, so a CRM user without a staff record would have no availability; `planner` is also an optional module, while booking lives in the always-present `customers` module. Booking needs only one weekly-hours list per profile (at most one range per day), kept in one `weekly_hours` jsonb column; there are no date overrides, and days off or breaks are CRM events that block time through busy time. If a later version wants staff-backed availability, an adapter can read planner rules into the same slot engine input. |
| User slug unique installation-wide (no org segment) | Answered: add the org slug. A per-organization user slug lets two organizations both have `/…/anna/meetings`. |

### Busy time ("everything that blocks the backend calendar")
Today, `GET /api/customers/interactions/conflicts` defines a blocked interval for a user as follows:
- an interaction with `author_user_id` or `owner_user_id` equal to the user,
- `status` not terminal (`TERMINAL_INTERACTION_STATUS_LIST`),
- `scheduled_at` set and `deleted_at` null,
- covering `[scheduled_at, scheduled_at + coalesce(duration_minutes, 30))`.

- visible to the **caller**: the route applies `applyEmailVisibilityFilter` (the viewer's own id, conversation grants from `listGrantsForViewer` and shared channels from `listSharedChannelIds`) before selecting conflicts. `userId` may name someone other than the caller, so this filter is an access boundary: without it a viewer could probe another user's private scheduled e-mails and read their titles through the route's title lookup.

This spec **extracts** the interval query (the `WHERE` and overlap part only) into `lib/booking/busy.ts` as `findBusyIntervals(em, options)`, where `options` is a discriminated union:

```ts
type FindBusyIntervalsOptions =
  | { mode: 'legacy'; tenantId: string; userId: string | null; from: Date; to: Date;
      organizationIds?: string[]; excludeId?: string; viewer: BusyViewer; limit?: number }
  | { mode: 'calendar'; tenantId: string; userId: string; from: Date; to: Date;
      organizationIds?: string[]; excludeInteractionIds?: string[]; timezone: string }
```

**First overlaps for a page of requests.** The pending list needs, per request, the first interaction of **that request's owner** overlapping its slot. `lib/booking/busy.ts` also exports `findFirstOverlaps(em, { tenantId, organizationIds, viewer, slots: [{ requestId, userId, from, to, excludeInteractionId? }] })` (at most 100 slots), built on the same `legacy` predicate builder: one SQL statement joins a `VALUES (request_id, user_id, slot_start, slot_end, exclude_interaction_id)` list to `customer_interactions` on `(author_user_id = user_id OR owner_user_id = user_id)` and `id IS DISTINCT FROM exclude_interaction_id`, the non-terminal status, `scheduled_at` not null, `deleted_at` null, the tenant and organization filter and the overlap test, applies `applyEmailVisibilityFilter` with the caller as `viewer` once in the `WHERE` clause (before `DISTINCT ON`, so a hidden earlier overlap can never mask a visible later one), and picks each request's first overlap with `DISTINCT ON (request_id) … ORDER BY request_id, scheduled_at, id`. The `VALUES` columns are cast (`::uuid`, `::timestamptz`), and an empty `organizationIds` list returns `[]` without a query, as the conflicts route does. The pending list passes a reschedule successor's predecessor `interaction_id` as `excludeInteractionId`, so the meeting being moved is never shown as the successor's overlap (a new time overlapping the current one is allowed, Architecture → Reschedule). `customer_interactions` has no index on `author_user_id`/`owner_user_id`, and `duration_minutes` has no maximum. So **Step 15 adds partial indexes** to `customer_interactions`, all `where deleted_at is null and scheduled_at is not null`: `(tenant_id, owner_user_id, scheduled_at)`, `(tenant_id, author_user_id, scheduled_at)` and, for long items, `(tenant_id, scheduled_at) where duration_minutes > 10080`. The overlap test then runs in two branches joined by `UNION ALL` before `DISTINCT ON`: ordinary items bounded below by `scheduled_at >= slot_start − interval '7 days'` (an index range scan per slot), and items longer than 7 days (`duration_minutes > 10080`, few rows, served by the small partial index), so a multi-week item such as a holiday that started long before the slot is still reported. The migration follows `sales/migrations/Migration20260916120000_sales_payment_allocation_order_idx.ts` exactly: a migration file containing only these statements, `isTransactional() => false`, and for each index `drop index concurrently if exists` followed by `create index concurrently` (not `IF NOT EXISTS`, which would succeed over an INVALID index left by a failed concurrent build); `down()` drops them `concurrently`. The indexes are also declared with `@Index` on `CustomerInteraction` and in the customers migration snapshot, so a later `yarn db:generate` does not propose dropping them. Indexes are additive under `BACKWARD_COMPATIBILITY.md`, and Step 15 records them in the dated section. Step 15 records an `EXPLAIN (ANALYZE)` of a 100-slot page in its PR, on a fixture where one owner has 100,000 past interactions and a few long items, showing an index range scan per slot. It returns `{ requestId, id, startsAt, endsAt }[]` and never titles (they stay encrypted; the caller decrypts them in one batch). A database-backed test (`packages/core/src/modules/customers/__tests__/booking-overlaps.integration.test.ts`, `OM_PG_INTEGRATION`, picked up by the extended `test:pg-integration` pattern) checks it returns the same first overlap per slot as calling `findBusyIntervals` in `legacy` mode once per slot, with fixtures whose start times differ (the legacy ordering has no tie-breaker) and with both short items and items longer than 7 days, so the two-branch query is checked against the legacy predicate.

The helper reads **interactions only**, returning `{ id, startsAt, endsAt, interactionType }[]` ordered by `scheduled_at` ascending (`interactionType` feeds the route's `type` field). In `legacy` mode it takes an optional `limit`, which the conflicts route passes as 10 so its SQL stays `ORDER BY scheduled_at LIMIT 10` exactly as today; the route keeps its title lookup and response shape.
- **`mode: 'legacy'`:** exactly today's predicate (author **or** owner, `organizationIds` and `excludeId` honoured) **including the e-mail visibility filter**. `viewer` is **required** in this mode (enforced by the type: `{ mode: 'legacy', viewer: { userId: string | null, sharedConversations, sharedChannelIds } }`), and the helper applies `applyEmailVisibilityFilter` with it **before** the user predicate, the ordering and the limit, exactly where the route applies it today. The route keeps resolving the viewer (`null` for API-key callers) and the grants as it does now and passes them in. The conflicts route switches to it as a pure refactor, so its behavior and access boundary do not change. Parity tests are pinned against the existing conflicts fixtures and add the access cases: another user's private scheduled e-mail is **not** returned (and its title is not leaked), a conversation share and a shared channel make it visible, and an API-key caller (`viewer.userId = null`) sees exactly what it sees today. Two more route behaviors are preserved: with `userId: null` (an API key without a bound user and no `userId` query) the author/owner predicate is **not** applied, exactly like the route's `if (checkUserId)`; and the route keeps its early `{ hasConflicts: false }` return for an empty `organizationIds` list before calling the helper. Both have parity cases. This refactor ships as its own PR (Step 2) before any booking code.
- **`mode: 'calendar'`:** used by booking only, server-side. It takes no `viewer`, because it reads the **owner's own** schedule to compute free time, and its result never leaves the booking code as ids or titles: the public API only returns free starts. So the owner's private scheduled e-mails do block availability, which is the intended meaning of "busy". It follows the CRM Calendar's own conflict rule (`lib/calendar/conflicts.ts`: **owner or participant**). It does **not** use `author_user_id`, so meetings an assistant creates for someone else do not consume the assistant's availability. On top of that:
  - **participants:** interactions whose `participants` jsonb contains `{ "userId": <user> }`;
  - **recurring series:** masters selected like the `recurrenceMasters=true` mode (start ≤ `to`, no end before `from`), expanded server-side with the existing `lib/calendar/recurrence.ts` expander. Its type imports from `components/calendar/types` move to `lib/calendar/types.ts`, with a re-export left behind. The expander currently falls back to the **process** timezone (`getDay()`/`getFullYear()`) for masters without `timezone`; busy-time expansion passes the **profile timezone** as the explicit fallback, and an added parameter keeps the client's current behavior unchanged;
  - **all-day items:** they block the whole day in the profile timezone (`lib/calendar/timezone.ts`, `date-fns-tz`; no new dependency). This is how an owner takes a day off or a lunch break, since profiles have no date overrides and one range per day.
- **Scope:** busy time covers **all organizations of the user within the tenant**, not just the profile's organization. A user with booking pages in two organizations, or with CRM meetings in another one, cannot be double-booked. This is a read of the owner's own records and leaks nothing across tenants.

The booking layer, `lib/booking/availability.ts` (`loadBusyTime(em, profile, range, { excludeInteractionIds?, excludeRequestIds? })`), then builds busy time as the union of:
- the user's `calendar`-mode intervals,
- `CustomerBookingRequest` rows for **any profile of the same user** with `status = 'pending'` and `expiresAt > now`,
- confirmed requests whose interaction is `done` but whose time is still in the future (calendar-mode busy skips terminal interactions, so marking a meeting completed early must not reopen its slot).

**Buffer:** a profile has one buffer, after meetings (`bufferAfter`). A slot `[s, e)` on a profile is free only when both hold:
- its padded range `[s, e + bufferAfter)` overlaps no busy interval (CRM meetings are not padded);
- the slot itself overlaps no **booking** of the same owner padded with the `bufferAfter` of the profile it was booked on (confirmed requests and pending requests with `expiresAt > now`; `loadBusyTime` returns these intervals with their own `padAfter`, which `computeFreeSlots` applies).

So after every booking there is at least the `bufferAfter` of the profile it was booked on, and before a new booking there is at least the new profile's `bufferAfter` ahead of the next busy item, whatever order they were booked in (the cal.com model, where existing bookings carry their event type's buffer). The slot list and the write gate use this one definition (`lib/booking/slots.ts`), so they cannot disagree.

### Keeping the booking in sync with the interaction
The owner can edit, reschedule, cancel or delete the created interaction from the CRM Calendar like any other. A subscriber on the interaction's existing CRUD/lifecycle events keeps the linked request (looked up via `interaction_id`) in sync:

| Owner action on the interaction | Request becomes | E-mail to booker |
|---|---|---|
| Cancelled (status `canceled`) or deleted | upcoming meetings: `cancelled`, `cancelled_by = owner`; a past meeting is left as it is (it happened) | cancellation, `METHOD:CANCEL` (upcoming only) |
| Time or duration changed | `confirmed`, with `starts_at`/`ends_at` updated, `ics_sequence + 1`, and, when `starts_at` moved, `starts_at_version + 1` and `starts_at_changed_at = now()` in the same statement (Proposed Solution → Reminder) | update, `METHOD:REQUEST`; none when the meeting had already ended before the edit and still has |
| Title or location changed | unchanged except the snapshots | update, `METHOD:REQUEST`, `SEQUENCE + 1`; none for a meeting that has ended |
| The person is deleted (cascade) | upcoming meetings only: `cancelled`, `cancelled_by = person_deleted`; past meetings are left as they are (they happened, and the 90-day anonymisation covers them) | cancellation, `METHOD:CANCEL` |
| Moved to another person | unchanged; `customer_entity_id` follows the interaction | none |
| Completed (status `done`, `customers.interaction.completed`) | unchanged (stays `confirmed`); `done` is the owner's record that the meeting happened | none |
| An interaction edit is undone (undo emits the CRUD `updated` event) | handled by the same snapshot diff as any edit | update if the booker-visible fields changed |

**Only confirmed bookings are synced:** the job ignores requests that are not `confirmed` (cancelled, declined, expired, pending), so it never changes the `ics_sequence` of a cancelled booking. **Ended and anonymised bookings:** the sync job skips **anonymised** rows entirely (`anonymised_at IS NOT NULL`: no snapshot write, no sequence, no e-mail), so the clean-up is never undone. For a meeting that has ended (`ends_at <= now()`, and the new time also in the past) it may update the snapshots but sends nothing and allocates no sequence.

A cancelled request is never re-opened, even if the interaction is later restored through undo. The restored interaction stays a normal CRM meeting; the owner can re-invite the booker manually. This matches the rule that ended requests are final (the slot may already be re-booked).

**Cancelling joins the booking transaction.** `interactions.cancel` currently forks its own EntityManager (`commands/interactions.ts`), unlike `interactions.create`/`update`, so it cannot be atomic with the request update. Step 13 makes it honour `ctx.transactionalEm` and `ctx.transactionLifetime` the same way in `prepare`, `execute` and `captureAfter` (`ctx.transactionalEm ?? fork()`, its effects through the deferral in Architecture → Public request write). Every booking path that cancels a meeting (owner cancel, booker cancel, undo of confirm) cancels the interaction, the request and any pending successor in one transaction.

**Pending reschedule cascade:** whenever a confirmed request is cancelled (by the booker, by the owner, by interaction cancel or delete, or by the person-delete cascade), its pending reschedule successor, if any, is set to `cancelled` (`cancelled_by = 'original_cancelled'`) **in the same transaction**, and no separate e-mail is sent for it. Such a row stays **visible** in the Meeting requests list with the badge "Cancelled: original cancelled".

**Sequence allocation:** a booking's `SEQUENCE` belongs to its `ics_uid` and is allocated, never copied. Every path that causes a `METHOD:REQUEST` or `METHOD:CANCEL` for a UID (the owner-sync job, booker reschedule, accept of a reschedule, every cancel) allocates the number in a transaction holding the same per-owner lock as public writes (`pg_advisory_xact_lock(hash(tenantId, userId))`) and allocates the number there with `UPDATE … SET ics_sequence = ics_sequence + 1 WHERE id = :liveRequestId RETURNING ics_sequence` on the request that currently holds the UID's interaction. Every path writes the returned value into its mail-outbox row in the same transaction, and the outbox worker sends with it. So owner edits and booking actions on one UID are serialised, each one sends a strictly higher number, and no path sends a value computed earlier (RFC 5546 §2.1.4: a higher SEQUENCE supersedes a lower one).

**Detecting changes:** interaction events carry ids and status only, so the request keeps snapshot columns (`starts_at`, `ends_at`, `title_snapshot`, `location_snapshot`). On each `customers.interaction.updated` (and the other lifecycle events in the table), the subscriber only enqueues a booking-owned job, `customers:booking-interaction-sync`, keyed by `interaction_id`, and never throws, as on the person-delete path; the job does the work under the per-owner lock, uses the standard queue retries (so a lock timeout is retried) and reports with `reportError` after the last attempt. The job loads the interaction and the request through the decryption helpers (tenant and organization scope) and diffs the decrypted values against the snapshots, writing new snapshots back through the encryption service; it sends an e-mail only when something the booker sees has changed.

**Person-delete cascade:** the person-delete command removes interactions with `nativeDelete` and emits no interaction events, so a booking-owned path cancels the bookings instead. It is deliberately simple and never reads audit-log states:
- **Subscriber:** a persistent subscriber on `customers.person.deleted` only enqueues a booking-owned job, `customers:booking-person-delete-cascade`, with `{ tenantId, organizationId, entityId }` (the event's `entityId`; its `id` is the person *profile* id, `commands/people.ts`) and `delayMs` of 2 minutes, roughly the undo-toast window. It never throws for control flow, so it never makes the events worker retry the other `customers.person.deleted` subscribers (`sales`, `customer_accounts`, webhooks, workflow triggers), which all run in the same queue job.
- **Job:** in one transaction it takes the per-owner lock (`pg_advisory_xact_lock`) of **every** owner with a confirmed request for that person, in ascending lock-key order (no deadlock between two cascades), then re-checks that the person is still deleted (no live `customer_entities` row for `entityId`). If the person exists again (the delete was undone, which is the common case for an undo within the delay), it does nothing. Otherwise it cancels each **upcoming** confirmed request with that `customer_entity_id` (`ends_at > now()`, `anonymised_at IS NULL`, and its interaction no longer exists, the same predicate as the backstop, so a meeting already moved to another person is never cancelled; past and anonymised rows are never touched or e-mailed, so a GDPR erasure months later sends nothing), with `cancelled_by = 'person_deleted'` and `cancelled_at = now()`, cascades to pending successors (`original_cancelled`), and commits, writing each booker's CANCEL into the mail outbox in that transaction and emitting `customers.booking_request.cancelled` per request after commit (E-mail safety: cancellation e-mails are written in the cancelling transaction). It uses the queue's standard retries (3 attempts, exponential backoff); a failure after the last attempt is reported with `reportError`. After commit, the job checks once more whether the person exists again; if it does (the accepted race below), it sends each affected owner `customers.booking_request.not_reinvited`, so somebody knows the bookers were told the meeting is off.
- **Backstop:** a hard delete leaves no record of when the person disappeared, so the maintenance job keeps one: on each tick, for upcoming confirmed requests whose `customer_entity_id` has no live row **and** whose interaction no longer exists (so a meeting already moved to another person, with the `customer_entity_id` sync lagging, is never cancelled), it sets `person_missing_since = now()` where it is null, and clears it where the person exists again. It cancels, the same way as the job, the requests whose `person_missing_since` is older than 10 minutes. So a tick inside the 2-minute delay only marks rows, and an undo resets the clock. That covers a lost or permanently failed cascade job and a crash in the middle of an undo.
- **Accepted risk:** an undo that commits while the job's transaction is open (after its re-check) is not blocked; the bookers then have a CANCEL for meetings that were restored. The window is the duration of one short transaction, two minutes after the delete; the cancellations stay final, consistent with "cancelled is final", the owners are notified by the job's after-commit check (best effort: a crash between the commit and that check loses the notice, and the backstop path sends none), and the restored meetings stay normal CRM meetings the owner can re-send.
Undoing a person delete restores the interactions silently (no interaction events). The booking requests stay `cancelled` and the bookers have their CANCEL; this is consistent with "cancelled is final". An `afterUndo` command interceptor on `customers.people.delete` counts the requests for that person with `cancelled_by = 'person_deleted'` and `cancelled_at` after the undone delete's log `createdAt` (so earlier booker or owner cancellations are not counted) and, when there are any, sends the undoing user an in-app notification, `customers.booking_request.not_reinvited`: "{n} booked meetings were cancelled and their bookers notified; they will not be re-invited automatically". Interceptor results have no channel for a non-blocking warning in the undo toast, so a notification is used instead; undo itself is never blocked.

**No loops:** booking commands run with `ctx.syncOrigin = 'customers.booking'`, which the interaction commands already copy into their event payloads (`commands/interactions.ts`). The subscriber ignores events with that origin. The interaction's `source` column is **not** used as a marker, because it persists and would hide later owner edits.

### Command context for public writes
Public writes follow the checkout public submit route (`checkout/api/pay/[slug]/submit/route.ts`), with one difference:
- `commandBus.execute` gets `auth: null` and `selectedOrganizationId = profile.organizationId`;
- `organizationScope: null`, exactly like checkout. Strict scope mode already accepts `null` together with `selectedOrganizationId` (`shared/lib/commands/scope.ts`);
- `syncOrigin = 'customers.booking'`.

With no auth, `normalizeAuthorUserId` leaves `author_user_id` null; `owner_user_id = profile.userId` is passed as normal input. No new actor fields are introduced: the action log shows the command with no user, and the request row records `source = 'public'`. Backend writes (accept, decline, link, cancel) run as the signed-in user, as usual.

**Undo:**
- **confirm:** undoing it cancels the interaction, sets the request to `cancelled` and writes the booker's CANCEL row into the mail outbox. The undo handler runs with the command bus's `atomicReplay: true`; its `stabilizeReplay` sets `lock_timeout` and takes the per-owner advisory lock (the CANCEL's `SEQUENCE` allocation needs it) before the bus claims the token, so the undo-token claim, the cancellation and its outbox row commit in one transaction (`bindReplayTransactionContext` gives the handler `transactionalEm` and `transactionLifetime`; the `cancelled` event goes out through `runAfterTransaction`), and a crash cannot consume the token without cancelling. The bus rejects a second undo of the same token. Undo is refused with `409 meeting_ended` once the meeting has ended, like owner cancel. The booker was told about the meeting, so they must be told it is gone;
- **accepting a reschedule:** not undoable (the meeting moved and the booker was e-mailed the new time). The owner can move it back from the calendar, and the sync sends an update;
- **link-person:** undoing it moves the interaction back and restores the soft-deleted person;
- **decline and cancel:** not undoable, because the booker's state would flip back without a matching e-mail. The owner can still book a new meeting manually.

**Action-log PII:** the command bus stores each command's full input as `commandPayload`, and `people.create` stores a `snapshotAfter` with names. So:
- the booker's e-mail and names are passed through the request row, never through a booking command's input, and every booking command's `captureBefore`/`captureAfter` snapshot is **ids and status only** (request id, status, `interaction_id`, `customer_entity_id`, `starts_at`, `ics_sequence`), so neither the command payload nor the snapshots carry PII;
- **undoable** booking commands (`confirm`, i.e. accept, and `link-person`) keep replay **enabled**: they supply an ids-only `redoInput` (`{ requestId, expectedUpdatedAt }`) and leave `replayable` unset, so the bus still issues an undo token (`CommandLogMetadata.redoInput`; `replayable: false` would clear it).;
- **non-undoable** booking commands (public `create` with its inline confirm, which runs with no user to undo it, `decline`, `cancel`, and `reschedule` including accepting a reschedule) use `replayable: false`, which is the intended effect: an audit entry without an undo token or payload;
- the auto-created person's own `people.create` log entry **does** keep the name and e-mail. That is standard CRM behavior for any person record, covered by the CRM's GDPR tooling and not by this feature's anonymisation (see Data Model → Retention).

### State transitions
All transitions live in `lib/booking/transitions.ts` and run as one conditional `UPDATE … SET status = :to, updated_at = now() WHERE id = :id AND status = :from [AND expires_at > now()] RETURNING *` inside the command's transaction:

| Transition | Guard |
|---|---|
| accept, decline | `status = 'pending' AND expires_at > now()`; the API's `expectedUpdatedAt` is checked as well |
| expire | `status = 'pending' AND expires_at <= now()` |
| cancel by the booker | `status IN ('pending','confirmed')` plus the caller's `expectedUpdatedAt`; also cancels a pending successor in the same transaction; a pending request gets no CANCEL e-mail (it was never invited) |
| cancel by the owner | `status = 'confirmed'` plus `expectedUpdatedAt`; a pending request is declined instead, so the owner never sends a CANCEL for an invitation that was never sent |
| reschedule (booker) | `status = 'confirmed'` plus the caller's `expectedUpdatedAt` |
| accept of a reschedule successor | the above, **plus** the predecessor still `confirmed` (checked under the owner lock) **and** its live interaction still current (Architecture → Reschedule → live-predecessor check); otherwise `409 original_booking_gone` and the successor is cancelled with `cancelled_by = 'original_cancelled'` |

Zero rows updated means the action lost the race: the API returns `409 request_state_changed`, and only the winner's e-mail is sent. For accept and decline, when the re-read row is `expired`, or still `pending` with `expires_at <= now()`, the code is `409 request_expired` instead, so the Meeting requests page can say "This request expired at {time}" rather than show the generic conflict bar. This replaces read-then-compare locking for these rows, so accept and expiry can no longer both commit.

**Optimistic locking on every edit or delete.** The status guard alone would accept a stale `confirmed` row after the owner moved the meeting or changed the person, so every write on a request also carries the version the user viewed:
- every read that feeds an action returns the request's `updatedAt`: the backend list and detail, and the public manage `GET`;
- every action sends it back as `expectedUpdatedAt`: accept, decline, link-person, owner cancel, and the public cancel and reschedule;
- the command checks it with `enforceCommandOptimisticLockWithGuards` (`resourceKind: 'customers.booking_request'`) on the request row, read under the per-owner lock, before the conditional transition;
- **the linked interaction is part of the version.** An ordinary CRM edit (`customers.interactions.update` from the calendar) commits the interaction first; the request row only catches up when the sync subscriber runs, which can be delayed. The request version alone would therefore still look current. So for a confirmed request:
  - reads that feed an action also return `interactionUpdatedAt` (the linked interaction's `updatedAt`), and the manage page and backend detail show the time, title and location **from the live interaction** (decrypted), not from the snapshots, so the booker sees an owner's move as soon as it commits;
  - actions on a confirmed request (owner cancel, link-person, public cancel and reschedule) send it back as `expectedInteractionUpdatedAt`. Accepting a pending reschedule successor has no interaction of its own to send a version for; it locks and checks the **predecessor's** live interaction instead (Architecture → Reschedule → live-predecessor check);
  - the booking command reads the interaction with `SELECT … FOR UPDATE` in its transaction and requires `updatedAt = expectedInteractionUpdatedAt`; otherwise it returns `409` and changes nothing. The row lock waits for an in-flight CRM write to commit, so the check sees its result. Ordinary interaction commands are unchanged: the interaction row they already update is the shared version boundary, and no extra lock is needed on their side;
  - nested interaction writes then run with `request: null`, so they do not pick up the HTTP request's version header; the check above already pinned the version the user viewed;
- a stale write returns the unified `409` conflict contract. The backend shows the standard conflict dialog; the public manage page shows "This booking was changed. Reload to see the latest details" with a **Reload** button.

### Reschedule
- **Busy time for a reschedule excludes the booking being moved:** `findBusyIntervals` in `calendar` mode takes `excludeInteractionIds`; the booking layer (`lib/booking/availability.ts`, which unions the helper's intervals with the request rows) takes `excludeRequestIds`, and the daily cap ignores the request being moved. So the booker's own meeting does not block overlapping new times or use up the cap.
- **Instant mode:** under the owner lock, the new `startsAt` is validated as an offered slot (with the exclusions above). The same request row is updated (`starts_at`, `ends_at`, snapshots, `starts_at_version + 1` and `starts_at_changed_at = now()` in the same statement, and `ics_sequence` allocated as in Architecture → Sequence allocation), the **same interaction** is moved through the interaction update command (with the booking `syncOrigin`); when that interaction is `done` (the owner completed it early), the same update also sets `status = 'planned'`, so the rescheduled meeting is open again rather than a completed meeting at a future time; and an update `METHOD:REQUEST` with the same UID is sent. The manage token stays the same.
- **Approval mode:** a new `pending` request is created, with `previous_request_id` pointing at the confirmed one, `source = 'reschedule'`, the same `ics_uid` and `customer_entity_id`, `ics_sequence` left at 0 (a placeholder; no number is reserved while pending), and `interaction_id` **null** until accept (so the sync lookup by `interaction_id` always finds exactly one row, the confirmed one). It holds the new slot and the old meeting stays confirmed. The old manage token **remains valid** and its page shows "Reschedule requested for {new time}, waiting for confirmation".
  - **Live-predecessor check (on accept):** the predecessor request's `status` lags an ordinary CRM cancel or delete of its interaction until the queued sync job runs, and the CRM commands do not take the per-owner lock. So, under the per-owner lock and **before** anything else in the acceptance transaction (before either request's status or `interaction_id` changes, the token moves, a sequence is allocated or an invitation is queued), the command reads the predecessor's interaction by `predecessor.interaction_id` with `SELECT … FOR UPDATE`, **without** the `deleted_at IS NULL` filter. The row lock waits for an in-flight CRM cancel or delete to commit, so the check sees its result. The original counts as **gone** when the predecessor is not `confirmed`, its `interaction_id` is null, the interaction row is missing (person-delete `nativeDelete`), `deleted_at` is set (`customers.interactions.delete`), or `status = 'canceled'` (`customers.interactions.cancel`); `done` is not gone (see the sync table); accepting reopens it (see **On accept** below). When the original is gone, the command commits only the successor's cancellation (`cancelled_by = 'original_cancelled'`, `cancelled_at = now()`, no e-mail of its own) and returns `409 original_booking_gone`; it does **not** move, update or revive the interaction, change the predecessor, move the token or send anything. The predecessor is left to the queued sync job (or the person-delete cascade), which cancels it and writes the booker's single CANCEL into the mail outbox when it runs; its successor cascade then finds the successor already cancelled and does nothing. This does not depend on the queue having run.
  - **On accept** (guarded: the predecessor is still `confirmed` and passes the live-predecessor check above): under the per-owner lock, the sequence is allocated **at acceptance** from the live predecessor (Architecture → Sequence allocation): `predecessor.ics_sequence + 1`, read and incremented in the same locked transaction, then written to the successor, together with `starts_at_version = 1` and `starts_at_changed_at = now()` (a new row with no reminder claim; the predecessor's open claim is closed by the sweep once it is `cancelled`). Owner edits made while the request was pending have already raised the predecessor's number, so the accept e-mail always supersedes them. The existing interaction is moved to the new time (same UID, the newly allocated SEQUENCE, update e-mail; a `done` interaction is reset to `planned` in the same update, as in instant mode), in the same locked transaction the predecessor's `interaction_id` is **first** set to null and **then** the successor takes it, as two explicit statements (`nativeUpdate` on the predecessor, then on the successor), never a single unit-of-work flush, whose statement order the ORM does not guarantee (the unique partial index on `interaction_id` is checked per statement, so assigning first would fail), so exactly one row ever holds an interaction; the predecessor becomes `cancelled` (`cancelled_by = 'superseded'`, no CANCEL e-mail), and the token is re-pointed: the accept takes its locks in a fixed order, the per-owner advisory lock, then the predecessor's **request** row (`SELECT … FOR UPDATE`), then the predecessor's interaction row (the live-predecessor check), and then moves the link in two explicit statements, first `manage_link_holder = false` on the predecessor and then `true` on the successor (the unique partial index on `(manage_chain_id) where manage_link_holder` is checked per statement, like `interaction_id`). The successor already carries the predecessor's `manage_chain_id`, so the link the booker holds keeps working and now manages the new time. Only one reschedule can be pending per booking (`409 reschedule_pending`).
  - **On decline or expiry:** the new request ends, the booker is e-mailed "your original time stays", and the old token keeps managing the original meeting.

### Link to existing person
The existing person-delete command (`commands/people.ts`) blocks only on deal links, then **hard-deletes** the person and cascades through comments, interactions, todos, tags, addresses and custom fields. It must not be used here. Instead:
- `lib/booking/dependents.ts` `countPersonDependents` counts, for the auto-created person:
  - same-module rows: interactions other than the one being moved, deal links, todo links, comments, activities, tag assignments, addresses, company links, e-mail conversation shares, custom-field values, and booking requests **outside this booking's own reschedule chain**. The chain is re-pointed to the target person in the same command, so a rescheduled booking does not pin the auto-created person;
  - cross-module references, each soft-optional (counted only when the module is enabled, through its public query surface): attachments, `sales` documents that reference the person as customer, and `customer_accounts` accounts linked to the person.
- The link command moves the interaction (`entity`) and the reschedule chain's `customer_entity_id`. When the count is zero, it soft-deletes the person and its profile through the module's CRUD side-effect helpers, running the standard soft-delete side effects (query index, search reindex and the CRUD `deleted` event) rather than a bare `deleted_at` write. The person-delete subscriber ignores events with the booking `syncOrigin`, so this does not cancel the booking just moved. Otherwise it keeps the person and returns `autoCreatedEntityKept: true`.
- Undo restores the interaction's previous person and clears `deleted_at`.

### Slot computation
For each local day `d` in the range (profile timezone):
1. Take the day's single window from `weeklyHours[weekday(d)]` (none means the day is off; a one-off day off is a CRM event, which blocks through busy time).
2. Walk the window from its start in steps of `slotDurationMinutes` (start times follow the meeting length; there is no separate interval); a slot is the range `[t, t + slotDurationMinutes)`.
3. Drop a slot that falls before `now + minNoticeMinutes`, after `today + horizonDays`, or whose padded range (slot plus buffers) overlaps busy time, or that overlaps an owner booking padded with its own profile's buffers (see Busy time).
4. When `maxBookingsPerDay` is reached (confirmed plus pending), drop the whole day.

The first-available scan goes forward in 31-day chunks up to the horizon and returns the **first free instant** (`firstAvailableAt`). The client converts it to the visitor's local date, so the preselected day is right in every timezone. The function is pure and unit-tested with fixed `now`. Timezone math uses `date-fns-tz` and `lib/calendar/timezone.ts`, which are already dependencies.

The same rules are the **write-side gate**, split in two so the API can tell the errors apart: `isOnGrid(profile, startsAt, now)` (working hours, the slot grid, notice and horizon: never offered → `422`) and `isFree(profile, busy, startsAt, { dayCount, excludeRequestIds? })` (busy time with buffers and the `maxBookingsPerDay` daily limit: offered but taken → `409`). `isOfferedSlot` is their conjunction, so `startsAt` is accepted only when it is exactly one of the computed starts.

### Public request write (race safety)
`POST …/requests`. Steps 1–2 run **before** the transaction, so a slow verification hook (for example an external CAPTCHA check) never holds a database connection. The transaction starts at step 3, and its first statement is `SET LOCAL lock_timeout` (`CUSTOMERS_BOOKING_LOCK_TIMEOUT_MS`, default 5 s; a booking-only setting, separate from the pool-wide opt-in `DB_LOCK_TIMEOUT_MS`), so every lock wait inside it is bounded. **Any** lock timeout inside a booking write (SQLSTATE 55P03; the existing `isTransientLockDbError` also matches other transient lock and connection errors, which are mapped the same way; the key row, the owner lock, the interaction `SELECT … FOR UPDATE`, or a row lock in a nested command) returns `503 booking_busy` with `Retry-After` on public routes and `409 request_state_changed` on backend routes:
1. Resolve the profile (it must be active). Apply the origin check, the fail-closed rate limiter (`503` without a limiter, `429` over a limit), `runMutationGuards` and the `customers.public-booking.verify-submission` hook.
2. Validate the payload with zod (`400`/`422` on invalid input).
3. **Idempotency:** insert a placeholder key row (`customer_booking_idempotency_keys`, `fingerprint`, `response = null`) with `ON CONFLICT (tenant_id, scope, key) DO NOTHING`. If the row already existed, a request with the same key is either finished or still in flight: the insert waits on the other transaction's row lock until it commits (bounded by the lock timeout; a timeout returns `503 booking_busy` with `Retry-After`), then this request reads the stored row and returns its stored response (same payload) or `422` (different payload); if the other request rolled back, the row is gone and this request proceeds as new. This runs before any availability check, so a retry never sees its own booking as busy.
4. Take `pg_advisory_xact_lock(hash(tenantId, userId))` to serialise writes per **owner**, so two profiles of the same user cannot race. The transaction's `lock_timeout` applies, so a burst against one owner cannot hold pooled connections indefinitely: on timeout the public routes return `503 booking_busy` (retryable, `Retry-After`) and backend routes return `409 request_state_changed`. The shared `withAdvisoryXactLock` helper is **not** used: it runs its body in its own forked transaction and forbids further forks, while the booking write must run inside the `withAtomicFlush` transaction whose lifetime the nested commands join. Every other use of the per-owner lock in this spec (sync subscriber, reschedule, accept) uses the same timeout.
5. **Offered:** `isOnGrid(profile, startsAt, now)` checks working hours, the slot grid, notice and horizon. Off-grid → `422 slot_not_offered`.
6. **Caps:** the daily creation cap (`CUSTOMERS_BOOKING_MAX_NEW_REQUESTS_PER_DAY`), the per-e-mail and per-IP open-request caps, and the owner-wide pending cap. Over any → `429` (`too_many_requests_today` or `too_many_open_requests`).
7. **Free:** load busy time with an overlap query over `[startsAt − 240 min, endsAt + bufferAfter + 240 min]` (240 minutes is the largest allowed buffer, so a padded booking from another profile is seen; the slots read widens its range edges the same way), and the count of bookings on the slot's profile-local day; `isFree(profile, busy, startsAt, { dayCount, excludeRequestIds? })` checks the padded slot against busy intervals and the `maxBookingsPerDay` daily limit, excluding a moved request. Busy or day full → `409 slot_taken`.
8. Insert the request; when approval is on, also write its `request_received` row into the mail outbox (`lib/booking/mailOutbox.ts`).
9. If approval is off, confirm inline: create the person and the interaction through the existing commands, with `ownerUserId = profile.userId` and the outer `ctx.transactionalEm`. The support must cover **every** phase the command has that reads or writes (`execute` and `captureAfter` for `people.create`, which has no `prepare`): each uses `ctx.transactionalEm ?? fork()`. A fork inside the uncommitted outer transaction cannot see the new rows, so `people.create`'s `captureAfter` (which forks today) would return an empty snapshot; `interactions.create` already does this in `captureAfter`. (`interactions.cancel` is covered under Architecture → Keeping the booking in sync.) `interactions.create` already honours it. `people.create` does **not** today (it forks its own EntityManager), so Step 8 adds `transactionalEm` support to `people.create` as an additive change (the same pattern as `interactions.create`). Without that change there is no single transaction, and a rollback would leave an orphan person.
10. When step 9 confirmed the booking, write its `confirmation` row into the mail outbox. Write the response (including `ics` when confirmed) into the idempotency row, in the same transaction, so the key and the booking commit or roll back together.
11. Commit.

**A rejected request leaves no key behind.** Every refusal after step 3 (`409`, `422`, `429`, `503`) rolls the whole transaction back, which also removes the placeholder key row. A retry with the same key is therefore evaluated again from scratch, and only a successful response is ever replayed.

The response precedence is therefore: rate limit and origin, validation, idempotent replay, `422 slot_not_offered`, `429` caps, `409 slot_taken`. Other public writes use the same building blocks:
- **manage-link writes** (`cancel`, `reschedule`) resolve the request by verifying the token and loading the chain's `manage_link_holder` row (Proposed Solution → Manage tokens), not by slug, and run the rate limiter, origin check and `runMutationGuards`, but **not** the `verify-submission` hook (holding the token is the credential; the bot check guards creation). Cancel works regardless of the profile's state and of every cap; no profile state or cap can refuse it. Reschedule needs an active profile: otherwise it returns `409 booking_unavailable`, the manage `GET` returns `canReschedule: false`, and the page offers Cancel only; Without a registered or healthy rate limiter, `cancel` still runs (the mac is the credential) and `reschedule` returns `503 booking_unavailable`.
- **approval-mode reschedule:** steps 1–4 (with the manage-link exceptions above), then the `cutoff_passed`, `reschedule_pending` and `expectedUpdatedAt`/`expectedInteractionUpdatedAt` checks (`409`), then steps 5–7 with the own-booking exclusions (a reschedule chain counts as **one** open booking: the moved request, and any pending successor whose predecessor is still confirmed, are left out of the per-e-mail and per-IP open-request counts, so a booker at the per-e-mail cap can reschedule each of their bookings), then insert the successor and write the idempotency response;
- **instant reschedule:** steps 1–4 (with the manage-link exceptions), the same `409` checks, steps 5 and 7 with the exclusions (no cap check, no new row), then move the request and the interaction and write the idempotency response;
- **cancel:** steps 1–4 (with the manage-link exceptions), the `cutoff_passed` and version checks, then the cancel transition (no slot or cap checks) and the idempotency response.

**Side effects run after commit.** `ctx.bulkImport` is **not** enough here: the bus only passes those flags to its queued CRUD flush (`dataEngine.flushOrmEntityChanges`), while the nested commands also emit directly. `people.create` calls `emitQueryIndexUpsertEvents` (`commands/shared.ts`, which emits `query_index.upsert_one` straight to the event bus), and `interactions.create` emits the parent `customers:customer_entity` index upsert and the `customers.next_interaction.updated` lifecycle event (`emitNextInteractionUpdatedEvent`). Each nested `execute` also flushes the CRUD queue as soon as it returns. All of that would escape before the outer transaction commits.

The framework already owns this boundary: `withAtomicFlush` begins a **transaction lifetime** (`shared/lib/commands/transaction-lifetime.ts`) and completes it with `committed` or `rolled_back` only after the real commit or rollback, and `onTransactionLifetimeComplete(em, cb)` registers work against it. The command bus already uses it for ambient atomic replay, where it defers the **entire** `runPostCommit()` phase (after-interceptors, cache invalidation and the CRUD flush). This spec reuses that mechanism instead of adding a parallel queue (Step 8, additive):
- **Bus:** `CommandBus.execute` generalises the ambient-replay branch to ordinary execution. When `ctx.transactionalEm` is inside a transaction **and** `ctx.transactionLifetime` is the token that owns it (`ownsTransactionLifetime`), the bus registers its whole `runPostCommit()` with `onTransactionLifetimeComplete` and runs it only on `committed`; on `rolled_back` it is skipped. Without an owned lifetime token (every existing caller) the bus runs `runPostCommit()` immediately, as today.
- **Direct emitters:** a shared helper `runAfterTransaction(ctx, effect)` (additive export next to the lifetime helpers) registers `effect` on the owned lifetime for `committed` only, or runs it immediately when there is none. `emitQueryIndexEvents` (upsert and delete paths, `customers/commands/shared.ts`) and `emitLifecycleEvent` (`customers/commands/interactions.ts`, which carries `customers.next_interaction.updated` and the interaction lifecycle events) go through it.
- **CRUD queue on rollback:** `emitCrudSideEffects` only marks changes on the request container's `dataEngine` queue, and with the deferral above nothing flushes that queue on rollback. **No `DataEngine` contract change** is needed: every booking write runs in its own request-scoped container (`createRequestContainer()`; public and backend routes already get one per request, and the maintenance worker creates one **per item**), so the unflushed entries of a rolled-back write are dropped with their container and can never be flushed by a later write.

The booking command opens its transaction with `withAtomicFlush(em, …, { transaction: true })`, reads the token with `getTransactionLifetime(em)`, and passes `transactionalEm`, `transactionLifetime` and the booking `syncOrigin` to the nested `people.create`, `interactions.create`, `interactions.update` and `interactions.cancel`. Then:
- **on commit:** each nested command's complete tail runs exactly once: after-interceptors, cache invalidation, the CRUD flush (person and interaction `created` events and index entries), the person `customers:customer_entity` index upsert, the parent projection upsert, and `customers.next_interaction.updated`;
- **on rollback:** none of it runs, and the container is discarded.

A failing completion callback is already reported through `reportError` by `completeTransactionLifetime` (`shared.transaction_completion_callback_failed`), and a maintenance-job pass re-indexes records of `source = 'public_booking'` that are missing from the index.

Booking e-mails are written to the mail outbox by the causing transaction and sent by the outbox worker; in-app notifications go out from event subscribers after commit; a mail failure never rolls back a booking. The `Idempotency-Key` header is required on every public write (`requests`, `cancel`, `reschedule`). Keys are stored **only** in `customer_booking_idempotency_keys` (`tenant_id`, `organization_id`, `scope`, `key`, `fingerprint`, `response`, `created_at`; unique `(tenant_id, scope, key)`; purged after 24 h by the maintenance job); the request row carries no idempotency columns. The same key and payload returns the stored response; the same key with a different payload returns `422`.

### Public profile resolution and the org slug
`organizations.slug` is unique per `(tenant_id, slug)`, not globally. Resolution reuses the portal's rule (`directory/api/get/organizations/lookup.ts`): a custom-domain host binds the tenant; otherwise the lookup is unscoped. The resolver then requires **exactly one** active profile matching `(org.slug = orgSlug, profile.slug = userSlug)`. Zero or several matches return 404, and several matches are also logged as `warn`. To keep that from happening, **enabling** a profile, or changing the slug of an already-active profile, is refused with `org_slug_ambiguous` when the organization has no slug or another tenant has an organization with the same slug and an active booking profile with the same user slug.

This guard is a **deliberate, documented cross-tenant read**: it returns only a boolean, never another tenant's data, and runs under `pg_advisory_xact_lock(hash(orgSlug, userSlug))`, so concurrent enables cannot both pass.

**Org slug changes:** a command interceptor on the directory module's organization update command (`commands/interceptors.ts`, the pattern `communication_channels` uses) runs whenever the slug changes and the organization has active booking profiles:
- **`beforeExecute`** checks the **requested** slug and **refuses** the change if it would collide, returning `{ ok: false, status: 409, body: { error: 'org_slug_ambiguous_for_booking' } }` (an explicit status per the Command Interceptor HTTP Status contract, so it is not a generic 500). It cannot see the final slug: `resolveUniqueSlug` is private to `directory/commands/organizations.ts` and only runs inside `execute`, where it may append a `-N` suffix on a same-tenant collision. No directory export is added for this;
- **`afterExecute`** reads the slug actually stored. If the suffix rule changed it and the stored slug is ambiguous, it does not refuse (the update has committed); it notifies each affected profile owner that their link is unavailable. `beforeExecute` runs outside the update's transaction, so both checks are advisory. The authoritative check is at resolution time (exactly-one match, else 404 plus a `warn` log and an owner notification);
- the same guard runs on `beforeUndo` of an organization update, which would restore an old slug;
- otherwise it lets the change through and notifies each profile owner that their link changed.

Old links return 404; manage links keep working because they are keyed by token. A redirect from old slugs is out of scope.

### Cross-module boundaries
- Owner identity: `userId` is an FK id to `auth` users, with no ORM relation. The auth `User` has no avatar, active flag or timezone. The public page shows the display name (falling back to the e-mail's local part) and **initials** in the avatar. An owner counts as "active" when the user has `deleted_at IS NULL` and still has access to the profile's organization; otherwise the page returns 404.
- Organization slug: read through `directory` as the portal does.
- E-mail: `@open-mercato/shared/lib/email/send`. Notifications go through the `notifications` module's typed notifications (`customers/notifications.ts`).
- Scheduler: soft-optional, **registered in Phase 1** as one **system-scoped** schedule whose id is `stableScheduleUuid('customers:booking-maintenance')` (the scheduler's primary key is a uuid; `stableScheduleUuid` is a private helper copied per module, so the customers module copies the one in `cart/lib/scheduling.ts` rather than importing it); the worker iterates over tenants itself. Registration happens in **two** places, because `seedDefaults` runs only when a tenant is created: `setup.ts` `seedDefaults` covers new installs, and a `customers.register-booking-maintenance-schedule` upgrade action (`configs/lib/upgrade-actions.ts`, the same pattern as `cart.register-sweeper-schedules` and `promotions.register-code-reservation-sweep-schedule`) covers existing installs that upgrade into the feature. Upgrade actions run only when an admin triggers them (`POST /api/configs/upgrade-actions`, `configs.manage`, per tenant and organization), so until then the schedule can be missing: the booking settings page and the Meeting requests page show a warning when the schedule is not active.

The pages cannot read the scheduler themselves (employees have no scheduler access), so the server computes `maintenanceSchedule: 'active' | 'missing' | 'inactive' | null` and returns it from `GET /api/customers/booking-profile` and `GET /api/customers/booking-requests/counts`:
- `missing`: no schedule row. Warning: "Booking maintenance is not scheduled: reminders, expiry e-mails and the 90-day data clean-up will not run. Ask an administrator to run the pending upgrade action.";
- `inactive`: the row exists but an admin disabled or deleted it. Warning: "Booking maintenance is disabled: reminders, expiry e-mails and the 90-day data clean-up will not run. Ask an administrator to enable or restore the Booking maintenance schedule in Scheduler." The upgrade action cannot fix this: registration omits `isEnabled` (so `register` keeps an admin's choice; the cart action passes `isEnabled: true`, this one deliberately does not) and does not clear `deletedAt`;
- `active`: no warning;
- `null`: the scheduler module is absent. Warning: "The scheduler module is not installed: reminders, expiry e-mails and the 90-day data clean-up run only when an administrator runs `mercato customers booking-maintenance`." (expiry itself is still derived on read).

The state comes from a new additive `schedulerService.isActive(id)` (`isEnabled = true AND deletedAt IS NULL`) together with the existing `exists(id)`, which counts disabled and soft-deleted rows. A `schedulerService` override that lacks `isActive` falls back to `exists()` alone: `missing` when there is no row, otherwise `active`. Such an override cannot report a disabled schedule, so the `inactive` warning needs `isActive`; the built-in service gains it in the same step.

The upgrade action declares `requiredModules: ['scheduler']`, so it is hidden on installs without the scheduler. Like the cart and promotions actions, it declares its `version` and the i18n `messageKey`/`ctaKey`/`successKey`/`loadingKey`. Both are idempotent on the stable id. The upgrade action is listed in UPGRADE_NOTES. When `schedulerService` is not registered, expiry still works at read time (pending blocks only while `expiresAt > now`, and lists show `expired` from the derived state); the job only makes the status change and the "expired" e-mail happen. Anonymisation then needs the CLI to be run by hand.

    { field: 'last_name' },

**Provisioning:** tenant encryption maps are seeded only at tenant creation, so a new map entry never reaches existing tenants by itself, and without a persisted rule `encryptEntityPayload` would write the first booking in plaintext with `email_hash` empty. So:
- **new tenants and organizations** get the entry through the existing seeding at tenant creation;
- **existing tenants** get it from a forward-only, idempotent customers migration that runs `buildEncryptionMapBackfillSql(bookingRequestEncryptionMap)` (`shared/lib/encryption/migration-backfill.ts`), with an empty `down()` as the helper requires. It inserts the entry for every (tenant, organization) scope with active maps that lacks it, and appends missing field rules to existing rows. Scopes with encryption disabled are skipped. The migration ships in Step 1, the same release as the tables, so the map is in place before public writes exist (Step 8);
- **operator recovery only:** `yarn mercato entities seed-encryption --tenant <uuid> [--org <uuid>]` re-seeds one scope. It is not part of the upgrade path.

**Foreign keys:** only `profile_id` is a real database FK. `interaction_id`, `customer_entity_id` and `previous_request_id` are plain uuid columns, the FK-id-plus-snapshot pattern used for cross-aggregate links. The existing person-delete command hard-deletes the person and its interactions with `nativeDelete`, and every FK option would break something: `NO ACTION` makes person delete fail (a behavior change on an existing command), `SET NULL` erases the `customer_entity_id` the `customers.person.deleted` subscriber matches on (bookers never get their CANCEL), and `CASCADE` deletes the requests before the subscriber runs. Readers treat a dangling id as "gone".

Plus a small table, `customer_booking_idempotency_keys`, for public-write idempotency (see Architecture → Public request write).

Plus the mail outbox, `customer_booking_mail_outbox` (Proposed Solution → E-mail safety): `id`, `tenant_id`, `organization_id`, `profile_id` (FK), `request_id` (plain uuid), `kind` text, `request_status` text, `ics_sequence` integer (the state the e-mail describes, from the causing transaction's `RETURNING`), `send_after` timestamptz, `unknown_pending` smallint not null default 0 (sends started and not yet settled: incremented by the pre-send claim, decremented by every settlement; a failure-type close while it is above zero sends no `mail_failed`), `notify_on_settle` boolean not null default false (set by a failure-type close while sends are unresolved; the rejection that resolves the last one clears it and notifies once), `send_version` integer not null default 1 (incremented by every statement that writes `send_after`; the wake-up job's version key), `attempts` smallint default 0, `lease_owner` uuid null, `lease_expires_at` timestamptz null, `sent_at` timestamptz null, `closed_at` timestamptz null, `created_at`. Unique `(request_id, kind, request_status, ics_sequence)`; index `(send_after) where sent_at is null and closed_at is null`; index `(created_at) where sent_at is null and closed_at is null` for the 72-hour close. It holds ids and states only, no PII, so it needs no encryption entry; rows are deleted 7 days after `sent_at` or `closed_at`, and all rows of a request are deleted when the request is anonymised.

**Retention and PII placement:** booker PII is kept out of every place the module does not control:
- **titles:** created interactions are titled with the profile title ("Meet with Anna"), never the booker's name; the booker is visible through the linked person;
- **events and notifications:** event payloads carry ids, `status`, `icsSequence` and `cancelledBy` only; notification texts say "New meeting request for {date time}" and resolve the name only when rendered for an authorised viewer;
- **audit log:** the platform action log stores command payloads and snapshots. Booking commands therefore use ids-only inputs (a redacted `redoInput` where undo is kept, `replayable: false` where it is not) and ids-only snapshots (Architecture → Command context), so their log entries never hold the e-mail or names. The auto-created person's own creation entry does hold them (standard CRM behavior).

Declined, expired and cancelled requests, and confirmed requests whose meeting ended, are anonymised 90 days later by the maintenance job (Phase 1):
- e-mail and names are replaced with a fixed marker (written through the encryption service like any other value), and `booker_message`, `decline_reason`, `title_snapshot` and `location_snapshot` are cleared;
- `email_hash` and `client_ip_hash` are cleared, `manage_link_holder` is set to false (so every link to the booking stops working), the request's mail-outbox rows are deleted, and `anonymised_at` is set.

**Not covered:** the person auto-created on confirmation is a normal CRM record and follows the CRM's retention and GDPR tooling, not this job.

Without the scheduler, the job can be run by hand with the CLI command `mercato customers booking-maintenance`. Confirmed requests whose meeting ended more than 90 days ago are anonymised the same way, because the person record holds the CRM copy. Interactions and persons follow the CRM's normal retention.

## 📝 API Contracts
Every handler exports `openApi`. Public routes declare `requireAuth: false`; all public writes go through commands.

### Public (no auth)
**Abuse controls** on the write routes (`requests`, `cancel`, `reschedule`):
- **Client IP:** resolved with the platform's `getClientIp`, which needs `RATE_LIMIT_TRUST_PROXY_DEPTH` set to the number of proxies in front of the app (it defaults to 0). Booking setup documents that this is **required** behind a proxy or load balancer. When the IP cannot be resolved, every **per-IP** limit below is **skipped**, never applied to a shared bucket, so visitors are never pooled into one lockout. The per-profile and per-e-mail limits still apply.
- **Rate limit** per resolved IP and per profile for the booking form and slot reads, through a module-local wrapper over the platform rate limiter; manage-link reads and writes use their own buckets (per IP, and per chain id after the mac verifies; Proposed Solution → Manage tokens), so booking-form spam on a profile never blocks a booker's cancel. Unlike checkout's wrapper, which lets requests through when the limiter is not registered, the booking wrapper is **fail-closed on writes**: with no rate limiter registered, public `POST`s return `503 booking_unavailable`, except the manage-link `cancel`, which still runs; reads stay available.
- **IP-independent creation cap:** checked **only** on writes that insert a request row: `POST …/requests` and an approval-mode reschedule (which creates a successor). Cancel and instant reschedule are never refused by it, so a booker can always cancel even when an attacker has exhausted the owner's quota. At most `CUSTOMERS_BOOKING_MAX_NEW_REQUESTS_PER_DAY` new requests per profile in any rolling 24 h (default 20, allowed 1–200; a system setting, not a per-user one, so abuse protection is an operator decision), counted on `created_at` under the per-owner lock, over every row created in the window whatever its status, so a book-then-cancel loop through the manage link cannot get around it. This is the bound that holds in the **default deployment**: `RATE_LIMIT_TRUST_PROXY_DEPTH` defaults to 0, so `getClientIp` returns `null` and every per-IP control below is skipped. Without it, a script rotating e-mail addresses could fill the whole horizon in instant mode, where nothing is pending. Over the cap: `429 too_many_requests_today`, and the owner is notified once per day (`customers.booking_request.cap_reached` with `cap: 'creation'`). The trade-off is that an attacker can exhaust one owner's daily quota, but cannot fill the calendar or create unbounded persons and e-mails. Per-IP protection being off (no trusted proxy depth configured) is an operator concern: the deployment documentation states it, and the app logs one `warn` at startup; the user's settings page does not show it.
- **Outstanding-request caps:**
  - at most 2 open (pending or future confirmed) requests per `email_hash` per owner; a reschedule chain (a confirmed request and its pending successor) counts once;
  - at most 3 open requests per `client_ip_hash` per owner (skipped when the IP is unknown);
  - the owner-wide pending cap `maxBookingsPerDay == null ? 10 : max(10, 2 × maxBookingsPerDay)` (10 when meetings per day are unlimited) counts at most 3 requests per `client_ip_hash`, and requests with an unknown IP count individually. So one resolved source cannot fill it, and unresolved traffic is still bounded by the cap itself.

  Over a cap, the route returns `429 too_many_open_requests`. The owner is notified when the owner-wide cap is hit (`cap_reached` with `cap: 'pending'`), so they can review the pending list.

  A `429` rolls back the booking transaction, so `cap_reached` (creation and pending) is emitted **after the rollback**, outside that transaction; its once-per-day dedupe check runs there as well.
- **Outbound mail cap:** see Proposed Solution → E-mail safety.
- **Bot check:** a server-side verification hook, `customers.public-booking.verify-submission` (DI-overridable, default no-op), plus the client form extension point `customers.public-booking.form`, where the matching CAPTCHA widget renders. A CAPTCHA provider plugs into both in v1 without code changes here.
- **Origin check** against `CUSTOMERS_BOOKING_ALLOWED_ORIGINS`, falling back to `APP_URL`/`NEXT_PUBLIC_APP_URL`. This is CSRF hygiene only, not abuse protection, and is applied on POST only.

### ACL (`acl.ts`, additive)
- `customers.booking.manage_own`: **no** dependency on `customers.interactions.manage`. It authorises only the caller's own booking profile and the requests and meetings that profile created. It is added to `defaultRoleFeatures` for `admin` (already covered by `customers.*`) and `employee`. The `employee` role does **not** gain `customers.interactions.manage`, so the existing grant boundary is unchanged.
- **Owner scope is enforced in the booking commands**, not by the feature alone: every backend booking command loads the request under the per-owner lock and requires `request.owner_user_id = auth.sub`, unless the caller has `customers.booking.manage` (then organization scope applies). Otherwise it returns 404, the same as an unknown id. The nested interaction commands are invoked only on the request's own `interaction_id`, so a booking action can never reach another interaction.
- **Effect for owners without `interactions.manage`:** they handle booking meetings through the booking actions (accept, decline, link person, cancel, from the Meeting requests page or a pending block in the calendar). Editing a booking meeting directly in the CRM Calendar still needs `customers.interactions.manage`, exactly as for any other interaction; when an owner who has it edits the meeting there, the sync subscriber informs the booker.
- `customers.booking.manage`: `admin` only (via `customers.*`).

Existing tenants pick these up with `yarn mercato auth sync-role-acls`, which is noted in UPGRADE_NOTES.

### Events (`events.ts`, additive)
Booking lifecycle event payloads carry ids plus `status`, `icsSequence` and `cancelledBy` (null unless cancelled) (no PII), for notification, webhook and workflow consumers; e-mails do not depend on them (the mail outbox is stamped by the causing transaction, Proposed Solution → E-mail safety). `events.ts` declares a `payloadSchema` for them, as the existing customers events do (for example `dealClosurePayloadSchema`); that schema is descriptive metadata (workflow editor, events API), so each step that emits a booking event asserts the **emitted** payload in its tests: Step 8 (`created`, `confirmed`), Step 11 (`cancelled` from the sync job and the person-delete cascade), Step 13 (`confirmed`, `declined`, `cancelled`), Step 14 (`expired`), Step 18 (`cancelled` by the booker) and Step 19 (`rescheduled`, `cancelled` with `superseded`).
`customers.booking_request.created`, `.confirmed`, `.declined`, `.expired`, `.cancelled`, `.rescheduled`, `.person_linked`. Payload: ids plus `status`, `icsSequence` and `cancelledBy` (no PII).

### Notifications (additive)
To the owner:
- `customers.booking_request.pending`, with an **Open request** `href` action to the Meeting requests page with the request preselected. It has no inline Accept/Decline: notification `commandId` actions send only `{ id, …payload }` and cannot carry `expectedUpdatedAt`, and an accept may need the overlap dialog,
- `customers.booking_request.confirmed` (instant booking),
- `customers.booking_request.cancelled`,
- `customers.booking_request.mail_failed`, with a `kind` field (the mail-outbox kind) and one text per kind, sent to the owner when the worker closes an outbox row after its third failed send, or when the tick closes a row after 72 hours or one left at 3 attempts by a crashed worker, in both cases only when no send for that row is still unresolved (`unknown_pending = 0`), or by the detached settle handler when the rejection of the last unresolved send follows such a close (`notify_on_settle`); never for a row closed as obsolete (its booking no longer matches the e-mail, for example cancelled) or ended (not sent when the owner no longer exists); no booker name in the text;
- `customers.booking_request.cap_reached`, with a `cap` field (`creation` | `pending` | `mail`) and one text per value: the daily creation cap was hit, the owner-wide pending cap was hit, or booking e-mails were held until the next local midnight by the mail cap (the mail outbox, and the reminder's own deferral); sent at most once per cap per day: the sender checks for an existing `cap_reached` notification for the same recipient with the same `(profileId, cap, local date in the profile timezone)` key in its payload before creating one,
- `customers.booking_profile.link_changed` (the organization slug changed).

To the acting user:
- `customers.booking_request.not_reinvited` (to the user who undid a person delete that had cancelled booked meetings).

Notification texts carry the date and time only; the booker's name is resolved at render time.

## 📝 UI/UX

### Public page `/calendar/{orgSlug}/{userSlug}/meetings`
Chrome-less: no backend menus, headers or portal nav. It uses the same `@open-mercato/ui` primitives and DS tokens as backend pages (Card, Button, Input, Calendar/day-picker, Badge, Spinner).
- **Header card:** owner initials avatar, owner name and organization name on two separate lines, title, description, a clock icon with "{n} min", the location **only when the owner entered one** (no video link is promised or generated), and the confirmation mode ("Instant confirmation", or, when approval is on, "{first name} confirms within 24 hours").
- **Layout:** three columns: header card, then the month calendar, then the slot list.
- **Calendar and slots:** in the month calendar, available days carry a tint **and a dot** (availability never depends on colour alone), unavailable days are disabled, and today has an outline ring with `aria-current="date"`; days of the adjacent months fill the first and last rows. A legend under the grid explains the dot and the ring. Prev/next month is limited to the horizon. The slot column shows the selected day's heading, then the slots stacked vertically as full-width buttons. Below the `lg` breakpoint (1024px) the columns stack (mobile-first).
- **Timezone and time format:** under the calendar, a timezone switcher (default: the browser timezone) and a **12h / 24h** segmented switch. The format defaults to the visitor's locale (`Intl.DateTimeFormat(locale, { hour: 'numeric' }).resolvedOptions().hourCycle`: 24-hour for `en-GB`, `pl`, `de`; 12-hour for `en-US`) and the choice is remembered in the browser. It applies to the slot list, the summaries and the result card.
- **Language:** the page renders in the visitor's browser language (`Accept-Language`, matched against the app's enabled locales) and otherwise in the default locale (Proposed Solution → E-mail safety). The footer, next to "Powered by Open Mercato", has a language select; changing it re-renders the page and sets a locale cookie. The language in use at submit is sent as `locale` and becomes the booker's e-mail language.
- **Initial state:** the day selected is the visitor-local date of `firstAvailableAt`. With no availability at all, the slot column shows an empty state, "No times available in the next {horizon} days", and every day is disabled (navigation still works).
- **Unavailable page:** an unknown slug, a disabled profile, an inactive owner and an ambiguous link all render the same 404 card, "This booking page isn't available. The link may be mistyped, or the page was turned off.", with no owner details.
- **Slot picked:** the card switches to a details step. The left column keeps the header with the chosen date, start and end time, timezone and location (when set), plus a **Back** button. The right column holds the form: e-mail, first name, last name, an optional "What would you like to talk about?" textarea (≤ 500 characters), the consent checkbox (**unticked by default**; privacy text from `content`), and **Book meeting** (or **Request meeting** when approval is on). Back returns to the slots with the selected day kept.
- **Result:** a centred card showing one of two outcomes:
  - **confirmed:** "You're booked", the invite e-mail address, a meeting summary, an **Add to calendar (.ics)** download built from the `ics` field of the response, the reminder line "We'll e-mail you a reminder 24 hours before the meeting" (only when the meeting is more than 24 hours away), and the change hint: Phase 1 says "Need to change it? Reply to the invite e-mail" (the reply goes to the owner), and Phase 3 says "To change it, use the link in your e-mail";
  - **pending:** "Request sent", {name} will confirm by {expiresAt}, an "Awaiting confirmation" badge, and a note that the time is held until then and released if not confirmed.
- **Errors:**
  - **validation:** after the first submit, each invalid field shows its error underneath ("Enter a full e-mail address, like name@example.com", "Enter your last name", "Tick the box to send your request"), the first invalid field gets focus, and a summary is announced through `aria-live`; errors clear as fields are fixed;
  - **`409 slot_taken` and `422 slot_not_offered`:** back to the slot list with a warning banner, "That time was just taken. Pick another time. Your details are kept.", and refreshed slots;
  - **`429`:** an error alert above the submit button, "Too many requests right now. Try again in a few minutes.";
  - **network or `5xx`:** "Your request wasn't sent. Check your connection and try again."
- **Accessibility:** the calendar has full keyboard navigation (arrow keys and Enter), each slot list is a `role="listbox"` per day, labels are tied to inputs, invalid fields carry `aria-invalid` and `aria-describedby`, and form errors are announced through `aria-live`.

## 📝 Edge Cases & Failure Scenarios
| Scenario | Behavior |
|---|---|
| Two visitors submit the same slot at the same time | The per-owner advisory lock plus the offered-slot recheck: the first gets 201, the second gets 409 `slot_taken` and the UI refreshes slots |
| The owner adds a CRM meeting over a pending request's time | Allowed (the backend calendar shows the conflict badge). Accepting later warns "conflicts with {title}" but may proceed |
| The approval deadline passes | Read paths treat the request as expired immediately. The job sets `expired` and e-mails the booker within ≤ 5 min; without the scheduler, status is derived on read |
| The deadline is after the slot start | `expiresAt` is capped at `startsAt` |
| The profile is disabled or the slug changed while a booking flow is open | Submit returns 404 and the page shows "This booking page is no longer available". Existing bookings and manage links keep working (keyed by token, not slug); on a disabled profile the manage page offers Cancel only |
| The owner is deleted or loses access to the organization | Profile resolution requires `deleted_at IS NULL` and organization access; the public page returns 404. Pending requests expire normally |
| A crafted request for a time that was never offered (03:17, a weekend, inside notice, past the horizon, off-grid) | `422 slot_not_offered`; nothing is written |
| Accept and expiry (or two accepts) at the same moment | The conditional update lets exactly one win; the loser gets `409 request_state_changed`, and only one e-mail is sent |
| The person is deleted while bookings point at it | The `customers.person.deleted` subscriber enqueues the delayed cascade job, which cancels the upcoming confirmed requests and writes the bookers' CANCEL e-mails into the mail outbox in the same transaction, unless the delete was undone first; the maintenance job is the backstop |
| E-mail send fails | The booking stays committed; its e-mail row stays in the mail outbox and is retried by the backoff; after the third failed attempt the worker closes it (or the tick after 72 hours; an obsolete row, whose booking no longer matches the e-mail, is closed without a report or notification), reports it through `reportError`, and sends the owner the `customers.booking_request.mail_failed` notification with a text per e-mail kind (for example "The confirmation e-mail to the booker could not be sent. Contact them directly.") |
| A DST transition on a slot day | Slots are generated in the profile timezone over wall-clock windows; a non-existent local time is skipped and an ambiguous one takes the first occurrence. Unit-tested for Europe/Warsaw and America/New_York |
| Visitor and profile timezones differ by a date line | The calendar widget marks days by the **visitor's** local date of each slot. The slots API returns instants, and the client groups them |
| The booker cancels after the cutoff | 409 `cutoff_passed`; the page says "reply to the invite e-mail" (the reply goes to the owner) |
| A manage token after a reschedule | Instant mode: the same token. Approval mode: the old token stays valid while the new request is pending, moves to the new request on accept, and keeps managing the original meeting on decline or expiry |
| A reschedule under approval | See Architecture → Reschedule: the existing interaction is moved on accept (same UID, higher SEQUENCE, no CANCEL), and the original stays on decline or expiry |
| A second reschedule while one is pending | `409 reschedule_pending` |
| The owner needs a day off or a lunch break | No date overrides or second ranges: the owner adds a CRM event (all-day for a day off), which blocks those times through busy time |
| The owner keeps meetings in Google or Outlook | Not checked (no external calendar sync); the settings page says so. Bookings can collide with those meetings unless the owner mirrors them as CRM events or narrows working hours |
| The visitor's note contains markup, links or a very long text | Stored as plain text (≤ 500 characters, trimmed), rendered escaped and clamped to two lines in the list; never sent in any e-mail, notification or `.ics` |
| A meeting is moved after its reminder was sent | `starts_at_version` is incremented and `starts_at_changed_at` set with the move, which invalidates the old reminder claim, so the booker gets a reminder for the new time (none if the move lands less than 24 hours before the new start) |
| The owner clicks Accept on a request that expired a minute ago | `409 request_expired`; the page explains that the request expired and the booker was told, and the row greys out |
| The owner cancels or deletes the original meeting in the CRM Calendar, then accepts its pending reschedule before the sync job has run | The acceptance locks and reads the live predecessor interaction, sees it `canceled` or deleted, cancels the successor (`original_cancelled`) and returns `409 original_booking_gone`; nothing is moved or sent. The sync job later cancels the original and writes the booker's one CANCEL into the mail outbox. |
| Link to a person that belongs to another organization | 404 (scoped lookup) |
| An abusive volume of requests | The IP-independent daily creation cap (`CUSTOMERS_BOOKING_MAX_NEW_REQUESTS_PER_DAY`, holds in every deployment), the fail-closed write rate limiter, and idempotency; per-IP limits apply only when a trusted proxy depth is set. Pending requests also count toward `maxBookingsPerDay`. A CAPTCHA plugs in through the form extension point `customers.public-booking.form` plus the `customers.public-booking.verify-submission` hook |
| Organization slug collision across tenants | Enabling is refused with `org_slug_ambiguous`; changing an org slug into a collision is refused by the directory interceptor; runtime ambiguity returns 404 |
| Mass bookings with rotating e-mails from one source | First the per-profile daily creation cap (`CUSTOMERS_BOOKING_MAX_NEW_REQUESTS_PER_DAY`; every created row counts, so book-and-cancel loops are bounded too), then the daily outbound-mail cap; the owner is notified at the cap. The per-IP open-request cap, per-IP rate limit and IP weighting of the owner-wide cap add to this only when `RATE_LIMIT_TRUST_PROXY_DEPTH` is set |

## 📝 Risks & Impact Review
| Risk | Severity | Area | Mitigation | Residual |
|---|---|---|---|---|
| A public endpoint leaks a user's schedule | Medium | privacy | Slots expose only free starts, never busy titles or reasons; opt-in; 404s are uniform | Free/busy shape is inferable by design (same as Calendly) |
| Spam bookings fill a user's calendar | Medium | abuse | Rate limits, approval mode, daily cap, manage-token cancel, decline from the list | No CAPTCHA in v1 |
| A person record created from an e-mail address that is not the booker's | Medium | data quality, privacy | No e-mail confirmation and no CAPTCHA, by **conscious product decision** (acknowledged in the UX review of 17 Nov 2026): approval mode (on by default) creates the person only when the owner accepts; instant mode is bounded by the creation, open-request and mail caps; the person is marked `source = 'public_booking'` and shown as "New from booking" so the owner can check or link it | Someone can still put another person's address into an owner's CRM; the CAPTCHA extension point and an e-mail confirmation step remain possible later |
| Double bookings with meetings kept outside the CRM | Medium | product | The settings page states that only the Open Mercato calendar blocks times; the owner can mirror outside meetings as CRM events or narrow working hours; approval mode lets the owner catch a clash before accepting | Until a calendar integration syncs external events into the CRM |
| Extracting the busy predicate changes conflict-route behavior or its access boundary | Medium | customers API, privacy | Pure refactor; `legacy` mode requires the viewer and applies the e-mail visibility filter before selection; existing conflicts tests stay green; parity tests including private e-mail, conversation share, shared channel and API-key caller | Low |
| PII in booking requests | Medium | GDPR | Encrypted columns, `findWithDecryption`, 90-day anonymisation; no PII in events, notifications, interaction titles or action-log payloads | The auto-created person follows CRM retention, not this job |
| The public form used as a mail relay | Medium | abuse | No booker free text in mails (the visitor's note never leaves the backend); escaped, truncated names; daily mail cap; per-IP and per-e-mail caps | No e-mail confirmation by product decision |
| A booking action reaching interactions it does not own | Medium | RBAC | `manage_own` has no `interactions.manage` dependency; commands require `owner_user_id = auth.sub` (or `booking.manage`) and touch only the request's own `interaction_id`; a regression test (Step 13) | — |
| Scheduler not installed | Low | expiry, reminders, e-mail recovery, retention | Derived-on-read expiry; outbox retries and deferrals carry their own delayed wake-ups; a warning on the settings and requests pages; CLI for manual runs | Without the scheduler, expiry e-mails, reminders, recovery of lost wake-ups and anonymisation need the CLI |
| Org slug not globally unique | Low | routing | Enable-time guard plus exact-one resolution | — |
| A booker receives a duplicate reminder, a reminder showing the old time after a concurrent move, or a reminder just after a cancellation | Low | booker e-mail | At-least-once delivery bounded to 3 sends per claim; a version-checked lease and live-interaction checks before each send; the send step's conditional update re-checks status, anonymisation and start time; the move's update e-mail carries the higher `SEQUENCE` | Rare duplicate (crash after the transport accepted the e-mail, or a send that outlived the 10-minute send ceiling and was delivered after a retry); a rare stale reminder text when a move commits while the send is in flight; a rare reminder after a CANCEL when the cancel commits during that window |
| A booking e-mail goes out just after a state change that commits while its send is in flight (a confirmation and then a CANCEL, or "your original time stays" just after the original was cancelled) | Low | booker e-mail | Every send re-checks the state it describes under a row lock right before sending; the later e-mail carries the higher `SEQUENCE`, so calendar clients end in the right state | The duration of one mail-server call (bounded by the send ceiling) |
| Booking e-mail is delayed because a wake-up job was lost and no scheduler runs | Low | booker e-mail | E-mails are committed to the mail outbox with the change, so none is lost; every first send, retry and deferral enqueues its own (delayed) wake-up; the maintenance tick re-enqueues due rows every 5 minutes; the settings and requests pages warn when the maintenance schedule is missing, inactive or the scheduler module is absent | Without the scheduler, only a row whose wake-up job was itself lost waits until someone runs `mercato customers booking-maintenance`; reminders, expiry and anonymisation also need that run |
| Booking e-mail is delayed or dropped by the daily mail cap | Low | booker e-mail | Over-cap mail goes to the mail outbox and is sent after the next local midnight with a fresh cap slot; a state re-check closes e-mails that no longer describe the booking; the owner gets `cap_reached` | A profile over its cap every day for 72 hours has its oldest deferred e-mails closed and reported instead of sent |
| A manage link leaks (forwarded e-mail) | Low | booker self-service | The token is an HMAC of a server secret, unguessable; manage writes still need `expectedUpdatedAt`, and reschedule is fail-closed on the rate limiter (only cancel runs without one) and mutation guards; links stop working on anonymisation; rotating `CUSTOMERS_BOOKING_TOKEN_SECRET` revokes all links | A forwarded link lets its holder cancel or reschedule that one booking until it is anonymised |

### Migration & Backward Compatibility
Additive, with one behavior change listed in UPGRADE_NOTES. The implementation adds a dated `BACKWARD_COMPATIBILITY.md` section, "CRM Calendar Public Booking" (created by Step 2, extended by each later step that changes a contract), covering: the CommandBus deferral of `runPostCommit()` when the caller passes an owned `transactionLifetime`; the optional `transactionalEm` support in `people.create` and `interactions.cancel`; the new `runAfterTransaction` export, and the shared customers emit helpers (`emitQueryIndexUpsertEvents`, `emitQueryIndexDeleteEvents`, the interactions lifecycle emits) which defer through it **only** when the caller passes an owned lifetime and are otherwise unchanged; the CRM Calendar types moving to `lib/calendar/types.ts` with a `@deprecated` re-export at `components/calendar/types` that also re-exports its runtime values (e.g. `calendarInteractionPayloadSchema`), kept for at least one minor version and scheduled for removal no earlier than the second minor release after it ships (import paths are STABLE, BC §4); the optional fallback-timezone parameter on the `lib/calendar/recurrence.ts` expander; the new `schedulerService.isActive(id)` method (additive on a DI service; an implementation without it falls back to `exists()`); and the directory refusal with its `409` status and error code.
- **Additive:** new tables, routes, ACL features, events, notifications and a frontend route. The conflicts route keeps its contract. `people.create` and `interactions.cancel` gain optional `transactionalEm` support; the command bus defers `runPostCommit()` only when the caller passes an owned `transactionLifetime`, and the new `runAfterTransaction` helper is an additive export. Existing callers pass neither and are unaffected. No `DataEngine` interface change. The scheduler service gains the optional `isActive(id)` method (`packages/scheduler`). No change to `CustomerInteraction`'s columns or statuses; Step 15 only adds three partial indexes on `customer_interactions` (Architecture → Busy time).
- **Behavior change (directory):** the organization update command can now be **refused** (`org_slug_ambiguous_for_booking`), but only when the new slug would make an active booking page ambiguous across tenants. Organizations without active booking profiles are unaffected. Per BACKWARD_COMPATIBILITY.md this is a new failure mode on an existing command, so it is documented with the error code and the workaround (disable the colliding booking profile first).
- **RBAC:** the default `employee` role gains only the new `customers.booking.manage_own`; no existing grant changes.
- **Environment variables (additive, all optional, recorded as ADDITIVE rows in the dated `BACKWARD_COMPATIBILITY.md` section and added blank or with their defaults to `apps/mercato/.env.example` and the create-app template in the step that introduces them):** `CUSTOMERS_BOOKING_TOKEN_SECRET` (Step 18; manage links are off without it), `CUSTOMERS_BOOKING_DAILY_MAIL_CAP` (Step 12, default 50), `CUSTOMERS_BOOKING_LOCK_TIMEOUT_MS` (Step 8), `CUSTOMERS_BOOKING_ALLOWED_ORIGINS` (Step 7), `CUSTOMERS_BOOKING_MAX_NEW_REQUESTS_PER_DAY` (Step 8).

**Rollback:** the preferred rollback is to disable profiles. Data stays, public pages return 404, and the CRM interactions already created remain normal meetings. Reverting the code is possible as well. The migration `down` drops the four booking tables (profiles, requests, idempotency keys, mail outbox) and **loses all booking history**, including the link from interactions back to their requests, so it is a last resort only. The encryption-map backfill migration is forward-only (empty `down()`), so the booking-request map rows stay in `encryption_maps`; they are inert without the table.

## 📋 Phasing
- **Phase 1: Instant booking (MVP).** Profile settings page (in Phase 1 the Approval row is hidden and profiles are saved with `requires_approval = false`; Phase 2 shows it, defaulting new profiles to on), the reminder e-mail (claimed by the maintenance job, delivered by `workers/booking-reminder.ts`), public page, slot engine with the write-side offered-slot gate, busy-time extraction, confirmed bookings with an auto-created person (in one real transaction), `.ics` confirmation e-mail, interaction→request sync (owner changes inform the booker, plus the person-delete cascade), abuse controls shipped **together with** the public write (Step 8), the mail cap, the idempotency table, the org-slug interceptor, and the maintenance job **with its system-scoped schedule and CLI**. Ships on its own: no manage links are sent (`manage_link_holder` is already set on confirmation, so these bookings get working links once Phase 3 and the secret are in place), and e-mails say "reply to this e-mail to change the meeting" (`replyTo` = owner).
- **Phase 2: Approval and matching.** `requiresApproval`, the pending lifecycle with conditional transitions, expiry added to the existing maintenance job, owner notifications, the Meeting requests list (tab counts), one-click accept and decline, Link to existing person with `countPersonDependents`, pending blocks in the CRM Calendar.
- **Phase 3: Booker self-service.** Manage tokens and the manage page, booker cancel, and reschedule (instant and approval semantics, token re-pointing), with `METHOD:CANCEL` and SEQUENCE updates.
