# Custom fields on customer and sales addresses

## 📝 TLDR

Administrators can define additional fields for CRM and sales addresses. Customer addresses hold the live values. Sales documents hold scoped copies that survive later edits to the customer address book.

## Resolved assumptions (autonomous defaults)

| Decision | Default and rationale |
| --- | --- |
| Scope | The issue explicitly requests one spec covering both modules. The CRM address book can ship first, and the Sales phase defines how it consumes the CRM values. |
| Sales address coverage | Primary billing, primary shipping, and additional addresses use the Sales address definition set. Each address has independent values. |
| Storage | Nullable columns on existing owning rows carry the values. A separate Sales document column keeps them outside the existing free-form snapshots and their downstream payloads. |
| Copy and visibility | A permitted staff member can copy compatible values when selecting a CRM address. Later copies require an explicit selection. Staff record visibility follows the owning address permissions, and arbitrary address values stay out of indexes and public payloads. |

## Overview

This follows [#5231](https://github.com/open-mercato/open-mercato/issues/5231) and the [address contact and tax fields spec](2026-08-10-address-contact-and-tax-fields.md). Medusa provides address-specific metadata and models customer and cart addresses independently. Adobe Commerce exposes typed attributes on customer addresses. Open Mercato can reuse its typed definitions with the same separation between the source address and the transaction. [Medusa customer address model](https://docs.medusajs.com/resources/references/customer/models/CustomerAddress) · [Medusa checkout addresses](https://docs.medusajs.com/resources/storefront-development/checkout/address) · [Adobe Commerce address types](https://developer.adobe.com/commerce/webapi/includes/autogenerated/graphql-api-saas-types-c-e)

## 📝 Problem Statement

The Customers address book and Sales document address editor have fixed inputs. Deployments need fields such as a delivery window or a driver note. Primary addresses on orders and quotes are JSON snapshots, while additional Sales addresses have their own rows. Storing values in the primary snapshots would also propagate them to consumers such as shipment metadata.

## 📝 Proposed Solution

Register `E.customers.customer_address` and `E.sales.sales_document_address` in their modules’ `ce.ts`. Reuse `cf.*`, existing field settings, scoped definitions, the field registry, and server-side definition validation. Use `cf.text` for an optional `delivery_instructions` definition on each host. Make it visible in forms and disable indexing. Deployments can define other supported field kinds in settings. Store values alongside the owning address or document through the existing commands.

## Architecture

- Customers owns address book definitions and data. Sales owns the document copies, the additional address records, and their lifecycle. Sales reads the source through the existing Customers dependency and never writes copied values back as part of a document edit. The explicit “Save this address to the customer” action remains the existing postal-address action.
- On selecting a saved customer address, the editor can request a copy by passing `copyCustomerAddressCustomValues: true` with the selected source ID. The server checks `customers.activities.view` in the current organization, the source ID and owner, and both definition sets before copying. Restrict automatic copy to active, form-visible definitions with the same normalized key and kind. Validate each candidate against the destination definition, including option sets. The explicit document patch then takes precedence. An inaccessible source yields the normal scoped error for the explicit copy request.
- The scope is the selected record’s tenant and organization. Use the trusted command scope and the destination document customer ID. For an additional address, verify the scoped document and source ownership before applying the copy. The existing legacy UUID resolution path continues to resolve postal fields, with copy triggered independently.
- Document create, address change and explicit reselection can copy, while ordinary edits preserve the previous values. A changed source or removal clears that address’s old bag before applying a new copy or patch. Changing the document customer clears both primary bags together with their postal snapshots. Additional rows that survive that operation keep their frozen values. Any subsequent copy on those rows requires a source belonging to the current customer. Changes to the CRM record later do not change existing documents. Quote conversion clones the primary values and carries additional address values with their reparented rows. Existing order-state locks also cover custom field writes.

## Data Models

| Owner | Nullable JSONB column | Shape |
| --- | --- | --- |
| `customer_addresses` | `custom_values` | Definition key to value |
| `sales_document_addresses` | `custom_values` | Definition key to value |
| `sales_quotes`, `sales_orders` | `address_custom_values` | Optional `billing` and `shipping` bags |

Register all columns in the owning module’s `defaultEncryptionMaps` and backfill map entries with the shared migration helper. Use the existing tenant encryption setting and scoped `findWithDecryption` reads. Before persisting a nonempty bag under encryption, require a usable tenant key and use the shared encryption service for the mapped field. Refuse an unchanged plaintext result from the encrypt path. On read, distinguish a missing bag from an unreadable encrypted value and reject edits against the latter. Cover this with at-rest and missing-key tests.

Keep the data behind owning APIs even though the settings registry is shared. The generic custom-entity record API remains unavailable for these system entities. The JSON bags do not write to `CustomFieldValue`. This keeps row writes, deletes and undo in the same unit of work as their owner and avoids automatic EAV indexing. Add explicit exclusion for the private columns and both address host IDs’ EAV values in query index document building and token extraction, including live and batch rebuild. Keep values out of full-text/vector sources and search result metadata even when Sales address search is enabled. Existing postal indexing follows the current configuration.

Use encrypted command snapshots for undo. Exclude bags from audit list, detail and export at the shared audit serialization boundary so redaction applies when an owning module is disabled. Preserve the existing Customers action-log redaction rules. Events, errors and logs carry IDs or field keys only. Explicit private record serializers carry values after authorization. Public quote, checkout, portal, shipping/carrier and other integrations retain existing projections.

Treat the bags as address data for retention and erasure. When a customer address is removed, its bag is removed with it. Any existing anonymization that clears an address while retaining its owning sales record must clear the matching bag. Document copies otherwise follow the document’s retention policy. Exclude the bags from general-purpose exports. Enumerate these paths with the [privacy coverage inventory](GDPR/2026-11-16-privacy-coverage.md) where it applies.

## API Contracts

| Existing operation | Additive contract |
| --- | --- |
| `GET /api/customers/addresses` | Optional `customValues` on each address item. The list remains under `customers.activities.view`. Embedded address projections on person and company detail use their existing shape. |
| `POST`, `PUT /api/customers/addresses` | Optional `customValues`. Existing response and `customers.activities.manage` requirement. |
| `GET /api/sales/document-addresses` | Optional `customValues` on each item under the owning quote or order view permission. |
| `POST`, `PUT /api/sales/document-addresses` | Optional `customValues` and `copyCustomerAddressCustomValues`; the latter uses the existing `customerAddressId`. Existing scope, status and write permissions apply. |
| Sales order and quote create, update and private `GET ?id=` | Optional `billingAddressCustomValues` and `shippingAddressCustomValues`. Writes can pass the matching `copyBillingAddressCustomValues` or `copyShippingAddressCustomValues` flag with the corresponding address ID. The grid and export projections keep their existing shape. |
| Existing address deletes and undo; quote conversion | Existing request and response contracts. New values follow the owning record lifecycle. |

Add optional fields to the existing Zod schemas and OpenAPI docs. Use bounded JSON input and the platform’s custom-field key limit. An omitted bag or individual key preserves its previous value during an update. An explicit `null` value clears that key. Setting a primary address to null also clears its bag. Reject a nonempty patch for an absent address. Validate submitted keys against the current host definitions and validate the merged active values, using `validateCustomFieldValuesServer` and `sanitizeCustomFieldHtmlRichTextValuesServer`. Leave parked values for inactive definitions out of the edit form. Legacy writes that omit the custom fields keep their previous behavior. Validate required fields when a create or edit supplies the bag or opts into source copy. Return localized field errors without including input values.

Reserve address identifiers, version/scope keys and all built-in address fields, including `phone`, `taxId`, `taxIdType` and `recipientName`. Normalize comparisons across camelCase, snake_case and case variants. Apply the same check to single and batch definition writes, code-declared definitions when deriving effective fields, and value writes. Existing colliding definitions remain administratively removable and their values are excluded from address form/use. Separate columns protect all opaque built-in snapshot keys, including any pre-existing `customValues` key inside a snapshot.

For custom address edits, keep the owning row’s optimistic-lock header and advance its `updatedAt` on a values-only write. Surface 409 conflicts through `surfaceRecordConflict`. The primary address uses the document version. Additional address edit/delete uses the additional row version. When a document form also mutates a customer address, use only that child’s version for the child write. All writes use the existing mutation guard and command, with undo/redo preserving the relevant bags and scoped transaction boundaries.

## UI/UX

Place the dynamic fields below the built-in address inputs, inside the same edit region. Use the existing field renderer driven by `fetchCustomFieldFormStructure` and keep the values in each editor’s draft. Both AddressEditor variants can accept an optional section using the current layout. These dialogs are separate from the outer `CrudForm`, whose `crud-form:<entityId>:fields` spot lacks a per-address value scope.

- Customers renders the section in the person and company address books and in their create-flow address drafts. Read mode uses the definition’s normal display format and label. A failed definitions request shows a localized retry state and disables submitting custom changes. Validate address drafts before creating the parent, including newly required custom values. If a subsequent child request fails, keep the unsaved child drafts and let the user retry those requests against the created parent ID without resubmitting the parent or already saved addresses.
- Sales renders the section in primary and additional address edit regions and primary address inputs on document creation. When a permitted user selects a source, show the matching values as a draft with the usual override affordance. A locked document presents the values read-only. A definitions fetch is shared for the Sales address host within the open view.
- Use the existing dialog keyboard actions, tab order, disabled state, translations and form field error treatment. Keep lookups and writes in the current interactive address components. Mount the field renderer only on these address surfaces. Preserve other callers of the two address editors and avoid global client providers.

### Performance and cache

Resolve each host’s definitions once per record write, or once per unique tenant and organization on a scoped list page. Private list serializers load address rows from the current page in a scoped batch using existing IDs and indexes. Keep the existing page cap of 100. Reuse the existing command cache invalidation and scoped definition cache. The address editor reuses the current client field registry and adds no page-root client boundary. Test that opening current editors with no configured fields preserves keyboard behavior and that rendering two address sections does not duplicate the definitions request.

## Edge Cases & Failure Scenarios

- Address selection uses two scopes. If the source or definitions become inaccessible between preview and save, the server rejects the explicit copy without changing the document. A stale document or child version opens the normal conflict recovery.
- Removed definitions leave encrypted historical values available to scoped undo, while the editor works with current definitions. Undo restores the captured address bag under the original record and scope. A setting change must never cause a legacy save to drop stored values.
- Null columns read as empty. Client requests that omit the new fields keep existing address behavior. Snapshot values from integrations are round-tripped using existing preservation logic.

## Risks & Impact Review

| Scenario | Severity and affected area | Mitigation and residual risk |
| --- | --- | --- |
| Gate codes or notes propagate through search, audit, or fulfillment | High, address privacy | Encryption mappings, explicit private projections, exclusion from indexes, audit redaction and absence tests. Authorized staff on the destination document can read a deliberately copied value. |
| A client saves two edits from a stale address version | Medium, CRM and Sales writes | Use the existing version preconditions and advance the owning version for bag-only changes. Legacy clients retain the existing optimistic-lock policy. |
| Conversion or undo only restores postal values | Medium, document and CRM history | Include the bags in existing clone and snapshot paths and test save, conversion, delete and undo. |
| A new field resembles a built-in or opaque snapshot key | Medium, settings and integrations | Reserve known aliases and store the bags outside postal snapshots. Older conflicting definitions remain removable. |

### Migration & Backward Compatibility

Add nullable columns and encryption-map inserts with checked-in ORM snapshots. Existing address data needs no value backfill. Keep route IDs, table and column names, event IDs, ACL IDs, and `AddressValue` contract. Test old payloads and pre-existing opaque snapshot data. Rollback can stop serving address custom values and retain their columns and map entries for a forward fix. Dropping those columns after deployment would discard saved values and requires a separate data-retention decision.

## Final Compliance Report

| Requirement | Design disposition |
| --- | --- |
| Tenant and organization scoping | Derive scope from the owning record and authorize both records for source copy. |
| Existing mutation behavior | Existing guards and command lifecycles own edits, deletes, conversion and undo. |
| Sensitive address data | Reuse tenant encryption and protect document, audit and search projections explicitly. |
| Additive contracts | Optional fields and columns, with independent storage for opaque snapshots. |

## Implementation Plan

### Phase 1 Customer address book

1. Register the CRM host and its optional field definition. Establish the reserved-key policy in settings and effective definitions. Add tests for duplicate and reserved names and existing definitions.
2. Add the customer storage column and encryption mapping, and implement private read, validated write, versioning and undo on the existing addresses API and commands. Cover parent deletion and index/audit exclusions with fixtures.
3. Render the existing field registry in person and company address drafts and in their address books. Add customer create, edit, reload and conflict coverage. Run generation and the CRM integration cases.

### Phase 2 Sales address snapshots

1. Register the Sales definition host and add encrypted storage to additional addresses, quotes and orders. Complete scoped additional address reads, commands, undo and search/audit exclusions.
2. Add primary-side serializers and command handling, including scoped copy, stale write conflicts, removal and quote conversion. Cover downstream payload exclusion and frozen copy behavior.
3. Wire the existing editors on Sales create and detail screens and add browser round-trip and read-only coverage. Run generation, Sales integration cases and the configured CI gate.
