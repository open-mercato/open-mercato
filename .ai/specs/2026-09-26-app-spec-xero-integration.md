## 0. Xero and Open Mercato facts

### 0.1 Xero API facts

Provenance tags: **[OpenAPI]** `xero_accounting.yaml` and `xero-identity.yaml` v19.1.0 (`github.com/XeroAPI/Xero-OpenAPI`), read 2026-10-12 · **[Docs]** developer.xero.com Contacts, Invoices, Scopes and HTTP Requests and Responses pages, read 2026-09-27 · **[FAQ]** developer.xero.com `/faq/limits`, `/faq/oauth2`, `/faq/granular-scopes`, `/faq/getting-started`, read 2026-09-27 and 2026-10-12 · **[OIDC]** `https://identity.xero.com/.well-known/openid-configuration`, read 2026-10-12 · **[Sandbox, <date>]** observed against the Demo Company on that date · **[Sandbox]** without a date: still to confirm, with Phase 2 (§ 10 #11) · **[Unverified]** trained knowledge (one item).

**Contacts** (`components.schemas.Contact`) [OpenAPI, Docs]:
- `ContactID` — "Xero identifier"; the only immutable, guaranteed-unique key.
- `MergedToContactID` — "ID for the destination of a merged contact. Only returned when using paging or when fetching a contact by ContactId or ContactNumber." Xero merges contacts and archives the merged-away contact [Sandbox, 2026-10-13]; an unpaged list walk, or one without archived contacts, never sees the signal (§ 6.1). A list filtered by `IDs` returns archived and merged-away contacts, with `MergedToContactID`, only when it also sends `includeArchived=true`; without the flag it returns the active ones only [Sandbox, 2026-10-14].
- `ContactNumber` (max 50) — writable through the API only, read-only in the Xero UI, "used to identify contacts in external systems". `AccountNumber` (max 50) — editable in the API **and** the Xero UI, so a weaker key. Both are unique per Organisation when set and usually blank.
- `ContactStatus` — `ACTIVE`, `ARCHIVED`, `GDPRREQUEST`. Contacts are never hard-deleted: they are archived or GDPR-redacted (PII stripped) and stay retrievable. A list call returns `ARCHIVED` contacts only with `includeArchived=true` ("Contacts with a status of ARCHIVED will be included in the response" [OpenAPI `GET /Contacts`]); a fetch by `ContactID` returns any status. Only Xero sets `GDPRREQUEST`, at the subscriber's request to Xero support; neither the UI nor the API can, so a sandbox cannot produce one (Xero developer blog, "GDPR and the Xero Contact API"). The walk sends `includeArchived=true` either way.
- `Name` (max 255) — `PUT /Contacts` currently rejects a duplicate name, but Xero's Contacts page warns that "'Contact Name' may no longer be a unique field" and tells integrators to key on `ContactID` [Docs].
- `TaxNumber` (max 50) — free text (ABN, GST, VAT, Tax ID), no format validation, no uniqueness. `TaxNumberType` — `SSN`, `EIN`, `ITIN`, `ATIN` (US-only), so it cannot normalize non-US numbers.
- `IsCustomer` / `IsSupplier` — read-only, computed from whether the contact has AR / AP invoices; a new contact with no invoices has both `false` (§ 6.4).
- Also mapped or relevant: `CompanyNumber` (max 50), `EmailAddress` (max 255), `Website` (read-only in the API), `ContactPersons[]`, `DefaultCurrency`, `UpdatedDateUTC`, `ContactGroups[]`, `Balances`. `Name` is the contact's only organisation name (`FirstName` / `LastName` name a contact person). An `Addresses[]` entry carries `AddressType` `POBOX` (postal) or `STREET` (physical), `AddressLine1`–`AddressLine4` (max 500 each), `City`, `Region`, `PostalCode`, `Country` (free text) and `AttentionTo`; a `Phones[]` entry carries `PhoneType` (`DEFAULT`, `DDI`, `MOBILE`, `FAX`, `OFFICE`) and `PhoneCountryCode`, `PhoneAreaCode`, `PhoneNumber` as separate fields (§ 6.2a).

**Invoices** (`components.schemas.Invoice`) [OpenAPI, Docs]:
- `InvoiceID` — Xero-generated unique id. `Type` — eight values (`ACCPAY`, `ACCPAYCREDIT`, `APOVERPAYMENT`, `APPREPAYMENT`, `ACCREC`, `ACCRECCREDIT`, `AROVERPAYMENT`, `ARPREPAYMENT`), so `Type=="ACCREC"` excludes credit notes and pre/overpayments exactly.
- `Status` — `DRAFT`, `SUBMITTED`, `DELETED`, `AUTHORISED`, `PAID`, `VOIDED`. `PAID` is system-set when an invoice is fully paid; the only terminal transitions are `AUTHORISED → VOIDED` and `DRAFT|SUBMITTED → DELETED`, so an import of `AUTHORISED, PAID, VOIDED` never meets a `DELETED` invoice.
- `InvoiceNumber` (max 255) — for `ACCREC` "unique alpha numeric code" (auto-generated when missing); nothing comparable is asserted for `ACCPAY`. A user can hand-edit it. `Reference` — `ACCREC` only, often a PO number.
- `Contact` — a summary (`ContactID`, `Name`) on list responses, so linking an invoice to its Company needs no extra call.
- Payment state on the invoice: `AmountDue`, `AmountPaid`, `AmountCredited`, `FullyPaidOnDate`. Amounts: `CurrencyCode`, `CurrencyRate`, `SubTotal`, `TotalTax`, `Total`, `TotalDiscount`, `RoundingAmount`. Dates: `Date`, `DueDate`, `UpdatedDateUTC`, and ISO-8601 `UpdatedDateUTCString`, `DateString`, `DueDateString`. Out of MVP scope but named: `RepeatingInvoiceID`, `CISDeduction` / `CISRate`.
- `LineAmountTypes` — `Exclusive`, `Inclusive`, `NoTax`, exclusive when absent — states whether a line's `LineAmount` and `UnitAmount` include tax. `LineAmount` already reflects the line's discount (`Quantity` × `UnitAmount` less `DiscountRate` % or `DiscountAmount`); `SubTotal` excludes tax whatever the line amount type, and `Total` = `SubTotal` + `TotalTax` + `RoundingAmount`. `RoundingAmount` comes only with a create, an update or a fetch by id, never with a list call, and on an Organisation that enabled Xero's opt-in supplied totals a list call returns Xero's calculated `SubTotal` / `TotalTax` / `Total`, at most 0.10 from the supplied ones [OpenAPI; Sandbox: § 10 #11 (k)].
- `LineItems[]` — `LineItemID`, `Description`, `Quantity`, `UnitAmount`, `ItemCode`, `AccountCode`, `AccountID`, `TaxType`, `TaxAmount`, `LineAmount`, `Tracking` (≤ 2), `DiscountRate` / `DiscountAmount` (ACCREC only), `Taxability`, `SalesTaxCodeId`, `TaxBreakdown[]`. `Quantity`, `UnitAmount`, `LineAmount` and `TaxAmount` are plain numbers with no minimum, and a line may carry only a `Description` [OpenAPI]; negative lines (discounts, deposits) are therefore representable; the Demo Company's invoices carry none [Sandbox, 2026-10-14] — OM's invoice validators reject them (§ 0.2.3).
- **A plain list call returns no line items.** Line items come back for a single invoice, a `Statuses` query or a paged query [Docs]; `?Statuses=AUTHORISED,PAID,VOIDED` paginates by default and returns lines, so it is the required query shape (WF3). `Statuses` does not filter by `Type`: the query also returns `ACCPAY` bills, so it adds `where=Type=="ACCREC"` (an optimised field), which keeps the lines [Sandbox, 2026-10-14].
- Optimised `where` fields: `Status`, `Type`, `InvoiceId`, `InvoiceNumber`, `Reference`, `Contact.ContactID`, `Contact.Name`, `Contact.ContactNumber`, `Date`, `DueDate`, `AmountDue`, `AmountPaid`; range operators on `Date`, `DueDate`, `AmountDue`. `or` is optimised for `InvoiceId` only; multi-value filters use the `Statuses`, `IDs`, `InvoiceNumbers`, `ContactIDs` list parameters [Docs].
- `summaryOnly=true` drops `LineItems`, `Payments`, `HasAttachments`, `CISDeduction` on invoices, and `Addresses`, `Balances`, `ContactGroups`, `ContactPersons`, `IsCustomer`, `IsSupplier` and four default-account fields on contacts [Docs]: it is rejected for both entities (§ 6.6).

**Dates** [OpenAPI example]: JSON dates use the .NET form `/Date(1539993600000+0000)/` or `/Date(1552326816230)/`; the adapter prefers the `*String` variants and parses the .NET form only where none exists.

**Paging and incremental sync** [OpenAPI, Docs]:
- `page` (1-based) and `pageSize` on `GET /Contacts` and `GET /Invoices`. OpenAPI declares `pageSize` as an integer with no maximum and describes `page` as returning "up to 100" records; the Docs give a maximum of 1000 with out-of-range values clamped. The adapter requests 1000, the effective maximum: a larger value is clamped to 1000 [Sandbox, 2026-10-13]. The response envelope `pagination: { page, pageSize, pageCount, itemCount }` bounds the walk.
- Paging is a correctness requirement for Contacts: unpaged `GET /Contacts` returns a subset of fields that excludes `MergedToContactID`, `ContactPersons`, `ContactGroups` and `Balances` [Docs].
- The Accounting API returns XML unless the request sends `Accept: application/json` [Docs].
- Default ordering `UpdatedDateUTC ASC` with an id tiebreak (`ContactID` / `InvoiceId`), stable across pages [Docs] — while nothing in the walk changes: a record edited mid-walk moves to the end of the order, every later record shifts one position earlier, and a walk that advances `page` skips one record per such edit. The adapter therefore pages by keyset (`If-Modified-Since` from the last record read, § 6.7).
- Contacts: optimised filters `Name`, `EmailAddress`, `AccountNumber` (equals only); optimised ordering `ContactID`, `UpdatedDateUTC`, `Name`; `searchTerm` is the sanctioned substring search. Both endpoints deny responses above 100,000 records and reject unoptimised filtering or ordering at that volume with `400` [Docs].
- `If-Modified-Since` header — "Only records created or modified since this timestamp will be returned" [OpenAPI `components.parameters.ifModifiedSince`], accurate to the second, evaluated against `UpdatedDateUTC` [Docs].
- **Blind spot** [Docs]: "Not all changes will trigger a change of the UpdatedDateUTC field. These include changes to partially paid transactions which don't generate a journal such as DueDate or SentToContact, and Contact fields pulled from other sources such as Balances, IsSupplier, and isCustomer." Consequences: an invoice's `DueDate` can go stale in OM, which only a periodic full pass corrects (§ 6.7); a supplier-only contact who becomes a customer is not re-sent, which the invoice-side self-heal covers (§ 6.5), so the self-heal is load-bearing.

**OAuth 2.0** (Authorization Code flow, Web app):
- [Unverified] Registering a Web ("Auth Code") app at `developer.xero.com` yields a Client ID and Client Secret.
- Redirect URI [FAQ, 2026-10-12]: pre-registered exactly, absolute, no wildcards, up to 50 per app; `https`, except `http://localhost` for testing; `http://127.0.0.1` is not allowed. The core builds it from `APP_URL` only (`resolveOAuthRedirectUri`), so production needs an `https` `APP_URL`.
- Endpoints [OIDC; authorize and token also in OpenAPI `securitySchemes.OAuth2`]: authorize `https://login.xero.com/identity/connect/authorize`, token `https://identity.xero.com/connect/token`, revocation `https://identity.xero.com/connect/revocation` (RFC 7009, `200` with an empty body); `code_challenge_methods_supported: [S256]`; `token_endpoint_auth_methods_supported: [client_secret_basic, client_secret_post]`. An Auth Code app accepts a `code_challenge` (S256) together with `client_secret_basic` [Sandbox, 2026-10-13] (core Q2), so the descriptor declares `pkce: 'S256'`.
- Lifetimes [FAQ]: authorization code single-use, 5 minutes; access token 30 minutes; refresh token 60 days when unused; every refresh returns a new refresh token and the previous one stays usable for 30 minutes ("If you don't receive a response from a token refresh you can retry using your existing refresh token for up to 30 minutes"); a refresh token is issued only with `offline_access`. A refresh token also dies when the user removes the app in Xero or changes their Xero password — recovery is a Reconnect.
- Scopes [Docs — Scopes page; FAQ]: granular scopes have been assigned to all Web and PKCE apps since March 2026 (custom connections since 29 April 2026); the broad `accounting.transactions`, `accounting.transactions.read` and `accounting.reports.read` remain until September 2027. `accounting.contacts(.read)` is not deprecated. Scopes are additive and cannot be narrowed without revoking ("It's not possible to remove scopes from an existing access token"), so over-requesting is a one-way door. OpenAPI still declares only the broad invoice scope (`paths./Invoices.get.security`: `accounting.transactions(.read)`; no `accounting.invoices.read`, no `offline_access`), so the granular invoice scope rests on the Scopes page; a new app is assigned it, and the `.read` scopes cover every call this integration makes [Sandbox, 2026-10-13]. A consent that requests fewer scopes than the Xero user granted the app before still returns all of them, `offline_access` and a refresh token included [Sandbox, 2026-10-14].

  | Scope | Why |
  |---|---|
  | `offline_access` | Required for a refresh token |
  | `accounting.contacts.read` | WF2 (Contacts, GET only) |
  | `accounting.invoices.read` | WF3 (Invoices, GET only) |

  Deliberately omitted: `openid` / `profile` / `email` (single sign-on; the account label comes from `/Connections.tenantName`), `accounting.payments.read` (payment state comes from the invoice), `accounting.attachments.read` (PDFs deferred), `accounting.settings.read` (no mapped field needs it). The set is the descriptor's `defaultScopes`, a code constant; the Client Configuration has no `scopes` field.
- Insufficient scope returns `401`, not `403`. The FAQ spells the header token `insufficent_scope` [FAQ `/faq/granular-scopes`]; the sandbox returned the correct `WWW-Authenticate: insufficient_scope` as a bare token, with `Detail: AuthorizationUnsuccessful` [Sandbox, 2026-10-13]. The client accepts both spellings.

**Connections** [OpenAPI `xero-identity.yaml`]: `GET https://api.xero.com/Connections` (query `authEventId`) returns `{ id, tenantId, authEventId, tenantType, tenantName, createdDateUtc, updatedDateUtc }[]`, `tenantType` `ORGANISATION` or `PRACTICE`; `DELETE /Connections/{id}` → `204` ("disconnect a tenant"), `404`. In the sandbox, a second `DELETE` of a removed id answered `403`. After the delete, Accounting calls answered `403` `AuthenticationUnsuccessful`, while the grant kept refreshing [Sandbox, 2026-10-13]. A short-lived consent by the same Xero user (no `offline_access`, shown as "Allow access for 30 minutes") takes over the shared connection record and removes it when it expires; runs then fail as "Xero Organisation no longer authorised" until a Reconnect [Sandbox, 2026-10-14]. One grant can cover several Organisations. `authEventId` is "Identifier shared across connections authorised at the same time" and comes from the access token's `authentication_event_id` claim [FAQ]. Both `/connections` and `/Connections` answer; the client uses `/connections` [Sandbox, 2026-10-13]. Every Accounting API call carries the `xero-tenant-id` header (the Organisation's `tenantId`) [OpenAPI `components.parameters.requiredHeader`]; there is no per-Organisation token. The connection cap also follows the tier: a new app is listed with "5 max connections" [Sandbox, 2026-10-13], against the FAQ's 25 for uncertified apps. Revoking a refresh token ends **every grant of the same Xero user for the app**, not just the revoked one. In the sandbox, the other grant's refresh token then answered `invalid_grant` and the shared connection record disappeared [Sandbox, 2026-10-13] (§ 10 #14). A consent over an Organisation that is already connected keeps the existing connection record; its `authEventId` stayed the original one on 2026-10-13 and became the new consent's on 2026-10-14 [Sandbox, 2026-10-13 and 2026-10-14], so the callback falls back to the unfiltered list whenever the filtered one is empty (WF1).

**Rate limits and errors** [FAQ `/faq/limits`]:
- Per Organisation: 5 concurrent calls, 60 per minute, and a daily limit that depends on the app's Xero pricing tier: 1,000 calls on Starter, the tier of a new app, and 5,000 on Core. A new test app showed `X-DayLimit-Remaining: 999` after its first call [Sandbox, 2026-10-13]. App-wide: 10,000 per minute across all connected Organisations. Limits cannot be increased. Every response carries `X-DayLimit-Remaining`, `X-MinLimit-Remaining`, `X-AppMinLimit-Remaining`; exceeding a limit returns `429`.
- `400` structured validation errors (writes only), `401` expired token (or insufficient scope, above), `5xx` transient.

**Demo Company:** every Xero login has a pre-populated "Demo Company" Organisation (Xero's own `/Connections` example names "Demo Company (NZ)") on the same API and base URL. Local development: register a Web app with the redirect URI the Xero tab shows (`APP_URL` on `http://localhost`), connect, and select the Demo Company.

### 0.2 Open Mercato platform — read from the repository (`main` @ `036a08ee9`)

Line numbers are those of `main` @ `036a08ee9` (0.10.0). Further sandbox results (tie order, the Contact deep link, `If-Modified-Since` inclusive at the second) are in the Phase 1 feature spec, Step 0 (m)–(o).

1. **OAuth is the grant lifecycle core's job; Xero owns only its routes, its tab and its Organisation picker.** The core (`packages/core/src/modules/integrations/lib/oauth/*`) supplies, for a tenant-level provider:
   - the **`OAuthProviderDescriptor`** (endpoints, client auth, `pkce`, `defaultScopes`, `requiresRefreshToken`, `defaultAccessTokenTtlSec`, `refreshSkewMs`), passed to every call, no registry; it has no disconnect hook, because Disconnect's cleanup is the core's revoke;
   - **protocol helpers** `createPkcePair`, `resolveOAuthRedirectUri` (`APP_URL` only), `buildAuthorizationUrl`, `exchangeAuthorizationCode`, `classifyResourceChallenge`;
   - the DI service **`integrationOAuthGrantService`**: `completeConnect`, `getAccessToken` (lazy refresh under a cluster-wide Grant Lock, at most one refresh per call window, `rejectedAccessToken` after a `401`, a `degraded` token on `transient`), `updateProviderData` (with `expectedRevisedAt`; it replaces the whole object and clears `previousProviderData`, `lib/oauth/grant-service.ts:1108`), `inspectGrant` (network-free; carries `hasExternalAccount` and `providerData`), `readGrantStatus`, `disconnect` (erase under the lock, then RFC 7009 revoke after release; `force` for an unreadable grant); `getAccessToken` also takes `forceRefresh`, its default margin `refreshSkewMs` is capped at half the token's lifetime, and `mapInspectionToHealth` reports `oauth.scope_drift` for missing scopes;
   - **`OAUTH_HEALTH_CODES` + `mapInspectionToHealth`** (`lib/oauth/health.ts`): a network-free health result; an `active` grant with no External Account maps to `healthy` / `oauth.connected` — Account pending is left to the provider;
   - the **reauth banner** on the integration detail page (reads the grant, never `reauthRequired`) and `detailPage.connectTabId` for its deep link;
   - **test infrastructure**: the fake authorization server (`lib/oauth/testing/fakeAuthorizationServer`: `rotation: 'strict'`, `strictGraceMs`) and the loopback-`http:` endpoint rule under `OM_ENABLE_TEST_OAUTH_GRANTS` that a provider's test seam relies on;
   - the **provider route contract** (core App Spec § 1.4.3, rules 1–11) and the **failure contract** (§ 1.4.5): Token Failures `transient`, `grant_invalidated`, `client_misconfigured`, `not_connected`, `platform_unavailable`; Connect Failures; the Resource Challenge outcome `scope_insufficient`.

   Provider-owned until the core's Phase 3 (core R2, R15): the initiate and callback routes, the Connect UI and External Account picking. The state cookie comes from `communication_channels/lib/oauth-state` (`verifyOAuthState`, `consumeOAuthStateOnce`, `OAuthStateError`) under a provider-specific cookie name (rule 5); the hub's `oauth-token.ts` and `credential-refresh.ts` are not used. A provider uses no export marked `@internal`: the list is the "Explicitly not covered" row of `BACKWARD_COMPATIBILITY.md` § OAuth2 Grant Lifecycle Core (among them `createIntegrationOAuthGrantService`, `requestTokenEndpoint`, `revokeToken`, `eraseIntegrationCredentials` and every export of `lib/oauth/{grant-blob,pin-tenant-dek,error-brand}`), plus any other `@internal` export. The core's `clientChanged` (part of `inspectGrant`'s result, `lib/oauth/grant-service.ts`) compares only the Client ID, so other Client Configuration fields can change without touching the grant. **Implementation state:** merged on `main` (#7057, 2026-10-21). **One gap for Xero:** `classifyResourceChallenge` matches RFC 6750's `insufficient_scope` (the `Bearer` error form and a bare token), not Xero's misspelling `insufficent_scope`; the Xero API client maps that one to `scope_insufficient` before branching.
2. **`SalesInvoice` has no Company link.** It has an optional `order` FK; the customer lives on `SalesOrder` (`customerEntityId`, `customerSnapshot`). `orderId` is optional on `invoiceCreateSchema`, so a standalone invoice is an accepted shape, but nothing records which Company an imported invoice belongs to — this spec adds a `sync_xero` custom field on `sales:sales_invoice` (§ 1.4).
3. **Invoice amounts are caller-asserted, but the invoice write path does not accept every Xero invoice as-is.** `sales.invoices.create` / `.update` take `subtotalNetAmount`, `grandTotalGrossAmount`, `paidTotalAmount`, `outstandingAmount`, … from the input; nothing recomputes them (`sales/commands/documents.ts:9350-9427`, `:9615-9637`). The gaps (§ 10 #19):
   - every invoice line amount — unit prices, tax amount and totals — is `decimal({ min: 0 })` (`sales/data/validators.ts:902-944`, unit prices `:926-927`), so a negative line is rejected; `invoiceNumber` is `max(191)` (`:904`) while Xero allows 255 (the column is `text`);
   - `invoiceCreateSchema` has no `customFields` key and `z.object` strips unknown keys, so the create command's custom-field branch (`documents.ts:9478-9488`, entered only when `customFieldSetId` is passed) never receives values; the invoices route also splits custom fields off before the command (`sales/api/invoices/route.ts:99-104`). `orderCreateSchema` and `quoteCreateSchema` do accept `customFields` (`validators.ts:723`, `:768`);
   - `sales.invoices.update` writes header fields only (`applyInvoiceHeaderUpdate`, `documents.ts:9615-9637`): no lines, no custom fields, and a `metadata` it is sent replaces the column whole (`:9636`);
   - `sales.invoices.delete` is a soft delete (`documents.ts:9790`), and `sales_invoices_number_unique` on `(organization_id, tenant_id, invoice_number)` is a plain constraint (`sales/migrations/Migration20251030150038.ts:67`), so a deleted invoice keeps its number.
   Header totals stay ≥ 0 for `ACCREC` invoices; `outstandingAmount` has no minimum. `SalesInvoice` has no reference or rounding column (`sales/data/entities.ts:1391`). A line takes a `kind` (`product`, `service`, `shipping`, `discount`, `adjustment`, `validators.ts:328`), a `quantity` ≥ 0, net and gross unit prices and totals, `taxAmount`, `taxRate` (0–100) and `metadata`; the create command derives a line's net total from its gross only when the net total passed is not positive (`sales/commands/shared.ts:88-101`). Amounts are `numeric(18,4)` columns.
4. **Invoice status is a dictionary entry.** Both invoice commands derive `status` from `statusEntryId` (`documents.ts:9378`, `:9669`) with `resolveDictionaryEntryValue`, which reads any tenant `DictionaryEntry` by id (`sales/lib/dictionaries.ts:117-125`). The sales module defines no invoice-status dictionary (its kinds: `sales/lib/dictionaries.ts:12-18`), so `status='voided'` cannot be set as free text. The `dictionaries` module registers entry commands only (`dictionaries.entries.create` / `.update` / `.delete`, `dictionaries/commands/entries.ts:25-30`); a module with a dictionary of its own finds or creates the `Dictionary` row with `em.findOne` / `em.create`, as `ensureSalesDictionary` does (`sales/lib/dictionaries.ts:84-114`).
5. **OM has no invoice screen.** `sales/backend` has channels, documents (orders and quotes), orders and quotes pages; no component renders invoices, and an invoice search result links to its parent order (`sales/search.ts:634`), so a standalone invoice has no page. Upstream #100 ("UIV8 Invoices & Credit Memos", open) proposes invoice editing on the order details page. Sales defines no read-only invoice feature: `sales.invoices.manage` guards every method of the invoices API (`sales/acl.ts:92`, `sales/api/invoices/route.ts:31-34`).
6. **`CustomerCompanyProfile` has no tax-ID column**, though `customers/AGENTS.md` mentions "tax ID optional". Upstream #5232 (open) adds `taxId` / `taxIdType` on addresses, not on the company profile.
7. **`ExternalIdMappingService` is 1:1 per local record and does not arbitrate concurrent writers.** `storeExternalIdMapping` finds an existing row by external id or by local id and re-points it (`data_sync/lib/id-mapping.ts:55-105`): storing a mapping for a Company that is already mapped moves that mapping, and storing a second Company for an external id that is already mapped moves the mapping off the first, which is left unmapped. The table has no unique index on `(integration_id, external_id, organization_id)` (`integrations/migrations/Migration20260304113737.ts:17`), so two concurrent first writes can both insert. `SyncExternalIdMapping.syncStatus` is the closed union `synced | pending | error | not_synced` with no setter on the service (`integrations/data/entities.ts:24-25`), and the entity has no metadata column. `lookupExternalId` returns only the external id (`data_sync/lib/id-mapping.ts:30-46`), and `storeExternalIdMapping` sets `syncStatus='synced'` and `lastSyncedAt` on every store (`:91-92`, `:113-114`): a mapping records when it was created and last stored, not when its record last synced. `data_sync/di.ts` registers the service from the factory `createExternalIdMappingService(em)`, so it can be bound to another EntityManager. `customers.companies.create` / `.update` write a Company's custom fields right after the Company's own transaction, not inside it, so a failing custom-field write fails the command after the Company has committed (`customers/commands/companies.ts:550-557`, `:770-823`); a field declared on the profile is stored under the `CustomerCompanyProfile` id, and the create command returns both ids, `entityId` and `companyId` (`:443-484`, `:574`); `sales.invoices.create` writes an invoice's custom fields inside the invoice transaction (`sales/commands/documents.ts:9432-9492`). Custom-field values are rows of `custom_field_values`, indexed on `field_key` and on `(entity_id, record_id, …)` but not on `value_text` (`entities/data/entities.ts:201-215`, `entities/migrations/Migration20251030150038.ts:21-22`); `filterable` in a field's config is list-filter metadata (`entities/api/definitions.ts:458`; the query engine uses it only to score definitions, `shared/src/lib/query/engine.ts:328`) and adds no index, so selecting records by a custom field's value reads every value of that field in scope, and the query engine's `cf:` filter left-joins each base row's value (`engine.ts:1135`). For serializing across processes the grant core's Phase 1 (PR #7057) adds the shared `withAdvisoryXactLock` (`@open-mercato/shared/lib/db/advisoryLock`): a Postgres transaction advisory lock whose callback does all DB I/O on the lock transaction, makes at most one external call and never forks — so a command, which forks its own EntityManager, cannot run inside it. Precedent for matching: `sync_excel/lib/adapters/customers.ts` (`buildEmailDedupeIndex`, § 6.1b).
8. **`data_sync` runs, schedules and telemetry**:
   - runs, cursors, retry and progress are generic; a provider implements `DataSyncAdapter`. An item's action is `create`, `update`, `skip` or `failed` (`lib/adapter.ts:74`): the engine counts every item that is not created, updated or failed as skipped (`lib/sync-engine.ts:119-132`) and writes a log row only for a `failed` item (`:336-371`), so a provider writes any other per-item message itself with `integrationLogService.write` and the run id; the run detail page lists a run's log rows (`backend/data-sync/runs/[id]/page.tsx:195-204`);

   - the scheduled worker returns before creating a run when the schedule or the integration is disabled (`workers/sync-scheduled.ts:52-58`), refuses an overlapping run per integration, entity type and direction, passes no cursor when the schedule has `fullSync` (`:73`) and records `triggeredBy: 'scheduler'` (`:120`);
   - a manual run of a disabled integration is refused with `409 Integration is disabled` (`api/run.ts:95-98`);
   - the adapter input carries no trigger (`StreamImportInput`, `lib/adapter.ts:33-66`), only the optional `runId`, which the engine always passes (`lib/sync-engine.ts:750`); a run's origin is `SyncRun.triggeredBy` — `'scheduler'` for a scheduled run; for a manual one the caller's own `triggeredBy` or else the user id (`api/run.ts:148`, `data/validators.ts:11`). `ImportItem.hash` is declared (`lib/adapter.ts:75`) but the engine never reads it;
   - the integration page's schedule editor defaults a new schedule to every hour (six hours for `categories` and `attributes`) with "Run as full sync" on for every entity type except `products` (`components/IntegrationScheduleTab.tsx:103-115`, `buildDefaultScheduleState`), so a `xero.*` schedule created there runs hourly with `fullSync` on;
   - cancellation aborts `StreamImportInput.signal` from the batch handler and the heartbeat tick; adapters return above the `yield` (`data_sync/AGENTS.md:277`);
   - a run whose adapter returns without yielding is finalized `completed` (`lib/sync-engine.ts:869-874`); with `adapter.operationalTelemetry` on, run start writes `lastHealthStatus: 'degraded'` and completion `'healthy'` (`:431-446`, `:526-531`, `:695-700`) — the same field the health service writes (`integrations/lib/health-service.ts:133`).
9. **Reauth signals are the core's.** `IntegrationState.reauthRequired` is not written in the core's Phase 1 (core R8); the banner reads the grant, and the health badge comes from the provider's health check, run by `integrationHealthService`'s 15-minute probe (registered once per tenant, so a tenant's other organizations update on "Run Check"); the probe never refreshes (R10).
10. **Where a Company shows integration data.** The generic External IDs widget injects only at `detail:*:sidebar` (`integrations/widgets/injection-table.ts:11`), and the Company detail page hosts `detail:customers.company:header`, `:status-badges` and `:footer` (`customers/extension-points.ts:39-41`) and `:tabs` (a spot id only the page declares, `companies-v2/[id]/page.tsx:299`) — no sidebar, so the widget does not render there. 11. **A Company's addresses are not Company fields.** `companyCreateSchema` / `companyUpdateSchema` (`customers/data/validators.ts:97-172`) take `displayName` (required, max 200), `legalName` (max 200), `primaryEmail` (an email address), `primaryPhone` (max 50; a leading `+` and 7–15 digits, `shared/src/lib/phone.ts`), `websiteUrl` (a URL, max 300), `status` (text; the seeded status values are `active`, `inactive`, `pending` and `archived`, `customers/cli.ts:77-82`), `isActive` and custom fields (`parseWithCustomFields`) — and no address. Addresses are `CustomerAddress` rows written by `customers.addresses.create` / `.update` / `.delete` (`customers/commands/addresses.ts:167`, `:367`, `:571`): `addressLine1` is required (`validators.ts:271`), `purpose` holds an `address_type` value (seeded `office`, `work`, `billing`, `shipping`, `home`, `customers/cli.ts:107-113`), setting `isPrimary` demotes the Company's other primary address (`addresses.ts:107-115`), and the commands take no custom fields. An address update accepts `entityId` and moves the row to another customer (`validators.ts:294-298`, `addresses.ts:382-386`). A value a validator rejects fails the whole command.

## 1. Business Context `PM`

### 1.1 Business Model

Open Mercato tenants who use Xero as their accounting system of record currently re-key Xero customers and sales invoices into Open Mercato by hand (or via the generic CSV importer) to use them in OM's CRM, sales reporting, and customer-portal workflows. The paying customer is the OM tenant (the business running its operations in OM). This integration removes the re-keying step: it does not sell Xero data, it removes friction between two systems the tenant already pays for.

**Flywheel:**
```
Xero import removes manual data entry
   -> OM's Company/Invoice data is trusted as accurate and current
   -> tenant relies more on OM's CRM/sales/portal workflows against that data
   -> tenant adopts more of OM's operational modules (sales reporting, customer portal, deals)
   -> OM becomes the tenant's "system of engagement" layered on Xero's "system of record"
   -> higher retention and expansion within the OM platform
```

### 1.2 Business Goals

**Primary goal:** eliminate manual duplicate entry of Xero Contacts and Xero Sales Invoices into Open Mercato, so a tenant's Companies and Invoices in OM reflect their real accounting records without a human re-typing them. Measurable: after the first sync, every active Customer Contact (§ 1.3), and every archived Contact an imported invoice references, has exactly one corresponding OM Company (no duplicates from repeated, concurrent or interrupted runs — residuals in § 6.1; no manual matching); every Xero `ACCREC` invoice in `AUTHORISED`, `PAID` or `VOIDED` status has exactly one corresponding OM Invoice within one scheduled-sync interval (one hour by default) of reaching that status in Xero, or a failed or refused item naming the reason (a number collision, an invoice deleted in OM, an unresolved Contact, § 6.5), re-attempted by the weekly full pass.

**Secondary goal:** N/A — this is not a reference/example app (§ 9 is N/A).

**What is NOT important (explicit exclusions):**
- Writing anything back to Xero (no export, no bidirectional sync) — this is import-only.
- Real-time webhook push from Xero — poll-based incremental sync (`If-Modified-Since`) only.
- Bills (`ACCPAY`), credit notes, detailed multi-payment records, invoice PDFs/attachments, Payroll, Projects, Files — all deferred (§ 6.3, § 7).
- Currency conversion — currency code and amounts are stored exactly as Xero reports them, no FX conversion in OM.
- A configurable field-mapping UI (unlike `sync_excel`) — the fixed, documented mapping ships (§ 10 #3).
- Xero Custom Connections (Xero's client-credentials app type) — this integration uses a Web app with the Authorization Code flow.

**Domain invariants:**
- At most one live Xero grant per OM tenant+organization (the core's single live row, serialized by its Grant Lock), bound to at most one Xero Organisation; one Client Configuration row per OM organization. Several Xero Organisations per OM organization are out of scope.
- A `SyncExternalIdMapping` row `(integrationId='sync_xero', internalEntityType='sales.invoice', externalId='<xeroOrganisationId>:<InvoiceID>')` is the sole signal that an invoice is Xero-sourced; no boolean flag.
- Every Xero-sourced invoice carries its Company link (§ 1.3), written in the same command transaction as the invoice and its lines — never an invoice without one (§ 10 #19 for the write path).
- A Contact is mapped to a Company only by a Company claim, and every Company this integration creates or matches carries the Xero contact marker: concurrent contacts and invoices runs never leave two mapped Companies for one Contact, a Company created by a writer whose claim lost to a different Company is deleted by that writer (or reported when the delete is refused, § 6.1), and an interrupted run maps the marked Company on retry instead of creating a second one (§ 0.2.7, § 6.1).
- The tax-number fallback matches a Contact only to a Company that has no `sync_xero` `customers.company` mapping: the run's index drops a Company as soon as it is claimed, and the claim re-checks under the lock (§ 6.1).
- A sync writes at most one address row per Xero address type per Company — the row its `customers.address` mapping names, while that row belongs to the Company — only from the `xero.contacts` run, and never sets `isPrimary`; every other address row is the user's and is never changed or deleted by a sync (§ 6.2a).
- The grant's `providerData` is either empty (Account pending) or holds the three Organisation keys above; `xeroConnectionId` is read fresh from `/connections` when the Organisation is saved, never copied from `previousProviderData`.
- Every `xero.*` cursor and mapping belongs to one Xero Organisation (core Q10): the cursor carries its `xeroOrganisationId`, the mapping its prefix; a cursor of another Organisation counts as no cursor (§ 6.5).
- At most one `SyncSchedule` per `(sync_xero, entity type, import)`; the provider creates one only when none exists (§ 6.7; the residual is two writers creating the same schedule within one instant, § 6.7).
- `sync_xero` never stores a token: every grant read and write goes through `integrationOAuthGrantService`, and no token reaches Xero's logs, run parameters, cursors or health `details` (core I4).
- An invoice whose Contact cannot be resolved is a `failed` item, never an invoice without its Company link (§ 6.5).
- After a Disconnect commits, a run in flight stops writing within about one second, plus the item in progress: the adapter reads `readGrantStatus` before each item's write, reuses a non-null result for at most one second, and ends quietly on `null` (§ 6.5). Only a new Connect completed within the same page hides the Disconnect from that check; the Organisation check at the next token call then applies.
- A mapped invoice that was deleted in OM is never updated, restored or re-created by a sync (§ 6.5).
- A sync calls a customers or sales command only for a record whose Xero-owned values differ from Xero's current state; an unchanged record is a `skip` item with no command, event, audit entry or webhook (§ 6.2).

**Access control:** internal-only (§ 2). No new ACL features — the integration reuses `integrations.view` / `integrations.manage` / `integrations.credentials.manage` and `data_sync.view` / `data_sync.run` / `data_sync.configure`, like every data-sync provider; the Company badge's `sync_xero` read route requires `customers.companies.view`, the feature that opens the Company page (§ 0.2.10); the Company "Xero invoices" tab's route requires the same feature, since sales has no read-only invoice feature (§ 0.2.5, § 10 #21). Xero's provider routes (initiate, callback, Organisation save, Disconnect) require `integrations.credentials.manage` in the resolved organization and follow the core's route contract (core App Spec § 1.4.3, rules 1–11). Creating the default schedules is part of the Organisation save, not a separate admin action.

## 3. Workflows `PM`

### WF1: Connect a Xero Organisation

**Journey:** Admin opens Integrations -> Xero -> the Xero tab shows the redirect URI (from `APP_URL`) with a copy button -> admin registers a Web ("Auth Code") app in Xero's developer portal with that URI -> enters Client ID + Client Secret on the Credentials tab and enables the integration -> clicks Connect on the Xero tab -> Xero's consent screen (the admin picks one or more Xero Organisations) -> the callback stores the Xero grant (Account pending) and lists the `ORGANISATION`-type connection records of that consent round (`GET /connections?authEventId=` from the access token's `authentication_event_id`; the unfiltered list when the claim is missing or the filter returns nothing) -> with exactly one, the callback saves it at once only when it is the previous Organisation (`previousProviderData`), or on a first connect with no `xero.*` mapping or cursor yet; otherwise — several Organisations, or one that may differ from what existing mappings and cursors refer to (after a Disconnect or a replaced unreadable grant, rule 11) — the tab asks the admin to pick exactly one, with the § 10 #2 confirmation when it differs -> every Organisation save (`updateProviderData` with the current Grant Revision) also creates the default schedules when none exist (WF4) -> the tab shows Connected with the Organisation's name.

**ROI:** Removes the only manual setup step between a tenant and automated accounting-data sync; a 5-minute one-time setup (excluding Xero's own screens) replaces indefinite manual re-keying.

**Key personas:** OM Admin.

**Boundaries:**
- Starts when: the admin opens the Xero integration detail page to connect — with no live Xero grant (first connect, or after a Disconnect), or over a live one (Reconnect, which updates the grant in place; WF5 recovers through this path).
- Ends when: a live `active` Xero grant exists with exactly one `xeroOrganisationId` in its `providerData`. Whether syncing runs is `IntegrationState.isEnabled`, which WF1 does not require (a Reconnect after a Disconnect leaves the integration paused, § 3.5 empty states).
- NOT this workflow: the data import (WF2/WF3), token refresh during operation (WF4, the core's Token Provider), reconnecting after invalidation (WF5). Disconnect is US-1.2.

**Edge cases:**
1. Admin cancels consent, or the consent round yields no Xero Organisation -> cancel: `connect_cancelled`, nothing written; no Organisation: the grant is stored Account pending, the tab says "No Xero Organisation was authorised — Reconnect and select one", manual runs fail with the Account-pending precondition error and scheduled runs end quietly.
2. Admin authorizes 2+ Organisations -> the picker asks for exactly one; the others stay authorized at Xero (OM never calls them) until a Disconnect revokes the grant.
3. Client ID/Secret are wrong -> the code exchange fails `client_misconfigured`; the tab asks the admin to check them, without echoing Xero's response; an existing grant is untouched.
4. Admin clicks Connect in two tabs, or a callback is replayed -> the state is single-use (`consumeOAuthStateOnce` before the code exchange, rule 3): only the first callback succeeds, the other fails `connect_state_invalid`. Single use holds across replicas only with `CACHE_STRATEGY=redis`.
5. Network/timeout at Xero's token endpoint -> `connect_exchange_failed`; no grant is written and an existing grant is untouched. `APP_URL` missing in production -> Connect is disabled with "Set APP_URL before connecting" (`baseUrlMissing`, rule 8).

### WF2: Import Contacts as Companies

**Journey:** A default schedule fires (or the admin starts a run) for `xero.contacts` -> the adapter pulls Xero Contacts page by page, archived ones included (`includeArchived=true`), by keyset (§ 6.7) -> each Contact is matched against an existing OM Company or created new -> Company fields Xero owns are written when they differ from Xero; OM-only fields are left untouched -> the run completes with per-Contact create/update/skip/failed counts -> the Company page shows a Xero badge with the link and the date the Company was linked.

**ROI:** A tenant with 400 Xero customers gets 400 correctly matched OM Companies with zero manual data entry and no duplicates from repeated, concurrent or interrupted runs (§ 6.1), versus hours of CSV preparation or hand entry.

**Key personas:** OM Admin (monitors); OM Sales/CRM user (consumes the result).

**Boundaries:**
- Starts when: a sync run for `xero.contacts` begins (scheduled or manual).
- Ends when: every Contact page returned by Xero for the current window has been processed into a create/update/skip/failed outcome.
- NOT this workflow: importing invoices (WF3); supplier-only contacts are filtered out (§ 6.4).

**Edge cases:**
1. A Contact has no `TaxNumber`/`CompanyNumber` and no mapping -> a new Company is always created (never matched by Name alone); a Name match is a soft duplicate-risk warning in the run log (§ 6.1).
2. A Contact's `TaxNumber` matches an unmapped Company's `xero_tax_number` with different whitespace or casing ("GB 123 456" vs "GB123456") -> both sides are normalized (strip whitespace, uppercase) before comparison; a Company that already has a `sync_xero` mapping — including one linked earlier in the same run — is never a fallback candidate (§ 0.2.7).
3. A Contact is `ContactStatus=ARCHIVED` -> Xero returns it only because the walk sends `includeArchived=true` (§ 0.1); the mapped Company is updated with `status='archived'` / `isActive=false`, never deleted — unless the Contact carries `MergedToContactID`, where § 6.1's merge rule applies instead. `ContactStatus=GDPRREQUEST` (PII stripped by Xero) -> OM keeps its existing PII and applies only the status flip (§ 6.4, § 10 #1). An archived or GDPR-redacted Contact without a mapping creates no Company (a skip, no log row) unless an invoice's self-heal needs it (WF3 edge case 1).
4. On a first sync both runs walk everything, and later a new Contact and its first invoice can arrive within one schedule interval, so the invoices run's self-heal and the contacts run can reach the same unmapped Contact -> each writer finds or creates the Company with the Xero contact marker and then claims the mapping; a writer whose claim loses to a different Company deletes the Company it has just created and uses the winner's; a claim that finds the mapping already naming its own candidate counts as won (§ 6.1).
5. A Contact is supplier-only (`IsSupplier=true`, `IsCustomer=false`) -> filtered out, no Company created (§ 6.4); if an imported invoice later references it, the invoice-side self-heal imports it (§ 6.5).

### WF3: Import Sales Invoices linked to Companies

**Journey:** A default schedule fires (or the admin starts a run) for `xero.invoices` -> the adapter pulls `ACCREC` invoices with **`?Statuses=AUTHORISED,PAID,VOIDED&where=Type=="ACCREC"`** (the query shape that paginates, returns line items and leaves out bills, § 0.1) modified since the cursor -> for each invoice, resolve its Contact's Company (self-healing the page's missing mappings with one batched `GET /Contacts?IDs=…&includeArchived=true`, § 6.6) -> create or update the OM Invoice with its lines, status, Company link and `metadata.xero` in one sales command -> store the `InvoiceID` mapping -> the run completes with counts -> the Company page lists its Xero invoices (§ 10 #21).

**ROI:** A tenant issuing 300 sales invoices a month stops re-typing them into OM — at an estimated 3 minutes per invoice with its lines, about 15 hours of data entry a month — and every imported invoice carries the Company it belongs to, with payment status no older than one sync interval (one hour by default).

**Key personas:** OM Admin (monitors); OM Sales/CRM user (reads invoice and payment-status data against a Company).

**Boundaries:**
- Starts when: a sync run for `xero.invoices` begins.
- Ends when: every `ACCREC` invoice page in the current window has been processed into create/update/skip/failed, each successful one carrying its Company link.
- NOT this workflow: Bills (`ACCPAY`), credit notes, payment allocations, PDFs/attachments — all deferred (§ 6.3). Never writes anything back to Xero.

**Edge cases:**
1. The invoice's Contact has no mapping (or, for a new invoice, a mapping to a Company deleted in OM, § 6.5) -> the adapter fetches it with the page's other unmapped Contacts in one `GET /Contacts?IDs=…&includeArchived=true` (§ 6.6) and imports it **without the supplier filter** (an `ACCREC` invoice makes it a customer), archived or not (an archived Contact's Company is created archived), through the Company claim (§ 6.1); only when Xero does not return the Contact or it fails validation is the invoice `failed` with `xero.invoice_contact_unresolved` (§ 6.5).
2. Xero's `InvoiceNumber` is already used in the OM organization (`sales_invoices_number_unique`, which counts soft-deleted invoices) -> when the holder is this integration's own invoice for the same `InvoiceID` (its `metadata.xero.invoiceId`, left without a mapping by an interrupted run), the adapter stores the missing mapping and updates it; otherwise the item is `failed` with `xero.invoice_number_collision` and the existing invoice is untouched — no renumbering (§ 6.1). A mapped invoice, or such a holder, that was removed in OM (soft-deleted while no live Xero grant existed, § 6.2, or hard-deleted by undoing its import in the audit log) -> refused with `xero.invoice_deleted_in_om`, its warning naming the number; never updated, restored or re-created (§ 6.5).
3. An invoice is `VOIDED` -> its `statusEntryId` points at the provider's `voided` entry; never deleted, since it may already be referenced elsewhere.
4. An invoice was `DELETED` in Xero -> only possible while `DRAFT`/`SUBMITTED`, which are never imported; documented so "why doesn't OM show drafts" has an answer.
5. Xero's daily or per-minute limit is hit on a large first sync -> backoff honours `Retry-After`; on the daily cap the run commits its progress and ends quietly (`xero.daily_limit_reached`), and the next run resumes from the committed cursor (`data_sync` has one failed run state; "run-terminal" and "retryable" in this spec name what the message asks for — fix the cause first, or retry — and every next run resumes from the committed cursor) — a multi-day first sync for very large tenants, no data loss.

### WF4: Scheduled incremental sync keeps OM current

**Journey:** Saving the Xero Organisation creates the default schedules — every hour, incremental, enabled, the two half an hour apart — for `xero.contacts` and, from Phase 2, `xero.invoices` when none exist -> the platform's scheduler fires -> a `SyncRun` is created and enqueued -> the adapter resumes from `If-Modified-Since` = the committed cursor -> only changed records are processed -> once a week, while the "Weekly full resync" toggle is on, a scheduled run makes a full pass instead (§ 6.7) -> every run refreshes the Xero grant when its access token has expired, so an enabled integration never idles out.

**ROI:** Zero setup and zero ongoing effort: OM lags Xero by at most one hour by default; changes Xero's incremental feed never reports (a partially paid invoice's `DueDate`) are corrected within a week; the grant never reaches Xero's 60-day idle expiry while the integration is enabled.

**Key personas:** OM Admin (adjusts schedules only if the defaults do not fit).

**Boundaries:**
- Starts when: an Organisation is saved (default schedules) or an admin edits a `xero.*` schedule.
- Ends when: N/A — the steady-state recurring workflow, bounded per run by WF2/WF3.
- NOT this workflow: the first sync of a new Organisation (WF2/WF3 with no cursor: a full pass by construction, which commits `lastFullAt`, § 6.7).

**Edge cases:**
1. Two runs of the same entity type would overlap -> `data_sync` refuses the second (per integration, entity type and direction). The weekly full pass happens inside the regular schedule, so it never overlaps an incremental run. A schedule an admin creates in the editor defaults to "Run as full sync" every hour (§ 0.2.8); the Xero tab flags a `xero.*` schedule with `fullSync` on, since every run would then re-read everything and, starting without a cursor each time, could never resume an interrupted full pass.
2. Xero's 30-minute access token expires between ticks, or while a `xero.contacts` and a `xero.invoices` run work in parallel in separate processes -> the core refreshes once under the cluster-wide Grant Lock; the other callers wait without holding a DB connection and reuse the result. Strict rotation makes this the double-redemption race the lock exists to prevent (core § 1.4.6).
3. A run ended with `failed` items -> the next incremental run does not retry them (the cursor has passed them); the weekly full pass re-attempts them, and "Run full resync now" does so at once (§ 6.5); both ship with Phase 2, and until then only a manual run with "Run as full sync" re-attempts them (§ 7 Phase 1, known limitation).
4. The admin disables or deletes every `xero.*` schedule while the integration stays enabled -> nothing refreshes the grant; the Xero tab warns that Xero expires a refresh token unused for 60 days, shows the days left (from `refreshedAt ?? obtainedAt`, § 10 #13) and offers "Create default schedule".
5. The daily quota cannot cover a due full pass -> the run does an incremental walk, logs one warning and retries the full pass at the next run (§ 6.7).

### WF5: Reauthorize or disconnect

**Journey:** Xero rejects a refresh (`invalid_grant`: refresh token unused for 60 days, the app removed in Xero's connected apps, or the authorization revoked) -> the core marks the Xero grant `invalidated` under the Grant Lock, logging `integrations.oauth_invalidated` once -> that run ends quietly, as do the following ones -> the integration detail page shows the core's reauth banner at once (health `oauth.invalidated` at the next probe of that organization, or on "Run Check") -> the admin follows the banner link to the Xero tab -> Reconnect -> Xero consent -> when the consent round holds only the previous Organisation the callback re-selects it; otherwise the picker pre-selects it for the admin to confirm -> the next sync succeeds. Disconnect branch (US-1.2): the admin clicks Disconnect on the Xero tab -> the confirm dialog warns that the revoke ends this Xero user's access through this Xero app for every OM organization connected that way, names any other Organisations the unfiltered `GET /connections` returns (§ 10 #14), and offers "Also remove the Client ID and Secret" -> the core checks the Grant Revision, erases the grant and revokes the refresh token -> Xero's health check runs once, so the badge shows `oauth.not_connected` -> when the admin also holds `integrations.manage`, the integration is disabled, so `xero.*` schedules stop firing (otherwise that step is reported `skipped`, the tab says so, and scheduled runs end quietly without a grant); a run in flight stops writing within about one second, plus the item in progress (§ 6.5).

**ROI:** No silent, indefinite sync failure — a dead grant shows on the integration page as soon as the next run's refresh observes Xero's rejection (≤ one schedule interval, one hour by default), instead of a tenant discovering stale data weeks later; Disconnect leaves no usable Xero refresh token in OM.

**Key personas:** OM Admin.

**Boundaries:**
- Starts when: a refresh under the Grant Lock gets a terminal response from Xero (`invalid_grant`), or the admin starts a Disconnect.
- Ends when: the admin reconnects and the first sync after it succeeds, or the Disconnect has erased the grant and logged its revocation outcome (grant erased and revoked, `isEnabled=false` when the admin holds `integrations.manage`, Client ID/Secret kept unless the admin chose to remove them).
- NOT this workflow: a transient refresh failure (core `transient`: grant untouched, a still-valid token returned `degraded`, the run retried by `data_sync`), a wrong Client ID/Secret (`client_misconfigured`: fix the configuration, never a reconnect), a missing scope (`scope_insufficient`: the run fails run-terminal naming the scope; recovery is a Reconnect).

**Edge cases:**
1. Admin disconnects while a run is in flight -> the adapter reads `readGrantStatus` before each item's write (a non-null result reused for at most one second), so after the erase the run finishes the item in progress and writes for at most about one second more, then ends quietly (a Xero call rejected after the revoke ends it the same way once the retry's `getAccessToken` returns `not_connected`); items written earlier stay, and the cursor is not advanced past the partial page. Schedules skip quietly while the integration is disabled (§ 0.2.8), and Xero-sourced invoices become editable (§ 6.2). Xero unreachable for the revoke -> the erase stands; after 5 minutes the tab says "Xero could not confirm the disconnect — remove the app in Xero's connected apps". An `invalidated` grant is erased without a revoke (its tokens are already dead).
2. Reconnect selects a **different** Xero Organisation -> while Xero-sourced invoices of the previous Organisation exist, the save is refused, naming their count, because they hold their numbers (§ 10 #20); otherwise, per § 10 #2 and rule 11, the admin confirms an explicit choice naming both Organisations and the affected counts before `updateProviderData`; the `xero.*` cursors carry the old `xeroOrganisationId`, so the next run of each entity type is a full pass of the new Organisation, and a run started for the old one aborts without committing when it sees the change. Mappings are never auto-cleaned.
3. The health probe cannot see a dead refresh token on its own (it never refreshes, core R10); detection waits for the next run that needs a refresh — at most one schedule interval.
4. Only the selected Organisation's connection record was removed in Xero (the grant still valid) -> calls for it are rejected; the adapter confirms with `GET /connections` that no record with the selected `tenantId` remains and fails the run run-terminal with "Xero Organisation no longer authorised — Reconnect and select it". The grant stays `active`.
5. One Xero user connects several OM organizations (for example an accountant serving several OM tenants) through the same Xero app -> revoking one grant ends every grant of that Xero user for the app, with the shared connection records (core Q8; [Sandbox, 2026-10-13]) -> the Disconnect dialog always warns about that reach and names the Organisations the unfiltered `/connections` list returns (§ 10 #14).

|---|---|---|---|
| Detect Xero's rejection | `getAccessToken` (core): invalidation under the Grant Lock, `grant_invalidated` | No | Core |
| End runs quietly | Adapter on `grant_invalidated` / `not_connected` (and Account pending on a scheduled run), at the start of a run and on any token call, and on a missing grant before each item's write (`readGrantStatus`, reused ≤ 1 s); scheduled vs manual by `SyncRun.triggeredBy`; `operationalTelemetry` off | **Yes** | Required by the core's first-consumer acceptance (core App Spec § 7, Phase 2) |

### Test seam

Phase 1's E2E test (connect → token → disconnect) and the adapters' tests need Xero without Xero. The descriptor's endpoints and the API client's base URL are code constants, and the core accepts a loopback `http:` endpoint only outside production or with `OM_ENABLE_TEST_OAUTH_GRANTS` on (core feature spec, descriptor validation details). The seam has three parts:
- **Fake Xero API** (`lib/testing/fakeXeroApi.ts`): `node:http` on `127.0.0.1:0`, serving `GET /connections` (with and without `authEventId`) and the `Contacts` and `Invoices` lists (Phase 1 serves Contacts; the `Invoices` list, `Statuses`, `Date` ranges and fetches by id arrive with Phase 2) (`IDs` filters included) and fetches by id with what the adapters rely on — keyset paging under `If-Modified-Since`, `includeArchived`, `Statuses`, `Date` ranges, `xero-tenant-id`, the quota headers — and accepting only access tokens the core's fake authorization server issued; injected `429` with `Retry-After`, `401`, `403` with `insufficent_scope`, `5xx` and delays; seeded Organisations, Contacts and Invoices; recorded requests. It imports no `@playwright/test`. OAuth is the core's fake authorization server (`startFakeAuthorizationServer`, `rotation: 'strict'`, 1800-second tokens), imported from the core's `lib/oauth/testing/fakeAuthorizationServer` subpath, its only import path. Xero adds no OAuth fake.
- **Not a contract:** the seam rides the core's `OM_ENABLE_TEST_OAUTH_GRANTS` flag, which `BACKWARD_COMPATIBILITY.md` lists as not a contract; the seam's test-only route, its actions, the `om_test_seam_` Client ID prefix and the fakes may change, and the flag is never set in production.
- **Endpoint override:** factories build the descriptor and the API client from endpoints and a base URL, the code constants being the defaults. Jest passes the fakes' endpoints directly. In the web process the factories use the fakes only while `OM_ENABLE_TEST_OAUTH_GRANTS` is on — the core's flag, wired the same way (the CLI test harness and the CI runner env, never `.env.example`) — and only for the OM organization that started them; every other organization keeps Xero's real endpoints. The endpoints come from the fakes running in the process (on `globalThis`, as the core keeps its fake), never from a request or an env value (core R12). Under the flag, an organization whose Client Configuration carries the seam mark (below) never falls back to those real endpoints: where its fakes are not running in the process (a queue worker, a restarted server), the factories build neither the descriptor nor the API client, and a run ends with a run-terminal error (`xero.test_fakes_unavailable`) instead of calling Xero with fake credentials and tokens.
- **Test-only route** `POST /api/sync_xero/test-fakes`, modelled on the core's `test-oauth-grants`: flag off → 404 before any fake is imported; `integrations.credentials.manage` and the mutation guards; actions `start` (both fakes and a generated Client Configuration for the caller's organization), `seed` (fake Xero data and, in an organization `start` prepared, the `sync_xero` mappings Playwright's fixtures need), `inject`, `authorize`, `counters` and `reset`; no response carries a token. The generated Client Configuration carries a seam mark (a reserved Client ID prefix). An organization belongs to the seam while its Client ID carries the mark or its fakes run in the process, and every `sync_xero` row of such an organization counts as the seam's. `start` answers 409 when an organization that does not belong to the seam holds a `sync_xero` grant, mapping or cursor, or a non-blank Client ID; `reset` erases only the seam's rows (grant, schedules, mappings, cursors and the Client Configuration) and stops the fakes; and while the override is active for an organization, its Xero tab shows a visible notice. Playwright intercepts the browser's redirect to the fake's authorize URL and has `authorize` issue the code (`issueAuthorizationCode`), so the browser never reaches a loopback port. A Playwright helper probes the route and skips the spec on a 404; a 404 throws when the Playwright process's own env has the flag on, like the core's helper.

**What each runner covers.** Sync runs execute on queue workers: the run start enqueues the run (`data_sync/lib/start-run.ts:136-138`), and Playwright drains the queue in a child process or in its own process (`helpers/integration/queue.ts:72-80`), never in the web process that holds the fakes. Run and adapter coverage therefore stays in Jest, with the fakes in-process. Playwright covers the routes (initiate, callback, Organisation save, Disconnect, the two Company read routes, the test-only route), the Organisation picker, the Company badge, the Xero tab and the Company "Xero invoices" tab, with fixtures created through the API: Companies and invoices, with their Company links, through their CRUD routes, and the `sync_xero` mappings through `seed`.

**Why `start` refuses.** The core's route writes only the `test_oauth_grant` integration, whose marketplace entry makes a misconfigured flag visible. Without the refusal, Xero's `start` would overwrite an organization's real `sync_xero` Client Configuration and point its real grant at loopback fakes with nothing on screen to show it, and a later Disconnect would revoke against the fake. The 409, `reset`'s limit to the seam's rows and the tab's notice confine a flag copied into production to organizations with no `sync_xero` state of their own, and make it visible there.

Scored 2 commits in WF2 (Phase 1), beside the API client it fakes: the fake Xero API with the endpoint factories, then the test-only route with its helper and the tab's notice, as the core splits its fake server (P2b) from its route and helper (P4a). It adds no OAuth code, so the OAuth part stays 5.

## 5. User Stories `PM`

> Every story traces to a workflow step (§ 3) and has happy, alternate and failure paths.

### WF1: Connect a Xero Organisation

**US-1.1** As an OM Admin, I connect my Xero Organisation so that Contacts and Invoices can start syncing into OM.
Success: after consent, exactly one live `active` Xero grant exists for the OM organization, with exactly one `xeroOrganisationId` in its `providerData`; one `integrations.oauth_connected` and one `integrations.oauth_external_account_selected` log entry name the acting admin; the Xero tab shows "Connected" with the Organisation's name; an hourly incremental schedule exists for each `xero.*` entity type that had none.
**Happy path:** Admin copies the redirect URI, registers the Xero app, enters Client ID/Secret, enables the integration, clicks Connect, completes consent for one Organisation, and returns to a "Connected" Xero tab with that Organisation auto-selected and the default schedules listed.
**Alternate paths:** Admin authorizes several Organisations -> the grant is Account pending until the picker saves exactly one (`PRACTICE` records are not offered). Admin connects again over a working grant (Reconnect) -> the grant is updated in place; if the consent round holds only the previous Organisation the callback re-selects it, otherwise the picker pre-selects it. Admin connects after a Disconnect while `xero.*` mappings exist -> no automatic selection: the picker shows the Organisation the mappings refer to (their prefix, § 10 #15) and the § 10 #2 confirmation when the choice differs. Admin abandons the picker -> the grant stays Account pending; manual runs fail with a precondition error naming the cause, scheduled runs end quietly, the health badge shows `degraded`. A mutation guard blocks the callback's automatic Organisation save -> the grant stays Account pending and the tab asks the admin to save the Organisation.
**Failure paths:** Wrong Client ID/Secret -> `client_misconfigured`; the tab shows a generic "check the Client ID and Secret" message; an existing grant is untouched. Network timeout mid-exchange -> `connect_exchange_failed`; nothing written or changed. Replayed or expired state (> 5 minutes) -> `connect_state_invalid`, nothing written. Another admin reconnected while this one had the picker open -> saving returns the standard 409 conflict; the tab reloads. Creating a default schedule fails after the Organisation was saved -> the Organisation stays saved and the tab shows "No schedule for `xero.invoices`" with "Create default schedule".

**US-1.2** As an OM Admin, I disconnect Xero so that no further syncing happens, OM no longer holds access to my Xero data, and previously imported invoices become editable again rather than staying locked.
Success: the Xero grant is erased (no decryptable Xero refresh token remains, core I5) and, for an `active` grant, its refresh token revoked at Xero (RFC 7009); the revocation outcome is logged; the health badge shows `oauth.not_connected` (one health check runs before the integration is disabled, since the scheduled probe skips disabled integrations); `IntegrationState.isEnabled=false` when the admin also holds `integrations.manage`, the feature of the integration state route (otherwise that step is reported `skipped` and the tab asks for the integration to be disabled), so every `xero.*` schedule stops firing without being deleted (§ 0.2.8) and resumes when the admin re-enables the integration after reconnecting; the Client ID/Secret stay unless the admin ticked "Also remove the Client ID and Secret"; every invoice locked by US-3.2's guard becomes editable — `SyncExternalIdMapping` rows stay, so the Xero link still displays.
**Happy path:** Admin clicks Disconnect, confirms, sees "Not connected"; a previously read-only Xero-sourced invoice now accepts API updates.
**Alternate paths:** The dialog always warns that the revoke ends this Xero user's access through this Xero app for every OM organization connected that way, and names the Organisations other than the selected one that the unfiltered `GET /connections` lists (§ 10 #14); the admin confirms or cancels. Admin ticks "Also remove the Client ID and Secret" -> after the erase the route saves an empty Client ID and Secret (keeping `weeklyFullResync`); the tab shows "not configured". Admin disconnects mid-run -> no cancellation: the adapter's `readGrantStatus` before each item's write returns `null` once its one-second reuse runs out, so the run finishes the item in progress, writes for at most about one second more and ends quietly; items written before the Disconnect stay, and the cursor is not advanced past the partial page. Admin disconnects an `invalidated` grant -> erased without a revoke.
**Failure paths** (the route runs the core's `disconnect` first, so every failure before the erase leaves everything unchanged):

| Step that fails | State after |
|---|---|
| Revision check (someone reconnected meanwhile) | Standard 409; nothing erased, integration still enabled |
| Grant unreadable | `disconnect_tokens_unreadable`; nothing erased; the tab offers "Disconnect anyway" (`force: true`) behind a confirm dialog saying the app must also be removed in Xero (rule 10) — that erases without a revoke |
| Lock deadline or DB error | `transient`; nothing erased; the admin retries |
| Revoke (Xero unreachable) | Grant erased; `integrations.oauth_revocation_failed` logged; the tab tells the admin to remove the app in Xero's connected apps; the remaining steps still run |
| Health check, disabling the integration, or removing the Client ID/Secret | Grant erased, invoices editable; the route reports the step that failed; if the integration stays enabled, scheduled runs end quietly with `not_connected` until the admin disables it |

### WF2: Import Contacts as Companies

**US-2.1** As an OM Admin, I let the default schedule (or a manual run) sync Contacts so that Xero customers appear as Companies in OM without manual entry.
Success: every active Customer Contact (§ 1.3) has exactly one OM Company carrying its Xero-owned values and addresses as § 6.2a maps them, and no Contact is skipped because another was edited while the walk ran (keyset paging; § 6.7 names the one exception); the run's create/update/skip/failed counts are visible in the Data Sync dashboard.
**Happy path:** A new Contact -> matched by its normalized tax or registration number to an unmapped Company, or created with the Xero contact marker; either way the mapping is stored by a Company claim, and the run's tax-number index drops the claimed Company.
**Alternate paths:** Re-running after no Xero changes -> nothing is returned by `If-Modified-Since`, so the run processes nothing; a record Xero re-touched without changing a Xero-owned field is a `skip` item — no command, no event (§ 6.2). A Contact archived in Xero -> returned because the walk sends `includeArchived=true`, and its Company is archived; an archived Contact without a mapping creates no Company. A Contact carries `MergedToContactID` -> the Company mapped to the losing `ContactID` is not updated; a refused item names both OM Companies and the surviving `ContactID` (§ 6.1, § 10 #8, #22). An invoices run's self-heal reaches the same unmapped Contact at the same moment -> one Company claim wins; the other writer, if it created a different Company, deletes it and uses the winner's. Two Contacts share a tax number (Xero does not enforce uniqueness) -> the first claims the unmapped Company, the second no longer finds it in the index, creates its own Company and logs a warning naming both Contacts. The Contact's mapped Company was deleted in OM -> refused with `xero.company_deleted_in_om`; the Contacts run does not re-create it (§ 6.5). A Contact whose Company an invoice's self-heal created -> its addresses arrive with this run, since only the Contacts run writes addresses (§ 6.2a).
**Failure paths:** A Contact with a blank required field (`Name` is required by Xero, so rare) -> `failed` with a clear message, the run continues. A Contact's email, phone or website that OM's validators would reject (a Xero phone without a country code is common) -> that value is left out and the adapter logs an item warning naming the field; the rest of the Contact syncs (§ 6.2a). A crash between an address create and its mapping -> the retry creates that address again, a duplicate row the user removes (§ 6.2a). A crash between the Company write and its claim -> the retry finds the Company by its Xero contact marker and claims it; no duplicate, unless another writer claimed a different Company meanwhile — then the marked Company stays unmapped and the next `xero.contacts` full pass reports it (`xero.company_orphaned`). A crash or a failed custom-field write between the Company row and its marker (the customers command writes custom fields right after its own transaction, § 0.2.7) -> the item fails or the run stops, and the retry creates a second Company, flagged by the Name-based duplicate-risk warning. The claim lock is not obtained within 15 seconds -> the run fails as retryable, its cursor committed through the last complete page. Token failures by class (core § 1.4.5): `transient` or `platform_unavailable` -> the run fails as retryable, its cursor committed through the last complete page; `client_misconfigured` (including a changed Client ID) or `scope_insufficient` -> run-terminal failure naming the fix (check the Client ID/Secret; Reconnect). Account pending (including when a Reconnect empties the Organisation mid-run) -> a manual run fails with the run-terminal precondition error; a scheduled run ends quietly with one warning. The grant's Organisation changed mid-run -> run-terminal "Xero Organisation changed — the next run syncs the new one", the cursor not advanced past the partial page. No live grant, or an `invalidated` grant, before or during the run -> the run ends quietly: no item written after that point (a missing grant is checked before each item, an `invalidated` one at each token call), the cursor not advanced past the partial page, one `warn` log naming the cause; the engine finalizes it `completed`, and because the adapter leaves `operationalTelemetry` off, that never overwrites the health badge (§ 0.2.8) — never a failed run with an error report on every scheduled tick (the core's first-consumer acceptance).

**US-2.2** As an OM Sales/CRM user, I see that a Company comes from Xero so that I know it is the current record from accounting.
Success: for every user who can open the Company (`customers.companies.view`), the Company detail page shows a Xero badge with the link to the Xero contact and the date the Company was linked (the mapping row's `lastSyncedAt`, set only by the Company claim that stored the current link), read from the `sync_xero` badge route (§ 3.5). The badge claims no sync time or sync status: the mapping records neither (§ 0.2.7).
**Happy path:** The badge reads "Xero · linked since 3 Oct 2026" and links to the contact in Xero.
**Alternate paths:** A Company with no `sync_xero` mapping -> no badge. The integration is disconnected -> the badge stays, since the mapping is kept.
**Failure paths:** The badge route fails -> the badge is not rendered and the rest of the page is unaffected, never an error. A failed sync of the Contact shows in the run's failed items (§ 6.5), not on the badge.

**US-2.3** As an OM Sales/CRM user, my edits to OM-only Company fields (owner, tags, notes) are never overwritten by the next Xero sync.
Success: after a re-sync, `ownerUserId`, tags, comments, a non-archive `status` and the address rows the user added are byte-identical to what the user last set; only Xero-owned fields and Xero-owned addresses (§ 6.2a) changed if Xero changed them.
**Happy path:** User sets an owner, a tag and a delivery address of their own; the next sync updates the Xero postal address; owner, tag and the user's address are untouched.
**Alternate paths:** N/A.
**Failure paths:** N/A — an invariant, not a user-triggered action; a violation is a bug.

### WF3: Import Sales Invoices linked to Companies

**US-3.1** As an OM Admin, I let the default schedule (or a manual run) sync Invoices so that Xero sales invoices appear in OM attached to the right Company.
Success: every `ACCREC` Xero invoice in `AUTHORISED`, `PAID` or `VOIDED` status modified since the cursor has exactly one OM Invoice whose Company link names the Company its Contact maps to, with lines and header amounts matching Xero exactly as § 6.2a maps them — every amount Xero's invoice list reports stored unchanged, each line's net and gross set by `LineAmountTypes`, no OM recalculation — and its status entry matching Xero's status.
**Happy path:** The Contact was synced earlier -> the invoice is created or updated with its lines, status, Company link and `metadata.xero` in one `sales.invoices.create` / `.update` command, then the `InvoiceID` mapping is stored.
**Alternate paths:** The Contact has no mapping -> the adapter fetches it in the page's batched `IDs` call (§ 6.6), creates or matches the Company through the Company claim without applying the supplier filter (the Company's addresses follow with the Contacts run, § 6.2a), then proceeds. The Contact's mapping names a Company deleted in OM -> for a new invoice the self-heal re-creates the Company through the claim; an existing invoice keeps its link until then (§ 6.5). The invoice changed in Xero -> the header, the Company link and the lines are updated; the guard does not apply to the adapter, which writes through the commands.
**Failure paths:** Xero does not return the Contact or it fails validation -> `failed` with `xero.invoice_contact_unresolved`; no invoice is created. The invoice write fails (validation, DB) -> the command's single transaction leaves no invoice, lines or Company link behind; `failed` with the reason. The mapping write fails after the invoice committed -> the invoice exists without a mapping; the next attempt's create collides on the number, finds the holder's `metadata.xero.invoiceId` equal to this `InvoiceID` and stores the mapping instead of failing (a holder deleted in OM is refused as below); a different holder -> `failed` with `xero.invoice_number_collision`, the existing invoice untouched. (If Xero renumbers the invoice between the two attempts, the unmapped copy stays as an orphan; accepted as a crash-plus-edit residual.) The mapped invoice was removed in OM (soft-deleted while no live Xero grant existed, § 6.2, or hard-deleted by undoing its import in the audit log) -> refused with `xero.invoice_deleted_in_om`, its warning naming the number; never updated, restored or re-created. A soft-deleted invoice that is restored (the delete command's undo) is updated by the next sync that returns it — a Xero change or a full pass.

**US-3.2** As an OM Sales/CRM user, I cannot change a Xero-sourced invoice while a live Xero grant exists, so it never silently diverges from the accounting record.
Success: `sales.invoices.update` / `.delete` through the invoices API on an invoice with a `sync_xero` mapping **while a live Xero grant exists** (§ 1.3, § 6.2) is rejected by the mutation guard with "Managed by Xero". The invoices API is the only invoice edit surface in OM today (§ 0.2.5); the audit log's undo and redo run no mutation guard, so undoing an adapter write bypasses the lock — an undone update is overwritten by the next sync that returns the invoice, an undone create is a removed invoice (§ 6.5); the Company "Xero invoices" tab (§ 10 #21) is read-only by construction. Disconnecting Xero (US-1.2) lifts the restriction; pausing syncs (disabling the integration) does not, since the next sync after re-enabling would overwrite any edit.
**Happy path:** An API client's update to a Xero-sourced invoice gets the "Managed by Xero" rejection naming the integration.
**Alternate paths:** Xero is disconnected -> the same update succeeds; the mapping stays, so the Xero link remains visible.
**Failure paths:** The grant cannot be read -> `readGrantStatus` returns `unavailable`, which counts as live: the guard fails closed and rejects.

**US-3.3** As an OM Sales/CRM user, I see an invoice's payment status (paid / partially paid / outstanding) sourced from Xero so I don't have to check Xero separately.
Success: `paidTotalAmount` / `outstandingAmount` on the OM Invoice match Xero's `AmountPaid` / `AmountDue` as of the last sync.
**Happy path:** A partially paid Xero invoice -> OM shows the same partial amounts.
**Alternate paths:** Fully paid between syncs -> the next sync sets the `paid` status entry and the amounts; OM never shows a payment as reversed unless Xero reports it.
**Failure paths:** N/A — a read-only projection of imported data.

**US-3.4** (Phase 2, § 10 #21 (a)) As an OM Sales/CRM user, I open a Company and see its invoices from Xero, so I can answer "what has this customer been invoiced and what is still open" without opening Xero.
Success: the Company's "Xero invoices" tab lists every Xero-sourced invoice whose Company link names this Company, with number, issue date, due date, total, paid, outstanding, status and a link to the invoice in Xero, newest first, paged at ≤ 100 rows.
**Happy path:** The tab shows 12 invoices, 2 outstanding, totals matching Xero.
**Alternate paths:** No invoices yet -> "No invoices from Xero for this company yet." Xero disconnected -> the tab still lists the imported invoices (they stay in OM), without a "Managed by Xero" note.
**Failure paths:** The tab's read route fails -> the standard `ErrorMessage` with retry. A user who cannot open the Company never reaches the tab: the route requires `customers.companies.view`, the feature that opens the page (§ 10 #21).

### WF4: Scheduled incremental sync keeps OM current

**US-4.1** As an OM Admin, once I save the Xero Organisation OM keeps syncing every hour without my creating a schedule, so data stays current and the Xero grant never idles out.
Success: after the first Organisation save, exactly one enabled, hourly, incremental schedule exists per `xero.*` entity type; further saves create no second schedule and re-create a deleted one; every run refreshes the grant when its access token has expired.
**Happy path:** Admin connects; in Phase 1 the Xero tab lists the hourly Contacts schedule, and from Phase 2 two schedules (Contacts on the hour, Invoices on the half hour); an hour later each entity type has a run.
**Alternate paths:** An admin already created a `xero.contacts` schedule -> it is kept as is (from Phase 2, unless it equals the Phase 1 default, which is moved to cron, § 6.7), and only `xero.invoices` gets a default. An admin turns a schedule's "Run as full sync" on -> the tab flags it. An admin deletes every schedule -> the tab warns about Xero's 60-day expiry with the days left and offers "Create default schedule".
**Failure paths:** The scheduler rejects the registration -> no schedule row is written (`saveSchedule` registers first, § 0.2.8), the Organisation stays saved, and the tab offers "Create default schedule".

**US-4.2** As an OM Admin, I keep the "Weekly full resync" toggle on (the default) and can run a full pass now, so changes Xero's incremental feed never reports are corrected.
Success: with the toggle on, at most 7 days pass between the starts of full passes of each entity type, plus any quota deferral, each logged; a `DueDate` changed on a partially paid Xero invoice is correct in OM after the next full pass; a pass calls a command only for records whose Xero-owned values changed; "Run full resync now" starts a full pass of both entity types at once.
**Happy path:** A scheduled run finds `lastFullAt` 7 days old, walks every record, and commits a new `lastFullAt`.
**Alternate paths:** Toggle off -> runs stay incremental; the help text names what that leaves stale (§ 6.7). A full pass is interrupted (daily cap, worker restart) -> the next run resumes it from the resume point in the committed cursor, skipping no record (§ 6.7). The first sync of an Organisation (no cursor) is a full pass itself -> it commits `lastFullAt`, so the first weekly pass follows 7 days later rather than at the next run. The quota cannot cover a due pass -> the run walks incrementally, logs one warning, and tries the pass at the next run.
**Failure paths:** "Run full resync now" while a run of that entity type is in progress -> refused by `data_sync`'s overlap check with its existing message. While the integration is disabled -> refused with 409 "Integration is disabled".

## 6. Decisions `PM` — matching, field mapping, re-import, scope and full pass

> § 6.1 matching keys · § 6.1b records that already exist in OM · § 6.2 re-import and overwrite · § 6.2a field mapping · § 6.3 invoice scope · § 6.4 archived, voided and deleted records, individuals vs. companies · § 6.5 import order and failures · § 6.6 rate limiting · § 6.7 full pass.

### 6.1 Matching keys

**Contacts -> Company:**

| Candidate key | Reliability | Risk |
|---|---|---|
| `ContactID` (via the mapping, after the first sync) | Highest — Xero-guaranteed unique, immutable | None once a mapping exists; Xero merges supersede an id (below) |
| `TaxNumber` (normalized: strip whitespace, uppercase) | Medium | Often blank; formatting drift (country prefix) reduced but not removed by normalization; not unique in Xero (sibling entities can share one) |
| `CompanyNumber` (max 50) | Low-medium | As `TaxNumber`, and filled in less often |
| `ContactNumber` (max 50) | Low as a first-run key, the better of the two external-key fields | API-writable only, so it cannot drift in the Xero UI; blank unless the Organisation used another integration |
| `AccountNumber` (max 50) | Lower than `ContactNumber` | Editable in the Xero UI and the API |
| `Name` (max 255) | **Not an auto-match key** | Xero tells integrators not to rely on `ContactName` as a unique reference (§ 0.1); casing and punctuation drift ("Acme Ltd" vs "ACME LTD.") |
| `TaxNumberType` | **Not usable for normalization** | US-only enum |

**Decision (2026-10-12):** `ContactID` via the mapping is the sole primary key and always wins once it exists. On the first sync of a Contact, fall back in order to `TaxNumber` (normalized), then `CompanyNumber` (normalized), both matched against `xero_tax_number` — **only among Companies that have no `sync_xero` mapping**, because storing a mapping for an already-mapped Company re-points that Company's mapping (§ 0.2.7). A match is claimed (below) and logged "matched existing company by tax/registration number". When several unmapped Companies carry the number, the oldest is claimed and the item warning `xero.company_match_ambiguous` names every candidate (§ 6.1b, Option B). **Never auto-match on `Name`.** A Contact whose Name matches an existing Company but whose numbers don't (or are blank) creates a new Company and a **soft duplicate-risk warning** (`xero.company_duplicate_risk`) in the run log — the "warn, don't silently merge, don't hard-block" pattern `sync_excel` established. The fallback index is built once per run and drops a Company as soon as it is claimed, so a second Contact with the same number (Xero does not enforce uniqueness) creates its own Company, and the run logs a warning naming both Contacts.

**Company claim.** Two writers create Companies — the Contacts run and the invoices run's self-heal (§ 6.5) — and on a first sync both walk everything. The mapping service cannot arbitrate between them: it re-points a mapping to the last writer and has no unique index (§ 0.2.7). For a Contact without a mapping — and, in an invoice's self-heal, for one whose mapping names a Company deleted in OM (§ 10 #23 (c)) — the adapter therefore:
1. looks for an unmapped Company carrying the Xero contact marker `xero_contact_id = <xeroOrganisationId>:<ContactID>` (left by an interrupted attempt or a concurrent writer; the marker sits on the profile record, so the lookup resolves the profile's `CustomerEntity` id, the id every mapping uses, § 1.4) in the run's marker index — built once per run from the organization's marker values, like the tax-number index, because no index covers a lookup by value (§ 0.2.7) — then for the tax/registration-number fallback above; with neither, it creates the Company with the marker through `customers.companies.create`;
2. claims the mapping: under `withAdvisoryXactLock` with the key `sync_xero_claim:<organizationId>` (one key per OM organization, so a run of a previous Organisation still in flight is serialized too) and `maxConcurrentHolders: 4` for the `sync_xero_claim` namespace (per process; the default pool holds 20 connections, `DB_POOL_MAX`), it re-reads the Contact's mapping and, for an existing candidate, the Company's mapping on the lock transaction, and stores the mapping only when both are free — in the self-heal, a Contact mapping that names a Company no longer in OM counts as free, checked on the same transaction, and the store re-points it — milliseconds of DB work, no Xero call, no command inside the lock (§ 0.2.7). A mapping that already names the candidate (another writer found it by its marker and claimed it first) counts as won;
3. after a won claim it writes the Xero-owned fields (a fallback-matched Company receives the marker with them; addresses only in the Contacts run, § 6.2a); after a claim lost to a different Company it uses the Company the existing mapping names, deletes a Company it created in step 1 through `customers.companies.delete`, and sends a fallback match that another Contact claimed meanwhile back to step 1 without the fallback. The deleted Company still passes through the customers commands' create and delete events, which reach every `*` subscriber (the outbound webhook dispatcher, workflow and business-rule triggers), and through the audit log and search index: a webhook consumer sees it created and deleted, and an audit-log undo of the delete restores it. The delete is refused when a person or deal was attached to the Company meanwhile (`customers/commands/companies.ts:1039-1063`, which locks the Company row before the check since #7628); the Company then stays, unmapped.

The marker index is a snapshot: a Company another writer marks after it was built is missed, both writers then hold a Company, and the re-read under the lock lets exactly one claim win while the other writer deletes its own (step 3); the retry of an interrupted run builds a fresh index, which holds the Company the attempt left. A mapped Contact needs no claim; the Contacts run refuses a Contact whose mapped Company was deleted in OM (`xero.company_deleted_in_om`, § 6.5). When the lock cannot be obtained (`AdvisoryLockUnavailableError`: the 15-second wait deadline, which includes waiting for a holder slot, or a transient DB error), the run fails as retryable with its cursor committed through the last complete page, like a `transient` token failure; the retry finds the Company it created by its marker. A `commit_unknown` outcome means the claim may have committed; the next run's re-read finds a mapping that already names the candidate and counts the claim as won. No deadlock can form: the helper takes the lock with `pg_try_advisory_xact_lock` and ends every failed attempt's transaction, so a waiter holds no connection and no lock; a holder works only on its own lock transaction (no fork, no second connection, no Grant Lock, token call or command); and the writer holds no other transaction when it asks, since the Company command has already committed. A holder can wait only on a row lock of a transaction that never waits for the claim key, so no wait cycle exists, and four holders per process cannot exhaust the pool.

Residuals: (1) the Company row commits without its marker — a process crash, or a failure of the custom-field write the customers command makes right after the Company's own transaction (`customers/commands/companies.ts:550-557`; the command then fails) — and the retry creates a second Company, flagged by the Name-based duplicate-risk warning; (2) a marked Company that no mapping names remains after a crash between a create and its claim while another writer claims a different Company, a crash between a lost claim and the deletion, a deletion refused by the dependents check, or an audit-log undo of the deletion. The `xero.contacts` full pass owns the report: once drained, it logs a `xero.company_orphaned` warning for each marked Company whose marker's Contact is mapped to another Company or to none, skipping Companies created within the minute before the report runs (OM's clock on both sides), so a Company whose claim is still in flight — a claim gives up after 15 seconds — is never reported. A reported Company is never deleted automatically, since users may have attached data to it.

**Limit of the tax-number fallback:** `xero_tax_number` is introduced by this integration, so it exists only on Companies created by a Xero sync (already mapped, never fallback candidates) or populated by an admin before the first sync. It does not prevent duplicates against manually entered Companies whose tax id lives elsewhere; the setup docs suggest populating `xero_tax_number` on existing Companies before the first sync, and § 6.1b's ambiguity reporting plus the Name warning are the safety net.

**Xero contact merges.** `MergedToContactID` names the surviving contact when a Xero user merges two; two OM Companies then map to what Xero treats as one contact, and only one would keep receiving updates. The signal arrives only on a paged walk or a fetch by id, and the merged-away contact is archived (§ 0.1; [Sandbox, 2026-10-13]), so the Contacts walk is paged, sends `includeArchived=true` and never uses `summaryOnly`, which drops fields of that class. On a Contact with a non-empty `MergedToContactID`, the adapter does not update the Company mapped to the losing id (this rule wins over § 6.4's archive rule, since the merged-away contact is `ARCHIVED` too: no status flip), records the supersession in the losing Company's `xero_merged_into` field (§ 10 #22 (b); the mapping service has no status or setter for it, § 0.2.7), and logs a refused item naming both OM Companies and the surviving `ContactID`. Xero moves the losing contact's invoices to the surviving contact (to be confirmed in the sandbox, § 10 #11 (l); the OpenAPI does not say): the Company link of each follows on the next sync that returns it, which links the invoice to the Company mapped to the surviving Contact (self-healed when unmapped); if the move bumps no `UpdatedDateUTC`, that sync is the next full pass — never, with the weekly full resync off (§ 6.7). Merging two OM Companies means reassigning their invoices, persons, deals and owners, which has no OM primitive and no safe automatic answer, so it stays a human decision (§ 10 #8).

**Invoices -> OM Invoice:** `InvoiceID` via the mapping is the only key — no fallback. `InvoiceNumber` is rejected because OM's `sales_invoices_number_unique` constraint means a Xero number can collide with an unrelated, manually created OM invoice, and because for `ACCPAY` bills the number is the supplier's free text with no uniqueness at all (moot while only `ACCREC` is in scope). A collision with an unrelated invoice is a `failed` item resolved by the admin — never auto-suffixed or renamed, which would diverge from Xero's numbering. A collision with this integration's own unmapped invoice (same `metadata.xero.invoiceId`) is recovered by storing the mapping (US-3.1).

### 6.1b Records that already exist in OM before the first import

**What the reference CSV import does** (`packages/core/src/modules/sync_excel/lib/adapters/customers.ts`): `resolveExistingPersonId` tries the mapping, then an email dedupe index. `buildEmailDedupeIndex` loads every active, non-deleted Person in scope ordered by `createdAt: 'asc'` and fills a `Map` with `if (!email || index.has(email)) continue`. Consequences:

1. **Ambiguity is not detected.** When two Persons share an email, the oldest wins silently.
2. **No partial or fuzzy matching** — an exact normalized email only.
3. **Conflicting data is not surfaced** — once matched, the incoming non-blank values win (§ 6.2).
4. The index is built once before the run (two rows with one email in a file can create two records), and it filters to `isActive: true` (an archived Person never matches, so a duplicate is created beside it).

That suits an attended, one-file import and fits an unattended, scheduled integration less well.

| Option | Description | Trade-off |
|---|---|---|
| **A — Mirror the reference exactly** | One deterministic fallback key (normalized `TaxNumber`, then `CompanyNumber`), oldest wins, no ambiguity reporting | Cheapest and consistent with the precedent, but silent ambiguity resolution in a job nobody watches |
| **B — Mirror the reference, but report ambiguity (chosen)** | Same keys and oldest-wins resolution among unmapped Companies, **plus** a warning item naming every candidate when more than one matches, and the Name-based duplicate-risk warning (§ 6.1) | Identical to A for every unambiguous record; one extra query shape (count candidates) and some run-log surface; the admin learns on the first run |
| C — Queue every first-sync candidate for human confirmation | No fallback matching; plausible matches become review items | Safest against wrong merges, but needs a review UI `data_sync` lacks and turns a first sync of thousands of contacts into a data-entry project |

**Decision (2026-09-27): Option B.** It reuses the CSV import's approach and fixes the one property that does not survive unattended execution. Option C fits a later phase if tenants report wrong matches.

**Asymmetry with Invoices:** the fallback applies to Companies only. A pre-existing OM invoice is never auto-linked to a Xero invoice (§ 6.1).

### 6.2 Re-import / overwrite behavior

**How `sync_excel` behaves:** unconditional partial overwrite — a mapped column with a non-blank value always overwrites the OM field; a blank cell is omitted. No skip/merge mode, no read-only fields, no visibility beyond the run's own log and generic `audit_logs`.

| Option | Description | Trade-off |
|---|---|---|
| A — Full Xero authority + read-only enforcement (Invoices), field-level ownership (Companies) | Xero-sourced invoices are always overwritten and the OM API refuses manual changes (mutation guard). Company fields Xero owns are overwritten; OM-only fields are never touched | Strongest integrity for legally relevant invoice data; small new guard. For Companies it matches what `sync_excel` already does (mapped fields only), made an explicit rule |
| B — CSV-style unconditional overwrite, no enforcement | Simplest, zero guard code | Silently overwriting a user's manual invoice correction with Xero data is an integrity risk for legal financial documents |
| C — "Last local edit wins" | Avoids clobbering a deliberate local edit | Breaks "Xero is the source of truth"; the systems diverge with no way to tell which is right; more code than A |

**Decision (2026-10-12): Option A**, with three implementation rules:
1. **Invoices.** "Xero-sourced" is derived from a `SyncExternalIdMapping` row (`integrationId='sync_xero'`, `internalEntityType='sales.invoice'`), and the invoice is read-only **while a live Xero grant exists** (§ 1.3), read with `readGrantStatus` (no lock, no Xero call, never throws; `active`, `invalidated` and `unavailable` all count, so an unreadable grant fails closed). The mutation guard checks this at write time on the invoices API (`makeCrudRoute` runs the guards; the adapter writes through the sales commands and is not blocked). Disconnecting erases the grant and releases every invoice; the mapping stays, so the Xero link remains. Reconnecting re-arms the guard. **Disabling the integration keeps the lock:** it only pauses syncing, and an edit made during the pause would be overwritten by the next sync — the silent clobber Option B was rejected for. An `invalidated` grant keeps the lock until the admin reconnects or disconnects. The lock is not scoped to one Organisation and need not be: § 10 #20 refuses a switch while the previous Organisation's invoices remain (the mapping prefix, § 10 #15, would make scoping possible). **Edits made while disconnected** are locked again by a Reconnect to the same Organisation and overwritten by the next full pass or Xero change; the Organisation confirmation after a Disconnect says so and offers "Run full resync now". An invoice **deleted** while disconnected, or removed by undoing its import, stays deleted: the sync refuses it with `xero.invoice_deleted_in_om` and never restores or re-creates it (§ 6.5). In-process callers of the sales commands (none in this spec) are outside the guard. No schema change.
2. **Companies.** Field-level ownership: Xero owns `displayName` / `legalName`, `primaryEmail`, `primaryPhone`, `websiteUrl`, its own address rows (one per Xero address type), `xero_tax_number`, the Xero contact marker `xero_contact_id`, the archive state (`status='archived'` with `isActive=false`, and its reversal) and the merge mark `xero_merged_into` (§ 10 #22 (b)); only a non-blank Xero value that OM's validators accept overwrites (§ 6.2a). OM-only is every other Company field — any other `status` value, `ownerUserId`, tags, comments, deals, `brandName`, `domain`, `description`, `industry` / `sizeBucket` / `annualRevenue`, `lifecycleStage`, `source` and the rest — every address row the user added, and every non-Xero custom field.
3. **Write only on change.** Before calling a command the adapter compares the mapped Xero-owned values with the record's current values — for an invoice the header, lines, status entry, Company link and every `metadata.xero` key; for a Company the fields of rule 2 and each Xero-owned address (§ 6.2a) — and reports a `skip` item without a command when none differs. Every `sales.invoices.update` sets `updatedAt` and emits an `updated` event (`sales/commands/documents.ts:9673-9687`); `customers.companies.update` advances a Company's `updatedAt` — its optimistic-lock version — whenever profile or custom fields are passed (`customers/commands/companies.ts:812-818`), so a no-op write would also give a user editing that Company a false conflict; and every command write reaches the audit log, the search index and each `*` event subscriber — the outbound webhook dispatcher, workflow and business-rule triggers — so without the comparison a weekly full pass over 50,000 unchanged invoices would emit 50,000 of each. `data_sync` declares `ImportItem.hash` but never reads it (§ 0.2.8), so the comparison lives in the adapter.

**Visibility of import-driven changes:** the run detail page shows the run's create/update/skip/failed counts and its log rows — the engine's row for each failed item and the adapter's rows for refused items and item warnings (§ 1.3, § 6.5). A created, updated or unchanged item has no row of its own, so "what did the last sync do to this record" is answered by those rows and, for every command write, by `audit_logs`. A field-level diff view is out of scope (no platform primitive beyond what `audit_logs` captures for command writes, which this integration gets because it writes through the commands).

### 6.2a Field mapping

The fixed mapping (§ 10 #3). Sources: Xero's OpenAPI schemas `Contact`, `Address`, `Phone`, `Invoice`, `LineItem` and `LineAmountTypes` (§ 0.1). Targets: `companyCreateSchema` / `companyUpdateSchema` and `addressCreateSchema` (`customers/data/validators.ts:97-172`, `:266-298`; § 0.2.11), `invoiceCreateSchema` / `invoiceUpdateSchema` (`sales/data/validators.ts:902-952`) and the invoice commands (`sales/commands/documents.ts:9350-9492`, `:9615-9637`; § 0.2.3).

Rules for every row:
1. **A blank Xero value never clears an OM value**; only a non-blank one is written — the `sync_excel` behaviour (§ 6.2) and § 10 #1's rule for redacted contacts. A value removed in Xero stays in OM until a user changes it.
2. **A value OM's validators would reject is left out** — an email that is not an address, a phone without a country code (common in Xero), a website that is not a URL — so the rest of the record still syncs; the adapter logs an item warning naming the field (§ 1.3, § 6.5). The left-out value takes no part in the comparison, so it causes no write on later runs.
3. **Text longer than OM's limit is truncated to it** (Xero allows 255 characters for `Name`, OM 200), with a warning; the comparison uses the truncated value. `addressLine2`, which joins up to three Xero lines, is truncated the same way; a postal code longer than OM's 30 characters is left out instead (rule 2), since a truncated code is a wrong one.
4. **Compare-before-write** (§ 6.2 rule 3) compares exactly the values these tables produce, after rules 1–3.

**Company (Phase 1)** — `customers.companies.create` / `.update`:

| Xero `Contact` | OM | Rule |
|---|---|---|
| `Name` | `displayName` and `legalName` | Xero has no separate legal or trading name; `FirstName` / `LastName` name a contact person and are not mapped (§ 6.4) |
| `EmailAddress` | `primaryEmail` | Rule 2 |
| `Phones[]` | `primaryPhone` | The first non-blank of `DEFAULT`, `MOBILE`, `DDI`, `OFFICE` (never `FAX`), as `+<PhoneCountryCode> <PhoneAreaCode> <PhoneNumber>`, with non-digits stripped from `PhoneCountryCode` and a leading trunk `0` dropped from `PhoneAreaCode` (except for Italy, `39`, which keeps it); without a `PhoneCountryCode` it is left out (rule 2): OM requires the `+` country code, and the Organisation's country would need `accounting.settings.read`, which this integration does not request (§ 0.1) |
| `Website` | `websiteUrl` | `https://` added when the value has no scheme; rule 2 when it is still not a URL |

**Addresses (Phase 1).** Xero owns at most one `CustomerAddress` row per Xero `AddressType` per Company: the row its `customers.address` mapping `<xeroOrganisationId>:<ContactID>:<AddressType>` names, as long as that row still belongs to the Company. Every other address row of the Company is the user's: a sync never compares, changes or deletes it, and never sets `isPrimary`, which would demote the user's primary address (§ 0.2.11). Only the `xero.contacts` run writes addresses, and `data_sync` refuses a second run of it (§ 0.2.8), so no two writers create the same row — apart from two runs started in the same instant, since the refusal is check-then-act, a residual like the crash case below; an invoice's self-heal creates its Company without addresses, which arrive with that Contact's next Contacts run (its next change in Xero, or the next full pass — with the weekly full resync off and the Contact unchanged, never, § 6.7). Per Xero address type the run:
- writes nothing for an address with no address line: OM requires `addressLine1`, and a blank address deletes nothing (rule 1), so `customers.addresses.delete` is never called;
- otherwise reads the mapped row; when the mapping names no row (never written, or deleted by a user) or a row a user moved to another customer (§ 0.2.11), it creates one through `customers.addresses.create` and then stores the mapping, which re-points it (§ 0.2.7), so a moved row is the other customer's from then on — a row a user deleted returns this way, like any overwritten Xero-owned value. A crash between that create and the mapping leaves the new row unmapped: it then counts as the user's, and the retry creates Xero's row again — a duplicate address, a residual like those of § 6.1;
- updates the mapped row through `customers.addresses.update` only when a mapped column differs (§ 6.2 rule 3).

**What "matches Xero exactly" covers (US-3.1).** Every amount Xero's invoice list reports is stored unchanged in OM's four-decimal columns, and each derived amount is the sum or difference of two of them, so it is exact too; the other-side unit price and `taxRate` are derived and outside the claim. Header totals are Xero's own, never summed from the lines, so a cent of Xero's tax rounding between the lines and `TotalTax` stays as Xero reports it. `RoundingAmount` never comes with a list call, and on an Organisation that enabled Xero's opt-in supplied totals a list call returns Xero's calculated `SubTotal` / `TotalTax` / `Total`, at most 0.10 from the supplied ones (§ 0.1): OM stores the list's values, since fetching each invoice by id would cost one call per invoice against a daily limit of 1,000 calls on Starter (§ 0.1); on the Demo Company the list's totals equal the by-id ones [Sandbox, 2026-10-14], and an Organisation with the opt-in stays sandbox check § 10 #11 (k). `AmountPaid` / `AmountDue` may then follow the supplied total, so paid + outstanding + credited can differ from the stored `Total` by up to that 0.10 (also § 10 #11 (k)).

### 6.3 Invoice data scope (MVP)

The MVP scope — sales invoices only (`ACCREC`), header + line items, currency code and amounts stored as-is, payment status from the invoice itself (`Status`, `AmountPaid`, `AmountDue`) — maps onto `SalesInvoice` / `SalesInvoiceLine` with three gaps: the Company link (§ 1.4), the invoice status dictionary (§ 0.2.4) and the sales write path (§ 0.2.3, § 10 #19). Two correctness rules:
- Only `Status IN (AUTHORISED, PAID, VOIDED)` invoices are pulled — `DRAFT` / `SUBMITTED` are not yet financial documents and would misstate OM's sales data (§ 6.4). `PAID` is a real status (§ 0.1): leaving it out would skip every fully paid invoice, the bulk of a mature Organisation's history. Amounts come from `AmountDue` / `AmountPaid`, not from the status.
- Voided invoices point at the `voided` status entry and are never deleted (WF3 edge case 3).

**Deferred:** Bills (`ACCPAY`) — no purchasing/AP target in OM. Credit notes — `SalesCreditMemo` / `SalesCreditMemoLine` exist and link to invoices, a low-gap candidate. Detailed payments — `SalesPayment` / `SalesPaymentAllocation` exist (a payment currently requires an order, upstream #7202). Invoice PDFs/attachments — the `attachments` module exists.

### 6.4 Archived/voided/deleted records, and individuals vs. companies

| Xero state | OM treatment | Rationale |
|---|---|---|
| Contact `ContactStatus=ARCHIVED` (a list call returns it only with `includeArchived=true`, which the Contacts walk sends) | The mapped Company: `status='archived'`, `isActive=false` — never deleted — unless the Contact carries `MergedToContactID`, where § 6.1's merge rule applies instead. Without a mapping: no Company (a skip, no log row), unless the invoice self-heal needs one, which it creates archived | Keeps deals, invoices and activities attached to the Company intact; a long-archived contact no invoice needs adds nothing to a CRM |
| Contact `ContactStatus=GDPRREQUEST` | Status flip only; existing PII is **not** overwritten with Xero's blanks. Without a mapping: no Company, unless the invoice self-heal needs one | § 10 #1: OM has no erasure primitive, and invoices are accounting records |
| Invoice `Status=VOIDED` | `voided` status entry, never deleted | A voided invoice stays a real historical document; Xero never removes it |
| Invoice `Status=DELETED` | Not applicable — only `AUTHORISED`/`PAID`/`VOIDED` are pulled, and Xero deletes only before authorisation | Answers "why don't drafts appear" |
| Invoice `Status=PAID` | Imported normally, with `AmountPaid`/`AmountDue` | System-set when fully paid |
| Contact is an individual (`FirstName`/`LastName`, no company signal) | Imported as a Company, uniformly | See below |
| Contact is supplier-only (`IsSupplier=true` AND `IsCustomer=false`) in a Contacts run | **Filtered out — no Company created**; a mapped one (its Company created by an invoice's self-heal) is updated like any other | Bills are out of scope; vendors in a CRM's Companies list would misrepresent them; Xero's computed flags can lag behind the invoice that made the Contact a customer (§ 0.1) |
| Contact fetched by the invoice-side self-heal | **Imported regardless of `IsCustomer`/`IsSupplier`** | An `ACCREC` invoice makes it a customer; Xero's computed flags do not bump `UpdatedDateUTC` (§ 0.1), so they can lag |
| Contact has `IsCustomer=false` AND `IsSupplier=false` (a new contact with no invoices yet) | **Imported** | Both flags are computed from invoices, so a new contact has both `false`; the filter must read `IsSupplier=true AND IsCustomer=false`, never `IsCustomer=false` alone |
| Contact has both flags `true` | Imported | A business both bought from and sold to |

**Individuals vs. companies — options:**

1. **Import every Contact uniformly as an OM Company** (chosen) — Xero has no reliable "individual" flag (only `FirstName`/`LastName` as a heuristic); one target keeps the Company link uniform.
2. Classify into Person vs. Company by `FirstName`/`LastName` — fragile (many Organisations put an individual's name only in `Name`) and doubles the invoice-linking design.
3. Filter out apparent individuals — loses real customers (sole traders, consumers).

**Decision (2026-10-12):** Option 1, with the supplier-only filter above.

### 6.5 Import order and failure handling

**Cursors carry their Xero Organisation.** Each `xero.*` cursor is a JSON value `{ v, xeroOrganisationId, modifiedSince, lastFullAt, fullPassStartedAt, fullPassModifiedSince, fullPassChunk, lastFullCalls }` (precedent: `sync_akeneo`'s `lib/cursor.ts`; `data_sync` supports identity-carrying cursors). A cursor of another Organisation counts as no cursor, so the run walks everything — a full pass that commits `lastFullAt` (§ 6.7). A run compares the grant's `providerData.xeroOrganisationId` (returned by every `getAccessToken`) with the one it started with: empty (a Reconnect left the grant Account pending) ends a manual run with the Account-pending precondition error and a scheduled run quietly; a different id ends the run with a run-terminal "Xero Organisation changed — the next run syncs the new one"; neither advances the cursor past the partial page. The adapter tells a scheduled run from a manual one by `SyncRun.triggeredBy` (only exactly `'scheduler'` counts as scheduled), read through the optional `StreamImportInput.runId`, because the adapter input carries no trigger (§ 0.2.8); without a `runId` or a readable run — the engine always passes one, so only a direct caller such as a test — it treats the run as scheduled and ends quietly with the warning.

Contacts and Invoices are two `supportedEntities` (`xero.contacts`, `xero.invoices`) on one adapter, so each has its own runs and schedule. Instead of an operator-managed "Contacts before Invoices" order, the Invoices adapter **self-heals** missing Contact mappings by fetching the page's unmapped Contacts in one batched call (§ 6.6) and importing them without the supplier filter (§ 6.4), through the Company claim (§ 6.1). Only when Xero does not return the Contact or it fails validation is the invoice `failed` with `xero.invoice_contact_unresolved`; the run remembers that Contact, so its other invoices fail without another call. A failed item is not retried by the next incremental run (the cursor has passed it); it is visible in the run's failed-item list, re-attempted by the next weekly full pass, and at once by "Run full resync now" (both Phase 2; in Phase 1 only a manual run with "Run as full sync", § 7 Phase 1) — `data_sync`'s existing failed-item visibility, no retry queue. Every failed item carries a stable `data.errorCode` (`xero.<reason>`) in the `module.reason` shape the engine records; without one the engine records `data_sync.item_failed` (`data_sync/lib/sync-engine.ts:367`).

**Warnings and refusals are the adapter's own log rows.** The engine counts every item that is not created, updated or failed as skipped and writes a log row only for a failed one (§ 0.2.8). Every refused item, item warning and run-level warning in this spec is therefore written by the adapter with `integrationLogService.write`: level `warn`, a stable `xero.*` code, the run id, and the Xero external id and OM record id in the payload, never a token (core I4); the run's detail page lists them. A refused item is then reported to the engine as `skip`, like an unchanged one, which writes no row (§ 1.3). A `catch` in the adapters, the routes or the upgrade that records an error, rather than rethrowing it, also calls `reportError` with a `sync_xero.*` code, so the failure reaches the deployment's telemetry as well as the run log.

The adapter honours `StreamImportInput.signal` per page and returns above the `yield`, so a cancelled run never advances its cursor past a half-applied page (§ 0.2.8); items already written stay, and re-reading them is idempotent.

**Disconnect during a run.** Each item's write is its own command and a run calls Xero only once per page (and per self-heal fetch), so the adapter reads `readGrantStatus` (network-free, never throws — the read the invoice guard makes on every API write) before each item's write and ends quietly on `null`. Each read forks an EntityManager, checks the live row, resolves the tenant key and decrypts the grant, so a non-null result is reused for at most one second within the run; `null` is never reused. After a Disconnect commits, writes stop within about one second, plus the item in progress (a self-heal item — Company create, claim, then the invoice — finishes after its single read). Items written earlier stay and the cursor is not advanced past the partial page, so a later run re-reads it. An `invalidated` or `unavailable` grant is handled at the next token call, since the page in hand was fetched under a valid token. The check sees presence only: a Disconnect followed by a completed Reconnect within the same page (about a minute) reads `active` again, so the rest of that page lands, and the Organisation check at the next token call stops a run whose Organisation changed (§ 6.5, first paragraph). Chosen over stopping only at the next token call, which would let the rest of a 1,000-record page — a minute or more of writes — land after "Not connected", into invoices the Disconnect just made editable.

**Records removed in OM.** A mapped invoice that was removed in OM is never updated, restored or re-created: the item is refused with `xero.invoice_deleted_in_om`, its warning naming the invoice number. Two ways lead there: a soft delete through the invoices API, possible only while no live Xero grant existed (§ 6.2), which keeps the number taken (§ 0.2.3); and undoing the adapter's `sales.invoices.create` in the audit log, which hard-deletes the invoice (`sales/commands/documents.ts:9542-9554`) and runs no mutation guard (`audit_logs/api/audit-logs/actions/undo/route.ts`). A restored soft-deleted invoice is updated by the next sync that returns it (a Xero change or a full pass). A mapped Company deleted in OM (`customers.companies.delete` is a hard delete that leaves the mapping): the Contacts run refuses its Contact with `xero.company_deleted_in_om`, its warning naming the Contact, and never re-creates the Company; an invoice's self-heal, when it creates a new invoice of that Contact, treats the mapping as none and re-creates the Company through the claim (§ 6.1). An invoice already imported keeps its link to the deleted Company until then; once a new invoice has re-created the Company, the mapping names it, so the next sync that returns an earlier invoice of that Contact — a change or a full pass — moves that invoice's link to it (§ 10 #23 (c)).

### 6.6 Rate limiting and partial failures

**Reused from existing modules:** queue workers with bounded concurrency, cursor persistence after every batch, per-item error logging that never aborts the run, `ProgressJob` progress, the failed-item list, retry, signal-based cancellation, scheduling, and overlap detection per integration, entity type and direction.

**New, inside `sync_xero`** (never inside `data_sync`, per its "never special-case provider logic" rule): a small rate limiter and a `429`-aware retry, against Xero's limits (§ 0.1):
- Budget **5 concurrent / 60 per minute / 1,000 (Starter) or 5,000 (Core) per day per Organisation**, plus the app-wide **10,000 per minute**, which matters once many tenants run from one registered Xero app (§ 10 #18).
- **Read the quota from the response headers** (`X-MinLimit-Remaining`, `X-DayLimit-Remaining`, `X-AppMinLimit-Remaining`) rather than counting locally: they survive restarts, parallel runs and other clients of the same app.
- Limits cannot be increased.
- **Paging is not optional on either entity:** an unpaged Contacts walk loses `MergedToContactID` (§ 6.1); an invoice list that is neither paged nor a `Statuses` query returns no line items (§ 0.1). Both failures are silent.
- **`includeArchived=true` is not optional on the Contacts walk:** without it Xero never returns an archived contact, so no Company is archived and no merge is seen (merged-away contacts are archived, § 6.1) — silent as well.
- **Keyset paging, never an advancing page number** (§ 6.7): page-number paging over `UpdatedDateUTC ASC` skips a record whenever an earlier one is edited during the walk.
- `pageSize=1000` (§ 0.1). The cost figures in § 6.7 assume it; at 100 per page they rise tenfold and the quota deferral of § 6.7 still applies. A large first sync can span several days on the 1,000/day Starter cap (WF3 edge case 5).
- **`summaryOnly=true` is rejected for both entities:** on Contacts it drops `Addresses` (mapped) and `IsCustomer`/`IsSupplier` (the supplier filter); on Invoices it drops `LineItems` (§ 0.1).
- Hourly incremental runs of both entity types cost about 48 calls a day when little changes (one page each): about 5% of the Starter limit, 1% of Core.
- **The invoices self-heal batches its Contact fetches:** the unmapped Contacts of one invoice page come in one `GET /Contacts?IDs=<up to 100 ContactIDs>&includeArchived=true`, never one call per Contact. A first sync would otherwise spend one call on every Contact the Contacts run has not mapped yet, which for a mature Organisation can exceed a Starter day. The flag is required: without it an `IDs` list returns active Contacts only, and with it the list carries `MergedToContactID` [Sandbox, 2026-10-14]. A Contact that Xero does not return or that fails validation is remembered for the rest of the run.

### 6.7 Full pass

`If-Modified-Since` misses some changes (§ 0.1): an invoice's `DueDate` can change in Xero without bumping `UpdatedDateUTC`, and § 6.2 makes that field read-only in OM — wrong data the API refuses to let anyone fix. Incremental sync alone cannot keep OM correct.

**Mechanism (§ 10 #12, #17):** a weekly full pass inside the regular scheduled runs, plus a "Run now" control.

| Control | Behaviour |
|---|---|
| **Weekly full resync** — the `weeklyFullResync` boolean in the Client Configuration (Credentials tab), **on by default** (absent counts as on) | When a scheduled run's cursor shows `lastFullAt` older than 7 days (or none), the run walks every record from the start of Xero's order (its first page sends no `If-Modified-Since`) and, once drained, commits `lastFullAt` = `fullPassStartedAt` and sets `modifiedSince` to the same instant, so the next incremental run re-reads whatever changed while the pass ran. Every walk without a usable cursor — the first sync, the first run after an Organisation switch, "Run full resync now" — is a full pass in the same sense and commits `lastFullAt` the same way, so the next weekly pass falls due 7 days later, not at the next run. `data_sync` keeps one schedule per integration, entity type and direction (§ 0.2.8), so the pass never needs a second schedule and never overlaps an incremental run. The field's help text carries the explanation, and the Xero tab shows the state and `lastFullAt` per entity type |
| **"Run full resync now"** on the Xero tab | Starts the existing `data_sync` run with `fullSync: true` for each `xero.*` entity type (no cursor, so a full pass that commits a new `lastFullAt`); a plain confirmation, because it is long-running; refused like any run while one is in progress or the integration is disabled |

**Keyset paging.** Every page of every walk — incremental, full or resumed — is requested with `page=1` and `If-Modified-Since` = the `UpdatedDateUTC` of the last record already read, minus one second (the first page of a full pass sends none; the first page of an incremental run sends the cursor's `modifiedSince` minus one second). `If-Modified-Since` has second precision while `UpdatedDateUTC` carries milliseconds, and Xero orders by `UpdatedDateUTC` with an id tiebreak (§ 0.1), so whether Xero compares inclusively or not, each page re-reads at most two seconds of records, which the adapter drops by id before processing. Only when a whole page falls inside that overlap — its last record still within the up-to-two-second window the page started in, as after a bulk import in Xero, so the keyset cannot advance — does it request `page=2…` under the same `If-Modified-Since` until it passes that second. A record edited during the walk moves to the end of Xero's order, where the walk reaches it again, so no record is skipped — except inside an overfull second, where an edit during the `page=2…` steps can shift one record past the walk, and the next full pass reads it (until Phase 2's weekly pass ships: the record's next change in Xero, or a manual run with "Run as full sync"); a walk that advanced `page` throughout would skip one record per such edit (§ 0.1). The cursor keeps the keyset, never a page number.

**Resume point.** With every committed page a pass records `fullPassStartedAt` (from the `Date` header of the pass's first response, so on Xero's clock — RFC 9110 § 6.6.1), `fullPassModifiedSince` (the `UpdatedDateUTC` of the last record of the last complete page) and, when the pass is chunked, `fullPassChunk` (the `Date` range in progress); an incremental run records its `modifiedSince` the same way. A pass interrupted by the daily cap or a restart resumes exactly like its next page: `fullPassModifiedSince` minus one second as `If-Modified-Since`, within `fullPassChunk`. Above Xero's 100,000-record threshold an invoice pass walks one `Date` range at a time (`Date` is an optimised filter with range operators, § 0.1), each to its end before the next.

**Default schedules.** Every Organisation save (the tab's save route and the callback's automatic save) calls `dataSyncScheduleService.getByKey('sync_xero', <entityType>, 'import', scope)` for each `xero.*` entity type and, when it finds none, `saveSchedule` with an hourly schedule, `fullSync: false` and `isEnabled: true`. Phase 1 registers only `xero.contacts`, as `scheduleType: 'interval'`, `scheduleValue: '1h'`. An interval runs from the moment it is registered, so two defaults saved together would start together every hour and the invoices self-heal would race the Contacts run for every new Contact; Phase 2 therefore creates both defaults as `scheduleType: 'cron'` schedules half an hour apart (`0 * * * *` for Contacts, `30 * * * *` for Invoices) and moves the Phase 1 Contacts default to its cron form while it is still the provider's unchanged default (`interval`, `1h`, incremental, enabled). The provider's defaults are incremental because the schedule editor would otherwise default to an hourly schedule with `fullSync` on (§ 0.2.8). Any other existing schedule — an edited one, a disabled one, or an admin's own that differs from the Phase 1 default — is never changed. The Xero tab lists the `xero.*` schedules with `listSchedules` (not `getByKey`, so a duplicate row shows), flags a missing, disabled or duplicate one and one with `fullSync` on (which re-reads everything on every run and, starting without a cursor each time, can never resume an interrupted pass), and offers "Create default schedule" (the same idempotent call). Every scheduled run gets its access token through the core, which refreshes it within the descriptor's `refreshSkewMs` (capped at half the token's lifetime), so an enabled integration with these schedules never reaches Xero's 60-day idle expiry (§ 10 #13). Saving the Organisation creates the defaults also for a caller without `data_sync.configure`, because they keep the connection alive; the `data_sync.schedule` guard still runs, and only "Create default schedule" needs `data_sync.configure`. **Phase 2 upgrade path:** an organization connected in Phase 1 may never save its Organisation again, so from Phase 2 every `xero.contacts` run also performs the step a save performs. When the `xero.contacts` schedule equals the Phase 1 default (`interval`, `1h`, incremental, enabled), the step first creates the `xero.invoices` default when none exists, then moves the Contacts schedule to its cron form. Once moved, the Contacts schedule no longer equals the Phase 1 default, so the step needs no stored marker; until the move succeeds the condition still holds. A failed write, other than the move's 409 below, logs one `warn` row `xero.schedule_upgrade_failed` and the run continues: when the create fails, the step skips the move, and the next `xero.contacts` run creates and then moves; after a failed move or a crash between the two writes, the next run finds the `xero.invoices` row and only moves. Until then the Contacts interval and the Invoices `30 * * * *` cron coexist, so their runs can overlap in each hour the move stays pending, which the Company claim absorbs; and when the move's 409 came from an admin edit, the Invoices default the step created stays, as "Create default schedule" would leave it. The condition is the schedule's state, whoever made it: an admin's own Contacts schedule equal to the Phase 1 default is moved the same way, which changes only the minute it fires at, and the step fires whenever a Contacts schedule equals that default. A `xero.invoices` schedule an admin deletes therefore stays deleted until the next Organisation save, which creates every missing default as the keep-alive (US-4.1), or until the admin sets the Contacts schedule back to the Phase 1 values, which the next run moves, re-creating the missing Invoices default. Where the Contacts schedule was edited or deleted in Phase 1, the step does nothing: the Xero tab flags the missing `xero.invoices` schedule, and "Create default schedule" creates the Phase 2 cron values. In a run the step is a system write: a scheduled run has no user, and the `data_sync.schedule` mutation guard is a route-level contract that needs the request's user, method and headers (`shared/src/lib/crud/route-mutation-guard.ts:119-124`, `CrudMutationGuardValidateInput.userId`), so the run calls `saveSchedule` without route guards, the first system caller to do so (both `data_sync` schedule routes run the guard, `data_sync/api/schedules/route.ts:85-90`): a deployment's `data_sync.schedule` guard does not see this write, accepted because it only re-times the provider's own default and adds its sibling. The move passes the row's `updatedAt` as `expectedUpdatedAt` with the writer's container, the run's or the save's (`saveSchedule` checks the version only with one, `data_sync/lib/sync-schedule-service.ts:153-159`); its 409 `CrudHttpError` means an admin edit, a held record lock or another writer came first, so the move writes nothing and logs nothing, and the next run re-reads the schedule. `saveSchedule` re-reads the row, checks the version, then registers the job and flushes an unconditional update, so the check stops an edit saved after the writer read the row and before that re-read, not one saved between the re-read and the flush, and two writers can both move the schedule, to the same values. A save and a run, or two runs, can perform the step together: the `xero.invoices` check-then-create has no guard and the schedule key has no unique index (`data_sync/migrations/Migration20260304113737.ts:16`), so both can create an Invoices row, as two Phase 1 saves in the same instant can. Both rows then fire on the same tick and the scheduled worker's overlap check takes no lock (`data_sync/workers/sync-scheduled.ts:61-69`), so two `xero.invoices` runs can start together; the invoice-number constraint and the Company claim keep them from duplicating records, and the tab flags the duplicate for the admin to delete (accepted: it needs two writers within milliseconds). With optimistic locking off for `data_sync.schedule` (`OM_OPTIMISTIC_LOCK`, on by default, takes a per-resource allowlist), the move's version check is skipped, so an admin edit made in between can be overwritten.

**Why the configuration screen carries the toggle:** without an explanation of what Xero's incremental feed misses, the first admin to notice a weekly full pass switches it off as waste. The toggle sits in the integration's own configuration with that explanation as its help text, which names what stays stale with the toggle off: a `DueDate` changed without an `UpdatedDateUTC` bump; a failed item, re-attempted only by a full pass (§ 6.5); a record an edit shifted past an overfull second; the addresses of a Company an invoice's self-heal created, until its Contact changes in Xero (§ 6.2a); and the Company link of invoices a Xero contact merge moved, when the move bumps no `UpdatedDateUTC` (§ 6.1).

**Cost** (at `pageSize=1000`):

| Tenant size | API calls per full pass | Share of a 1,000/day (Starter) / 5,000/day (Core) limit |
|---|---|---|
| 5,000 invoices + 1,500 contacts | ~7 | 0.7% / 0.14% |
| 50,000 + 10,000 | ~60 | 6% / 1.2% |
| Xero's 100,000-invoice ceiling | ~100 | 10% / 2% |

With the self-heal's Contact fetches batched (§ 6.6), the binding constraint of a pass is OM's side — a read and comparison per record, a command only for a changed one (§ 6.2) — not Xero's limit; no confirmation dialog about quota is shown.

**Quota deferral, in code:** a cursor carrying `fullPassStartedAt` always resumes its pass and is never deferred; mid-pass cursors carry the pre-pass `modifiedSince` (none after a walk without a usable cursor). Deferral applies only to starting a new pass, and only when the cursor has `modifiedSince` and `lastFullCalls`: before starting a due full pass, the adapter reads `X-DayLimit-Remaining` from the run's first response and estimates the pass from the previous pass's call count (`lastFullCalls`). When the remaining quota cannot cover it, the run does its incremental walk instead, logs one warning ("full pass deferred: insufficient daily quota") and tries the pass at the next run — the incremental data stays current and the deferral is visible, never a silent skip. "Run full resync now" always starts; on the daily cap it commits its progress and the next run resumes it.

The default schedules ship here because they are the keep-alive (§ 10 #13) and make WF4 work without admin action. The reconnect prompt itself is the core's banner.

**Acceptance criteria:** `DDD writes, PM challenges`

**Domain criteria** `DDD`:
- [ ] At most one live Xero grant exists per OM tenant+organization, bound to at most one `xeroOrganisationId` — a Reconnect updates it in place (core I2).
- [ ] A `SyncExternalIdMapping` row for `(integrationId='sync_xero', internalEntityType='customers.company', externalId='<xeroOrganisationId>:<ContactID>')` is unique, names the `CustomerEntity` id, and is written only by a Company claim; a run interrupted between writing a Company and its mapping maps that Company on retry through its Xero contact marker instead of creating a second one.
- [ ] The tax-number fallback never matches a Company that already has a `sync_xero` mapping, including one claimed earlier in the same run; when several unmapped Companies match, the oldest is claimed and `xero.company_match_ambiguous` names every candidate.
- [ ] Company create/update events fire through the customers commands for every Xero-sourced change, exactly as for a manual change — no bypass of event, audit or index side effects; a Contact whose Xero-owned fields are unchanged calls no command, so it fires no event and writes no audit entry.
- [ ] The Contacts walk sees every Contact it should: archived and merged Contacts arrive (`includeArchived=true`), no Contact is skipped because another was edited during the walk (keyset paging, outside § 6.7's overfull-second exception), and an archived Contact without a mapping creates no Company.
- [ ] An OM-only Company field (owner, tags, notes, non-Xero custom fields) is never present in the payload sent to the update command, and a blank or invalid Xero value never clears or replaces an OM value; a Contact carrying one still syncs (§ 6.2a).
- [ ] A sync writes only Xero-owned addresses — at most one row per Xero address type per Company, recognised by its `customers.address` mapping — from the `xero.contacts` run only, and only when they differ from Xero; an address row a user added is never changed or deleted, and no sync sets `isPrimary`.
- [ ] After any number of Organisation saves, exactly one `SyncSchedule` exists per `(sync_xero, entity type, import)`, and the ones the provider created are incremental.
- [ ] No `xero_tax_number` value appears in the text the Company search source builds, so none reaches a search index or an embedding provider through it (§ 10 #31; verified by #7874's regression tests).
- [ ] `packages/sync-xero` contains no `pg_advisory` SQL of its own (the Company claim uses the shared `withAdvisoryXactLock`), no `grant_type=refresh_token` or `code_challenge` construction, and imports no `@internal` export (§ 0.2.1); every grant write goes through `completeConnect`, `updateProviderData` or `disconnect`; no token reaches Xero's logs, run parameters, cursors or health `details` (core I4).
- [ ] After a Disconnect or an invalidation, scheduled `xero.*` runs neither report an error nor fire `data_sync.run.failed` on every tick, and their quiet `completed` never changes the health badge.
- [ ] After a Disconnect commits, a run in flight stops writing within about one second, plus the item in progress (a non-null grant read is reused for at most one second).

**Business criteria** `PM`:
- [ ] An admin connects a Xero Demo Company end-to-end and sees "Connected" in the same session; time-to-first-sync ≤ 5 minutes excluding Xero's screens; no schedule to create.
- [ ] An admin triggers a Contacts sync on demand and sees accurate create/update/skip/failed counts, including a sync running longer than Xero's 30-minute access token.
- [ ] A sales/CRM user opens an imported Company: it behaves like a manually created one (editable OM-only fields) and shows the Xero badge with its link, also to a user without `integrations.view`.
- [ ] After an invalidated grant, the admin sees the banner, reconnects through its link, the previous Organisation is re-selected (or pre-selected), and the next sync succeeds.
- [ ] Disconnecting an `active` grant shows the revocation outcome, warns when Xero lists other Organisations, and optionally removes the Client ID and Secret; a forced Disconnect or an `invalidated` grant says that no revocation was attempted.
- [ ] Jest tests cover the route-contract rules 1–11 against the core's fake authorization server (`rotation: 'strict'`, 30-minute `strictGraceMs`, 1800-second tokens); an E2E test runs connect → token → disconnect through the test seam (§ 4.5: the core's fake authorization server and the fake Xero API); runs and adapters are covered in Jest against the in-process fakes.

**Value delivered:**
- **Business value:** zero manual re-keying of Xero customer records into OM's CRM, kept current hourly, on a Xero grant that reports its own failure and can be cut off cleanly.
- **ROI metric:** for a tenant's Xero contact list, 100% of active Customer Contacts (§ 1.3) land as OM Companies — none missed through edits during a walk, outside § 6.7's overfull-second exception — with zero duplicates created by a second or interrupted run outside the residuals of § 6.1; a dead grant is visible on the integration page ≤ one schedule interval after Xero rejects it.

**PM's challenges to the DDD criteria:** Kept after challenge — the absence of the provider's own `pg_advisory`, refresh and `code_challenge` code (the core's first-consumer acceptance, and the proof that the provider did not re-implement the grant core); one schedule per key (the provider's idempotent create is new code that could break it). All other criteria accepted: reused platform guarantees or direct expressions of § 6.1, § 6.2 and § 6.2a.

**Acceptance criteria:** `DDD writes, PM challenges`

**Domain criteria** `DDD`:
- [ ] Every Xero-sourced invoice carries its Company link, written in the same command transaction as the invoice and its lines — never an invoice without one.
- [ ] An invoice's header and line amounts are byte-identical to what Xero reported at the last sync — no OM recalculation path touches them (true today, § 0.2.3; this guards against a regression such as wiring `salesCalculationService` or #7202's derivation into imported invoices).
- [ ] A `sales.invoices.update` / `.delete` call on a Xero-sourced invoice while a live Xero grant exists is rejected by the mutation guard on the invoices API; with no live grant it is accepted; a disabled integration keeps the lock.
- [ ] `SyncExternalIdMapping` for `sales.invoice` is the sole source of truth for "is this invoice Xero-sourced".
- [ ] A failed mapping write never produces a second OM invoice for the same `InvoiceID` on retry.
- [ ] Concurrent contacts and invoices runs leave exactly one mapped Company per Contact; a Company whose claim lost to a different Company is deleted by the writer that created it; the next `xero.contacts` full pass reports every marked Company that no mapping names, never one whose claim is in flight.

- [ ] Each line's net and gross follow its invoice's `LineAmountTypes`, and the header totals are Xero's own, never summed from the lines (§ 6.2a).
- [ ] A full pass brings every Xero-owned field and every Xero-sourced invoice to the current Xero state — a `DueDate` changed on a partially paid invoice is corrected by the next pass — and calls a command only for a record that differs, so unchanged records emit no event, audit entry or webhook.
- [ ] Every walk without a usable cursor commits `lastFullAt`, and no walk — incremental, full or resumed — skips a record because another was edited while it ran (keyset paging by `UpdatedDateUTC`; `page` advances only inside one overfull second, where a record an edit shifts past the walk is read by the next full pass, § 6.7).
- [ ] The weekly full pass runs inside the entity type's single schedule; no second `xero.*` schedule exists (except the accepted duplicate of § 6.7's two-writer race), and no other `xero.*` schedule is changed, except that a `xero.contacts` schedule equal to the Phase 1 default is moved to its cron form (§ 6.7).
- [ ] A Phase 1 organization whose Contacts schedule is the unchanged Phase 1 default has cron Contacts and Invoices defaults after its first Phase 2 `xero.contacts` run or Organisation save (a failed write logs `xero.schedule_upgrade_failed` and the next run performs the step again); no run re-creates a `xero.invoices` schedule an admin deleted while the Contacts schedule differs from the Phase 1 default (§ 6.7).
- [ ] A due full pass that the remaining daily quota cannot cover is deferred with one warning, and that run still does its incremental walk.

**Business criteria** `PM`:
- [ ] An admin syncs invoices from the Xero Demo Company and a sales/CRM user sees them on the right Company (the "Xero invoices" tab, § 10 #21 (a)).
- [ ] An API client cannot change a Xero-sourced invoice while a live Xero grant exists.
- [ ] An invoice whose Contact wasn't synced yet still imports via self-heal, without the admin re-ordering two syncs.
- [ ] The "Weekly full resync" toggle is on by default, its reason is explained next to the toggle, and "Run full resync now" starts one on demand.

**Value delivered:**
- **Business value:** per-Company invoice history and payment status reflect real, current Xero data with no manual entry and no risk of a user corrupting a legally relevant document; blind-spot staleness lasts at most a week.
- **ROI metric:** for a tenant's `ACCREC` invoices in `AUTHORISED`, `PAID` or `VOIDED` status, 100% land as OM Invoices with the right Company, or as a failed item naming the reason (keyset paging, § 6.7); zero silent amount discrepancies after any sync; stale `DueDate`s last ≤ 7 days at 0.7–10% (Starter) or 0.14–2% (Core) of the daily Xero budget per pass.

**PM's challenges to the DDD criteria:** Kept after challenge — rejection at the invoices API, not only in a UI (OM has no invoice UI, so the API is the only surface, and the read-only guarantee is why § 6.2 chose Option A); no second invoice on a retried mapping write (invoice duplicates are financial-data errors, and the number collision makes the recovery cheap); writes only on change (without it every weekly pass floods webhooks, workflow triggers and the audit log with no-op updates).
