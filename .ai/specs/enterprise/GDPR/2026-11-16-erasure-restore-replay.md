## 📝 TLDR

When a database is restored to a point before an erasure, the erased person comes back. Nothing in the product notices: the record of the erasure was in the database that was just rolled back. **Proposed (future):** a protected erasure synchronously makes a small signed file durable outside the database after verification and before its event/completed audit/success; an applied row follows completed-audit proof. Event delivery and later repair do not establish that guarantee. Only files tagged with the deployment's signing key count. After a restore, some file run ids have no row. The product computes that exact set difference, says so loudly, and an operator runs one command that erases those subjects again.

**Status.** Design settled. The program's decision DEC-4 makes replay work for a restore done outside the product, through an external manifest independent of the backup module; this spec implements it. It ships after the governance engine (C3) and, through it, the OSS erase run (C4) are delivered, including C4's awaited capture.

**Not in this spec:** taking or restoring backups; automatic replay with no operator; removing erased data from backup archives, which age out; an object-store backend for the files.

## 📝 Overview

The 07-08 erasure spec set the position this spec keeps: one mechanical guarantee, that backups expire, and one operator control, a guided re-run after a restore. It also noted that a raw restore bypasses the control. This spec makes the control detect a restore it was not told about.

The erasure evidence must outlive a database rollback. Replay uses the normal guarded erasure service; this spec owns external capture and the operator workflow. **The `eraseSubjects` entry point (R3-14)**, in C4's API Contracts, owns the unchanged input/result and event. C4's **The run**, step 10, and **Optional completion capture — C9** now specify the awaited capture call with this spec's exact input; its **Audit entries** defines per-attempt `PrivacyErasureAuditContext.verifiedAt`, mandatory for new complete subject entries and identical to the capture timestamp. The OSS implementation and C9's capture/crash/restore-before-repair tests remain required before protected completion can be claimed. A spec revision, finite evidence expiry and asynchronous reconciliation do not themselves close the program's durability gate.

## 📝 Problem Statement

- **An erasure does not survive a restore.** The subject's rows, the engine's ledger row and the OSS audit entries are all in the restored database.
- **Backup tooling cannot be the only trigger.** The companion backup design is not required for a raw database restore. Detection must compare durable files with database rows without relying on a product restore hook.

- **Storage options are limited.** The attachments storage drivers can store, read and delete but not list, and their configuration is itself read from the database (`packages/core/src/modules/attachments/lib/drivers/types.ts:22-33`, `packages/core/src/modules/attachments/lib/drivers/driverFactory.ts:64-66`). This interface cannot supply manifest enumeration independently of the restored database.
- **Only the worker role has a start-up hook.** Module runtimes are wired for `worker` alone (`packages/shared/src/modules/runtime.ts:22-23, 67`; `packages/cli/src/mercato.ts:1892-1895`), and the optional bootstrap fallback catches its import/bootstrap errors (`packages/shared/src/lib/di/container.ts:278-284`). The web tier cannot be made to refuse at start without new wiring.
- **Events are redelivered.** A subscriber may run more than once for one erasure, and two may run at once.
- **Useful parts of the reference:** the entry shape, atomic owner-only writes, preview by default, a typed confirmation, a check that the command is pointed at the intended database, and re-running each entry through the normal erase path so that holds are checked again.

## 📝 Proposed Solution

**Protected cutover.** Close traffic and destructive workers before rewinding the active database or switching its target. Configure a fresh random UUID in `OM_ERASURE_RESTORE_GENERATION` outside the database and its backups on every publisher and readiness checker before switching. Never reuse a UUID. A publisher reads `current_database()` and its current `pg_database.oid` on the same target connection and hashes the database name, OID and configured host/port into the credential-free `targetBinding`. Bind signed status to the generation and binding; readiness repeats that bounded identity read. A target rewind that preserves database identity still needs a new generation. A partial rollout cannot open the gate. After replay require an unfiltered `mercato data_erasure restore-status --refresh --require-clear`; continue strict readiness using `--max-age <minutes> --require-clear`. Pending, deferred, quarantine, invalid, missing or unprotected evidence does not clear the gate. Manual external reconciliation can support a separate controller decision but never produces product-certified clearance.

**Bootstrap verification contract.** Deployment configuration mounts three read-only paths set outside the application database and its backups. Core verifies `OM_PRIVACY_RESTORE_POSTURE_FILE` against an installation-pinned Ed25519 trust key file `OM_PRIVACY_RESTORE_TRUST_PUBLIC_KEY_FILE` and a separately pinned `OM_PRIVACY_DEPLOYMENT_ID`. The controller publishes the strict signed payload `{ version: 1, deploymentId, generation: positiveInteger, posture: 'never_activated' | 'activated', issuedAt, keyId, signature }`. Sign canonical JSON excluding the signature with the distinct label `om-privacy-restore-posture-v1`; verify installation and key and read the controller's authoritative, separately managed current register directly. Core reads the current register before each destructive entry, using an owner-only no-follow read without cached or restored fallback. The controller must make the register non-rewindable, never republish or serve an older generation, and prohibit fallback copies. Any read, validation or provider resolution failure refuses destructive work. OSS deployments can provision signed `never_activated` without installing Enterprise, using the controller/bootstrap provisioning documented by C4; unsigned, absent or stale fallback values never qualify. Neither an operator flag nor database roll back can choose posture. Activation requires a write freeze across replicas, successful verification on every writer and coordinated publication of the external coverage record. No transition to ordinary is supported after activation.

C9 reads signed time evidence from `OM_ERASURE_TIME_ATTESTATION_FILE` and the signed restore record from `OM_ERASURE_RESTORED_SNAPSHOT_ATTESTATION_FILE` through the same installation trust root, with distinct protocol labels `om-privacy-erasure-clock-v1` and `om-privacy-restore-snapshot-v1`. The clock envelope is `{ version: 1, deploymentId, sourceIdentity, clockIdentity, intervalStartAt, intervalEndAt, maxErrorMs, noClockStep: true, keyId, signature }`. The provider compares the known source clock identity and validated sample interval on the writer host, rejects unknown clock identity or drift outside the signed bound, and refuses if the caller cannot prove its already-committed verification observation occurred within that interval. The snapshot envelope carries `{ version: 1, deploymentId, sourceIdentity, clockIdentity, recoveryCoordinate, generation, targetBinding, oldestPossibleSnapshotAt, maxErrorMs, lowerBoundAt, keyId, signature }`. `recoveryCoordinate` is a verified archive manifest digest, authenticated consistency classification and all source epochs, or a verified PostgreSQL system identifier, timeline ancestry and recovered point for PITR. The signer independently verifies the provenance and intervals used to produce the bound, which the provider validates against the claimed target, pinned generation, original source and arithmetic. Use one authenticated source lineage for the coverage record, bound read, strict refresh and all readiness probes; ambiguous lineage or unsupported evidence is a refusal. A protected environment needs these independently managed controller operations before the feature can claim support.

**Comparable recovery evidence.** Protection uses a conservative UTC interval backed by independently managed infrastructure clock evidence, never two unqualified wall-clock readings. At initial activation and protected capture a configured infrastructure attestation must establish the sample's clock identity, verified UTC sample and maximum absolute uncertainty for the entire sample interval. Accept only evidence independently authenticated to the deployment, covering the actual sampling interval, with no clock step, expired evidence, unknown offset or unverifiable source. Sample after all mutation transactions and standing checks have committed. Store verified source identity alongside both times so repairing a file cannot treat another timeline as the original lineage. Store `verifiedUpperBoundAt = verifiedAt + verified uncertainty` in the signed manifest (for repair use that exact value and verified source identity from the original committed verification checkpoint, never a new guess). Keep `verifiedAt` for reporting and audit correlation only. With unknown uncertainty, refuse protected completion. Outside the database activate a signed create-only coverage record. Its monotonic floor is at least the upper bound of protection activation and of every protected file removed. Advance and fsync it under the deployment prune lock before deleting files; if an entry has no proven upper bound, keep it and require manual reconciliation rather than advancing from its wall-clock timestamp.

For each restore the controller pins an externally authenticated recovered-snapshot lower-bound attestation to the generation and target. `OM_ERASURE_RESTORED_SNAPSHOT_AT` carries that verified lower bound, with its independent evidence supplied alongside it to every publisher/checker. Its attestation names the source, snapshot or recovery coordinate, clock identity, verified sample and uncertainty. Protected cutover accepts a managed archive only when its authenticated manifest, index and snapshot evidence prove `single-snapshot` or `quiesced` consistency across all restored tables. A `multi-snapshot`, absent or indeterminate classification refuses with `snapshot_consistency_unverified` (exit 1), even if every source epoch is above the signed floor and the archive restore succeeds. For an eligible archive use the earliest source snapshot bound on its authenticated archive provenance, including across proven-quiescent resumed epochs. Only use `startedAt - validated uncertainty` if the trusted archive evidence and capture ordering prove it preceded every source snapshot across all resumed epochs. PITR uses the verified recovered point on the actual WAL timeline with its lower time bound accounting for source/timeline and clock uncertainty. Subtract the maximum validated uncertainty from the indicated oldest snapshot/recovered point; the resulting lower bound, not an archive completion time or target wall clock, must be strictly greater than the signed coverage floor. Verify matching source and clock attestations, generation and target on each strict decision. A missing, incomparable, unauthenticated or indeterminate bound keeps cutover closed even with no listed files. Keep the signed floor out of the database and monotonic across retention increases and restarts. The attestation protocol, fixtures and operator prerequisites ship with protected mode; until proven on the deployment, report it as unprotected.

**Manifest completeness evidence.** Protected mode requires an installation-owned, independently authenticated inventory outside the application database, backup artifacts and manifest-directory failure domain. Its authenticated head is monotonic, protected against rollback and read directly from the pinned installation trust source. Each live member binds deployment, tenant, run id, relative manifest key and SHA-256 of the exact published signed file. Configure the inventory before activation. A missing, unavailable, stale or unverifiable head refuses protected readiness, capture and pruning. File signatures and the coverage floor alone cannot establish completeness.

C9 consumes a bounded internal `privacyErasureManifestInventory` owner capability. It acknowledges a durable expected member under the current head, pages expected members in stable order against a pinned head, and verifies current storage membership for strict readiness. The bounded readiness proof must bind the current inventory head to an authenticated live view of the manifest namespace, checking availability and exact digests. An equivalent storage capability is acceptable if independently verified to detect file deletion, replacement and rollback. A cached list, object count, filesystem timestamp or previously signed clear record cannot substitute. Protected activation is unavailable on a storage composition without this proof. Strict refresh compares expected identities and digests with actual directory entries from the same pinned view and fails closed on a changed head during the check. Strict readiness verifies live membership under the head bound to the signed clear status. If the head or trusted live view changed, require a fresh strict refresh. Diagnostic mode can report the gap without granting clearance. For audit expiry it also verifies one exact `{ deploymentId, tenantId, runId }` against a current authenticated inventory head and live immutable file. Return `verified`, `not_expected` (authenticated nonmembership), or `unsettled` for a retiring member or an expected file that is missing, corrupt, replaced or unreadable. Verify the exact inventory digest, signature and scope before returning `verified`. An unavailable read, stale or changed head, or unknown membership throws. The lookup is bounded and read-only and never substitutes a cached clearance or directory absence. Require this capability when protected replay is activated.

1. **External capture before protected completion.** Register `privacyErasureCompletionCapture` in `data_erasure/di.ts`. An activated OSS run invokes `assertCaptureReady(): Promise<void>` at preflight. The provider validates the scope-independent storage root, signed posture and deployment binding, current signing key, independently verified inventory availability and complete live membership, and a usable durable directory with a bounded no-follow create/flush/unlink probe. Missing configuration or a failed probe refuses before subject writes. Successful admission does not promise later availability. The run must await its `capture` after final standing verification (including both history passes and pending-file drain), before emitting `privacy.subject.erased`, writing its completed audit or returning success. The provider first supplies `attestVerificationTime(): Promise<{ verifiedAt: string; verifiedUpperBoundAt: string; verificationSourceIdentity: string }>` under Comparable recovery evidence. The capture input is `{ scope: PrivacyScope, subject: PrivacySubjectReference, runId: string, origin: PrivacyErasureOrigin, prefer: PrivacyErasurePreference, excludedRelated: PrivacySubjectReference[], results: Array<{ dataClassId: string; sections: PrivacyErasureSectionResult[] }>, verifiedAt: string, verifiedUpperBoundAt?: string, verificationSourceIdentity?: string }`; `capture(input): Promise<void>` validates zod and contains no reference, aliases or values. These R3-14 types come from **The `eraseSubjects` entry point**; this is a separate optional internal DI seam, not an added input/result member or event field.
   - For configured protection, atomically create the immutable manifest, tagged with the current signing key (**Manifest authenticity**, Data Models), flush the file and containing directories to durable shared storage, then obtain acknowledged publication of the exact file digest in the independent inventory, then upsert the run's `privacy_erasure_pending` row (**Data Models**) in this module's own transaction, and only then resolve. Use create-if-absent publication with identity comparison, never an overwriting rename. `dataClassIds` is distinct `results[].dataClassId`; `executedAt` is this final verification timestamp, never event delivery or a later repair time. The applied row is inserted only once the completed audit proves success. A file, flush, signing, inventory acknowledgement or pending-row failure throws `evidence_capture_failed`; the run remains incomplete with its started journal, owes retry, and emits no completion event. Missing registered provider resolution also refuses. No protected success is returned before durability; unsupported directory durability is an unprotected deployment, not success. Each failure is reported at error level and increments the tenant's `capture_failure_count` with `last_capture_failure_at` in its own short transaction; the first failure of a UTC day, and every failure after the count reaches three, sends `data_erasure.capture_failed` (**API Contracts**, Notification). The first successful capture resets the count. A directory outage therefore stalls protected erasures. Use the retry procedure in **Edge Cases**, "The manifest directory is unavailable".
   - A file with no row after a capture/event/audit crash is conservatively pending, even without a restore. A crash before inventory acknowledgement leaves any valid signed file conservatively pending and requires idempotent registration under the trusted head before clearance. A crash after acknowledgement preserves a required member even if its file or database row is lost. Never reconstruct the inventory from a directory listing. Its verified intent is usable for replay after a restore that removes every database repair source. An incomplete verified run may therefore require a safe redundant re-erasure. Audit reconciliation can settle it while the completion still exists. A retry compares identity and preserves an existing file's original `executedAt` and upper bound; a later same-run completion must not clear a pending identifier file without acknowledgement.
   - Authenticated replay generates no new manifest, including adoption with its original origin: the existing pending file is already durable. Replay completion still commits its applied row/ledger proof. For zero-change or no-event completions, capture is still awaited before protected success. A multi-subject caller invokes capture for each subject's run id, never only the coordinator id.
   - Before activation, close erasure writers and write the non-rewindable, independently configured installation posture and signed coverage record. The C4-owned reader uses a deployment bootstrap trust source independent of C9 DI, the manifest-directory environment, and the application database. Its authority returns verified ordinary-never-activated or activated, keyed to the installation identity; unavailable, inconsistent and uninitialized are errors. Provision an explicit ordinary posture for installations that have never activated and never default absence to ordinary. Upgrade from that posture to activated monotonically under the controller fence; restoring the database, omitting configuration or disabling C9 cannot reset it. The activation authority and trust locator are protected outside application backups and declared as bootstrap prerequisites for all destructive compositions. Retain a database hint only as corroborating evidence, never as permission. Once activated, C4 also requires the C9 provider and its readiness validation; provider or storage failure blocks protected erasure before destructive work. Keep routine service diagnostics distinct from permission to erase or cut over.
2. **Repair precedes comparison.** Startup, the daily job, `restore-status --refresh`, and every `restore-reapply` preview/apply/acknowledgement call run the same sequence: reconcile completed audit entries; repair surviving verified captures or write missing files for surviving completed audits/rows; compute the exact file-minus-row set and verify authenticated expected members, then upsert a pending row for each unsettled run; prune settled pairs and eligible local-unprotected rows; publish the stored status. A failed repair reports `repair_incomplete`; it never clears a previous pending alert. The read-only status route shows the stored count, last check and repair error without scanning files. A successful refresh, with no tenant filter, also publishes the deployment's signed status record (**Refresh status record**, Data Models) outside the database; the readiness form reads that record. Protected readiness also reads the active database binding once and compares it and the external restore generation to the signed record. An older signed record cannot clear a different target or generation. When the directory is unavailable or unset, both forms fall back to one read of the stored replay-state rows, which can keep a gate closed but never report `clear` (**API Contracts**, CLI, "Directory unavailable or unset").
   - **Unsettled capture, detected restore and inventory mismatch.** The pending row's `source` distinguishes verified capture awaiting settlement, a verified file requiring replay after comparison, and an authenticated expected member whose file is missing, mismatched or corrupt. The third state is not a replayable instruction. Report the corresponding inventory failure separately and keep protected clearance closed. None of these states becomes clear through age, deferral or quarantine alone.

   - **Deferral and quarantine.** An entry the product cannot resolve now may be deferred: an identifier entry awaiting the operator's re-run or made unverifiable by a lookup-secret change, a `scope_unsupported`, `authority_unverified` or `kind_unavailable` entry, a held subject, or a pending row whose file is missing. `restore-reapply --defer <runId> --reason <code> [--defer-days <n>]` sets `deferred_until` (default 7 days, at most 30) on its pending row. A deferred entry stays listed, on the page and in the notification with its reason and expiry, and still holds evidence through R4-4, but leaves the exit code until `deferred_until`; it then counts again unless re-deferred. Version 1 entries with unresolved original authority may be deferred under `authority_unverified`. Use that same closed code in persisted records, CLI validation and translated display. Test that the deferral never satisfies strict clearance. A record subject that `--apply` can replay is refused with `defer_not_allowed`. An invalid file (failed schema, path match or signature) may be quarantined: `restore-reapply --quarantine <fileId> --reason <code>`, where `fileId` is the SHA-256 of the relative path that status prints, moves the file with create-if-absent publication to `<deployment>/_quarantine/<yyyy-mm>/<fileId>.json`, outside enumeration, and never deletes it. A quarantined file is never replayed, pruned or used as proof; its pending row, if one exists, stays pending. Both actions are previewed and token-bound like acknowledgements, take `actor: 'system:privacy-cli'`, and write one action-log entry of resource kind `data_erasure.replay_exception`, scoped to the tenant of the entry or of the file's path, with resource id the pending row id for a deferral or that tenant's `privacy_erasure_replay_state` row id for a quarantine, and context holding the run id or file id, reason code and expiry, and no subject values. A deferral is a database row and rolls back with a restore; the entry then counts again, which fails safe.
3. **Mandatory audit reconciliation.** Resolve `actionLogService.list` by DI and list tenant-scoped `privacy.subject_erasure` entries with `sortField: 'createdAt'`, `sortDir: 'asc'`, `pageSize: 100`, independent `resourceKind`, `after` and `before` filters. These filters and stable createdAt/id ordering exist (`packages/core/src/modules/audit_logs/services/actionLogService.ts:491-541, 566-604`). The service decrypts its own context; no audit table access is added here. Validate the delivered `PrivacyErasureAuditContext`, require `status: 'complete'` and matching subject/intent, and separate authenticated replay completions (including adopted journal completions with a preserved origin). Use their audit-only `replayOperationId` and `replaySourceRunId` linkage only to settle the existing selected record. Started/incomplete context and an event alone are not completion proof. Rebuild absent protected applied rows and v2 files only from authentic original evidence with matching source identity and protected upper bound, even if no event was delivered or the run changed nothing, subject to the existing-file/reused-run rule below. Reconstruct execution time from the required saved verification timestamp; completion `createdAt` is only a conservative historical fallback for explicitly labelled legacy/unprotected repair. After rollback, never manufacture a row for an unproven file from another erasure's completion.
   - Persist a per-tenant cursor with the last fully scanned time window, its fixed upper timestamp, page and last completed audit id. Start the initial scan at the earliest retained completion; use a one-millisecond overlap at exclusive time bounds, stable pages of 100 and run-id upserts. Advance the time watermark only after every page and corresponding file write succeeds. Retry an interrupted window idempotently. The daily sweep also rescans all retained completed privacy entries, so late commits behind the incremental watermark are not lost.
   - Scope, `origin`, `prefer`, `excludedRelated`, subject, `runId`, reference, completion status and per-attempt `verifiedAt` are specified in C4's typed encrypted context under **Audit entries**. Consume the timestamp from that validated context; C4's **The run**, step 10, and **Optional completion capture — C9** specify the same verified time and protected upper bound at synchronous capture. The reference is used only for ledger correlation and never copied to a file or event. Their implementation remains an OSS dependency; a missing service or unusable context makes repair incomplete, not a supported silent gap.
   - C4's **Erasure-evidence expiry** checks the durable owner requirement, protected deployment posture and captured fact before consulting R4-4's `privacyErasureEvidenceHold.isPending({ scope, runId })`. An unavailable required owner, unknown proof or unresolved result holds the audit group as `held_by_owner`. C9 answers from owned pending/applied state and the exact authenticated live inventory result. This protects repair even before maintenance records the mismatch. Scan only surviving audit evidence. A pending external file remains pending regardless of age. Acknowledgement without a surviving later complete proof refuses. C4's evidence window remains independent of the settled replay-pair window.
   - **An existing file and a reused run id.** A valid existing file is immutable. If the same run id has a later completion whose typed `context.verifiedAt` is strictly after the file's `executedAt`, compare subject, scope, preference and exclusions with that file; a mismatch is an evidence error. For a matching pending identifier file, do not recreate its original applied row from that later completion: preserve pending state until explicit acknowledgement, which may use the later completion as proof. Maintenance must not overwrite its timestamp or clear it before `--acknowledge`. An already satisfied row retains the file's original execution metadata. This also makes resumed-run acknowledgement compatible with strict same-run file validation.
4. **Exact pending set.** Verify all files in the configured deployment and tenant scope. Eligible replay is the exact set of valid signed files minus satisfying applied rows. Invalid files add `invalid_file_count` and never supply a replay instruction or subject identity. Independently compare each authenticated expected member to its current file. Missing, corrupt or wrong-digest expected members return `manifest_inventory_incomplete` and upsert `privacy_erasure_pending` for the trusted deployment/tenant/run id with source `inventory` if no pending row exists. Otherwise preserve the existing source and set the closed mismatch outcome there. Use tenant and run identity from the authenticated inventory rather than the damaged file. Quarantine preserves this pending state. Distinguish it from an invalid file with no authenticated expected member, which is a status error and creates no per-run erasure instruction. A mixed archive or an empty diagnostic set difference cannot satisfy strict readiness. An eligible file without an applied row remains pending even if unrelated mismatches balance the counts.
5. **Preview-bound replay.** Require `--expect-database <name>` and compare it with the configured active database name before any destructive call. Preview lists pending entries and emits a fifteen-minute confirmation token over actual database name, deployment id, target binding, configured restore generation (if present), tenant filter, every pending run id and normalized manifest digest, selected run ids under `--max`, original organization scopes, preferences, effective exclusions, acknowledgement ids, and deferral/quarantine requests with their reason codes and expiry. Canonical JSON sorts keys and sets. Use the OSS purpose-key derivation with label `privacy-restore-replay-confirmation`; without lookup secret, use a disclosed plain digest for record subjects, as the OSS confirmation design does. Apply repeats these flags, rebuilds the pending set from re-verified files and refuses an expired/mismatched token before erasure. Preview, apply and acknowledgement verify every file's signature before comparison and again before acting on it. A new pending entry, edited file, changed exclusion or changed database or restore generation requires a new preview.
6. **Apply.** For a selected record entry with explicit tenant-wide scope, issue an opaque handle to the manifest version 2 proof under the confirmed operation. Call C4's internal `privacySubjectService.replayCapturedErasure({ replayOperationId, evidence, actor })`. C9 registers `privacyErasureReplayAuthority.verify`; under the operation fence revalidate the signed file and its digest against the selected preview-bound intent, current target and external generation, tenant, source run id and invoking operator. Return the exact original origin, ownership authority, subject, scope, class IDs, preference and exclusions to C4. Apply is never a new controller grant. With a restored matching open journal, C4 adopts its original reference, approval and authority as specified in C4 **Restore replay authority and journal adoption**. Unrelated open journals or intent mismatches leave the file pending. An absent original journal can start a new replay using the same signed authority and stable operation linkage. Replays preserve the original allowed selector. Any extra operator exclusions may narrow a new controller replay only; refuse their use with a journal adoption or portal replay. A historical non-null scope is `scope_unsupported`; never widen it. Signed version 1 evidence whose original mode is ambiguous is `authority_unverified` and remains pending without automatic apply or generic acknowledgement. Authenticated out-of-band reconciliation may be recorded as manual, never as C9 proof. Require the matching authenticated C4 subject result `complete` with zero files pending before settlement. An apply result of `not_found` is always recorded as `absent_root_unverified` and never inserts an applied row. A separate controller acknowledgement must prove fresh scoped absence. Authenticated portal replay can satisfy acceptance only by returning a verified `complete` under the original account authority.
Reject `scope_unsupported` and `authority_unverified` entries before apply or acknowledgement verification; their evidence stays pending.
7. **Identifier entries stay manual (DEC-A, "Subjects known only by an identifier (`privacy:identifier`)").** `--apply` neither calls the run nor inserts an applied row for `privacy:identifier`. Preview prints its run id, time, class ids and the identifier erase command to run with the original preference/scope/exclusions. It stays pending until `--acknowledge <runId>` is verified.

   - **Record-subject absence acknowledgement.** An authorized CLI operator with an `absent_root_unverified` entry previews and runs C4's scoped `mercato privacy erase --absent-root` procedure using the original preference and exclusions. A portal-origin entry cannot use the generic controller `--absent-root` command or its generic acknowledgement. Keep it pending unless the C4 owner can verify the original exact portal-account authority and remaining scope through the authenticated replay seam. For an otherwise eligible controller entry's explicit `--acknowledge <runId>`, call C4's optional `verifyAbsentRecordDependants({ scope, subject, actor, prefer, excludedRelated })` in the exact original tenant scope and with the preview-bound intent. Accept only `{ status: 'verified_clear', checkedAt }` from that owner; a missing seam, pending/refused result, absent attribution for required alias-only copies, or newer hold leaves the entry pending. Call the verifier again on confirmation. Write the owner-verified scope, checked time and operator to the acknowledgement operation and audit before inserting the applied row, with no inferred absence or raw identifiers. Identifier acknowledgements still use the later completion proof below.
   - Resolve completed entries for that derived id through `actionLogService.list`. Require the same tenant and explicit tenant-wide scope (historical organization-scoped entries are blocked), preference and exclusions, a complete result, and validated `context.verifiedAt > entry.executedAt`. The original completed entry carries exactly the capture's verification timestamp, so its later audit-write `createdAt` never qualifies as rerun proof. Missing verification time refuses; never fall back to audit-write time for acknowledgement. Compare the erasure's context `runId`, not its audit entry id. A later completion may reuse the original `runId` if an interrupted run was resumed; its fresh final-verification timestamp distinguishes it from the original completion. Every resumed completion performs final verification again and stores that attempt's `verifiedAt`; the initial attempt's timestamp remains immutable in the manifest. An unchanged original verification at `executedAt` proves nothing, even if its audit entry was written later. A zero-change completion is valid. This implements DEC-A's completed-rerun requirement without accepting a weaker preference.
   - A matching completion inserts the applied row as acknowledged and records the verifying audit id, `runId`, time and operator in the ledger/audit. Without it, refuse and leave pending. A changed lookup secret may make verification impossible; that entry remains visible indefinitely until resolved, never silently pruned.
8. **Ledger and pair completion.** Before apply/acknowledgement, create a `privacy_operations` row with type `replay` or `replay_acknowledgement`, source run id, exact scope and intent. On satisfaction, update that operation, insert the original applied row and delete the run's pending row in one own-module transaction; use source run id and operation type for idempotent recovery. Record the independently verified dependant-clearance proof or the verifying completion when relevant. Failed/refused attempts also remain in the ledger but get no applied row. Reconciliation uses the audit-only operation reference to complete an interrupted operation; it never depends on the engine subscriber ignoring engine origins. No new file is written for a replay run.

### Design decisions

| Decision | Rationale |
|---|---|
| The file is durable before protected completion; the row follows completed-audit proof | A restore before asynchronous repair must still leave external evidence. A verified file without a row may be a crash, so pending can conservatively over-report until reconciliation or replay. |
| The rows live in the database on purpose | They are the thing that *should* roll back with a restore; that is how the restore is seen. |
| No ordering between entries is needed | Set difference does not care which worker committed first. |
| Replay goes through the normal erase run | Holds placed since are honoured, module rules apply, and the run is idempotent. |
| Replay writes no new file | The subscriber ignores events whose origin is replay; repeated restore drills must not grow the list. |
| Refusal and unverified absence remain pending | The ordinary owner absence result does not verify surviving dependant rows. Only explicit acknowledgement with C4 clearance can settle a missing-root entry. |
| Files are grouped by deployment, tenant and month | The exact difference is streamed by directory in bounded batches; equal counts never prove equality. |
| Backup restore and privacy readiness have separate results | The amended backup carrier prints the C9 runbook only; it imports no replay DI service and computes no pending count. |
| Evidence is signed, and only the signing key makes a file actionable | Directory write access is a weaker trust boundary than host access; the tag confines replay to evidence this deployment's own processes wrote (assumption 10). |
| The start gate refreshes; protected readiness reads the signed record, coverage floor and target binding | A probe that reconciles and lists the whole directory on every tick is too expensive, and a database row would roll back with the restore it is meant to reveal. Stored rows are read only when the directory is unavailable or unset, and only to keep a gate closed. |
| Unresolvable entries can be deferred, never cleared | Some entries have no product-side resolution; a bounded, audited deferral keeps them visible and held without making the readiness gate permanently red. |

### Alternatives considered

| Alternative | Why rejected |
|---|---|
| A "newest applied" marker per tenant | See assumption 3. |
| Keep the manifest in the database | It rolls back with the data. |
| Automatic replay at start | Ruled out in the 07-08 spec; it would erase without anyone looking, including subjects under a new hold. |
| Refuse to serve when a restore is detected | See assumption 6. |
| Event delivery and database repair as the only capture | A restore before repair removes the row, journal and audit together. This cannot establish durable evidence before protected completion; the awaited capture seam is required. |
| Keep the identifier's lookup hashes, encrypted, in the file so that replay can find an identifier-only subject's records | It would place a pseudonym of the person's address outside the database for the whole retention window, under a key that sits beside the directory. It would also need the in-process erase run to accept caller-supplied aliases, which the contract does not offer. The derived id cannot be reversed into aliases, but it is itself a keyed identifier pseudonym and permits guess-testing with secret material; the sensitivity remains explicit. |
| Accept `--acknowledge` on the operator's word | The status would clear while the restored records stay live if the re-run was mistyped, never made, or failed. |
| Reuse the attachments drivers | No list operation, and their configuration is in the database being restored. |
| An object-store backend for the files | It needs a new production dependency and its own spec. Until one exists, deployments with only ephemeral disks stay unprotected and are told so. |
| Leave manifest files unauthenticated and rely on owner-only permissions | Anyone with write access to the shared volume could plant a file naming a live subject, which a routine replay would erase (assumption 10). |
| Derive the signing key from the lookup secret | A lookup-secret rotation would invalidate every pending file at once, and evidence signing would share material with tenant lookup hashes (assumption 10). |
| Run `restore-status --refresh` as the readiness probe | Every probe would repeat audit reconciliation and a full directory listing, and one unresolvable entry would keep every tenant unready with no supported way out. |
| Derive file-only pending runs for the R4-4 signal from the aggregate status or a tenant-wide rule | Aggregate counts cannot name a run, and a tenant-wide hold would keep every erasure-evidence group of the tenant while one identifier entry waits for acknowledgement. A per-run own row holds only the runs replay still needs. |

#### ADDED Requirement: Erasure manifest

- WHEN a protected erasure completes
- THEN its external file is already durable, and the matching applied row follows completed-audit proof; comparison conservatively reports pending until that settlement

##### Scenario: Delivered twice
- WHEN the completion event is delivered twice, or to two workers at once
- THEN there is still one row and one file

##### Scenario: Crash between the two writes
- WHEN external capture succeeded but the process crashes before event/completed audit/applied-row settlement
- THEN the file remains pending until completed-audit reconciliation or guarded replay; a database rollback before repair cannot remove it

##### Scenario: Restore before any asynchronous repair
- WHEN a protected completion is followed by a crash and a restore to before erasure before any subscriber or repair job runs
- THEN external evidence still exists and exact comparison reports the run pending

##### Scenario: Undelivered completion event
- WHEN a completion event is never delivered, including a no-event zero-change completion
- THEN synchronous capture still leaves durable external evidence before protected success

##### Scenario: External capture fails
- WHEN a configured directory write or durability flush fails
- THEN no protected completion/event is reported, the started run remains incomplete and retryable, and status exposes the failure

##### Scenario: The directory stays unavailable
- WHEN captures keep failing because the directory is unreachable, full or read-only
- THEN each failure is reported at error level, the restore audience receives `data_erasure.capture_failed` without one notice per failure, routine diagnostics report `directory_unavailable` (exit 3) and strict protected readiness remains closed, and unsetting the directory variable may report unprotected diagnostics while previously protected erasure writes remain blocked

#### ADDED Requirement: Manifest authenticity
The system SHALL act only on manifest files tagged with this deployment's signing key.

##### Scenario: A file planted in the directory
- WHEN a file naming a live subject is written into the directory without a valid tag for a current or listed previous key id
- THEN it is reported as invalid evidence with a non-zero status, is not pending, creates no pending row, and preview, apply and acknowledgement never act on it

##### Scenario: Another deployment's key
- WHEN a validly shaped file is tagged with a key this deployment does not hold
- THEN it is invalid evidence, as if untagged

##### Scenario: Key rotation
- WHEN the current key is replaced and the old key id is listed as a previous key
- THEN files tagged with the old key still verify, new files use the new key, and status reports the count of files per key id so the old key is removed only when none remain

#### ADDED Requirement: Restore detection
The system SHALL detect that erasures recorded outside the database are missing from it, and SHALL report it.

##### Scenario: Restored database
- WHEN files exist for a tenant with no matching rows
- THEN an error is reported, the privacy settings page shows the number of erasures to replay, and the status command exits non-zero

##### Scenario: An erasure after the restore
- WHEN a new erasure completes while older ones are pending
- THEN the older ones are still pending

##### Scenario: Another deployment's files
- WHEN the directory also holds files written under a different deployment id
- THEN they are ignored

##### Scenario: Equal counts hide different run ids
- WHEN one file lacks its row and a different row lacks its file in the same month
- THEN repair runs first and exact set difference still reports the pending file

##### Scenario: A pending file reaches the age window
- WHEN the settled-evidence retention date passes and no applied row exists
- THEN the file and alert remain until the entry is satisfied

##### Scenario: Readiness after a refresh
- WHEN the start command has run `restore-status --refresh` and the readiness probe runs `restore-status --max-age <minutes>`
- THEN the probe checks the signed record and, under `--require-clear`, the live target binding and external generation. It verifies live membership through the bounded inventory owner proof and performs no reconciliation or ad hoc directory listing. A missing, old, wrong-generation, wrong-target or unverifiable record cannot authorize cutover

##### Scenario: Readiness during loss of manifest evidence
- WHEN the directory is unavailable or unset, or the signed record is stale and a later stored directory failure exists
- THEN activation posture comes from the signed external register. The stored replay state can strengthen refusal. Activated installations report a nonzero unavailable result and refuse destructive work, including after restart with unset configuration. Unknown posture fails closed. A verified never-activated installation alone reports diagnostic `unprotected` with exit 0 when no stronger issue exists. Strict forms never clear from stored state.

##### Scenario: An entry the product cannot resolve
- WHEN an identifier entry cannot be acknowledged after a lookup-secret change, or an invalid file is found
- THEN the operator can defer the entry for at most thirty days or quarantine the file through a previewed, audited CLI action; the entry or file stays listed and the deferred entry stays held, but neither keeps the exit code non-zero while deferred or quarantined

##### Scenario: Crash-pending versus restore-detected
- WHEN one pending entry has a capture pending row and another was found only by comparison
- THEN status and the page label the first as an unsettled capture and the second as a detected restore, and both count as pending

##### Scenario: Erasure-evidence expiry meets unsettled replay work
- WHEN C4 checks a run with an unsettled manifest entry or applied-row pair, including a captured run whose applied row is not yet inserted
- THEN replay's R4-4 `privacyErasureEvidenceHold.isPending` returns true from its own scoped rows, expiry counts the run as `held_by_owner` and retries on the next pass; a throwing or unavailable required provider also holds the group

#### ADDED Requirement: Replay
The system SHALL let an operator re-run the pending erasures, in preview by default.

##### Scenario: Preview
- WHEN the command runs without the apply flag
- THEN it repairs evidence metadata, lists the subjects it would erase and emits a token, without changing subject data

##### Scenario: Apply
- WHEN it runs with the apply flag and the confirmation
- THEN the preview-bound set is replayed through R3-14 with its original scope, preference and exclusions; only verified complete record results are satisfied. Record-subject `not_found`, refused, incomplete and identifier entries stay pending

##### Scenario: Record subject absent after restore
- WHEN a record subject was created and erased after the restored point and R3-14 returns `not_found` in its original scope
- THEN the entry stays pending until an explicit audited acknowledgement obtains fresh C4 clearance. A surviving orphan or unverifiable alias-only copy keeps it pending even if the original audit is gone

##### Scenario: Preview no longer matches
- WHEN database, pending set, manifest, exclusions or acknowledgement inputs change
- THEN apply refuses before subject changes and requires a fresh token

##### Scenario: Held since
- WHEN a subject to replay is now under a legal hold
- THEN it is skipped, reported, and still pending afterwards

##### Scenario: A subject known only by an identifier
- WHEN a pending entry is for a `privacy:identifier` subject
- THEN preview lists it as needing the identifier, apply does not run it and inserts no row, and it stays pending until the operator acknowledges it after re-running the erasure by identifier

##### Scenario: An acknowledgement with no re-run
- WHEN the operator passes `--acknowledge` for that entry and no completed erasure of the same derived id is recorded after the entry's time with the same scope, preference and exclusions
- THEN the command refuses it, inserts no row, and the entry stays pending

##### Scenario: An acknowledgement after the re-run
- WHEN a completed erasure by the same identifier has run since the restore
- THEN `--acknowledge` inserts the row and the entry is no longer pending

## 📝 Architecture

All inside the enterprise `data_erasure` module.

- **`lib/manifestStore.ts`**: `write(entry)` and `list(deployment, tenant, month)` plus guarded `prune({ scope, olderThan, appliedRunIds })`. Write owner-only temporary files, fsync them, publish exclusively and fsync the directory chain to `<deployment>/<tenant>/<yyyy-mm>/<runId>.json`. Zod validation is mandatory on write/read; the path's deployment, tenant, run id and UTC month must equal the payload. Reject unknown versions, unsafe path tokens, malformed ids/dates, conflicting same-run payloads and symlinks. `write` tags each file with the current signing key; every read verifies the tag (**Manifest authenticity**, Data Models) before the payload is compared, counted or returned, so comparison, preview, apply, acknowledgement, repair identity checks and pruning all see only verified files. Invalid files produce a visible status error and are neither replayed nor pruned; they cannot masquerade as a zero pending count. Enumeration skips the reserved `_status` and `_quarantine` directories under the deployment; `quarantine(fileId)` is the only operation that moves a file, and nothing deletes an unverified one.
- **`lib/manifestSigning.ts`**: parses `OM_ERASURE_MANIFEST_SIGNING_KEY` and `OM_ERASURE_MANIFEST_SIGNING_PREVIOUS_KEYS`, computes and verifies HMAC-SHA256 tags with a constant-time comparison, and reports per-key-id file counts. It never logs key material and has no database or directory access of its own.
- **`lib/completedErasureReconciliation.ts`**: mandatory audit-service scan and row/file repair with persisted per-tenant windows and page cursor. Reuses the engine's operation reconciliation for audit references. The action-log listing is a required dependency for protected replay; missing service/context keeps the warning/error active.
- **Erasure-evidence owner signal**: `data_erasure/di.ts` registers one `privacyErasureEvidenceHold` composite in `lib/evidenceHold.ts`. It combines C3's unresolved-operation check and this replay check, without multiple registrations under one Awilix key. Replay `isPending({ scope, runId })` is true for an owned pending row or a protected applied row with no `file_written_at`. In protected posture, also perform the fresh bounded live inventory check for that exact run under the caller's existing tenant fence. An `unsettled` result, an `applied` row without the expected member, or unavailable evidence preserves the group. Return false for a verified live file with a satisfying applied row, or for authenticated nonmembership with neither pending nor protected applied row. A verified live file without a satisfying row remains pending. Missing check, unreadable state, deployment mismatch or unknown posture throws and holds evidence. C9's `local-unprotected` applied rows create no expected member and never authorize bypass of the activated-posture rule. The expiry call writes no replay state. Restore comparison persists mismatches for status and maintenance. No audit table access is added.
- **`lib/completionCapture.ts`** and DI **`privacyErasureCompletionCapture`**: the synchronous verified file-first completion boundary above. The provider has no cross-module table reads. C4's **The run**, step 10, specifies the awaited call, `evidence_capture_failed` checkpoint and retry; no implementation can claim protection until that dependency ships.
- **`subscribers/erasure-manifest.ts`**: idempotent event ingestion; obtain typed attribution through `actionLogService.list` using the subject event's `runId`, wait for completed proof, and settle the existing file/applied row. The R3-14 event has no reference or timestamp; the persisted capture/audit supplies verification time. Missing evidence makes repair incomplete; delivery never substitutes for capture.
- **`workers/`** and **`runtime.ts`**: the ordered repair/detection/prune sequence on the module queue, plus worker-start invocation. No new polling mechanism.
- **`lib/restoreDetection.ts`**: exact scoped run-id set difference and stored status.
- **`cli.ts`**: `restore-status` (refresh and readiness forms), token-producing preview, confirmed apply, verified acknowledgement, deferral and quarantine with expected database.
- **`notifications.ts`**: the two notification types under **API Contracts**, sent by `lib/restoreNotifications.ts` with `createBatch` and `skipExistingGroup`.
- **Backup boundary**: the current backup carrier prints the independent status/replay runbook and keeps archive exit status separate. No `erasureReplayStatus` integration is required or promised.

**Pruning.** Only a validated old file whose scoped applied row exists is eligible. A file without a row is pending, regardless of age; preserve it until replayed/acknowledged. Under the owning deployment prune lease and D3’s tenant hold fence, refresh the eligible set and guard before each bounded irreversible file dispatch. Use the privacy retention owner’s durable dispatch evidence and keep unsettled outcomes pending. Verify the current inventory and the candidate’s exact file first. Advance the durable external coverage floor to at least the signed `verifiedUpperBoundAt`, then durably mark that exact member as retiring in the independent inventory before deleting its file. A retirement in progress blocks strict clearance. Under the same tenant fence, the C9 owner exposes bounded read-only `erasureManifestInventory.getTenantRetirementState({ tenantId }): Promise<'clear' | 'pending' | 'unavailable'>` to C3. Resolve only the current authenticated inventory’s exact tenant and return `pending` on its first unsettled retiring member. Invalid, unavailable, timed-out or unscopable evidence returns `unavailable`. Neither result permits successful hold publication. A hold retry never dispatches an unlink. Test lease loss after the retirement marker and before verified unlink: a competing hold stays pending until independently proven settlement, with a second tenant unaffected. After verified unlink, durably complete the retirement under the current inventory head before removing the matching applied row. An unauthorized disappearance without that recorded retirement stays missing. Resume a crash using the durable retirement, matching identity and advanced floor proof. Never retire a missing file by assumption. After an interrupted dispatch, verify file absence under the same scoped ownership before settling the marker. Never settle unknown outcomes from elapsed time alone. Keep the reconciliation watermark so the same old completed audit is not regenerated as a new file during an ordinary sweep; full audit backscans skip settled completions older than the configured evidence window. This exclusion never applies to an existing pending file. A crash leaves an old row with no file, which repair can reconstruct or prune on retry. Never age-delete an invalid file or pending entry, including an identifier entry made unacknowledgeable by a secret change. Report the oldest pending age and the capacity cost. Completed privacy-operation ledger rows have the engine's separate 365-day window.

**R4-4 per-run pending state.** Capture upserts an owned `privacy_erasure_pending` row after the signed file and its inventory acknowledgement are durable and before capture resolves. Exact comparison also upserts rows for verified files without a satisfying applied row and for mismatched expected inventory members. Any such row holds C4 evidence. A pending row can be removed only when the replay owner proves and records its exact outcome: the currently authenticated file and satisfying applied row are reconciled, or an authorized, independently verified retirement is settled under the inventory protocol and current coverage floor. Missing or corrupt expected bytes, quarantine, a deferral and an interrupted retirement do not settle the row. After repair, reverify the exact expected digest and current head before clearing an inventory mismatch. Before this table reflects a new mismatch, the expiry check independently reads live inventory for the candidate run. No pending or applied row is insufficient on its own to prove clearance.

Require valid tenant/organization/run UUIDs, a subject kind declared by the contract with a UUID record id or contract-derived `idv1_` identifier id, known preference, typed exclusion references, UTC date-time and a safe deployment token. `organizationId` is required and nullable: a missing field cannot silently widen scope. Non-null historical scopes are retained but cannot execute with today's tenant-only run.

Validate `origin` as the closed original, non-replay origin. For `portal`, require exactly `authority: { kind: 'portal_account', accountId }`, a matching `customer_accounts:user` record subject and immutable original exclusions. Non-portal origins use `{ kind: 'controller' }`. This is internal authorization evidence, never reconstructed from an email or operator flags. A v2 repair can issue a manifest only from matching typed completed audit evidence that proves origin, authority and verified upper bound. A signed v1 reader uses the old schema/signature label only for inventory and diagnostics. Old evidence missing trustworthy authority or time evidence remains pending for manual reconciliation; it never becomes a replayable unsigned/defaulted v2 entry.

**Manifest authenticity.** `signature` is required in version 2. Its `value` is HMAC-SHA256, base64url, over the canonical JSON of every other field (keys sorted recursively, sets sorted, no insignificant whitespace), prefixed with the version-specific label `om-erasure-manifest-v2` (v1 diagnostic files retain their original label). The trust model:
- **Who signs.** Only `lib/completionCapture.ts` and the repair step of `lib/completedErasureReconciliation.ts`, inside application and worker processes of this deployment. Repair signs a file it rebuilds from a surviving completed audit with the current key; it never re-signs or rewrites an existing file.
- **With what key.** `OM_ERASURE_MANIFEST_SIGNING_KEY` is `<keyId>:<secret>`: a key id of 1–32 ASCII letters, digits, hyphen or underscore, and at least 32 random bytes, base64url. It is deployment-scoped: a staging copy needs its own key even if it wrongly shares the directory. It lives in the deployment's secret store, never in the database, its backups or the manifest directory. `OM_ERASURE_MANIFEST_SIGNING_PREVIOUS_KEYS` is an optional comma-separated list in the same format, used for verification only.
- **What verification refuses.** A missing `signature`, an `alg` other than `HMAC-SHA256`, a key id that is neither current nor listed, a duplicate key id across the two variables, or a tag that does not match (compared in constant time). Each is `invalid_signature`: the file is invalid evidence, counted in `invalid_file_count`, never pending, replayed, acknowledged, pruned or used as repair proof, and `restore-status` exits 1 until it is quarantined. Signature checks run before path/payload comparison results are trusted, and the payload is never printed.
- **Rotation.** Set a new current key with a new id and move the old one to the previous list; restart every process. Files are immutable and keep their original key id. `restore-status` prints the file count per key id, including pending files; remove a previous key only when its count is zero. Removing it earlier turns those files invalid, which the status makes visible rather than silently dropping them. A suspected key compromise is handled the same way, followed by review of every file signed after the suspected exposure, using the per-key counts.
- **What it does not cover.** A party holding the signing key, or the host environment that holds it, can sign evidence; such a party can already run the erase command directly. The tag also carries no secrecy: the directory still needs owner-only permissions (**The manifest itself is sensitive**).

**Refresh status record.** After every successful unfiltered `restore-status --refresh`, startup run or daily job, publish `<deployment>/_status/refresh.json` with create-then-rename into that reserved directory (the one file this module replaces), fsync it and its directory, and sign it like a manifest: `{ version: 2, deploymentId, restoreGeneration, targetBinding, sourceIdentity, snapshotAttestationDigest, restoredSnapshotAt, coverageFloorAt, manifestInventoryHeadDigest, checkedAt, result: 'clear' | 'pending' | 'invalid' | 'repair_incomplete', pendingCount, capturePendingCount, deferredCount, invalidFileCount, quarantinedFileCount, signature }`. The generation and target binding identify the recovery attempt, never the subject. Version 1 may be read as diagnostic history but cannot satisfy protected readiness. The refresh rechecks its pinned generation, snapshot bound, live target and complete manifest inventory head before replacing the record. Validate the SHA-256 head digest on strict reads. A record without it is diagnostic only. A failed refresh replaces it with `result: 'repair_incomplete'` when it can write. When the directory is unreachable, full or read-only, the refresh stores `repair_error_code: 'directory_unavailable'` and the attempt's `checked_at` on the deployment's state rows instead, keeping their last counts; the previous record then ages, and the readiness form uses that stored failure to report `directory_unavailable` rather than a stale record (**API Contracts**, CLI). Protected readiness also validates the current signed floor and rejects if it supersedes the recorded clearance. A restored database cannot change the record, and a directory writer without the key cannot forge a clear one.

The file's internal subject reference is pseudonymous personal data. In particular, an identifier entry stores a keyed pseudonym of an address/number, useful for verified manual acknowledgement; it does not provide the aliases needed for automatic replay. The ordinary settled row/file window is 90 days, a minimum while any subject hold is active in the tenant (assumption 7). Pending files and their metadata never age out automatically.

Replay operation rows store `source_run_id` and, for acknowledgement, `verification_run_id`/verification audit id; a resumed operation is idempotent by deployment, tenant, source run id and type. The applied-row/ledger completion transaction owns only this module's tables. In `privacy.ts.tables`, use the table-coverage spec's exact objects: applied rows have `{ personalData: { kind: 'retention_bounded', boundedBy: 'data_erasure.replay_evidence' } }`; replay state has `{ personalData: { kind: 'tenant_configuration', note: 'deployment/tenant status and audit cursor; no subject values' } }`; pending rows have `{ personalData: { kind: 'runtime_state', note: 'pending replay run ids; deleted when the run is satisfied; no subject values' } }`. Declare record set `data_erasure.replay_evidence`, `targets: ['records']`, `minimumDays: 1`, `excludableSubjectKinds: []`, `unmatchedHoldsOptOut: 'forbidden'`, `handlerService: 'replayEvidenceRetentionHandler'`. `privacy.ts.retentionBounds` gains one `PrivacyRetentionBoundDefinition` of `kind: 'retention_set'` with id and `retentionSetId` `data_erasure.replay_evidence`, `handlerService: 'dataErasureRetentionBounds'` (the module's shared read-only bound handler, defined in the DSR engine's **Retention bounds**) and one whole-table target: table `privacy_erasure_applied`; exact permitted columns `created_at`, `data_class_ids`, `deployment_id`, `excluded_related`, `executed_at`, `file_written_at`, `id`, `organization_id`, `origin`, `prefer`, `run_id`, `satisfied_at`, `satisfied_by`, `subject_id`, `subject_kind`, `tenant_id`, `updated_at`, `verification_json`; `ageAnchor: { columns: ['satisfied_at'], rule: 'data_erasure.replay_applied.satisfied_at' }`; `eligibility: 'data_erasure.replay_applied.settled_pair'` (a settled row of the configured deployment whose file was written and whose run has no `privacy_erasure_pending` row; pending, invalid or file-less evidence is never eligible). The rule ids name predicates in `lib/replayEvidenceRetention.ts` that the settled file-first pruning also uses. For this bound the handler's `resolve` returns `effectiveWindow: { value: <OM_ERASURE_MANIFEST_RETENTION_DAYS>, unit: 'days' }`; active mode for eligible local rows even when protected replay is unconfigured; the diagnostic separately reports replay as unprotected; `mode: 'pending'` while a prune continuation is outstanding; `scheduled` from the `data_erasure:daily-maintenance` schedule; `workerState` from the scheduler or `'unknown'`; and `unboundedReason: 'hold_not_honourable'` when the guard returns any subject, since the set declares `excludableSubjectKinds: []`. A missing runner and a failing guard follow the DSR engine's projection rules. `evaluateFixtureRow` returns `not_eligible` for pending or invalid rows and protected rows without a verified file and otherwise `within_window` or `expired` anchored on `satisfied_at`. The handler requires a window at least `OM_ERASURE_MANIFEST_RETENTION_DAYS`. It prunes protected pairs file-first only with a matching configured deployment and removes eligible `local-unprotected` rows without file I/O after a row-lock recheck. Daily maintenance runs the local branch even with no manifest directory. Skip pending, invalid, foreign-deployment or unreconciled rows. Audit repair may rebuild only still-in-window legacy evidence. Maintenance uses `privacyRetentionService.run`, preserving DEC-C, "Retention sets and holds", and its conservative hold skip and guard errors. This named set supplies `boundedBy`; the positive default remains 90 days, not an indefinite exemption. Applied rows are replay evidence, deliberately exempt from subject erasure until their bounded settled window expires; they are not claimed as anonymous.

**Tenant export (C8).** `data_erasure/di.ts` registers `dataErasureReplayPrivacyTableReader`: C8's `PrivacyTableReader` with `count`, built on the tenant-exit spec's shared helper over an allowlist of exactly these three tables, so `count` agrees with the rows. It is separate from the [DSR engine](2026-11-16-privacy-dsr-engine.md)'s `dataErasurePrivacyTableReader`, whose allowlist is the engine's four tables; a second registration under one Awilix key would replace the first. Both keys carry the required `dataErasure` module prefix. Each table is attributed by its non-null `tenant_id`, over every deployment id of the tenant, `local-unprotected` included. `data_class_ids`, `excluded_related` and `verification_json` are jsonb. `privacy.ts.tableExports` gains:
- `privacy_erasure_applied`: `reader: 'dataErasureReplayPrivacyTableReader'`; `redact: [{ columns: ['subject_id'], reason: 'key_material' }]`, because an identifier entry's `subject_id` is an `idv1_` keyed identifier pseudonym, which the tenant-exit rules treat as an identifier-purpose digest; record UUIDs in the same column are redacted with it. `json`: `data_class_ids` export (declared contract class ids), `excluded_related` redact as `key_material` (it may hold identifier subject references), `verification_json` export (R3-14 outcome, scope, checked time and verifying audit/run ids; no field values). The other scalar columns export under the normal guards.
- `privacy_erasure_replay_state`: `reader: 'dataErasureReplayPrivacyTableReader'`, `exclude: { reason: 'runtime_state' }`: deployment status counts and the audit scan cursor. The whole-table exclusion also satisfies the text-column rule for its `tenant_configuration` classification.
- `privacy_erasure_pending`: `reader: 'dataErasureReplayPrivacyTableReader'`, `exclude: { reason: 'runtime_state' }`: run ids of unsettled replay work.

No column matches the secret-name or extended-token guards. The manifest files and the status record are outside the database and are never exported. Until this step ships, the three tables are named `reader_unavailable` gaps of a tenant export with `data_erasure` enabled.

Deployment names allow 1–64 ASCII letters/digits, hyphen or underscore; `local-unprotected` is reserved and cannot be configured. Both variables must be set before generating files. When configuration is later enabled, audit reconciliation creates evidence under the explicitly configured deployment; it never relabels an imported deployment's rows.

## 📝 API Contracts

- **Settings.** Core posture settings and Enterprise time-attestation settings follow **Bootstrap verification contract**; document the read-only mounted files and controller responsibilities in both app/template `.env.example` and the runbook. `OM_ERASURE_MANIFEST_DIRECTORY`; `OM_ERASURE_MANIFEST_DEPLOYMENT_ID` (validated as above); `OM_ERASURE_MANIFEST_RETENTION_DAYS` (positive integer, default 90); `OM_ERASURE_MANIFEST_SIGNING_KEY` and `OM_ERASURE_MANIFEST_SIGNING_PREVIOUS_KEYS` (format under **Manifest authenticity**). Add those settings plus `OM_ERASURE_RESTORE_GENERATION` (externally pinned UUID) and `OM_ERASURE_RESTORED_SNAPSHOT_AT` (verified UTC snapshot lower bound) to both app/template `.env.example` files with empty values and a comment that the key is a deployment secret; no default key ships. The window controls settled evidence only.
- **CLI.** `mercato data_erasure restore-status [--refresh | --max-age <minutes>] [--tenant <id>] [--require-clear]` has three forms. `--refresh` runs the full repair/comparison sequence and reports pending counts distinguishing unsettled capture, detected restore and expected-member inventory failures, deferred entries with reason and expiry, invalid and quarantined files, files per signing key id, and repair/validation state; without `--tenant` it also publishes the signed status record. `--max-age` (1–1440, no tenant filter) is the readiness form: in diagnostic mode it reads the signed status record. Both refresh and readiness accept `--require-clear` only without a tenant filter. This mode requires independently verified activated posture and configured, signed, fresh, unfiltered clearance for the current target, external restore generation and a qualifying coherent recovered snapshot within independently retained coverage, no pending or deferred entries, and no unresolved invalid or quarantined evidence. It performs one target identity read and verifies the bounded current inventory membership proof on a probe, without listing the directory itself. An unprotected, unavailable or uncertain result exits nonzero. Without either flag it reads only the stored database rows, for operators. Diagnostic exit codes: 2 while non-deferred entries are pending, 1 on invalid configuration, an unquarantined invalid file, incomplete repair, or (readiness form) a missing, unverifiable or older-than-bound record in an available directory, 3 for `directory_unavailable` below, 0 only for a successful clear check or a verified never-activated diagnostic state as defined below. Deferred entries and quarantined files are reported but leave the exit code. **Directory unavailable or unset.** The two gate forms, `--refresh` and `--max-age`, then fall back to one indexed read of the deployment's stored `privacy_erasure_replay_state` rows: with the directory unset, those of `OM_ERASURE_MANIFEST_DEPLOYMENT_ID`, or, when that is unset too, of the most recently checked configured deployment; never `local-unprotected`. (a) *Configured but unavailable*: the refresh cannot list or write the directory (unreachable, full or read-only); or the readiness form cannot open the configured root within five seconds; or it finds the record older than the bound while a stored `directory_unavailable` failure is checked after the record's `checkedAt`. The command prints `directory_unavailable` with the stored failure time, if one is stored, and exits 3. (b) *Unset directory*: resolve the same signed installation posture first and apply the diagnostic outcomes below. In both cases the gate still refuses when the stored rows hold a non-deferred pending entry (exit 2) or, otherwise, an unquarantined invalid file (exit 1), and a failed state read exits 1. Stored rows can keep a gate closed after a restore was detected. They cannot supply protected clearance. A verified never-activated installation alone may report diagnostic `unprotected` with exit 0. An activated posture with unset configuration or unavailable storage reports `directory_unavailable` (exit 3) unless the stored pending/invalid result is stronger. Unreadable or unknown posture reports `activation_posture_unavailable` (exit 1), even with the directory unset. Erasure checks at entry refuse for activated or unknown posture whose required evidence is unavailable. A missing record under an available root still exits 1, so a deleted record cannot pass for an outage. Only routine diagnostics may use bare refresh/readiness. Every protected cutover recipe MUST use unfiltered `restore-status --refresh --require-clear` after reviewed replay and `restore-status --max-age <m> --require-clear` afterwards, with strict refresh scheduled at a shorter interval. No diagnostic exit 0 or exit 3 permits protected reopening. A database row alone never authorizes reopening. `mercato data_erasure restore-reapply --expect-database <name> [--tenant <id>] [--max <n>] [--exclude-related <kind:id> …] [--acknowledge <runId> …] [--defer <runId> … --reason <code> [--defer-days <n>]] [--quarantine <fileId> … --reason <code>] [--apply --confirm <token>]`. Preview is the default and prints its token. `--max` defaults to 100 and allows 1–1000; processing batches/page sizes stay at most 100. Repeat the exact flags with `--apply`; acknowledgements, deferrals and quarantines are also previewed and confirmed. Exit 2 on pending/refused/incomplete entries; a confirmation/database/schema error exits 1 before subject changes. `--acknowledge` accepts identifier entries or a record-subject entry with `absent_root_unverified` and verifiable current C4 clearance, verified by the matching completed audit as specified above. `--defer` takes a `deferral_reason` value valid for the entry (Proposed Solution, step 2) and refuses `defer_not_allowed` for a replayable record subject; `--defer-days` is 1–30, default 7. `--quarantine` takes reason `invalid_signature`, `invalid_schema` or `path_mismatch` and refuses a file that verifies. Every action uses actor `system:privacy-cli` and writes its `data_erasure.replay_exception`, replay or acknowledgement audit; no route or RBAC feature exposes these actions (assumption 11).
- **Route.** `GET /api/data_erasure/restore-status`, feature `data_erasure.view`, exports `GET = withTenantWideScope(handler)` under R3-9, "Organization-scope guard on every DSR route", in the engine spec's API Contracts. It reads only the caller tenant's stored counts/time/error state; restricted or unresolved organization scope returns 403.
- **Notification.** Two types in `data_erasure/notifications.ts`, in-app, `severity: 'error'`, with locale-key title/body, linking to the privacy settings page:
  - `data_erasure.restore_pending`: sent after a refresh or detection pass finds non-deferred pending entries or invalid files for a tenant. Group key `data_erasure.restore_pending:<deploymentId>:<tenantId>:<setDigest>`, where `setDigest` is the hex SHA-256 of the sorted non-deferred pending run ids and unquarantined invalid file ids. The same unchanged set produces no second notice across worker starts and daily passes; a changed set, or a deferral that expires, produces one new notice.
  - `data_erasure.capture_failed`: sent on configured capture failures as specified in Proposed Solution, step 1. Group key `data_erasure.capture_failed:<deploymentId>:<tenantId>:<utc-date>`, so a stalled directory produces at most one notice per tenant per day.
  Both are sent with `notificationService.createBatch(..., { skipExistingGroup: true })` (`packages/core/src/modules/notifications/lib/notificationService.ts:271-279`), as the security module's bypass notice does. Send only to tenant staff who currently have the erase feature through wildcard-aware RBAC and satisfy the same unrestricted organization-scope predicate. Re-evaluate the audience when sending, rather than trusting a feature grant alone. Payload carries counts and a page link, no manifest references, run ids or subject ids; page/status access rechecks scope.
- **Doctor.** `data_erasure.manifest_unconfigured` is declared in `privacy.ts.doctorChecks` under DEC-I, "The doctor's extension point", and R3-2, "The registry carries the whole `privacy.ts` default export". The default check is configuration-only: required variables, safe deployment name, and a well-formed current signing key with no duplicate key ids when the directory and deployment id are set; it never prints key material. Report directory existence, shared durability and cross-replica visibility as operator attestations, not verified configuration facts; the status/capture commands perform I/O checks. A second configuration-tier check, `data_erasure.backup_retention_exceeds_replay_window`, is declared in the same `privacy.ts.doctorChecks` with the same shape. It reads only environment values and the doctor's enabled-module snapshot (`moduleIds`) and imports no backups code. When `moduleIds` includes `backups` and the effective `OM_BACKUP_RETENTION_DAYS` (default 35) is at or above the effective `OM_ERASURE_MANIFEST_RETENTION_DAYS` (default 90), it reports a warning: restored archives older than the settled-manifest window cannot be fully replayed, because their erasures may be recorded only in files already pruned. An unset or invalid value is read as its documented default. Severity is fixed per check under the doctor's rule, so with `backups` disabled the check reports nothing rather than an informational finding; archives taken outside the product remain the deployment docs' rule (assumption 7). Database inspection, if added by the doctor owner, belongs to R3-4, "An opt-in database tier for the doctor"; this spec adds none.

## 📝 Edge Cases & Failure Scenarios

| Case | Behaviour |
|---|---|
| Directory or deployment id not configured | A never-protected installation may erase with explicit unprotected evidence. Previously activated installations refuse unprotected erasure through C4’s signed external activation posture. Diagnostics still report unprotected or the stronger pending/invalid result; neither clears cutover |
| Configured capture file write/flush fails | The erasure stays incomplete, emits no completion and is not protected; retry its started journal. Surviving historical rows may be repaired but do not retroactively prove the original completion was protected |
| The manifest directory is unavailable, full, read-only or unset after activation | Protected erasures refuse before the first mutation when preflight detects the outage. A failure after preflight leaves the started run incomplete and retryable, with no protected completion. Preserve `evidence_capture_failed` logging, tenant failure counters and bounded notices. Routine reads and status diagnostics can continue. An activated installation still refuses after restart with configuration unset and both strict gate forms remain closed. Restore the original storage and provider configuration, verify posture, rerun `restore-status --refresh --require-clear` for protected cutover and retry the same erasure journal. No capture-free erasure mode exists after activation. |
| A file planted or edited in the directory | Its tag fails or is missing: `invalid_signature`, status exits 1, nothing is replayed, acknowledged or pruned, no pending row is created. The operator inspects it and quarantines it |
| A file signed with a key that has since been removed from the previous list | Invalid evidence, as above; status had listed its key id with a non-zero count before removal. Re-adding the previous key restores verification |
| Directory and deployment id set, signing key missing or malformed | Invalid configuration: capture refuses, status exits 1, the doctor reports it; never unsigned files |
| An entry with no supported resolution (identifier after a secret change, `scope_unsupported`, `kind_unavailable`, held subject, pending row without a file) | Listed and alerted. The operator may defer it for up to thirty days with a reason; it stays listed and held, leaves the exit code until expiry and re-enters it unless re-deferred |
| An invalid file the operator has inspected | Quarantined by a previewed CLI action into `_quarantine/`; never deleted, replayed or pruned; leaves the exit code |
| A restore rolls back a deferral | The entry counts again and alerts; the operator defers it again. Fails safe |
| A readiness probe runs between refreshes | Diagnostic mode may report the last refresh within its age limit. Protected readiness also binds the record to its current generation and target. A cutover stays closed until a new unfiltered comparison succeeds. |
| A readiness probe runs during a directory outage | Diagnostic mode reports `directory_unavailable` (exit 3), or a stronger stored pending/invalid result. `--require-clear` refuses without current evidence. Cutover remains closed. |
| Event not delivered, or a zero-change run emitted none | Protected completion already awaited durable capture; mandatory audit reconciliation settles rows. Restore-before-repair still finds the file; a scan error preserves incomplete status |
| Replicas with separate local directories | Each sees only its own files; detection is unreliable. Unsupported, and the documentation says the directory must be shared |
| A staging copy of production with its own deployment id | Sees no files under its id; nothing is pending |
| A staging copy configured with production's deployment id and directory | With its own signing key, production treats staging's files as invalid evidence and staging treats production's the same way; both statuses exit 1. With production's key copied too, it is indistinguishable from production. The documentation names both as mistakes to avoid; the replay command's database check is the last guard |
| A restore from another environment's dump | Its rows carry another deployment id and are ignored; every file is then pending. Reported; the operator decides |
| The directory is lost | Detection finds nothing; stated as the reason it must be on durable storage |
| Replay target is the wrong database | Require `--expect-database`, compare with the active configured database and refuse a mismatch before erasure; the token also binds that database and deployment |
| A record subject was created and erased after the restored point | Ordinary `not_found` leaves `absent_root_unverified`. A previewed, audited acknowledgement may settle only with fresh C4 dependant-clearance evidence in the original scope. |
| The pending entry is for a `privacy:identifier` subject | Not run; no row inserted; listed as needing the identifier; pending until `--acknowledge <runId>` after the operator's own re-run by identifier |
| `--acknowledge` names an entry for a record-subject | Only an `absent_root_unverified` entry is eligible; a present root or held/unverified dependants refuse. Present records follow normal guarded apply. |
| `--acknowledge` with no re-run, a re-run by another identifier, or a re-run that did not complete | Refused; no row; the entry stays pending. The message names the missing run |
| The operator's re-run found nothing left to change | Accepted: the erase run writes its completed entry even with zero rows affected |
| The re-run is refused by a hold placed since | No completed entry; `--acknowledge` refuses, as `--apply` does for a held subject |
| The lookup secret changed between erasure and re-run | Different derived ids fail acknowledgement; retain the pending file and alert regardless of age. Resolve before changing the secret or restore the old derivation material under the key-rotation procedure; there is no automatic expiry escape. Until then the operator may defer the entry with reason `identifier_unverifiable`, which keeps it listed and held but out of the readiness exit code |
| The subject has gained a related subject since | Refuse until a new preview binds an explicit exclusion; replay never widens the original subject list by naming an additional subject |
| Several replicas run detection at once | Each stores the same result; none replays |
| Old file with a matching applied row | Eligible for file-first pruning; a subsequent restore older than the evidence window is unprotected |
| Old file without a matching row | Still pending and never age-pruned; a near-window restore cannot clear itself |
| Any subject hold is active in the tenant | The `data_erasure.replay_evidence` pass skips with `hold_not_honourable`; every settled pair stays past its window until no hold is active, and the bound projection reports the reason |
| `backups` enabled with archive retention at or above the replay window | The doctor warns with `data_erasure.backup_retention_exceeds_replay_window`; restoring an archive older than the window can miss erasures whose settled files were pruned |
| Equal file and row counts with different run ids | Exact set difference still reports the missing run id; repair is attempted first |
| Missing/changed token or changed manifest/pending set | Refuse before any subject mutation and require another preview |
| Invalid file or path/payload mismatch | Do not replay or prune it; store a validation error and keep status non-zero until it is quarantined |
| Pending row with no file and no applied row | Keep the row so R4-4 still holds the run; report an evidence error. Repair writes the file from a surviving completed audit and settles the run; otherwise C4's open run owes retry |
| Historical organization-scoped erasure | Preserve the original scope, report `scope_unsupported` and leave pending without an erase/acknowledge call. Current C4 requires tenant-wide erasure; never widen an entry |
| Restricted user holds the view/erase features | Status route returns 403 and no restore notice is sent |

## 📝 Risks & Impact Review

#### A restore goes unnoticed
- **Scenario**: The directory was not configured, was not shared between replicas, or was on a disk that did not survive.
- **Severity**: High
- **Affected area**: every erased subject since the restored point
- **Mitigation**: A standing warning when unset; the documentation and the doctor's configuration check.
- **Residual risk**: Deployments with only ephemeral disks have no protection until an object-store backend is specified.

#### Erased data is served between restore and replay
- **Scenario**: The application runs for hours after a restore before anyone replays.
- **Severity**: High
- **Affected area**: restored tenants
- **Mitigation**: Error-level report from the worker at start and daily; a deduplicated `data_erasure.restore_pending` notification; `restore-status --refresh --require-clear` at protected cutover and the generation-bound readiness form, refreshed on the operator's schedule; the procedure in the docs puts replay before reopening.
- **Residual risk**: By default the application runs, and detection can lag a restore by up to a day where no worker restarts and no refresh is scheduled; with a schedule, by up to its interval. That is assumption 6.

#### The manifest itself is sensitive
- **Scenario**: Someone reads the directory.
- **Severity**: Medium
- **Affected area**: internal ids of erased records
- **Mitigation**: Owner-only directory/files; no raw identifiers or lookup hashes; the signing key is never stored in the directory; settled evidence expires at the configured window. Pending entries keep the pseudonym because replay/verified acknowledgement needs it.
- **Residual risk**: Record ids can be linked to retained data. An `idv1_` identifier id is a keyed pseudonym of tenant/type/address or number; someone with directory access and lookup-secret material can test guesses and infer an erasure request without a database copy. Pending files may remain indefinitely; protection of the directory and keys is required.

#### Replay erases something it should not
- **Scenario**: The command is aimed at the wrong database, or the directory holds another deployment's files under this deployment's id.
- **Severity**: High
- **Affected area**: the target database
- **Mitigation**: Strict zod and path/payload validation, a per-deployment signing key so another deployment's files are invalid evidence, original organization scope, explicit `--expect-database`, a short-lived token over pending entries and manifest contents, preview by default and holds rechecked. A record-subject `not_found` stays pending until explicit acknowledgement using independent C4 dependant verification.
- **Residual risk**: An operator who confirms a preview without reading it, or two deployments configured identically, signing key included.

#### A planted manifest makes a routine replay erase a live subject
- **Scenario**: Someone with write access to the shared directory, but not to the application host, writes a well-formed file naming a live customer. Without authentication it would surface as pending, and the normal replay workflow would erase that customer.
- **Severity**: High
- **Affected area**: any live subject of the deployment; the shared-storage trust boundary
- **Mitigation**: Assumption 10 and **Manifest authenticity**: every file is HMAC-tagged under a deployment-scoped key held only by the application's processes, outside the database and the directory; verification precedes comparison, preview, apply, acknowledgement, repair and pruning; An untagged, foreign-key or mismatched file is invalid evidence and never replayable. A live authenticated inventory member with invalid bytes is pending for repair. Quarantine alone cannot clear an expected-member failure. Rotation keeps listed previous keys verify-only, with per-key counts. `manifestSigning.test.ts`, `restoreReapply.test.ts` and TC-PRIVACY-REPLAY-004 cover planted, foreign-key and rotated-key files.
- **Residual risk**: A party holding the signing key can sign evidence; that party already holds the host environment and could run the erase command directly. A leaked key requires rotation and review of files signed since the exposure.

#### The manifest directory is unavailable
- **Scenario**: The shared volume is unmounted, full or read-only, and every protected erasure in the installation refuses.
- **Severity**: High
- **Affected area**: page, portal, CLI and retention erasures of every tenant; the controller's response deadlines
- **Mitigation**: Error-level logs per failure, `capture_failure_count` and last failure time in status, and at most one `data_erasure.capture_failed` notice per tenant per day to the restore audience. Diagnostic status reports `directory_unavailable` (exit 3), and routine incident handling may keep an already-open service running, so the outage does not also take the application out of service, while a stored unreviewed restore still fails them. Previously protected installations pause erasure during degraded diagnostics. Removing configuration or a provider cannot create an untracked coverage interval. Operators restore durable evidence availability or carry out the separately documented external controller process with the product cutover still uncertified.
- **Residual risk**: Erasure writers remain paused during an evidence outage in a previously protected installation. The controller still owns incident handling and separately evidenced manual reconciliation.

#### An unresolvable entry keeps readiness red, or a deferral hides a real restore
- **Scenario**: An identifier entry after a lookup-secret change, a historical organization-scoped entry or an invalid file keeps every tenant unready; or an operator defers entries to reopen without replaying.
- **Severity**: Medium
- **Affected area**: availability; restore protection
- **Mitigation**: Deferral and quarantine are host-level CLI actions, previewed, token-bound, reason-coded and audited (assumption 11). A replayable record subject cannot be deferred; a deferral lasts at most thirty days, stays listed, notified and held through R4-4, and re-enters the exit code on expiry or after a restore rolls it back. Quarantine moves, never deletes. `restoreStatusReadiness.test.ts` covers both paths.
- **Residual risk**: A host operator can keep re-deferring an identifier entry; each deferral is a visible audit entry.

#### An identifier-only erasure is reported as replayed when it was not
- **Scenario**: After a restore, the pending entries include an erasure of a guest payer known only by email. A replay that runs it finds nothing, because nothing in the entry can find the person's records, and marks the entry applied while the restored records stay live.
- **Severity**: Critical
- **Affected area**: people known only by an address or number: guest baskets, pay-link payers, email claimants, correspondents
- **Mitigation**: Assumption 8. Such entries are never run or marked applied by `--apply`. They are listed apart with the command to re-run, and stay pending, with a non-zero status, until the operator acknowledges each after re-running it by identifier. The acknowledgement is refused unless a completed erasure of the same derived id is recorded after the restore, so a mistyped, missing or failed re-run cannot clear the status. Unit tests and TC-PRIVACY-REPLAY-003 cover it.
- **Residual risk**: Their replay depends on the operator re-running each with the identifier from their own request records. The product cannot do it alone, and the docs say so. After a lookup-secret change verification can fail indefinitely; pending entries are preserved and cannot age-clear the alert.

#### A verified capture reports pending after a crash
- **Scenario**: A file exists and its row does not, with no restore.
- **Severity**: Medium
- **Affected area**: operators' trust in the report
- **Mitigation**: Label this as pending replay evidence, not proof that a restore occurred. Mandatory completed-audit repair can settle a surviving completion, and exact set difference plus settled-pair pruning remain authoritative.
- **Residual risk**: File-first capture deliberately permits conservative pending alerts after a crash before completion; redundant guarded erasure is safer than lost restore evidence.

#### Erasure evidence expires while a replay pair is unsettled
- **Scenario**: C4's audit group reaches its expiry age while replay still needs it to settle a manifest entry or applied-row pair.
- **Severity**: High
- **Affected area**: erasure-evidence expiry, replay repair and identifier acknowledgement
- **Mitigation**: R4-4 checks owned pending and applied rows and reads the exact authenticated inventory member and its current file. A newly missing, corrupt, wrong-digest or retiring member holds C4 evidence before maintenance. The next pass retries after verified repair or retirement, with tests for provider failures and tenant/run isolation.
- **Residual risk**: Pending work or provider failures may retain evidence indefinitely; the program rule that unresolved work extends evidence accepts this. A later identifier rerun's own evidence is not held, so acknowledgement after that evidence expires refuses and the operator reruns again.

#### Holds keep replay evidence past its window
- **Scenario**: A subject hold is active in the tenant, so the `data_erasure.replay_evidence` pass skips and settled applied rows and files outlive the 90-day window.
- **Severity**: Low
- **Affected area**: settled replay evidence (internal pseudonymous subject references)
- **Mitigation**: Because `data_erasure.replay_evidence` declares `excludableSubjectKinds: []`, any active subject hold in the tenant defers expiry of every settled entry until no hold is active; the 90-day window is then a minimum, not a bound. The hold reason is reported by the bound projection (`unboundedReason: 'hold_not_honourable'`) and the status output, and `unmatchedHoldsOptOut: 'forbidden'` stops a policy from trading the hold away. The first pass after release expires the backlog at the original age.
- **Residual risk**: A tenant that always has a hold keeps settled replay evidence indefinitely.

### 2026-11-17
- Manifest authenticity: every manifest file and the new refresh status record carry an HMAC-SHA256 tag under a deployment-scoped `OM_ERASURE_MANIFEST_SIGNING_KEY` kept outside the database and directory, with verify-only previous keys for rotation. Untagged, foreign-key or mismatched files are invalid evidence, never pending or replayed. Assumptions 10 and 11 state who signs, what verification refuses, and that every override is a host-level, audited CLI action with no RBAC route.
- Readiness: `restore-status --refresh` is the start gate and `--max-age` reads only the signed status record. Bounded, reason-coded deferral and quarantine keep unresolvable entries and invalid files listed and held without keeping readiness red. Output separates unsettled captures from detected restores.
- Named notification types `data_erasure.restore_pending` and `data_erasure.capture_failed` with group keys and `skipExistingGroup` dedupe; directory-outage reporting, risk and degraded-mode procedure; one composite `privacyErasureEvidenceHold` registration for both `data_erasure` checks. Tests, integration cases, risks, migration and compliance updated.
- Replay evidence bound: `data_erasure.replay_evidence` declares `unmatchedHoldsOptOut: 'forbidden'` and a `retentionBounds` entry for `privacy_erasure_applied`, served by the DSR engine's `dataErasureRetentionBounds` handler with pruning's predicates. Assumption 7 and a new Low risk state that any active hold makes the 90-day settled window a minimum. A second configuration doctor check, `data_erasure.backup_retention_exceeds_replay_window`, warns when `backups` keeps archives at or beyond the replay window.
- The file-only pending gap recorded as open in pass five is closed by the `privacy_erasure_pending` table under Data Models (R4-4 file-only pending state).
- Directory outages and degraded mode no longer take the application out of service: both gate forms fall back to one stored-state read, reporting `directory_unavailable` (exit 3, diagnostic only) or `unprotected` (exit 0), while a stored unreviewed restore still fails them. A refresh that cannot reach the directory stores `directory_unavailable`. Worker start writes one tenant-scoped `protection_disabled` entry per affected (deployment, tenant) state row; deferral and quarantine entries name their tenant and resource id.
- The three tables get their own C8 reader, `dataErasureReplayPrivacyTableReader`, with `tableExports` entries (applied-row `subject_id` and `excluded_related` redacted as `key_material`; replay state and pending rows excluded as `runtime_state`), tested in the Enterprise package in Phase 1.
