## 📝 TLDR

A customer-portal user can see their email, last login and roles on a read-only profile page. They cannot change anything there, download what is held about them, or close their account; the colleague-removal route refuses a user who tries to remove themselves. **Proposed (future):** a Privacy page in the portal where a signed-in user can download their account data as a file and ask for their account to be deleted. Deletion takes effect after a grace period, during which they can still sign in and cancel, and during which the company's staff are told and can cancel it too. The profile page also gains a form for the display name.

**Status.** The program's DEC-2b proposes OSS placement, with named upstream carrier approval required before implementing the rights invokers or claiming OSS delivery. Phase 1 (display name) includes the profile-route hardening below and can ship independently of the privacy module. DEC-13 governs the narrowed existing-route behaviour one narrowing at a time: the registry and cross-site checks on the existing profile and password-change writes take its Emergency Security Exception, because an accepted cross-site request is itself the exploit; password change's re-authentication 429 follows the ordinary protocol with an upgrade note and a one-minor bridge (assumption 10, Migration). Phases 2 and 3 ship once their parent contracts are implemented.

**Not in this spec:** changing the account's email, which needs a verified flow of its own (`portal-email-change`, added to the program); the CRM record a tenant keeps about the person, which stays under the tenant's control; data in modules that do not yet register a data class; portal MFA.

## 📝 Overview

> **Market reference.** GitLab and Discourse both let a user download their own data and delete their own account from account settings, ask for the password again first, and delay deletion — GitLab by seven days — so that a hijacked session cannot destroy an account instantly. Adopted: re-authentication, a grace period with cancel, a confirmation email. Rejected: Discourse's rule that an account with content cannot self-delete; here the erasure run decides what is kept, not the form.

## 📝 Problem Statement

- **The profile page is read-only.** It renders email, last login, roles and features with no form (`packages/core/src/modules/portal/frontend/[orgSlug]/portal/profile/page.tsx`). A profile update route exists and accepts only `displayName` (`customer_accounts/api/portal/profile.ts`; `data/validators.ts`), and no page calls it.
- **Self-deletion is refused.** `customer_accounts/api/portal/users/[id].ts` returns 400 when a user targets themselves. That route is for a company administrator removing a colleague.
- **Nothing exports.** No portal route returns the user's data as a file. The staff-side forms export is the only precedent: a synchronous JSON response with an attachment header (`forms/api/subjects/[subjectType]/[subjectId]/export/route.ts`).
- **No shared re-authentication counter exists** for portal actions. Password change checks the current password, without counting or throttling failures (`customer_accounts/api/portal/password-change.ts`). `passwordHash` is nullable.
- **A token's issue time does not prove recent authentication.** The refresh route mints a new eight-hour token on the same session row from the thirty-day cookie, with no credentials (`sessions-refresh.ts`; `customerSessionService.ts`). Only the session row's creation time is trustworthy; rows are created by password login, magic-link verification and invitation acceptance. Older tokens carry an empty session id (`customerAuth.ts`).
- **Login lockout is shared.** Five wrong passwords lock sign-in for fifteen minutes behind a generic 401 (`customerUserService.ts`). A re-authentication prompt that counted against it would let a session thief keep the owner out.
- **Rate limiting fails open**, is keyed by IP and hashed identifier, and can be bypassed in the test runner's opt-in rate-limit mode (`auth/lib/rateLimitCheck.ts`).
- **No rule protects a company's last administrator.** "Administrator" is any user holding `portal.users.manage` in the same company.
- **A soft-deleted portal user keeps email, hash and name** (`customerUserService.ts`), and the deletion event carries the email. The erasure spec changes both.
- **A new account with the same email is linked back to the retained CRM person** (`autoLinkCrm.ts`).

## 📝 Proposed Solution

One new page, seven new HTTP handlers across five route files, account-state columns, and one daily job. Phase 1 also hardens the existing profile write.

| Action | What happens |
|---|---|
| Edit display name | A versioned form calls the hardened profile update command through the existing route |
| Download | After re-authentication the browser receives one JSON file: the export document for the user's own account, from the account class only |
| Request deletion | After re-authentication the account is marked, a confirmation email is sent, staff are notified, and the page shows the date and a cancel button |
| Cancel | The user, or staff with a reason, clears an unclaimed request; a claimed request returns 409 |
| Grace period ends | A daily job runs the erasure operation for the account alone |

### Design decisions

| Decision | Rationale |
|---|---|
| The account stays usable during the grace period unless staff deactivate it | Blocking login would make cancelling impossible from inside the portal. |
| New columns carry the pending state | `is_active` and `deleted_at` both block login. |
| The request outlives a deactivation or soft delete by staff | Otherwise an administrator's soft delete would quietly replace an erasure with a row that keeps the email and name. |
| Only a complete erase result closes a request | The erase run keeps the row, anonymized and soft-deleted (erasure spec, three roots). A mark left set would run the erasure again every day and show a pending deletion with a cancel button for ever. |
| The download names its data class explicitly | Fan-out is by subject kind, so a class added later would otherwise join the download unreviewed. |
| Re-authentication has its own failure counter | So that it cannot be used to lock the owner out of sign-in, and so that password change stops being an unthrottled oracle. |
| New routes for self-service; the colleague-removal route keeps its refusal | That route is authorized by a company-administration feature and must stay distinct. |
| Every write uses server mutation guards and the cross-site check | The browser hook alone cannot protect a direct HTTP request. Phase 1 hardens the existing profile route too. |
| The privacy service is reached through a DI key, softly | Download needs `privacySubjectService`; deletion also needs `subjectHistoryService` and its schedule, so interrupted erasure can recover. |

### Alternatives considered

| Alternative | Why rejected |
|---|---|
| Delete immediately | A stolen session would be enough to destroy an account. |
| Include the CRM person in the download | See assumption 1. |
| Email a download link | Needs stored generated files, signed links and expiry, none of which exist. |
| Let the last administrator leave and notify staff | A company with users and no administrator cannot manage itself; refusing is the smaller change. |
| Use the age of the session token | It can be renewed without credentials. |
| Self-service off by default; users ask the company | Every deployment should answer access and erasure requests from the product (DEC-2b); a tenant that answers by hand turns the switch off. |
| Staff are notified but cannot cancel | The controller could not stop a request on identity doubt or its own legal grounds. |
| An ordinary one-minor bridge for the cross-site narrowing of the profile and password-change writes | DEC-13: the accepted cross-site request is itself the vulnerability. Password change's re-authentication 429 is not argued that way and keeps the ordinary bridge. |

The system SHALL let a signed-in portal user download the data held in their portal account, after re-authentication, and SHALL NOT include another person's data.

- THEN they receive a file containing their profile, sessions, roles and the invitations addressed to them

##### Scenario: Wrong password
- WHEN the password is wrong
- THEN nothing is returned, and sign-in with the right password still works

#### MODIFIED Requirement: Removing one's own portal account
The system SHALL let a signed-in portal user request deletion of their own account, SHALL keep the account usable for a grace period, and SHALL erase it when the period ends unless the request was cancelled.

##### Scenario: Request and cancel
- WHEN a user requests deletion and cancels the next day
- THEN the account is unchanged and no erasure runs

##### Scenario: Grace period ends
- WHEN the period ends without a cancel
- THEN signing in fails, the email can be used for a new account, the linked CRM person still exists, and the request is closed: the account shows as erased, nothing is pending, and a later run of the job changes nothing

##### Scenario: Staff remove the user during the period
- WHEN an administrator soft-deletes the user before the period ends
- THEN the erasure still runs at the end of the period

##### Scenario: Sole administrator
- WHEN the only active user with user-management rights in a company that has other active users requests deletion
- THEN the request is refused with an explanation

##### Scenario: Concurrent administrators
- WHEN two administrators in one company request deletion together
- THEN the company lock serializes acceptance and at least one request is refused

- WHEN the seventh failure's `recordFailedHandoff` call throws for an infrastructure failure

## 📝 Architecture

- **`customer_accounts`**: the self-service and settings routes; profile hardening; `lib/reauth.ts`; deletion-state service and columns; a worker on its own queue; templates, events and notification.
- **`portal`**: the Privacy page and versioned profile form.
- **`privacy`**: supplies `privacySubjectService` through DI. `subjectHistoryService` is an additional required capability for portal deletion, resolved softly. No portal code reads another module's tables.

**Shared service and export audit.** C1 owns `privacy/di.ts` and `privacy/lib/subjectService.ts`; C7 consumes that registration and never creates a second service or registry. Definitions come from operation-time runtime `getModules()` and `Module.privacy` through `getPrivacyDataClasses`, as R3-2 specifies, not `getCliModules()` or an early cached class list. Export follows C1's Architecture → Subject kinds and the subject set (In-process callers), API Contracts → Export document (version 1) and Audit entries. Omit `publish` for this in-process call. The service must write a started entry before resolution/reads and terminal evidence after assembly, before returning. The route inspects data `complete` and the returned terminal `auditStatus`; only `complete: true` with `auditStatus: 'complete'` permits an attachment response. Bound synchronous work through C1's optional internal export budget: `maxRecordsPerSection: 100`, `maxUtf8Bytes: 1048576` of exact attachment encoding, `deadlineMs: 15000` measured from route entry with monotonic time. Pass the remaining deadline through the optional second `{ budget }` argument to C1 and its owner readers; deliver the exact bounded attachment encoding returned by C1 without reserializing it and honor it during reads, serialization and audit completion; keep a bounded two-second portion of that absolute budget for terminal audit. Use bounded UTF-8 serialization without accumulating an oversized output. Budget exhaustion cancels further reads, records an incomplete attempt with a closed reason, and returns sanitized 503 with no partial file; a failed or timed-out audit must never produce an attachment. A document's `auditStatus: 'started'` is a lifecycle marker, not successful terminal evidence. Missing/failed start, failed terminal evidence, incomplete data or no applicable classes returns a sanitized 503 with no file. The portal adds no duplicate audit lifecycle or separate evidence store; C1 owns export-evidence expiry.

**Profile write, Phase 1.** `GET` and `PUT /api/customer_accounts/portal/profile` retain existing response fields and add `user.updatedAt`. Initialize `customer_users.updated_at` on creation and backfill null versions from `created_at` in the scoped migration. The form sends `buildOptimisticLockHeader(record.updatedAt)` through `withScopedApiRequestHeaders` and shows `surfaceRecordConflict` on 409. The route rejects cross-site requests, runs the registry described below, and dispatches a profile-update command. Under the scoped user row lock the command calls `enforceCommandOptimisticLock`, writes the display name through the managed entity and advances `updated_at`. After commit it emits the dedicated `customer_accounts.user.profile_updated` event with `portalBroadcast: true` and exactly `{ id, recipientUserId, tenantId, organizationId }`. Existing search reindex and ecommerce customer-cache invalidation subscribe to the new event and reuse their scoped id handling. The payload carries only ids. The existing staff `customer_accounts.user.updated` publisher and its fields, including `email` and `updatedBy`, retain their contract. Webhooks, workflows and rules may subscribe to the new event separately. Existing callers omitting the lock header remain accepted; the new form always supplies it.

**Server write guards.** Every new `POST`, `PUT` and `DELETE`, the profile `PUT`, and the password-change route run `runMutationGuards` before mutation. Collect `getAllMutationGuardInstances()` plus `bridgeLegacyGuard(container)` when present, use the closest create/update/delete operation, and pass the authenticated realm's effective grants as `{ userFeatures }`. Return `errorBody` and `errorStatus` on refusal; merge and revalidate `modifiedPayload`. Run every `afterSuccessCallbacks` item after commit, and log and report callback failures without failing a committed response. Export's POST uses an update action for its access/audit side effects. All these handlers call `isCrossSiteBrowserRequest` from `@open-mercato/shared/lib/url` before writes. The UI uses `apiCall`, `useGuardedMutation` and `retryLastMutation` in its injection context.

**Re-authentication** (`lib/reauth.ts`) is shared by export, deletion request, email change and password change. Its columns and migration ship once, in whichever portal spec lands first. Email change replaces step 4's recent-session rule with old-mailbox approval for an account without a password ([`portal-email-change`](2026-11-16-portal-email-change.md), assumption 12).

1. Load the scoped user under a row lock in a short transaction. If `reauth_locked_until > now`, refuse with 429 without extending the lock or incrementing.
2. When a lock expires, atomically reset `reauth_failed_attempts` to 0 and clear `reauth_locked_until` before evaluating this attempt.
3. With a password, verify it while holding that lock. A failure atomically increments the counter; the fifth failure sets a fifteen-minute lock. That failure retains the action's invalid-password response; further attempts get 429. A successful verification resets both fields in the same transaction. Parallel failures cannot lose increments; a success cannot clear a lock set by another committed attempt. Password change refuses while locked only from the minor after its bridge (Migration); during the bridge minor it counts failures as above, but while the lock is set it verifies the password as today, answers 400 or succeeds, and leaves the counter and lock unchanged.
4. Without a password, require a live scoped session row named by the token, created by sign-in in the last fifteen minutes; an empty session id is refused. A successful check resets the re-authentication fields. Login counters are never read or changed by this helper. Operational counter writes do not advance the profile's edit version.

### Deletion request state and cancellation

**Shared company administrator floor.** The account owner supplies a single tenant-and-organization-qualified company operation fence, used by request, claim, cancellation, failure, and every writer that can change the eligible administrator count while a request is pending or claimed. Inventory portal/staff user deletion, activation, company/person relinking (including both CRM subscribers), invitation membership creation, user role replacements, role capability changes, per-user ACL/portal-admin changes and bulk equivalents. Use the same predicate over effective wildcard-aware portal grants inside the owning transaction. Acquire affected company locks in deterministic scope/company order before user or role row locks; re-read membership and permission rows under the fence. Tenant-wide role/ACL edits that can affect multiple companies expand their locked company set before applying and refuse if it changed. No foreign table write is added.

The durable pending/claimed request excludes that user from available administrators, even if the worker releases its transaction before C4 disables or anonymizes the account. Every other writer rejects an operation that would leave remaining active company members without an eligible administrator while that reservation applies. C4's lock/anonymization writer also uses the same company-owner path, rechecking the floor on its account mutation. Users without a company do not impose a company floor. Optimistic-lock and existing RBAC still apply. Publish the translated 409 company-floor response and exact affected routes in the compatibility notes. Roll out the writer fence with C7 deletion disabled and keep it disabled until all replicas run the fence and the ordinary compatibility rollout is complete; removal is forbidden while open requests exist. Integration interleaves claim with portal role replacement, staff deactivation/move and deletion of the remaining administrator. Assert no ordering strands a company and that pending reservations survive a worker stop.

A successful deletion re-authentication returns only internal evidence captured under its scoped user lock before credential verification. The evidence binds the current `emailHash`, `sessionsRevokedAt` and the authenticated live session id. The request never accepts these fields from input. Final acceptance and identity-recovery start both take `withAdvisoryXactLock` on `customer_accounts:deletion_company:<tenant>:<organization>:<company>` when a company exists, then on `customer_accounts:session_cap:<userId>`, then the scoped user row lock. The outer company callback holds only the advisory lock. The inner callback manager owns every acceptance or recovery write. Re-read the user's company under both fences and refuse changed scope or membership before any write. No path taking both fences acquires the company key after the session-cap key. At acceptance, recheck unresolved recovery, the captured credential version, the authenticated live scoped session, the current ACL through `customerRbacService`, the administrator floor and pending state. Recovery returns 409 `identity_recovery_pending`. If the session or credential version changed without an unresolved recovery, require fresh authentication with the existing invalid-session response. Neither refusal stores a request or publishes its email or event. Count only active, undeleted administrators who are neither pending nor claimed. Count all other active company users for the floor. The feature is `portal.users.manage`, including wildcard and portal-admin semantics. Two simultaneous requests cannot both pass using one another as the remaining administrator.

A new request stores `deletion_requested_at = now` and `deletion_effective_at = now + configured grace`, resets attempts, last-attempt date and failure, and leaves `deletion_claimed_at` and `deletion_excluded_related` null. The effective date is immutable for that request. Release of the floor reservation uses the same company-before-user lock ordering and occurs only after cancellation/failure finalization or C4 account disablement and request finalization. The request reference is derived from the user id and stored request time, never from free text.

| State | Stored marks | Request route | User and staff cancel |
|---|---|---|---|
| Idle | No requested, effective, claimed, failed or last-attempt date; attempts 0 | Accept | 404 |
| Pending | Requested and effective date, no claim or failure; no stored exclusions yet | 409 with existing effective date | Lock the scoped row, compare the supplied version, clear request/effective/last-attempt dates, stored exclusions and attempts, return 200 |
| Claimed or partially applied | Requested, effective and claimed date; immutable stored related-subject exclusions | 409 | Lock the same row and return 409 `deletion_in_progress`; never report a successful cancel |
| Failed | Requested, effective and claimed dates null; failed date set; attempts 7, or fewer after an immediate `RESUME_REQUEST_MISMATCH` failure | 409 `deletion_recovery_pending`: an earlier erasure journal may still be open in `failed_handoff`, so a new request could only mismatch it | User: 409 `deletion_recovery_pending`. Staff: dismiss the failure after operator recovery finished or was reviewed, clear the last-attempt date and reset attempts, return 200 and return the account to Idle; this restores no erased data or disabled account |
| Anonymized, no open portal request | `anonymized_at` set; no request/last-attempt marks or attempts | Unavailable to the anonymized account | 404; this state alone does not assert that files, event and history work completed |

**While a failure is undismissed.** The portal never reads erasure journals, so it cannot tell whether a failure left a `failed_handoff` journal open. A Failed account therefore accepts no new request, and the user cannot dismiss the failure; the privacy page shows that the company is completing or reviewing the earlier request and how to contact it. Only staff dismissal returns the account to Idle, and the staff line tells them to finish or review R5-1 operator recovery first. If a request accepted after dismissal still meets an open journal, C4 refuses with `RESUME_REQUEST_MISMATCH`; the worker takes the failure transition at once, without waiting for seven attempts, and its single staff notice names the open journal.

**While identity recovery is unresolved.** [`portal-email-change`](2026-11-16-portal-email-change.md), **Identity recovery locks the account**, refuses export and new deletion requests with 409 `identity_recovery_pending` through the shared `hasUnresolvedIdentityRecovery` check. The fence still applies after the confirmation capability expires or cleanup scrubs it. Recovery start cancels a Pending request in its own transaction as a staff cancellation with reason `identity_review`, emitting the ordinary `deletion_cancelled` event; no cancellation email is sent, because the current address belongs to the identity under review, and the staff recovery notice carries the outcome. A Claimed request is not cancelled; the staff notice says so. Both transitions share the fence above. If recovery wins after re-authentication, acceptance refuses without mutation. If acceptance wins and the request is still Pending, recovery cancels it with the existing event and staff notice. A claim that already committed under the company fence retains the Claimed rule.

Both cancels take the same user row lock used by claiming, including for staff-soft-deleted accounts. Staff must supply a zod reason code (`duplicate_request`, `identity_review` or `controller_review`) and hold `customer_accounts.manage` in the target's tenant and organization. After commit send a cancellation/dismissal email while the account still has a non-placeholder address, even if deactivated. For an anonymized account no address is retained: send staff an explicit follow-up task through the controller's independent verified contact/case channel instead; never try to email a placeholder. For a deliverable cancellation notice, include the reason's translated explanation, company contact and how to complain to the relevant supervisory authority. Emit `deletion_cancelled` with ids, `cancelledByKind: 'self' | 'staff'` and the reason code, with no free-text reason. Self-cancel uses `user_cancelled`. Dismissing a failed request is labelled as dismissal in the UI and email; it does not claim that an incomplete erasure was reversed.

### Daily worker and recovery

The system-scoped schedule scans due `deletion_effective_at <= now` accounts in bounded batches of at most 100, excluding failed requests but including inactive and soft-deleted accounts. It ignores the tenant switch for accepted requests. For each account:

**Scope boundary.** Export keeps the authenticated `{ tenantId, organizationId }` scope. Deletion HTTP routes authorize only the authenticated account, or the staff target in the staff member's tenant and organization, and persist a local request. Under R4-2 only the portal deletion worker may run `eraseSubjects` with `origin: 'portal'` and actor `{ kind: 'system', worker: 'portal-self-service' }`, except for R5-1's operator recovery of a journal in `failed_handoff` below. The subject's own verified request is the authority; this worker needs no staff authorization. It independently reloads that exact accepted account scope and constructs erasure `scope: { tenantId }` for the account's tenant, with no `organizationId`. It supplies exactly the requesting `customer_accounts:user`, never browser-selected ids, and excludes every related subject. C4 limits automatic erasure across organizations to candidates whose owner proves an immutable typed relationship to the exact requesting account. A current or previous address or phone match cannot authorize a change to records, history or copies, even if it appears unique and related roots were excluded. The worker treats `PORTAL_ATTRIBUTION_AMBIGUOUS` as a failed attempt. Staff review the attribution through the verified case channel after failure. If a run already exists, record the normal portal handoff without expanding what it can erase. If the refusal precedes journal creation, the staff notice carries the closed reason and no run id. R5-1 adoption preserves the same account-only scope. Broader related data requires a separate reviewed controller run. A scope mismatch refuses the attempt. Supplying the actor and origin does not authorize another caller: the erasure service itself confirms the worker's request, in pre-flight and again under the subject lock, through the account handler's `customerAccountUserPrivacyHandler.verifyPortalErasureRequest({ scope: { tenantId }, userId, mode, excludedRelated })` (C4 → Authority for a portal-initiated erasure (R4-2)). `dry-run` accepts a pending, due, not-failed request; `apply` additionally needs `deletion_claimed_at` set and the stored `deletion_excluded_related` equal to the sorted `excludedRelated` passed; `handoff` (used by `recordFailedHandoff`) needs a pending, not-failed request. The worker's order below matches those modes: its dry run runs before the claim, and its apply runs only after the claim and exclusions are persisted, passing exactly the stored exclusions. A refusal (`NO_ACCEPTED_REQUEST`, `NOT_DUE`, `REQUEST_FAILED`, `NOT_CLAIMED` or `EXCLUSIONS_MISMATCH`) comes back as a `refused` subject and counts as a failed attempt. The method reads this spec's request columns; until they ship it answers `NO_ACCEPTED_REQUEST`, consistent with `deletionAvailable: false`. The design is complete; until the parent implements R4-2 including required owner-attribution checks and the durable hold-protection latch, and until the shared company writer fence is active throughout the deployment, report `deletionAvailable: false`, refuse new deletion requests with 503 and make no dry-run or apply call; the tenant switch cannot enable it. Never catch `TENANT_WIDE_SCOPE_REQUIRED` and retry after removing `organizationId`.

**Restore replay is a separate caller.** [Erasure restore replay](../enterprise/GDPR/2026-11-16-erasure-restore-replay.md), **Apply**, consumes the internal authenticated `privacySubjectService.replayCapturedErasure({ replayOperationId, evidence, actor })` seam. The signed manifest binds the original authority, origin, exclusions and exact account scope. A portal-origin replay remains limited to the original account under tenant-only scope and does not become a controller erase. An older non-null organization scope remains pending as `scope_unsupported`, with no widened erase call. Absence alone stays pending. Generic controller acknowledgement cannot settle portal evidence. The owning C4/C9 contracts govern clearance under exact signed portal authority. This path is distinct from R5-1 operator adoption of an open portal run.

1. Acquire a per-account worker advisory lock, `customer_accounts:deletion_worker:<tenant>:<organization>:<user>`, using `withAdvisoryXactLock`. Hold it for the whole attempt. The lock transaction never holds a user row lock during the erase call, whose transactions belong to the privacy service. Redelivery waits and re-reads; no second worker applies concurrently. A crash releases the database lock; the next job resumes the persistent claim without a lease timeout.
2. Re-read the scoped state. With no pending request, a future effective date, or `deletion_last_attempt_at` already in this UTC day, stop. A crash before recording an outcome leaves that day uncounted and may resume immediately. A request already at seven attempts, whose handoff did not complete, skips the dry run and apply and retries only step 6's handoff. Otherwise run `eraseSubjects` with `mode: 'dry-run'` using R3-14 and the tenant-only scope above; collect the matching account entry's `relatedSubjects`. Pass its single subject, `excludedRelated` (empty on first discovery, the stored exclusions on retry), `prefer: 'delete'`, `origin: 'portal'`, actor and the stable reference. Dry-run completion is a planning result only, never grounds to close a request. On a first attempt this dry run precedes the claim, which `verifyPortalErasureRequest`'s `dry-run` mode allows; a refusal code here is a refused planning result. No CLI confirmation token is invented for this in-process caller.
3. For an unclaimed request, a refused, incomplete, absent or `not_found` account planning result takes the failure path without claim/apply. A claimed retry keeps its stored exclusions and lets the parent's apply resume pending work; an explicit pre-flight refusal still stops it. Otherwise take the company advisory lock, then the user row lock, and recheck the same request timestamp, due date and administrator floor. Conditionally set `deletion_claimed_at` and persist the sorted/deduplicated dry-run exclusions as `deletion_excluded_related` only while the request still matches, is not failed and has no claim. If a cancel committed during the dry run, do not apply. A sole-administrator deferral counts as an attempt by the atomic request/day rule below; do not send daily deferral notices. On the seventh deferral use the failure transition and its one notification.
4. Immediately before apply, re-read the matching request, claim and stored exclusions under the same user row lock; then release that short transaction. Both cancel routes refuse a committed claim. Call `eraseSubjects` with `mode: 'apply'` and exactly the stored exclusion set, only after the claim and exclusions have committed; `verifyPortalErasureRequest`'s `apply` mode refuses an unclaimed request (`NOT_CLAIMED`) or different exclusions (`EXCLUSIONS_MISMATCH`). On retry keep the original scope, subject, exclusions, preference and origin, as the parent's The run → Serialize and journal requires; a stable reference alone does not establish a matching resume. A newly discovered related subject or `RESUME_REQUEST_MISMATCH` leaves the request incomplete for staff review, never expands or silently rewrites its input. Per R3-1 the service owns both history-strip passes; the worker adds no strip.
5. Find exactly the requested kind/id in `subjects[]` and require its `status: 'complete'`, `filesPending: 0`, and the run's `complete: true`. Interpret its `sections` as `PrivacyErasureSectionResult[]`; there is no section-level pending/status field to invent, and the parent's verified retained/anonymized outcomes may be complete. Then lock the row and clear requested, effective, claimed, failed and last-attempt dates, stored exclusions and attempts. A root `not_found` is not silently treated as portal success; the parent must return a verified standing `complete` result from its durable journal, otherwise staff must investigate. An `anonymized_at` flag or aggregate `runId` alone never closes a request.
6. Count an attempt for planning/guard failures that steps 2–3 stop, administrator deferral, an apply error, or an apply result with `refused` (including each `verifyPortalErasureRequest` refusal code), `incomplete` or `not_found`, a missing account entry, or `complete: false`. The incomplete planning result explicitly allowed to proceed on a claimed retry is not itself a failed attempt: evaluate that retry's subsequent apply outcome. Lock the row and conditionally increment attempts only if the same request timestamp is still present and `deletion_last_attempt_at` is before this UTC day or null; set that timestamp in the same update. An already-counted redelivery does no apply or increment until the next day. Keep the claim while an apply has been attempted, so a partial erasure cannot be cancelled. At seven, follow C4's R5-1 handoff. Before touching the marks, call `privacySubjectService.recordFailedHandoff({ scope: { tenantId }, subject: { kind: 'customer_accounts:user', id }, actor: { kind: 'system', worker: 'portal-self-service' } })`; it moves any open portal-origin journal to `failed_handoff` and returns `{ recorded: true, runId }` for the handed-off run, or `{ recorded: true, runId: null }` when no open portal-origin journal exists. The worker never writes a journal entry itself. Only after it returns `recorded: true`, lock the row, clear requested, effective and claimed dates and stored exclusions, retain the last-attempt date, set `deletion_failed_at`, and notify staff once, naming the returned `runId` when there is one. If it returns `{ recorded: false, code: 'RUN_IN_PROGRESS' }`, or throws for invalid input or an infrastructure failure, keep the marks, claim and exclusions, do not set `deletion_failed_at`, and retry the handoff on the next daily attempt (step 2). If it returns `{ recorded: false }` with `NO_ACCEPTED_REQUEST` or `REQUEST_FAILED`, the request is no longer pending or its failure is already recorded: make no account change, send no notice and do not retry. Email the user only when a non-placeholder delivery address still exists; after owner anonymization no such address is retained, so the staff notice explicitly requires follow-up through the controller's independently held case/contact channel. A `RESUME_REQUEST_MISMATCH` result takes this transition on its first occurrence. The account accepts a new request only after staff dismiss the failure. After this terminal transition, a partial run uses C4's R5-1 recovery below; a failed row is never automatically selected. Staff may dismiss the failed mark without asserting completion or restoring erased data.

**Recovery after bounded failure.** Consume R5-1 through the erasure parent's “Origin-preserving portal recovery”: after the worker's seventh failed attempt, C4's `recordFailedHandoff` moves any open portal-origin journal to `failed_handoff`, and only then does the worker clear the account's request marks as above. Only a journal in `failed_handoff` permits an operator to resume through `mercato privacy erase --tenant <id> --resume-run <runId> [--out <file>] [--apply --confirm <token>]`, or through the enterprise page with `data_erasure.subjects.erase`. This is the sole exception to R4-2's worker-only rule; ordinary portal execution and retries retain the exact worker actor. C4 owns `privacySubjectService.resumeErasureRun({ scope, runId, actor, mode }): Promise<PrivacyErasureRunResult>`, with tenant-wide scope and `mode: 'dry-run' | 'apply'`. Its service owns journal reads and preserves the accepted scope, original single account subject, exclusions, preference, reference, `origin: 'portal'` and exact `runId`; audit entries record the operator as `resumedBy`. No journal outside `failed_handoff`, or a failure that opened no journal, gains the operator-recovery exception. Never reconstruct intent from the cleared account marks, supply replacement subject/identifier/exclusion/preference/reference flags with `--resume-run`, or start a fresh CLI/replay-origin run to replace it. Unknown, expired, malformed, ambiguous or mismatching journal evidence refuses. Recovery recreates no account request and does not reselect a failed row; staff retain the failed-state/dismissal rules and independent case channel. A verified complete result may support failure dismissal, never restoration of cleared data. C4 Phase 3 delivers `verifyPortalErasureRequest`, `recordFailedHandoff` and `resumeErasureRun`, tested there with a worker test double; it is a prerequisite of this spec's Phase 3, and the dependency runs one way only.

The account owner erase clears its re-authentication fields. It preserves request fencing, stored exclusions and retry metadata until the worker's complete-result finalizer clears them; clearing those fields in the owner transaction would lose recovery after a failed emit, pending files or the second history strip. If apply completed but finalization failed, the next job resumes the same request and the parent's durable started/completed entries through `eraseSubjects`, then clears it. Deletion is offered only when `subjectHistoryService`, `actionLogService`, `privacySubjectService`, the required `attachmentService`, exact owner-attribution support for the account and its declaring classes, the required hold protection and the registered schedule are available. The POST repeats those checks; capability loss after acceptance is reported as failure after bounded attempts. The service owns journal reads; the portal never reads audit tables or treats `subjectHistoryService.stripSubject` as a journal-query API.

- **Versions.** New update/delete actions return `updatedAt` and enforce the expected version under the row lock with `enforceCommandOptimisticLock`; the UI supplies `withScopedApiRequestHeaders(buildOptimisticLockHeader(record.updatedAt), …)` and `surfaceRecordConflict`. It serializes first creation too; null means no tenant row yet, and a global fallback record is not a tenant row. No module queries `module_configs` directly.
- **Rate limits.** Export and deletion request get dedicated entries in `lib/rateLimiter.ts`. The row-backed re-authentication counter remains authoritative if the outer limiter fails open.
- **Grace setting.** `OM_PORTAL_ACCOUNT_DELETION_GRACE_DAYS`, integer days, default 14, minimum 1, in both `.env.example` files; changing it affects only new requests. Status uses the stored effective date and reports that request's grace duration while pending.
- **Tenant switch.** Boolean `privacy.selfServiceEnabled` in `module_configs` as declared above, read with DI `moduleConfigService.getRecord('customer_accounts', 'privacy.selfServiceEnabled', { tenantId })`: use a validated boolean only when the returned `source` is `tenant`; an absent tenant row defaults to true even if the service returns an instance fallback. A corrupt value refuses new self-service actions with 503. Writes use `setValue` with the authenticated tenant and null organization. Scoped staff may still manage users in their own organization but cannot change a tenant-wide switch. The switch disables new downloads and deletion requests, never cancellation or the worker.
- **Settings boundary.** R3-3 — Tenant privacy settings live in `module_configs` governs C1's numeric retention settings under `module_id = 'privacy'` and `retention.<area>.<setting>`, read with `privacySettingsService.get(scope, name)`. This account-owned boolean and the grace-period environment variable are separate controls; neither is registered as a numeric retention age or silently moved to that service.
- **Events.** `customer_accounts.user.deletion_requested`, `…deletion_cancelled` and `…deletion_failed` carry ids and enumerated state/reason codes only. Cancellation also carries `cancelledByKind` and `reasonCode`; no email, dates or free-text reason enters the event. The parent erasure event carries the exclusions under R3-14, and no free-text reference.
- **Notification.** One type sent to staff with `customer_accounts.manage` on request and terminal failure, once per transition. Sole-administrator deferral is not notified daily.
- **Email.** Three templates: requested (stored effective date and cancel instructions), failed (company contact), and cancelled by staff (reason, company contact, complaint instructions). Delivery failure is logged and reported with sanitized codes, never an address or capability; the state and staff UI keep the reason code without storing free-text personal data.

When a request is pending the section shows the date and a cancel button; when it failed, it says so, says that the company is completing or reviewing the request, gives its contact, and offers neither a new request nor a dismissal.

State precedence is failed, then pending/claimed processing, then account-anonymized, then idle. `deletionFailedAt` therefore remains visible even if `anonymizedAt` is set, and staff can dismiss the failure without restoring data. With no pending/failed marks show only “account anonymized” with the `anonymizedAt` date and no cancel, never an “erasure complete” badge inferred from those fields. This remains true after dismissing a partial-erasure failure; completion evidence belongs to the parent erasure run/history.
- **Staff Portal Settings:** a translated self-service toggle, with its `updatedAt`, visible to `customer_accounts.manage` callers with unrestricted organization visibility; saves use guarded mutation and surface 409 conflicts.
- States: loading, self-service unavailable (the page says these options are not available here), and errors through the shared flash messages.

## 📝 Edge Cases & Failure Scenarios

| Case | Behaviour |
|---|---|
| No password; old session row or empty session id | 403; ask the user to sign in again |
| Five concurrent wrong re-authentication passwords | All increments count; the fifth locks for fifteen minutes; attempts while locked get 429; login still works |
| Re-authentication succeeds or its lock expires | Reset its counter and lock atomically; login state stays separate |
| Deletion requested twice | 409 with the stored effective date |
| Grace configuration changes | Existing request dates and due selection do not change |
| Staff deactivate or soft-delete the user | The request survives; owner erase includes the row; staff in the same organization may cancel before claim |
| Two company administrators request together | The company lock makes the second see the first's pending mark; at least one is refused |
| User becomes the sole administrator later | Count one daily attempt; after seven distinct UTC-day deferrals fail and notify once |
| Cancel during dry run | If cancel commits first, claim fails and apply is never called |
| Cancel after claim or partial apply | Both routes return 409 `deletion_in_progress`; no successful cancellation notice |
| Seven refused or incomplete attempts | `recordFailedHandoff` moves any open portal-origin journal to `failed_handoff` under R5-1; only after it returns `recorded: true` (with or without a `runId`), clear requested/effective/claimed, keep failure with attempts 7, notify staff once and email only while an address remains; the user gets 409 `deletion_recovery_pending` on re-request or cancel until staff dismiss the failure |
| The seventh failure's handoff call throws or returns `{ recorded: false, code: 'RUN_IN_PROGRESS' }` | Marks, claim and exclusions stay; no `deletion_failed_at`, notice or email; the next daily attempt retries only the handoff |
| The seventh failure's handoff call returns `{ recorded: false }` with `NO_ACCEPTED_REQUEST` or `REQUEST_FAILED` | The request is no longer pending or its failure is already recorded; no account field changes, no notice or email, no retry |
| `verifyPortalErasureRequest` refuses (`NO_ACCEPTED_REQUEST`, `NOT_DUE`, `REQUEST_FAILED`, `NOT_CLAIMED`, `EXCLUSIONS_MISMATCH`) | The subject comes back `refused` before any journal or write; the worker counts a failed attempt |
| Re-request after staff dismissal meets an open `failed_handoff` journal | C4 returns `RESUME_REQUEST_MISMATCH`; the worker fails the request at once and notifies staff once, naming the open journal |
| Staff identity recovery starts (email change) | Pending request cancelled with `identity_review`, no email to the current address; claimed request kept and staff told; export and new requests 409 `identity_recovery_pending` until recovery ends |
| Failure after partial erasure | Claimed worker retries retain R4-2's caller and actor. | Scheduler, erasable account class, audit/history or required attachment service absent | No new deletion request; capability loss after acceptance counts as refusal |
| Privacy or config service absent | No new download or deletion request; status reports unavailable; accepted work does not depend on the switch |
| Mail delivery fails | State transition remains committed; the page shows status; log and report delivery failure; staff must deliver a failed cancellation notice through another channel |
| Linked CRM person | Excluded; `privacy.subject.erased` carries the exclusion and C4's typed audit intent preserves `excludedRelated` for matching recovery |
| Company has a single active user | No other active user can be stranded; the administrator floor does not apply |
| Tenant switch off with a pending request | New requests/downloads return 403; cancellation and worker continue |
| Duplicate worker delivery after an attempt was counted | `deletion_last_attempt_at` fences that request for the UTC day; no second increment/apply; a crash before the outcome update can resume |
| Terminal failure after the owner removed the email | No extra email copy is kept; notify staff, whose case workflow must deliver the outcome through an independently verified channel |
| Worker crashes before or after apply | Database advisory lock releases; persistent claim is resumed with the same reference and durable erasure run; no lease expiry can start a second apply |
| Related subjects change after claim | Keep stored `excludedRelated` unchanged; parent refuses mismatching resume or verification; no automatic inclusion or replacement of the reviewed set |
| Organization-scoped HTTP caller reaches erasure | Refuse; R4-2 permits the portal deletion worker with actor `{ kind: 'system', worker: 'portal-self-service' }` to construct tenant-only input for exactly the requesting account; its own verified request supplies authority without staff authorization. R5-1's operator-recovery exception requires tenant-wide scope and a journal in `failed_handoff`; never widen an HTTP caller's scope |
| Another caller, actor, subject or tenant attempts a portal run | Refuse under R4-2 unless R5-1 authorizes recovery of the same journal in `failed_handoff`; no extra subject, related-subject inclusion or foreign tenant is authorized by either path |

## 📝 Migration & Backward Compatibility

New columns, seven handlers in five new route files, three deletion events, one notification type, three templates, two settings and the Privacy page are additive. Re-authentication schema is shared with the email-change spec and must migrate once. New module files require `yarn generate`; migrations and snapshots ship without applying a local migration. Both `.env.example` copies and the create-app template stay in sync.

R5-1's `failed_handoff` journal state and `resumedBy` audit attribution are C4-owned additions. The portal consumes that handoff through `recordFailedHandoff` and the resume operation through `resumeErasureRun`, both C4 members on `privacySubjectService`; `verifyPortalErasureRequest` is a C4-specified method on the account's privacy handler that reads this spec's request columns. R5-1 adds no portal route or portal-owned recovery DI seam.

Profile GET/PUT response fields are retained and `user.updatedAt` is additive. New forms send the version header; legacy profile callers without it keep working for at least one minor. New staff/deletion forms always version their writes. These behavioural narrowings are not declared additive. The program's DEC-13 — C7 existing-write compatibility and Migration → C7 narrowing (DEC-13), separate from A1/C2, govern them, and the PR argues each one on its own (assumption 10):

- **Registry and cross-site checks** on the profile and password-change writes take the Emergency Security Exception. The argument: an accepted cross-site request is itself the exploit, so a bridge would keep it exploitable for a minor. No unguarded branch and no registry-bypass toggle ships. Process gate: that PR carries the qualifying argument, a dated `BACKWARD_COMPATIBILITY.md` entry, client/operator `UPGRADE_NOTES.md` notes, the `security` label and the named security-maintainer approval.
- **The re-authentication 429** on password change is not argued as the exploit and follows the ordinary protocol. In the minor that routes password change through the shared helper, failures are counted and the fifth sets the lock, but password change keeps its invalid-current-password 400 and still accepts the right password while the lock is set; its `UPGRADE_NOTES.md` entry announces the 429. From the next minor password change returns 429 during the re-authentication lock. The sign-in lockout is unchanged.
- **The identity-recovery 409 on the profile write** is specified and argued by [`portal-email-change`](2026-11-16-portal-email-change.md), Migration: it follows the ordinary protocol with a one-minor bridge, because a display-name write is not a credential.

New handlers enforce guards, cross-site checks and the re-authentication lock immediately. This spec grants no approval.

`UPGRADE_NOTES.md` documents the setting key, default, ACL and UI; the password-change 429, one minor before it is enforced; email change's profile recovery 409 is announced in its own notes; grace changes affect new requests only; the daily-job registration upgrade action; the history dependency; and the dedicated `customer_accounts.user.profile_updated` event with its four ids and unchanged staff event contract. Deletion is unavailable without durable erasure history. Phases 2 and 3 and profile hardening are specified for OSS under DEC-2b, with the named upstream maintainer approval for this carrier required before implementation or an OSS delivery claim. No frozen API, event field, import or feature id is removed.

## 📝 Risks & Impact Review

#### A hijacked session destroys an account
- **Scenario**: Someone with a stolen cookie requests deletion.
- **Severity**: High
- **Affected area**: portal accounts
- **Mitigation**: Re-authentication against the session row, the grace period, the confirmation email to the account's address, the notification to staff, the cross-site check.
- **Residual risk**: A passwordless account whose sign-in is under 15 minutes old. The email, the staff notification and the grace period are the remaining controls.

#### The user believes everything about them is gone
- **Scenario**: The account is deleted and the company still holds orders, tickets and a CRM record; a later sign-up with the same email shows them again.
- **Severity**: High
- **Affected area**: user expectations; the tenant's obligations
- **Mitigation**: The page, the dialog and the email all say what is and is not removed, whom to ask, and what a new sign-up does.
- **Residual risk**: The tenant must still answer a full erasure request by hand until the coverage specs land.

#### The download leaks another person's data
- **Scenario**: A section includes a colleague, an invitee, or a record keyed to the company.
- **Severity**: High
- **Affected area**: the export
- **Mitigation**: One named data class; related subjects not followed; sent invitations left out; TC-PORTAL-PRIVACY-002 asserts a colleague's and an invitee's email, a linked CRM note and the person id are absent from the serialized file.
- **Residual risk**: A later change to the account class itself. Its handler tests are the control.

#### Requests never take effect
- **Scenario**: The worker stops after requests were accepted, or every attempt is refused.
- **Severity**: Medium
- **Affected area**: installations whose background processing breaks
- **Mitigation**: Require the enabled schedule and durable history before acceptance; count refusal, incomplete runs and administrator deferrals; after seven attempts notify staff once and email the user while an address remains; after owner anonymization staff must deliver the outcome through their independent case channel. The seventh failure first calls C4's `recordFailedHandoff`, which moves any open portal-origin journal to `failed_handoff` under R5-1, and keeps the marks for the next day when that call throws or returns `RUN_IN_PROGRESS`; the handoff allows an operator to resume the same intent through the CLI or the enterprise page with `data_erasure.subjects.erase`, audited as `resumedBy`. Failed requests leave the user waiting for staff dismissal, so a re-request cannot collide with an open recovery journal; a request that still does fails at once. Dismissing an anonymized failure records no claim that the erasure finished.
- **Residual risk**: A stopped worker counts no attempts, so the date passes with nothing sent until it runs again. The [`privacy-doctor-cli`](2026-11-16-privacy-doctor-cli.md) check `scheduler.module_absent` warns only when the module is absent; `pruners.unscheduled` is an opt-in database counting check for declared pruners under R3-4 — An opt-in database tier for the doctor, not proof that this deletion job or any scheduler process is running. Monitor this job's execution and overdue requests separately.

#### A completed request never closes
- **Scenario**: The erase run keeps the account row, anonymized, and the worker leaves `deletion_requested_at` set. It then runs a dry run and an apply on every erased account every day, and the staff page shows a pending deletion with a past date and a cancel button.
- **Severity**: Medium
- **Affected area**: the deletion worker, the action log, the staff user page
- **Mitigation**: The worker clears the request only when the erase run reports the subject complete. For an account that already carries `anonymized_at` it still calls the idempotent erase run, so an erasure that stopped after the owner committed is finished and its event emitted before the request closes. The staff line and cancellation apply failed/processing precedence before `anonymizedAt`. Unit tests and TC-PORTAL-PRIVACY-004 check that a second run does nothing; the staff UI never infers full erasure completion from `anonymizedAt` alone.
- **Residual risk**: A failed or disabled worker delays finalization, and capability removal after acceptance can leave partial erasure requiring staff. Claims block cancellation from the start of apply; a terminal failure or failure dismissal does not restore already erased data.

#### Re-authentication becomes a way to guess a password
- **Scenario**: A session thief uses the prompt to try passwords.
- **Severity**: Medium
- **Affected area**: portal accounts
- **Mitigation**: Five tries per fifteen minutes, stored on the row, shared by the two new routes and password change.
- **Residual risk**: 480 guesses a day against one account for as long as the session lives. During the one-minor bridge for the password-change 429, password change still verifies while the lock is set, so it stays the unthrottled oracle it is today until the enforcing minor; the new routes refuse from their first release.

#### A session thief keeps the re-authentication lock saturated
- **Scenario**: Someone holding a stolen session submits a wrong password every fifteen minutes, so the owner's own export, deletion request, email change and password change keep answering 429.
- **Severity**: Low
- **Affected area**: the owner's self-service actions
- **Mitigation**: The counter is separate from sign-in, so the owner can still sign in. The existing password reset (`api/password/reset-confirm.ts`) is not gated by this counter and revokes every session, which evicts the thief; staff can also deactivate the account or end its sessions.
- **Residual risk**: Until the owner resets the password or staff act, self-service actions stay blocked. A passwordless owner must request a magic link and ask staff to end the other sessions.

#### Staff cancel or cross-organization access defeats a request
- **Scenario**: Staff cancel with no explanation, or another organization's staff cancel by id.
- **Severity**: High
- **Affected area**: deletion rights and tenant/organization isolation
- **Mitigation**: Scope the target by both tenant and organization; require `customer_accounts.manage`, a reason, the shared row lock, a version and a cancellation email. TC-PORTAL-PRIVACY-003 covers refusal and notice.
- **Residual risk**: Email can fail or be ignored; staff must follow up through another verified channel. Staff can still cancel on a reason the user disputes; the notice tells the user how to complain to the supervisory authority.

#### An account request becomes general tenant erasure authority
- **Scenario**: A caller supplies `origin: 'portal'` to erase another account, includes a related subject or substitutes another tenant.
- **Severity**: High
- **Affected area**: the erasure entry point and tenant isolation
- **Mitigation**: Consume C4's R4-2 boundary: the portal deletion worker with actor `{ kind: 'system', worker: 'portal-self-service' }` runs for exactly the requesting `customer_accounts:user` in the account's tenant, excluding every related subject. Its verified request supplies authority without staff authorization, and the service confirms that request itself through `verifyPortalErasureRequest`; HTTP routes retain their organization checks. R5-1 is the sole exception: operator recovery requires a journal in `failed_handoff`, preserves its original scope, single subject, exclusions and portal origin, and records `resumedBy`; enterprise recovery requires `data_erasure.subjects.erase`. Unit tests and TC-PORTAL-PRIVACY-004 cover permitted worker/recovery calls and refusal for other journal states, callers, scopes and replacement intent.
- **Residual risk**: Correct accepted-request and handoff-state validation depends on parent enforcement. A wrongly authorized operator or incorrect journal-state check could misuse recovery; audit attribution does not itself authorize a broader erasure.

#### Cancel reports success while erasure proceeds
- **Scenario**: A worker selected an account before cancel, or a queue redelivers while the first worker applies.
- **Severity**: Medium
- **Affected area**: worker and cancellation routes
- **Mitigation**: Per-account worker advisory lock, conditional durable claim, final row-lock re-read, and both cancels refusing a claim. Company locks serialize acceptance; deferrals are bounded.
- **Residual risk**: Cancellation is unavailable after a committed claim, including an interrupted run; the UI states processing and staff must resolve terminal partial failures and deliver the outcome through another verified channel when the email has already been erased.
