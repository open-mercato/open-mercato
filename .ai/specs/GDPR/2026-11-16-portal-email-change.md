## 📝 TLDR

A customer-portal user's email address is their sign-in name, and nobody can change it. The user's own profile route accepts only a display name. The staff route for portal users has no email field either. A person whose address changed — or who asks for it to be corrected, which is their right — has to be given a new account. **Proposed (future):** a signed-in portal user can ask to change their address. A link is sent to the new address and a notice to the old one; the change takes effect only when the link is used, and then every session is ended. An account without a password must first approve the request from its current mailbox. Staff can start the same flow for a user; they cannot set an address directly. After a confirmed takeover, staff can start a verified recovery which the current mailbox cannot cancel, and while it is live the account cannot sign in, receive sign-in links or change its credentials. Email change is OSS, in `customer_accounts`, with C7's download and deletion (assumption 7, program DEC-2b). Its narrowed existing password-change, reset-confirm and profile writes follow DEC-13 one narrowing at a time: the registry/cross-site checks and credential fences, including the recovery refusals on credential paths, take its Emergency Security Exception, with the named security-maintainer approval, while the re-authentication 429 and the profile write's recovery 409 follow the ordinary protocol with a one-minor bridge.

**Not in this spec:** changing a staff user's address, which already works and takes effect at once; changing the address the tenant holds on the CRM person, which is the tenant's record; merging two portal accounts.

## 📝 Overview

> **Market reference.** GitLab, GitHub and Discourse all treat a new address as unconfirmed until a link sent to it is used, keep signing in with the old one until then, and tell the old address that a change was requested. Adopted: all three. Rejected: an immediate change, which is what the staff profile does here — for a sign-in name it lets a hijacked session take the account away from its owner.

## 📝 Problem Statement

- **The address is the identity** for sign-in, magic links, password reset and invitation acceptance (`customer_accounts/api/login.ts`; `api/magic-link/request.ts`; `api/password/reset-request.ts`).
- **It is stored encrypted with a lookup hash**, unique per tenant among users not deleted (`customer_accounts/data/entities.ts`; `encryption.ts`). Uniqueness is per tenant, not per organization.
- **Nobody can change it.** The portal profile schema has only a display name (`data/validators.ts`); `adminUpdateUserSchema` has no email either.
- **The verification table cannot hold a target address.** It has a user, a token hash, a free-text purpose, an expiry and a used time (`entities.ts`).
- **No "pending address" exists anywhere** in the codebase.
- **Sessions.** A token lasts eight hours and carries the address; refresh re-signs it from the database. `revokeAllUserSessions` ends every session and invalidates older tokens (`services/customerSessionService.ts`).
- **The CRM link is made once**, when the user is created, and is skipped when a link already exists (`subscribers/autoLinkCrm.ts`).
- **Copies of the address** include invitation rows, JWT claims, some event payloads and the signup staff notification. `search.ts` marks email `hashOnly`, while display name is searchable and used in the result title. `subscribers/search-reindex-updated.ts` reindexes by id on `customer_accounts.user.updated`; it does not need an email in the event.
- **The existing verify route has no rate limit** (`api/email/verify.ts`), and the staff update writes with a raw update and no audit entry (`api/admin/users/[id].ts`). A raw update also bypasses encryption; the address must be written through the entity.
- **Lookups by hash try several forms** — keyed and legacy (`packages/shared/src/lib/encryption/aes.ts`) — while the unique index compares stored strings, so an account stored under the legacy form and a change under the new one would not collide in the index.
- **Tokens in flight are keyed by the user.** Magic links live 15 minutes and password resets 60 (`services/customerTokenService.ts`). `api/magic-link/verify.ts` consumes its token before `createSession`, whose only current lock is the session cap lock; a pre-change credential can otherwise create a post-change session.
- **Token cleanup is not scheduled.** `setup.ts` registers domain-verification and TLS-retry queues, not `customer-accounts-cleanup-tokens`. This spec must schedule bounded cleanup for its own table, including upgraded installations, without waiting for the pruner spec.
- **The outer rate limiter fails open and uses IP and hashed identifier keys** (`auth/lib/rateLimitCheck.ts`).
- **The search index is rebuilt on `customer_accounts.user.updated`**, and the reverse CRM link runs only when a person is created (`subscribers/autoLinkCrmReverse.ts`).

## 📝 Proposed Solution

| Step | What happens |
|---|---|
| Request | The signed-in user gives a new address and re-authenticates with the current password. A pending change is stored, replacing any earlier one |
| Messages | A link goes to the new address. A notice goes to the old one, saying a change was requested, with a link that cancels it without signing in |
| Without a password | The pending change is stored awaiting approval. The old-address notice carries an approval link as well as the cancel link; only approval sends the link to the new address |
| Until confirmed | Nothing changes. The user signs in with the old address and can cancel from the profile page or from the notice |
| Confirm | In one transaction take the shared tenant hold fence before the per-user and tenant/address locks; lock and consume only a live pending row, check all target hash forms, replace and verify the address through the managed entity, capture old/new identifiers through the privacy owner on the same manager, revoke sessions and unused user tokens, and cancel pending old-address invitations. Any failure rolls back every change, including the hold append. After commit tell the old address and staff with `customer_accounts.manage`, including how to obtain staff recovery |
| Staff | In the user's tenant and organization, `customer_accounts.manage` may start/cancel normal changes. Verified recovery uses the same start route with `mode: 'recovery'`; only staff can replace/cancel it and the recovered mailbox must confirm |

**When the new address is taken.** The request behaves identically in everything the requester can see: a pending change is stored, the old address gets the notice, the status shows it pending, cancelling works. The link is not sent — the pending change can never be confirmed and expires — and the owner of the existing account receives a notice, with its own wording, that someone tried to use their address.

**Limits.** At most three requests per user per hour, counted from the pending-change rows themselves, which are kept until the clean-up removes them. Staff-started changes are limited per staff user and per target, as invitations are. All three public POST routes (confirm, approve, cancel) use the existing limiter; tokens come from `generateSecureToken` (32 random bytes) and only `hashToken` digests are stored. Count requests under the user lock so concurrent replacements cannot exceed three per hour; finished rows remain for at least the counting window. After a successful public cancel of a self-requested change, new self-requests for that user return 429 for 24 hours, counted from that cancelled row's `cancelled_at` and `cancelled_via = 'public'`; staff-started changes are not blocked.

### Design decisions

| Decision | Rationale |
|---|---|
| A table for pending changes | The verification table has no place for the target address, and widening it would change a table three other flows share. |
| The new address is stored encrypted, with no hash of its own | Nothing looks a pending change up by address; the check at confirmation computes every hash form from the decrypted address. |
| Uniqueness is checked twice, at request and at confirmation, under a lock | Someone else may take the address in between, and the unique index alone does not see an account stored under an older hash form. |
| Request, cancel and the confirmed change are commands that cannot be undone, with audit entries that name no address | The staff route's lack of any audit entry is a defect not to be copied; an undo would restore an old sign-in name. |
| The confirmed change emits a dedicated `customer_accounts.user.email_changed` event with ids only | The reindex and cache consumers need only ids, and the portal broadcast can target the affected account |
| The confirm route is public and rate-limited | The person using the link may not be signed in on that device. |

### Alternatives considered

| Alternative | Why rejected |
|---|---|
| Change immediately, as the staff profile does | See the market reference. |
| Let staff set the address | See assumption 4. |
| Reuse the verification table with a new purpose | No column for the target address. |
| Update the CRM person's email as well | See assumption 5. |
| A several-day signed revert link, with the old address stored encrypted | It adds a prior-address archive and a public revert route; staff recovery reuses the verified flow (assumption 10). |
| A portal-owned history of old email hashes, for general prior-address coverage | It retains replaced identifiers outside an active hold. Use the shared atomic hold-capture contract for held identifiers and explicit DEC-A handling for other historical records (assumption 11). |

### Atomic changes, recovery and identity boundaries

**One winner.** Request, both authenticated cancels, public token cancel, public approval, public credential issuance and confirmation share the existing per-user advisory key `customer_accounts:session_cap:<userId>`. Confirmation opens one READ COMMITTED write transaction and first calls `privacyHoldProtectionService.withPrivacyHoldFence({ tenantId }, callback, { em })` with that active manager. Inside it, acquire the session-cap key and then the tenant invitation admission row and both sorted old/new `customer_accounts:email_target:<tenantId>:<hashForLookup(normalizedEmail)>` keys, followed by user, pending-change and invitation rows. The address keys carry current-form lookup hashes. Use bounded transaction-scoped acquisition on that exact manager for these locks; the current `withAdvisoryXactLock` forks an independently committing transaction and MUST NOT be nested under the tenant fence. Deliver an additive transaction-aware acquisition helper, or reuse a verified same-manager primitive, without changing the existing helper's behavior. No confirmation mutation, delegated credential/invitation write or capture may fork, independently commit or reacquire the tenant fence. The transaction owner commits or rolls back all of them together and retains every transaction lock until then. Account for one write connection and bounded waits; never hold a user lock and then wait for the tenant fence. Derive old/new lock candidates from the owner’s state under the session-cap lock, then after locking the user/pending rows verify their current hash-form epochs and addresses still correspond to those keys. An unexpected identity/epoch change restarts admission without writing.

This ordering follows D3's tenant-before-owner rule. C4 erasure-owned callers already hold their subject lease before entering the tenant fence and pass their active manager/context to owner writes; no email-change callback acquires or reacquires a subject lease beneath the tenant or user lock. Standalone email confirmation needs no C4 subject lease. Other requests and cancellations that do not mutate an identifier may retain their user-lock callback transaction and must never call confirmation from inside it. Recovery start's outer company transaction holds only its advisory lock while the session-cap callback manager owns all its writes. Session creation uses the existing session-cap lock and does its credential reload and insert on that callback's exact manager.

Read the row by tenant and its user's organization; public routes resolve the hashed capability to that scope rather than accepting a browser-supplied tenant. Confirmation and normal cancellation require `used_at IS NULL`, `cancelled_at IS NULL` and `expires_at > now`. An explicit staff recovery settlement may address an unresolved row after token expiry and follows the additional evidence and credential checks below. A portal/staff cancel losing to confirmation returns 409; public replay, expired or superseded tokens return generic 400. If cancel wins, confirm returns 400 and makes no address write. Replacement serializes under the user lock. Close expired normal rows before the partial unique index is checked. An unresolved recovery row occupies that slot even after token expiry. Verified staff replacement closes the predecessor and inserts its successor in one transaction.

**Approval without a password.** A self-request from an account whose `password_hash` is null stores the row with an `approval_token_hash` and no `token_hash`, and sends only the requested notice, carrying approval and cancel links, to the current address. `POST /api/customer_accounts/email/change-approve` resolves the hashed approval capability to its row scope, conditionally sets `approved_at` on a live, unapproved row under the same per-user lock, generates the confirmation token, stores its `hashToken` digest in `token_hash`, and after commit sends the confirmation link — or, for a taken address, the attempted-use notice to its owner. Approval keeps the row's original `expires_at`. Confirmation requires `token_hash` and, when `approval_token_hash` is set, `approved_at`. Replay, cancelled, superseded or expired approval tokens return generic 400. Staff-started and recovery rows need no approval: staff verify identity themselves.

**Public cancel ends the requester's access.** In the transaction that cancels a self-requested normal row through the public token, also set `cancelled_via = 'public'`, call `revokeAllUserSessions` and consume the user's unused verification, magic-link and reset tokens on the same callback manager. After commit notify staff with `customer_accounts.manage` in the user's organization. The result page tells the owner to set a new password through the existing reset flow, or to request a fresh magic link for a passwordless account. A cancel of a staff-started normal row only cancels it.

**Identity recovery locks the account.** `lib/identityRecovery.ts` exposes one account-owned check, `hasUnresolvedIdentityRecovery(em, { tenantId, organizationId, userId })`: a scoped row with `mode = 'recovery'` and null `used_at` and `cancelled_at`. This durable fence ignores `expires_at`, which limits public confirmation capability only. While the fence is active, each path below refuses for that user without a new mutation, token or message:

| Path | Behaviour while recovery is unresolved |
|---|---|
| `POST /api/customer_accounts/login` | The existing generic 401 invalid-credentials response, after the same timing-equalization compare |
| `POST …/magic-link/request`, `POST …/password/reset-request` | The existing `{ ok: true }`. No token is created and no email or requested event is emitted. See **In-flight public issuance** for the owning transaction. |
| `POST …/magic-link/verify`, `POST …/password/reset-confirm` | The existing generic 400; checked before the token is consumed and again under the user lock |
| Existing staff `POST …/admin/users/:id/reset-password` and `POST …/admin/users/:id/send-reset-link` | Scoped and feature-gated as today; stale credential state or unresolved recovery returns 409; no password, capability, response link or event is produced |
| `createSession` | Rechecked inside the session-cap lock callback with the credential version; refusal inserts no session, so an in-flight sign-in cannot slip past |
| `POST …/portal/password-change`, `PUT …/portal/profile`, email-change POST/DELETE | 409 `identity_recovery_pending`; on the existing profile PUT only from the minor after the ordinary one-minor bridge (Migration) |
| Self-service `POST …/portal/privacy/export` and `POST …/portal/privacy/deletion-request` | 409 `identity_recovery_pending` |

Sessions are already revoked at recovery start, so the authenticated rows apply only to a session that raced the start; the session-cap check closes that race. Public confirmation still requires a live capability. Authorized staff can act on an unresolved row after expiry. Recovery start acquires the company fence before the session-cap fence, in the order and scope specified in [portal self-service](2026-11-16-portal-privacy-self-service.md#deletion-request-state-and-cancellation). It cancels an unclaimed pending deletion request in the same scoped transaction as session and token revocation with `cancelledByKind: 'staff'` and reason `identity_review`, with no email to the current address; a claimed request cannot be cancelled and the staff recovery notice says so. Verified recovery confirmation or the explicit audited staff settlement below releases the fence. Expiry, delivery failure, cleanup and staff replacement keep the fence active.

**Invitations.** Confirmation computes `lookupHashCandidates(oldEmail)` in memory and cancels every still-pending invitation in the tenant matching any candidate, including another organization because account uniqueness is tenant-wide. The account module owns both tables. These cancellations are in the same transaction as consuming the change and writing the new address. Never reassign an invitation's roles to the changed account. Old accepted, cancelled and expired invitations remain subject to the cleanup/privacy coverage limit below.

**Invitation admission and acceptance.** The account owner keeps one `customer_invitation_admission_epochs` row per tenant with a nonnegative `generation`. It carries no mailbox or invite history. Confirmation increments it in the same transaction as releasing an address. New issuance and resend capture the generation before resolving the target/links. Before writing, on one owner transaction acquire the applicable existing-user session-cap lock (when an account is already resolved), take a shared lock on the admission row, acquire the normalized address key using the same namespace and verified current hash epoch, and reload the generation and scoped state. Initialize the unique tenant row transactionally when absent. Resolve all legacy/current hash variants inside the locks. Reject a stale generation with a retryable staff conflict and require a fresh review of the explicit target and links. Do not mint or send from the stale admission. An unrelated address release can force this bounded retry. The confirmation path takes the admission row exclusively, then sorted address keys and affected rows. Any invite row locks follow the address keys in stable id order. An initial read identifies lock candidates only. If the protected read discovers a different existing account, release and retry with the correct user key rather than acquiring it in reverse order. Current-hash epoch changes refuse/restart admission safely.

Acceptance uses the company-floor fence first when its membership mutation requires one, followed by the same account, admission and address locking order, rechecks the token and live invitation row after any wait, and commits token consumption, account creation or claim, roles and explicit links on the same owner transaction. Reuse the scoped person occupancy lock for a person link and preserve the original linked account and its inferred company when another account occupies that person. Validate explicit person/company consistency through the customers-owned resolver; an occupied person cannot authorize transferring its associated company. Standalone company grants remain available to authorized staff through a fresh post-change invitation that explicitly identifies that company under the ordinary scoped grant rules. Acceptance uses only the links admitted on the live invitation. Send invitation mail after commit. When confirmation wins, a previously admitted issue/resend fails its generation check and an existing old-address token fails its live-row check. When issue/resend wins, confirmation cancels the newly written pending row. Acceptance that commits before confirmation is evaluated against then-current occupation, and no accepted access to a person/company is transferred by release itself. Invitation acceptance never mints a session until the fenced account and explicit grant transaction commits and the credential-version recheck succeeds. Roll out issuance, resend and acceptance on all first-party writers before enabling email release; a mixed fleet must not claim the release guarantee.

**In-flight credentials.** Add an optional trailing `credentialVersion` argument to `customerSessionService.createSession`. It holds the stored `emailHash` and `sessionsRevokedAt` observed before password verification or magic-link consumption; invitation acceptance returns the newly created user's initial values before another flow can change them. The routes capture the stamp themselves; `customerTokenService` and its result types do not change. New account-owned `lib/credentialVersion.ts` exports `readTokenCredentialVersion(em, { kind: 'email_verification' | 'password_reset', token, purpose? })`: a non-consuming read of the module's own `customer_user_email_verifications` or `customer_user_password_resets` row by `hashToken(token)`, populated with its user, returning `{ userId, tenantId, credentialVersion }` for a live row or null. The magic-link route calls it before `verifyEmailToken`, then requires the service's returned `userId` and `tenantId` to equal the captured ones; a stamp loaded after consumption is never used. No stamp is sent in an HTTP body or event. Under the same user fence, each identity boundary that revokes all sessions must advance the persisted `sessionsRevokedAt` to a strictly later representable value, including two revocations in the same clock tick. The session owner computes it from the current locked row and the database clock. This prevents a stale request from matching again after same-address recovery settlement. The three first-party session callers (`api/login.ts`, `api/magic-link/verify.ts`, `api/invitations/accept.ts`) pass it. Inside the single existing session-cap lock callback transaction, before insertion, reload the scoped active user with `findOneWithDecryption`, and compare both values. A mismatch refuses sign-in with the flow's generic invalid-credential response and inserts no session. If session creation wins first, confirmation subsequently revokes that session; if confirmation wins first, the old credential is refused. Refresh continues to require a live session. Capture before the credential check/consume, not after it. A DI override of `customerTokenService` that extends the class or delegates token storage to the module's tables keeps working unchanged, because the stamp comes from the route's own read. An override that stores tokens elsewhere leaves no row for that read, so the first-party magic-link and reset-confirm routes return their generic invalid-token response rather than disabling the fence; this narrowing and the transaction-bound issuance capability are argued separately under DEC-13 (Migration below). Existing downstream callers of `createSession` may omit the new argument for one minor as a documented bridge; they keep the old contract and do not gain the credential-race guarantee until migrated.

**In-flight public issuance.** Magic-link and password-reset request keep their enumeration-safe `{ ok: true }` contract and existing rate limits. Resolve the tenant from the trusted request context. At the initial lookup capture the scoped account id, normalized requested mailbox and credential version (`emailHash` and `sessionsRevokedAt`) before any mint. Under the existing per-user session-cap lock, reload the active account in the same tenant and organization with decryption on the exact callback manager. Require its current mailbox to equal the normalized request, the credential version to match, and no unresolved recovery. A mismatch, absent account, unresolved recovery or unavailable bound issuer returns the generic success response without minting, sending or emitting a requested event. Only the token owner may issue a capability, using that callback manager. After commit, send to the mailbox read inside the fence and emit the existing event. If issuance commits first, a subsequent email change or recovery revokes that token in its own fenced transaction, so a late email carries no usable capability. If confirmation, recovery start or settlement wins first, the stale request cannot mint. Test both orders for both routes, ordinary address changes, recovery start and a pause that spans recovery settlement without an address change. Never log the address, version or token.

**Transaction-bound token owner.** Add an optional trailing transaction option to `createMagicLink` and `createPasswordReset`; preserve existing unbound signatures and behavior. The first-party public issuers and staff reset-link issuer use their scope-checked transaction-bound implementations. An override inheriting the built-in method keeps that path. An override replacing it must explicitly advertise transaction-bound support for that method, must write the normal owner token row using the supplied manager, and must return only the capability issued by that write. Reject unsupported overrides before calling the issuer. Verify the issued capability against its owner row on the same manager before returning a committed send result. There is no fallback to an unbound mint. For the public routes an override refusal stays generic. Maintainer approval and upgrade notes for this narrowing are separate from the ordinary signature bridge.

**In-flight password writes.** The reset route first resolves the live token without consuming it through `readTokenCredentialVersion` with `kind: 'password_reset'`, derives the user scope and captures the credential version, and runs the server guard registry/cross-site check and the identity-recovery check before any token or password mutation. It then calls the unchanged `verifyPasswordResetToken`, requires the returned user and tenant to match the captured ones, and so revalidates and conditionally consumes the token; guard-modified inputs are revalidated and cannot change the server-derived target scope. A pre-recovery password-reset or self password-change must not install a password after recovery. `api/password/reset-confirm.ts` carries the captured version into the password-write transaction; `api/portal/password-change.ts` captures a version before checking the current password. Both acquire the same existing session-cap/user advisory lock once, reload the scoped user with decryption on its callback manager, compare email/revocation versions, and only then call `updatePassword` and revoke sessions on that exact manager. A mismatch returns the existing generic invalid-credential/token result without a password write. If the old password write commits first, recovery subsequently clears it and revokes its sessions/tokens; if recovery commits first, the old write is refused. A token the route's own read cannot find fails closed on reset-confirm, as above. Both existing staff credential routes are included. Resolve the same scoped target and feature, capture its account credential version and, before any password/token mutation, take the existing user advisory lock once and re-read the scoped user on the callback's exact manager. Refuse stale versions or unresolved recovery with 409 `identity_recovery_pending` or `credential_version_changed`; no staff override. Staff reset uses `updatePassword` and revokes sessions in that transaction. Staff reset-link uses the transaction-bound token contract above on the same callback manager. A staff override without that capability returns the existing scoped conflict without minting. Publish the existing success response and event only after commit; after a recovery start wins, no earlier route can recreate credentials or mint a live link. If staff wins first, recovery invalidates its password on settlement and its reset link on start. Test both orders for both routes, including exact tenant/organization scope, no leaked token or event, and unavailable override capability. This extends the fence to credential writes, not only session insertion.

**Post-confirmation recovery.** The notice to the old address directs the owner to the company. After checking identity through an independent channel, staff POST the existing start route with `{ newEmail: recoveredAddress, mode: 'recovery', identityVerified: true }`. The address comes from the independent check. The command supersedes normal changes, revokes sessions and unused user tokens, and applies the deletion-request rule above. Portal POST/DELETE and public cancel cannot replace or settle unresolved recovery. Return 409 to authenticated callers and generic 400 to the public route. The recovery notice carries no cancel capability. Confirmation still requires a live recovered-mailbox link and its uniqueness and revocation checks. Under the same user lock, staff may reverify identity and reissue through the existing staff POST, using the current user version and atomically replacing the unresolved row with a new one.

Only same-organization staff with `customer_accounts.manage` can use staff DELETE to settle recovery without confirmation. Require the current pending-row and user versions, a closed audited reason `identity_verified`, and an independent identity and exclusive-control check for the exact current sign-in mailbox on the `customer_users` row. The pending recovery row's `new_email` is only a proposed destination. Proof of control of that address alone cannot settle recovery while a different address remains the sign-in mailbox. Staff attest the independently checked mailbox as `verifiedSignInEmail` with `identityVerified: true`, using the user and pending-row versions captured for that verification. Staff must repeat the check after a version conflict. Reload the exact scoped user and recovery row with decryption on the manager holding the same credential/user lock. Require unresolved recovery, matching versions and equality between the transient normalized `verifiedSignInEmail` and the locked user's current normalized sign-in mailbox. Do not substitute the pending target, an earlier account address, a request-origin session or an unbound acknowledgement. Reject a missing/invalid attestation with 400 and an address/version/state mismatch with 409. In either case, keep the recovery fence and credentials unchanged. If exclusive control of the current sign-in mailbox cannot be confirmed, leave the fence active, reissue to the independently verified recovery mailbox and require the owner to confirm its address-changing link. The address attestation is a sensitive input checked only in memory. It never enters command or audit history, undo snapshots, events, logs or telemetry.

Both confirmation and authorized settlement clear the existing password, failed-login count, lockout and re-auth lock/counter, consume any unused user tokens and revoke all sessions in the same transaction as settling the row. Only mailbox confirmation changes the address. Mailbox confirmation and audited staff settlement require fresh magic-link sign-in or a new password via the reset flow. No pre-recovery password can authenticate afterwards. Audit records contain the closed reason and ids with no address, credential or free-text evidence.

**CRM linking.** For CRM matching/ownership reads, both touched subscribers consume the customers-owned DI seam `customerPortalLinkResolver`, resolved softly. [`privacy-data-class-contract`](2026-11-16-privacy-data-class-contract.md), Architecture → Customers-owned portal-link resolver, defines `CustomerPortalLinkInput`, `CustomerPortalLinkResult` and `resolveLinks(input: CustomerPortalLinkInput): Promise<CustomerPortalLinkResult | null>`, with `customers/di.ts` registration and Phase 3 delivery. Its `customers/lib/__tests__/portalLinkResolver.test.ts`, CLASSIC DI case and `TC-CUSTOMER-PORTAL-LINK-001` are release prerequisites. Use its strict zod union: forward calls supply the loaded account's `scope: { tenantId, organizationId }`, `email`, nullable `personEntityId` and nullable `customerEntityId`, with no `createdPersonOrProfileId`; reverse calls supply event `scope: PrivacyScope`, `createdPersonOrProfileId` and optional `email`, with neither link-input member. Scope/link/event ids are UUIDs; a supplied email must be valid and normalized; mixed alternatives and extra keys are rejected. The common result contains `organizationId`, nullable `personEntityId` and nullable `customerEntityId`, never an email. Null means no eligible match; invalid input or unavailable reads throw and never count as a match. When the resolver is absent it leaves the account unlinked and refers to staff, with no CRM-table fallback.

Preserve C1's exact owning-organization and tenant predicates on every undeleted candidate and recovered company; privacy export's organization-plus-null rule does not apply to linking. A reverse event without an organization first resolves its scoped person/profile id to the owning organization. `autoLinkCrmReverse.ts` resolves the event's link ids without an email, then reads its own unlinked account candidates in bounded keyset batches and supplies each candidate's email and the same `createdPersonOrProfileId` back to `resolveLinks` to verify the match, preserving the first eligible account behavior. No CRM address is returned, and no account link crosses the resolved organization. No touched subscriber directly imports or queries customers entities. After finding a candidate through that seam, `autoLinkCrm.ts` takes `customer_accounts:crm_person:<tenant>:<organization>:<person>` with `withAdvisoryXactLock` and queries only its own `CustomerUser` rows for another active, undeleted account linked to that person in that scope. If found, it leaves the new user's person and company ids unset and notifies staff for manual review; no company is inferred from the blocked candidate. Apply the same check and lock in `autoLinkCrmReverse.ts`. A concurrent pair of subscribers cannot both attach. Only the customers-owned resolver reads CRM tables, through decryption helpers. Occupancy queries and link writes stay in `customer_accounts`; there is no cross-module ORM relationship. A previously linked changed account retains its link, so signup with the released address cannot adopt that person's company.

**Atomic hold capture and historical coverage.** Both normal and recovery confirmation consume D3's [Identifier mutation capture](2026-11-16-privacy-record-retention.md#legal-holds) and the [DSR engine's hold contract](../enterprise/GDPR/2026-11-16-privacy-dsr-engine.md#how-a-hold-matches). Under the tenant fence, resolve the durable protection latch and reload the scoped user and live pending row. When capture is required, derive bounded `previousIdentifierIds` and `nextIdentifierIds` from the owner's locked before/after account state in the currently verified lookup epoch, using C1's identifier derivation; never accept ids, tenant or organization assertions from the capability request. For the subject `{ kind: 'customer_accounts:user', id: user.id }` and its loaded `scope`, call `privacyHoldProtectionService.captureIdentifierMutation({ scope, subject, previousIdentifierIds, nextIdentifierIds }, { em })` before commit, using the exact active manager of the address change. The shared privacy owner validates the fence/manager and delegates to the hold owner; `customer_accounts` never reads or writes Enterprise hold tables. The hold owner appends introduced identifiers to matching active/pending holds and advances the alias generation in the same transaction, retaining earlier held ids when the address changes again.

A failed capture, stale or unverifiable lookup epoch, unavailable required capture owner, unknown protection state or failed fence acquisition refuses confirmation. Roll back the new email and lookup hash, verification and credential versions, pending-row consumption/recovery settlement, password/session/token changes, old-address invitation cancellation, and all hold appends/generation changes together. Do not publish a changed email, notification or event after rollback; the existing pending link remains retryable within its original lifetime. The clear, positively verified never-protected OSS posture permits the shared owner to no-op, including when no identifier key is configured (pass empty identifier sets only in that positively verified posture); it does not require Enterprise or add an OSS hold store. Owner-derived identifier ids are required whenever protection requires capture. An absent/disabled Enterprise module is never itself evidence that the durable latch is clear.

Alias resolution for ordinary export/erase still uses the current email only. Records keyed by addresses replaced before a hold captured them can remain outside an account-only export/erase; cancelling pending invitations closes the credential path, not that historical coverage gap. Staff must include those previous identifiers explicitly through DEC-A (`privacy:identifier`) and the relevant module-owned classes, with the linked CRM record reviewed separately. Guard-time refresh remains a defense in the DSR engine; it is not a substitute for this atomic capture. The fence serializes confirmation with first-hold admission and destructive guard/write batches, and an address introduced then replaced between guard reads remains in a matching hold. Staff notifications/UI ask the controller to review historical identifiers and hold scope, without implying that a later manual extension is needed to capture this confirmed change. No portal-owned hold subscriber or historical alias archive is added.

## 📝 Delta

### Capability: portal-email-change

#### ADDED Requirement: Change own email address
The system SHALL let a signed-in portal user replace their email address after re-authentication, and SHALL apply the change only when a link sent to the new address is used.

##### Scenario: Request
- WHEN a user requests a change
- THEN a link is sent to the new address, a notice to the old one, and signing in still uses the old address

##### Scenario: Confirm
- WHEN the link is used within its lifetime
- THEN signing in works with the new address and not the old, every earlier session is ended, and required hold capture commits atomically; any capture or fence failure leaves the address, credentials, invitations, pending row and holds unchanged

##### Scenario: Cancel
- WHEN the user cancels before confirming
- THEN the link no longer works

##### Scenario: Address already in use
- WHEN the new address belongs to another account in the tenant
- THEN the response, the notice to the old address, the pending status and cancelling are the same as for a free address, and no link is sent

##### Scenario: Old links
- WHEN a magic link or a password-reset link was sent to the old address before the change was confirmed
- THEN it no longer works afterwards

##### Scenario: Cancel from the notice
- WHEN the owner uses the cancel link in the notice without signing in
- THEN the pending change is cancelled

##### Scenario: Taken in the meantime
- WHEN another account takes the address after the request and before the link is used
- THEN confirming fails and the user's address is unchanged

##### Scenario: Confirm and cancel race
- WHEN a confirm and cancel target the same live pending row together
- THEN exactly one commits; a successful cancel prevents the address change

##### Scenario: Old-address invitation
- WHEN a pending invitation matches any hash form of the released old address in the tenant
- THEN confirmation cancels it in the same transaction and it cannot be accepted

##### Scenario: Invitation issuance crosses address release
- WHEN staff issue or resend a linked invitation and the old-address release commits after the invitation generation was observed but before issuance commits
- THEN the stale admission mints no token and copies no links; when issuance commits first, confirmation cancels the resulting invitation across organizations and hash forms. A fresh, authorized explicit company grant after release still works without adopting an occupied CRM person.

##### Scenario: Sign-in already in flight
- WHEN a first-party sign-in checked credentials before confirmation but inserts its session afterwards
- THEN the credential-version recheck refuses it, or confirmation revokes the session that committed first

##### Scenario: Wrong password
- WHEN re-authentication fails
- THEN no change is stored and no message is sent

##### Scenario: Account without a password
- WHEN a user with no password requests a change from a live session
- THEN only the old address is notified, with approval and cancel links; no link reaches the new address until the old mailbox approves

##### Scenario: Owner cancels from the notice
- WHEN the owner cancels a self-requested change through the notice
- THEN every session of the account ends, unused sign-in and reset tokens stop working, staff are told, and a new self-request is refused for 24 hours

#### ADDED Requirement: Staff-started change
The system SHALL let authorized staff start an address change for a portal user, which takes effect only when the link sent to the new address is used.

##### Scenario: Staff start
- WHEN staff with `customer_accounts.manage` enter a new address for a user in their tenant and organization
- THEN the user's address is unchanged until the link is used

##### Scenario: Staff boundary
- WHEN staff lack `customer_accounts.manage` or target a different organization in the same tenant
- THEN both staff methods refuse (403 for feature, 404 for target scope) without changing anything

##### Scenario: Recovery after confirmation
- WHEN the former owner contacts staff after the attacker already confirmed and staff verify identity independently
- THEN staff start recovery to the verified address, the current mailbox cannot cancel or replace it, and confirmation restores access while ending all attacker sessions

##### Scenario: Attacker during recovery
- WHEN recovery is unresolved, including after the confirmation link expires, and the current address holder tries to sign in, request a sign-in or reset link, export or request deletion
- THEN each attempt is refused, nothing is sent to the current address, and an unclaimed deletion request is cancelled with reason `identity_review`

##### Scenario: A public issuer races an identity transition
- WHEN either public link request reaches the owner before an ordinary email confirmation, recovery start or recovery settlement commits
- THEN the transition invalidates any previously committed capability. If the transition takes the fence first, the earlier request returns the same generic response without mint, send or event.

##### Scenario: Cleanup after upgrade
- WHEN an upgraded installation has finished pending-change rows and the user makes no further request
- THEN this package's registered cleanup job removes them after the bounded retention period

##### Scenario: Recovery and deletion acceptance contend
- WHEN recovery commits after successful deletion re-authentication but before final acceptance
- THEN the final scoped check refuses and neither deletion state nor its email or event is written. If the unclaimed request commits first, recovery cancels it with `identity_review` in its own transaction.

## 📝 Architecture

- **`customer_accounts`**: pending-change entity and service; audited non-undoable request/approve/cancel/confirm commands; three portal handlers, three public handlers and two staff handlers across five route files; four email templates; one new event plus the existing update event; rate limits; `lib/credentialVersion.ts` and `lib/identityRecovery.ts`, consumed by the existing sign-in, link and credential routes; an hourly cleanup worker with setup and upgrade registration.
- **`portal`**: profile form, pending/cancel state and a public confirm/cancel result page.
- **Staff user page**: start/cancel, recovery mode with an identity-check acknowledgement, expired unresolved status and separate reissue or identity-verified settlement actions. Settlement identifies the current sign-in mailbox from the already authorized user detail. It prompts for attestation of that mailbox and binds the acknowledgement to the user and pending-row versions shown when the staff check begins. Refresh or conflict clears that acknowledgement. The proposed recovery destination cannot be substituted. Include instructions for prior identifiers and active holds. Authorization is `customer_accounts.manage` and the user's organization, not a staff role name.

**Every write is guarded.** Before mutation call `isCrossSiteBrowserRequest` from `@open-mercato/shared/lib/url`, collect `getAllMutationGuardInstances()` plus `bridgeLegacyGuard(container)` when present, and call `runMutationGuards` with the create/update/delete operation and `{ userFeatures }`. Portal features come from `customerRbacService`, staff features from `rbacService`; public token handlers have no granted features and use the capability's scoped resource, never impersonate a privileged user. A blocked guard returns its `errorBody`/`errorStatus`. Merge and revalidate `modifiedPayload`; run every `afterSuccessCallbacks` item after successful commit, logging and reporting callback failure without turning a committed change into an error. This covers portal request/cancel, public approve/confirm/cancel, staff start/cancel, recovery, and the password-change/reset-confirm writes integrated with the credential fence. On recovery settlement reject a guard transformation that changes the mailbox attestation or either reviewed version. Pass the validated address only to the in-memory credential check and opt the input out of request-body telemetry and command snapshot capture. The browser uses `apiCall`, `useGuardedMutation`, scoped lock headers, `surfaceRecordConflict` and `retryLastMutation`.

**Optimistic locking.** Authenticated start/replacement uses the user's `updatedAt`, supplied by profile/staff GET. Status returns the pending row id and `updatedAt`; authenticated cancel supplies that row's version. Commands enforce the expected version under the locked row with `enforceCommandOptimisticLock` and return the next version. Public approve/confirm/cancel use one-use capability and locked conditional live-state checks rather than a browser edit version. All pending-row transitions advance their `updated_at` and the owning user's `updated_at`, so a stale user version cannot replace a newer pending request. Status returns both `updatedAt` for the pending row and `userUpdatedAt` for start/replacement. Existing staff `GET /api/customer_accounts/admin/users/:id` retains `customer_accounts.view` and its organization filter, and adds `emailChange: { id, expiresAt, mode, updatedAt } | null`; this is the read path for staff cancellation and contains neither target address nor token. Existing root `updatedAt` versions staff starts. Staff action controls require `customer_accounts.manage` even when a viewer can see pending metadata.

**Re-authentication dependency.** Whichever portal spec lands first ships `lib/reauth.ts`, its columns, migration and snapshot. Follow self-service Architecture → Re-authentication exactly: separate atomic row-locked counter, reset on success/expiry, fifth failure locks fifteen minutes, locked requests 429, login counters untouched. Password change joins that helper, with its 429 behind the ordinary one-minor bridge (Migration). For email change only, an account without a password does not use the helper's recent-session rule; the old-mailbox approval above is its re-authentication. This spec does not depend on the self-service UI phases for its schema.

## 📝 Risks & Impact Review

#### A hijacked session takes the account
- **Scenario**: Someone with a stolen cookie changes the address to their own.
- **Severity**: High
- **Affected area**: portal accounts
- **Mitigation**: Re-authentication with the password, or old-mailbox approval for an account without one; pre-confirmation cancel, which also ends the requester's sessions and blocks re-requests for 24 hours; and a changed notice with a staff recovery path which the current mailbox cannot cancel, during which the account cannot sign in, receive links, export or request deletion; the recovered address must confirm. Session creation and password writes fence old credentials.
- **Residual risk**: An attacker who knows the password and controls the new mailbox can confirm within seconds, before the owner can read any notice; a passwordless account additionally needs the old mailbox. Access may be lost until staff verify identity and recovery confirms. Compromise of both mailboxes or a mistaken staff identity check remains a risk — a mistaken recovery also locks the real holder out until staff cancel it. Downstream session callers omitting the optional fence retain their documented race.

#### The request reveals who has an account
- **Scenario**: A signed-in user tries addresses to see which exist.
- **Severity**: Medium
- **Affected area**: other users of the tenant
- **Mitigation**: Every observable outcome is the same for a free and a taken address; three requests an hour.
- **Residual risk**: Timing. Both paths send the same number of messages (two with a password, one at request time without), but delivery is awaited inline after commit, so the response time includes each recipient's delivery latency and can differ between a free and a taken address. Post-response delivery is not part of this design; a deployment that needs response-time equivalence must add a queued sender.

#### The user is locked out
- **Scenario**: The address is confirmed, sessions end, and the user mistyped nothing but cannot receive mail at the new address later.
- **Severity**: Low
- **Affected area**: that user
- **Mitigation**: Proof at confirmation plus independently verified staff recovery which the current mailbox cannot cancel.
- **Residual risk**: Recovery depends on reachable, competent staff and a mailbox the owner controls; delay and verification mistakes remain possible.

#### Historical addresses remain outside ordinary current aliases
- **Scenario**: A user changes address; records keyed by identifiers replaced before hold capture are not reached by account-only export/erase.
- **Severity**: Medium
- **Affected area**: subject coverage and enterprise holds
- **Mitigation**: Cancel live old-address invitations; atomically capture old/new identifiers for matching holds under the shared tenant fence on the confirmation manager. Hold capture and all account changes roll back together on failure; guarded destructive work and first-hold admission use the same fence. Document the current-only export/erase limit and explicit DEC-A handling for uncaptured historical identifiers.
- **Residual risk**: Addresses replaced before capture remain a manual-discovery responsibility. Unavailable required protection temporarily prevents confirmation; it never permits a missed held alias. Arbitrary downstream writers remain outside the protected claim until the fleet participation gate verifies them. This flow adds no general historical alias archive.

#### Finished target addresses have no scheduled deletion
- **Scenario**: An upgraded account never makes another request, or its scheduler later stops.
- **Severity**: Medium
- **Affected area**: encrypted pending-change addresses
- **Mitigation**: Own hourly cleanup, idempotent setup/upgrade registration, bounded batches, 24-hour terminal retention and refusal of new requests without registration. TC-PORTAL-EMAIL-003 covers upgrade without a later request.
- **Residual risk**: Registration cannot prove a running scheduler; an outage delays deletion until processing resumes. Operators must monitor the job. On an upgraded installation email change stays unavailable until a tenant is set up or a `configs.manage` user runs the upgrade action.

#### A token-service override stops working
- **Scenario**: An application replaced `customerTokenService` with an implementation that stores tokens outside the module's tables.
- **Severity**: Low
- **Affected area**: magic-link sign-in and password reset in that application
- **Mitigation**: The routes take the stamp from the module's own tables, so subclass and delegating overrides keep working; the remaining case is named in the DEC-13 compatibility entry and upgrade notes with its migration, and `customerTokenService.override.test.ts` pins both behaviours.
- **Residual risk**: Such an application loses those two flows until it migrates; it does not lose the fence.

#### Released address acquires another account's CRM access
- **Scenario**: The old mailbox signs up while the retained person still carries that address.
- **Severity**: High
- **Affected area**: portal company access
- **Mitigation**: Forward/reverse linking serialize by person and query account-owned occupancy; skip attaching another active user and refer to staff. Organization predicates apply to linking and every staff operation.
- **Residual risk**: Explicit staff relinking still needs identity review. A deleted/inactive account no longer triggers the active-account guard; this design does not create a permanent released-address registry.
