## 📝 TLDR

A handler's own tests cannot find copies it forgot. **Proposed (future):** an independent tenant scan reports locations of planted text, record ids, network identifiers and supported lookup hashes across tables, indexes, files and local queues. An erasure test proves fixture presence in each inspected store, then accepts table survivors only against exact run-bound retained rows or reviewed operational table/column/window declarations. Non-table queue copies have their own assessment. A program acceptance matrix prevents three tests from being mistaken for the whole deployment gate.

**Not in this spec:** implementing handlers, a coverage inventory replacement, or an external audit. The scan is operator-only; it adds no HTTP route or UI.

## 📝 Overview

The test uses canary values with no connection to real people. It scans independently of the erasure handlers. A reader failure is a named gap, not an empty result. A global table is not applicable only when its reviewed declaration proves that classification.

## 📝 Problem Statement

- Encrypted columns and encrypted custom fields hide leftovers from SQL `LIKE`. `decryptCustomFieldValue` in `packages/shared/src/lib/encryption/customFieldValues.ts` handles flagged custom fields outside encryption maps.
- `entity_indexes.doc` is a denormalised JSON document with encrypted fields (`query_index/data/entities.ts` and `query_index/lib/indexer.ts`). `decryptIndexDocForSearch` in shared `encryption/indexDoc.ts` decrypts it for its entity type.
- `packages/search/src/vector/drivers/pgvector/index.ts` creates a runtime vector table outside module snapshots. Fulltext is an external driver. The response cache and Redis are not generically inspectable by this tool.
- `SearchService.search` in `packages/search/src/service.ts` uses `Promise.allSettled`, logs and skips strategy failures, filters entity and organization visibility, then ranks results. It cannot establish that a fulltext store was read completely.
- `tokenizeText` and `hashToken` in shared `search/tokenize.ts` currently use unkeyed `createHash`, not the lookup secret. A different token configuration or failed decryption still makes an empty lookup inconclusive. There is no existing keyed-token verification helper.
- `lookupHashCandidates` in shared `encryption/aes.ts` returns current keyed and legacy unkeyed lookup forms. A leftover address hash remains linkable even after the address is cleared.
- `QueueJobScope` and `removeQueuedJobsByScope` already define scoped queue operations (`packages/queue/src/types.ts`). Local `queue.json` stores all tenants' jobs per queue (`strategies/local.ts`); its private `payloadMatchesScope` reads top-level `tenantId`, `organizationId` and `jobType`. The scanner must not read the file itself.
- Attachment drivers cannot list objects (`attachments/lib/drivers/types.ts`). Erasure's future `attachment_pending_deletions` is needed to find objects whose first delete failed. R4-5 classifies those rows as `runtime_state`: successful drain deletes them, and they write no action-log entries or planned history identities. The attachments-owned `attachments.pending_deletions_stale` database doctor check surfaces rows older than 7 days; it supplies neither an object TTL nor proof of deletion.
- The CLI banner echoes arguments (`packages/cli/src/mercato.ts`); searched values must never be arguments. A scan that only matches text misses surviving junction ids, sessions, IP addresses and user agents.

## 📝 Proposed Solution

### 1. Run-bound retained declarations

A data class gains `retained` entries with `section`, `table`, `columns` and `reason: PrivacyRetainReason`, imported from the erasure contract. The class id comes from the enclosing definition. The reason enum stays owned by the erasure spec; this spec does not add a reason. Separately load applicable whole-table/subset `personalData.kind: retention_bounded` classifications through C5's validated inventory. Record-set definitions come from `getPrivacyRetentionBounds(modules)`; operational-pruner references resolve through their registry under R4-13 below. C5's “Declarations and row subsets” and API Contracts own `PrivacyRetentionBoundDefinition`, `PrivacyRetentionBoundProjection` and `PrivacyRetentionBoundHandler`: resolve each `boundedBy` through its owner's `resolve({ scope, boundId, now, em })`, then evaluate the exact captured row with `evaluateFixtureRow`. Read the declared table/subset, allowed columns, age anchor, effective window, mode/counting grace and enabled/scheduled/worker state from those owner contracts. A class-retained list alone is not the full survivor policy.

A survivor is accepted only when all of these agree: the scanned row id; the declaration's class, section, table and column; and this applied run's retained section and exact row evidence with the same reason. A section with outcome deleted, anonymized, refused or not_found never grants permission merely because its columns are retainable in another case. An anonymized section that retains a lawful subset must report that subset as a separate retained section.

C4's “Contract additions — `@open-mercato/shared/modules/privacy`” defines `PrivacyRetainedRecord`, `PrivacyErasureSectionResult.dataClassId` and `retainedRecords`; import those owner types instead of defining another record shape. The runner stamps class identity on every flattened section, and coverage handlers must populate exact surviving rows/columns before their verification lane can pass. Do not infer rows from `affected` counts or rerun the handler to ask whether its own leftover is allowed. Evidence comes from the private run report or encrypted completed audit, never `privacy.subject.erased`: C4's event-safe projection deliberately excludes retained rows. R3-14, “The `eraseSubjects` entry point”, remains the entry/result contract; R3-1 and DEC-B own history stripping and are not redefined here.

For a `retention_bounded` survivor, require an exact captured fixture row, declared table/subset and column, plus a still-open effective window under that owner's terminal-state/clock predicate. Validate the projection against C5's immutable target/column/anchor inventory and require the row evaluator's matching `within_window`, `anchorAt` and `expiresAt`. Rule identifiers describe owner predicates; never execute metadata strings as SQL. Off/report mode, active counting grace, an unscheduled handler, unknown/unavailable worker or pending deletion remains explicitly unbounded/pending. Missing or failed metadata/evaluation fails verification; a declared default alone does not prove a deadline.

R4-13 resolves `{ kind: 'operational_pruner', prunerId }` through the operational-pruners registry owned by `2026-11-16-operational-retention-pruners.md`, “Operational bound projection for C5/G6”. The pruner owner implements C5's exact `PrivacyRetentionBoundProjection`/`PrivacyRetentionBoundHandler`, with `boundId = prunerId`; its `resolve({ scope, boundId, now, em })` and `evaluateFixtureRow` use the deleting owner's exact table/subset, column allowlist, terminal-state predicate and clock. Consume the effective window and actual mode, counting phase, registration, execution and pending evidence. Disabled/report/counting paths, missing/disabled schedules, unknown execution or outstanding continuation cannot establish an enforced finite bound. The pruner owner publishes that registry as `operational_pruner` entries of C5's `retentionBounds` member (its “Registry publication”; C5 assumption 7), and `getOperationalRetentionBounds(modules)` selects them. Collection, static validation and operational survivor coverage are claimed only once those entries and the owner handlers ship. No duplicate operational definition/status/`describe` contract is consumed. The sixteen core pruner ids imply no enterprise, access-log, forms or queue bound; those owners supply their own evidence.

Privacy evidence has no single program-wide window. Resolve the actual owner declarations: C1's “Export-evidence expiry” defines `privacy.export_evidence` / `retention.privacy.exportEvidenceAgeDays`; C4's “Erasure-evidence expiry”, assumption 20, defines `privacy.erasure_evidence` / `retention.privacy.erasureEvidenceAgeDays`; record retention's “Retention-run evidence” defines `privacy.retention_evidence` / `retention.privacy.retentionEvidenceAgeDays`; each defaults to 365 days with floor 30, extended by holds and unresolved work. C1's settings evidence remains separately owned by “Settings-command evidence expiry”. C8 separately defines `privacy.tenant_export_evidence` / `retention.privacy.tenantExportEvidenceAgeDays` with the same default and floor; unresolved publication/reconciliation preserves its evidence. Under R4-3 every tenant-export evidence row carries its tenant, so the same tenant-scoped set expires it; a soft-deleted tenant keeps its policy and schedule running until that set is empty. C3's “Metadata retention and coverage” declares `data_erasure.governance_evidence` (365-day terminal operations/holds; unused previews fifteen minutes) and `data_erasure.retention_failures` (thirty days or earlier subject completion/policy deletion); its “Governance action entries” separately defines `data_erasure.audit_evidence` / `retention.data_erasure.auditEvidenceAgeDays` (default 365 days, floor 30, terminal proof required, active holds/configuration and unresolved dependencies preserved). C9's “Data Models” declares `data_erasure.replay_evidence`, using the settled-pair window from `OM_ERASURE_MANIFEST_RETENTION_DAYS` (default 90 days), not a blanket privacy exemption. Include all these C3/C9 `boundedBy` targets in C5's registry-based evidence coverage and require exact fixture rows, columns, lifecycle and resolved clocks. A named set alone grants no table waiver.

These bounds depend on an actual runner and their hold/guard rules. C4 preserves open/incomplete journals and unreconciled coordinators; C3 preserves active holds and accepted incomplete operations; C9 preserves pending/invalid files and unsatisfied pairs regardless of age. Under R4-4, C4 expiry checks the durable `privacy.erasureEvidenceOwnerRequired` tenant requirement through `privacyErasureEvidenceRequirements`, signed activation posture and persisted capture evidence. Required owner absence, unverified state, a throwing provider or pending work skips the run, counts it once as `held_by_owner` and retries. Only positively clear, verified never-activated tenants with no capture evidence proceed without the composite, subject to the ordinary age, hold and local-recovery checks. DSR answers from its own unresolved operation state. Replay checks its pending/applied rows and authenticates the live inventory and file for the exact run, even before maintenance records a missing or corrupt file. A settled run can become eligible after the required owner confirms repair or authenticated retirement. The tenant requirement remains latched while the owner is disabled. C8's R4-3 evidence is verified through an ordinary tenant-scoped run, including one for a soft-deleted tenant. Other null-tenant evidence still needs its owner's expiry rule or an explicit gap, never a tenant setting. Check fresh evidence rows separately from erased content, including whole-entry expiry with no copied actor/reference/id fragments; unexpected copies outside each reviewed evidence shape fail. A configured age does not prove deletion while a runner is absent or work is unresolved.

**Retained queue copies.** B6 queue-payload-minimization assumption 8 retains queued/delayed/failed copies outside table declarations, with no subject purge. Consume C4's private `PrivacyRetainedQueueCopies` under “Queue copies after completion”; never turn its `retainedCopies` into class sections, exact subject-attributed counts or R3-14 result members. `QUEUE_FAILED_JOB_RETENTION_HOURS` is unset/0 in bridge minor N, unset/168 in N+1, explicit 0 count-only. Positive age applies to failed jobs from `finishedOn` while a worker or `mercato queue prune-failed` pass runs. Unacknowledged abandoned jobs can outlive it; waiting/delayed/backlog lifetime has no such bound. Sealing protects content but is not deletion; legacy plaintext remains until resolved. Under assumption 10 the B6 lane discloses and measures these copies. Acceptance of that lane does not establish or waive verified absence for DEC-15. Report exact fixture jobs, states, plain/sealed status and actual bounds separately. The retained-queue-copy report also carries, from B6's `mercato queue payload-status`, the oldest stored job age per queue and state, counts and ages only, and names each queue whose maximum enqueue delay is unbounded in B6's inventory (`workflow-activities`). A table declaration cannot excuse a queue match or gap.

### 2. The scan

`mercato privacy scan-values --tenant <id> --values-file <path | -> --reference <text> [--only <store>]… [--out <file>] [--force] [--allow-production]`

One UTF-8 value per line, blanks ignored. `--values-file -` reads stdin without echo; empty/unreadable input refuses before store reads. Reuse C1's no-echo input/redaction policy; its `--email -`, `--phone -` and `--name -` read a single identifier, while this command reads a list. The caller includes text markers, subject/profile/account/user UUIDs and synthetic network identifiers. `--value` is a usage error and its refused argument is redacted in `SENSITIVE_MODULE_CLI_OPTIONS_BY_COMMAND`, so the banner cannot leak it.

**Input limits.** Input is bounded before the audit entry and before any store read; exceeding a limit is exit 1 with no value echoed: at most 1 MiB of input, 1,000 non-blank values, 1,024 UTF-8 bytes per value, and 20,000 generated comparison candidates (values plus lookup-hash and token candidates). These keep the in-memory candidate set and per-row comparison cost bounded; a larger inventory is split across runs.

**Batches, progress and store selection.** Every store is read in tenant-scoped pages of at most 100: the table and query-index readers with `batchSize: 100`, token, vector and fulltext scans with pages of at most 100, the local queue in pages of at most 100 jobs, and attachments one file at a time. As each store completes, the command prints one line to standard error with the store id, its status and scanned/not-scanned counts, never values or locations. `--only <store>` (repeatable; `tables`, `query_index`, `attachments`, `tokens`, `vectors`, `fulltext`, `local_queue`) limits a run on a large tenant; every unselected store is reported as `not_requested`, which keeps the run incomplete (exit 2), so a clean result always needs every store. The command is read-only, so a failed run is simply repeated; it has no resume state.

String and JSON leaves and plain-text files use case-insensitive substring matching. UUID values additionally match exact typed UUID/scalar values and elements inside JSON; ids are searched in every relevant column, not just names. For email/phone-shaped values, compute `lookupHashCandidates(value)` and, for phone numbers, candidates for the normalized digits using the contract's shared normalization (not a new handwritten normalizer). Compare exact digest strings, including JSON leaves, in memory. The candidate set covers current and legacy forms and mapped/module-declared contexts; never return digests. A column using an undeclared context is an explicit unsupported-hash gap, not a clean result. Wrong/absent lookup material is reported as `lookup_hash_unverified`; integration fixtures require positive known-hash calibration before trusting absence. Use the separate control record's decrypted email/phone and its stored sibling hash, exact entity/row/column and declared context; require a current-key candidate hit, so a legacy-only hit cannot certify the active secret. No eligible control or mismatch is lookup_hash_unverified, including after erasure. No plaintext or candidate is persisted. R3-12 and DEC-F in the encryption-map spec own hash columns/backfills; this spec consumes them.

**Token calibration.** The search-index-PII-protection spec owns future `hashSearchToken` / `tokenizeSearchText` and their keyed/legacy bridge (Architecture and API Contracts). Use its current keyed and legacy candidates once that package lands; do not keep the deprecated unkeyed helpers as the only scan path. Keyed calibration must hit the current keyed form, so a legacy hit cannot conceal a wrong lookup secret. Before that package lands, use today's unkeyed tokenizer and report that narrower capability explicitly. During each scan, the table reader finds a decrypted plaintext value in a tenant row/field that the real indexer declares searchable and indexes. `scanTokenValues` derives tokens with the owning search package's supported current/bridge tokenizer and `resolveSearchConfig` and requires corresponding `search_tokens` hits for that exact tenant, entity type, entity id and field. The witness must fit indexing limits and yield at least one token. Try another eligible value if one is too short; no suitable witness gives `token_probe_unavailable`. Missing/mismatched hashes give `token_probe_mismatch`. A decryption failure cannot supply a witness. Calibration proves only this witness, not uniform health of all rows; the integration pre-scan still requires planted-marker hits. The test owns a separate indexed control record, not erased with the subject, so a positive probe remains after erasure. A wrong encryption secret must fail decryption/calibration rather than produce clean token coverage. Changing only the lookup secret cannot invalidate today's unkeyed token hashes; once the search-index package lands it must fail the current-key probe as well as lookup-hash calibration. Unit tests cover both stages; TC-PRIVACY-VERIFY-001 at program closure requires keyed-token coverage.

**Fulltext.** `scanFulltextValues` calls the resolved fulltext driver directly, in pages of at most 100 tenant documents, across all organizations. It bypasses result ranking, blocked-type filters and strategy fallback. Add optional `iterateTenantDocuments({ tenantId, batchSize })` to `FullTextSearchDriver`; it yields raw indexed documents with tenant checks and exhaustive paging, without ranked-search hit caps. Drivers without it are explicitly unsupported. The search-owned function matches values in the documents and returns locations only; no raw document leaves the package. Any page failure makes the store incomplete even if prior pages matched. Meilisearch is the initial adapter; other drivers may implement the additive capability later.

**Queue scope.** `privacy` resolves each registered queue through the queue package; it never opens `.mercato/queue` files. `findValuesByScope` is an optional additive `Queue` member, using the existing scope matcher before scanning payloads. Inspect both current and coalesced pending payloads through queue-owned code. Valid jobs of another tenant are excluded before any value comparison or output. A missing/non-object payload or invalid/missing tenant scope is counted as `unattributed_job` without examining its contents for values. A sealed payload that cannot be attributed without opening is counted as `sealed_job`; no key is requested and nothing is written. Report these unknowns conservatively for the queue; they cannot be called clean tenant coverage. Async strategy returns `unsupported_strategy`.

**Results.** Matches identify store, table/index/queue, column/path, stable row/job id, input position and `form: 'text' | 'id' | 'lookup_hash' | 'token'`. No matched content, digest, snippet, file name or job payload is returned; stable row/job ids remain location metadata and may equal a searched record id, so the report is still handled as sensitive owner-only data. Include table row-presence locations for fixture assertions even when no column is searchable. Results list scanned, not-scanned and not-applicable stores separately, with reasons and global declaration evidence. Not-applicable is never inferred from a missing reader.

**Reference, production and audit.** Every run requires `--reference` (1–120 characters) and refuses without it. Production uses the key-guard definition, including R3-11's IPC-bound runtime mark; the doctor cannot observe other processes (DEC-E). In production `--allow-production` is an extra required confirmation. Write one `actionLogService.log` entry before any store is read, in every mode: resource kind `privacy.value_scan`, resource id tenant UUID, command id `privacy.value.scan`, actor `system:privacy-cli`; context reference, value count, planned store names and the OS user name and host name labelled as non-authoritative hints. A missing audit service or a failed audit write refuses in every mode, independent of `NODE_ENV`. The entry records that a scan ran under that reference; it does not authenticate a person, so personal attribution relies on host access controls. No input value, digest or match location is audited.

**Output.** C1's “File handling” is normative: write and fsync a `0600` temporary file in the target directory; without `--force`, publish with `link(temp, target)`, which atomically fails if the target exists, then unlink the temp and fsync the directory where supported. ### Known limits

Split-across-column, compressed and arbitrary transformed/salted hashes remain outside matching. Current/legacy lookup hashes with declared contexts and digit-normalized phones are covered; they are no longer a blanket limit. A wrong lookup secret can make hash coverage unverified and must be reported. Redis, backups, logs, binary file bytes and unreferenced objects remain explicit gaps. Evidence has owner-defined terminal windows, but missing runners, holds and unresolved C4/C3/C9 work can preserve it beyond those ages; operational/queue bounds may likewise be disabled or pending. Queue copies left after an erasure are disclosed, not purged (assumption 10). File-deletion receipts are lifecycle evidence, never a content scan. Extracted attachment text is checked through `attachments.content`. Calibration is a positive sample, not proof that every index record is healthy. Runtime grows with the class/store inventory.

## 📝 Architecture

The `privacy` module owns the command, matching and acceptance fixtures. Table access uses DEC-G's exact `PrivacyTableReader` from the exit-export spec through program DEC-9's module-owned DI readers. Owners invoke its shared helper only for their own tables; all registrations precede G6. `query_index` supplies its scanReader; attachments owns byte scanning; search owns token/vector/fulltext scans; queue owns scoped payload scanning. Each optional peer resolves softly; missing capability is a gap. No cross-module ORM relationship or foreign table access is added by the verifier.

R3-2 in the contract spec supplies `module.privacy`; shared collectors independently validate its members. This spec adds definition fields and tests, not a generator. R3-1/DEC-B define the history strip and R3-14 the erasure entry; the suite tests their observable effects without redefining them.

## 📝 Data Models

No database entity or migration. All raw values, hash candidates and fixture inventories stay in memory, bounded by the input limits above. Output contains locations and counts. Test artifacts with row ids follow owner-only output rules. Row probes are test-only and limited to captured fixture ids; no broad foreign-table query is added to privacy.
