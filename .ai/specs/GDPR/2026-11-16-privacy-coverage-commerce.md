## 📝 TLDR

Customer data also lives on orders, quotes, baskets, pay-link payments and warranty records. **Proposed (future):** module-owned classes export these records and delete, blank or retain their personal parts with an explicit reason. Marked records have a follow-up through retention sets. Provider writes use the same row locks as privacy writes, so a poll cannot restore cleared data. Each module phase ships export and erase together.

Invoices, credit memos and payments have no customer column; when they belong to an order, their free text and metadata are covered through it. Rows without an order are unattributed and stay a reported limit. Card details held only at a provider and tenant configuration with no subject link are outside this design.

## 📝 Overview

This carrier covers the commerce modules of Track C's coverage roll-out: `sales`, `cart`, `checkout`, `payment_gateways`, `warranty_claims`, and, assigned by DEC-J, `shipping_carriers`, `promotions`, `customer_groups` and `packages/carrier-*`, plus the gateway provider packages `gateway-autopay`, `gateway-stripe` and `gateway-tpay`. It is OSS under DEC-2: every class, mapper, set and fill lives in the module that owns the data, and enterprise adds only scheduling and holds through the shared services. It needs the contract (C1) Phases 6–7, the erasure run (C4) Phase 4 with R3-1/DEC-B, record retention's DEC-C, the doctor's R3-4/R4-7 tier and, for source notification copies, communication coverage Phase 1. Each phase also registers its modules' tenant-export (C8) readers, which needs tenant exit's Phase 2 helper. C5's census, C8's export, G6's verification suite and B1 Phase D's maintenance consume its declarations. Phases 1–5 each ship their modules' export and erase together and leave those modules' personal data reachable, reduced or bounded, with their remaining baseline entries named; Phase 6 adds the sessions-route gateway order link and its idle-transaction bound.

## 📝 Resolved assumptions (autonomous defaults)

| # | Question | Decision | Rationale |
|---|---|---|---|
| 1 | Which orders must survive identified | An order with an invoice, a completed payment, a non-cancelled sales shipment or a non-cancelled carrier shipment retains a reduced buyer block: name, company, billing and shipping postal addresses and tax id. Signals use status codes, not labels: any non-deleted `sales_invoices` row counts; a `sales_payments` row counts unless its status code is `pending`, `authorized`, `failed` or `canceled`; a `sales_shipments` row counts unless its status code is `canceled`; a `carrier_shipments` row counts unless its `unified_status` is `cancelled`. Sales statuses are tenant dictionary entries, so the code is read from `status` (resolved through `status_entry_id` when set), trimmed and lower-cased, with `cancelled` treated as `canceled`. A null, tenant-defined or otherwise unknown code counts as a signal. The reviewed dry run lists each order's outcome and the signal that decided it before apply | These four signals are the product's record of a sale that was billed, paid or dispatched; an order with none of them has no commercial record to keep. Counting an unknown status as retaining errs toward keeping a commercial record rather than destroying one; the dry run shows the operator why. A carrier shipment counts even when no `sales_shipments` row exists. Phone, email, contact title, department, comments and internal notes are unnecessary for this block. A retained carrier label is a separately reported evidence copy under the rule below |
| 2 | Until when | The tenant sets whole calendar years, minimum 1, counted from `placed_at`, falling back to `created_at`. There is no product default. Unset means `retainedUntil: null` and the legal-retention set refuses; `mercato privacy doctor --database` reports the unset age | Periods differ by jurisdiction and record type, so none is guessed; OSS operators must run the set |
| 3 | Other orders and quotes | Blank personal copies and free text; keep numbers, system references and totals | Numbering and arithmetic survive without the buyer |
| 4 | Finding retained records again | Keep the owner's anonymized root and document link where available; keep the buyer-email hash only while a record is retained. With its source email cleared, the owning fill's next run, normally after a lookup-secret change, clears it (API Contracts, “Source-less retained hashes”) | The hash also reaches guest records and records orphaned by ordinary customer deletion |
| 5 | Identifier-only and portal subjects | Use DEC-A and the contract's “A subject that is only an identifier”; also declare `customer_accounts:user` on email-keyed classes | An unlinked portal account still reaches its own email-keyed records through its aliases |
| 6 | Completed pay-link payments | Retain name, consents and email hash until the tenant's checkout age, clearing contact and client data and reducing gateway data to refund/reconciliation fields. A matched provider with no verified reducer refuses in pre-flight, before any write | Refunds need provider identifiers and amounts, not the whole provider response. Refusal keeps an unfiltered provider blob from being retained as if it were reduced |
| 7 | Baskets | Delete where allowed; otherwise blank. A locked checkout basket is `retained` / `open_case` and retried after unlock | Four restrict foreign keys can prevent deletion: `carts.proposed_to_cart_id` and the merge log's source, target and proposal |
| 8 | Warranty claims | The terminal set is the product's own `isTerminal` set in `warranty_claims/lib/stateMachine.ts`: `closed` and `cancelled`. A terminal claim is blanked immediately and stamped `anonymized_at`. Every other status, including `resolved` and `rejected`, is open: mark it, retain it as `open_case`, and blank it through `warranty_claims.retained_open_claims` once it reaches `closed` or `cancelled` (both `resolved` and `rejected` may move to `closed`). The transition command refuses to move an `anonymized_at` claim out of `closed` (the lifecycle's `closed → in_review` reopen) with 409 `warranty_claims.errors.claimErased`; a returning customer files a new claim | A contact point is needed while a case is being worked; a later run must not need the email typed again. A reopened blank claim would be worked with no contact point and no history, so refusal is the honest outcome. `resolved` and `rejected` claims can still reopen or close, so they are not terminal; one left there is a visible `open_case` with a null end until someone closes it |
| 9 | Staff authorship | Leave staff ids on commercial records as reference-only ids, as the program's reference-only rule specifies; no commerce class declares `auth:user`. Cart merge replay records are the explicit exception and always lose `merged_by_actor_id` when stripped | Authorship alone is not a buyer copy; a staff user's own erasure renders these ids as "Unknown user". The replay record must not retain its actor copy |
| 10 | Pending and processing payments | Retain payment and gateway contents as `open_case`; set the host's retention and open-case marks. `checkout.finished_open_payments` handles terminal payments later | An in-flight provider may still complete the financial record |
| 11 | Existing coverage bundle or split | Keep the commerce spec and its per-module release phases | Module phases ship independently |

## 📝 Proposed Solution

### Classes and discovery

| Class | Subject kinds | Finds by |
|---|---|---|
| `sales.documents` | `customers:person`; `customer_accounts:user`; `privacy:identifier` | `customer_entity_id`; `customer_contact_id` through `profile_ids`; buyer-email hash through `email_hashes` |
| `cart.baskets` | `customers:person`; `customer_accounts:user`; `privacy:identifier` | Customer id and JSON customer-id list; portal user id; email hash |
| `checkout.payments` | `customers:person`; `customer_accounts:user`; `privacy:identifier` | Email hash, then its own transaction ids passed to `paymentGatewayService` |
| `warranty_claims.claims` | `customers:person`; `customer_accounts:user`; `privacy:identifier` | `customer_id`; new `created_by_customer_user_id`; contact-email hash; registrations by `customer_id` |
| `promotions.usages` | `customers:person` | `customer_id` |
| `customer_groups.memberships` | `customers:person` | `customer_id` |

All are `erasureGroup: 'records'`; none owns a subject kind. The owner rule comes from the erasure spec. CRM and portal owners publish their own `email_hashes`; a portal user with no CRM person reaches orders and pay-link payments by that alias. There is no separate gateway class: the checkout class calls the gateway's service by payment id. The contract's `providedAliases` / Identifier coverage guard validates every address-keyed class against all owners publishing `email_hashes` or `phone_hashes`: currently `customers:person` and `customer_accounts:user`, in addition to `privacy:identifier`. Reject a future missing kind during collection; do not hard-code today's owner list as the entire rule.

DEC-A — “Subjects known only by an identifier (`privacy:identifier`)” — remains owned by the contract and erasure specs: identifier derivation, normalized aliases, re-supplying the same identifier for apply, redacted CLI flags, and refusal without a lookup secret. This design does not introduce another identifier format.

**Phone identifiers are not matched.** Commerce stores email hashes only; it adds no phone hash, although `checkout_transactions.phone` and `customer_snapshot.primaryPhone` hold numbers. For a subject whose aliases carry `phone_hashes` but no `email_hashes` (an `erase --phone` or `export --phone` identifier subject), each of `sales.documents`, `cart.baskets`, `checkout.payments` and `warranty_claims.claims` reports its export section `truncated: true` with the contract's `ALIASES_NOT_AVAILABLE`, so the export is not complete, and lists the same named limit in the erasure dry-run and apply reports. Numbers on records reached by id or by an email alias are exported and cleared as below. Known limits states this.

### What erasure does

| Record | Outcome and follow-up |
|---|---|
| Protected order inside the tenant age, or with no age set | `retained` / `legal_retention`: buyer block reduced by the buyer-block reducer below, and email hash; `privacy_retained_at` set, `retainedUntil` date or null, `retentionSetId: sales.retained_orders` |
| Protected order already past the age, or other order or quote | `anonymized`: snapshots, email hash, comments, internal notes where present, `external_reference`, `customer_reference` and personal line/metadata fields cleared; numbers and totals kept |
| `sales_document_addresses` | For an anonymized document delete its rows and clear its address ids/snapshots. For a retained order keep at most one row per retained snapshot: after decryption, a row is the billing (or shipping) row when its `name`, `company_name`, `address_line1`, `address_line2`, `building_number`, `flat_number`, `city`, `region`, `postal_code` and `country` equal the reduced `billing_address_snapshot` (or `shipping_address_snapshot`) fields, compared trimmed and case-insensitively with null equal to empty. `purpose` is free text and is never used to select. If several rows match one snapshot keep the lowest id; one row may serve both snapshots. Delete every other row, including all rows when none matches: the reduced snapshot then carries the address alone. On kept rows clear `customer_address_id`, `purpose`, `latitude` and `longitude`; delete them when the set blanks the order |
| Contact on a company's document | Clear only that contact's copy and link; the company's buyer record stays. Do not blank the company's postal address for its contact's erasure |
| Sales child records | Shipments, returns, payments, invoices, credit memos and their lines follow the order's retention decision; clear personal notes, descriptions, metadata and credit-memo `reason`. Retained billing numbers, amounts and dates stay |
| Basket not locked | Delete it and its owned line/application rows where FKs allow; otherwise blank buyer ids, email/hash, note, personal line data and metadata, and soft-delete its live lines in the same write. Mark the surviving cart permanently non-writable. Sanitize related merge logs and delete its idempotency rows in both branches |
| Locked basket | `retained` / `open_case`, `retainedUntil: null`; retry after unlock. No invented `pending` outcome |
| Pending or processing pay-link payment | `retained` / `open_case`, `retainedUntil: null`, `retentionSetId: checkout.finished_open_payments`; set `privacy_retained_at` and `privacy_open_case_at` without clearing personal data or touching its gateway rows |
| Completed pay-link payment inside its age, or with none set | `retained` / `legal_retention`: name, consents and email hash kept; email, phone, customer data, IP and user agent cleared; mark set; gateway data reduced; name `checkout.retained_payments` and its end |
| Completed payment past its age, or failed/cancelled/expired payment | `anonymized`: name, consents, all contact/client data and email hash cleared; gateway personal data cleared |
| Gateway rows for an anonymized payment | Clear provider blobs, redirect URL, client secret, webhook log and operation personal payloads; mark `anonymized_at`. Keep only operational ids, amounts, status and safe operation replay envelopes |
| Gateway rows for a legally retained payment | Reduce through the provider-owned mapper below, set `privacy_reduced_at`; never keep an unfiltered provider blob merely because the payment is retained |
| Order-linked gateway rows (Phase 6) | Follow the order: reduced for a retained order (`order_gateway`), cleared for an anonymized one (`gateway_structure`). A transaction still `pending`, `authorized` or `unknown` is `retained` / `open_case` (`order_gateway_open`), unchanged until `payment_gateways.idle_transactions` reduces it |
| Closed or cancelled warranty claim | `anonymized`: clear name, email/hash, notes, resolution summary, fault/inspection text, event bodies and customer actor copies, return label and personal tracking data; release its files; set new `anonymized_at`, after which the reopen transition refuses (assumption 8) |
| Open warranty claim (every status other than `closed` and `cancelled`, including `resolved` and `rejected`) | `retained` / `open_case`, `retainedUntil: null`, `retentionSetId: warranty_claims.retained_open_claims`; set `privacy_retained_at` and keep working data until terminal |
| Warranty registration | Export product, variant/SKU, serial, purchase/warranty dates and notes. Delete the registration on erasure and release `proof_attachment_id` through `releaseByIds`; claim lines keep their own existing product/serial copies, whose personal free text follows the claim |

**Free text policy.** For anonymized sales documents and their children, clear custom descriptions, free-text names, comments and references; use the shared placeholder for required textual fields. Clear metadata except a typed allowlist of system ids, enum codes and numeric totals; arbitrary strings and unknown keys do not survive. Apply this to order/quote lines, invoice/credit-memo lines, invoice metadata and credit-memo reason/metadata. For retained records clear these fields on initial erasure too; only the stated reduced buyer block is kept in sales tables. The carrier-label evidence exception below is a separate retained section. Tests put a name in a line description, metadata and a credit-memo reason. No `anonymized` section may retain those names under a known-limit footnote.

**Buyer-block reducer.** `sales/lib/privacy/buyer-block.ts` exports `reduceBuyerBlock`, a pure zod-validated function over `customer_snapshot`, `billing_address_snapshot`, `shipping_address_snapshot` and `tax_info`, applied to a retained order at initial erasure. A quote, including one converted into a retained order, is never reduced: it follows the anonymized row of What erasure does, and only its `document_structure` columns survive. It rebuilds each JSON value from an explicit allowlist and never copies the stored object:

| Column | Keys kept | Everything else, dropped |
|---|---|---|
| `customer_snapshot` | `customer.id`, `customer.kind`, `customer.displayName`; `customer.personProfile.{id, firstName, lastName}`; `customer.companyProfile.{id, legalName}`; `contact.{id, firstName, lastName}` | `primaryEmail`, `primaryPhone`, `preferredName`, `brandName`, `domain`, `websiteUrl`, contact `preferredName`/`jobTitle`/`department`, and every unknown key that `customerSnapshotSchema`'s `.passthrough()` admitted |
| `billing_address_snapshot`, `shipping_address_snapshot` | `name`, `companyName`, `addressLine1`, `addressLine2`, `buildingNumber`, `flatNumber`, `city`, `region`, `postalCode`, `country` | The CRM address `id`, `purpose`, `latitude`, `longitude`, `isPrimary` and unknown keys |
| `tax_info` | String or numeric tax-identifier, tax-rate and tax-amount values | Unknown keys and nested objects |

A kept value must be a string, number or null; another type drops the key. The reducer is idempotent. It runs before the section's survivor inventory is taken, so `buyer_block` evidence names columns that hold only reduced values, and G6's planted-marker proof fails if any dropped key survives. `sales-privacy.test.ts` plants email, phone, preferred name, job title, department, website, coordinates, CRM address id, purpose and an extra passthrough key in each snapshot and asserts that only the allowlisted keys remain, unchanged, and that a second run changes nothing.

**Orderless documents.** Invoices, credit memos and payments may be created without an order (`orderId` is optional in `sales/data/validators.ts`) and carry no customer column. `sales.documents` reaches billing documents only through their order, so orderless rows are unattributed: their lines, metadata and credit-memo reason are not found by any subject. Every `sales.documents` export and erasure report states the tenant's count of orderless invoices, credit memos and payments as unattributed coverage, without their contents, and the rows stay a named C5 baseline remainder (Coverage metadata below). No attribution is guessed from free text.

**Source notification copies.** Erasing a sales document, a pay-link payment or a warranty claim also clears notification copies that name the buyer in colleagues' inboxes. In the same transaction each class calls `notificationService.clearSourceForErasure({ scope, callerModuleId, sourceEntityType, sourceEntityIds, dryRun }, { em })`, the generic notifications seam defined in people-ops coverage, “Source notification copies”, with its own module id, for every record it anonymizes, blanks, reduces or retains: `sales.documents` with `callerModuleId: 'sales'` for `sales:order` and `sales:quote`, `checkout.payments` with `callerModuleId: 'checkout'` for `checkout:checkout_transaction`, and `warranty_claims.claims` with `callerModuleId: 'warranty_claims'` for `warranty_claims:warranty_claim`. The service refuses a source type that does not begin with the caller's module id, so no class can clear another module's copies. A retained branch clears them too, because a notification is not the legal record. The owner returns `{ affected, historyRecords, sections }`; each class unions the history identities and passes the owner's sections through unchanged. A missing seam leaves that section incomplete, as communication coverage specifies for message sources.

Custom values consume C4's “Custom values — `entitiesPrivacyService`”. `listCustomValuesForPrivacy({ scope, entityId, recordIds, after?, limit }, { em? })` returns `{ records: Array<{ recordId: string; organizationId: string | null; values: Record<string, unknown>; recordIdentities: Array<{ table: 'custom_field_values'; rowId: string; columns: string[] }> }>, next?: string, done: boolean }`. Prove the served entity/record ids from commerce's own rows, include soft-deleted values and removed definitions, and exhaust scoped pages with at most 100 record ids and a page limit of 100. With `em`, listing uses the caller's transaction and the same scoped value locks as clearing. `clearCustomValuesForPrivacy({ scope, entityId, recordIds, dryRun }, { em })` returns `{ affected: number, historyRecords: PrivacyHistoryRecord[], recordIdentities: Array<{ table: 'custom_field_values'; rowId: string; columns: string[] }> }` and clears only those values in the caller's transaction without a nested commit. Dry run supplies the complete planned history identities and projected survivors; apply returns actual changed history identities and actual survivors, normally `[]` after hard deletion. The listing's exact value-row ids/columns and clearing's survivor identities are owner evidence, never permission to retain fields this policy clears. Union its planned/actual `entities.custom_field_value` histories and containing owner snapshots into R3-1's footprint; schedule the owning field/index/cache side effects after commit. Missing service, malformed/unexhausted pages, ambiguous tenant-less values or failed decryption refuse affected apply or make export incomplete; no class reads entities tables.

Attachment releases consume C4's attachments contract: `releaseForRecord` and `releaseByIds` take trailing `{ em, dryRun?: boolean }` options, return planned/actual `historyRecords: PrivacyHistoryRecord[]` and survivor `recordIdentities: Array<{ table: string; rowId: string; columns: string[] }>` alongside released/pending/retained/skipped files, and use the caller's transaction without a nested commit. Union every owner-returned attachment history identity into the class footprint; current assignments are embedded in `attachments.storage_metadata` and use `attachments.attachment`, never an inferred assignment id. Map surviving row ids/columns only to the matching declared retained-file section and reason. Missing/truncated identities or changed ownership require replan before writes; pending bytes remain incomplete. No commerce class reads attachment tables.

**Cart write admission.** When a cart cannot be deleted, set server-only `carts.privacy_blanked_at` in the same owner transaction as token rotation, buyer/contact clearing and soft deletion of lines. The marker is permanent. Every cart mutation that can add identifying or replay content, including storefront lines, promotions, merge, checkout callbacks and owner replay paths, takes the same scoped cart row lock used by blanking and rechecks a fresh row immediately before its writes. Keep existing lock/status guards and treat a missing or privacy-blanked cart as the existing unavailable cart, without new identifying effects. A stale token resolution, preloaded active status or queued cart id cannot authorize writes. Hold the row lock through data/idempotency commit and enqueue only out of the successful transaction. Multi-cart writers use their stable cart lock order and recheck every target before mutation. An ingest that commits first is included in the erasure; if blanking commits first, the writer refuses without restoring lines, buyer data or executable replay state.

**Cart replay stores.** Find merge logs by source, target or proposal cart, including the survivor buyer context nested in `source_snapshot`. Remove all buyer ids/contact fields, personal line snapshots, metadata and replay payloads, null `merged_by_actor_id`, and set new `privacy_stripped_at`. Preserve only merge topology and numeric dispositions. `restoreCartMerge` and the merge-undo command re-read that mark under the same locks as privacy and refuse a stripped merge with 410, including an undo that loaded the row earlier. Delete all idempotency rows for the affected carts, including their response bodies. These edited merge logs are history records even if another person's basket survives the merge. A locked basket keeps its replay stores until it can be processed.

### Provider services, export and concurrent writes

`paymentGatewayService` gains the following additive methods. All accept `PrivacyScope`, enforce tenant plus the optional organization rule, and take a trailing `{ em }` option: the caller's transactional fork. The DI registration in `payment_gateways/di.ts` closes over the scoped `cradle.em`, which is not the caller's transaction, so every read and write of these methods uses the passed `em`, mirroring the custom-value and attachment seams; a mutating call without `em` is refused. No class reads a provider table directly.

| Method | Contract |
|---|---|
| `exportForPayments({ scope, paymentIds, maxRecords }, { em })` | Returns `{ records, truncated, recordIdentities }` with transaction ids, provider, status, amounts, dates, provider-owned exported payer fields, sanitized webhook entries and safe operation results. Secrets, authentication material and launch grants never leave the service |
| `reduceForRetention({ scope, paymentIds, dryRun }, { em })` | Reduces provider metadata, webhook copies and operation results to the verified refund/reconciliation allowlist; clears client secret and redirect URL; sets `privacy_reduced_at`; returns `{ affected, historyRecords, recordIdentities }` |
| `clearForErasure({ scope, paymentIds, dryRun }, { em })` | Clears personal copies and sets `anonymized_at`; returns `{ affected, historyRecords, recordIdentities }` for every changed transaction/operation |
| `listTransactionsForOrders({ scope, orderIds }, { em })` | Phase 6. Returns `{ transactions: Array<{ orderId: string, paymentId: string }> }` for `gateway_transactions` whose new `order_id` matches, so `sales.documents` can pass those payment ids to the three methods above |

Add optional `exportForPrivacy` and `reduceForPrivacy` adapter methods to `GatewayAdapter` in `packages/shared/src/modules/payment_gateways/types.ts`; provider packages implement them. They are local, pure mappings over stored metadata, operation results and webhook entries, with zod-validated outputs. `exportForPrivacy` includes stored payer-related fields while removing provider secrets; it does not call the provider. `reduceForPrivacy` allowlists only provider/session/charge/refund ids, typed status, amount and currency fields. Unknown keys, arbitrary notes, form posts, launch grants, URLs and embedded presentation payloads are dropped. Safe operation replay envelopes preserve typed ids, status and amounts, without personal blobs. Stripe's existing adapters use the intent id to refund; Autopay's adapter resolves its remote id from the session id through its status lookup. Tpay keeps only `providerStatus` and drops the free-text `title`; its status lookup uses `provider_session_id`, a column the reduction keeps, and it supports no refund today. Unit tests verify the Autopay and Stripe refund paths and the Tpay status lookup after reduction with fake clients. No provider-specific policy goes into core.

Every first-party gateway package ships both mappers in Phase 3: `gateway-autopay`, `gateway-stripe` and `gateway-tpay`, plus the example module's `mock` adapter (`apps/mercato/src/modules/example/lib/mock-gateway-adapter.ts` and its create-app template copy) that the integration tests use. Phase 3 is not done while an enabled first-party provider lacks either mapper; `privacy-mapping.test.ts` enumerates the registered first-party adapters and fails on a missing one.

For these host service methods, `recordIdentities` is an array of `{ table: string, rowId: string, columns: string[] }` over the service's actual scoped transaction/operation rows, including unchanged rows whose personal subset remains open. It contains identifiers/column names only. Read-only export supplies the pre-write inventory for the open-payment branch; dry-run reduction/clearing supplies its full planned `historyRecords` and survivor inventory without writes; apply returns actual history and surviving row identities. Checkout intersects the survivor columns with its branch's retained declarations, stamps the reason/section, and produces `retainedRecords`; the identity inventory alone grants no permission. A truncated export or incomplete identity inventory refuses erasure planning rather than silently omitting a row. Ordinary subject exports serialize only the safe `records` sections, not this internal planning member.

Both optional adapter methods receive `{ providerData: unknown, webhookLog: unknown, operationResults: unknown }` and return `{ providerData: Record<string, unknown>, webhookLog: Array<Record<string, unknown>>, operationResults: Array<Record<string, unknown>> }`. `providerData` is the whole stored `gateway_metadata` object: the session's `providerData` and `clientSession`, `statusResult`, `captureResult`/`refundResult`, and every webhook `event.data` key that `syncTransactionStatus` merged in unprefixed. Payer details a provider sends in a webhook therefore arrive here, not in `webhookLog`, which carries only event type, receipt time, idempotency key, unified status and processed flag. Provider-owned zod schemas validate each allowed output field; the generic shape alone is not the safety boundary. Reduction is idempotent, so already-reduced input yields the same output.

An installed provider without its mapper causes export to report a class failure and aggregate `complete: false`; its omitted provider store is a named export limit, never a complete gateway section. Erasure's `checkErasable` refuses before any writes when reduction/export support required for matched rows is absent, so a third-party provider package without mappers blocks erasure, not only export, of every subject with a payment through it until the package ships them. Optional adapter methods leave ordinary payment calls unchanged.

Every metadata, operation-result or webhook-log write in session finalization, polling, webhooks, capture, refund and cancellation re-reads the transaction under `PESSIMISTIC_WRITE` with refresh immediately before writing. Privacy reduction/clearing takes that same lock. Network calls may run outside it; their stale entity is never flushed back. A reduced row accepts only mapper-approved fields; an anonymized row accepts no personal data. Both marks preserve allowed status transitions, amount accounting, webhook deduplication and safe replay ids. Re-check in-flight operation completion too. Thus a successful webhook or poll racing an open payment's erasure still completes it; a later poll cannot refill a cleared payment.

**Sessions-route coverage (Phase 6).** Phases 1–5 reach only checkout-originated gateway rows. Phase 6 of this spec is the carrier for the rest of `gateway_transactions` and `gateway_payment_operations`, created by `POST /api/payment_gateways/sessions` and any other `createPaymentSession` caller; `payment_gateways` and `sales` own it, and #8593 cannot close before it ships. It has two parts:

1. **Order link.** `gateway_transactions` gains nullable `order_id`, and `createGatewayTransaction` persists the `orderId` that `createPaymentSession` already validates and reconciles against the order total. `sales.documents` calls `listTransactionsForOrders` for its matched orders and passes those payment ids through the three methods above, following the order's branch: reduce for a retained order, clear for an anonymized one, the open-case rule for a non-terminal transaction. Rows created before Phase 6 have no stored order id and are not backfilled; they fall to part 2.
2. **Bounded remainder.** A gateway-owned record set, `payment_gateways.idle_transactions` (Settings and retention sets below), reduces every transaction not yet reduced or anonymized whose `updated_at` is older than the caller window, whatever created it, through the same provider mappers, once proven non-resumable as defined below. After reduction a row holds only operational ids, status and amounts, and a late webhook or poll still matches by provider id. Age and quiet alone do not establish expiry. The owner requires durable terminal/non-resumable evidence from a verified provider mapping or provider-confirmed irreversible session expiry. Pending, authorized, unknown and any other potentially resumable state is skipped unless that evidence specifically proves the launch session cannot resume and required capture/refund coordinates remain. Unsupported, stale, unavailable or contradictory provider evidence is an explicit unbounded gap. Verify provider state outside owner locks, bind the evidence to the transaction and provider-session revision/fingerprint, then compare both and recheck eligibility under lock before writing. Discard evidence after any mismatch and retry later. An authorized or captured operation whose remaining settlement obligations depend on removed data remains ineligible. Existing replay keys still identify the original session and never create a new charge after reduction. Status and replay preserve their response schemas and the provider-confirmed final state; only now-unusable launch information is removed.

With both parts shipped, each table declares whole-table `retention_bounded` with `boundedBy: 'payment_gateways.idle_transactions'` and its surviving operational columns, and leaves the baseline; the checkout and sales seams remain the subject export and erase path. Until then both tables stay whole-table baseline entries with this backlog named, and no full gateway coverage is claimed. Rows without a mapper or verified non-resumability evidence are skipped and counted in every set report. The bound states the affected subset as unbounded and Known limits names it. No `sales_payments`-to-gateway link is claimed.

The optional Phase 6 owner-validated adapter method `checkIdleReductionEligibility({ providerSessionId, storedStatus, revision })` returns `{ status: 'non_resumable', terminalStatus, verifiedAt }` or `{ status: 'resumable' | 'unknown', reason }`. Use an authoritative provider observation or a provider-documented irreversible terminal status already present in a verified event. Bind the observation to the original session and revision and validate it with Zod. Verify again on mismatch; no fallback from age or an unverified local status alone. Bound remote calls by owner batch budget and timeout; timeout is unknown. The count-only C5 evaluator never calls the provider: consume only valid owner evidence for the observed row, including its revision, or report unknown/unbounded. Persist any evidence needed by the evaluator as owner-reviewed minimal enum, time and revision metadata, never provider response bodies. No existing required adapter signature changes. The Phase 6 implementation and each first-party provider test must establish its own irreversible-state rules and preservation of needed settlement fields or mark it unsupported.

**Pre-flight.** `checkout.payments.checkErasable` and `sales.documents.checkErasable` (gateway rows from Phase 6) resolve the required provider seams and inspect method availability for matched records. A disabled peer with no persisted dependants needs no seam. An enabled peer lacking a method, an unavailable provider mapper, or an unavailable service needed to establish whether dependants exist refuses the subject before the host's hash or aliases are cleared. Unexpected runtime failures roll back the batch and leave the subject incomplete (exit 2), rather than inventing a section outcome. File deletion failures are counted in `filesPending` through the attachments contract.

**Pages.** “Complete” means the union over every page of C4's rule 1 until the class reports `done`, not one call. Each mutation transaction changes at most 500 rows of one section (`PRIVACY_ERASURE_PAGE_ROWS`), and a class with more returns C4's opaque `next` with `done: false`; dry run plans the same pages. A document or payment commits with its own child and provider rows in one page; a page ends before the document or payment that would take any section past 500 rows, and one whose rows alone exceed the bound pages its children before its own header write. Each page is idempotent because the class recomputes candidates from current data, so a crash between pages resumes from the last checkpoint without repeating or skipping a row. `cart.baskets` and `warranty_claims.claims` page by the same rule over their own tables; promotions and customer groups need a second page only past the bound.

A later retention batch must strip history written since the original erasure. Handlers enqueue releases in their transaction; preview never drains and neither the handler nor an enterprise caller adds a second drain.

### Alternatives considered

| Alternative | Why rejected |
|---|---|
| Delete numbered commercial documents | Their totals and numbering must survive |
| Retain whole provider blobs for refunds | Verified adapters refund through operational ids; personal echoed fields and launch grants are unnecessary |
| Match an identifier hold to an email hash | DEC-A ids match no stored lookup column; exclusion carries no alias |
| Finish retained records through a second subject erasure | An email-only claimant may never be requested again; marked-record sets need no identifier input |
| Treat every non-completed payment as safe to blank | Pending/processing can still complete at the provider |
| Report an absent peer method as a pending section | It is outside the closed outcome set and may orphan provider data after the host hash is cleared |
| Hold every protected order for manual review before erasure | Every erasure would wait on a person, although the four retention signals of assumption 1 are recorded in the product |
| Ship a default legal age | Periods differ by jurisdiction and record type; a wrong default either deletes records a controller must keep or keeps them too long |
| Keep an encrypted source email, or a per-row secret fingerprint, so a retained hash survives a secret change | The first keeps the email the reduced block excludes; the second adds a column and a shared helper for a rare maintenance event. The record stays retained and its set still ends it |
| Leave a stale retained hash after a secret change | It matches nothing, and anyone holding a leaked old secret can still test addresses against it |

### Known limits

- A class released after its owner was already anonymized cannot recover old email aliases. Id-linked records are still reachable.
- Address-only subjects sharing an address remain indistinguishable. Never override a known other person's id link merely because the address matches.
- Old company-account claims cannot be attributed to a portal author whose id was never stored.
- Until Phase 6 ships, sessions-route gateway rows remain an explicit baseline/backlog gap and export reports identify it; no full gateway coverage is claimed. Phase 6 links new rows to their order; rows created before it, and session-route rows created without an order, are reached by no subject and keep their payer data until `payment_gateways.idle_transactions` reduces them, which needs an operator run in OSS. Rows without a mapper or verified non-resumability are not reduced and remain a named unbounded gap in each set report.
- Sales history for documents deleted before related-person stamps existed, deleted guest documents, and a company's contact copies cannot all be found. Reports state the history gap; enterprise age retention may bound it.
- An installed provider package without both mappers makes exports incomplete and refuses erasure, in pre-flight, of every subject with a payment through it, until the package ships them; first-party packages ship them in Phase 3. External provider copies and carrier-side labels are outside local erasure.
- Commerce matches identifier subjects by email hash only. A phone-only identifier subject (`--phone`) finds no guest order, basket, pay-link payment or claim; each commerce export section reports `ALIASES_NOT_AVAILABLE` and every identifier run report names the limit.
- Until a module's phase ships its tenant-export readers, a tenant export reports that module's tables as named `reader_unavailable` gaps, so a complete handover (exit 0) needs every enabled commerce phase.
- Orderless invoices, credit memos and payments carry no customer or order link and are reached by no subject; reports state their count and the rows stay a C5 baseline remainder.
- Notification copies sent before erasure are cleared for colleagues' inboxes; copies already delivered to devices or by email cannot be recalled.
- Identifier holds freeze the sales set; any hold freezes the other four sets. Without an OSS scheduler, retained records remain until the operator runs the relevant set.
- A legally retained order or completed payment keeps its email hash after its source email has been cleared, so R5-7 cannot refresh that hash after a lookup-secret change. The owning fill clears it under B1's null-source rule (API Contracts). The record stays retained and its set still blanks it, and a linked order stays reachable through its anonymized owner's id, but a later request by email no longer finds it.

- THEN `sales.retained_orders` skips with `hold_not_honourable` and blanks no order

##### Scenario: An edit after erasure
- WHEN a retained order is edited and its retention set later blanks it
- THEN the newer header and child audit copies are stripped in that batch and cannot undo or redo

##### Scenario: Provider completion races erasure
- WHEN a pending payment's erasure races a successful poll or webhook
- THEN the refreshed locked status chooses the branch: still pending/processing is `open_case`, already completed uses the completed-payment rule. Completion still applies, and any open-case mark is handled by the terminal follow-up

##### Scenario: Provider data returns late
- WHEN a poll, webhook or operation result started before provider data was cleared
- THEN its refreshed write preserves the mark, keeps personal fields empty and applies valid status/accounting changes

##### Scenario: A carrier shipment on a draft order
- WHEN the draft order has a non-cancelled carrier shipment
- THEN it is retained with its label; after the age its set clears the label and future polls cannot refill locations

##### Scenario: Personal free text and replay
- WHEN an order has a name in line descriptions/metadata or a basket has identity in a merge snapshot and idempotency response
- THEN these copies are cleared, and the stripped merge cannot be undone

##### Scenario: Missing seam
- WHEN a matched gateway or carrier dependency lacks a privacy method in pre-flight
- THEN the subject is refused before host, provider or hash changes

##### Scenario: Retained buyer block
- WHEN an invoiced order is retained and its snapshots hold an email, phone, job title, coordinates and an unknown key
- THEN only the allowlisted name, company, postal and tax-id keys remain in `customer_snapshot`, both address snapshots and `tax_info`

##### Scenario: An erased claim is reopened
- WHEN a closed claim has been blanked and someone moves it back to `in_review`
- THEN the transition is refused with `warranty_claims.errors.claimErased` and the claim stays closed

##### Scenario: A buyer with many documents
- WHEN a customer has more than 500 sales documents and the run stops after a committed page
- THEN each page changed at most 500 rows of one section, the dry run's `historyRecords` are the union of every page, and the re-run resumes from the checkpoint and finishes without repeating or skipping a document

##### Scenario: A sessions-route payment
- WHEN `POST /api/payment_gateways/sessions` created a payment with an `orderId` and that order's buyer is erased
- THEN the gateway row follows the order's branch; a payment created without an order is reduced by `payment_gateways.idle_transactions` once idle past the window

## 📝 Architecture

Each module owns its classes, hashes, blankers and `privacy.ts` declarations. Collectors use the whole default export under R3-2. Module settings consume R3-3; the module-owned database checks consume R3-4/R4-7 and complement `privacy.retention_settings_unset`, without module-specific storage. Aliases and owner locking remain in the contract/erasure specs. Aliases/identifiers require contract Phase 6; the age declarations/service require its “Phase 7 — Settings and bounded export evidence”. Provider packages supply pure export/reduction mappings; hosts use DI seams. No cross-module ORM/table access is introduced.

|---|---|---|

## 📝 API Contracts

- Use the erasure spec's existing `retainedUntil?: string | null` and `retentionSetId?: string` on retained sections, in dry run, completed audit and CLI output. No separate `retainUntil` spelling or new local outcome. `open_case` without a date uses null.
- Settings, sets, provider methods and optional adapter mappings are the additive contracts specified above. Validate every new input/output with zod; bound id batches per service call and listing pages to at most 100. Erasure mutation pages follow C4's rule 1 instead: at most 500 rows of one section per transaction (`PRIVACY_ERASURE_PAGE_ROWS`, “Pages” above).
- Carrier signatures are `exportForOrders({ scope, orderIds, maxRecords }, { em })` → `{ records, truncated, recordIdentities }`, `retentionForOrders({ scope, orderIds }, { em })` → `{ orders: Array<{ orderId: string, hasNonCancelledShipment: boolean }> }`, and `reduceForRetention({ scope, orderIds, dryRun }, { em })` / `clearForErasure({ scope, orderIds, dryRun }, { em })` → `{ affected, historyRecords, recordIdentities }`; all use zod-validated bounded ids and outputs. Carrier `recordIdentities` uses the same identity-only shape above for actual shipment/idempotency rows; dry-run gives the planned history/survivors and apply the actual survivors, which sales maps into its declared sections.
- Gateway/carrier methods receive full `PrivacyScope`: tenant required; organization absent means all in the tenant, present means it plus organization-less rows. Every method takes a trailing `{ em }` and uses that caller transaction for reads and writes, never the scoped `cradle.em` its DI registration closes over and never an independently committed inner transaction; a mutating call without `em` is refused. Unit tests with the host roll back the host transaction and assert no gateway or carrier change survives.
- New `mercato {sales,cart,checkout,warranty_claims} fill-privacy-hashes --tenant <id> [--after <id>] [--batch-size <1..100>] [--apply]` commands require one explicit tenant. No implicit all-tenant decryption. Preview is default and writes neither database nor KMS; apply uses UUID keyset batches and a bounded transaction per batch with row locks/rechecks. Empty targets use C1's initial-fill writer; stale populated targets use the B1 maintenance updater below under R5-7, without an extra CLI flag. Resume returns an opaque last-id cursor and per-tenant scanned/filled/cleared/skipped counts, never plaintext or hashes. A new invocation from the start catches earlier-id rows inserted during a fill. Missing keys or lookup secret fail before mutation. The contract's bounded empty-hash fallback remains until initial fill completes; it cannot repair stale populated hashes after a secret change.
- **Non-empty hash maintenance:** classify current, old-keyed, legacy-unkeyed, null and unrecognised forms from verified decrypted source. Preserve current hashes and repair stale non-null hashes under the current secret. Old-secret precedence is B1's `LOOKUP_HASH_OLD_PEPPER`, then `TENANT_DATA_ENCRYPTION_OLD_KEY`, never a flag. Apply B1's “Maintenance write safety”: each conditional update compares the primary key, exact tenant, null-safe actual organization and every read source/target column; use per-row savepoints, preserve `updated_at` and write no protected-value command snapshot. Unreadable ciphertext, collision or concurrent change preserves the row and leaves maintenance incomplete with a non-zero exit. Ordinary application, queue, scheduler and token writers stay stopped through the fills and B1's verification gates; verify a repeat report from the beginning before traffic resumes.
- **Source-less retained hashes:** a legally retained order or completed payment keeps `sales_orders.customer_email_hash` or `checkout_transactions.email_hash` after its source email is cleared. With no source the fill can neither classify nor refresh that hash, so it applies B1's null-source rule: preview counts the row and apply clears only the hash under the same conditional write, leaving the privacy mark, the retained block and `updated_at` unchanged. These rows count as `cleared`, not as incomplete work. No source email is kept to rebuild the hash. Operators run each fill at its first deployment and after a lookup-secret change, as B1's runbook lists; an extra run ends email lookup of retained records early, never their retention.
- `gateway_transactions.order_id` is internal in Phase 6: the sessions route keeps its request and response shapes, and the transactions API gains no field. The warranty transition route gains the 409 `warranty_claims.errors.claimErased` response for a reopen of an `anonymized_at` claim, documented in its OpenAPI.
- The warranty claim response/OpenAPI gains `createdByCustomerUserId`; portal POST sets it from authenticated customer-user identity, never client input. Email intake uses a shared non-address placeholder instead of email as `customer_name`.
- All new user-visible labels, refusal and settings messages use locale keys. No new UI page is added by this spec.

## 📝 Edge Cases & Failure Scenarios

| Case | Behaviour |
|---|---|
| Retention setting unset or window too short | Legal set refuses; report names exact setting/command; `doctor --database` warns |
| Lookup secret changes with populated commerce hashes | R5-7 re-runs each deployed owning fill through B1 maintenance, refreshing stale non-null hashes from readable sources; incomplete work keeps traffic stopped |
| Retained hash whose source email was cleared | The fill clears that hash and counts it as cleared; the record stays retained and its set still ends it |
| Pending payment becomes terminal during apply | Lock/re-read determines current branch; never suppress provider completion |
| Held closed claim | Stays marked; later set invocation can process it after exclusions end |
| Claim reopens during pruning | Lock/re-read sees nonterminal state and skips; no generic status write or lifecycle bypass |
| Reopen of a blanked closed claim | The transition command re-reads `anonymized_at` under the claim lock and refuses with 409 `warranty_claims.errors.claimErased` |
| Claim left `resolved` or `rejected` | Stays `open_case` with null end; the run report lists it so an operator can close it |
| Payment or shipment with a tenant-defined or null status | Counts as a retention signal; the dry run names it |
| Several document addresses match one retained snapshot | Keep the lowest id; delete the rest |
| Crash between erasure pages of a heavy buyer | The subject stays incomplete under the account lock; the re-run resumes from the last committed page, recomputing candidates from current data |
| Cart that FKs prevent deleting | Blank it with `buyer_digest = ''`, a fresh random `token_hash` and `privacy_blanked_at`; the old token stops resolving and even an already-authorized request fails the locked write check. Its live lines are soft-deleted in the update that nulls `configuration`, so same-product lines that differed only by configuration do not violate `cart_lines_unique_line_key` |
| Idle gateway set meets a provider without a mapper | Skips and counts those rows; reports them as the bound's unbounded remainder |
| Phone-only identifier subject | Commerce sections report `ALIASES_NOT_AVAILABLE`; export is not complete |
| Provider unavailable in pre-flight | Refuse before clearing lookup hashes or host records |
| Late provider or carrier response | Re-read under lock and apply the current privacy mark to stored and returned data |
| Audit-strip failure in a later set | Roll back blanking and retain mark for retry |
| File deletion failure | Logical release is durable; count `filesPending`, using record-retention R3-8 for draining |
| Four cart restrict FKs block deletion | Blank the basket; strip merge replay stores and refuse their undo |
| Portal user with no linked person | Its email aliases still reach sales/checkout; unrelated id-linked buyer is excluded |
