## Findings

### High

**1. `is_personalized` / `personalization_reason` on sales lines can never be populated**
`packages/core/src/modules/sales/lib/omnibusSnapshot.ts:124`

`applyOmnibusSnapshotToLine` calls `readOmnibusPersonalization(block)`, which reads `isPersonalized`
and `personalizationReason` off the value returned by `resolveOmnibusBlock`. That value is an
`OmnibusBlock` (`omnibusTypes.ts:96-113`) and `OmnibusBlock` has no such fields — personalization
lives in the separate `OmnibusPersonalization` type and is written only onto products-list items in
`decorateProductsWithOmnibus`. `readOmnibusPersonalization` therefore returns `null` on every real
call, and the two new columns on `sales_order_lines` / `sales_quote_lines` will be `NULL` forever.

The unit test at `omnibusSnapshot.test.ts:146` passes only because it mocks `resolveOmnibusBlock` to
return an object that includes `isPersonalized` — a shape the production service never produces.

Fix: thread the request-level personalization decision into `applyOmnibusSnapshotToLine` explicitly,
or extend `resolveOmnibusBlock` to return it. Add a test that exercises the real service.

**2. The in-window scan silently truncates to 1000 rows and can return a wrong reference price**
`catalogOmnibusService.ts:34`, `:376-393`

`fetchInWindow` orders `recordedAt DESC` and caps at `IN_WINDOW_ROW_CAP = 1000`. Rows dropped are the
**oldest** in the window — precisely the ones most likely to hold the minimum. Nothing signals this:
`insufficientHistory` is driven by the separately fetched baseline, so a truncated scan still reports
`insufficientHistory: false` and a fully-applicable block.

Fix: aggregate (`MIN` over the axis with the EC-7 exclusion pushed into SQL), which removes the cap
entirely. At minimum, detect `rows.length === IN_WINDOW_ROW_CAP`, set `insufficientHistory`, and log.

**3. Withdrawn and undone prices are counted as valid reference candidates**
`catalogOmnibusService.ts:195-197`, `commands/prices.ts:525`

The candidate set is filtered only by EC-7 and the anchor bound; it never inspects `change_type`.

- `delete` (`prices.ts:926`) records the price as it was when removed — it then competes to become
  the reference for a price that no longer exists.
- Undo of a **create** (`prices.ts:525`) passes the `after` snapshot with `changeType: 'undo'`, i.e.
  it records the value of the price being *removed*. A fat-fingered price that is immediately undone
  becomes a permanent reference candidate. Undo of `update` (`:879`) and `delete` (`:1015`) correctly
  record the `before` snapshot, so create-undo is the odd one out.

Fix: exclude `delete` and `undo` from the candidate set, or record create-undo as a tombstone and
filter tombstones out.

**4. Per-row query fan-out on the products list**
`api/products/route.ts:394-480`

`decorateProductsWithOmnibus` runs `Promise.all` per item. Each iteration: `resolvePresentedPrice`
(price-kind lookup memoized, plus an unmemoized `CatalogProductPrice` query and an unmemoized
`CatalogPriceHistoryEntry` query) then `resolveOmnibusBlock` (baseline + in-window, plus up to two
more). At `pageSize` 100 that is ~400–600 concurrent queries on one forked `EntityManager`. The
neighbouring pricing/unit-conversion enrichment in the same hook is deliberately batched.

Fix: batch presented-price and history lookups by `(productId, priceKindId, currencyCode)`.

### Medium

**5. A repo-wide Turborepo configuration change is bundled into a catalog feature PR** — `turbo.json:14`
Split `turbo.json`, `scripts/dev-ephemeral.ts` and `.ai/skills/om-prepare-test-env/SKILL.md` into a
separate infrastructure PR. Also: `turbo.json` now carries `//` comments — Turborepo's JSONC parser
accepts them, but anything reaching for `JSON.parse` will break.

**6. `CatalogOmnibusService` is referenced but never imported**
`sales/commands/documents.ts:3182`, `:3274`, `:3361`, `:3500`
Four signatures annotate a parameter as `CatalogOmnibusService | null`; the type is not imported.
Only `// @ts-nocheck` on line 1 keeps it compiling. Add the `import type`.

**7. Unbounded history fetch in the progressive-reduction path** — `catalogOmnibusService.ts:426-432`
`resolveProgressiveReduction` loads every history row for the offer with no `limit`.

**8. Existing tenants silently lose the new settings panel until an operator runs the ACL sync**
`api/settings/route.ts:104`, `:157`
Call the required `yarn mercato auth sync-role-acls` out in the PR description / `UPGRADE_NOTES.md`,
or add a `configs` upgrade action. Related: `PUT` requires only `catalog.settings.manage`, so a role
with `manage` but not `view` can write a config it cannot read back.

**9. The immutability trigger function is created under an unqualified, generic name**
`Migration20260721120100.ts:76`, `:97`
`prevent_history_modification()` in the default search path; `down()` drops it unconditionally.
Rename to e.g. `catalog_prevent_price_history_modification()`.

### Low

**10. The implemented spec is still filed as awaiting implementation** — `.ai/specs/README.md:106`
Move to `.ai/specs/implemented/` and move the README row to match.

**11. A cache tag is written but never invalidated** — `lib/omnibus.ts:121`
`buildOmnibusCacheTags` returns prefix + product + variant tags; `invalidateOmnibusCache` filters the
prefix out, so a scope with neither id invalidates nothing and returns silently. Unreachable today.
