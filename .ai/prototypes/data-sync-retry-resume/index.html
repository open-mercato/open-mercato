Data Sync — Retry vs Resume — screen inventory

Interactive backend screens derived from .ai/prototypes/data-sync-retry-resume/REQUIREMENTS.md. The shell, page scaffolding, DataTable chrome, and CrudForm layout mirror packages/ui/src/backend/; colors and spacing come from globals.css. Every screen lists its requirement and user-story coverage. All data is fictional. Nothing here is implemented — it is a proposal to accept or reject.

1. Action model by run state

The single table the rest of the prototype draws. Read this first; every later screen is one cell of it.

Why not two peer buttons named Resume and Retry To an operator they are synonyms; they would have to learn which is which every time. The rare action is presented as a modifier of the common one, and the common one explains itself in a helper line. If peer buttons are ever wanted, the only unambiguous pair is Resume / Restart — never Resume / Retry.
1“Retry” always creates a new sync_runs row with fresh counters and a new progress job. No screen in this prototype implies the original row changes — and no screen can currently link the two, because there is no retried_from_run_id column. That gap is listed in §4 of the requirements.
2The last row is a finding, not a design: paused is in the status union, the validator, the entity and the badge map, but nothing in sync-engine.ts or sync-run-service.ts ever writes it. Either produce it or drop it; the prototype shows no actions for it.

1The dialog's job is to make the cost concrete: it names the record count, the batch the resumable retry would have started at, and the batch this one starts at. A generic “Are you sure?” would teach operators to click through it.
2The confirm button is not destructive-styled. Nothing is deleted — a full replay updates matched records. Using destructive here would spend the red budget the real destructive action (Cancel run) needs.

2“Run as full sync” is shown on, because arriving here from a completed run usually means “do the whole thing again”.
