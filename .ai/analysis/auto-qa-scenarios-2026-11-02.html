P0 — AI approval, delegated permissions and search privacy

AI writes now require the staged approval path, creator ownership, current tool permissions and the exact record version previewed. Delegated keys are bounded by the owner's live ACL, and search/web research suppresses sensitive fields and policy-denied content, including redirects and provider synthesis. Use deterministic test tools or fixtures where possible; optional orchestrator adapters and credential-isolated API requests are prerequisites for the adversarial checks.

  • /backend/catalog/products → edit the same product in a second browser session
  • /backend/config/ai-assistant/playground → run a read tool and a staged mutation

What human QA should verify

  • Direct mutation boundary: in a credential-isolated API client call POST /api/ai_assistant/tools/execute for a server-registered mutation tool, including forged approval fields and a superadmin actor. Expect 403 and no write. A permitted read tool still returns results, and a normal chat-generated approval card can be confirmed through the staged action route (#8304).
  • Creator boundary: user A stages a pending product update and shares the conversation with same-organization user B. B cannot read, confirm or cancel A's action, even with its ID (404); A retains access. Before A confirms, revoke the tool's manage feature and expect 403 tool_features_denied with no mutation (#7329).
  • Stale bulk preview: stage updates to two products, edit one manually in a second session, then confirm. Only the unchanged previewed row is updated; the manually edited row retains its human value and is reported stale_version. If every row is stale, confirm returns 412 and writes nothing. Race a second edit between recheck and write to exercise the optimistic-lock boundary (#7428).
  • Delegated-key ceiling: issue a disposable AI/MCP session key to a user with a narrower UserAcl than its roles, remove a role or organization grant, and retry a privileged read/write using the already-warmed key. It must immediately respect the narrower current feature/organization scope; a foreign owner binding, deactivated owner or changed home organization must not preserve old authority (#8086, #8034, #8245). Legacy persistent MCP keys require revoke/regenerate and client-secret updates.
  • Search privacy: create a person/company and an encrypted custom field containing unique synthetic email/phone and secret markers. Reindex using the supported environment process. Global search and AI search_get may show permitted business fields but must not expose excluded/hash-only custom-field values, including cf_ and cf: aliases; inspect embedding/presenter evidence to ensure protected values never enter plaintext vector sources. Test with encryption-definition lookup unavailable: plaintext custom fields must fail closed (#8081, #8079, #8043).
  • Web search policy: configure an agent allow/deny domain rule and an allowed test page that redirects to a denied controlled destination. includeContent must not fetch/contact or return the denied destination, and a cached enriched result must not bypass a new policy. Explicit browser rendering under restrictions must fail closed; allowed HTTP sources remain usable (#8215).
  • Provider synthesis: repeat web-search preview and agent execution with any nonempty domain policy, including a cached result. The top-level synthesized answer is null with diagnostics.answerWithheld=domain_policy, while permitted source links remain available. Unrestricted-policy synthesis retains normal behavior; privileged raw adapter-comparison data must not appear in agent context (#8378).
  • Network boundary (controlled test harness): make Code Mode api.request() encounter 301/302/303/307/308 and same-origin chained redirects; it returns a safe error with the original redirect status and does not forward credentials, scope headers, request bodies or redirect contents. Local-use IPv6 page targets must be blocked. The MCP dev/HTTP server defaults to loopback; test from an independent machine that it is unreachable unless the operator explicitly configured exposure (#8146, #7998, #6712).
  • Business Rules ceiling: as a restricted rule author, the CALL_OPEN_MERCATO profile selector must omit ungrantable, AI-session and one-time keys. Revoke the author's role after saving an eligible rule, then run it: execution must fail closed before minting a more privileged temporary key. A permitted profile still executes the intended scoped action (#7320).
  • Global catalogues/session-secret storage: after supported reindexing, declared platform-wide catalogue entries remain findable with an organization selected, without duplicate legacy projections; an undeclared tenant-less type remains hidden. In operator-only storage inspection for a disposable AI session, persist only the token hash and a non-secret name, while its issued token still authenticates and expiry/revocation work; never include tokens in evidence (#8287, #7177).

What can go wrong

  • A shared-conversation participant confirms another user's mutation, a stale bulk row is overwritten, or a direct tool endpoint bypasses approval.
  • Revoked owner grants remain effective through cached AI keys or Business Rules profiles.
  • Sensitive custom fields reach a search presenter or embedding, or denied web content leaks through redirect enrichment, stale caches or provider-generated answers.
  • Search fixes do not erase old external indexes/embeddings automatically; apply each PR's upgrade remediation before signing off privacy. MCP and real-provider tests need an explicitly configured isolated environment.
