# GDPR-ready deployments specs — four-model council review

> **Subject:** the 43 files of commit `9e09023483` on `feat/8593-gdpr-ready-deployments-spec` (program spec, audit verification, 39 child specs, 2 supersede notes) for [open-mercato/open-mercato#8593](https://github.com/open-mercato/open-mercato/issues/8593).
> **Council:** Claude Opus 5.5 (fresh context, om-code-review host pass) · GPT-5.6 Sol via Codex (`xhigh`, read-only repo access) · DeepSeek V4 Flash (`high`) · Kimi K3.1 Pro. Run with the `om-harness` runtime, `all-required` policy across three independent provider families.
> **Method:** 8 track-coherent groups, each one immutable review packet (rubric + repository rules + program spec context). Every reviewer saw the same packet; no reviewer saw another's output. Every blocker/major/minor was then de-duplicated and adversarially verified against the spec text and the code by a fresh Opus verifier; severities were recalibrated independently of the reviewers.
> **Date:** 2026-11-16. Design review only; nothing in the repository was changed.

## Verdict

**Request changes on all 8 groups.** 581 raw findings collapsed to **330 verified issues**: **6 critical, 62 high, 175 medium, 87 low**; 46 findings rejected on verification, 27 nits. Issues touch 43 of the 41 spec files.

The program is well structured. Tracks, decisions and carriers are clear, and most claims about today's code checked out. It is not ready to hand to implementers. The defects cluster into six themes, and fixing the first two unblocks most of the rest.

### 1. The erasure core is not durable or complete enough for everything that depends on it

C4 (subject erasure) is the hub that the coverage specs, portal self-service, the DSR engine and restore replay all build on. Its weak points spread to every consumer:

- **Lost events and files.** A crash or a failed emit after commit loses `privacy.subject.erased` for good (g2-04). A file whose deletion fails after commit can never be found again (g2-01, critical). Restore replay and the DSR ledger record an erasure only from that event.
- **The apply step cannot run.** The dry-run confirmation token is keyed by a per-process secret, so the separate `--apply` process cannot check it (g2-02, raised by all four models).
- **Address-only subjects cannot be erased.** People known only by an email address or phone number are promised erasure, but erase rejects identifiers and the identifier subject's id is regenerated every run (g2-03, all four models). Commerce, communication and content-ai send guests, payers and claimants down exactly that path (g3-03), and restore replay marks them applied without re-erasing (g4-02, critical).
- **Consumers assume behaviour C4 does not have.** Portal deletion waits for an account row that C4 keeps, so the request never closes (g4-03). The gateway class needs a "related records" hand-off the contract lacks (g3-02).

### 2. Cross-spec seams that no spec delivers, or that two specs claim

- **Two owners for one thing.** Both `privacy-data-class-contract` and `privacy-doctor-cli` create the `privacy` module. The doctor's extension point is a named export, while the contract fixes a single default-export object (g7-02, all four models).
- **Hand-offs with no carrier.** Work handed to B1 (customers lookup hash, lookup-rehash tool, system-scoped rotation) is delivered by no spec, so A2's enforce flip can never be scheduled (g0-03, g1-04). Doctor checks are delegated to specs that do not contain them (g7-08).
- **Callers and callees disagree.** `applyRetention` lacks the inputs its OSS erasure caller passes (g5-09). The erasure history strip now depends on an enterprise routine while the rest of C4 still designs its own (g2-06).
- **Domains with no owner.** The roll-out gives no domain spec to workflows, shipping_carriers, promotions, customer_groups or the channel and carrier provider packages (g0-04).

### 3. Load-bearing claims about today's code that are false

Each of these is a design resting on code that does not behave as stated:

- **Encryption defaults.** Declared default encryption maps are merged only for system-scoped maps, so existing tenants keep writing vector text in clear (g1-02).
- **Queue cleanup.** The failed-queue sweep runs only for the two data_sync queues, and it uses the failed set as its dead-letter store (g6-04).
- **AI allow-list.** The tenant allow-list has no endpoint field (g6-03), and inbox model resolution falls back to a direct client on factory errors (g6-06).
- **Webhooks.** No tenant-level webhooks exist; organization-less events fan out to every organization (g7-03).
- **Chat attachments.** They are bound to `ai-chat-draft`, not to the conversation, so deleting the conversation releases nothing (g5-01, critical).
- **Messages lookup.** The messages class finds people by `external_email_hash`, which only the encryption service writes (g3-09).
- **Consent test.** The consent test needs a cookie that does not exist (g6-05).
- **Export scope.** The export scope `page` does not exist in the CRUD factory (g7-10).

### 4. New surfaces that introduce security defects

- **Portal lockout broadcast.** `customer_accounts.user.locked` is `portalBroadcast: true`, so emitting it as specified streams every lockout to all portal sessions of the organization: an account-enumeration oracle (g7-01, critical, verified against `customer_accounts/events.ts:7` and the SSE bridge).
- **Path traversal in tenant-exit export.** The export writes `attachments/<id>/<file name>` from a stored name that `sync_excel` and others take verbatim from the client (g3-01, critical, verified at `sync_excel/api/upload/route.ts:149`).
- **DSR organization scoping.** The DSR engine's subject export and erase have no organization check, so an administrator restricted to one organization reaches every organization in the tenant (g4-01, critical).
- **Secrets on the command line.** `scan-values` takes the searched personal value as an argument, and the CLI banner echoes it (g7-05).
- **Key-guard escape hatch.** `OM_DEV_RUNTIME=1` is an operator-settable switch that disables the published-secret refusal (g1-03).

### 5. The privacy machinery creates or keeps data without its own limits

- **Unbounded security tables.** Security signals and alerts have no retention window (g7-04).
- **End dates nothing enforces.** Retained orders and payments get an end date that nothing acts on (g3-04). Kept employment records are never blanked when their age is reached (g3-11).
- **Holds ignored.** Manual record retention ignores legal holds (g5-08). Change-history retention strips held subjects' data by default (g5-10). The DSR engine never skips a record set that cannot honour a hold (g4-05).

### 6. Backward-compatibility claims that do not hold

- **Search wrappers.** The deprecated `tokenizeText`/`hashToken` wrappers change their output, so the "bridge" breaks existing callers (g1-01, all four models).
- **Frozen event payload.** Removing email from `customer_accounts.user.deleted` changes a frozen event payload, yet the compliance matrix says Compliant (g2-07).
- **Counting-period bridge.** The operational pruners' 30-day counting period is called ordinary protocol, contradicting the program's rule for D1 (g5-06).

### Suggested order

1. **Critical issues (6).** Each is a small, local change to one spec.
2. **The erasure core (Theme 1).** Rewrite C4's durability section once: an outbox or retry for the event, a durable record of pending file deletions, a token that survives processes, and a real address-subject path. Then re-check its consumers (portal, DSR, replay, coverage).
3. **Ownership seams (Theme 2).** One decision each: which spec owns the `privacy` module and its export shape, which spec carries each B1 hand-off, and an owner for every uncovered module.
4. **Code-claim corrections (Theme 3).** Then a second pass by one reviewer with repository access over the revised set. The program changelog already says the per-spec revisions were never re-read.

## Critical issues

### g3-01 · CRITICAL · Attachment files are written to a path built from the stored, tenant-controlled file name

- **Where:** [2026-11-16-tenant-exit-export:64](.ai/specs/2026-11-16-tenant-exit-export.md:64) — raised by Opus, DS-Flash, Kimi (confirmed)
- **Problem:** Step 4 writes each file to `attachments/<id>/<file name>` using the stored `file_name`. Nothing in the spec sanitises that name, makes it canonical, or checks that the final path stays under `--out`. Some current write paths store the uploaded name as sent, so a tenant user can store a name like `../../…`. The operator-run export would then write tenant-chosen bytes outside the export directory with the operator's permissions.
- **Evidence:** Spec line 64: "Writes each attachment to `attachments/<id>/<file name>`." The only output-directory rule is line 201: "The output directory exists and is not empty \| Refused". Code: `attachments/data/entities.ts:80` (`file_name` text). Unsanitised writers: `sync_excel/api/upload/route.ts:149` (`fileName: file.name`), `forms/api/[id]/theme-logo/route.ts:98` (`fileName: file.name \|\| 'logo'`), `attachments/lib/createFromBuffer.ts:89` (stores `input.fileName` as given). Only the main upload route passes `sanitizeAttachmentDisplayName` (`attachments/lib/security.ts:108`).
- **Fix:** Write each file as `attachments/<id>/<generated safe name>`, for example `<id>` plus a sanitised basename, and keep the original name only in the manifest. Resolve the final path and refuse anything outside `--out`. Add unit tests for `..`, separators, absolute paths and NUL in the stored name.
- **Verification:** Read the spec's command, edge-case and attachments sections: no rule on name sanitisation. Read the code: the sync_excel upload, the forms theme-logo route and createAttachmentFromBuffer all persist the name as supplied, so a crafted multipart filename reaches `file_name`. Rated critical because, as written, it is an arbitrary-file-write security defect driven by tenant input.

### g4-01 · CRITICAL · Subject export and erase have no organization check, so an administrator restricted to one organization can export or erase people in every organization of the tenant

- **Where:** [enterprise/2026-11-16-privacy-dsr-engine:270](.ai/specs/enterprise/2026-11-16-privacy-dsr-engine.md:270) — raised by Opus, Sol (confirmed)
- **Problem:** The engine keeps every table and route tenant-scoped and grants view, policies, holds and export to ordinary administrators. Staff ACLs can be restricted to some organizations, but nothing passes the caller's organization scope into the OSS export or erase run, or checks that a pasted kind:id belongs to an organization the caller may see, and the contract reads an absent organizationId as every organization. An organization-restricted administrator can therefore download the full export of, or irreversibly erase, a person in another organization, read that organization's operations and holds, and create tenant-wide policies and holds. The only negative test covers another tenant.
- **Evidence:** engine:33 'Scope of policies and holds \| The tenant. No per-organization policies or holds in this version'; :101 'Tables have no organization column \| Tenant scope is then the only scope'; :270 'POST subjects/export \| data_erasure.subjects.export \| Takes kind:id. Returns the OSS export document as a download'; :274 'administrators get view, policies, holds and export'; :347 the only negative case is 'another tenant's person returns nothing'; :392 'Scope comes from the session, never the body'. contract:280 'organizationId absent means every organization in the tenant'. Code: packages/core/src/modules/auth/data/entities.ts:302, :344 (organizations_json on role and user ACLs); packages/shared/src/lib/auth/organizationAccess.ts:12-29 (restricted principals are denied when there is no target organization).
- **Fix:** Require an unrestricted organization scope (super-admin or allowedOrganizationIds null, via isUnrestrictedOrganizationScope) for every data_erasure feature, or pass the request's resolved organization scope into exportSubjects/eraseSubjects and refuse a subject whose organization is outside it; define what the operations and holds lists show a restricted user. Add same-tenant, other-organization negative cases to TC-PRIVACY-GOV-001 and 003.
- **Verification:** Read assumptions 6-8, the data model and the API table: the only scoping statement is tenant-from-session. Confirmed organization-restricted ACLs exist and the shared fail-closed predicate denies restricted principals without a target organization; the contract defines an absent organizationId as all organizations. The tenant-only decision was made so holds match reliably, not as an authorization rule, so it does not answer this.

### g5-01 · CRITICAL · Deleting an assistant conversation cannot release its uploaded files, yet the spec says it does, with no residual risk

- **Where:** [2026-11-16-privacy-record-retention:87](.ai/specs/2026-11-16-privacy-record-retention.md:87) — raised by Opus (confirmed)
- **Problem:** The conversations set promises that a pruned conversation's attachments are released through the attachments service. Chat uploads are not attached to the conversation: the UI stores them under entity id `ai-chat-draft` with a client-minted record id, and nothing on the server re-links them, so a `releaseForRecord(entity, conversationId)` call finds nothing and succeeds. Every uploaded file, typically a personal document, would outlive the deletion the spec claims, and the planned integration test checks only conversations and messages, so this would ship unnoticed.
- **Evidence:** Spec L87: "its attachments are released through the attachments service"; L151: "their attachments are released"; L276-277: "Release goes through the attachments service ... Residual risk: None while that dependency holds." Seam: privacy-subject-erasure.md L204 `releaseForRecord(entityId, recordId, scope)` "lists a record's attachments". Code: packages/ui/src/ai/upload-adapter.ts:16 (`DEFAULT_AI_CHAT_ENTITY_ID = 'ai-chat-draft'`), :346-347 (`recordId = options.recordId?.trim() \|\| mintRecordId()`); packages/ui/src/ai/AiChat.tsx:1217 `useAiChatUpload()` with no record id; ai_assistant/data/entities.ts:182-183 and :923-924 keep only `attachment_ids` on messages and pending actions. Test L247 asserts conversation and messages gone, not files.
- **Fix:** Release by attachment id: collect ids from the conversation's messages and pending actions and add a scoped release-by-ids method (or an id filter on `releaseForRecord`) that checks tenant/organization and shared objects; or re-link uploads to the conversation when the message is persisted. Add an assertion that the stored object is gone after the soft-deleted target is pruned, and drop "Residual risk: None".
- **Verification:** Read upload-adapter.ts and AiChat.tsx: the default entity id is `ai-chat-draft` and the record id is minted client-side; grep of ai-assistant finds no code that rewrites an attachment's entity/record. The claim holds; severity raised to critical because the spec asserts the files are deleted and the test cannot catch that they are not.

### g2-01 · CRITICAL · A file whose deletion fails after commit can never be found again, but the spec says a re-run removes it

- **Where:** [2026-11-16-privacy-subject-erasure:80](.ai/specs/2026-11-16-privacy-subject-erasure.md:80) — raised by Kimi (confirmed)
- **Problem:** Rule 5 and the edge-case table promise that a file that fails to delete after commit is reported as pending and removed by re-running. The attachment rows are removed inside the erasure transaction and the blob deletion is only an in-memory closure returned to the caller, so after a storage error or a crash the re-run lists no attachments for the record, reports nothing pending and exits 0 while the personal file stays in storage for good. The operator is told the erasure is finished when it is not.
- **Evidence:** erasure:80 'Rows change in the transaction; stored files are removed after commit through a new attachments seam. A file that fails to delete is reported and removed by re-running.'; :204 releaseForRecord 'lists a record's attachments, releases them, and returns the blob cleanup'; :324 'Rows are already changed; the section reports files pending; a re-run removes them'. Code: packages/core/src/modules/attachments/lib/attachment-service.ts:496-497 (em.remove(attachment) in the caller's transaction, then returns deleteProviderBytes as a closure); packages/core/src/modules/attachments/workers/ holds only quota-recovery.ts, no orphan-blob sweep.
- **Fix:** Persist each pending blob deletion (partition, storage path, tenant, run id) in the same transaction as the row changes, as a pending-cleanup row or a durable queue job, and have the re-run or a worker retry from that record; keep the subject reported incomplete until it is drained. Add a test: storage delete fails, re-run, blob is gone and the report says so.
- **Verification:** Read releaseScoped: with flush:false the row is removed in-transaction and the storage delete is returned as a closure; nothing durable records the storage path. Searched the attachments module for an orphan sweeper and found none. The spec's recovery claim is therefore false and the re-run reports success. F-07 raises the same blob point inside its event finding.

### g4-02 · CRITICAL · Replay cannot re-erase people known only by an email address or phone number, yet marks them applied

- **Where:** [enterprise/2026-11-16-erasure-restore-replay:159](.ai/specs/enterprise/2026-11-16-erasure-restore-replay.md:159) — raised by Kimi (confirmed)
- **Problem:** The manifest and the applied row keep only the subject's kind and id. For a privacy:identifier subject the id is generated per run and records are found through aliases hashed from the identifier the operator typed, which the contract keeps out of subject ids and events. After a restore, replaying such an entry has nothing to compute aliases from, finds nothing, and the spec then inserts the row, so the entry stops being pending while the restored guest-basket, pay-link, claim and message records stay live.
- **Evidence:** replay:88 'without any identifier of the person beyond the internal subject reference'; :159-163 manifest { subject: { kind, id }, dataClassIds, prefer, excludedRelated }; :56 replay runs each entry through the OSS erase run; :189 'A subject no longer exists after the restore \| The run reports nothing found; the row is inserted'. contract:376-380 'Subject kind privacy:identifier ... Its id is generated for the run. Its aliases are the hashes of the identifier typed ... No hash appears in a subject id, an export document or an event'. erasure:290 event shape carries no aliases.
- **Fix:** Either store, for identifier subjects only, a protected replayable alias set (for example the lookup-hash candidates, encrypted with a key kept outside the database, on the same retention as the file) and pass it as aliases on replay, or exclude identifier-subject erasures from the guarantee explicitly and report them as not replayable instead of inserting the row. Add a unit test that replays an identifier-only erasure.
- **Verification:** Read the contract addendum on aliases and identifier subjects and the erasure event: nothing in the event or manifest lets a later run reconstruct the aliases, and the identifier's lookup hash lives only in an audit entry inside the restored database. The replay spec never mentions privacy:identifier and treats nothing-found as success.

### g2-03 · HIGH · People known only by an address are promised erasure, but erase rejects identifiers and the identifier subject's id changes every run

- **Where:** [2026-11-16-privacy-data-class-contract:377](.ai/specs/2026-11-16-privacy-data-class-contract.md:377) — raised by Opus, Sol, DS-Flash, Kimi (confirmed)
