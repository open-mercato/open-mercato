# Phase 3a

## 1. If/Else + Switch as transition sugar

**(a) Requirements** (spec §5.8, line 284; Architecture Notes line 398):
> "**If/Else** with the business_rules `ConditionExpression` language + ConditionBuilder UI inline (one condition language platform-wide), 'use Business Rule instead' toggle" · "**Switch** on one field, N labeled outputs + required otherwise" · "**Engine-semantics gate:** If/Else and Switch compile to prioritized transitions (pure sugar, additive)" · "new step types (`IF_ELSE`, `SWITCH`, `LOOP`, `WAIT_FOR_CONDITION` — additive enum values) … `minEngineVersion` (definition metadata; old engines refuse to *instantiate* definitions above their version instead of misexecuting them)".
Loop container is **OUT** ("requires its own mini-spec as a Phase 3 entry criterion — the UI must not ship ahead of defined semantics").

**(b) Anchors:** transition condition already IS `ConditionExpression` evaluated by `ruleEvaluator.evaluateConditions` (`transition-handler.ts` :706–752); priority ordering :240–243; step enum `data/validators.ts` :57 + `data/entities.ts` :14; step-handler switch ~:318; node registration `WorkflowGraphImpl.tsx` :222, `node-type-icons.ts`, `graph-utils.ts` direction maps ~:459/:475.

**(c) Approach:**
1. "Compile to prioritized transitions" means: `IF_ELSE`/`SWITCH` are **step types that behave exactly like `AUTOMATED` with no activities** — the branching is entirely in their outgoing transitions (conditions + priority + one unconditioned `otherwise` at lowest priority). Cheapest honest engine change: add both to the enum and to `executeStepByType` as thin delegates to the existing automated/pass-through handling (they complete immediately; transition evaluation does the rest). No new runtime semantics.
2. Editor: If/Else node inspector edits the condition of its "true" route via ConditionBuilder inline; "otherwise" route auto-created. Switch inspector: one field picker (ledger-backed) + N case values → N transitions with generated `condition` (`field == value`) + required otherwise; validator warns when a branching node lacks an otherwise route (spec §4.4: "validator warns when a branching node lacks one").
3. Add `minEngineVersion` optional definition-metadata field; `startWorkflow` (in `workflow-executor.ts`) refuses to instantiate when `definition.minEngineVersion > ENGINE_VERSION` const. Set it on definitions that use the new step types when saving from the Studio.
4. i18n all 4 locales (`workflows.stepTypes.*`); new node components in `components/nodes/`; palette entries.

**(d) Tests:** `data/__tests__/validators.test.ts` (enum + otherwise-warning), `lib/__tests__/step-handler.test.ts` (IF_ELSE/SWITCH complete + route via transitions; byte-identical trace for old defs), `lib/__tests__/transition-handler.test.ts` untouched behavior, graph round-trip in `lib/__tests__/graph-utils-layout.test.ts` style, engine-version refusal test.

## 3. Error routes + error directives + workflow-level error handler

**(a)** Spec §5.9 (line 285):
> "every activity-bearing node gets an optional **error output handle** → red dashed route into real handling. When unwired, a named **error directive** applies: `Fail instance` (default), `Continue with fallback value` (typed against the output contract), `Send to failure queue` (parks as ATTENTION for §8.5 triage). `continueOnActivityFailure` maps to directive #2 (additive alias)." · "A **workflow-level error handler** (designated handler sub-workflow/branch receiving `{failedStepId, error, contextSnapshot}`) is the catch-all — implemented as an **engine construct, not an event trigger** (the event-trigger subscriber deliberately excludes `workflows.*` events; implementers must not reach for that path)."

**(b)** Failure paths: `step-handler.ts` :255–295 (step FAILED), `workflow-executor.ts` :347/:486/:589 (instance FAILED + compensation :749), `transition-handler.ts` :457 (`continueOnActivityFailure`). **(c)** Suggested step-sized approach:
1. **Model (additive):** transition gains optional `kind: 'error'` (or `onError: true`) field; step/definition gain `errorDirective` (`'fail' | 'continueWithFallback' | 'failureQueue'`, with `fallbackValue`) and definition-level `errorHandler: { workflowId | stepId }`. All optional; absent ⇒ today's behavior.
2. **Engine:** in the catch/FAILED paths of `step-handler`/`workflow-executor`, before failing the instance: (i) look for an outgoing `kind:'error'` transition from the failed step → follow it (log a new `ERROR_ROUTED` event); (ii) else apply the step directive; (iii) else the workflow-level handler: start the designated handler sub-workflow (reuse the SUB_WORKFLOW start machinery in `step-handler.ts` :710–900 region) with input `{failedStepId, error, contextSnapshot}`, then fail/park the instance per handler config. 3. **Failure queue:** new instance state or metadata flag `attention: true` + list filter on the instances page (full triage UI is Phase 5 §8.5 — Phase 3 only needs the park semantics).
4. **Canvas:** error routes render red dashed (extend `EDGE_COLORS`/`EdgeState` in `lib/status-colors.ts` with DS status tokens); an error output handle on activity-bearing nodes (`AutomatedNode`, `UserTaskNode`, `SubWorkflowNode`, `InvokeAgentNode`).
5. Every new state change logs a `workflow_events` row (AGENTS.md rule 6).

## 4. WAIT_FOR_CONDITION (existing spec `.ai/specs/2026-07-20-workflows-wait-for-condition.md`)

**(a) Design summary (~20 lines):**
- New **step type** (not activity — only `StepExecutionResult` can express `WAITING`; activity state machine untouched, avoiding the AGENTS.md "Ask First" gate). Pauses a workflow or a single parallel branch until a boolean `ConditionExpression` over the run context holds.
- Config: `{ condition: ConditionExpression, timeout: ISO-8601 (REQUIRED), onTimeout: 'FAIL'(default)|'CONTINUE', pollIntervalMs?: 5000–3600000 }`. "Wait for variable set" = `IS_NOT_EMPTY` shorthand. Reuses `ruleEvaluator.evaluateConditions` — same evaluator as transitions; field paths resolve against `tokenReadContext` (root: `instance.context`; branch: overlay of `contextNamespace`).
- Resume is **event-driven first** (new `PATCH /api/workflows/instances/[id]/context` merges a context patch and calls `wakeConditionWaiters`), with a **delayed queue job (`kind: 'condition'`) as durability backstop** mirroring `timer-handler.fireTimer`; `deadlineAt` is absolute on the job (slow queues can't extend the wait); attempt cap `OM_WORKFLOWS_MAX_CONDITION_ATTEMPTS` default 1000.
- **No DB migration** — `step_instances.step_type` is `varchar(50)`; everything lives in definition JSON, events (`CONDITION_AWAITING/EVALUATED/MET/TIMED_OUT` — EVALUATED only on false poll ticks), and queue payloads.

- Branch-aware: paused branch resumes via `resumeBranch` exactly like timers (`timer-handler.ts:60–84`).
- Its spec's implementation phases: 1 engine core, 2 event-driven wake + API, 3 visual editor, 4 docs — 1 and 3 independently mergeable. ## 7. Path-identity rework + edit-safety rule (the pillar of 3b)

**(a)** Spec §4.1 (line 231):
> "Nodes and routes get durable ids **no longer derived from endpoints** (today `e_${from}_${to}`, and `branchKey`/`pendingTransition` persist transition ids that the engine re-looks-up mid-flight). The path-identity rework therefore ships **together with an edit-safety rule** (same phase, not deferred): structural edits to a definition with active instances require a new version (running instances keep executing their pinned definition snapshot), or — where versioning is not yet wired — old transition ids are kept as aliases. Re-pointing an edge under a running instance must be impossible, not merely discouraged."
§10 verification item (line 424): "confirm whether running instances actually pin their definition version today; if not, version-pinning is engine work that must land with the §4.1 edit-safety rule."

**(b) Verified pinning answer:** `WorkflowInstance` stores `definitionId` (uuid FK to a specific `(workflowId, version, tenantId)` row) + `version` (`data/entities.ts` :345–352), and `find-definition.ts` resolves per instance — **but** `PUT /api/definitions/[id]` mutates that same row's `definition` JSONB in place (`api/definitions/[id]/route.ts`, version bumped only when `input.version` supplied :358). So instances pin a row, not an immutable snapshot: editing the row changes running instances mid-flight. Version-minting machinery **already exists**: `api/definitions/[id]/publish/route.ts` mints frozen published versions (lifecycle field :238, unique constraint :197). Mid-flight state that re-looks-up ids: `instance.pendingTransition` (entities :389), `branch.branchKey === transitionId` (`parallel-handler.ts` :148, :369).

**(c)** Approach:
1. Ids: `generateTransitionId` → opaque unique id (`t_<nanoid>`); keep accepting legacy `e_from_to` ids on load (no rewrite of stored definitions — rewrite only on Customize for code defs, per §10: "priority normalization and id-migration happen only on Customize").
2. Edit-safety: in the PUT route, detect **structural** change (steps/transitions topology diff vs. stored) AND active instances (`RUNNING/PAUSED/FORKED/WAITING_FOR_ACTIVITIES` count for `definitionId`); if both → 409/422 with structured body offering "save as new version" (client then drives the existing publish-style mint + edit of the new row). Non-structural (labels, positions, activity config) edits stay in-place. Studio surfaces this as a banner + one-click "Create version".
3. Do not change engine lookup semantics; because instances keep their old row, aliasing is unnecessary on the versioned path (the alias fallback is only if the guard is bypassed — don't build it unless needed).

**(d)** Route test: structural edit with active instance → structured 409; without instances → in-place OK; label-only edit with instances → OK. Engine regression: `workflow-executor.test.ts`, `parallel-handler.test.ts` unchanged. Integration: start instance on v1, structural-edit mints v2, running instance completes on v1.

## Risks / unknowns

1. **Workflow-level error handler is a new engine construct** — the spec names the mechanism only negatively ("not an event trigger"). It concretely needs: (i) a hook inside `completeWorkflow`'s FAILED path **before** compensation (decide ordering: handler first, then compensation, or configurable — spec is silent; propose handler-then-compensation and document); (ii) a way to start the handler (sub-workflow start reuse) **outside** the failing transaction (the executor already forks an EM for durable-FAILED writes at `workflow-executor.ts` :656–718 — the handler start must ride that same durability path or a queued job, or a crash between FAILED-write and handler-start loses the handler); (iii) loop protection (a failing handler must not recursively invoke itself); (iv) branch semantics (does a branch failure trigger the instance-level handler or only after join-failure propagation?). Flag these in the PR / mini-design note before coding.
2. **Edit-safety semantics for drafts:** the draft layer (Phase 1) autosaves per-user; the structural-edit guard must fire on **Save** (definition PUT), not on draft writes — otherwise WIP is unsavable. Also decide what "active instances" includes (`PAUSED` long-lived waits can hold a definition hostage; version-minting is the escape).
3. **Legacy dialog deletion state is ambiguous** — Phase 1 scheduled "legacy dialog deletion (post-soak)" but `NodeEditDialog.tsx`/`EdgeEditDialog.tsx` still exist on base. If they're still referenced (page :1337/:1342 fallback), WFC editor work and step-type conversion should target only the CrudForm variants and let the legacy files die separately; do not extend legacy dialogs.
4. **`e_from_to` ids in the wild:** existing definitions, `examples/*.json`, templates, and mid-flight `pendingTransition`/`branchKey` values embed endpoint-derived ids. New opaque ids must coexist; never rewrite stored ids outside Customize; parallel-fork `branchKey === transitionId` means reattaching a fork's branch edge changes branch identity — forbid reattachment of fork-branch edges or keep the id (durable ids solve this).
5. **If/Else "sugar" temptation:** do NOT introduce runtime branching semantics in the step handler — all routing must remain in `findValidTransitions` (priority + condition). Any deviation is new engine semantics and breaks the additive claim.
6. **WFC spec drift vs. base:** written 2026-07-20 against pre-Phase-0 code; line anchors (e.g. `step-handler.ts:318/:822`, `validators.ts:293`) have shifted and its UI file list predates CrudForm-only dialogs and the registry. Re-anchor during implementation; the design itself remains valid.
7. **Bundle risk (icon picker):** a full lucide grid can bloat the editor chunk; use lazy loading and the module's established lazy-boundary pattern (#3169 note in `WorkflowGraphImpl`).
8. **60-node density QA** is an explicit exit criterion — build the 60-node fixture early (seed JSON under `examples/`) so chips/zoom/undo work can be exercised against it, and every template must keep validating against `workflowDefinitionDataSchema` (enforced by test).
9. **Sequencing inside Phase 3:** do 3a item 1 (enum + minEngineVersion) and 3b item 7 (durable ids + edit-safety) first — chips, reattachment, conversion, copy/paste all assume durable route identity; Code view + retirement last (retirement precondition), WFC engine core can proceed in parallel.
