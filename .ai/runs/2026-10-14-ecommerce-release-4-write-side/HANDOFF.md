## Two new open items from Step 5.5 (real-HTTP findings, documented not fixed — same tier as Step 3.4 Part A / Step 4.9's CONC-05)
Full detail: NOTIFY.md's `2026-10-15T10:15:00Z` entry and the header comment of `cart/__integration__/TC-CART-PRICE-01-02-reprice-triggers.spec.ts`.
1. **Trigger 3's disclosed label is unreachable through the real storefront route.** `ecommerce/lib/buyerContext.ts`'s digest formula hashes `effectiveLocale` and a `priceScopeKey` that embeds `currencyCode` — so a real currency/locale drift always also changes the buyer digest, and `detectCartRepriceTrigger`'s precedence (identity > currency > locale > staleness) means `buyer_context_changed` always wins over `currency_changed`/`locale_changed` in practice. Not a bug in `cart` itself — a consequence of a cross-module digest formula. Trigger 3's own label is still correctly proven in isolation at the Jest level (a synthetic `freshContext` no real `StoreContext` ever produces).
2. **A real currency/locale change never actually updates `Cart.currencyCode`/`Cart.locale`.** Because of finding #1, `applyCartRepriceTriggerFields` (`commands/cart.ts`) only ever takes the `buyer_context_changed` branch for a real currency/locale drift, which updates buyer-identity fields only — `currencyCode`/`locale` stay stale forever on the cart row, even though the lines DO get re-priced (using the stale currency/locale). This contradicts `lib/triggers.ts`'s own doc comment claiming the re-price is "identical no matter which reason wins." **Fix for whoever picks this up**: make `applyCartRepriceTriggerFields` sync `currencyCode`/`locale` from `freshContext` whenever ANY of triggers 2/3 fires, not only when one of them is the labeled winner.

## OPEN ITEM 3 — CORRECTED at Step 8.2 (QA F12); read this before trusting the Step 5.1 text above any copy of it elsewhere
This item originally claimed (Step 5.1, per spec §5.2's own "it does not re-price on every read" line) that `Cart.totals` is intentionally stale between re-pricing triggers — that an ordinary `cart.lines.add`/`.update`/`.remove`/`.bulkAdd` call does NOT itself recompute the whole-cart aggregate. **That is no longer true for writes.** Step 8.2 (commit `c5be747249`, QA F12) made every one of those four line commands run the same promotions-effects + totals-recompute phases `cart.reprice` uses (`buildPromotionsEffectsPhase`, `buildRecomputeCartTotalsPhase`), inside their own `withAtomicFlush`, gated only on the mutation actually being accepted (never on a rejection) — so `Cart.totals` and every line's `discountTotalNet` are live after every accepted write, not just after a `cart.reprice` trigger. The fix was prompted by a real QA repro: a 2-unit "5% off 2+ items" cart showed zeroed totals right after an add, kept a stale discount after a quantity cut below the threshold, and left a non-zero grand total after the last line was deleted — all three are now correct immediately.

The one residual nuance, narrower than the original note: a bare `GET /current` with no intervening write and no re-price trigger firing (no buyer-context/currency/locale drift, inside the 30-min staleness budget) still does not itself force a recompute — it returns whatever `Cart.totals` the most recent write (or `cart.reprice`) left. So "stale between triggers" now describes only back-to-back reads, never a write. The release invariant's own mandatory guarantee still lands at trigger 5 (checkout lock, Phase 7, never skipped) regardless.
