## How this file works

One row per task. `Status` is the single source of truth for progress and is updated **as work lands**, not in advance. A task is `done` only when its own verification command has been run and passed.

| Symbol | Meaning |
|---|---|
| `todo` | not started |
| `wip` | subagent dispatched, not yet verified |
| `done` | code landed **and** its verification passed |
| `gate-blocked` | code landed and reviewed, but its verification cannot run yet for a reason outside the task |
| `blocked` | needs a decision or an upstream task |

**Owner** names the subagent that executed it. **Verify** is the exact command that must pass.

Tasks within a phase that touch disjoint files run in parallel; tasks sharing a file are sequenced. The `Files` column is the conflict key — two `wip` tasks must never list the same file.

**Known shared surfaces the `Files` column does not capture:** `i18n/*.json` and `UPGRADE_NOTES.md` are appended to by many tasks. Agents touching them must read-modify-write and verify a concurrent agent's keys survived, rather than rewriting the file wholesale. T2.1 and T2.3 both wrote i18n concurrently and both sets of keys survived — by care, not by design.

## Decisions in force (from the spec)

D-1 per-project Kanban columns · D-2 subtasks are child tasks carrying time, parent shows inclusive rollup · D-3 currency read-only once entries exist · D-4 presets fill an editable range · D-5 already-reported entries excluded by default · D-6 access request is a real notification · D-7 round at the entry then sum upward · D-8 end-before-start reads as midnight crossing · D-9 `customer_id` → `customer_entities` + snapshot · D-10 project code auto-derived, 20-char cap.

## Standing constraints for every task

- Tenant + organization scoping on every query; never cross-tenant.
- Writes go through commands, not raw ORM in route handlers.
- `withAtomicFlush` when a phase queries between mutation and flush; side effects and cache invalidation **after** the commit.
- Custom write routes wire the mutation guard registry.
- Client code uses `apiCall`/`apiCallOrThrow`; non-`CrudForm` writes use `useGuardedMutation`.
- No hardcoded user-facing strings; no raw Tailwind status colors; no arbitrary values.
- `yarn db:generate` may emit unrelated migrations — drop those from the diff, keep only `staff`, update its snapshot.
- Never run `yarn db:migrate`.

## Rework and watch items

**R3 — project access was not enforced anywhere.** *(CLOSED 2026-08-13)*

The spec's "Project access is one resolver" says every board, task, entry, timesheet and report route filters through `resolveProjectAccess`. Verified against the tree:

- `grep -rn NoProjectAccess` across `packages/core/src` and `apps` finds **no importer**. T2.6 built, translated and unit-tested the component; nothing renders it.
- Only **one** route under `api/timesheets/` consults `timeTrackingAccessResolver` — `time-entries/overlaps/` (T4.3, landed today). `GET /api/staff/timesheets/time-projects` does not.
- That route is gated on `staff.timesheets.projects.view`, which `setup.ts` grants to **`employee`**. So a Team Member who is not a project member currently **receives the project record** — customer name and project name leak outright.

This breaks **US-A1** ("unassigned/other customers are not visible"), **US-A2**, and screen 17 note 1 (the message must not confirm a resource exists). The detail page's only negative branch is `RecordNotFoundState` — no request-access action, wrong message.

**I marked T2.6 `done` on its unit tests. That was wrong** — the component was verified in isolation and never checked for a caller. Corrected to PARTIAL.

**Fixed:** `api/timesheets/time-projects/route.ts` now resolves access and narrows list **and** `?id=` detail; `projects/[id]/page.tsx` and `[id]/edit/page.tsx` both render `NoProjectAccess` instead of `RecordNotFoundState`; `TC-TT-017` is un-quarantined and lists as a real test. Staff suite **625 passing**, core+app typecheck clean, eslint at baseline.

**Policy question CLOSED 2026-08-13 → spec D-13:** keep the `projects.view` grant, scope the data. A Team Member keeps the Projects nav entry and sees only the projects they are assigned to. **No code change needed** — the R3 fix already narrows the list through `resolveProjectAccess`.
