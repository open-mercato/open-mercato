## 🎯 Goal

Close the one blocker that keeps PR #4160 from merging: rows written **before** system-scoped encryption landed stay plaintext forever, because no existing tool can encrypt them. Ship a CLI backfill command that encrypts historical rows covered by a **system-scoped** default encryption map (today: `onboarding:onboarding_request`), and hand the operator a runbook for running it against the DokPloy-deployed `demo.openmercato.com`.

## Scope

- `packages/core/src/modules/entities/cli.ts` — a new backfill command alongside `rotate-encryption-key` / `decrypt-database`.
- `packages/core/src/modules/entities/__tests__/` — unit coverage for the new command.
- `apps/docs/docs/user-guide/encryption.mdx` — operator documentation for the new command.
- A PR comment addressed to Mateusz Staniaszek with the DokPloy runbook.

## Non-goals

- **System-key rotation / decryption semantics.** `rotate-encryption-key --old-key` and `decrypt-database` remain tenant-scoped; extending them to `keyScope: 'system'` maps is a separate public-contract decision and belongs in a follow-up. This plan only adds the forward-only (plaintext → ciphertext) backfill the PR conversation actually asked for.
- Changing the write path, the encryption map declaration, or the migration already landed on this PR.
- Running the backfill against production; the run is an operator action documented in the runbook, not something this PR executes.

## Assumptions

- The backfill belongs in the `entities` module CLI, not the `onboarding` module: it is generic over every module that declares a `keyScope: 'system'` default map, and `entities` already owns `seed-encryption`, `rotate-encryption-key` and `decrypt-database`. A module-local command would have to be duplicated by the next system-scoped map.
- Forward-only is the right default. The command never decrypts and never accepts an old key, so the most destructive failure mode (re-encrypting under a wrong key) is structurally impossible.
- Soft-deleted rows are backfilled too — encryption at rest is about the bytes on disk, not row visibility.
- The runbook targets an operator with DokPloy access; exact application/slot names are left as placeholders rather than guessed.

## Risks

- The command writes to production tables. Mitigated by `--dry-run` being explicitly documented as the first step, batching, and a fail-closed abort when `TENANT_DATA_ENCRYPTION` is off or the KMS is unhealthy.
- A row whose plaintext is already ciphertext-shaped but not decryptable under the current DEK would be re-encrypted (double-encrypted). The service's `isEncryptedWithDek` check binds on an authenticated decrypt, so this only happens for genuinely foreign payloads; the command reports such rows.
