# Execution plan — migrate the nanoid 3.3.18 bump to `develop`

**Brief:** Dependabot opened [#5215](https://github.com/open-mercato/open-mercato/pull/5215)
(`chore(deps): bump nanoid from 3.3.16 to 3.3.18`) against `main`. This repository's
configured base branch is `develop`, so the bump has to be re-landed there and the
original PR closed as superseded.

## Goal

Bring `nanoid` up to `3.3.18` on `develop` — the branch that actually receives feature
work — and close the mis-targeted Dependabot PR #5215 with a pointer to the replacement,
so the dependency fix is not lost when `main` is next refreshed from `develop`.

## Scope

`develop` has already diverged from `main` on this dependency: PR
[#5157](https://github.com/open-mercato/open-mercato/pull/5157) pinned nanoid through a
root `resolutions` entry (`"nanoid@npm:^3.3.16": "3.3.17"`) rather than leaving the
transitive range floating. Dependabot's diff against `main` (a plain `^3.3.16` lock entry
moving `3.3.16 → 3.3.18`) therefore does not apply to `develop` at all — the equivalent
change is advancing the pin.

In scope:

- Root `package.json` — move the `nanoid@npm:^3.3.16` resolution from `3.3.17` to `3.3.18`.
- `yarn.lock` — refresh the resolved `nanoid` entry and checksum for `3.3.18`.
- Close PR #5215 as superseded, with a comment explaining why `develop` needed a different
  change than the one Dependabot generated.

### Non-goals

- Not bumping `nanoid` to the `5.x` line — the `^3.3.16` range is what upstream
  dependencies (postcss and friends) ask for, and a major jump is a separate decision.
- Not touching any other `resolutions` entry, and not refreshing unrelated lockfile drift.
- Not changing Dependabot's own configuration to target `develop` — that is repository
  automation policy and falls under "Ask First" in `AGENTS.md`.
- Not retargeting #5215 in place: Dependabot re-generates its branch from `main`, so an
  in-place base change would be reverted by the next Dependabot run.

## Implementation Plan

### Phase 1 — Advance the nanoid pin on `develop`

Update the resolution to `3.3.18`, re-resolve the lockfile with an install, and confirm
the lockfile now carries exactly one `nanoid` entry at the new version with no unrelated
drift.

### Phase 2 — Validate and supersede the Dependabot PR

Run the configured validation gate over the refreshed dependency tree, then close #5215
with a comment linking the replacement PR so the audit trail stays intact.

## Risks

- **Lockfile drift.** `yarn install` can pull in unrelated resolution changes if the
  checked-in lockfile is stale. Mitigation: inspect the diff and hard-restrict it to the
  `nanoid` entry, discarding anything else.
- **Upstream behavior change.** 3.3.17 fixed an infinite loop on zero size and 3.3.18
  fixed an infinite loop in the React Native async path. Both are bug fixes with no API
  change; the risk of regression is limited to callers that relied on the previous
  hanging behavior, which is nonsensical. Mitigation: the full validation gate.
- **Dependabot re-opens the bump.** Closing #5215 tells Dependabot not to retry that exact
  version pair, but a future `main`-targeted bump is still possible. Accepted: out of
  scope per the Non-goals above.

### Validation gate result

All eight configured `validation.commands` pass on `3282af216`, run in **local mode** (no
compose `app` container was running): `build:packages` ✅, `generate` ✅ (no generated-file
drift), `build:packages` ✅, `i18n:check-sync` ✅, `i18n:check-usage` ✅, `typecheck` ✅,
`test` ✅, `build:app` ✅.

Two host-environment failures surfaced during the run and were diagnosed as unrelated to this
change:

1. The first `yarn test` attempt died with `jest: failed to cache transform results …
   UNKNOWN: unknown error, write`. Root cause was the machine's 16 GB `/tmp` tmpfs at 80 %
   capacity (84 % of inodes), with `/tmp/jest_rs` alone holding 12 GB of accumulated jest
   transform cache — ENOSPC in disguise, not a test failure. Clearing the cache directory and
   re-running gave 9516 passing tests in `@open-mercato/core` alone and green results across
   every other package.
2. Four `standalone template dev wrapper` cases in
   `packages/create-app/src/lib/template-dev-log-files.test.ts` fail on this host because
   `fs.inotify.max_user_instances` is 128 against the 4096 the guard requires. This is a
   pre-existing local sysctl limit that passes in CI; raising it needs sudo and is out of
   scope. Re-running the create-app suite without that single file gives 456 passed / 0 failed.
