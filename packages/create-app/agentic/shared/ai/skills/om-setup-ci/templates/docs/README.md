# Continuous Integration

This repository's CI was generated by the Open Mercato `om-setup-ci` skill. It
carries over the checks and conventions the Open Mercato framework uses in its
own CI, trimmed to what applies to an app created with `create-mercato-app`,
and adds a layered set of security scans.

Every pull request to __OM_BRANCHES_INLINE__, and every push to those branches,
runs the pipeline in `.github/workflows/ci.yml`. A pull request is ready to
merge when the single **`CI`** check is green.

## What runs, and why

The pipeline is a set of GitHub Actions jobs. Independent jobs run in parallel,
and the `CI` job at the end collects their results.

```text
 push / PR ─► changes ─┬─► audit           (dependencies changed)
                       ├─► secrets
                       ├─► sast
                       ├─► workflow-lint   (.github changed, or a push)
                       └─► docker + Trivy  (image inputs changed, or a push)
              lint ──────────┐
              validate ──────┼─► integration
                             ▼
                            CI  ◄── the one required check
```

### `changes`: detect what the change touches

Compares the change with its base: for a pull request, the commit it branches
from; for a push, the previous commit on the branch. Two things depend on it:

- **Which conditional jobs run.** Skipping the audit, Docker build and workflow
  scan when nothing relevant changed keeps pull requests fast. The nightly
  workflows and post-merge pushes still cover them.
- **The baseline.** The audit, secret scan and SAST block only problems the
  change **introduces**, so a pull request is never red for something that was
  already on the base branch. The nightly scans own existing problems and keep
  a tracking issue open until they are fixed.

### `audit`: dependency vulnerabilities (SCA)

- **What:** `node scripts/ci/audit-ci.mjs --severity __OM_AUDIT_SEVERITY__ --baseline <base yarn.lock>`
  checks every package resolved in `yarn.lock` against the npm advisory
  database.
- **Why:** a dependency with a known vulnerability is the cheapest security
  problem to catch and the most expensive to find in production.
- **Fails on:** advisories at severity `__OM_AUDIT_SEVERITY__` or higher that the
  change introduces. If the advisory database can't be reached, the job fails
  instead of passing silently.
- **Why not `yarn npm audit`:** the npm bulk-advisory endpoint currently returns
  a gzip body without a `Content-Encoding` header, which makes Yarn 4 crash
  before it evaluates anything. The script runs the same check and decompresses
  the response defensively.

### `secrets`: secret scan (Gitleaks)

- **What:** Gitleaks scans **every commit** the change adds, not only the final
  files.
- **Why:** a key committed and removed in a later commit is still in the Git
  history, and anyone with read access can recover it. Leaked credentials are
  the most common real-world compromise of application repositories.
- **How it is installed:** a pinned release whose SHA-256 checksum is verified
  before the binary is unpacked (`.github/actions/gitleaks`).

### `sast`: static analysis (Semgrep)

- **What:** Semgrep over the app code in `src/`, test files excluded, with two
  rule sets:
  - **Open Mercato rules** (`scripts/ci/semgrep/open-mercato.yml`), every
    severity: runtime code execution (`eval`, `new Function`), shell commands
    built from variables, raw SQL with interpolated values, `dangerouslySetInnerHTML`
    with non-constant HTML, open redirects from request parameters, and cookies
    with `httpOnly: false`.
  - **Semgrep registry `p/default`**, ERROR severity only.
- **Why custom rules:** Semgrep's free rulesets barely cover Next.js route
  handlers and server actions. On a deliberately vulnerable route they missed
  `exec()` with user input and `dangerouslySetInnerHTML`. The Open Mercato
  rules target exactly those patterns and allow the framework's safe idioms:
  constants, `?` placeholder lists, and `{ sql, params }` clause builders.
- **Fails on:** findings the change introduces.

### `workflow-lint`: workflow security (zizmor)

- **What:** zizmor audits the files in `.github/`: expression injection,
  over-broad token permissions, credentials left in checkouts, cache poisoning,
  unpinned actions, Dependabot cooldowns.
- **Why:** CI workflows run with access to your code and secrets. A workflow
  that interpolates a pull request title into a shell script can be taken over
  by anyone who can open a pull request.
- **When:** pull requests that touch `.github/`, and every push.

### `lint`: code quality

- **What:** `yarn lint` (ESLint with the Next.js core-web-vitals rules).
- **Why:** catches bugs such as hook misuse, unused code and accessibility
  problems before review. It doesn't need generated files, so it runs in
  parallel and fails fast.

### `validate`: the build gate

Runs the steps of the validation gate that coding agents use before opening a
pull request (`.ai/agentic.config.json` → `validation.commands`), in the same
order:

| Step | Command | Why |
| --- | --- | --- |
| Generate | `yarn generate` | Rebuilds every registry in `.mercato/generated/` from `src/modules.ts` and the installed packages. This proves the app builds from committed sources alone. |
| Clean-tree check | `git status --porcelain` | Generated output is never edited by hand. If `yarn generate` changes a tracked file, the committed copy is stale. |
| Typecheck | `yarn typecheck` | `tsc --noEmit` over the whole app, including the generated registries. |
| Design-system check | `yarn ds:check` | Blocks hard-coded palette colours (`text-red-500`), arbitrary Tailwind values (`p-[13px]`) and manual `dark:` overrides, so the UI stays consistent with Open Mercato's tokens and dark mode. |
| Time-bomb tests | `node scripts/ci/time-bomb-scanner.mjs --fail src .ai/qa/tests` | Finds tests that assert a hard-coded future date as "still valid". They pass today and fail on an unrelated pull request once the date passes. |
| Unit tests | `__OM_TEST_COMMAND__` | Jest unit tests under `src/`. A fresh app has none, and the run passes until you add some. |
| Production build | `yarn build` | `next build` in production mode. It catches server/client boundary errors, missing environment handling and anything else that only fails in a real build. |

Dependencies are installed with `yarn install --immutable`. If `package.json`
and `yarn.lock` disagree, the install fails, so a dependency change that was
never installed locally can't reach the main branch.

### `integration`: end-to-end tests

- **What:** `yarn test:integration:ephemeral` builds the app, starts it against a
  throwaway PostgreSQL container (testcontainers, using the Docker daemon on
  GitHub-hosted runners), runs the Playwright suites, and tears everything
  down.
- **Which tests:** specs in `src/modules/<module>/__integration__/*.spec.ts`
  and `.ai/qa/tests/**/*.spec.ts`. If there are none, the job reports
  "skipping" and passes.
- **Why:** unit tests can't show that an API route, a CRUD form or an
  access-control rule works in the running app. Each run starts from an empty
  database, so the tests have to create their own fixtures. That keeps them
  stable and independent of demo data.
- **When it fails:** the Playwright report, traces and screenshots are uploaded
  as the `integration-test-results` artifact on the run page.

### `docker`: production image and Trivy scan

- **What:** builds the image from `Dockerfile` without pushing it (layers cached
  in the GitHub Actions cache), then scans its **OS packages** with Trivy.
- **Why:** a broken `Dockerfile` otherwise only shows up at deploy time, and the
  npm audit can't see vulnerabilities in the base image's Alpine packages.
- **Fails on:** HIGH or CRITICAL vulnerabilities that have a fix available.
  Unfixed ones are left to the nightly scan, since there is nothing to upgrade
  to yet.
- **When:** on every push, and on pull requests that touch `Dockerfile`,
  `.dockerignore`, `.trivyignore`, `docker/`, `package.json`, `yarn.lock`,
  `.yarnrc.yml` or `next.config.*`.

### `CI`: the aggregate verdict

Waits for all jobs and fails if any of them failed or was cancelled. A skipped
job counts as passed. Mark only this check as required, so you never have to
edit branch protection when a job is added or renamed.

### Nightly dependency audit: `.github/workflows/audit.yml`

Runs every day (`__OM_AUDIT_CRON__`, UTC) on each protected branch, and on
demand from the Actions tab. It audits **without** a baseline, so it catches
advisories published after a dependency was merged. It keeps one issue per
branch open (labels `security`, `dependencies`) while advisories exist, and
closes it on the first clean run.

### Nightly security scan: `.github/workflows/security.yml`

Runs every day (`__OM_SECURITY_CRON__`, UTC) on `__OM_DEFAULT_BRANCH__`, and on
demand. It runs the full versions of the pull-request scans:

| Job | Scope |
| --- | --- |
| Secret scan | The **entire** Git history. |
| Static analysis | All of `src/` with the Open Mercato rules, not just new findings. |
| Image scan | OS **and** npm packages in the production image, including vulnerabilities with no fix yet. The base image's own global npm toolchain is skipped: only a newer Node base image can fix it. |
| Dynamic scan (opt-in, `--with-dast`) | An OWASP ZAP baseline scan of the running app (next section). |

Any failure opens or refreshes one issue labelled `security`, and the first
clean run closes it.

### Dynamic scan (DAST): OWASP ZAP, opt-in

- **What:** boots the app the same way as the integration tests (ephemeral
  database) and runs a passive ZAP baseline scan against it. It checks security
  headers, cookie flags, information leaks and error disclosure.
- **What decides failure:** `scripts/ci/zap-rules.tsv`. Out of the box,
  missing anti-clickjacking and `X-Content-Type-Options` headers and
  application error disclosure fail the job; everything else is reported. The
  HTML and JSON reports are uploaded as the `zap-report` artifact.
- **Limits:** the scan is unauthenticated and passive. It sees public pages and
  the login screen, not the backend behind it, and it does not attack the app.

### CodeQL: opt-in (`--with-code-scanning`)

`.github/workflows/codeql.yml` runs GitHub's dataflow-aware analysis on the
app's TypeScript and on the workflows, on every pull request and weekly.
Findings appear under *Security → Code scanning*. With this option, the
Semgrep and zizmor results are uploaded there as well. CodeQL requires a
public repository or **GitHub Code Security** on a private one, which is why
it is off by default.

### Dependabot: `.github/dependabot.yml`

Opens a weekly grouped pull request that keeps the GitHub Actions used here up
to date. It waits **14 days** after a release before proposing it, which gives
the community time to catch a compromised release. npm packages are
deliberately not bumped this way: `@open-mercato/*` packages move in lockstep
and are upgraded with the `om-auto-upgrade-*` skills. For third-party security
fixes, enable Dependabot security updates (see below).

### Conventions applied to every job

- **Least privilege:** the workflow token is read-only (`contents: read`). Only
  the jobs that need more get it, each at job level: `issues: write` for the
  tracking issues, and `security-events: write` for code scanning.
- **Pinned supply chain:** every third-party action is pinned to a commit SHA
  (with its version as a comment), container images to a digest, and the
  Gitleaks binary to a checksum. Tags can be moved; SHAs and digests can't.
  Every pinned release was at least two weeks old when it was chosen.
- **No credentials in checkouts:** every checkout uses
  `persist-credentials: false`, so later steps can't read or leak the token.
- **No untrusted expressions in scripts:** event data (commit SHAs, branch
  names) reaches shell and JavaScript steps through environment variables,
  never through `${{ }}` interpolation, which is the classic
  workflow-injection vector.
- **One run per pull request:** a new push cancels the previous run for the
  same pull request. Pushes to protected branches always finish.
- **Pinned toolchain:** Node.js comes from __OM_NODE_SOURCE__, and Yarn from
  `package.json#packageManager` via Corepack.
- **Shared setup:** jobs install dependencies through `.github/actions/setup`, so
  a Node, cache or install fix is made in one place.
- **Timeouts:** every job has a `timeout-minutes`, so a hung process can't use
  up your Actions minutes.

## Security coverage

| Risk | On every pull request | Nightly | Tool |
| --- | --- | --- | --- |
| Vulnerable npm dependencies | New advisories | All advisories, every protected branch | `audit-ci.mjs` (npm advisory DB) |
| Leaked secrets | Commits in the change | Full history | Gitleaks |
| Injection, XSS, RCE patterns in app code | New findings | All of `src/` | Semgrep + Open Mercato rules |
| Dataflow vulnerabilities | With `--with-code-scanning` | Weekly | CodeQL |
| Insecure CI workflows | When `.github/` changes | (every push) | zizmor |
| Vulnerable base-image packages | Fixable HIGH/CRITICAL | All HIGH/CRITICAL | Trivy |
| Missing security headers, cookie flags, error leaks | — | With `--with-dast` | OWASP ZAP baseline |

**What these tools don't cover.** Automated scanners don't understand your
business rules. They won't notice that an API route forgets to check a
permission, filter by `organization_id`, or that a user can read another
tenant's records. They also don't test authenticated pages dynamically.
Code review against Open Mercato's rules (feature-based guards, tenant
scoping, `findWithDecryption` for encrypted entities) and periodic manual
penetration testing remain necessary.

## Running the checks locally

Before you push, run the same commands CI runs, from the app root:

```bash
yarn install --immutable
yarn generate
git status --porcelain --untracked-files=no   # must print nothing
yarn typecheck
yarn lint
yarn ds:check
node scripts/ci/time-bomb-scanner.mjs --fail src .ai/qa/tests
yarn test
yarn build
yarn test:integration:ephemeral                # needs Docker running
node scripts/ci/audit-ci.mjs --severity __OM_AUDIT_SEVERITY__
```

The security scanners run in Docker, with the same pinned versions as CI:

```bash
# Secret scan (needs the gitleaks binary: https://github.com/gitleaks/gitleaks/releases)
gitleaks git --redact .

# Static analysis
docker run --rm -v "$PWD:/src" -w /src __OM_SEMGREP_IMAGE__ \
  semgrep scan --metrics=off --config scripts/ci/semgrep/open-mercato.yml \
  --exclude '**/__tests__/**' --exclude '**/__integration__/**' --exclude '*.test.*' --exclude '*.spec.*' src

# Image scan (after `docker build -t app:local .`)
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock __OM_TRIVY_IMAGE__ \
  image --severity HIGH,CRITICAL --ignore-unfixed app:local
```

To run one integration suite, use
`yarn test:integration:ephemeral --filter <module-or-path>`. To keep the
ephemeral app running while you iterate on a test, use
`yarn test:integration:ephemeral:start`.

## Branch protection and repository settings

The pipeline reports results but doesn't block merges by itself. To make the
`CI` check required on each protected branch:

1. Open *Settings → Branches* (or *Settings → Rules → Rulesets*).
2. Add a rule for __OM_BRANCHES_INLINE__.
3. Enable **Require status checks to pass** and add the check named **`CI`**.
   The check only appears in the list after the workflow has run once, so open
   a pull request first.
4. Recommended: also enable **Require branches to be up to date before
   merging** and **Require a pull request before merging**.

To set this up with the GitHub CLI instead (admin rights required; this replaces
the branch's existing protection settings):

```bash
gh api -X PUT repos/{owner}/{repo}/branches/<branch>/protection \
  -H "Accept: application/vnd.github+json" \
  -F 'required_status_checks[strict]=true' \
  -f 'required_status_checks[contexts][]=CI' \
  -F 'enforce_admins=false' \
  -F 'required_pull_request_reviews[required_approving_review_count]=1' \
  -F 'restrictions=null'
```

Also enable these repository settings in *Settings → Code security*. They
complement CI, which can only report a problem after it has been pushed:

- **Secret scanning with push protection** blocks a push that contains a
  recognised secret before it reaches the repository. Free for public
  repositories; private ones need GitHub Secret Protection.
- **Dependabot alerts** and **Dependabot security updates** open pull requests
  for vulnerable third-party packages.

## When a check fails

| Failing step | What to do |
| --- | --- |
| Install dependencies | `yarn.lock` doesn't match `package.json`. Run `yarn install` locally and commit `yarn.lock`. |
| Dependency audit | Upgrade the affected package (`yarn up <pkg>`, or a `resolutions` entry for a transitive one). Only when **no patched release exists**, add the advisory to `scripts/ci/audit-ci-allowlist.json` (see [Handling false positives](#handling-false-positives)). |
| Secret scan | **Treat the secret as compromised: revoke and rotate it first**, at the provider. Removing the commit is not enough, because forks, clones and caches keep it. Then move the value to an environment variable or secret store and remove it from the code. Rewriting history is optional once the secret is revoked. |
| Static analysis | Fix the flagged code using the rule's message: an argument array instead of a shell string, bound SQL parameters, text instead of HTML. If the line is genuinely safe, suppress it with a reason. |
| Workflow security | Follow the zizmor message. Its documentation link explains each audit and the safe pattern. |
| Verify generation left tracked files untouched | Run `yarn generate` and commit the changed files. Never edit generated files by hand. |
| Typecheck / Lint / Unit tests | Reproduce with the same command locally (see above). |
| Design-system check | Replace the flagged classes with design-system tokens (for example `text-status-error-text` instead of `text-red-600`). The error message names the rule. |
| Time-bomb test literals | Compute the date relative to now (`new Date(Date.now() + 86_400_000)`), or freeze time in the test. If the literal really is safe, add it to `.ai/time-bomb-allowlist.json` with a reason. |
| Production build | Run `yarn build` locally. These failures are usually server-only code imported into a client component, or a missing environment default. |
| Integration tests | Download the `integration-test-results` artifact and open `html/index.html`. Traces open at <https://trace.playwright.dev>. |
| Docker image | Run `docker build .` locally. Check that `.dockerignore` doesn't exclude a file the build needs. |
| Image scan | Rebuild on a newer base image (`docker pull node:24-alpine`, then rebuild). Add `apk upgrade --no-cache` to the runner stage if the fix is newer than the base image. |
| Dynamic scan | Open the `zap-report` artifact. Most findings are fixed with a response header in `next.config.ts` → `headers()`, or with cookie options. |

## Handling false positives

Every suppression mechanism expects a written reason, so it stays reviewable:

| Tool | How to suppress | Example |
| --- | --- | --- |
| Semgrep | Comment on the flagged line | `// nosemgrep: om-dangerously-set-inner-html — sanitized with DOMPurify above` |
| Gitleaks | Fingerprint in `.gitleaksignore` (printed in the job log) | `a1b2c3…:src/fixtures/sample.ts:generic-api-key:12` |
| Trivy | CVE id in `.trivyignore`, with a comment | `CVE-2026-12345  # not reachable: build-time only tool` |
| OWASP ZAP | Change the rule's action in `scripts/ci/zap-rules.tsv` | `10054	WARN	(reason)` |
| Dependency audit | Entry in `scripts/ci/audit-ci-allowlist.json` | see below |

```json
{
  "version": 1,
  "advisories": {
    "GHSA-xxxx-xxxx-xxxx": {
      "package": "some-package",
      "reason": "No patched release exists; only reachable from a build-time tool that never sees user input. Re-check when upstream ships a fix.",
      "addedAt": "2026-01-31"
    }
  }
}
```

Use suppressions for genuine false positives and for problems with no fix yet,
never to get a red build to merge.

## Customizing the pipeline

All generated files are ordinary files in your repository, so you can edit
them. A few changes come up often:

- **Bigger runners:** the build and typecheck use up to 8 GB of Node heap. If
  the standard runner of a private repository runs out of memory, switch to a
  larger runner with `--runner <label>` (for example
  `ubuntu-latest-4-cores`). Larger runners are configured under
  *Settings → Actions → Runners*.
- **Environment variables for the build:** add them under the `env:` key of the
  `validate` job. Use repository secrets (`${{ secrets.NAME }}`) for anything
  sensitive, and never commit real values.
- **Enterprise modules or feature flags:** variables that `src/modules.ts`
  reads must be set at build time. Put them in the workflow-level `env:` so the
  `validate` and `integration` jobs build the same app.
- **Your own Semgrep rules:** add them to `scripts/ci/semgrep/open-mercato.yml`,
  or to a new file plus another `--config` line in the `sast` job.
- **Deployments:** keep them in a separate workflow that runs after `CI`
  succeeds (`on: workflow_run`), or use your hosting provider's Git
  integration. Don't add deploy steps to `ci.yml`.

If you edit the generated files, `--force` will overwrite your changes on the
next regeneration. Either re-apply them afterwards, or record the change as a
generator option instead. The audit allowlist and `zap-rules.tsv` are never
overwritten.

## Regenerating and upgrading

The generator is part of the `om-setup-ci` skill in `.ai/skills/om-setup-ci/`.
Ask your coding agent to "set up CI", or run it directly:

```bash
node .ai/skills/om-setup-ci/scripts/setup-ci.mjs --dry-run              # show the plan
node .ai/skills/om-setup-ci/scripts/setup-ci.mjs --force                # refresh to the latest templates
node .ai/skills/om-setup-ci/scripts/setup-ci.mjs --with-dast --force    # enable the nightly ZAP scan
```

Options you pass once are saved in `.github/om-ci.json` and reused on later
runs. After upgrading Open Mercato, refresh the skill with
`yarn mercato agentic:init --update-harness`, then re-run the generator with
`--force` to pick up template improvements and newer pinned tool versions.
Review the diff before you commit it. Between upgrades, Dependabot keeps the
pinned actions current. Its bumps edit generated files, so a later run reports
them as conflicts, and `--force` resets those actions to the generator's own
pins. Dependabot proposes the newer pins again on its next run.
